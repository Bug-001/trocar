# asight · RFC 1.6 — 命令行界面

> **这是什么**:asight 命令行的契约:开关模型(`on` / `off` / `status` / `uninstall`)与各自的保证、命令清单、旧采集(过渡期)、跨命令规则、asight 自己坏了时怎么办、VPN 感知的 CLI 一侧、网络拓扑与诊断(§9)。
> **受众**:人(核对「我的 agent 有没有被监听」「asight 出了问题能不能一条命令关掉」是否成立)+ agent(据此改 `bin/asight.mjs` 与采集器命令)。
> **Source-decision**:**D39**(二元开关;4.6 原「注入一次、长期保持,不随开关变化」推翻)。承 D31(按进程,不碰系统代理 / 整机流量)· D36(按用户运行,sudo 只在助手)· D37④(信任入口)· D28(只剥哨兵块)· D38(失败不静默)。§9 网络拓扑与诊断 = **D39⑩**。
> **不含 → 去哪查**:采集器内部机制 → [4.6](4.6-process-collector.md);旧采集机制 → [4.1](4.1-capture-sources.md) / [4.5](4.5-distribution.md);改包命令 → [5.1](5.1-intervention.md);macOS / Windows 的引流方式与各 VPN 产品的适配 → 引流单元(以后写,见 §6)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集;`off` 撤掉 asight 对这些 agent 的全部影响,asight 坏了也能用。每个改动用户机器的命令都打印回执;改用户文件前先备份。

## 1. 开关模型

### 1.1 四个命令与各自的保证

| 命令 | 做什么 | 做完之后保证什么 |
|---|---|---|
| `asight on [harness…]` | 开始采集这些 harness;不带名字 = 本机检测到的全部。首次运行即安装(§1.6)。写信任入口([4.6](4.6-process-collector.md) §身份与信任的表),挂引流(Linux = 本实例的 link;macOS / Windows 见引流单元;没有新采集器的平台上 `on` 驱动旧采集,见 §4),启用自启并拉起守护进程。 | 之后新启动的这些 agent 被采集。`on` 之前就在跑的进程照常透传、不被弄断;`on` 的输出与 `status` 逐个点名「重启后才会被采集」,点的是真正发请求的进程(如 Codex 的 app-server 守护进程,不是用户看到的 TUI;[4.6](4.6-process-collector.md) §各 harness 的进程特征)。 |
| `asight off [harness…]` | 撤掉 asight 对这些 agent 的全部影响:引流、信任入口、VPN / 代理软件里的块。被改过的文件回到改前的样子。不带名字时另外停守护进程、停用自启(§1.4)。 | **off 保证**(§1.2)。 |
| `asight status [harness…]` | 每个 agent:正在被采集;或者没有,为什么。 | 只读。 |
| `asight uninstall [--purge-data]` | 先把全部 harness 的期望态写成 off,停用自启并停守护进程(§1.4 第 4、5 步;由 systemd 停,它不会按 `Restart=on-failure` 拉回),确认引流已摘;再对全部 harness 做 `off`,再删 asight 自己(CA、自启单元、运行目录、安装清单、备份、独立撤销程序)。采集数据默认保留。停守护进程时先摘引流,按 §1.3 关连接(HTTP 在当前响应结束时、WebSocket 在本轮终止消息处);仍开着的透传连接与看不到终止消息的 WebSocket 随守护进程退出被切断,回执写明条数。 | 本用户下零残留(例外见 [4.5](4.5-distribution.md) §C)。整机的能力助手另要一步 `sudo asight setup-helper --remove`。 |

- 没有 `restore`:关与撤是同一件事(不区分 off 与 restore:用户分不清)。
- **信任入口随开关**(推翻 [4.6](4.6-process-collector.md) 原「注入一次、长期保持,不随开关变化」):`on` 写,`off` 撤。理由:Codex、Hermes 的入口替换整个信任库(合并包);合并包坏了或被删,它们连真上游都可能连不上,所以 `off` 必须能把入口撤掉。
- **代价**:信任入口只在 agent 启动时读。`off → on` 之后,已在跑的 agent 要重启一次才被采集。这不会弄断它们:守护进程把「入口在进程启动之后才出现」判为未信任(4.6 §确认信任 `config-after-start`;「之后」按安装清单该条的 `installed_at`),未信任的进程照常透传。`installed_at` 只在 `on` 实际(重新)写入该入口时更新:入口已在、sha 等于 `post_sha256` 时,`on` MUST NOT 写这个文件、MUST NOT 改 `installed_at` 或它的 mtime;否则在跑、已被采集的进程会被判 `config-after-start`,采集静默停掉(R9)。
- **登出后停采(Linux)**:用户级 systemd 单元在该用户最后一次登出时停掉,除非开了 linger;留在 tmux / SSH 里的 agent 之后照常直连、不再被采集(fail-open)。`on` 不替用户开 linger(R8)。linger 没开时,`on` 与 `status` 各印一行「登出后停采(未开 linger)」,并给出开启命令 `loginctl enable-linger <用户名>`;读不到 linger 状态时印「不知道」加原因,不印「已开」(R11)。读法:`/var/lib/systemd/linger/<用户名>` 在不在,只读,与守护进程 `daemon-start` 事件的 `linger` 字段同一读法。守卫:test V39。

### 1.2 off 保证

**`off` 返回、且在途响应结束之后,asight 不在这些 agent 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。** 做不到这条的引流方式不提供。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 11 条),V4 / V17 落地后加测。

**例外(如实写明)**:透传(splice)连接,以及看不到终止消息的 WebSocket 连接(harness 文件没声明终止消息,或这一轮的终止消息解不出、被略去,[4.6](4.6-process-collector.md) §传输与帧级记录「看不到终止消息时」),引擎看不到响应边界,在它们自己关闭之前仍经引擎(§1.3);对这两类,保证只到「新连接直连」为止,在那之前守护进程也不退出(§1.4),除非操作者用 `asight off --now` 立即切断(§1.3)。`off` 的回执与 `status` 单列它们的条数。

下表「能否做到」「验证状态」两列是评估,待验证;保证本身与「做不到的不提供」是定下的。

| 引流方式 | 能否做到 off 保证 | 验证状态 | 结论 |
|---|---|---|---|
| 系统的按进程机制:Linux eBPF(已有);macOS Network Extension、Windows WFP / WinDivert(D31⑥) | 预计能:摘钩即可,不碰 agent。Linux 开着时另有两层 fail-open(4.6 §Linux 机制) | Linux 有实验室用例(4.6 S1、S7)。macOS、Windows 未验证;验证之前不对这两个平台作这条承诺,`status` 在那里 MUST NOT 断言「asight 已脱离路径」,只写「引流已摘(按什么读到的)」 | Linux 提供;macOS / Windows 验证后再定 |
| VPN / 代理软件里加 asight 的块 | 能,有条件:`off` 按 D28 只剥哨兵块,热重载后核对生效(D29 的做法);或块内用 fallback 组,asight 不在时退回原路由(健康检查有窗口期,如实标出) | 剥块并热重载核对:旧 Clash 块已在用(D29);fallback 组未试 | 可提供;要改 D31⑤,归引流单元 |
| asight 自带一个代理内核 | 看流量怎么进来:经系统代理或 TUN = 整机接管(违 D31④);经 agent 的代理字段 = 下一行 | — | 现下不提供:上面两种进入方式都已排除;自带内核本身不被排除,归引流单元重议 |
| 把 agent 的代理字段指向 asight | 不能:agent 只在启动时读代理设置;`off` 之后它要么继续经 asight(asight 一停就断),要么改配置再重启 | Windows 实验已见 asight 一停 agent 就断 | 不提供 |

- `off` 之后,`on` 期间启动的 agent 仍信任 asight CA,直到它重启(入口只在启动时读,4.6 §撤销顺序第 5 步)。这不影响路径:没有引流,它的连接不经 asight。回执列出这些进程(「重启前仍信任」)。

### 1.3 在途连接

`on` 期间已经经引擎中转的连接,TCP 上没法中途改道。规则:`off` 返回后,引擎在每条中转连接的**当前响应结束**时关掉它,agent 的下一个请求就直连。细节:

| 连接的状态 | 引擎怎么做 |
|---|---|
| 空闲(keep-alive,没有请求在途) | 立即关两侧 |
| 有 HTTP 请求在途(含 SSE;含 CONNECT / SOCKS / `https://` 代理隧道里解密的) | 响应按被动分帧收全、转完,再关两侧。客户端在此之前已发出下一请求的字节:照转、不记录(`off` 返回之后开始的请求零记录,4.6 §开关语义),它的响应结束后再关 |
| 透传(splice,引擎不分帧) | 看不到响应边界,等它自己关闭;`off` 的回执与 `status` 计它的条数(§1.2 例外) |
| WebSocket | 在这一轮的**终止消息**处关:终止消息按 harness 文件以数据声明的模式认([4.6](4.6-process-collector.md) §传输与帧级记录「逻辑调用怎么切」),引擎把含终止消息末帧的那块字节照转完,再按下文「怎么关」关两侧;Codex 下一轮自己重连。`off` 时没有打开的调用 = 空闲,立即关。MUST NOT 自己合成 close 帧(不往连接里写 asight 自己的字节)。harness 没声明终止消息、或这一轮看不到终止消息(同节「看不到终止消息时」):同透传,等它自己关闭、计数 |
| 被 [5.1](5.1-intervention.md) 扣留的请求或响应 | `off` 先停用规则(规则保留、不删;不带名字的 `off` 停用全部,带名字的只对这些 harness 的请求停用),把扣留队列里的条目原样放行(不改一字节,审计记 `released-by-off`),再按「有 HTTP 请求在途」处理;`off` 之后新到的请求不再匹配规则。5.1 尚未实现:本行是规则,随 5.1 一起实现,在那之前不适用 |

- **怎么关**:先把已转发的字节写完再 `end()`(发 FIN),等对端关闭,至多 5 s 后才 `destroy()`;MUST NOT 在接收缓冲里还有未读的客户端字节时直接 `destroy()`(会发 RST,客户端可能丢掉已写出、还没收到的最后一段响应)。关连接本身不改任何字节,只由操作者的 `off` 触发,不属 D30 的改包。
- **`Connection: close`**:`off` 落在一条响应还在途时,引擎 MAY 在这条(最后一条)响应上加逐跳头 `Connection: close`,客户端就不再复用这条连接,不会撞上关连接时的复位。它是逐跳头,由操作者的 `off` 引起,不算 D30 的改包,不记 `intervention`。约束:只在这条响应的头还没转给客户端时加(头已转出的,比如正在流的 SSE,加不了,照常在响应结束后关;此时客户端恰在关闭时复用这条连接会看到一次复位,靠它自己重试,[4.6](4.6-process-collector.md) S5 单独计数);只在头部结尾的空行前插入一行 `Connection: close\r\n`,原有的头逐字节不动,响应已带 `close` 时不加;体逐字节不变(`content-length` 不变)。**MUST 记账**:这次调用被记录时,信封带 `asight_added:['connection-close']`(`resp_head_raw` 仍是上游发来的原字节,4.6 §记录);不论记没记(`off` 返回之后才开始的请求不记),`flows/` 的连接行带 `asight_added:[{seq, what:'connection-close'}]`。看板 MUST 在该调用上就地标「asight 加的 · Connection: close」(不变式 4)。除这一行头之外,MUST NOT 为了让客户端断开而改写响应。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 11 条)· test V37。
- **`asight off --now`**:不等在途连接,立即切断这些 harness 仍经引擎的连接(HTTP 在途响应、WebSocket、透传都算);不带名字时守护进程随即退出。这是操作者的显式意图:被切断的 agent 看到连接错误,靠自己重试(Claude Code 对已开始输出的流不重发,4.6 §Linux 机制「fail-open 两层」)。回执写切断的条数(`relayed.cut`);每条被切断的连接在 `flows/` 留连接行,`error.type` 为 `cut-by-off`。守卫:test V36。
- `off` 的输出与 `status` 写「N 条连接仍经 asight 中转,本次响应(或本轮)结束后关闭」(HTTP 在途与等终止消息的 WebSocket);透传与看不到终止消息的 WebSocket 另计「M 条等它自己关闭(`asight off --now` 立即切断)」;读不到写「不知道」加原因。

### 1.4 不带参数的 off

不带参数的 `off` 另外停守护进程、停用自启;之后没有 asight 进程在跑。`on` 重新启用。「asight 进程」的范围与例外见本节末。顺序:

1. 把全部 harness 的期望态写成 off(`state.json`,原子写,R12)。
2. 摘引流,按内核实际态确认。守护进程不在时,确认本实例的助手已不在(link 随它摘掉,4.6 §Linux 机制)。守护进程没响应(`lock` 超过 5 s 没刷新,或控制 socket 5 s 不应答)或还在启动中(有 `lock`、socket 不应答):不等它,先按第 5 步停掉它(助手随之退出、link 摘掉),确认 link 已消失,再进第 3 步。
3. 撤信任入口与 VPN / 代理软件里的块,新旧两代都撤(§4)。
4. 停用自启。Linux:`systemctl --user disable`,删 `default.target.wants/` 链接;单元文件是 asight 自己的,留到 `uninstall`。
5. 让守护进程排空后退出:按 §1.3 关完连接即退出(干净退出,systemd 不拉回),助手随它退出。`off` 不等它,回执写明守护进程的 pid 与还剩几条;透传连接与看不到终止消息的 WebSocket 还开着时它不退出,回执写「守护进程仍在排空:pid N,还剩 M 条等它们自己关闭;`asight off --now` 立即切断」。`--now`:不排空,按 §1.3 切断后立即退出。**要停它时**(没响应、`uninstall`):由自启单元管着时用 `systemctl --user stop asight-collector`(systemd 因此不按 `Restart=on-failure` 把它拉回);单元没管它或 stop 超时:SIGTERM,10 s 不退再 SIGKILL。每次发信号前按 `lock` 的 `start_time` 与 `boot_id` 核对 pid 身份,不符不发;`lock.helper_pid` 还活着一并 SIGTERM。收尾 `systemctl --user reset-failed asight-collector`,确认单元既不是 active 也不是 activating;写一条事件。

- 用户在终端里自己起的 `asight serve`(只读看板,不在任何 agent 的路径上)、前台的 `asight capture` / `asight mitm`:`off` 不杀,回执与 `status` 列为「你自己起的 asight 进程仍在跑」。前台的 `capture` / `mitm` 可能正中转 agent 的流量(agent 的 base_url 或代理指向它们),杀掉会弄断那些 agent;它们不是 asight 装的或拉起的,off 保证不管它们。守护进程排空后退出,`--now` 不排空。

### 1.5 按 harness

- `on` / `off` / `status` 都可带 harness 名(§3);不带 = 全部(可按 harness)。
- 期望态按 harness 记。`~/.asight/collector/state.json` 升到 version 2:`{version:2, updated_at, harnesses:{<id>:{desired:'on'|'off', policy:'auto'|'all', extra_hosts:[…], updated_at}}}`(看板「采集关 · 自 T 起」的 T 取它,[4.4](4.4-server.md) `/api/capture-health`)。读到 version 1 时,把它的 `desired` / `policy` / `extra_hosts` 套到每个已安装的 harness(已安装 = 安装清单点名的 harness;从没装过的不套、也不判);读不出时全部按 off 起,并留失败事件(4.6 §开关语义)。
- Linux:任一 harness 为 on 就挂本实例的 link。期望态为 off 的 harness,其进程从内核 `watch` 表摘掉:不改写、不上报元数据;守护进程不为它们写 `agent-untrusted`(它们本就不是采集目标)。某个 harness 的实际态:有在跑的进程时逐个核对内核 `watch` 表;没有在跑的进程时 = link 已挂且它的入口完好。都不读自己记的标志(4.6 §开关语义)。
- **`off` 的次序**:每次 `off`(带不带名字)都先写期望态,再把该 harness 的进程从 `watch` 表摘掉并读内核确认(全部为 off 时确认 link 已摘;守护进程不在时确认本实例没有 link),之后才撤入口、改写合并包;确认之前 MUST NOT 动入口或合并包。反过来做,进程还在 `watch` 表里时合并包已不含 asight CA,它的新连接拿到 asight 的叶证、被拒、请求失败(Codex 每次连接重读合并包,4.6 §身份与信任)。`on` 的次序见 R9。
- 逐个 `off` 完全部 harness 时:link 已摘,不在任何 agent 的路径上,守护进程与自启仍在(空转);要停它们用不带参数的 `off`。
- 按 harness 撤时,共用文件怎么处理见 [4.6](4.6-process-collector.md) §撤销顺序「按 harness 撤」。

### 1.6 首次 on(即安装)

- 先打印计划:要改的每个文件、asight 自己要建的东西、跳过的 harness 与原因、本机网络环境(§6)、要重启的进程。终端里等确认;不在终端里(stdin 或 stdout 不是 TTY,如 agent 代为安装)没有 `--yes` 时,只打印计划、什么都不改,退出 2。
- 之后的 `on`:要改的文件比上次确认过的(清单顶层 `confirmed_paths`)多出来时(新检测到的 harness、新的 `CODEX_HOME`),只列出多出的那些,再确认。
- 回执写明开、关、看状态、卸载的命令,以及独立撤销程序的路径(装完告知开关命令)。

## 2. 命令清单

help 分四段:常用 / 数据 / 维护 / 旧采集(过渡期)。现状列:已有 / 已有需改 / 改名 / 合并。`on` `off` `status` `uninstall` 四个名字与含义由设计固定;其余命令名、旗标、别名、`doctor` 的改动见本单元。

| 命令 | 段 | 现状 | 说明 |
|---|---|---|---|
| `asight on [harness…] [--dry-run] [--yes] [--no-autostart\|--no-unit] [--json]` | 常用 | 改名 + 改义 | 原 `collector install` + `collector on`。`--no-autostart`:装单元但不 `enable`,本次只 `start`;`--no-unit` 保留原义(不装单元,测试与没有 systemd `--user` 的机器用)。D39 之前 `asight on` 指旧 CC-CLI steer,它今在 `monitor on --no-autostart`;带旧旗标 `--proxy` 时退出 2,并给出这条提示 |

## 4. 旧采集(过渡期)

- D31 过渡期:现有 base_url 反代、Clash steer、按 host 解密继续运行,新机制落地后退役。D39⑥ 让退役按平台进行:某平台的新采集器落地、并在该机验收([4.6](4.6-process-collector.md) R2 完成线)之后,才退役该平台上的旧命令。
- 旧命令 `capture` `mitm` `desktop` `monitor` `shard` 在 help 的「旧采集(过渡期)」段,每条标「过渡期」。不加新功能,只修错;退役时删除。
- 不设 `legacy` 前缀(命令要尽量少):D39 之前的 `asight on [--proxy]` / `off [--remove-ca]` 就是今天的 `monitor on --no-autostart` / `monitor off --remove-ca`,旧 steer 仍够得着。

**各平台上 `on` / `off` 指什么**(没有新采集器的平台上 `on` / `off` 驱动旧采集,不带参数的 `off` 撤掉旧采集的全部影响):

| 平台 | 新采集器 | `asight on` | `asight off`(不带参数) |
|---|---|---|---|
| Linux | 有(4.6;本机验收前旧命令仍在) | 新采集 | 新采集的全部,加上本机旧采集留下的(CC settings 的旧 steer、用户 NSS 库里的旧 CA) |
| macOS | 无 | 旧采集,即 `desktop on` 做的那些:Clash `Script.js` 哨兵块 + 热重载、`com.asight.mitm`、`com.asight.env` | 旧采集的全部影响:CC settings 的旧 steer(按暂存值还原)· Clash 块(D28 只剥哨兵块;D29 热重载并核对)· `com.asight.mitm` / `com.asight.monitor` / `com.asight.env` 三个 LaunchAgent(登录环境里 `NODE_EXTRA_CA_CERTS` 的当前值指向 asight 自己的 CA 时 `launchctl unsetenv`)· login keychain 里的旧 CA |
| Windows | 无 | 报「本平台未实现」,退出 1 | 撤上一格里本机存在的部分 |

- 在没有新采集器的平台上跑 `on` / `off`,先印一行「本平台 on / off 驱动旧采集(过渡期)」。
- 没有新采集器的平台上,带 harness 名的 `on` / `off` 只认 `claude-code`(等于不带名字);别的名字退出 2,印「本平台只有 claude-code 的旧采集,没有按 harness 的开关」,什么都不碰。`status` 把 `claude-code` 拆成 Desktop(Clash 块 + MITM)与 CLI(旧 steer)两行;CLI 没被采集时写「`on` 不做旧 steer;要采集 CLI 用 `monitor on`」。
- `com.asight.env` 随旧采集整体关闭一起撤:`asight off`、`asight uninstall`、`desktop off`(改 [0.0](0.0-overview.md) §过渡期遗留)。旧采集开着时仍 MUST NOT 单独移除它(会停掉 macOS 上 Desktop 的采集)。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 4 条);V12 的 `off codex` 用例落地后加测。
- 旧 CC-CLI steer(`HTTPS_PROXY` 指向本地端口)就是「把 agent 的代理字段指向 asight」,做不到 off 保证,`on` 不做它;仍可经 `monitor on` 用。`off` 照撤它,并列出 steer 生效期间启动、仍在跑的 claude 进程:它们重启前仍连那个端口。
- 旧 MITM 达到 off 保证的条件:先剥 Clash 块、热重载并核对生效(新连接不再进 MITM),再向 MITM 发 SIGTERM:它停止接受新连接,等在途连接自己结束(旧 MITM 不跟踪响应边界,不按 §1.3 逐响应关),至多 10 s;之后卸 `com.asight.mitm`,余下的连接随之切断,回执写条数。现代码(`desktop off`)剥块后立即卸载,经它的在途连接被切断:这是缺陷,实现时修。
- `on` / `off` 驱动旧机制时同样守 §5 的规则:回执、改前备份、入账。账记在 `~/.asight/legacy-manifest.json`(格式同采集器的安装清单;不放进 `~/.asight/collector/`,免得看板以为装了新采集器)。旧命令自己(`desktop on` 等)保持原样。旧命令装的东西(`desktop on`、`monitor on` 写的 Clash 哨兵块、`com.asight.*` plist、CC settings 的暂存文件)不在这本账里:它们自己的标记就是它们的账,`off` 直接按标记撤,不走 R3 的按标记撤销确认;这些改动没有改前备份,`status` 与回执标「旧命令装的,无备份」。旧命令保持原样、不补账;经 `on` 装的(含 macOS 上做 `desktop on` 那些事的 `on`)都入账、有备份。所以 §6「VPN / 代理软件里的改动都入账」过渡期只对经 `on` 写的成立。
- **网页开关([4.4](4.4-server.md) · D26)在过渡期**:没有新采集器的平台上,`POST /control/monitoring {action:'off'}` 改为调不带参数的 `asight off`(两代都撤,回执与退出语义同 CLI),不再只调 `atraceOff`。网页的「开」过渡期不变(仍是 `atraceOn` 加 `com.asight.monitor`,即旧 `monitor on`);有新采集器的平台上两个端点都不变,网页的「关」就地标「只管旧 CC-CLI steer,不等于 `asight off`」,直到 [4.4](4.4-server.md) 的按用户隔离落地后改接新的 `on` / `off`。守卫:test V40。
- 作者的 Mac 跑的是旧采集,会话可能正被它采集。`off`(不带参数,或带 `claude-code`)、`uninstall`、`desktop off`、`monitor off` 都会停掉这台 Mac 上的采集:agent 未经用户同意 MUST NOT 跑它们。必拒 · 审查([0.1](0.1-engineering-rules.md) §5「未经同意…」一行 + §6 第 11 条)。
- v0 的残留(`com.atrace.serve`、`~/.local/share/atrace`、`.atrace-bak`)只报告、不碰;不建议、不调用 `atrace-uninstall`。

| R9 | **幂等、可续。** 同一命令连跑两次无副作用:入口已在、sha 等于 `post_sha256` 时 `on` 不写它、不改 `installed_at`(§1.1)。`on` 的次序:被入口指到的文件(合并包、插件、shim)先于入口,挂引流最后;崩在任一步都不得留下指向缺失文件的入口。装到一半续装:按 `pre/post_sha256` 逐项判,已完成的跳过、未开始的补做、被用户改过的报告并跳过(现代码拒绝上次没装完的,要改)。撤到一半续撤。 | MUST · test V21 |
| R10 | **help 与分派一致。** help 列出的命令集合 == 代码分派的命令集合;隐藏别名另成一张表,测试一并核对。现在 help 缺 `monitor` `shard` `collector` `setup-helper`,未知命令打印用法后退出 0。 | SHOULD · test V19 |
| R11 | **不静默(D38)。** 每次状态变化、每个失败都写 `flows/` 事件;旧采集写它原来的日志。写不进时先 stderr,恢复后第一条是 `log-gap`。读不到的报「不知道」加原因,不报 0 或「无」。 | MUST · 审查([0.1](0.1-engineering-rules.md) §6 第 10 条)· test V10 |
| R12 | **同一时刻只有一个改状态的命令。** 持 `~/.asight/collector/op.lock`(O_EXCL 写 `{pid, start_time}`;陈旧锁按 pid 加启动时间判)。`state.json` 与清单一律写临时文件、fsync、rename、fsync 目录。`off` 优先:拿不到锁时先原子写这些 harness 的 `desired:'off'`,再等锁至多 10 s;`on` 每写一个文件、每挂一次引流之前 MUST 重读 `state.json`,见到 off 即停、退出 1。别的系统用户各有自己的 `~/.asight`,互不影响。 | MUST · test V34 |

**asight 自己坏了时**(R3 的细化):

| 坏在哪 | 怎么办 |
|---|---|
| 守护进程不在 | `off` / `uninstall` / `status` 照常(`status` 读盘);`on` 拉起它,拉不起报原因、退出 1 |
| 守护进程卡死或还在启动中 | 新连接已因心跳过期直连(4.6 §Linux 机制)。`off`(带不带名字)与 `uninstall` 都先按 §1.4 第 5 步停掉它(它已卡死,别的 harness 本就没在被采集,回执写明),确认 link 已消失,再撤入口;停不掉时照样撤入口,退出 1,回执给 pid 与手动停止的命令(它恢复后先重读 `state.json` 再发心跳,4.6 §开关语义)。 |
| 助手缺失或版本不对 | `on` 什么都不挂,提示 `sudo asight setup-helper`(4.6 OPEN「助手与守护进程版本不一致」);`off` 不受影响 |
| 清单坏了或丢了 | R3 的按标记撤销(引流照摘,只有改文件那一步要确认) |
| 两条命令同时跑 | R12 的锁;`off` 优先 |
| 用户改过入口 | 只撤 asight 的部分,报「已撤销,但不逐字节相同」,备份留着(R2) |
| 哨兵被改坏 | 不动这个文件,`ok:false`、退出 1,给备份路径与手动 `cp` 命令,说明会丢掉什么 |
| 源码目录没了 / 缺 `node_modules` | 用 `~/.asight/bin/asight-off`;`status` / `doctor` 报「PATH 上的 asight 指向的文件不存在」 |
| 没有 node | 按清单的 `undo_by_hand` 手动撤 |
| `~/.asight` 写不进(磁盘满) | 备份写不进就不改用户文件(R2);日志写不进按 R11 |
| 本平台没有新采集器 | `on` / `off` 驱动旧采集(§4);`daemon` 报「本平台未实现」、退出 1 |

## 6. VPN 感知(CLI 一侧)

机器上装了 VPN 软件,asight 要自动感知,在 CLI 和界面里显示它改了什么地方;力求所有改动可追踪、可撤销。1.6 只定 CLI 一侧的四条要求:

- **探测**:`status`、`doctor`、首次 `on` 探测本机的代理 / VPN 软件:哪个产品、什么模式(规则 / 全局 / TUN / 系统代理)、每个 harness 的流量是否经过它。只读;不读也不印密钥、订阅地址、节点信息。认不出 → 「不知道」加原因,MUST NOT 报「无」。探测结果写 `~/.asight/netenv.json`(0600;只含产品、模式、各 harness 是否经过,不含密钥、订阅地址、节点;不放进 `~/.asight/collector/`,没有新采集器的平台也写)。首版 `src/netenv/` 只认 Clash Verge / mihomo(旧 steer 已在读它),其余报「不知道」加原因;各产品的适配归引流单元。守卫:test V22(计划)。
- **入账**:asight 在 VPN / 代理软件里的每一处改动,和 agent 文件的改动一样记账:安装清单一条、改前备份(R2)、回执一行(R1)、`status` 列出、`off` 撤掉;块用 D28 的哨兵块语义(只剥块、块外一字不动、剥不掉报 `ok:false`)。旧采集的 Clash 块经 `on` 写时同样入账(§4)。守卫:test V23(计划)。
- **核对生效**:`status` 与 `off` 对 VPN / 代理软件里的块 MUST 读它实际生效的运行时配置(D29 的做法:经该软件的控制接口读),不只看文件或清单。`off` 即使文件里已没有块也 MUST 热重载并核对,不走「早已还原」的跳过(运行时可能仍留着块:D29 记过重新生成时写进运行时配置的那份);核对不了报「不知道」加原因(`off` 退出 1,`status` 退出 3)。块被 VPN 软件改写或抹掉:`status` 报「块被 <产品> 改动」。守卫:test V23(计划)。
- **看板**:同样的内容显示在「本机网络环境」卡片上,经 [4.4](4.4-server.md) 只读数据面(`/api/capture-health` 的 `netenv` 字段)读 `~/.asight/netenv.json` 与清单(卡片属 D31⑧ 的设置面板,UI 单元待写)。

**前向引用**:各产品的探测与适配清单、D31⑤「不依赖、不修改用户的 VPN 软件」的修订,写在引流单元里(依据 VPN 调研综合与 Windows 实验室)。引流单元加任何 VPN 写入时 MUST 满足上面四条。

## 9. 网络拓扑与诊断

**来源**(D39⑩):每个 agent harness 的网络情况各画一个简单的拓扑结构,让用户看清数据的流动;把不同情况说清楚,也顺畅适应改 agent 网络配置(例如挂自己的 proxy)的需要,一目了然、容易配置,这些后面会进到 GUI 里。agent 不能正常工作或网络不同时,`asight doctor` 要给出明确的、可执行的指令。另外几条 —— 出口不变;用户直接改了 agent 的代理,asight 能发现,`status` 画出新的流向并给出接上的命令;asight 不悄悄覆盖用户的设置。产品设计取决于用户的具体需求,给出的命令只是例子,不固化成 subcommand。命令面、画法、`--json` 形状、发现目录与码见本单元。

本节跨平台。各引流方式的具体形状见 §9.8。

### 9.1 在哪看(不加新命令)

| 命令 | 给什么 |
|---|---|
| `asight status` | 表格之后一段「各 harness 的路」:每个 harness 一行紧凑链;分 HTTP 与 WebSocket 走不同路的,每支一行 |
| `asight status <harness…>` | 另给每个点名的 harness 画详细拓扑:每跳一行;另加「关掉 asight 时的路」「要换代理」两行 |
| `asight doctor [harness…]` | 发现(§9.6):每条写什么、为什么、要跑的命令、怎么验证 |
| `--json` | 同一份 `topology` 对象(§9.4);看板经 `/api/capture-health` 的 `netenv.topology` 读同一份 |

- 不设 `asight net`、`asight proxy`(§8)。理由:拓扑回答的正是 `status` 那一问的「为什么」;多一个动词,用户多记一个,两处输出还会分叉。
- `doctor` 新收 harness 名(规则同 §3):用户的症状是按 agent 说的,如「codex 连不上」。

### 9.2 画法

- **一条链** = 从 agent 进程到出口的每一跳,用 `→` 连。节点写具体的东西:进程(名、pid、版本)、地址与端口、产品与版本、模式(规则 / 全局 / 直连 / TUN / 系统代理)。边写怎么过去(方括号:`[eBPF]` `[系统代理]` `[HTTPS_PROXY]` `[TUN]` `[asight 块]`)。asight 自己的节点标「asight」。
- **画新连接的路**:按 agent 现在的设置(它会读的环境变量、配置文件里的代理键、它认的系统代理)和本机网络环境算。代理设置只在 agent 启动时读;在跑的进程启动时的设置与现在不同时,另列一行「pid N 仍按启动时的设置:<链>;重启后按上面的路」。
- **关掉 asight 时的路**:同样的设置,去掉 asight 的跳。`status <harness>` 印它。asight 在路径上时,asight 之后的第一跳 MUST 等于这条链里 agent 之后的第一跳(出口不变,§9.5);不等时报 `egress-differs`。
- **读不到**:那一跳写「不知道 · <原因>」(原因是闭集,§9.4),不省略这一跳,不写「无」(R11)。按别的平台实测推断的,标「推断」。
- **判词**:每个 harness 末尾写两件事:asight 在不在路径上(是 / 否 / 不知道);被采集没有(是 / 否 + 原因码,§9.6)。只有「被采集」本身不知道时,`status` 才退出 3;单跳不知道不改退出码。
- **永远不印**:代理 URL 里的用户名与密码(印成 `***@`)、VPN 的 secret、订阅地址、节点名。出口只写「由 <产品> 选」或「直连」。

| 字段 | 闭集 / 规则 |
|---|---|
| `routing` | `ebpf` · `vpn-block` · `own-forwarder` · `legacy` · `none`(全部关着)· `unknown` |
| `nodes[].kind` | `agent` · `proxy`(用户的代理或 VPN 的本地入口)· `asight-engine` · `asight-forwarder` · `legacy-mitm` · `upstream`(API 或中转 host)· `egress` · `unknown` |
| `edges[].via` | `direct` · `proxy-http` · `proxy-socks` · `proxy-https` · `system-proxy` · `tun` · `ebpf` · `vpn-rule`(asight 块;带 `rule`)· `forward` · `egress` · `unknown` |

| `branches[].name` | `all` · `http` · `ws`(按 harness 文件声明的分支) |

- 文本只从这个对象渲染,不另算(V43)。键名与闭集放 `src/cli/schema.mjs`(R5)。`status --json` 带 `topology`;`doctor --json` 带 `findings`(§9.6)。

### 9.5 用户自己的代理

用户的要求:自己的代理照常工作、出口不变;换代理的过程要顺;asight 不悄悄覆盖用户的设置;不为此固化一个子命令。下表是做法:

| 规则 | 内容 |
|---|---|
| 唯一来源 | 「用户的代理」= agent 自己会用的那个:它读的环境变量、配置文件里的代理键、它认的系统代理。读哪些由 harness 文件声明(§9.7)。asight 没有另一处记它,用户不用告诉 asight 两遍。 |
| 接上 | `on <harness>` 读该 harness 现在的网络设置,把 asight 接在 agent 与它原本的下一跳之间;asight 的上游 = 那个下一跳(用户的代理、VPN 或 API host)。eBPF:不写任何网络设置,引擎按原目的地转,CONNECT / SOCKS 原样转给用户的代理(4.6 §引擎 第 3 步)。VPN 块:不写 agent 的设置,块豁免 asight 自己,上游回到同一个 VPN(4.8)。自带转发:把 agent 的代理字段改指转发,原值记为该 harness 的上游(4.8)。计划与回执各印一行接上后的链,凭据打码。 |
| 记下接上的是什么 | `on` 在 `~/.asight/netenv.json` 写 `adopted.<harness> = {at, routing, chain, source:[{kind:'env'\|'file'\|'system-proxy', where}], sha256}`。`chain` 是打码后的紧凑链;`sha256` 是原始设置值的哈希,不存原值(原值里可能有密码)。 |
| 发现漂移 | `status`、`doctor` 和守护进程用同一读法重读设置,与 `adopted` 比。守护进程在 4.6 §开关语义的 5 s 核对里一起做,先比这些文件的 inode / 大小 / mtime。设置不同 = `proxy-changed`;本机网络环境变了(VPN 从系统代理改 TUN、退出、升级、新装)= `netenv-changed`。各写一条 `netenv-change` 事件;让期望为开的 harness 采不到时,另写一条 `failure`(§9.7)。没有守护进程的平台上,由 `status` / `doctor` 与上次的 `netenv.json` 比。 |
| 漂移之后 | `status` 画出新的路,说清 asight 还在不在路径上,印那一条接上的命令(已有命令)。eBPF:新进程照常被采,不用做什么,只列「在跑的 pid N 仍按旧设置,重启后按新的」。VPN 块:新代理不经那个 VPN 时报 `not-routed`,步骤见 `doctor`。自带转发:agent 已绕过 asight,印 `asight on <harness>`。 |
| 不悄悄覆盖 | 只有操作者跑的 `on` 会写 agent 的网络设置。`status`、`doctor`、守护进程只读、只报,MUST NOT 改回。`on` 要改写用户在上次 `on` 之后改过的网络设置时,像 §1.6「多出来的文件」一样列进计划、再确认(R6);不在终端又没有 `--yes`:只打印计划,退出 2,什么都不写。 |
| `off` 留下用户的设置 | `off` 只撤 asight 写的值(R2「只撤 asight 的部分」):字段仍是 asight 的值,就回到接上时的原值;用户之后改过,就不动,回执写「你改过,没动」。eBPF 与 VPN 块下 `off` 不碰任何网络设置。 |
| 不加命令 | 换代理 = 照常改 agent 的设置(或 VPN),需要时再 `on <harness>`。没有 `asight proxy`。以后真有「不改 agent 设置、只换 asight 的上游」的需要,再进 Extensions,并写明是什么需要。 |

### 9.6 `doctor` 的发现

每条发现:`{code, class, harness?, what, why, commands:[{run, shell}], verify}`。`class` ∈ 失败(让看板指示变 ⚠,同 D38)· 预期 · 提示。`shell` ∈ `sh` · `powershell` · `gui`(界面操作,写菜单路径)。

- 先给 asight 命令,再给应用或 OS 里的步骤。命令是填好值、可直接复制的整行:pid、端口、路径都填上。某个值读不到时,写「不知道 · 原因」,并给出读它的命令;不留 `<占位符>`。
- `doctor` 只读(V50),一条也不替用户执行(R8)。
- `doctor <harness>` 只报该 harness 的;不带名字报全部,再加本机的。
- agent 连不上、又找不到具体原因时,报 `cause-unknown`,第一条命令是 `asight off <harness>`:off 保证(§1.2)之后 asight 不在它的路径上,再试仍连不上,就与 asight 无关。

下表命令列里的 `<h>` `<pid>` `<端口>` `<用户名>` 是目录里的写法,输出时填成真值。

### 9.7 闭集与数据(D38)

- `where` 加 `netenv`(与 4.7 共用)。
- 事件加 `netenv-change`,状态类:`{event:'netenv-change', where:'netenv', harness?, code, from, to}`;`from` / `to` 是打码后的紧凑链。
- `code` 加一组 `net`:`not-routed` `proxy-changed` `proxy-dead` `proxy-unsupported` `netenv-changed` `elevated-agent` `forwarder-down` `egress-differs` `linger-off` `system-proxy-pac` `other-redirector` `fake-ip` `inferred-behaviour` `cause-unknown`。与 4.7 共用的 `clash-mode-bypass` `route-loop` `vpn-block-*`,由先落地的一方加,只定义一次。
- 写成 `failure` 事件(`where:'netenv'`)的:`not-routed` `proxy-dead` `proxy-unsupported` `elevated-agent` `forwarder-down` `route-loop` `clash-mode-bypass`,以及让期望为开的 harness 采不到的 `proxy-changed` / `netenv-changed`。其余只进 `status` / `doctor`。
- `status` 的原因闭集(§2;4.6 §记录)加 `not-routed` `proxy-changed` `elevated-agent` `forwarder-down` `clash-mode-bypass` `route-loop`。
- 名字放 `src/health/codes.mjs` 单独一块(`NET_WHERE` · `NET_EVENTS` · `NET_CODES` · `NET_FAILURE_CODES`),放法同 `OFF_*`:不碰 D40 在改的三张表。
- harness 文件加一项 `proxy`(数据;D37①):读哪些环境变量键、哪些配置文件键;读不读系统代理(分 HTTP 与 WebSocket);支持哪些代理协议;不支持时怎样(静默直连 / 连不上);本平台是实测还是推断;怎么退出与重启。格式以 4.7 为准;1.6 只要求这些字段在。

## 验收(可跑 check)

单元测试走 `npm test`,在 `mkdtemp` 沙箱 HOME 里跑,信任库、`launchctl`、`systemctl`、进程管理器都注入(0.1 §3「不碰真实机器」);标 [VM] 的在测试机上跑。下列各条现在都是**计划**:本单元刚写,命令还没按它实现;每条在实现 PR 里落成会变红的断言。

1. **V1 守护进程不在时 off**:`on` 后杀掉守护进程,再 `off`:每个入口回到 `pre_sha256`(用户改过的报「已撤销,但不逐字节相同」),退出 0,全程没有拉起守护进程。
2. **V2 独立撤销程序**:把源码目录挪走,`~/.asight/bin/asight-off` 撤净同样的入口,输出与 `asight off` 一致。
3. **V3 回执 == 实际改动**:回执(与 `--json`)列出的文件集合 == 实际被写的文件集合(并入 4.6 T10)。
4. **V4 [VM] off 保证**:`off` 返回、在途响应结束后 `kill -9` 守护进程:受管 agent 的新连接零失败,看到上游真实证书;`bpftool link` 里没有本实例的 link。
