# asight · RFC 1.6 — 命令行界面

> **这是什么**:asight 命令行的契约:开关模型(`on` / `off` / `status` / `uninstall`)与各自的保证、命令清单、旧采集(过渡期)、跨命令规则、asight 自己坏了时怎么办、VPN 感知的 CLI 一侧。
> **受众**:人(核对「我的 agent 有没有被监听」「asight 出了问题能不能一条命令关掉」是否成立)+ agent(据此改 `bin/asight.mjs` 与采集器命令)。
> **Source-decision**:**D39**(二元开关;4.6 原「注入一次、长期保持,不随开关变化」推翻)。承 D31(按进程,不碰系统代理 / 整机流量)· D36(按用户运行,sudo 只在助手)· D37④(信任入口)· D28(只剥哨兵块)· D38(失败不静默)。
> **不含 → 去哪查**:采集器内部机制 → [4.6](4.6-process-collector.md);旧采集机制 → [4.1](4.1-capture-sources.md) / [4.5](4.5-distribution.md);改包命令 → [5.1](5.1-intervention.md);macOS / Windows 的引流方式与各 VPN 产品的适配 → 引流单元(以后写,见 §6)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集;`off` 撤掉 asight 对这些 agent 的全部影响,asight 坏了也能用。每个改动用户机器的命令都打印回执;改用户文件前先备份。

## 1. 开关模型

### 1.1 四个命令与各自的保证

| 命令 | 做什么 | 做完之后保证什么 |
|---|---|---|
| `asight on [harness…]` | 开始采集这些 harness;不带名字 = 本机检测到的全部。首次运行即安装(§1.6)。写信任入口([4.6](4.6-process-collector.md) §身份与信任的表),挂引流(Linux = 本实例的 link;macOS / Windows 见引流单元;没有新采集器的平台上 `on` 驱动旧采集,见 §4),启用自启并拉起守护进程。 | 之后新启动的这些 agent 被采集。`on` 之前就在跑的进程照常透传、不被弄断;`on` 的输出与 `status` 逐个点名「重启后才会被采集」,点的是真正发请求的进程(如 Codex 的 app-server 守护进程,不是用户看到的 TUI;[4.6](4.6-process-collector.md) §各 harness 的进程特征)。 |
| `asight off [harness…]` | 撤掉 asight 对这些 agent 的全部影响:引流、信任入口、VPN / 代理软件里的块。被改过的文件回到改前的样子。不带名字时另外停守护进程、停用自启(§1.4)。 | **off 保证**(§1.2)。 |
| `asight status [harness…]` | 每个 agent:正在被采集;或者没有,为什么。 | 只读。 |
| `asight uninstall [--purge-data]` | 先把全部 harness 的期望态写成 off,停用自启并停守护进程(§1.4 第 4、5 步;由 systemd 停,它不会按 `Restart=on-failure` 拉回),确认引流已摘;再对全部 harness 做 `off`,再删 asight 自己(CA、自启单元、运行目录、安装清单、备份、独立撤销程序)。采集数据默认保留。停守护进程时先摘引流、等 HTTP 在途响应结束(§1.3);仍开着的 WebSocket 与透传连接随守护进程退出被切断,回执写明条数。 | 本用户下零残留(例外见 [4.5](4.5-distribution.md) §C)。整机的能力助手另要一步 `sudo asight setup-helper --remove`。 |

- 没有 `restore`:关与撤是同一件事(不区分 off 与 restore:用户分不清)。
- **信任入口随开关**(推翻 [4.6](4.6-process-collector.md) 原「注入一次、长期保持,不随开关变化」):`on` 写,`off` 撤。理由:Codex、Hermes 的入口替换整个信任库(合并包);合并包坏了或被删,它们连真上游都可能连不上,所以 `off` 必须能把入口撤掉。
- **代价**:信任入口只在 agent 启动时读。`off → on` 之后,已在跑的 agent 要重启一次才被采集。这不会弄断它们:守护进程把「入口在进程启动之后才出现」判为未信任(4.6 §确认信任 `config-after-start`;「之后」按安装清单该条的 `installed_at`),未信任的进程照常透传。`installed_at` 只在 `on` 实际(重新)写入该入口时更新:入口已在、sha 等于 `post_sha256` 时,`on` MUST NOT 写这个文件、MUST NOT 改 `installed_at` 或它的 mtime;否则在跑、已被采集的进程会被判 `config-after-start`,采集静默停掉(R9)。

### 1.2 off 保证

**`off` 返回、且在途响应结束之后,asight 不在这些 agent 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。** 做不到这条的引流方式不提供。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 11 条),V4 / V17 落地后加测。

**例外(如实写明)**:透传(splice)与 WebSocket 连接,引擎看不到响应边界,在它们自己关闭之前仍经引擎(§1.3、文末 OPEN);对这两类,保证只到「新连接直连」为止,在那之前守护进程也不退出(§1.4)。`off` 的回执与 `status` 单列它们的条数。

下表「能否做到」「验证状态」两列是评估,待验证;保证本身与「做不到的不提供」是定下的。

| 引流方式 | 能否做到 off 保证 | 验证状态 | 结论 |
|---|---|---|---|
| 系统的按进程机制:Linux eBPF(已有);macOS Network Extension、Windows WFP / WinDivert(D31⑥) | 预计能:摘钩即可,不碰 agent。Linux 开着时另有两层 fail-open(4.6 §Linux 机制) | Linux 有实验室用例(4.6 S1、S7)。macOS、Windows 未验证;验证之前不对这两个平台作这条承诺,`status` 在那里 MUST NOT 断言「asight 已脱离路径」,只写「引流已摘(按什么读到的)」 | Linux 提供;macOS / Windows 验证后再定 |
| VPN / 代理软件里加 asight 的块 | 能,有条件:`off` 按 D28 只剥哨兵块,热重载后核对生效(D29 的做法);或块内用 fallback 组,asight 不在时退回原路由(健康检查有窗口期,如实标出) | 剥块并热重载核对:旧 Clash 块已在用(D29);fallback 组未试 | 可提供;要改 D31⑤,归引流单元 |
| asight 自带一个代理内核 | 看流量怎么进来:经系统代理或 TUN = 整机接管(违 D31④);经 agent 的代理字段 = 下一行 | — | 现下不提供:上面两种进入方式都已排除;自带内核本身不被排除,归引流单元重议 |
| 把 agent 的代理字段指向 asight | 不能:agent 只在启动时读代理设置;`off` 之后它要么继续经 asight(asight 一停就断),要么改配置再重启 | Windows 实验已见 asight 一停 agent 就断 | 不提供 |

- `off` 之后,`on` 期间启动的 agent 仍信任 asight CA,直到它重启(入口只在启动时读,4.6 §撤销顺序第 5 步)。这不影响路径:没有引流,它的连接不经 asight。回执列出这些进程(「重启前仍信任」)。

### 1.3 在途连接

`on` 期间已经经引擎中转的连接,TCP 上没法中途改道。规则:`off` 返回后,引擎在每条中转连接的**当前响应结束**时关掉它,agent 的下一个请求就直连。细节:

| 连接的状态 | 引擎怎么做 |
|---|---|
| 空闲(keep-alive,没有请求在途) | 立即关两侧 |
| 有 HTTP 请求在途(含 SSE;含 CONNECT / SOCKS / `https://` 代理隧道里解密的) | 响应按被动分帧收全、转完,再关两侧。客户端在此之前已发出下一请求的字节:照转、不记录(`off` 返回之后开始的请求零记录,4.6 §开关语义),它的响应结束后再关 |
| 透传(splice,引擎不分帧) | 看不到响应边界,等它自己关闭(§1.2 例外) |
| WebSocket | **OPEN**(见文末);定之前等它自己关闭 |
| 被 [5.1](5.1-intervention.md) 扣留的请求或响应 | **OPEN**(见文末);5.1 尚未实现,落地时一并定 |

- **怎么关**:先把已转发的字节写完再 `end()`(发 FIN),等对端关闭,至多 5 s 后才 `destroy()`;MUST NOT 在接收缓冲里还有未读的客户端字节时直接 `destroy()`(会发 RST,客户端可能丢掉已写出、还没收到的最后一段响应)。关连接不改任何字节,只由操作者的 `off` 触发,不属 D30 的改包。
- MUST NOT 为了让客户端主动断开而改写响应(比如加 `Connection: close`;它算不算 D30 的改包,见文末 OPEN,定之前不改)。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 11 条)。已知代价:客户端恰在关闭时复用这条连接发下一请求,会看到一次连接复位,靠它自己重试。
- `off` 的输出与 `status` 写「N 条连接仍经 asight 中转,当前响应结束后关闭」;透传与 WebSocket 另计「M 条等它自己关闭」;读不到写「不知道」加原因。

### 1.4 不带参数的 off

不带参数的 `off` 另外停守护进程、停用自启;之后没有 asight 进程在跑。`on` 重新启用。「asight 进程」的范围与例外见本节末与文末 OPEN。顺序:

1. 把全部 harness 的期望态写成 off(`state.json`,原子写,R12)。
2. 摘引流,按内核实际态确认。守护进程不在时,确认本实例的助手已不在(link 随它摘掉,4.6 §Linux 机制)。守护进程没响应(`lock` 超过 5 s 没刷新,或控制 socket 5 s 不应答)或还在启动中(有 `lock`、socket 不应答):不等它,先按第 5 步停掉它(助手随之退出、link 摘掉),确认 link 已消失,再进第 3 步。
3. 撤信任入口与 VPN / 代理软件里的块,新旧两代都撤(§4)。
4. 停用自启。Linux:`systemctl --user disable`,删 `default.target.wants/` 链接;单元文件是 asight 自己的,留到 `uninstall`。
5. 让守护进程排空后退出:按 §1.3 关完连接即退出(干净退出,systemd 不拉回),助手随它退出。`off` 不等它,回执写明守护进程的 pid 与还剩几条;透传与 WebSocket 连接还开着时它不退出,回执写「守护进程仍在排空:pid N,还剩 M 条等它们自己关闭」(要不要给一个立即切断的选项,见文末 OPEN)。**要停它时**(没响应、`uninstall`):由自启单元管着时用 `systemctl --user stop asight-collector`(systemd 因此不按 `Restart=on-failure` 把它拉回);单元没管它或 stop 超时:SIGTERM,10 s 不退再 SIGKILL。每次发信号前按 `lock` 的 `start_time` 与 `boot_id` 核对 pid 身份,不符不发;`lock.helper_pid` 还活着一并 SIGTERM。收尾 `systemctl --user reset-failed asight-collector`,确认单元既不是 active 也不是 activating;写一条事件。

- 用户在终端里自己起的 `asight serve`(只读看板,不在任何 agent 的路径上)、前台的 `asight capture` / `asight mitm`:`off` 不杀,回执与 `status` 列为「你自己起的 asight 进程仍在跑」。前台的 `capture` / `mitm` 可能正中转 agent 的流量(agent 的 base_url 或代理指向它们),杀掉会弄断那些 agent;它们不是 asight 装的或拉起的,off 保证不管它们。

### 1.5 按 harness

- `on` / `off` / `status` 都可带 harness 名(§3);不带 = 全部(可按 harness)。
- 期望态按 harness 记。`~/.asight/collector/state.json` 升到 version 2:`{version:2, updated_at, harnesses:{<id>:{desired:'on'|'off', policy:'auto'|'all', extra_hosts:[…], updated_at}}}`(看板「采集关 · 自 T 起」的 T 取它,[4.4](4.4-server.md) `/api/capture-health`)。读到 version 1 时,把它的 `desired` / `policy` / `extra_hosts` 套到每个已安装的 harness;读不出时全部按 off 起,并留失败事件(4.6 §开关语义)。
- Linux:任一 harness 为 on 就挂本实例的 link。期望态为 off 的 harness,其进程从内核 `watch` 表摘掉:不改写、不上报元数据;守护进程不为它们写 `agent-untrusted`(它们本就不是采集目标)。某个 harness 的实际态:有在跑的进程时逐个核对内核 `watch` 表;没有在跑的进程时 = link 已挂且它的入口完好。都不读自己记的标志(4.6 §开关语义)。
- **`off` 的次序**:每次 `off`(带不带名字)都先写期望态,再把该 harness 的进程从 `watch` 表摘掉并读内核确认(全部为 off 时确认 link 已摘;守护进程不在时确认本实例没有 link),之后才撤入口、改写合并包;确认之前 MUST NOT 动入口或合并包。反过来做,进程还在 `watch` 表里时合并包已不含 asight CA,它的新连接拿到 asight 的叶证、被拒、请求失败(Codex 每次连接重读合并包,4.6 §身份与信任)。`on` 的次序见 R9。
- 逐个 `off` 完全部 harness 时:link 已摘,不在任何 agent 的路径上,守护进程与自启仍在(空转);要停它们用不带参数的 `off`。
- 按 harness 撤时,共用文件怎么处理见 [4.6](4.6-process-collector.md) §撤销顺序「按 harness 撤」。

### 1.6 首次 on(即安装)

- 先打印计划:要改的每个文件、asight 自己要建的东西、跳过的 harness 与原因、本机网络环境(§6)、要重启的进程。终端里等确认;不在终端里(stdin 或 stdout 不是 TTY,如 agent 代为安装)没有 `--yes` 时,只打印计划、什么都不改,退出 2。
- 之后的 `on`:要改的文件比上次确认过的(清单顶层 `confirmed_paths`)多出来时(新检测到的 harness、新的 `CODEX_HOME`),只列出多出的那些,再确认。
- 回执写明开、关、看状态、卸载的命令,以及独立撤销程序的路径(装完告知开关命令)。

## 2. 命令清单

help 分四段:常用 / 数据 / 维护 / 旧采集(过渡期)。现状列:已有 / 已有需改 / 改名 / 合并。`on` `off` `status` `uninstall` 四个名字与含义由设计固定;其余命令名、旗标、别名、`doctor` 的改动见本单元。

| 命令 | 段 | 现状 | 说明 |
|---|---|---|---|
| `asight on [harness…] [--dry-run] [--yes] [--no-autostart\|--no-unit] [--json]` | 常用 | 改名 + 改义 | 原 `collector install` + `collector on`。`--no-autostart`:装单元但不 `enable`,本次只 `start`;`--no-unit` 保留原义(不装单元,测试与没有 systemd `--user` 的机器用)。D39 之前 `asight on` 指旧 CC-CLI steer,它今在 `monitor on --no-autostart`;带旧旗标 `--proxy` 时退出 2,并给出这条提示 |
| `asight off [harness…] [--dry-run] [--yes] [--json]` | 常用 | 改名 + 改义 | 原 `collector off`;两代都撤。`--yes` 只在清单丢失、按标记撤销时用(R3)。旧旗标 `--remove-ca` 照收(`off` 本来就撤旧 CA),提示一次 |
| `asight status [harness…] [--json]` | 常用 | 改名 | 原 `collector status`,吸收 `desktop status`、`monitor status`。按 harness 列:期望态与实际态、引流方式、信任入口完好否、在跑进程(已信任 / 未信任及原因 / 要重启)、仍经 asight 的连接数、负缓存、最近 24 h 的失败(D38⑦)、守护进程与助手的健康、本机网络环境(§6)、旧采集留下的东西 |
| `asight uninstall [--purge-data] [--dry-run] [--yes] [--json]` | 常用 | 合并 | 旧 `uninstall` 与 `collector uninstall` 合成一个。旧的只撤一半(不撤 `com.asight.monitor`、CA 文件与采集器;登录环境变量只打印一句 `launchctl unsetenv` 提示),要补全 |
| `asight doctor [--source F\|DIR] [--json]` | 常用 | 已有需改 | 并入 `verify`。零条记录 = 无法判定(退出 3),不是过:什么也没核到时报「过」,会让人以为采集文件的权限已经核过(0.1 §3「测试必须能变红」同理);失败文案改为「采集文件可被他人读取」(现在印「credential leak」,`bin/asight.mjs`) |
| `asight serve …` · `asight etl …` · `asight raw export\|journal …` | 数据 | 已有 | 参数不变 |
| `asight raw seal\|verify\|compare …` | 维护 | 已有 | 参数不变 |
| `sudo asight setup-helper [--binary P] [--remove]` | 维护 | 已有 | 唯一要 sudo 的命令 |
| `asight daemon` | 维护 | 改名 | 原 `collector start`:前台跑守护进程,自启单元跑的就是它 |
| `asight help [命令]` · `--help` · `-h` · `--version` · `-v` | — | 已有需改 | 补 `help <命令>`;help 第一屏先印「开 `asight on` · 关 `asight off` · 状态 `asight status`」,并写明本平台 `on` / `off` 驱动哪一代(§4) |
| `asight capture` `mitm` `desktop` `monitor` `shard` | 旧采集(过渡期) | 已有 | 见 §4 |

**隐藏别名**(不进 help,照常分派):

| 别名 | 等于 | 为什么留 |
|---|---|---|
| `asight install …` | `asight on …` | 设计稿 v2 用过这个名字;「代装的 agent 常先试 `install`」是推测,未核实 |
| `asight collector install [--no-unit]` · `collector on\|off\|status` · `collector uninstall [--purge-data]` | `on [--no-unit]` · `on\|off\|status` · `uninstall` | 旧文档与脚本 |
| `asight collector start` | `asight daemon` | 已装好的单元 `ExecStart` 在调它;改名不能让它静默停采 |
| `asight verify` | `doctor` 里「旧 CA 只在用户级信任库」那一项 | 随旧采集退役 |

- 删掉 `asight test`(`doctor` 的别名;与 `npm test` 撞名,一个概念一个动词)。
- 不设:`restore` · `ca rotate`(轮换 = `uninstall` 再 `on`,生成新 CA,数据保留,之后 agent 各重启一次)· `legacy` 前缀(§4)· 选引流方式的命令(`status` 显示每个 harness 用的哪种)· `log`(`status` 显示最近的失败,完整的看看板)· `--only` / `--skip`(harness 名直接写在命令后)。
- 以后:`asight scope <harness> [auto|all] [--add-host H] [--rm-host H]`(按 harness 改解密策略,写 `state.json` 并记事件;第一次真有人需要时再加,见 Extensions)。改包命令 `rules` / `queue` / `replay` / `audit` 见 [5.1](5.1-intervention.md),都经守护进程的 0600 socket,改包或重发的命令打印审计记录 id。

## 4. 旧采集(过渡期)

- D31 过渡期:现有 base_url 反代、Clash steer、按 host 解密继续运行,新机制落地后退役。D39⑥ 让退役按平台进行:某平台的新采集器落地、并在该机验收([4.6](4.6-process-collector.md) R2 完成线)之后,才退役该平台上的旧命令。
- 旧命令 `capture` `mitm` `desktop` `monitor` `shard` 在 help 的「旧采集(过渡期)」段,每条标「过渡期」。不加新功能,只修错;退役时删除。
- 不设 `legacy` 前缀(命令要尽量少):D39 之前的 `asight on [--proxy]` / `off [--remove-ca]` 就是今天的 `monitor on --no-autostart` / `monitor off --remove-ca`,旧 steer 仍够得着。

**各平台上 `on` / `off` 指什么**(没有新采集器的平台上 `on` / `off` 驱动旧采集,不带参数的 `off` 撤掉旧采集的全部影响):

| 平台 | 新采集器 | `asight on` | `asight off`(不带参数) |
|---|---|---|---|
| Linux | 有(4.6;本机验收前旧命令仍在) | 新采集 | 新采集的全部,加上本机旧采集留下的(CC settings 的旧 steer、用户 NSS 库里的旧 CA) |
| macOS | 无 | 旧采集,即 `desktop on` 做的那些:Clash `Script.js` 哨兵块 + 热重载、`com.asight.mitm`、`com.asight.env` | 旧采集的全部影响:CC settings 的旧 steer(按暂存值还原)· Clash 块(D28 只剥哨兵块;D29 热重载并核对)· `com.asight.mitm` / `com.asight.monitor` / `com.asight.env` 三个 LaunchAgent(登录环境里 `NODE_EXTRA_CA_CERTS` 的当前值指向 asight 自己的 CA 时 `launchctl unsetenv`)· login keychain 里的旧 CA |
| Windows | 无 | 报「本平台未实现」,退出 1 | 撤上一格里本机存在的部分 |

- 在没有新采集器的平台上跑 `on` / `off`,先印一行「本平台 on / off 驱动旧采集(过渡期)」。
- 没有新采集器的平台上,带 harness 名的 `on` / `off` 只认 `claude-code`(等于不带名字);别的名字退出 2,印「本平台只有 claude-code 的旧采集,没有按 harness 的开关」,什么都不碰。`status` 把 `claude-code` 拆成 Desktop(Clash 块 + MITM)与 CLI(旧 steer)两行;CLI 没被采集时写「`on` 不做旧 steer;要采集 CLI 用 `monitor on`」。
- `com.asight.env` 随旧采集整体关闭一起撤:`asight off`、`asight uninstall`、`desktop off`(改 [0.0](0.0-overview.md) §过渡期遗留)。旧采集开着时仍 MUST NOT 单独移除它(会停掉 macOS 上 Desktop 的采集)。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 4 条);V12 的 `off codex` 用例落地后加测。
- 旧 CC-CLI steer(`HTTPS_PROXY` 指向本地端口)就是「把 agent 的代理字段指向 asight」,做不到 off 保证,`on` 不做它;仍可经 `monitor on` 用。`off` 照撤它,并列出 steer 生效期间启动、仍在跑的 claude 进程:它们重启前仍连那个端口。
- 旧 MITM 达到 off 保证的条件:先剥 Clash 块、热重载并核对生效(新连接不再进 MITM),再向 MITM 发 SIGTERM:它停止接受新连接,等在途连接自己结束(旧 MITM 不跟踪响应边界,不按 §1.3 逐响应关),至多 10 s;之后卸 `com.asight.mitm`,余下的连接随之切断,回执写条数。现代码(`desktop off`)剥块后立即卸载,经它的在途连接被切断:这是缺陷,实现时修。
- `on` / `off` 驱动旧机制时同样守 §5 的规则:回执、改前备份、入账。账记在 `~/.asight/legacy-manifest.json`(格式同采集器的安装清单;不放进 `~/.asight/collector/`,免得看板以为装了新采集器)。旧命令自己(`desktop on` 等)保持原样。旧命令装的东西(`desktop on`、`monitor on` 写的 Clash 哨兵块、`com.asight.*` plist、CC settings 的暂存文件)不在这本账里:它们自己的标记就是它们的账,`off` 直接按标记撤,不走 R3 的按标记撤销确认;这些改动没有改前备份,`status` 与回执标「旧命令装的,无备份」。所以 §6「VPN / 代理软件里的改动都入账」过渡期只对经 `on` 写的成立;旧命令要不要也入账见文末 OPEN。
- 作者的 Mac 跑的是旧采集,会话可能正被它采集。`off`(不带参数,或带 `claude-code`)、`uninstall`、`desktop off`、`monitor off` 都会停掉这台 Mac 上的采集:agent 未经用户同意 MUST NOT 跑它们。必拒 · 审查([0.1](0.1-engineering-rules.md) §5「未经同意…」一行 + §6 第 11 条)。
- v0 的残留(`com.atrace.serve`、`~/.local/share/atrace`、`.atrace-bak`)只报告、不碰;不建议、不调用 `atrace-uninstall`。

## 6. VPN 感知(CLI 一侧)

机器上装了 VPN 软件,asight 要自动感知,在 CLI 和界面里显示它改了什么地方;力求所有改动可追踪、可撤销。1.6 只定 CLI 一侧的四条要求:

- **探测**:`status`、`doctor`、首次 `on` 探测本机的代理 / VPN 软件:哪个产品、什么模式(规则 / 全局 / TUN / 系统代理)、每个 harness 的流量是否经过它。只读;不读也不印密钥、订阅地址、节点信息。认不出 → 「不知道」加原因,MUST NOT 报「无」。探测结果写 `~/.asight/netenv.json`(0600;只含产品、模式、各 harness 是否经过,不含密钥、订阅地址、节点;不放进 `~/.asight/collector/`,没有新采集器的平台也写)。首版 `src/netenv/` 只认 Clash Verge / mihomo(旧 steer 已在读它),其余报「不知道」加原因;各产品的适配归引流单元。守卫:test V22(计划)。
- **入账**:asight 在 VPN / 代理软件里的每一处改动,和 agent 文件的改动一样记账:安装清单一条、改前备份(R2)、回执一行(R1)、`status` 列出、`off` 撤掉;块用 D28 的哨兵块语义(只剥块、块外一字不动、剥不掉报 `ok:false`)。旧采集的 Clash 块经 `on` 写时同样入账(§4)。守卫:test V23(计划)。
- **核对生效**:`status` 与 `off` 对 VPN / 代理软件里的块 MUST 读它实际生效的运行时配置(D29 的做法:经该软件的控制接口读),不只看文件或清单。`off` 即使文件里已没有块也 MUST 热重载并核对,不走「早已还原」的跳过(运行时可能仍留着块:D29 记过重新生成时写进运行时配置的那份);核对不了报「不知道」加原因(`off` 退出 1,`status` 退出 3)。块被 VPN 软件改写或抹掉:`status` 报「块被 <产品> 改动」。守卫:test V23(计划)。

## 8. CLI 不该有的

本表各行的强度与守卫以所引规则为准;没有引用规则的行是 SHOULD。

| 不该有的 | 理由 · 依据 |
|---|---|
| `restore`,或任何把「关」和「撤」分开的命令 | 用户分不清「关」和「撤」 |
| 把 agent 的代理字段指向 asight 作为引流 | 做不到 off 保证(§1.2) |
| `ca rotate` | 轮换 = `uninstall` 再 `on` |
| 改系统代理、接管整机流量;不入账地改 VPN / 代理软件 | D31④⑤;VPN 改动只经引流单元、按 §6 入账 |
| 往登录环境写 CA 变量(`launchctl setenv`、`environment.d`、rc 里 `export`) | D37④;旧 `com.asight.env` 是过渡期遗留,`off` 撤它 |
| 把采集器 CA 装进任何信任库;`add-trusted-cert -r trustRoot`;写 `/etc/ssl` | 采集安全 |
| 拿备份自动整文件写回(`--force`、`--from-backup` 之类) | 会静默抹掉用户后来的修改(D28);撤不掉时只给手动 `cp` 命令 |
| 默认删采集数据;`rm -rf ~/.asight`;建议或调用 `atrace-uninstall` | [4.6](4.6-process-collector.md) §安装清单与卸载第 3 条;采集安全 |
| 常驻 root 服务;每次开关要密码 | D36 |
| 非环回监听(`serve --host 0.0.0.0` 之类) | [4.4](4.4-server.md) 只绑环回 |
| 实时提醒(`--notify`、声音、系统通知) | D38⑦ · Non-Goal「实时告警」 |
| 给旧采集命令加新功能,或把新功能挂到旧命令上 | [4.6](4.6-process-collector.md) §取代 |
| `npm run serve` / `npm run etl` 各有一套参数解析 | 默认值已分叉;npm 脚本改为调用 `bin/asight.mjs` |
| `ASIGHT_SOURCE` 一个名字两个意思(`capture` / `mitm` 写,`serve` / `doctor` 读) | 过渡期保持;新代码只当「读」,旧命令退役时去掉「写」 |

## 验收(可跑 check)

单元测试走 `npm test`,在 `mkdtemp` 沙箱 HOME 里跑,信任库、`launchctl`、`systemctl`、进程管理器都注入(0.1 §3「不碰真实机器」);标 [VM] 的在测试机上跑。下列各条现在都是**计划**:本单元刚写,命令还没按它实现;每条在实现 PR 里落成会变红的断言。

1. **V1 守护进程不在时 off**:`on` 后杀掉守护进程,再 `off`:每个入口回到 `pre_sha256`(用户改过的报「已撤销,但不逐字节相同」),退出 0,全程没有拉起守护进程。

3. **V3 回执 == 实际改动**:回执(与 `--json`)列出的文件集合 == 实际被写的文件集合(并入 4.6 T10)。
4. **V4 [VM] off 保证**:`off` 返回、在途响应结束后 `kill -9` 守护进程:受管 agent 的新连接零失败,看到上游真实证书;`bpftool link` 里没有本实例的 link。
5. **V5 按 harness**:`off claude-code` 只撤 claude-code 的入口,其余 harness 的入口逐字节不变、仍被采集;`--json` 只印代码 id;别名 `claude` 与 `claude-code` 结果相同。

## OPEN

- **WebSocket 的在途连接(OPEN)**:`off` 之后,在一轮的终止消息处关(harness 文件已声明终止消息,4.6 §传输与帧级记录;Codex 下一轮会重连),还是等它自己关闭(Codex 连接可开 60 分钟,其间仍经 asight)。定之前按「等它自己关闭」,`status` 计数。
- **关连接时的复用竞态**:引擎在响应结束后关一条 keep-alive 连接,客户端恰在此时复用它发下一请求,会看到一次连接复位(非幂等的 POST 客户端多不自动重试,靠 agent 自己的重试)。办法之一是在最后一个响应上加逐跳头 `Connection: close`,客户端就自己不再复用;但它改了 agent 收到的字节,算不算 D30 的改包、要不要记 `intervention`,仍是 OPEN。定之前 MUST NOT 改写(§1.3),[4.6](4.6-process-collector.md) S5 把这种复位单独计数、报告。
- **透传连接**:引擎不分帧,看不到响应边界;现定为等它自己关闭。它们不经解密,但仍经引擎,所以在它们关闭前 off 保证对它们只到「新连接」为止。
- **立即切断的选项(OPEN)**:WebSocket 与透传连接可能开很久(Codex 的连接可开 60 分钟;MCP 的 SSE 之类长连接),其间守护进程不退出(§1.4)。`asight off --now`:不等它们,立即退出并切断,回执写条数(操作者的显式意图)。可随 WebSocket 那条一起定。
- **「没有 asight 进程」的范围(OPEN)**:不带参数的 `off` 之后没有 asight 进程在跑。现定(§1.4):不杀用户自己在终端起的 `serve` 与前台 `capture` / `mitm`(后两者可能正中转 agent 的流量,杀掉会弄断 agent);WebSocket 与透传连接未关时守护进程仍在排空。若用户的意思是字面上一个都不留:`off` 要杀前台 `capture` / `mitm`(经它们的 agent 会断),并立即切断长连接。
- **被 5.1 扣留的请求在 `off` 时怎么办(OPEN)**:扣留没有默认超时([5.1](5.1-intervention.md) 第 2 条),扣着的连接不会自己关,off 保证就完成不了。推荐默认:`off` 先停用全部规则(规则保留、不删),把扣留队列里的条目原样放行(不改一字节,审计记 `released-by-off`),再按「有请求在途」处理;`off` 之后新到的请求不再匹配规则。备选:丢弃(重置连接,agent 看到连接错误、自行重试)。牵涉 D30「没有操作者意图时原样转发」;5.1 尚未实现,落地时一并定。
- **网页开关在过渡期的「关」(OPEN)**:D26 的 `POST /control/monitoring off` 现在只调 `atraceOff`(旧 CC-CLI steer),在 macOS 上不撤 Clash 块、旧 MITM 与 `com.asight.env`,不满足 off 保证。推荐:没有新采集器的平台上改接 `asight off`(两代都撤);备选:保持原样,网页开关就地标「只管旧 CC-CLI steer,不等于 `asight off`」。D26 的映射待定;定之前 [4.4](4.4-server.md) 如实标注。
- **旧命令写的 VPN 块要不要入账(OPEN)**:所有改动都要可追踪、可撤销;`desktop on` / `monitor on` 写的 Clash 块与 settings steer 现在只靠它们自己的标记撤、没有改前备份(§4)。推荐:过渡期不改旧命令(它们只修错),`status` 与回执标「旧命令装的,无备份」;备选:旧命令也写 `legacy-manifest.json` 与备份。
- **登出后的守护进程**:用户级 systemd 单元在最后一次登出时停掉,除非开了 linger(4.6 OPEN「登出后守护进程的存活」)。`on` 是否提议 `loginctl enable-linger`,随那条 OPEN 定。
