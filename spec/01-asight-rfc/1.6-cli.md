# asight · RFC 1.6 — 命令行界面

> **这是什么**:asight 命令行的契约:开关模型(`install` / `on` / `off` / `status` / `uninstall`)与各自的保证、命令清单、各平台上 `on` / `off` 指什么(§4)、跨命令规则、asight 自己坏了时怎么办、系统代理感知的 CLI 一侧、网络拓扑与诊断(§9)。
> **受众**:人(核对「我的 agent 有没有被监听」「asight 出了问题能不能一条命令关掉」是否成立)+ agent(据此改 `bin/asight.mjs` 与采集器命令)。
> **Source-decision**:**D39**(二元开关;4.6 原「注入一次、长期保持,不随开关变化」推翻)· **D43**(引流只有驱动模式与代理模式;VPN 只读、只决定上游;影响超出 agent 的改动由用户点名,§1.7)· **D47**(代理模式里引擎自己当本地代理,每个入口组一扇引擎的门)。承 D31(按进程,不碰系统代理 / 整机流量)· D36(按用户运行,sudo 只在助手)· D37④(信任入口)· D38(失败不静默)。§9 网络拓扑与诊断 = **D39⑩**。**D55**(证书归 `install` / `uninstall`,`on` / `off` 只管代理是否接入;实现细则见 D55⑥)。
> **不含 → 去哪查**:采集器内部机制 → [4.6](4.6-process-collector.md);改包命令 → [5.1](5.1-intervention.md);代理模式 → [4.8](4.8-win-collector.md)(Windows)· [4.9](4.9-macos-collector.md)(macOS);系统代理感知(只读)→ [4.7](4.7-netenv.md)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集;`off` 撤掉 asight 对这些 agent 的全部影响,asight 坏了也能用。每个改动用户机器的命令都打印回执;改用户文件前先备份。

## 1. 开关模型

### 1.1 五个命令与各自的保证(`install` 与证书一面 D55)

| 命令 | 做什么 | 做完之后保证什么 |
|---|---|---|
| `asight install [--dry-run] [--yes] [--json]` | 一次性装好证书(D55①)。先打印计划、等确认(§1.6);在本机生成这台机器自己的 CA(`ca/ca.key`,0600;只有 `install` 生成,守护进程与 `on` 从不生成,D55⑤);写 asight 自己的文件(`asight-ca.pem`、合并包与 `extra-*.pem`、`extra-login.pem`、(d) 级插件、独立撤销程序 `asight-off`);按每个形态描述符的 `cert` 字段([4.6](4.6-process-collector.md) §身份与信任)写证书载体:(c) 级的配置键、(b) 级的登录环境增量变量、最后 (a) 级的用户级系统信任根(唯一要等人的一步);记判活快照,打回执。不收 harness 名:装到的 harness 记进清单的 `install.harnesses`(D55⑥)。 | 本机检测到的每个形态,有一级够得到的都信任这张 CA(级别与 `since` 写进回执与 `status`);够不到的、根被拒或待定的,逐个列出原因与命令,退出 1。证书之后不随开关变:`on` / `off` 不碰任何证书字节。 |
| `asight on [harness…]` | 开始采集这些 harness;不带名字 = `install.harnesses`。没装过(没有可用的 CA,或没有带 `install.state` 的 v3 清单)时拒绝,退出 1,提示「先 `asight install`」(`cert-not-installed`);`on` 从不写证书,所以也不会悄悄安装(D55⑥)。只接代理:挂引流(驱动模式 = 本实例的 link;代理模式 = 开各入口组的门、写各形态的代理入口,[4.8](4.8-win-collector.md) §4.1 · [4.9](4.9-macos-collector.md) §3;没有采集器的平台由 loadArch 自己报不支持(§4);点名项见 §1.7),启用自启并拉起守护进程。它写的项在清单里都是 `phase: on`;Linux 上 `on` 不写任何 agent 文件。 | 之后新启动的这些 agent 被采集;证书对它不生效的形态(装了一部分、根待定、够不到)照样挂引流,只转发(D51④),回执逐个点名原因与命令。`on` 之前就在跑的进程照常透传、不被弄断;`on` 的输出与 `status` 逐个点名「重启后才会被采集」,点的是真正发请求的进程(如 Codex 的 app-server 守护进程,不是用户看到的 TUI;[4.6](4.6-process-collector.md) §各 harness 的进程特征)。 |
| `asight off [harness…]` | 撤掉 asight 在这些 agent 路径上的一切:引流、代理入口、点名项(§1.7),即清单里 `phase: on` 的项;被改过的文件(代理那一半)回到 `install` 之后的样子。证书一项不碰(D55①):CA、合并包、登录环境载体、证书配置键、信任根都留到 `uninstall`。不带名字时另外停守护进程、停用自启(§1.4)。 | **off 保证**(§1.2)。 |
| `asight status [harness…]` | 每个 agent:正在被采集;或者没有,为什么。 | 只读。 |
| `asight uninstall [--purge-data]` | 先在 op.lock 下核对「采集全部下线」(D55⑥:每个 harness 的期望态都是 off · 清单里没有 `phase: on` 的项 · 没有守护进程承载连接;空闲的守护进程由它停掉,活着却不应答的算不知道),并持锁到撤完。不成立:什么都不改,退出 1,码 `collectors-online`,列出还开着的 harness 或「守护进程承载 N 条连接」,指向 `asight off`;**`uninstall` 从不代做 `off`**。成立:按后进先出撤——agent 的证书项(D50 判活照旧,「重启前仍信任」在这里报)→ 登录环境载体(恢复用户原值)→ 合并包与 `extra-*.pem` → 插件 → 信任根(按指纹;可能弹框)→ **CA 私钥(一律删)** → asight 自己的文件(自启单元、运行目录、清单、备份、独立撤销程序)。根的移除被拒或待定时私钥照删(此后那张根是死的),清单只留那一项,退出 1 并给出移除命令。**`--purge-data` 的清单(2026-10-12 补,按用户字面批准)**:除 `capture-*.ndjson`、`flows/`、`audit/`、`replays/` 外,一并删采集器自己的机器——`control.json`(守护进程控制端点)与 `ingress.json`(入口端口与令牌),以及采集器目录里存在才删的 `kernel/`、`kernel-archive/`、`forwarder/`([4.8](4.8-win-collector.md) §8);不带 `--purge-data` 的卸载保留 `control.json`;`ingress.json` 在守护进程停下之后删(依据 [0.2](0.2-architecture-overview.md) 入口配置一行、不变式 5、D54②)。采集数据默认保留。 | 本用户下零残留(例外见 [4.5](4.5-distribution.md) §C;根的移除被拒或待定时那张已失效的根留着,`status` / `doctor` 报「孤儿 asight 根」与移除命令)。整机的能力助手另要一步 `sudo asight setup-helper --remove`。 |

- 没有 `restore`:关与撤是同一件事(不区分 off 与 restore:用户分不清)。
- **证书不随开关**(D55①,取代 2026-10-07 的「信任入口随 `on` 写、随 `off` 撤」):证书放着不用也没问题,所以归一次性的 `install` / `uninstall`;代理是动态的,归 `on` / `off`。证书生效是装好时验一次的性质,`on` / `off` 出问题时只剩代理这一个变量。轮换 = `off` → `uninstall` → `install` → `on`。
- **代价**:证书只在 agent 启动时读。`install` 之前就在跑的 agent 要重启一次,证书才对它生效。这不会弄断它们:守护进程把「证书在进程启动之后才装上」判为未信任(4.6 §确认信任 `config-after-start`;「之后」按清单里该证书项(`phase: install`)的 `installed_at`,代理入口的写入时间从不当证书的 `since`),未信任的进程照常透传。`installed_at` 只在 `install` 实际(重新)写入该项时更新:项已在、sha 等于 `post_sha256` 时,`install` MUST NOT 写这个文件、MUST NOT 改 `installed_at` 或它的 mtime;否则在跑、已被采集的进程会被判 `config-after-start`,采集静默停掉(R9)。`off → on` 不动证书,不让在跑的 agent 变成未信任(D55)。
- **登出后停采(Linux)**:用户级 systemd 单元在该用户最后一次登出时停掉,除非开了 linger;留在 tmux / SSH 里的 agent 之后照常直连、不再被采集(fail-open)。`on` 不替用户开 linger(R8)。linger 没开时,`on` 与 `status` 各印一行「登出后停采(未开 linger)」,并给出开启命令 `loginctl enable-linger <用户名>`;读不到 linger 状态时印「不知道」加原因,不印「已开」(R11)。读法:`/var/lib/systemd/linger/<用户名>` 在不在,只读,与守护进程 `daemon-start` 事件的 `linger` 字段同一读法。守卫:test V39。
- **保存设置不随开关(D40 × D39)**:`~/.asight/retention.json` 与 `~/.asight/logs/retention.ndjson`(`asight keep` 的设置和它的修改记录)说的是之后的调用存什么,不是 asight 对 agent 的影响,也不是采集数据。所以 `off`(带不带名字、带不带 `--now`)不碰它们,off 保证(§1.2)与它们无关,采集关着时设置只是不生效,`on` 之后照旧;`uninstall` 也留着它们(它们不在「asight 自己的文件」那一串里),`--purge-data` 也不删(那删的是采集数据)。理由:CA 轮换的做法是 `uninstall` 再 `on`(D39),操作者为省盘设的 `log` 不该因此悄悄改回全部 `full`。想清掉:`asight keep all all full`(留下文件,全部 `full`),或自己删文件。设置文件不在 `state.json` 里,所以 `state.json` 的版本、迁移与 `off` 的撤销清单都不涉及它。守卫:V59 · V60。

### 1.2 off 保证

**`off` 返回、且在途响应结束之后,asight 不在这些 agent 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。** 做不到这条的引流方式不提供。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 11 条)· V4 · V17。

**例外(如实写明)**:透传(splice)连接,以及看不到终止消息的 WebSocket 连接(harness 文件没声明终止消息,或这一轮的终止消息解不出、被略去,[4.6](4.6-process-collector.md) §传输与帧级记录「看不到终止消息时」),引擎看不到响应边界,在它们自己关闭之前仍经引擎(§1.3);对这两类,保证只到「新连接直连」为止,在那之前守护进程也不退出(§1.4),除非操作者用 `asight off --now` 立即切断(§1.3)。`off` 的回执与 `status` 单列它们的条数。

**例外二:代理模式(D43 登记;「稳健 = 两句话」)**:`off` 撤掉入口;无人携带的门关掉,carried 的门(装过、点过名的组的门)保持开着、只转发。`on` 期间启动、读了入口的 agent 重启前仍连着 carried 的门(只转发:不解密、不记录),守护进程排空到它们退出(§1.4)。守护进程在那之前死了,门随它死,它们的新连接被拒,直到守护进程被重拉或它们重启。`off` 的回执与 `status` 写「还有 N 个 agent 连着 asight 的门(只转发),重启它们之后 asight 就完全退出」;`asight off --now` 立即断开,回执列出会断的 pid。守卫:V55 · [4.8](4.8-win-collector.md) W48。

下表「能否做到」一列是评估;保证本身与「做不到的不提供」是定下的。

| 引流方式 | 能否做到 off 保证 | 结论 |
|---|---|---|
| 驱动模式:操作系统的按进程机制(Linux eBPF;D43 起只有 Linux 用它) | 能:摘钩即可,不碰 agent。Linux 开着时另有两层 fail-open(4.6 §Linux 机制) | Linux 提供 |
| 代理模式:agent 的代理入口指向引擎自己的门(Windows、macOS;D43 · D47) | 能,有一处例外(上文「例外二」):`on` 期间启动的 agent 重启前仍连着 carried 的门,只转发。各形态经入口进来,门不在时 fail-closed、门回来即恢复,不重启 agent(4.8 E9) | Windows 提供(4.8 §4.2);macOS 提供(4.9 §4) |
| asight 开 TUN 或当系统代理 | 整机接管(违 D31④) | 不提供 |

- `off` 不撤证书(D55①),所以 `off` 之后 agent 照旧信任 asight CA。这不影响路径:没有引流,它的连接不经 asight。「重启前仍信任」的报告归 `uninstall`(4.6 §安装清单与卸载「uninstall 的撤销」)。

### 1.3 在途连接

`on` 期间已经经引擎中转的连接,TCP 上没法中途改道。规则:`off` 返回后,引擎在每条中转连接的**当前响应结束**时关掉它,agent 的下一个请求就直连。细节:

| 连接的状态 | 引擎怎么做 |
|---|---|
| 空闲(keep-alive,没有请求在途;含引擎已终结 TLS、客户端还没发过请求的连接) | 立即关两侧 |
| 有 HTTP 请求在途(含 SSE;含 CONNECT / SOCKS / `https://` 代理隧道里解密的) | 响应按被动分帧收全、转完,再关两侧。客户端在此之前已发出下一请求的字节:照转、不记录(`off` 返回之后开始的请求零记录,4.6 §开关语义),它的响应结束后再关 |
| 透传(splice,引擎不分帧) | 看不到响应边界,等它自己关闭;`off` 的回执与 `status` 计它的条数(§1.2 例外) |
| WebSocket | 在这一轮的**终止消息**处关:终止消息按 harness 文件以数据声明的模式认([4.6](4.6-process-collector.md) §传输与帧级记录「逻辑调用怎么切」),引擎把含终止消息末帧的那块字节照转完,再按下文「怎么关」关两侧;Codex 下一轮自己重连。`off` 时没有打开的调用 = 空闲,立即关。MUST NOT 自己合成 close 帧(不往连接里写 asight 自己的字节)。harness 没声明终止消息、或这一轮看不到终止消息(同节「看不到终止消息时」),或任一方向的帧已不再被跟踪:同透传,等它自己关闭、计数 |
| 被 [5.1](5.1-intervention.md) 扣留的请求或响应 | `off` 先停用规则(规则保留、不删;不带名字的 `off` 停用全部,带名字的只对这些 harness 的请求停用),把扣留队列里的条目原样放行(不改一字节,审计记 `released-by-off`),再按「有 HTTP 请求在途」处理;`off` 之后新到的请求不再匹配规则 |

- **怎么关**:先把已转发的字节写完再 `end()`(发 FIN),等对端关闭,至多 5 s 后才 `destroy()`;MUST NOT 在接收缓冲里还有未读的客户端字节时直接 `destroy()`(会发 RST,客户端可能丢掉已写出、还没收到的最后一段响应)。关连接本身不改任何字节,只由操作者的 `off` 触发,不属 D30 的改包。
- **`Connection: close`**:`off` 落在一条响应还在途时,引擎 MAY 在这条(最后一条)响应上加逐跳头 `Connection: close`,客户端就不再复用这条连接,不会撞上关连接时的复位。它是逐跳头,由操作者的 `off` 引起,不算 D30 的改包,不记 `intervention`。约束:只在这条响应的头还没转给客户端时加(头已转出的,比如正在流的 SSE,加不了,照常在响应结束后关;此时客户端恰在关闭时复用这条连接会看到一次复位,靠它自己重试,[4.6](4.6-process-collector.md) S5 单独计数);只在头部结尾的空行前插入一行 `Connection: close\r\n`,原有的头逐字节不动,响应已带 `close` 时不加;体逐字节不变(`content-length` 不变)。**MUST 记账**:这次调用被记录时,信封带 `asight_added:['connection-close']`(`resp_head_raw` 仍是上游发来的原字节,4.6 §记录);不论记没记(`off` 返回之后才开始的请求不记),`flows/` 的连接行带 `asight_added:[{seq, what:'connection-close'}]`。看板 MUST 在该调用上就地标「asight 加的 · Connection: close」(不变式 4)。除这一行头之外,MUST NOT 为了让客户端断开而改写响应。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 11 条)· test V37。
- **`asight off --now`**:不等在途连接,立即切断这些 harness 仍经引擎的连接(HTTP 在途响应、WebSocket、透传都算);不带名字时守护进程随即退出。这是操作者的显式意图:被切断的 agent 看到连接错误,靠自己重试(Claude Code 对已开始输出的流不重发,4.6 §Linux 机制「fail-open 两层」)。回执写切断的条数(`relayed.cut`);每条被切断的连接在 `flows/` 留连接行,`error.type` 为 `cut-by-off`。守卫:test V36。
- `off` 的输出与 `status` 写「N 条连接仍经 asight 中转,本次响应(或本轮)结束后关闭」(HTTP 在途与等终止消息的 WebSocket);透传与看不到终止消息的 WebSocket 另计「M 条等它自己关闭(`asight off --now` 立即切断)」;读不到写「不知道」加原因。

### 1.4 不带参数的 off

不带参数的 `off` 另外停守护进程、停用自启;之后没有 asight 进程在跑(代理模式的例外:守护进程排空到 `on` 期间启动、仍连着门的 agent 都退出,§1.2 例外二)。`on` 重新启用。「asight 进程」的范围与例外见本节末。顺序:

1. 把全部 harness 的期望态写成 off(`state.json`,原子写,R12)。
2. 摘引流,读回实际态确认(Linux:内核里的 `watch` 表与 link;代理模式:引擎的门)。守护进程不在时,确认本实例的助手已不在(Linux:link 随它摘掉,4.6 §Linux 机制)。守护进程没响应(`lock` 超过 5 s 没刷新,或控制 socket 5 s 不应答)或还在启动中(有 `lock`、socket 不应答):不等它,先按第 5 步停掉它(助手随之退出、link 摘掉),确认 link 已消失,再进第 3 步。
3. 撤代理入口与点名项(§1.7),即清单里 `phase: on` 的项;证书项与合并包不动(D55①)。代理模式的门随第 2 步处置:无人携带的门关掉,carried 的门保持只转发(§1.2 例外二)。
4. 停用自启。Linux:`systemctl --user disable`,删 `default.target.wants/` 链接;单元文件是 asight 自己的,留到 `uninstall`。macOS:`launchctl bootout` 摘掉 LaunchAgent,先于停进程([4.9](4.9-macos-collector.md) §4)。Windows:停用计划任务,或删登录启动项([4.8](4.8-win-collector.md) §7)。
5. 让守护进程排空后退出:按 §1.3 关完连接即退出(干净退出,systemd 不拉回),助手随它退出。`off` 不等它,回执写明守护进程的 pid 与还剩几条;透传连接与看不到终止消息的 WebSocket 还开着时(代理模式下含 `on` 期间启动、仍连着门的 agent 的连接)它不退出,回执写「守护进程仍在排空:pid N,还剩 M 条等它们自己关闭;`asight off --now` 立即切断」。`--now`:不排空,按 §1.3 切断后立即退出。**排空期间又 `on`**:这条退出请求撤销,守护进程接着服务(`on` 只拉起没在跑的守护进程,它还活着,`on` 就落在它身上);之后再一次不带参数的 `off` 重新排空。任何时候退出都要求没有 harness 为 on,否则不退(退出是干净退出,systemd 不拉回,会留下 `state.json` 写着 on 而什么都没挂的局面;守卫定义在此;该缝的真 e2e:test/collector/install-endpoint.test.mjs)。**要停它时**(没响应、`uninstall`;以及不带名字的 `off` 遇到守护进程不在、而自启单元还开着或正等着 `Restart=on-failure` 重启——`systemctl --user is-active` 答 `active` / `activating`,`disable` 不取消那次重启):由自启单元管着时用 `systemctl --user stop asight-collector`(systemd 因此不按 `Restart=on-failure` 把它拉回);单元没管它或 stop 超时:SIGTERM,10 s 不退再 SIGKILL。每次发信号前按 `lock` 的 `start_time` 与 `boot_id` 核对 pid 身份,不符不发;`lock.helper_pid` 还活着一并 SIGTERM。收尾 `systemctl --user reset-failed asight-collector`,确认单元既不是 active 也不是 activating;写一条事件。**macOS**(守护进程由 launchd 的 KeepAlive 管着,不建监管父进程,[4.9](4.9-macos-collector.md) §4):先 `launchctl bootout` 摘掉 LaunchAgent(保证不被拉回),再停进程。**Windows**(守护进程由监管父进程管着,[4.8](4.8-win-collector.md) §7):要停它时**先停监管父进程**(核对 `supervisor.lock` 的 pid 与启动时间),再停守护进程;顺序反了父进程会把它拉回来。守护进程以退出码 0 退出时父进程随之退出,非 0 才重拉。代理模式下守护进程排空到 `on` 期间启动、仍连着门的 agent 都退出;`--now` 立即断开,回执列出会断的 pid([4.8](4.8-win-collector.md) §4.2)。

- 用户在终端里自己起的 `asight serve`(只读看板,不在任何 agent 的路径上):`off` 不杀,回执与 `status` 列为「你自己起的 asight 进程仍在跑」;它不是 asight 装的或拉起的,off 保证不管它。守护进程排空后退出,`--now` 不排空。

### 1.5 按 harness

- `on` / `off` / `status` 都可带 harness 名(§3);不带 = 全部(可按 harness)。
- 期望态按 harness 记。`~/.asight/collector/state.json` 升到 version 2:`{version:2, updated_at, harnesses:{<id>:{desired:'on'|'off', policy:'auto'|'all', extra_hosts:[…], updated_at}}}`(看板「采集关 · 自 T 起」的 T 取它,[4.4](4.4-server.md) `/api/capture-health`)。`policy` 缺省取 `all`(D40:默认解密该进程的全部 TLS;`switch.mjs` 的 `DEFAULT_POLICY` 是唯一一处);写着 `auto` 的保持 `auto`,因为盘上分不出它是旧默认还是操作者选的。读到 version 1 时,把它的 `desired` / `policy` / `extra_hosts` 套到每个已安装的 harness(`policy` 只带过去写着的、写对的 `all` / `auto`,没写或写坏的取缺省)(已安装 = 安装清单点名的 harness;从没装过的不套、也不判);读不出时全部按 off 起,并留失败事件(4.6 §开关语义)。
- Linux:任一 harness 为 on 就挂本实例的 link。期望态为 off 的 harness,其进程从内核 `watch` 表摘掉:不改写、不上报元数据;守护进程不为它们写 `agent-untrusted`(它们本就不是采集目标)。某个 harness 的实际态:有在跑的进程时逐个核对内核 `watch` 表;没有在跑的进程时 = link 已挂且它的入口完好。都不读自己记的标志(4.6 §开关语义)。
- **`off` 的次序**(D55):每次 `off`(带不带名字)都先写期望态,再把该 harness 的进程从 `watch` 表摘掉并读内核确认(全部为 off 时确认 link 已摘;守护进程不在时确认本实例没有 link),之后才撤代理入口(代理模式;Linux 的 `on` 不写 agent 文件);确认之前 MUST NOT 动入口。证书项与合并包 `off` 不碰(D55①);原先「先摘引流、再改写合并包」的理由移到 `uninstall`:它要求采集全部下线,改写合并包时已没有进程经 asight。`on` 的次序见 R9。
- 逐个 `off` 完全部 harness 时:link 已摘,不在任何 agent 的路径上,守护进程与自启仍在(空转);要停它们用不带参数的 `off`。
- 按 harness 撤时,共用文件怎么处理见 [4.6](4.6-process-collector.md) §撤销顺序「按 harness 撤」。

### 1.6 install(D55)

- **先打印计划,等确认**:要写的每个文件与键、asight 自己要建的东西、每个 harness × 形态落在哪一级(或「够不到 · 原因」)、要弹的 OS 框、跳过的 harness 与原因、要重启的进程。计划**总是**印 D55 的代价一行:「证书在时,本用户所有读系统信任库或读这些变量的程序都信任这张 CA,直到 `asight uninstall`」。终端里等确认;接受 `--yes`、`--dry-run`、`--json`。不在终端里(stdin 或 stdout 不是 TTY,如 agent 代为安装)没有 `--yes` 时,只打印计划、什么都不改,退出 2。
- **拒绝 root**:每一项都是用户级(D55②);macOS 的信任框与 Windows `Root` 的 Yes/No 框是操作系统的同意,不是提权。以 root 或提升的令牌跑,在读写任何东西之前退出 1(R7、D53③)。
- **步骤**(全程持 op.lock,R12;每步先在日志里写意图,崩了能续):① 没有 `ca/ca.key` 就生成(0600,本机);② asight 自己的文件(`asight-ca.pem`、`combined-<h>.pem` / `extra-<h>.pem` / `extra-login.pem`、(d) 级插件、`asight-off`);③ (c) 级配置键,改前先备份(R2);④ (b) 级载体;⑤ (a) 级根,放最后,因为只有它要等人;⑥ 判活快照,`install.state` 写 `complete`,或 `partial` 加 `pending[]`。
- **对账**:期望集合 = 本机找到的每个 harness 每个形态描述符的 `cert`。缺的写上、不再期望的按 `uninstall` 的办法撤掉(判活规则照旧);形态的级别实测后改了、从 v2 清单升级、入口被删要修、上次之后新装的 harness,都走这一条。`on` 开着时也能跑 `install`:`off` 与 `uninstall` 之后仍按字节撤对(V67)。
- **幂等**(D54,扩到 `install`):`install; install` 不改任何字节、不生成第二把私钥、不弹任何 OS 框(根先按 SHA-256 读回再决定加不加);合并包只在组出的字节变了时重写。
- **OS 框**:两个平台都等 120 s。用户拒绝 = `declined`;超时或没有图形会话(如经 ssh)= `pending`。其余项照常做完,退出 1,印原样命令与「再跑一次 `asight install`」。**不降级**到下一级(D55⑥)。
- **退出码**:0 = 全部装好 · 1 = 部分或失败 · 2 = 用法错误,或不在终端又没有 `--yes`。
- **回执**(`install-note`,R1):CA 指纹;每一项与它的 `undo_by_hand`;每个 harness × 形态的级别,或「够不到 · 原因」;开、关、看状态、卸载的命令;独立撤销程序 `asight-off` 的路径(装完告知开关命令)。
- **之后的 `on`**:要改的文件比上次确认过的(清单顶层 `confirmed_paths`)多出来时(新检测到的 harness、新的 `CODEX_HOME`),只列出多出的那些,再确认;不在终端又没有 `--yes` 时只印、退出 2。

### 1.7 点名项(D43⑥)

> **D52 · D53 修订本节**:启动器与快捷方式类的点名项随替代办法撤掉;命令行的 PATH shim(shell rc 里的一行、Windows 的用户 PATH)不再是点名项,改为随 `on` 写、随 `off` 撤的代理与证书注入;要管理员的项由 asight 起操作系统的提权提示,没有权限时只做不要 root 的项,不要 root 的项绝不用 root 做。本节随实现改写。

> **D55 修订本节**:证书不是点名项。用户级系统信任库、登录环境里的增量信任变量、各 harness 的证书配置键都归 `install` 按阶梯一次装好、`uninstall` 撤(§1.6;`uninstall` 要求所有 harness 已 `off`);OS 弹的框就是同意。本节的点名项只剩代理一半(D43⑥:影响超出 agent 的代理改动由用户点名),证书类的点名项一律撤掉;Windows Claude Desktop 那一项改名 `claude-policy`,只写策略值(代理),它的根是 `install` 的([4.8](4.8-win-collector.md) §2.4)。VS Code 不写任何信任设置(D55④)。见 [0.0](0.0-overview.md) D55。

D43⑥:影响超出只属于 agent 的改动从不默认做;用户按形态点名,asight 执行并负责撤销。下表的命令面:只加一个旗标 `--opt-in`,确认仍是 R6 那一次,账仍是同一本清单(多一个字段 `scope`)。

## 4. 各平台上 `on` / `off` 指什么

`on` / `off` / `status` / `uninstall` / `daemon` 在一切平台上驱动按进程采集器,CLI 没有平台门;没有采集器的平台由 loadArch 自己报「not supported yet」(4.6 §结构)。

| 平台 | `asight on` | `asight off`(不带参数) |
|---|---|---|
| Linux · Windows · macOS | 按进程采集器(4.6 / 4.8 / 4.9) | 采集器的全部(清单与标记) |
| 其余平台 | loadArch 的不支持报错(退出 1) | 照常运行:没有可撤的就如实说「没有东西要关」 |

- 旧版 asight 留在机器上的东西(launchd 的 `com.asight.*` 任务、旧 CA、登录环境变量、VPN 软件脚本里的哨兵块)`off` / `uninstall` 都不动,由用户手动清理;`asight doctor --only old-ca`(隐藏别名 `verify`)只读核对旧 CA。旧版写下的采集与日志照读(不变式 2、D38)。
- **网页开关**([4.4](4.4-server.md) · D26):现在的 `/control/monitoring` 与 `/control/status` 走旧采集(`atraceOn` 装旧 CA、把 steer 指向没人听的端口),连同背后的旧采集库一起删掉;4.4 的按用户隔离落地后,网页开关改接 `asight on` / `off`(依 D39⑥ 旧采集整体退役、D43⑥ 采集 CA 默认不进信任库(D55 起改为 `install` 装进用户级系统信任库;旧 `atraceOn` 装的是另一张旧 CA,结论不变)与不变式 5;D26 要的网页开关随按用户隔离回来;V40 随之改写)。
`off`(不带参数,或带 `claude-code`)、`uninstall` 都会停掉这台 Mac 上的采集:agent 未经用户同意 MUST NOT 跑它们。必拒 · 审查([0.1](0.1-engineering-rules.md) §5「未经同意…」一行 + §6 第 11 条)。
- v0 的残留(`com.atrace.serve`、`~/.local/share/atrace`、`.atrace-bak`)只报告、不碰;不建议、不调用 `atrace-uninstall`。

## 6. 系统代理感知(CLI 一侧)

D49:asight 只需感知代理设置,以免打破用户原本设置的正确的 proxy 链路;不识别、不显示 VPN / 代理产品。1.6 只定 CLI 一侧的三条要求:

- **读什么**:`status`、`doctor`、`on` 读 agent 自己的代理设置(harness 文件 `proxy` 声明的键、入口原值、Linux 上进程的 environ)与 OS 系统代理(Windows 注册表、macOS `scutil --proxy`;Linux 不读),再读代理端口在监听表里的属主进程名与 pid。只读;不读也不印代理凭据(URL 里的用户名密码印成 `***@`)。读不到 → 「不知道」加原因,MUST NOT 报「无」。读法与落点见 [4.7](4.7-netenv.md) §1。
- **不写**:asight 不往任何 VPN / 代理软件里写东西、不改系统代理(D43②),所以清单、备份、回执里没有这类条目。守卫:test V23。
- **看板**:`~/.asight/netenv.json`(0600;不放进 `~/.asight/collector/`,没有新采集器的平台也写)只含 `adopted`(接上记录,§9.5)与 `topology`(§9.4),经 [4.4](4.4-server.md) 只读数据面(`/api/capture-health` 的 `netenv` 字段)读取。`status` 与 `doctor` 写它(只在 `~/.asight` 已经存在时:没装过 asight 的机器上它们不建任何东西);`on` 只在记 `adopted` 时写它。点名项(§1.7)也在这个面板里,读同一份 `opt_in`(§9.4)。

**参见**:读法在 [4.7](4.7-netenv.md)(Windows)与 [4.9](4.9-macos-collector.md) §8(macOS);D31⑤「不依赖、不修改用户的 VPN 软件」成立(D43)。代理模式里系统代理只决定 asight 的上游([4.8](4.8-win-collector.md) §2.2 · [4.9](4.9-macos-collector.md) §2.2)。

## 9. 网络拓扑与诊断

**来源**(D39⑩):每个 agent harness 的网络情况各画一个简单的拓扑结构,让用户看清数据的流动;把不同情况说清楚,也顺畅适应改 agent 网络配置(例如挂自己的 proxy)的需要,一目了然、容易配置,这些后面会进到 GUI 里。agent 不能正常工作或网络不同时,`asight doctor` 要给出明确的、可执行的指令。另外几条 —— 出口不变;用户直接改了 agent 的代理,asight 能发现,`status` 画出新的流向并给出接上的命令;asight 不悄悄覆盖用户的设置。产品设计取决于用户的具体需求,给出的命令只是例子,不固化成 subcommand。命令面、画法、`--json` 形状、发现目录与码见本单元。

本节跨平台。各引流方式的具体形状见 §9.8。

### 9.1 在哪看(不加新命令)

| 命令 | 给什么 |
|---|---|
| `asight status` | 表格之后一段「各 harness 的路」:每个 harness 一行紧凑链;分 HTTP 与 WebSocket 走不同路的,每支一行 |
| `asight status <harness…>` | 另给每个点名的 harness 画详细拓扑:每跳一行;另加「关掉 asight 时的路」「要换代理」两行 |
| `asight doctor [harness…]` | 发现(§9.6):每条写什么、为什么、要跑的命令、怎么验证 |
| `--json` | 同一份 `topology` 对象(§9.4);看板经 `/api/capture-health` 的 `netenv.topology` 读同一份 |

- 不设 `asight net`、`asight proxy`(§8)。理由:拓扑回答的正是 `status` 那一问的「为什么」;多一个动词,用户多记一个,两处输出还会分叉。
- `doctor` 新收 harness 名(规则同 §3):用户的症状是按 agent 说的,如「codex 连不上」。

### 9.2 画法

- **一条链** = 从 agent 进程到出口的每一跳,用 `→` 连。节点写具体的东西:进程(名、pid、版本)、地址与端口;代理那一跳只写地址、端口与属主进程名和 pid,不写产品与模式。边写怎么过去(方括号:`[eBPF]` `[系统代理]` `[HTTPS_PROXY]`);代理模式下 agent 到 asight 的门那条边写入口与谁写的,如 `[.env HTTPS_PROXY · asight 写的]`、`[kimi shim · 你点名的]`。asight 自己的节点标「asight」。引流模式写在 `status` 那一段的段首,或 `status <h>` 的第一行:「驱动模式(eBPF)」或「代理模式」(D43)。
- **画新连接的路**:按 agent 现在的设置(它会读的环境变量、配置文件里的代理键、它认的系统代理)和本机网络环境算。代理设置只在 agent 启动时读;在跑的进程启动时的设置与现在不同时,另列一行「pid N 仍按启动时的设置:<链>;重启后按上面的路」。
- **关掉 asight 时的路**:同样的设置,去掉 asight 的跳。`status <harness>` 印它。asight 在路径上时,asight 之后的第一跳 MUST 等于这条链里 agent 之后的第一跳(出口不变,§9.5);不等时报 `egress-differs`。
- **读不到**:那一跳写「不知道 · <原因>」(原因是闭集,§9.4),不省略这一跳,不写「无」(R11)。按别的平台实测推断的,标「推断」。
- **判词**:每个 harness 末尾写两件事:asight 在不在路径上(是 / 否 / 不知道);被采集没有(是 / 否 + 原因码,§9.6)。只有「被采集」本身不知道时,`status` 才退出 3;单跳不知道不改退出码。
- **永远不印**:代理 URL 里的用户名与密码(印成 `***@`)。出口只写「出口」或「直连」。

`asight status` 里的一段(Linux):

```
各 harness 的路(驱动模式 · eBPF · 新连接 · 12 秒前探测 · 细节: asight status <harness>)
  claude-code  claude 4121 → [eBPF] asight 引擎 :47123 → 127.0.0.1:7890 → 出口   在路径上 · 是
  codex        codex app-server 5530 → [eBPF] asight 引擎 :47123 → chatgpt.com(直连)      在路径上 · 是
  kimi-code    kimi → api.moonshot.cn(直连)                                                 不在 · 否 · desired-off
  hermes       hermes → 127.0.0.1:7891(不知道是谁 · owner-unreadable)                        不在 · 否 · config-after-start
```

`asight status codex`(Windows,代理模式;用户的 VPN 开着系统代理):

```
codex · 开 · 代理模式 · 被采集: 是(HTTP 与 WebSocket)
新连接的路(读自 %USERPROFILE%\.codex\.env 与 WinINET 系统代理 · 12 秒前)
  codex app-server        pid 5530 · …\codex.exe 0.160.1
  → [.env HTTPS_PROXY · asight 写的]  asight 门            127.0.0.1:17992(引擎的门)
  → asight 引擎           pid 4121 · 127.0.0.1:17990 · 解密(已信任)
  → [系统代理]  verge-mihomo.exe pid 11800 · 127.0.0.1:7897
  → 出口
关掉 asight 时的路: HTTP codex app-server → [系统代理] 127.0.0.1:7897 → 出口 · WebSocket 直连
提示: WebSocket 原本直连,现在也经系统代理(egress-differs)
若你的 VPN / 代理按进程分流,它看到的来源是 asight,不是 codex
要换代理: 照常改 codex 的设置,再跑 asight on codex,把 asight 接在新代理前面;系统代理变了不用做什么
```

最后第二行就是 D43 说的那一句:asight 在路径上时,代理模式的 `status <h>` 总印它(D49:不探测是否有 VPN / 代理软件,措辞带条件);驱动模式同理(4.6 §身份与信任「引流的观测者效应」)。只有这一句:不为它另设发现码,也不读用户 VPN 的规则去找点名 asight 的那一条(不建,4.8 OPEN 24)。

### 9.4 `--json` 的形状(给 GUI)

```json
{ "topology": { "claude-code": {
  "at": "2026-10-07T10:02:12Z", "routing": "driver",
  "on_path": true, "captured": true, "reason": null,
  "nodes": [
    { "id": "a", "kind": "agent", "name": "claude", "pid": 4121, "version": "2.1.291", "path": "~/.local/share/claude/versions/2.1.291" },
    { "id": "e", "kind": "asight-engine", "name": "asight 引擎", "pid": 4012, "addr": "127.0.0.1", "port": 47123, "mode": "decrypt", "asight": true },
    { "id": "p", "kind": "proxy", "name": "mihomo", "pid": 777, "addr": "127.0.0.1", "port": 7890 },
    { "id": "x", "kind": "egress", "name": "出口" }
  ],
  "edges": [
    { "from": "a", "to": "e", "via": "ebpf", "evidence": ["link:17", "watch:4121"] },
    { "from": "e", "to": "p", "via": "proxy-http", "evidence": ["env:HTTPS_PROXY"] },
    { "from": "p", "to": "x", "via": "egress" }
  ],
  "branches": [ { "name": "all", "path": ["a","e","p","x"], "off_path": ["a","p","x"], "on_path": true, "captured": true, "reason": null } ],
  "running": [ { "pid": 3990, "path": ["a2","p","x"], "note": "start-time-settings" } ],
  "findings": []
} } }
```

| 字段 | 闭集 / 规则 |
|---|---|
| `routing` | `driver`(驱动模式)· `proxy`(代理模式)· `none`(全部关着)· `unknown`。一个平台只有一种模式(D43) |
| `nodes[].kind` | `agent` · `proxy`(用户的代理的本地入口)· `asight-engine` · `asight-forwarder`(代理模式的本地代理 = 引擎的门)· `upstream`(API 或中转 host)· `egress` · `unknown` |
| `edges[].via` | `direct` · `proxy-http` · `proxy-socks` · `proxy-https` · `system-proxy` · `ebpf` · `forward`(门到引擎)· `egress` · `unknown`。边上 `asight: true` = 这条边来自 asight 写的入口,另带 `entry: {where, opt_in}`;文本印「asight 写的」或「你点名的」 |
| `unknown` | 节点或边上 `{reason}`;`reason` ∈ `denied` · `timeout` · `absent` · `unparseable` · `owner-unreadable` · `pac` · `kernel-filter-invisible` · `env-unreadable`(Windows 读不到别的进程的启动环境,4.8 §10.1);另有 `detail` 放 errno 或探针名 |
| `inferred` | 节点或边上为 `true` 时,文本标「推断」(按别的平台实测) |
| `branches[].name` | `all` · `http` · `ws`(按 harness 文件声明的分支);一个 harness 有多个形态时(Windows),每个形态各一支,另带 `form`(形态 id;4.8 §10.1) |
| `captured` / `on_path` | `true` · `false` · `null`(= 不知道);`reason` 是 §9.6 的码 |
| 其余 | 每个节点有 `id` `kind` `name`;每条边的 `from` `to` 都是已有节点;`path` 与 `off_path` 第一个都是 `agent`;一条 `path` 里节点不重复(D43 起没有「Clash → asight → Clash」的路) |

- 文本只从这个对象渲染,不另算(V43)。键名与闭集放 `src/cli/schema.mjs`(R5)。`status --json` 带 `topology` 与 `opt_in`(下);`doctor --json` 带 `findings`(§9.6)。
- **拓扑造不出来时**(这个构建没有接上事实读取者,或建图那一步抛了):`status --json` 没有 `topology`,带 **`topology_error`**(一句原因的字符串);文本在原处写「各 harness 的路: 不知道(<原因>)」,什么也不画。表(`harnesses`)与退出码不变:拓扑是 `status` 的解释,不是它的判词(R11:读不到写不知道,不写「无」;§9.2「单跳不知道不改退出码」同理)。

**`opt_in`(点名项,§1.7)**:跟 `topology` 并列,按 harness 分;自动写的项(`scope:'agent'`)不在里面。

```json
{ "opt_in": { "kimi-code": [
  { "form": "kimi-code.cli", "kind": "optin-user-path", "scope": "user", "admin": false,
    "state": "needed", "code": "opt-in-needed", "reason": null,
    "implies": "本用户所有程序看到的 PATH 顺序变了;只有同名命令 kimi 解析到 asight 的 shim",
    "enable": "asight on kimi-code --opt-in kimi-code.cli", "undo": "asight off kimi-code", "elevated": null }
] } }
```

| 字段 | 闭集 / 规则 |
|---|---|
| `form` | 形态 id(§3 的写法) |
| `kind` | 清单里的种类名;各平台单元定(Windows:[4.8](4.8-win-collector.md) §2.4 的表) |
| `scope` · `admin` | `user` · `machine`;`admin` 为 `true` 当且仅当要管理员权限(= `scope:'machine'`) |
| `state` | `needed`(没点名)· `done`(做了,入口有效)· `broken`(做了,入口失效)· `pending-admin`(等用户给管理员权限)· `needs-admin`(`off` 之后机器级的还没撤)· `unknown`(核对不了) |
| `code` | `needed` → `opt-in-needed`;`broken` → `shim-not-on-path` · `entry-changed` · `not-via-entry` 之一;`needs-admin` → `needs-admin`;其余 `null`。都取自 §9.6 的目录 |
| `reason` | `unknown` 时的原因(同 `unknown.reason` 的闭集);其余 `null`。读不到不写「无」(R11) |
| `implies` | 「影响」那一行,与 `on` 的计划里那一行逐字相同(`--yes` 不换它) |
| `enable` · `undo` | 填好值的整行命令:`enable` 含 `--opt-in <形态>`;`undo` 是 `asight off <harness>`,也是唯一的撤销动作(§1.7「界面上没有按条撤销」)。`elevated`:没有提示可弹时的那一整行提权命令(退路,§1.7;有提示可弹的机器上是 `null`——正常路径是确认后操作系统自己的提权提示) |

**`install` · `cert` · 每个形态的 `certificate` / `proxy`(D55)**:`install --json` 与 `status --json` 都带顶层 `install`(安装的状态)与 `cert`(整机的证书块);`status --json` 另在每个 harness 的每个形态下分开 `certificate` 与 `proxy` 两项,两条轴互不牵连(D55①:证书是装好时验一次的性质,代理是开关)。文本从它渲染,不另算(同 V43)。

### 9.5 用户自己的代理

用户的要求:自己的代理照常工作、出口不变;换代理的过程要顺;asight 不悄悄覆盖用户的设置;不为此固化一个子命令。下表是做法:

| 规则 | 内容 |
|---|---|
| 唯一来源 | 「用户的代理」= agent 自己会用的那个:它读的环境变量、配置文件里的代理键、它认的系统代理。读哪些由 harness 文件声明(§9.7)。asight 没有另一处记它,用户不用告诉 asight 两遍。 |
| 接上 | `on <harness>` 读该 harness 现在的网络设置,把 asight 接在 agent 与它原本的下一跳之间;asight 的上游 = 那个下一跳(用户的代理或 API host)。驱动模式(eBPF):不写任何网络设置,引擎按原目的地转,CONNECT / SOCKS 原样转给用户的代理(4.6 §引擎 第 3 步)。代理模式:把 agent 的代理入口指向引擎的门;上游 = agent 自己的代理(原值),没有就是它跟随且开着的系统代理,再没有就直连(D43;4.8 §2.2)。计划与回执各印一行接上后的链,凭据打码。 |
| 记下接上的是什么 | `on` 在 `~/.asight/netenv.json` 写 `adopted.<harness> = {at, routing, chain, source:[{kind:'env'\|'file'\|'system-proxy', where}], sha256}`。`chain` 是打码后的紧凑链;`sha256` 是原始设置值的哈希,不存原值(原值里可能有密码)。 |
| 发现漂移 | `status`、`doctor` 和守护进程用同一读法重读设置,与 `adopted` 比。守护进程在 4.6 §开关语义的 5 s 核对里一起做,先比这些文件的 inode / 大小 / mtime。设置不同 = `proxy-changed`。系统代理变了(开、关、换端口)= `netenv-changed`(D49:只此一种):代理模式下守护进程按新的系统代理重算上游,写一条 `netenv-change`,不算失败,不碰 agent 的设置。各写一条 `netenv-change` 事件;让期望为开的 harness 采不到时,另写一条 `failure`(§9.7)。没有守护进程的平台上,由 `status` / `doctor` 与上次的 `netenv.json` 比。 |
| 漂移之后 | `status` 画出新的路,说清 asight 还在不在路径上,印那一条接上的命令(已有命令)。eBPF:新进程照常被采,不用做什么,只列「在跑的 pid N 仍按旧设置,重启后按新的」。代理模式:agent 的代理字段被改(不再指向 asight 的门)= 它已绕过 asight,印 `asight on <harness>`(把新代理记成上游,再指回 asight 的门);系统代理变了不用做什么(上一行)。 |
| 不悄悄覆盖 | 只有操作者跑的 `on` 会写 agent 的网络设置。`status`、`doctor`、守护进程只读、只报,MUST NOT 改回。`on` 要改写用户在上次 `on` 之后改过的网络设置时,像 §1.6「多出来的文件」一样列进计划、再确认(R6);不在终端又没有 `--yes`:只打印计划,退出 2,什么都不写。 |
| `off` 留下用户的设置 | `off` 只撤 asight 写的值(R2「只撤 asight 的部分」):字段仍是 asight 的值,就回到接上时的原值;用户之后改过,就不动,回执写「你改过,没动」。驱动模式下 `off` 不碰任何网络设置。 |
| 不加命令 | 换代理 = 照常改 agent 的设置(或 VPN),需要时再 `on <harness>`。没有 `asight proxy`。以后真有「不改 agent 设置、只换 asight 的上游」的需要,再进 Extensions,并写明是什么需要。 |

**实现要点**:

- `adopted.<harness>` 实际存 `{at, routing, chain, source:[{kind, where, key?}], sha256, file_sha256, file_paths, proxy, written_sha256?}`:`proxy` 是打码后的设置(`http://***@proxy.corp:8080`;「仍按启动时的设置」要它),`file_sha256` 是只算文件那一部分的哈希(守护进程没有 agent 的环境变量,只能比文件),`file_paths` 是 `on` 读到那些文件的路径(按描述符 `proxy.files` 的顺序;`CLAUDE_CONFIG_DIR`、`CODEX_HOME` 这类由 `on` 所在 shell 的环境定下的路径,守护进程没有那个环境,所以按记下的路径 stat 与读,`on`、`status`、`doctor`、守护进程读的是同一批文件),`written_sha256` 只在路由拥有代理字段时有(`on` 写进字段的值的哈希,用来把用户的改动与 asight 自己写的分开)。设置没变的第二次 `on` 不重写(R9,回执的 `created` 里没有 `netenv.json`)。`netenv.json` 的写入合并:探测的键整体替换,`adopted` 与未重画的 harness 的 `topology` 保留。
- 驱动模式的计划与回执各印一行「接上后 <h> 的路: <链>(它的代理设置 <打码>,读自 <文件与键>)」;链是把期望态、link、入口当作已就位(`projectedOn`)算出的新连接的路。`--dry-run` 同样印,不写。
- **漂移只比文件**(`status` / `doctor` 与守护进程同一读法):用户改的是 agent 的配置文件;跑 `status` / `doctor` 的那个 shell 里导出的 `HTTPS_PROXY`、或 `on` 当时的 shell 里有而现在这个没有,都不是用户改了什么,不报 `proxy-changed`(新连接的路仍按这个 shell 读到的画,那是「新进程从这个 shell 启动会走的路」)。**期望态为 off 的 harness 不报漂移**(守护进程不核对,`diagnose` 不给 `proxy-changed` / `netenv-changed`):`off` 之后 asight 不在它的路径上,它的设置怎么改都不是 asight 的事;`off` 不清 `adopted.<h>`(`src/off/` 只 import `node:*`,不碰 `netenv.json`),下一次 `on` 重写它。
- 路由契约(代理模式,由其平台经 `deps.routing` 注入):`{ownsProxyField(h), fieldOf(h) → {path, key}, adopt(h, setting)}`。入口的写与上游的取在守护进程里、同一次 `on` 请求内完成(上游取自它对同一批文件的读)。`on` 在确认之后、`turnOn` 成功之后,对拥有字段的 harness 调 `adopt(h, setting)`,平台一侧的 `adopt` 是核实这一半:入口在账里的组,字段必须是引擎的门的地址,核实不过或抛错 = 这次 `on` 没做完(退出 1,点名该 harness,不记 `adopted`);之后读字段记 `written_sha256`。用户在上次 `on` 之后改了字段(现值的哈希既不是 `written_sha256` 也不是 `file_sha256`):计划里列「你改过的代理设置」,要确认(R6)。字段的清单项、备份与 `off` 的撤销由平台写(R2)。
- 守护进程的 5 s 核对只比「每个已接上的 harness 的代理设置文件」(先 stat 的 inode / 大小 / mtime;只读;同一漂移只记一次,重启守护进程后会再记一次),漂移的语义取自**记录本身**(`routing` 为 `proxy`、或带 `written_sha256` 的记录 = 路由拥有代理字段:与 asight 写进去的值比,别的值绕过 asight;其余按 `on` 找到的值比,harness 照旧被采)而不是平台模块的某个属性——守护进程没有自己的 routing,平台模块也不必声明一个(`driftRoutingOf`),不探测 VPN。`netenv-changed` 是系统代理变了的事件码(D49):代理模式下由那个平台的监视器调 `recordDrift`(`netenv-changed`,`captured: true`,一条事件、零条 `failure`)。

### 9.6 `doctor` 的发现

每条发现:`{code, class, harness?, what, why, commands:[{run, shell}], verify}`。`class` ∈ 失败(让看板指示变 ⚠,同 D38)· 预期 · 提示。`shell` ∈ `sh` · `powershell` · `gui`(界面操作,写菜单路径)。

- 先给 asight 命令,再给应用或 OS 里的步骤。命令是填好值、可直接复制的整行:pid、端口、路径都填上。某个值读不到时,写「不知道 · 原因」,并给出读它的命令;不留 `<占位符>`。
- `doctor` 只读(V50),一条也不替用户执行(R8)。
- **发现算不出来时**(拓扑没造出来,或这个平台没读事实,或 `diagnose` 抛了):`doctor --json` 的 `findings` 是 `null`,另带 **`findings_error`**(一句原因;拓扑没造出来时就是 `topology_error` 的那句);文本写「发现(网络与采集): 不知道(<原因>)」,不写「没有」。`null` 与 `[]` 不混:`[]` 是读了、没有发现。退出码不变(§2 `doctor` 一行)。
- `doctor <harness>` 只报该 harness 的;不带名字报全部,再加本机的。
- agent 连不上、又找不到具体原因时,报 `cause-unknown`,第一条命令是 `asight off <harness>`:off 保证(§1.2)之后 asight 不在它的路径上,再试仍连不上,就与 asight 无关。

**实现要点**:

- 驱动模式的 `proxy-changed`(预期类)**没有要跑的命令**(V47 (a)):`commands` 里只有一步「无需操作:…」(`gui`,schema 要求预期类也写做什么,什么都不用做就是做什么),怎么看新的路在 `verify`(`asight status <h>`);代理模式的同一条是失败类,第一条命令 `asight on <h>`。V49 的「asight 的命令在前」只对有命令可跑的发现查。
- **要重启的发现**(未信任原因里要重启的几个、`negative-cache`):第一步是 harness 文件 `proxy.restart.hint`(应用里的步骤);`restart.managed: true`(设置活在它的窗口不会结束的托管进程里,目前只有 Codex 的 app-server)时,第二步是填好 pid 的命令 `kill <pid>`(Windows `Stop-Process -Id <pid>`),pid 取自事实里该进程(`restart.processes` 去掉旗标后的名字对得上的进程,不含 TUI);那个进程没在跑,就没有第二步。
- 命令里「设置的文件与那一行」取自**这个设置自己的来源**(`setting.source[0]`):来自启动它的 shell 的变量就给 `unset` / `export <变量>`(不指任何文件);来自第二个文件就指那个文件和实际命中的键;没有来源(还没有这个设置,如 PAC 之后要写一个具体地址)才给 harness 读的第一个文件,再没有就给它读的第一个环境变量(`behaviour.env`)。一个步骤一个动词:删就是「删掉 <文件> 里的 <键>」,改就是「<文件> 里的 <键> 写成 "<值>"」。
- 目录在 `src/netenv/findings.mjs` 的 `FINDINGS`(每个码一项:类、`asightFirst`、`what` / `why` / `commands` / `verify`)与 `diagnose({facts, topology, harnesses, user})`;`doctor` 与 `status --json` 的 `topology.<h>.findings`(码的列表,给看板)用同一个函数。§9.3 的每一行各自只给出表里写的码(测试逐行对)。每个未信任原因(4.6 `TRUST_REASONS`)是一条发现:要重启的几个为预期类,其余为失败类,命令是 harness 给的重启办法或守护进程给的提示。
- `cause-unknown` 只回答被点名的 harness(症状是用户按 agent 说的,§9.1),期望态为开、已安装、且这个 harness 没有任何失败类或预期类发现(它们已经说了为什么)时才报;不带名字的 `doctor` 不报它。**它是提示,不是失败,措辞是条件句(「如果 <h> 仍连不上:…」)**:asight 没有一项事实说得出「这个 agent 连不上」(那要读失败记录,而各事件不都带 harness),点名只表明用户的症状;所以对一个被采集、一切正常的 harness 不断言它连不上,也不让看板指示变 ⚠。它的类别定为提示;要把它做成「有症状才报」,得先有一项读得到的症状(如该 harness 近 24 小时的失败记录),那是另一件事。
- 失败类发现让 `doctor` 退出 1(R4「1 = 发现问题」;§2 的 `doctor` 一行随之改写);其余发现不改退出码,无法判定仍是 3。§9.3 第 21、22 行的判词照 §9.2:「在路径上」取 asight 自己的事实,一个读不到的下一跳只让那一跳写「不知道」。
- `opt-in` 的 `pending-admin` / `needs-admin` 两态,拓扑的判词原因是 `not-routed`(状态原因的闭集里没有 `needs-admin`),发现是 `needs-admin`,命令是该项 `elevated` 的整行。

**事实的形状(`NetFacts`;一切打印与 `--json` 的拓扑都由它算出)**——`src/netenv/facts.mjs` 文件头是权威,这里记接口:

- `gatherNetFacts({platform, home, env, harnesses, status, netenv, archFacts, adopted, now, fs, deps})` 把 `status` 已读到的(期望态、守护进程、link、入口、进程)、各 harness 文件的 `proxy` 导出(行为)、现读的代理设置(`readProxySetting`:先文件后环境变量,与 agent 同序;读不出的文件是 `{unknown}`,不是「没有」)与平台的 `archFacts(ctx)` 拼起来。平台部分返回 `{routing, listeners?, procs?, forwarder?, forms?, systemProxy?, otherRedirector?, fakeIp?, unknowns?}`;抛错(不含测试守卫的拒绝 `ESANDBOX`)让 `routing` 变 `unknown` 并写明原因;没有 `archFacts` 的平台 `routing: 'unknown'`。读不到的事实进 `unknowns: [{fact, reason, detail}]`(闭集 `UNKNOWN_REASONS`),不留空。
- 代理模式的平台(Windows:4.8 §10.1;macOS 照 4.9 §9)要给:`routing: 'proxy'`;`forwarder: {pid, up, forms: {<形态>: {h, port, state, upstream, source, clients, upstream_error?}}}`(这一跳就是引擎的门:`pid` 是守护进程的,`up` = 守护进程答了,`state` ∈ `on` · `forward-only`(carried 的门),`clients` = 仍连着这扇门的 pid);每个 harness 的 `forms: [{id, setting, systemProxy, follows?, procs, entry: {where, asight, opt_in, intact} | null, optIn: {state, code, enable, form?, elevated?} | null, routeLoop?, route?, entryPlace?}]`;`procs[].elevated`。`routeLoop: true` = 平台拒绝接这个形态(上游会是 asight 自己);`upstream_error` = 引擎拨不通上游(平台的最近 60 s)。`route: {reason, code?, why?, detail?, protocol?}` = 这个形态所在组的采集计划(`planRoutes`)留给 doctor 的判词字段(`code` 缺省等于 `reason`;`upstream-protocol` 在 doctor 里的名字是 `proxy-unsupported`);`entryPlace` = 该组代理入口所在的位置(按 harness 文件的 `proxyEntry` 算:`{kind:'file', file, format:'json'|'dotenv', key}` · `{kind:'shim', command}` · `{kind:'policy', path, name}` · `{kind:'launcher', shortcut}` · `{kind:<组名>}`),doctor 的「把代理设成…」一步按它给文件与键。
- Linux(`src/collector/arch/linux/netfacts.mjs`,`routing: 'driver'`)读:各 harness 的进程与 watch 表的判词(`decrypt` / `no-decrypt` / `absent`)、进程启动时的代理(只读**该 harness 自己的** `proxy.env` 里的键、按它的顺序,别的键对它不是设置:claude-code 不读 `ALL_PROXY`,z-code 只认 `ZCODE_HTTP_PROXY`;与现在的设置比;设置来自文件的、文件在进程启动之后才变的,用 `adopted` 里记的)、`ss -ltnpH` 的监听与属主(别人的进程列不出属主 = `owner-unreadable`)(不读默认路由与网卡:不感知 TUN,D49)。Linux 的系统代理(gsettings / kioslaverc)不读(`proxy.measured.linux`:claude-code 是 `lab`——V54 让真的 `claude -p` 经 settings.json `env.HTTPS_PROXY` 指向的 CONNECT 代理出去、测过这条路;其余 harness 是 `inferred`,没有已知的 harness 在 Linux 上跟随它;所以 Linux 上 `doctor claude-code` 不再带「按别的平台实测推断」那条提示,别的 harness 仍带)。**NO_PROXY**:读在跑进程自己的 `NO_PROXY` / `no_proxy`(4.6 表里那几个键,只留「它盖住了该 harness 的哪几个 API host」),没有进程就读当前 shell 的;盖住了 API host 而 agent 有自己的代理时,拓扑加一条说明(「`NO_PROXY` 里写了 <host>:<h> 对它可能不经代理直连(各 harness 认不认 `NO_PROXY` 还没逐个测),这里按它的代理设置画」)——不改画出来的路,因为认不认没测过(**OPEN**:实测哪个 harness 认之后,再改成画直连并标「推断」/「实测」)。**`https://` 代理**:agent 自己的设置里的 `https://` 代理,引擎终结外层 TLS 后把里面的 CONNECT 原样转(4.6 §引擎 第 3 步),所以这条边写 `[CONNECT 原样转 · https 代理]`;4.6 表里「透传 · https 代理」那一种是代理 host 不取自该进程自己的设置(守护进程没告诉引擎),Linux 的事实里只有来自环境变量与 harness 文件的代理,画不出它;系统代理里的 `https://`(代理模式)归 4.8。
- `doctor` / `status` 跑的 OS 工具只有只读的查询:Linux `ss` `gsettings` `ps`,macOS `scutil` `lsof` `ps`,Windows `netstat` `reg query` `schtasks /Query` `where.exe`(不用 `Get-NetTCPConnection`,4.8 E6);`bpftool` 与 `netsh` 只印给用户,不跑。`src/netenv/` 里除 `writeNetenv` 之外没有写调用(4.7 N15 的守卫在 Windows 分支),也没有自己的连接。
- 每个 harness 文件的 `proxy` 导出:`{env, files: [{path, format, keys}], systemProxy: {http, ws}, schemes, unsupported: {<协议>: 'silent-direct' | 'fails'}, branches, measured: {win32, linux, darwin}, restart: {hint, processes}}`;`loadHarnesses` 对形状检查。`unsupported` 为 `silent-direct` 的协议(dsh 的 SOCKS),拓扑把它画成直连并标「推断」(未在本平台实测时)。

## 验收(可跑 check)

单元测试走 `npm test`,在 `mkdtemp` 沙箱 HOME 里跑,信任库、`launchctl`、`systemctl`、进程管理器都注入(0.1 §3「不碰真实机器」);标 [VM] 的在测试机上跑。验收编号不复用;缺的号码是已删除的条目。

1. **V1 守护进程不在时 off**:`on` 后杀掉守护进程,再 `off`:每个入口回到 `pre_sha256`(用户改过的报「已撤销,但不逐字节相同」),退出 0,全程没有拉起守护进程。
2. **V2 独立撤销程序**:把源码目录挪走,`~/.asight/bin/asight-off` 撤净同样的入口,输出与 `asight off` 一致。
3. **V3 回执 == 实际改动**:回执(与 `--json`)列出的文件集合 == 实际被写的文件集合(并入 4.6 T10)。
4. **V4 [VM] off 保证**:`off` 返回、在途响应结束后 `kill -9` 守护进程:受管 agent 的新连接零失败,看到上游真实证书;`bpftool link` 里没有本实例的 link。
5. **V5 按 harness**:`off claude-code` 只撤 claude-code 的入口,其余 harness 的入口逐字节不变、仍被采集;`--json` 只印代码 id;别名 `claude` 与 `claude-code` 结果相同。
6. **V6 用法错误**:未知命令、未知 harness、旧旗标 `--proxy`:退出 2,沙箱 HOME 逐字节不变。
7. **V7 非终端的 install**:不带 `--yes` 只打印计划(含 D55 的代价一行)、什么都不写、退出 2;带 `--yes` 才写。`--dry-run` 什么都不写、退出 0,回执与正式执行一致。要改的文件不在 `confirmed_paths` 里的 `on` 同样:不带 `--yes` 只印、退出 2、零写入。
8. **V8 备份**:备份目录 0700、文件 0600;文件验证回到 `pre_sha256` 后备份被删;用户改过的文件的备份留下并列出;`uninstall` 之后 `~/.asight/backup/` 不在(撤不掉的入口除外),回执列出「不逐字节相同」的那些;备份写不进时用户文件逐字节不变、有 `backup-failed` 事件。`off` 之后清单的 `kept_backups` 含被留下的那条,再次 `on` 不覆盖它的备份文件;「早已还原」而备份还在时,备份被删。
9. **V9 `--json`**:每个命令的输出过 schema 校验;stdout 只有一个 JSON。
10. **V10 不知道**:连接数、网络环境、守护进程状态读不到时 `status` 印「不知道」加原因,不印 0 或「无」。`--json` 同样带原因,不只文字:每个 harness 的 `why`(读不到什么、哪个文件、什么 errno;守护进程答了但读不出内核状态的,带它给的 `error` / `error_code`),顶层的 `state_error` / `manifest_error` / `health_error`,`relayed_reason`。`~/.asight/netenv.json`(看板读的副本)写不成也不静默:文字一行、`--json` 的 `netenv_write_error`(文件加 errno),不改判词与退出码。
11. **V11 只用内置模块**:静态检查 `src/off/` 与生成的 `asight-off` 的 import 全是 `node:*`(`asight-off` 内不含别的 import)。
13. **V13 卸载不代做 off,按后进先出撤**:有 harness 期望态为 on 时 `uninstall`:退出 1、`collectors-online`,注入的进程管理器与引流记到零次调用(没有写期望态、没有摘引流、没有停守护进程——不代做 `off` 的任何一步),沙箱 HOME 逐字节不变。全部 `off` 之后:空闲的守护进程经 `systemctl --user stop` 停下;撤销次序 = agent 的证书项 → 登录环境载体 → 合并包与 `extra-*.pem` → 插件 → 信任根(按指纹)→ CA 私钥 → 单元、运行目录、清单、备份、`~/.asight/bin/asight-off`;注入根的移除被拒时私钥仍被删、清单只留那一项、退出 1 并给出移除命令;零次重启调用。
