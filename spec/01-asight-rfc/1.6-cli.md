# asight · RFC 1.6 — 命令行手册

> **这是什么**:asight 命令行的完整手册。依次是:总则(语言与版式、输出通道、退出码、确认、权限、名字、文件)、命令一览、每个命令的用法 / 行为 / 输出 / 退出码、读数据的唯一入口 `asight query`、附录(路由的画法、`doctor` 的发现目录、`--json` 的形状、性能的参考数据)。
> **受众**:用户(核对两件事:能不能一条命令关掉;输出看不看得懂)+ agent(改 `src/cli/` 与采集器命令时以本单元为准)。
> **决策**:D39(二元开关与 off 保证)· D43 · D47(引流模式)· D54(开关幂等)· D55 · D57(证书归 install,开关只管代理;macOS / Windows 的模型在 [4.11](4.11-collector-model.md))· **D58**(界面语言英文、可读性、看图验收)· **D59**(读数据只有 `asight query` 一个核心,看板是它的 HTTP 外壳;去掉 DuckDB)· **D60**(原始层按大小切段、守护进程自动封存、可编辑的流量类别)。
> **不在这里**:采集器的机制 → [4.6](4.6-process-collector.md) · [4.11](4.11-collector-model.md);存储格式 → [4.2](4.2-storage-etl.md);改包 → [5.1](5.1-intervention.md);系统代理感知 → [4.7](4.7-netenv.md)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集,`off` 撤掉 asight 对 agent 的全部影响,asight 自己坏了也能用。读数据也只有一个入口 `asight query`,看板与脚本都经它,它多快看板就多快。每条输出让人一眼看懂:先说结论,再给细节,要人做的事写成能直接复制的命令。

## 1. 总则

### 1.1 语言与可读性(D58)

- **英文**。help、计划、回执、状态、错误,以及 `--json` 里给人读的 `message`,一律英文。
- **只写用户看得懂的话**。人读输出里不出现规格节号、决策号、源文件路径、内部码名(如 `desired-off`、`uninstall/left-unparsable`)、内部机制的名字(如「门」「持有者」「负缓存」)。码只在 `--json` 里;人读文本把它说成一句话。
- **读不到就说读不到**。读不到的值写 `unknown` 加一句原因,从不印 `undefined`、`null`、`NaN`、空白,也不把陈旧的记录(比如已经不在的 pid)当成现状。
- **出错也是一句话**。错误印成一行 `asight <command>: <what went wrong>. <what to do>`,从不印程序的调用栈(调用栈只在 `--json` 的 `error.detail` 与内部错误的报告里)。
- **版式**:
  1. 第一行是结论:一句话说做了什么,或现在是什么状态。
  2. 细节用对齐的两列(短标签 + 内容)或带表头的表。一行一件事,不嵌套括号。
  3. 要人做的事写成一行能直接复制的命令,值都填好,不留占位符。一次输出最多给一两个下一步。
  4. 默认只给要紧的。更细的在 `status <harness>`、`--failures`、`--json`。
  5. 路径用 `~` 缩写家目录;本机回环地址只写端口(`:17992`)。时间:人读输出写本地时间或相对时间(`10 min ago`),JSON 写 ISO 8601 UTC。大小写 `KB` `MB` `GB`,按 1000 进位。
  6. 按 80 列排版。超长的值(路径、命令)单独成行,不折断。表格放不进 80 列就砍列:次要的数只放进 `--json`,不让表格折行。
  7. 排版符号只用 ASCII(路径与用户自己的值除外):Windows 的旧控制台显示不了别的符号。
- **颜色**:只在 stdout 是终端、且没设 `NO_COLOR` 时用。用途只有五种:标题加粗;正常用绿色;问题用红色;提示用黄色;次要信息变暗。颜色从不是唯一的信号:去掉颜色,信息一点不少。
- **看图验收**:可读性靠看,不靠比字符串。设计、实现、测试 CLI 输出的 agent,都要先把典型输出渲染成图看过,才算定稿:
  - 本机迭代用 `scripts/cli-shot.mjs`:按 80 列终端的样子,把一条命令的输出渲染成 PNG;
  - 本手册里的样例就是版式的基准。

### 1.2 输出通道

- **人读模式**:结果写 stdout;错误与警告写 stderr,一行一件事。
- **`--json`**:stdout 恰好是一个 JSON 文档,出错时也一样(用法错误、拒绝、内部错误都算);stderr 什么都不写,进程本身崩溃时除外。终端里缩进两格,管道里写成一行。
- **共有的键**:每个文档都有 `schema`(本手册定的形状是 `2`)、`command`、`ok`;出错时另有 `error: {code, message}`。其余的键各命令自己定义(附录 C)。
- **读数据的命令**:`status`、`doctor`、`classes`(显示)的 `--json`,就是对应的 `asight query <名字>` 的那个文档,一字不差,连 `command` 也是那个查询的名字(§4.1)。
- **改状态的命令每跑一次留一条回执事件**,写进 `collector/flows/`:`install` 与 `on` 写 `install-note`,`off` 写 `off-note`,`uninstall` 写 `uninstall-note`;一次运行的最后一行带 `kind:'result'`。失败的那次也写一条。写不进时先往 stderr 写一行,之后第一条写成功的记录以 `log-gap` 开头(D38)。

### 1.3 退出码

| 码 | 含义 |
|---|---|
| 0 | 做完了;或者一切与期望一致 |
| 1 | 做了,但没全做完;或者发现了问题 |
| 2 | 没有运行,什么都没碰。原因:命令、选项或名字写错;以 root 运行;需要确认,却不在终端里也没给 `--yes` |
| 3 | 判断不了,原因写在输出里。只有 `status`、`doctor`、`raw verify` 用 |
| 70 | asight 自己出错(未捕获的异常)。stderr 印一行 `asight: internal error: <message>`,再加一行怎么报告 |

不同命令的同一个码含义相同。每个命令那一节只写它会用到哪几个码。

### 1.4 确认、预演与 `--yes`

- **要确认的步骤**:改 `~/.asight` 之外的文件或删数据之前,先印计划。只有这几处:
  - `install`;
  - `uninstall`(它撤掉证书与 `install` 写过的文件;带 `--purge-data` 时还删数据);
  - 要改的文件比上次确认过的多,或要改写你改过的代理设置时的 `on`;
  - 安装记录丢了时,`off` 按标记撤文件的那一步。
- **计划写全**:计划逐个点名要改的文件(完整路径)与键,一项都不省;路径还不知道的项(比如那个 harness 没装)写明原因。
- **怎么确认**:终端里问 `Proceed? [y/N]`,`--yes` 代替回答。不在终端里(stdin 或 stdout 不是终端)又没有 `--yes`:只印计划,什么都不改,退出 2。例外是 `off` 撤文件的那一步:引流照撤,文件不动,退出 1。
- **`off` 平时不问**:它只撤 asight 自己的东西,随时能再 `on`;出事时一条命令就能完成。
- **`--dry-run`**:印出与真跑同一份回执(用将来时),什么都不写,退出 0。真跑时会在写之前停下的原因(比如还没 `install`)照样列出,在 `--json` 里是 `blocked`。
- 改 `~/.asight` 之外文件的命令(`install` `on` `off` `uninstall`)收 `--dry-run` 与 `--yes`。

### 1.5 用户与权限

- **只碰当前用户**。每个命令都只碰当前用户的东西。macOS / Windows 上没有一项要管理员;macOS 的钥匙串框、Windows 的根证书框是操作系统的同意框,不是提权。asight 不画密码框,也不经手密码。
- **改状态的命令拒绝 root**。这些命令是 `install`、`on`、`off`、`uninstall`、`daemon`、`classes set|add|rm|reset`、`raw seal`。以 root 或提升的令牌运行时,它们在读写任何东西之前就拒绝:印 `asight on: run this as your own user, not as root.`,退出 2。
  - 例外:Windows 上没有拆分令牌的账号(UAC 关闭、内置 Administrator)放行 `install`、`on`、`off`、`uninstall`。这种账号开和关用的是同一个令牌。
- 只读的命令不限。唯一要 root 的命令是 Linux 的 `sudo asight setup-helper`。

harness 的名字(输出一律印左列):

| 名字 | 输入也认 |
|---|---|
| `claude-code` | `claude` |
| `codex` | |
| `opencode` | |
| `kimi-code` | `kimi` |
| `deepseek-dsh` | `dsh` |
| `hermes` | |
| `z-code` | `zcode` |

- **不带名字**:收 harness 名的命令不带名字 = 全部。`on` 的「全部」是 `install` 记下的那些。
- **名字写错**:印 `asight on: unknown harness 'claud'. Known: claude-code, codex, opencode, kimi-code, deepseek-dsh, hermes, z-code`,退出 2。
- **形态**:同一个 harness 的不同装法叫形态(form),写成 `<harness>.<形态>`,如 `codex.cli`、`codex.app`。只在细节里出现。
- **流量类别**的名字见 `classes`(§4.2)。

### 1.7 文件

asight 在盘上的一切都在 `~/.asight/`(D27):

| 路径 | 是什么 | 谁写 |
|---|---|---|
| `raw/<段>.ndjson` · `raw/<段>.sealed` | 采集到的原始记录:正在写或刚关闭的段是明文,封存后是 `.sealed`(D60;格式见 [4.2](4.2-storage-etl.md)) | 守护进程、`raw seal` |
| `raw/journal.jsonl` | 封存与核对的记录 | 封存器、读者 |
| `index/` | 读数据时建的段索引。可以删,下次读时重建 | `query`、`serve` |
| `classes.json` · `logs/classes.ndjson` | 你的流量类别表,与它的修改记录。没有这个文件就用内置表 | `classes` |
| `collector/` | 守护进程与开关的状态:`state.json`、`install-manifest.json`、`ingress.json`、`control.json`、`lock`、`op.lock`、`ca/`、`flows/<日期>.ndjson`(连接与事件日志)、`logs/daemon-out.log` · `daemon-err.log`(守护进程自己的输出,D46)、`audit/`、`replays/` | `install` `on` `off` `uninstall`、守护进程 |
| `backup/` | asight 改你的文件之前留下的原样(目录 0700、文件 0600) | `install`、`on` |
| `bin/asight-off` | 独立的 `off`:源码目录没了、缺依赖时也能跑 | `install` |
| `agents.json` | 你自己加的 agent 进程名(可选) | 你 |
| `netenv.json` | `on` 接上的你的代理:只存打码后的链与哈希 | `on` |

- 采集数据(原始记录、`flows/`、备份)只有属主能读(文件 0600、目录 0700)。
- 读的命令不写文件:`status`、`doctor`、`query`、只显示的 `classes`。唯一的例外是可删、可重建的索引 `index/`。
- **删数据**:`asight uninstall --purge-data` 把采集数据全删。只想删一部分就从 `~/.asight/raw/` 里删封存好的段文件(`*.sealed`,每个自成一体);正在写的那个段不要动。删掉之后的查询只是看不到它们,索引自己重建。`asight query segments` 印出每个段的时间范围与大小。

```

  asight off       [<harness>...] [--now] [--yes] [--dry-run] [--json]

  asight classes   [<class>] [--json]

  asight raw verify [<segment>...] [--json]

  asight daemon     [--supervise]
```

- `asight` 不带参数 = `asight help`,退出 0。help 分上面三段;help 文本与命令分派出自同一张命令表。没有隐藏别名。
- 未知命令:印 `asight: unknown command 'frobnicate'. Run: asight help`,退出 2。不整屏印 help。
- 未知选项:印 `asight status: unknown option '--frob'`,再加一行它的用法,退出 2。
- `--version` 印 `asight <版本>`。

## 3. 采集

### 3.1 开关模型与保证(D39 · D54 · D55)

- **证书与代理分开管**。证书一次装好,放着不用也没问题,归 `install` / `uninstall`;代理是动态的,归 `on` / `off`。`on` / `off` 从不碰证书的任何字节。轮换证书 = `off` → `uninstall` → `install` → `on`。
- **off 保证**:`off` 返回、在途的响应结束之后,asight 不在这些 harness 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。做不到这条的引流方式不提供。有三种例外,如实写明;`off` 的回执与 `status` 报出它们的条数:
  1. 透传的连接,与看不到本轮结束消息的 WebSocket。asight 看不到它们的响应边界,只能等它们自己关闭。
  2. 代理模式(macOS / Windows)里,`on` 期间启动、现在还活着的进程,闲着的也算。它们的环境里记着 asight 的代理地址,所以那个端口为它们开着,只转发,不解密、不记录,直到它们退出。
  3. `asight off --now` 不等,立即切断。被切断的 agent 会看到一次连接错误,由它自己重试。
- **证书只在 agent 启动时读**。`install` 之前就在跑的 agent 要重启一次,才会被采集。在那之前它的连接照常透传,不会被弄断。`on` 与 `status` 点名这些进程。
- **不自动重启任何东西**。命令只列出要重启的进程。唯一例外是看板上的 Restart 按钮:由用户点,点了先确认。
- **幂等**。每个 harness 的 `on` / `off` 连跑两次与跑一次结果相同,不影响已经开着或已经关掉的 harness(D54)。
- **先备份,只撤自己的**。改你的文件之前先备份到 `~/.asight/backup/`。撤销时只撤 asight 改的部分,你后来改的留着。从不拿备份整文件写回,因为那会抹掉你后来的修改。撤不掉时给出备份路径与手动命令。
- **一次只跑一个改状态的命令**,靠锁 `~/.asight/collector/op.lock` 保证。`off` 优先:拿不到锁时先写下「关」,再至多等锁 10 s;正在跑的 `on` 一看到「关」就停。锁里记着持有者的 pid 与那个进程的启动时间,两者都对才算有人在跑;进程没了、或启动时间不符,就是残留,直接接管。没记启动时间的旧锁:超过 10 分钟就当崩溃残留。
- **更早版本的安装记录先拒绝**:发现更早的 asight 写的安装记录(v2)时,`install`、`on`、`off`、`uninstall` 都在写任何东西之前拒绝,连 `~/.asight/bin/asight-off` 也不覆盖;退出 1,输出点名要先用哪个程序敲干净:先用那个版本跑 `asight off`,再跑 `asight uninstall`。
- **系统代理与 VPN 只读**。asight 读 agent 自己的代理与系统代理,把自己接在原来的下一跳前面,出口不变。它不往任何 VPN / 代理软件里写东西,不改系统代理,不开 TUN(D31 · D43 · D49)。

### 3.2 `asight install`

```
asight install [--yes] [--dry-run] [--json]
```

一次性装好证书。不收 harness 名:本机找到的 harness 都装,并记进安装记录。

做什么(macOS / Windows 的次序与细节按 [4.11](4.11-collector-model.md) §1「install」,Linux 按 [4.6](4.6-process-collector.md)):

1. 先写独立撤销程序 `~/.asight/bin/asight-off`。写不进就停,什么都不改。
2. 为这台机器生成自己的根证书。
   - macOS:私钥在登录钥匙串里,只由 asight 的签名助手使用,不能导出;
   - Windows:不能导出的 CNG 密钥;
   - Linux:`~/.asight/collector/ca/ca.key`(0600)。
3. macOS / Windows:把根装成本用户信任的根。系统会弹一次框,asight 等 120 秒。
4. 让每个形态都够得到证书。用户级根够得到的,就不再用别的办法;够不到的,按 harness 描述符写配置键、放 Kimi 的包装,或放 DeepSeek 的插件。如果你的设置已经指向你自己的证书文件,就在那个文件末尾追加一段带标记的内容,设置本身不动。从不写登录环境变量。
5. 记下安装记录与判活快照。

- **计划**:先印计划,再确认(§1.4)。计划列出:要写的每个文件与键、要建的东西、每个形态的证书载体(或够不到的原因)、要弹的框、跳过的 harness、要重启的进程。计划末尾总是印这一行:
  ```
  While installed, programs you run trust certificates issued by this machine's asight root. Remove it: asight uninstall
  ```
  macOS / Windows 另印一行风险:
  ```
  Any program running as you can ask asight to issue a trusted certificate, but cannot copy the key. If you suspect misuse: asight uninstall, then asight install.
  ```
- **幂等**:再跑一次 `install` 不改任何字节,不生成第二把密钥,也不弹框(先按指纹读回已有的根)。它也用来补装:新装的 harness、被 agent 安装器盖掉的包装、被删的证书文件。
- **已经到位的项不重写**:`install` 与 `on` 遇到哈希与记下的相同的项就跳过,它的 `installed_at`、inode 与修改时间都不变。重写会把那些已经在跑、已经被采集的进程判成「启动在证书之前」,从此悄悄不再被采集。
- **系统框的结局**:
  - 你点了拒绝,记为 declined;
  - 超时,或没有图形会话(比如经 ssh 跑),记为 pending;
  - 工具答成功、读回却没有信任,也记为 pending。

  遇到这些情况,其余项照装,退出 1,并印出要再跑的命令;不改用别的证书载体。macOS 上密钥要图形登录会话:经 ssh 跑时,密钥这一项记为 pending,提示你在图形会话的终端里再跑。
- **更早版本的安装记录**:四个开关命令统一拒绝,见 §3.1。

```
If asight itself breaks: ~/.asight/bin/asight-off
```

退出码:0 全部装好 · 1 有项没装上 · 2(§1.3)。`--json` 的键见附录 C「install」。

### 3.3 `asight on`

```
asight on [<harness>...] [--no-autostart] [--yes] [--dry-run] [--json]
```

开始采集这些 harness。

- **前提**:没跑过 `install`(没有可用的根,或没有安装记录)时拒绝,印 `asight on: certificates are not installed. Run: asight install`,退出 1。macOS / Windows 上某个 harness 的证书项缺了或被改了,只拒绝这一个,提示再跑 `asight install`。
- **做什么**:
  - Linux:挂上引流,不写 agent 的任何文件。
  - macOS / Windows:先让守护进程开好这一组的本地代理端口并读回,再把 agent 自己配置里的代理指向它,或建开关文件([4.11](4.11-collector-model.md) §1「on / off」)。崩在任何一步,都不会留下指向没开的端口的设置。
  - 启用登录自启,拉起守护进程(已在跑就不动它)。`--no-autostart`:只拉起这一次,不设登录自启(Linux 上没有 systemd 用户实例时用它)。
- **接上你的代理**:asight 的上游,就是没有 asight 时 agent 会走的下一跳:你的代理、系统代理,或直连。回执给每个 harness 印一行接上之后的路,凭据打码。
- **要确认时**(§1.4):要改的文件比上次确认过的多(比如新装的 harness、新的 `CODEX_HOME`),或要改写你在上次 `on` 之后改过的代理设置。这时列出来,再确认。
- **之后的效果**:
  - 新启动的进程都会被采集。
  - 证书对它不生效的形态(根待定、够不到、还没在实验室验过)照样经 asight,但只转发;回执点名原因。
  - `on` 之前就在跑的进程照常直连。回执与 `status` 把它们列在 `Restart to capture` 下,列出的是真正发请求的那个进程(比如 Codex 的 app-server)。
- **登记过的副作用照实写**:
  - VS Code 的代理设置会让 VS Code 里所有扩展都经 asight,只转发;
  - OpenCode 会为 asight 的插件在自己的配置目录里装依赖,`off` 之后这些依赖还在。
- **linger**:Linux 上没开 linger 时多印一行:`Capture stops when you log out. To keep it on: loginctl enable-linger alice`。
- **排空中又 `on`**:不带名字的 `off` 正在让守护进程排空时跑 `on`,排空就取消,守护进程接着服务。

```
Capturing claude-code and codex. Daemon running (pid 4012); it starts at login.

  claude-code  ~/.claude/settings.json: env.HTTPS_PROXY -> asight (was: none)
  codex        ~/.codex/.env: HTTPS_PROXY -> asight
               (was: http://***@proxy.corp:8080)
               route: codex -> asight :17992 -> proxy.corp:8080 -> internet

Restart to capture: codex (pid 5530 started before capture was on)
Stop: asight off
```

退出码:0 都开了 · 1 有 harness 没开成 · 2(§1.3)。`--json` 的键见附录 C「on」。

### 3.4 `asight off`

```
asight off [<harness>...] [--now] [--yes] [--dry-run] [--json]
```

撤掉 asight 在这些 harness 路径上的一切。不带名字 = 全部 harness,并且停用自启、让守护进程排空后退出。

- **撤什么**:
  - Linux:摘掉引流。
  - macOS / Windows:撤掉 agent 配置里的代理,删掉开关文件。改过的文件回到 `install` 之后的样子;你在 `on` 期间改过的键原样留着。
  - 证书一项不碰,归 `uninstall`。不杀、不重启 agent。
- **次序**:每次 `off` 都是这个次序:先写下「关」,再摘引流并读回确认,确认之后才撤文件。停守护进程的次序按平台:macOS 的 `off` 只停用 LaunchAgent、从不 `bootout`(见 [4.9](4.9-macos-collector.md) §4「开与关(launchd)」);Windows 先停监管父进程、再停守护进程(见 [4.8](4.8-win-collector.md) §4.2「off 保证」)。
- **在途的连接**(D39):
  - 空闲的连接立即关。
  - 有响应在途的,把响应收全、转完再关:先发 FIN,至多等 5 s。
  - WebSocket 在本轮的结束消息处关。
  - 透传的连接等它自己关。
  - 被改包规则扣着的请求,原样放行。
  - 响应头还没转出时,asight 可以在这条最后的响应上加一行 `Connection: close`,让客户端不再复用这条连接。这一行记在那条记录上,看板上会标出来(不变式 4)。
  - 已经收到的字节全部转完,再发 FIN。客户端还有没读的字节留在缓冲里时,从不 RST。
  - 从不自己造 WebSocket 的结束帧。
  - 除了上面记下来的那一行 `Connection: close`,asight 不往连接里写任何属于自己的字节。
- **`--now`**:不等,立即切断这些 harness 仍经 asight 的连接;被切断的连接记录标 `cut-by-off`。不带名字时,守护进程随即退出。
- **不依赖守护进程**:守护进程不在、卡住或还在启动时,`off` 照常完成;卡住的守护进程先被停掉。
- **不依赖源码**:源码目录没了也能撤,用 `~/.asight/bin/asight-off`,参数与输出都和 `asight off` 相同。
- **安装记录丢了或读不了**:按 asight 写的标记撤。只认这几样:代理块自己的标记、指向 asight 的值、asight 建的开关文件。引流照摘;撤文件那一步要确认(§1.4)。撤完之后,坏的记录文件留在原处,回执写明它在哪。
- **撤不掉的文件**(标记被改坏、文件解析不了):不动它,退出 1,给出备份路径、手动恢复的命令,并说明那样会丢掉什么。
- **你自己起的 `asight serve`** 不停,回执把它列出来。

```
Capture is off for all harnesses. asight is no longer on their path.

  claude-code  ~/.claude/settings.json restored
  codex        ~/.codex/.env: asight's lines removed; your later edits are kept

The daemon (pid 4012) exits after 2 open responses finish.
Still connected through asight, forwarded only: codex (pid 5530).
asight exits when it does.
Cut them now: asight off --now
Certificates stay installed. To remove them: asight uninstall
```

退出码:0 引流已确认摘掉、入口都撤了(还在排空的连接不算没做完)· 1 有没撤掉的 · 2(§1.3)。`--json` 的键见附录 C「off」。

## 6. 系统代理感知(CLI 一侧)

D49:asight 只需感知代理设置,以免打破用户原本设置的正确的 proxy 链路;不识别、不显示 VPN / 代理产品。1.6 只定 CLI 一侧的三条要求:

- **读什么**:`status`、`doctor`、`on` 读 agent 自己的代理设置(harness 文件 `proxy` 声明的键、入口原值、Linux 上进程的 environ)与 OS 系统代理(Windows 注册表、macOS `scutil --proxy`;Linux 不读),再读代理端口在监听表里的属主进程名与 pid。只读;不读也不印代理凭据(URL 里的用户名密码印成 `***@`)。读不到 → 「不知道」加原因,MUST NOT 报「无」。读法与落点见 [4.7](4.7-netenv.md) §1。
- **不写**:asight 不往任何 VPN / 代理软件里写东西、不改系统代理(D43②),所以清单、备份、回执里没有这类条目。守卫:test V23。
- **看板**:`~/.asight/netenv.json`(0600;不放进 `~/.asight/collector/`,没有新采集器的平台也写)只含 `adopted`(接上记录,§9.5)与 `topology`(§9.4),经 [4.4](4.4-server.md) 只读数据面(`/api/capture-health` 的 `netenv` 字段)读取。`status` 与 `doctor` 写它(只在 `~/.asight` 已经存在时:没装过 asight 的机器上它们不建任何东西);`on` 只在记 `adopted` 时写它。

**参见**:读法在 [4.7](4.7-netenv.md)(Windows)与 [4.9](4.9-macos-collector.md) §8(macOS);D31⑤「不依赖、不修改用户的 VPN 软件」成立(D43)。代理模式里系统代理只决定 asight 的上游([4.8](4.8-win-collector.md) §2.2 · [4.9](4.9-macos-collector.md) §2.2)。

## 8. CLI 不该有的

|---|---|
| `restore`,或任何把「关」和「撤」分开的命令 | 用户分不清「关」和「撤」 |
| 做不到 off 保证、又没在 §1.2 登记例外的引流方式 | §1.2;代理模式的例外登记在 §1.2「例外二」 |
| `ca rotate` | 轮换 = `off` → `uninstall` → `install` → `on`(D55) |
| 改系统代理、接管整机流量(含 asight 自己开 TUN 或当系统代理);往 VPN / 代理软件里写任何东西 | D31④⑤ · D43 |

| 拿备份自动整文件写回(`--force`、`--from-backup` 之类) | 会静默抹掉用户后来的修改;撤不掉时只给手动 `cp` 命令 |

| 非环回监听(`serve --host 0.0.0.0` 之类) | [4.4](4.4-server.md) 只绑环回 |

## 9. 网络拓扑与诊断

**来源**(D39⑩):每个 agent harness 的网络情况各画一个简单的拓扑结构,让用户看清数据的流动;把不同情况说清楚,也顺畅适应改 agent 网络配置(例如挂自己的 proxy)的需要,一目了然、容易配置,这些后面会进到 GUI 里。agent 不能正常工作或网络不同时,`asight doctor` 要给出明确的、可执行的指令。另外几条 —— 出口不变;用户直接改了 agent 的代理,asight 能发现,`status` 画出新的流向并给出接上的命令;asight 不悄悄覆盖用户的设置。产品设计取决于用户的具体需求,给出的命令只是例子,不固化成 subcommand。命令面、画法、`--json` 形状、发现目录与码见本单元。

本节跨平台。各引流方式的具体形状见 §9.8。

### 9.1 在哪看(不加新命令)

| 命令 | 给什么 |
|---|---|
| `asight status` | 表格之后一段「各 harness 的路」:每个 harness 一行紧凑链;分 HTTP 与 WebSocket 走不同路的,每支一行 |
| `asight status <harness…>` | 另给每个点名的 harness 画详细拓扑:每跳一行;另加「关掉 asight 时的路」「要换代理」两行 |
| `asight doctor [harness…]` | 发现(§9.6):每条写什么、为什么、要跑的命令、怎么验证 |
| `--json` | 同一份 `topology` 对象(§9.4);看板经 `/api/capture-health` 的 `netenv.topology` 读同一份 |

- 不设 `asight net`、`asight proxy`(§8)。理由:拓扑回答的正是 `status` 那一问的「为什么」;多一个动词,用户多记一个,两处输出还会分叉。
- `doctor` 新收 harness 名(规则同 §3):用户的症状是按 agent 说的,如「codex 连不上」。

### 9.2 画法

- **一条链** = 从 agent 进程到出口的每一跳,用 `→` 连。节点写具体的东西:进程(名、pid、版本)、地址与端口;代理那一跳只写地址、端口与属主进程名和 pid,不写产品与模式。边写怎么过去(方括号:`[eBPF]` `[系统代理]` `[HTTPS_PROXY]`);代理模式下 agent 到 asight 的门那条边写入口与谁写的,如 `[.env HTTPS_PROXY · asight 写的]`、`[kimi 包装 · 开关文件 · asight 建的]`、`[配置库 PAC · asight 写的]`。asight 自己的节点标「asight」。引流模式写在 `status` 那一段的段首,或 `status <h>` 的第一行:「驱动模式(eBPF)」或「代理模式」(D43)。
- **画新连接的路**:按 agent 现在的设置(它会读的环境变量、配置文件里的代理键、它认的系统代理)和本机网络环境算。代理设置只在 agent 启动时读;在跑的进程启动时的设置与现在不同时,另列一行「pid N 仍按启动时的设置:<链>;重启后按上面的路」。
- **关掉 asight 时的路**:同样的设置,去掉 asight 的跳。`status <harness>` 印它。asight 在路径上时,asight 之后的第一跳 MUST 等于这条链里 agent 之后的第一跳(出口不变,§9.5);不等时报 `egress-differs`。
- **读不到**:那一跳写「不知道 · <原因>」(原因是闭集,§9.4),不省略这一跳,不写「无」(R11)。按别的平台实测推断的,标「推断」。
- **判词**:每个 harness 末尾写两件事:asight 在不在路径上(是 / 否 / 不知道);被采集没有(是 / 否 + 原因码,§9.6)。只有「被采集」本身不知道时,`status` 才退出 3;单跳不知道不改退出码。
- **永远不印**:代理 URL 里的用户名与密码(印成 `***@`)。出口只写「出口」或「直连」。

```
  → 出口
关掉 asight 时的路: HTTP codex app-server → [系统代理] 127.0.0.1:7897 → 出口 · WebSocket 直连
提示: WebSocket 原本直连,现在也经系统代理(egress-differs)
若你的 VPN / 代理按进程分流,它看到的来源是 asight,不是 codex
要换代理: 照常改 codex 的设置,再跑 asight on codex,把 asight 接在新代理前面;系统代理变了不用做什么
```

最后第二行就是 D43 说的那一句:asight 在路径上时,代理模式的 `status <h>` 总印它(D49:不探测是否有 VPN / 代理软件,措辞带条件);驱动模式同理(4.6 §身份与信任「引流的观测者效应」)。只有这一句:不为它另设发现码,也不读用户 VPN 的规则去找点名 asight 的那一条(不建,4.8 OPEN 24)。

- **拓扑造不出来时**(这个构建没有接上事实读取者,或建图那一步抛了):`status --json` 没有 `topology`,带 **`topology_error`**(一句原因的字符串);文本在原处写「各 harness 的路: 不知道(<原因>)」,什么也不画。表(`harnesses`)与退出码不变:拓扑是 `status` 的解释,不是它的判词(R11:读不到写不知道,不写「无」;§9.2「单跳不知道不改退出码」同理)。

### 9.5 用户自己的代理

用户的要求:自己的代理照常工作、出口不变;换代理的过程要顺;asight 不悄悄覆盖用户的设置;不为此固化一个子命令。下表是做法:

| 规则 | 内容 |
|---|---|
| 唯一来源 | 「用户的代理」= agent 自己会用的那个:它读的环境变量、配置文件里的代理键、它认的系统代理。读哪些由 harness 文件声明(§9.7)。asight 没有另一处记它,用户不用告诉 asight 两遍。 |
| 接上 | `on <harness>` 读该 harness 现在的网络设置,把 asight 接在 agent 与它原本的下一跳之间;asight 的上游 = 那个下一跳(用户的代理或 API host)。驱动模式(eBPF):不写任何网络设置,引擎按原目的地转,CONNECT / SOCKS 原样转给用户的代理(4.6 §引擎 第 3 步)。代理模式:把 agent 的代理入口指向引擎的门;上游按 [4.11](4.11-collector-model.md) §1「on / off」的五步取,认出进程之后按连接取(4.11 §3 ⑥;「接在原本的下一跳前面」是 D43)。计划与回执各印一行接上后的链,凭据打码。 |
| 记下接上的是什么 | `on` 在 `~/.asight/netenv.json` 写 `adopted.<harness> = {at, routing, chain, source:[{kind:'env'\|'file'\|'system-proxy', where}], sha256}`。`chain` 是打码后的紧凑链;`sha256` 是原始设置值的哈希,不存原值(原值里可能有密码)。 |
| 发现漂移 | `status`、`doctor` 和守护进程用同一读法重读设置,与 `adopted` 比。守护进程在 4.6 §开关语义的 5 s 核对里一起做,先比这些文件的 inode / 大小 / mtime。设置不同 = `proxy-changed`。系统代理变了(开、关、换端口)= `netenv-changed`(D49:只此一种):代理模式下守护进程按新的系统代理重算上游,写一条 `netenv-change`,不算失败,不碰 agent 的设置。各写一条 `netenv-change` 事件;让期望为开的 harness 采不到时,另写一条 `failure`(§9.7)。没有守护进程的平台上,由 `status` / `doctor` 与上次的 `netenv.json` 比。 |
| 漂移之后 | `status` 画出新的路,说清 asight 还在不在路径上,印那一条接上的命令(已有命令)。eBPF:新进程照常被采,不用做什么,只列「在跑的 pid N 仍按旧设置,重启后按新的」。代理模式:agent 的代理字段被改(不再指向 asight 的门)= 它已绕过 asight,印 `asight on <harness>`(把新代理记成上游,再指回 asight 的门);系统代理变了不用做什么(上一行)。 |

**实现要点**:

- `adopted.<harness>` 实际存 `{at, routing, chain, source:[{kind, where, key?}], sha256, file_sha256, file_paths, proxy, written_sha256?}`:`proxy` 是打码后的设置(`http://***@proxy.corp:8080`;「仍按启动时的设置」要它),`file_sha256` 是只算文件那一部分的哈希(守护进程没有 agent 的环境变量,只能比文件),`file_paths` 是 `on` 读到那些文件的路径(按描述符 `proxy.files` 的顺序;`CLAUDE_CONFIG_DIR`、`CODEX_HOME` 这类由 `on` 所在 shell 的环境定下的路径,守护进程没有那个环境,所以按记下的路径 stat 与读,`on`、`status`、`doctor`、守护进程读的是同一批文件),`written_sha256` 只在路由拥有代理字段时有(`on` 写进字段的值的哈希,用来把用户的改动与 asight 自己写的分开)。设置没变的第二次 `on` 不重写(R9,回执的 `created` 里没有 `netenv.json`)。`netenv.json` 的写入合并:探测的键整体替换,`adopted` 与未重画的 harness 的 `topology` 保留。
- 驱动模式的计划与回执各印一行「接上后 <h> 的路: <链>(它的代理设置 <打码>,读自 <文件与键>)」;链是把期望态、link、入口当作已就位(`projectedOn`)算出的新连接的路。`--dry-run` 同样印,不写。
- **漂移只比文件**(`status` / `doctor` 与守护进程同一读法):用户改的是 agent 的配置文件;跑 `status` / `doctor` 的那个 shell 里导出的 `HTTPS_PROXY`、或 `on` 当时的 shell 里有而现在这个没有,都不是用户改了什么,不报 `proxy-changed`(新连接的路仍按这个 shell 读到的画,那是「新进程从这个 shell 启动会走的路」)。**期望态为 off 的 harness 不报漂移**(守护进程不核对,`diagnose` 不给 `proxy-changed` / `netenv-changed`):`off` 之后 asight 不在它的路径上,它的设置怎么改都不是 asight 的事;`off` 不清 `adopted.<h>`(`src/off/` 只 import `node:*`,不碰 `netenv.json`),下一次 `on` 重写它。
- 路由契约(代理模式,由其平台经 `deps.routing` 注入):`{ownsProxyField(h), fieldOf(h) → {path, key}, adopt(h, setting)}`。入口由命令行写,守护进程只开门、按连接取上游(4.11 §3 ①、⑥)。`on` 在确认之后、`turnOn` 成功之后,对拥有字段的 harness 调 `adopt(h, setting)`,平台一侧的 `adopt` 是核实这一半:入口在账里的组,字段必须是引擎的门的地址,核实不过或抛错 = 这次 `on` 没做完(退出 1,点名该 harness,不记 `adopted`);之后读字段记 `written_sha256`。用户在上次 `on` 之后改了字段(现值的哈希既不是 `written_sha256` 也不是 `file_sha256`):计划里列「你改过的代理设置」,要确认(R6)。字段的清单项、备份与 `off` 的撤销由平台写(R2)。
- 守护进程的 5 s 核对只比「每个已接上的 harness 的代理设置文件」(先 stat 的 inode / 大小 / mtime;只读;同一漂移只记一次,重启守护进程后会再记一次),漂移的语义取自**记录本身**(`routing` 为 `proxy`、或带 `written_sha256` 的记录 = 路由拥有代理字段:与 asight 写进去的值比,别的值绕过 asight;其余按 `on` 找到的值比,harness 照旧被采)而不是平台模块的某个属性——守护进程没有自己的 routing,平台模块也不必声明一个(`driftRoutingOf`),不探测 VPN。`netenv-changed` 是系统代理变了的事件码(D49):代理模式下由那个平台的监视器调 `recordDrift`(`netenv-changed`,`captured: true`,一条事件、零条 `failure`)。

**实现要点**:

- 驱动模式的 `proxy-changed`(预期类)**没有要跑的命令**(V47 (a)):`commands` 里只有一步「无需操作:…」(`gui`,schema 要求预期类也写做什么,什么都不用做就是做什么),怎么看新的路在 `verify`(`asight status <h>`);代理模式的同一条是失败类,第一条命令 `asight on <h>`。V49 的「asight 的命令在前」只对有命令可跑的发现查。
- **要重启的发现**(未信任原因里要重启的几个、`negative-cache`):第一步是 harness 文件 `proxy.restart.hint`(应用里的步骤);`restart.managed: true`(设置活在它的窗口不会结束的托管进程里,目前只有 Codex 的 app-server)时,第二步是填好 pid 的命令 `kill <pid>`(Windows `Stop-Process -Id <pid>`),pid 取自事实里该进程(`restart.processes` 去掉旗标后的名字对得上的进程,不含 TUI);那个进程没在跑,就没有第二步。
- 命令里「设置的文件与那一行」取自**这个设置自己的来源**(`setting.source[0]`):来自启动它的 shell 的变量就给 `unset` / `export <变量>`(不指任何文件);来自第二个文件就指那个文件和实际命中的键;没有来源(还没有这个设置,如 PAC 之后要写一个具体地址)才给 harness 读的第一个文件,再没有就给它读的第一个环境变量(`behaviour.env`)。一个步骤一个动词:删就是「删掉 <文件> 里的 <键>」,改就是「<文件> 里的 <键> 写成 "<值>"」。
- 目录在 `src/netenv/findings.mjs` 的 `FINDINGS`(每个码一项:类、`asightFirst`、`what` / `why` / `commands` / `verify`)与 `diagnose({facts, topology, harnesses, user})`;`doctor` 与 `status --json` 的 `topology.<h>.findings`(码的列表,给看板)用同一个函数。§9.3 的每一行各自只给出表里写的码(测试逐行对)。每个未信任原因(4.6 `TRUST_REASONS`)是一条发现:要重启的几个为预期类,其余为失败类,命令是 harness 给的重启办法或守护进程给的提示。
- `cause-unknown` 只回答被点名的 harness(症状是用户按 agent 说的,§9.1),期望态为开、已安装、且这个 harness 没有任何失败类或预期类发现(它们已经说了为什么)时才报;不带名字的 `doctor` 不报它。**它是提示,不是失败,措辞是条件句(「如果 <h> 仍连不上:…」)**:asight 没有一项事实说得出「这个 agent 连不上」(那要读失败记录,而各事件不都带 harness),点名只表明用户的症状;所以对一个被采集、一切正常的 harness 不断言它连不上,也不让看板指示变 ⚠。它的类别定为提示;要把它做成「有症状才报」,得先有一项读得到的症状(如该 harness 近 24 小时的失败记录),那是另一件事。
- 失败类发现让 `doctor` 退出 1(R4「1 = 发现问题」;§2 的 `doctor` 一行随之改写);其余发现不改退出码,无法判定仍是 3。§9.3 第 21、22 行的判词照 §9.2:「在路径上」取 asight 自己的事实,一个读不到的下一跳只让那一跳写「不知道」。
