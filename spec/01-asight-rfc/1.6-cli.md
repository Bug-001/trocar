# asight · RFC 1.6 — 命令行手册

> **这是什么**:asight 命令行的完整手册。依次是:总则(语言与版式、输出通道、退出码、确认、权限、名字、文件)、命令一览、每个命令的用法 / 行为 / 输出 / 退出码、读数据的唯一入口 `asight query`、附录(路由的画法、`doctor` 的发现目录、`--json` 的形状、性能的参考数据)。
> **受众**:用户(核对两件事:能不能一条命令关掉;输出看不看得懂)+ agent(改 `src/cli/` 与采集器命令时以本单元为准)。
> **决策**:D39(二元开关与 off 保证)· D43 · D47(引流模式)· D54(开关幂等)· D55 · D57(证书归 install,开关只管代理;macOS / Windows 的模型在 [4.11](4.11-collector-model.md))· **D58**(界面语言英文、可读性、看图验收)· **D59**(读数据只有 `asight query` 一个核心,看板是它的 HTTP 外壳;去掉 DuckDB)· **D60**(原始层按大小切段、守护进程自动封存、可编辑的流量类别)· **D63**(读归守护进程的查询工作进程,CLI 先问它、没人答就自己跑)。
> **不在这里**:采集器的机制 → [4.6](4.6-process-collector.md) · [4.11](4.11-collector-model.md);存储格式 → [4.2](4.2-storage-etl.md);改包 → [5.1](5.1-intervention.md);系统代理感知 → [4.7](4.7-netenv.md)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集,`off` 撤掉 asight 对 agent 的全部影响,asight 自己坏了也能用。读数据也只有一个入口 `asight query`,看板与脚本都经它,它多快看板就多快。每条输出让人一眼看懂:先说结论,再给细节,要人做的事写成能直接复制的命令。

## 1. 总则

### 1.1 语言与可读性(D58)

- **英文**。help、计划、回执、状态、错误,以及 `--json` 里给人读的 `message`,一律英文。
- **只写用户看得懂的话**。人读输出里不出现规格节号、决策号、源文件路径、内部码名(如 `desired-off`、`uninstall/left-unparsable`)、内部机制的名字(如「门」「持有者」「负缓存」)。码只在 `--json` 里;人读文本把它说成一句话。
- **读不到就说读不到**。读不到的值写 `unknown` 加一句原因,从不印 `undefined`、`null`、`NaN`、空白,也不把陈旧的记录(比如已经不在的 pid)当成现状。
- **出错也是一句话**。错误印成一行 `asight <command>: <what went wrong>. <what to do>`,从不印程序的调用栈(调用栈只在 `--json` 的 `error.detail` 与内部错误的报告里)。
- **版式**:
  1. 第一行是结论:一句话说做了什么,或现在是什么状态。
  2. 细节用对齐的两列(短标签 + 内容)或带表头的表。一行一件事,不嵌套括号。
  3. 要人做的事写成一行能直接复制的命令,值都填好,不留占位符。一次输出最多给一两个下一步。
  4. 默认只给要紧的。更细的在 `status <harness>`、`--failures`、`--json`。
  5. 路径用 `~` 缩写家目录;本机回环地址只写端口(`:17992`);看板的网址除外——它是要拿去浏览器里打开的,整串印出(`http://127.0.0.1:9800/`,§3.5 · §4.3 的样例)。时间:人读输出写本地时间或相对时间(`10 min ago`),JSON 写 ISO 8601 UTC。大小写 `KB` `MB` `GB`,按 1000 进位。
  6. 按 80 列排版。超长的值(路径、命令)单独成行,不折断。表格放不进 80 列就砍列:次要的数只放进 `--json`,不让表格折行。
  7. 排版符号只用 ASCII(路径与用户自己的值除外):Windows 的旧控制台显示不了别的符号。
- **颜色**:只在 stdout 是终端、且没设 `NO_COLOR` 时用。用途只有五种:标题加粗;正常用绿色;问题用红色;提示用黄色;次要信息变暗。颜色从不是唯一的信号:去掉颜色,信息一点不少。
- **看图验收**:可读性靠看,不靠比字符串。设计、实现、测试 CLI 输出的 agent,都要先把典型输出渲染成图看过,才算定稿:
  - 本机迭代用 `scripts/cli-shot.mjs`:按 80 列终端的样子,把一条命令的输出渲染成 PNG;
  - 本手册里的样例就是版式的基准。

### 1.2 输出通道

- **人读模式**:结果写 stdout;错误与警告写 stderr,一行一件事。
- **`--json`**:stdout 恰好是一个 JSON 文档,出错时也一样(用法错误、拒绝、内部错误都算);stderr 什么都不写,进程本身崩溃时除外。终端里缩进两格,管道里写成一行。
- **共有的键**:每个文档都有 `schema`(本手册定的形状是 `2`)、`command`、`ok`;出错时另有 `error: {code, message}`。其余的键各命令自己定义(附录 C)。`raw` 没有 `--json`:它印的是采集到的原始字节(§5.1),套一层 JSON 就不是逐字了。
- **读数据的命令**:`status`、`doctor`、`classes`(显示)的 `--json`,就是对应的 `asight query <名字>` 的那个文档,一字不差,连 `command` 也是那个查询的名字(§4.1)。
- **改状态的命令每跑一次留一条回执事件**,写进 `collector/flows/`:`install` 与 `on` 写 `install-note`,`off` 写 `off-note`,`uninstall` 写 `uninstall-note`;一次运行的最后一行带 `kind:'result'`。失败的那次也写一条。写不进时先往 stderr 写一行,之后第一条写成功的记录以 `log-gap` 开头(D38)。

### 1.3 退出码

| 码 | 含义 |
|---|---|
| 0 | 做完了;或者一切与期望一致 |
| 1 | 做了,但没全做完;或者发现了问题 |
| 2 | 没有运行,什么都没碰。原因:命令、选项或名字写错;以 root 运行;需要确认,却不在终端里也没给 `--yes` |
| 3 | 判断不了,原因写在输出里。只有 `status`、`doctor` 用 |
| 70 | asight 自己出错(未捕获的异常)。stderr 印一行 `asight: internal error: <message>`,再加一行怎么报告 |

不同命令的同一个码含义相同。每个命令那一节只写它会用到哪几个码。

### 1.4 确认、预演与 `--yes`

- **要确认的步骤**:改 `~/.asight` 之外的文件或删数据之前,先印计划。只有这几处:
  - `install`;
  - `uninstall`(它撤掉证书与 `install` 写过的文件;带 `--purge-data` 时还删数据);
  - 要改的文件比上次确认过的多,或要改写你改过的代理设置时的 `on`;
  - 安装记录丢了时,`off` 按标记撤文件的那一步;
  - `update`(它先关后开 harness、换代码与守护进程,§5.5)。
- **计划写全**:计划逐个点名要改的文件(完整路径)与键,一项都不省;路径还不知道的项(比如那个 harness 没装)写明原因。
- **怎么确认**:终端里问 `Proceed? [y/N]`,`--yes` 代替回答。不在终端里(stdin 或 stdout 不是终端)又没有 `--yes`:只印计划,什么都不改,退出 2。例外是 `off` 撤文件的那一步:引流照撤,文件不动,退出 1。
- **`off` 平时不问**:它只撤 asight 自己的东西,随时能再 `on`;出事时一条命令就能完成。
- **`--dry-run`**:印出与真跑同一份回执(用将来时),什么都不写,退出 0。真跑时会在写之前停下的原因(比如还没 `install`)照样列出,在 `--json` 里是 `blocked`。
- 改 `~/.asight` 之外文件的命令(`install` `on` `off` `uninstall` `update`)收 `--dry-run` 与 `--yes`。

### 1.5 用户与权限

- **只碰当前用户**。每个命令都只碰当前用户的东西。macOS / Windows 上没有一项要管理员;macOS 的钥匙串框、Windows 的根证书框是操作系统的同意框,不是提权。asight 不画密码框,也不经手密码。
- **改状态的命令拒绝 root**。这些命令是 `install`、`on`、`off`、`uninstall`、`update`、`daemon`、`classes set|add|rm|reset`。以 root 或提升的令牌运行时,它们在读写任何东西之前就拒绝:印 `asight on: run this as your own user, not as root.`,退出 2。
  - 例外:Windows 上没有拆分令牌的账号(UAC 关闭、内置 Administrator)放行 `install`、`on`、`off`、`uninstall`。这种账号开和关用的是同一个令牌。
- 只读的命令不限。唯一要 root 的命令是 Linux 的 `sudo asight setup-helper`。

harness 的名字(输出一律印左列):

| 名字 | 输入也认 |
|---|---|
| `claude-code` | `claude` |
| `codex` | |
| `opencode` | |
| `kimi-code` | `kimi` |
| `deepseek-dsh` | `dsh` |

- **形态**:同一个 harness 的不同装法叫形态(form),写成 `<harness>.<形态>`,如 `codex.cli`、`codex.app`。只在细节里出现。

### 1.7 文件

asight 在盘上的一切都在 `~/.asight/`(D27):

| 路径 | 是什么 | 谁写 |
|---|---|---|
| `raw/<段>.ndjson` · `raw/<段>.sealed` | 采集到的原始记录:正在写或刚关闭的段是明文,封存后是 `.sealed`(D60;格式见 [4.2](4.2-storage-etl.md)) | 守护进程 |
| `raw/journal.jsonl` | 封存与核对的记录 | 封存器、读者 |
| `index/` | 守护进程随写维护的段索引(D62)。可以删,下次读时重建(那次读会在 `errors` 里说它自己建了) | 守护进程(正在写的段:只追加)、封存子进程;`query` 与看板只在**封存**段的索引缺失或过期时写一份,明文段的索引它们从不写([4.2](4.2-storage-etl.md) §段索引) |
| `classes.json` · `logs/classes.ndjson` | 你的流量类别表,与它的修改记录。没有这个文件就用内置表 | `classes` |
| `collector/` | 守护进程与开关的状态:`state.json`、`install-manifest.json`、`ingress.json`、`control.json`、`board.token`(看板的每用户口令,0600,守护进程第一次托管看板时生成,[4.4](4.4-server.md))、`lock`、`op.lock`、`ca/`、`flows/<日期>.ndjson`(连接与事件日志)、`logs/daemon-out.log` · `daemon-err.log`(守护进程自己的输出,D46)、`audit/`、`replays/` | `install` `on` `off` `uninstall`、守护进程 |
| `backup/` | asight 改你的文件之前留下的原样(目录 0700、文件 0600) | `install`、`on` |
| `bin/asight-off` | 独立的 `off`:源码目录没了、缺依赖时也能跑 | `install` |
| `agents.json` | 你自己加的 agent 进程名(可选) | 你 |
| `netenv.json` | `on` 接上的你的代理:只存打码后的链与哈希 | `on` |

- 采集数据(原始记录、`flows/`、备份)只有属主能读(文件 0600、目录 0700)。
- 读的命令不写文件:`status`、`doctor`、`query`、只显示的 `classes`。唯一的例外是可删、可重建的索引 `index/`。
- **删数据**:`asight uninstall --purge-data` 把采集数据全删。只想删一部分就从 `~/.asight/raw/` 里删封存好的段文件(`*.sealed`,每个自成一体);正在写的那个段不要动。删掉之后的查询只是看不到它们,索引自己重建。`asight query segments` 印出每个段的时间范围与大小。

## 2. 命令一览

```
Capture
  asight install   [--yes] [--dry-run] [--json]
  asight on        [<harness>...] [--yes] [--dry-run] [--json]
  asight off       [<harness>...] [--now] [--yes] [--dry-run] [--json]
  asight status    [<harness>...] [--failures] [--json]
  asight uninstall [--purge-data] [--yes] [--dry-run] [--json]
  asight doctor    [<harness>...] [--json]

Data
  asight query     <name> [--<param> <value>...]
  asight classes   [<class>] [--json]
  asight classes   set <class> full|log
  asight classes   add <class> <host-regex> [<path-regex>] [--harness <harness>]
  asight classes   rm <class> [<rule>]
  asight classes   reset
  asight board

Maintenance
  asight update    [--yes] [--dry-run] [--json]
  asight raw       <segment>[:<from>[-<to>]]
  asight daemon    [--supervise]
  sudo asight setup-helper [--remove] [--binary <path>]

asight help [<command>]   asight <command> --help   asight --version
```

- `asight` 不带参数 = `asight help`,退出 0。help 分上面三段;help 文本与命令分派出自同一张命令表。没有隐藏别名。
- 未知命令:印 `asight: unknown command 'frobnicate'. Run: asight help`,退出 2。不整屏印 help。
- 未知选项:印 `asight status: unknown option '--frob'`,再加一行它的用法,退出 2。
- `--version` 印 `asight <版本>`;在 git 仓库里带 HEAD 的前 7 位:`asight 0.1.0+1a2b3c4`(D67⑤)。

## 3. 采集

### 3.1 开关模型与保证(D39 · D54 · D55)

- **证书与代理分开管**。证书一次装好,放着不用也没问题,归 `install` / `uninstall`;代理是动态的,归 `on` / `off`。`on` / `off` 从不碰证书的任何字节。轮换证书 = `off` → `uninstall` → `install` → `on`。
- **off 保证**:`off` 返回、在途的响应结束之后,asight 不在这些 harness 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。做不到这条的引流方式不提供。有三种例外,如实写明;`off` 的回执与 `status` 报出它们的条数:
  1. 透传的连接,与看不到本轮结束消息的 WebSocket。asight 看不到它们的响应边界,只能等它们自己关闭。
  2. 代理模式(macOS / Windows)里,`on` 期间启动、现在还活着的进程,闲着的也算。它们的环境里记着 asight 的代理地址,所以那个端口为它们开着,只转发,不解密、不记录,直到它们退出。
  3. `asight off --now` 不等,立即切断。被切断的 agent 会看到一次连接错误,由它自己重试。
- **证书只在 agent 启动时读**。`install` 之前就在跑的 agent 要重启一次,才会被采集。在那之前它的连接照常透传,不会被弄断。`on` 与 `status` 点名这些进程。
- **不自动重启任何东西**。命令只列出要重启的进程。唯一例外是看板上的 Restart 按钮:由用户点,点了先确认。
- **幂等**。每个 harness 的 `on` / `off` 连跑两次与跑一次结果相同,不影响已经开着或已经关掉的 harness(D54)。
- **先备份,只撤自己的**。改你的文件之前先备份到 `~/.asight/backup/`。撤销时只撤 asight 改的部分,你后来改的留着。从不拿备份整文件写回,因为那会抹掉你后来的修改。撤不掉时给出备份路径与手动命令。
- **一次只跑一个改状态的命令**,靠锁 `~/.asight/collector/op.lock` 保证。`off` 优先:拿不到锁时先写下「关」,再至多等锁 10 s;正在跑的 `on` 一看到「关」就停。锁里记着持有者的 pid 与那个进程的启动时间,两者都对才算有人在跑;进程没了、或启动时间不符,就是残留,直接接管。没记启动时间的旧锁:超过 10 分钟就当崩溃残留。
- **更早版本的安装记录先拒绝**:发现更早的 asight 写的安装记录(v2)时,`install`、`on`、`off`、`uninstall` 都在写任何东西之前拒绝,连 `~/.asight/bin/asight-off` 也不覆盖;退出 1,输出点名要先用哪个程序敲干净:先用那个版本跑 `asight off`,再跑 `asight uninstall`。
- **系统代理与 VPN 只读**。asight 读 agent 自己的代理与系统代理,把自己接在原来的下一跳前面,出口不变。它不往任何 VPN / 代理软件里写东西,不改系统代理,不开 TUN(D31 · D43 · D49)。
- **速度目标(D62)**:`on` · `off` · `status` · `status <harness>` · `doctor` 每条 **≤ 0.5 s**(冷启动的进程,macOS 与 Windows 同一条线),p50 与 p95 都算。`on` 要等守护进程的门起来时,等待本身也在这 0.5 s 里:门起得慢不是借口,要么让它快,要么别在 `on` 的墙上时间里等。CPU 与磁盘:守护进程空转时 **≤ 1 % CPU 且 ≤ 10 次 idle wakeups/s**,采集一次请求的 CPU **≤ 5 ms + 8 ms/MB**(MB = 这次请求与响应的线上字节,D62④),封存子进程跑在低优先级(nice ≥ 5;实现取 `os.constants.priority.PRIORITY_BELOW_NORMAL` = 10 这一个常量，因为 libuv 按段把 nice 映射成 Windows 的优先级类，nice 5 在那里仍是 NORMAL、什么都没降)上——合起来「总量几乎可以忽略不计,不影响 agent 正常工作」。
  - **写放大两条线**(依据 D62 的「写放大 ≤ 1.1 字节/采集字节(明文 + 索引,封存的副本不算)」;单写一个比值会被小记录的形状架空:一次 keeper pass 不论记录多小都要一条 entry 行加一条 mark 行,236 B 的记录由此得出 ≈ 2.25 的比值,而绝对量只有几百字节,这个比值什么也说明不了):
    - **比值**:在 `scripts/gen-dataset.mjs` 生成的参考流量混合上 **≤ 1.1 字节/采集字节**(明文 + 索引 + 用量旁注,封存的副本不算)。参考混合里模型调用占了绝大多数字节,真实流量也是,所以比值在这里才有意义。
    - **每条记录的绝对量**:最坏到达形状(每次 keeper pass 只有一条很小的模型调用,且每条之后都补一次用量旁注)下,**每条记录写出的索引与用量旁注合计 ≤ 1 KB**。超了才需要瘦格式。
    - 两条都由 `scripts/perf-cli.mjs --write-amp <HOME>` 一次量出(可复现的脚本模式,不是源码注释)。
  - **空转怎么量**(依据 D62④ 的「idle wakeups/s」本身就是个速率:读法错了这条线无从判定):macOS 的 `top` 在缺省模式下把每个进程的计数器(`IDLEW` · `CSW`)按**自进程启动起的累计值**打在**每一个样本**里(不只是第一个;它追加的 `+` 只表示「比上一样本涨了」,不是增量值)。所以 `top -l 2` 的任何一行 MUST NOT 当成速率——要速率得两次读数:`top -c d`(增量模式,第一个样本之后的那几个才是每秒增量),或自己把相邻两个累计样本相减;`scripts/perf-cli.mjs --idle <pid>` 两种都算、互相印证。CPU 同样按时间差算(`ps -o time=` 在 60 s 空转前后之差)。机器本身不空闲时 `IDLEW` 恒为 0(没有可唤醒的空闲 CPU),这时以 `CSW` 的增量为上界;`IDLEW ≤ CSW`,所以 `CSW` 增量达标即达标。
  - **空转时最密的周期性定时器 ≥ 1 s**(由 D62④ 与 [4.6](4.6-process-collector.md) §控制面 推出:spec 里周期最短的空转定时器是每 1 s 刷新 `lock` 的那个,10 次/s 的线给出 10 倍余量)。所以「一个harness开着、门在听、没有 agent 流量」时,守护进程 MUST NOT 装上周期短于 1 s 的定时器;`off {exit}` 之后等持有者退出的 250 ms 定时器不算空转(它只在退出路上活着,且一退就清)。守卫:`test/collector/daemon-idle.test.mjs`(注入的定时器缝,只断言周期集合,不断任何时序)。

### 3.2 `asight install`

```
asight install [--yes] [--dry-run] [--json]
```

一次性装好证书。不收 harness 名:本机找到的 harness 都装,并记进安装记录。

做什么(macOS / Windows 的次序与细节按 [4.11](4.11-collector-model.md) §1「install」,Linux 按 [4.6](4.6-process-collector.md)):

1. 先写独立撤销程序 `~/.asight/bin/asight-off`。写不进就停,什么都不改。
2. 为这台机器生成自己的根证书。
   - macOS:私钥在登录钥匙串里,只由 asight 的签名助手使用,不能导出;
   - Windows:不能导出的 CNG 密钥;
   - Linux:`~/.asight/collector/ca/ca.key`(0600)。
3. macOS / Windows:把根装成本用户信任的根。系统会弹一次框,asight 等 120 秒。
4. 让每个形态都够得到证书。用户级根够得到的,就不再用别的办法;够不到的,按 harness 描述符写配置键、放 Kimi 的包装,或放 DeepSeek 的插件。如果你的设置已经指向你自己的证书文件,就在那个文件末尾追加一段带标记的内容,设置本身不动。从不写登录环境变量。
5. 注册登录自启并拉起守护进程(D61):macOS 写 `~/Library/LaunchAgents/com.asight.collector.plist`,`launchctl enable` 清掉早先留下的停用覆盖,再 `bootstrap`;Windows 注册计划任务 `\asight\collector`;Linux `systemctl --user enable --now`。从这一刻到 `uninstall`,守护进程每次登录都起来——`on` 改过 agent 的配置,守护进程不回来它们就全连不上(D61)。
6. 记下安装记录与判活快照。

- **计划**:先印计划,再确认(§1.4)。计划列出:要写的每个文件与键、要建的东西、每个形态的证书载体(或够不到的原因)、要弹的框、跳过的 harness、要重启的进程。**登录自启项也是计划里的一行**:macOS 印那个 plist 的路径,Windows 印计划任务 `\asight\collector`,并说明从这次 install 起守护进程每次登录都会起来、`asight uninstall` 会把它撤掉。计划末尾总是印这一行:
  ```
  While installed, programs you run trust certificates issued by this machine's asight root. Remove it: asight uninstall
  ```
  macOS / Windows 另印一行风险:
  ```
  Any program running as you can ask asight to issue a trusted certificate, but cannot copy the key. If you suspect misuse: asight uninstall, then asight install.
  ```
- **幂等,且只写缺的那几项**(V67):再跑一次 `install` 不改任何字节,不生成第二把密钥,也不弹框(先按指纹读回已有的根;已经到位的项按哈希跳过,见下一条)。它也用来补装:asight 装好之后才装的 harness、被 agent 自己的安装器盖掉的包装、被删的证书文件——**只动真正缺的那几项**。看板上按 harness 的 **Set up** 调的就是这个函数、只针对那一个 harness(D65④ · D26②);装与卸本身只在命令行。
- **已经到位的项不重写**:`install` 与 `on` 遇到哈希与记下的相同的项就跳过,它的 `installed_at`、inode 与修改时间都不变。重写会把那些已经在跑、已经被采集的进程判成「启动在证书之前」,从此悄悄不再被采集。
- **系统框的结局**:
  - 你点了拒绝,记为 declined;
  - 超时,或没有图形会话(比如经 ssh 跑),记为 pending;
  - 工具答成功、读回却没有信任,也记为 pending。

  遇到这些情况,其余项照装,退出 1,并印出要再跑的命令;不改用别的证书载体。macOS 上密钥要图形登录会话:经 ssh 跑时,密钥这一项记为 pending,提示你在图形会话的终端里再跑。
- **更早版本的安装记录**:四个开关命令统一拒绝,见 §3.1。

```
Installed. asight's root certificate is trusted by your user.

  Fingerprint  SHA-256 3F:9A:0C:...:24:75
               made on this machine; the key cannot be exported
  Keychain     you approved the trust dialog
  claude-code  uses your user trust
  codex        uses your user trust
  opencode     uses your user trust
  z-code       ~/.zcode/cli/config.json: network.caCertFile set (backup kept)
  kimi-code    ~/.kimi-code/bin/kimi: wrapped
               the real program moved to .asight-real/
  hermes       skipped: not installed

Restart to pick it up: claude-code (pid 4121)
Next: asight on
If asight itself breaks: ~/.asight/bin/asight-off
```

退出码:0 全部装好 · 1 有项没装上 · 2(§1.3)。`--json` 的键见附录 C「install」。

### 3.3 `asight on`

```
asight on [<harness>...] [--yes] [--dry-run] [--json]
```

开始采集这些 harness。

- **前提**:没跑过 `install`(没有可用的根,或没有安装记录)时拒绝,印 `asight on: certificates are not installed. Run: asight install`,退出 1,`error.code` 为 `cert-not-installed`。
- **前提(这个 harness 还没装好)**(D65④):`status` 说某个 harness 的 `setup.state` 是 `needed`(asight 装好之后才装的 harness,或它的证书载体被它自己的更新盖掉了)时,**只拒绝这一个**、其余照开:那个 harness 一个字节都不写,`error.code` 为 `setup-needed`,修法两行——`asight install`,再 `asight on <harness>`。`--dry-run` 照常退出 0,把它放进 `blocked:[{what, reason}]`(附录 C.2)。看板上这个 harness 那一行显示的就是 **Set up**(D26②)。
- **前提(登录自启)**(D61;依据:`on` 之后一关机,不自启的话 agent 全都不能用):`on` 在**写任何东西之前**问这个系统的自启机制:登录项注册着且是启用的吗(macOS `launchctl print`、Windows `schtasks /Query`、Linux `systemctl --user is-enabled`——同一个问题,由 arch 的自启单元各问一次,调用处不分平台)。答案不是「在」(没注册、或读不出来、不能证明),就拒绝:退出 2,一个字节都不写,`error.code` 为 `autostart-missing`,修法那一行是 `asight install`。`--dry-run` 照常退出 0,把这个拒绝放进 `blocked:[{what, reason}]`(附录 C.2)。拿不到证据时回执里不许出现「登录时会起来」这类话。
- **做什么**:
  - Linux:挂上引流,不写 agent 的任何文件。
  - macOS / Windows:先让守护进程开好这一组的本地代理端口并读回,再把 agent 自己配置里的代理指向它,或建开关文件([4.11](4.11-collector-model.md) §1「on / off」)。崩在任何一步,都不会留下指向没开的端口的设置。
  - 确认守护进程在;不在就按这个系统的自启机制起一个(已在跑就不动它)。**登录自启归 `install`,`on` 与 `off` 都不碰它**(D61):开关只写在期望态里,所以 `on` 跨关机重启仍是 on——守护进程每次登录起来,照期望态把门开在入口记着的端口上。
- **接上你的代理**:asight 的上游,就是没有 asight 时 agent 会走的下一跳:你的代理、系统代理,或直连。回执给每个 harness 印一行接上之后的路,凭据打码。
- **要确认时**(§1.4):要改的文件比上次确认过的多(比如新装的 harness、新的 `CODEX_HOME`),或要改写你在上次 `on` 之后改过的代理设置。这时列出来,再确认。
- **之后的效果**:
  - 新启动的进程都会被采集。
  - 证书对它不生效的形态(根待定、够不到、还没在实验室验过)照样经 asight,但只转发;回执点名原因。
  - `on` 之前就在跑的进程照常直连。回执与 `status` 把它们列在 `Restart to capture` 下,列出的是真正发请求的那个进程(比如 Codex 的 app-server)。
- **登记过的副作用照实写**:
  - VS Code 的代理设置会让 VS Code 里所有扩展都经 asight,只转发;
  - OpenCode 会为 asight 的插件在自己的配置目录里装依赖,`off` 之后这些依赖还在。
- **linger**:Linux 上没开 linger 时多印一行:`Capture stops when you log out. To keep it on: loginctl enable-linger alice`。
- **排空中又 `on`**:驱动模式(Linux)下不带名字的 `off` 正在让守护进程排空时跑 `on`,排空就取消,守护进程接着服务。代理模式没有这个局面:`off` 从不请守护进程退出(D62⑥),`on` 落在还在跑的那个进程上。

```
Capturing claude-code and codex. Daemon running (pid 4012); it starts at login.

  claude-code  ~/.claude/settings.json: env.HTTPS_PROXY -> asight (was: none)
  codex        ~/.codex/.env: HTTPS_PROXY -> asight
               (was: http://***@proxy.corp:8080)
               route: codex -> asight :17992 -> proxy.corp:8080 -> internet

Restart to capture: codex (pid 5530 started before capture was on)
Stop: asight off
```

退出码:0 都开了 · 1 有 harness 没开成 · 2(§1.3)。`--json` 的键见附录 C「on」。

### 3.4 `asight off`

```
asight off [<harness>...] [--now] [--yes] [--dry-run] [--json]
```

撤掉 asight 在这些 harness 路径上的一切。不带名字 = 全部 harness。代理模式(macOS / Windows)关掉门、**守护进程空转留着**(D62⑥:下一次 `on` 直接请它开门,不经 OS 重拉);驱动模式(Linux)让守护进程排空后退出(那里的退出才是摘掉内核的 watch 表与 link)。**不碰登录自启**(D61):下次登录守护进程照常起来,照期望态什么门都不开。

- **撤什么**:
  - Linux:摘掉引流。
  - macOS / Windows:撤掉 agent 配置里的代理,删掉开关文件。改过的文件回到 `install` 之后的样子;你在 `on` 期间改过的键原样留着。
  - 证书一项不碰,归 `uninstall`。不杀、不重启 agent。
- **次序**:每次 `off` 都是这个次序:先写下「关」,再摘引流并读回确认,确认之后才撤文件。代理模式下没有「停守护进程」这一步(D62⑥):macOS 不碰 LaunchAgent——不 `disable`、不 `bootout`(见 [4.9](4.9-macos-collector.md) §4「开与关(launchd)」);Windows 不停监管父进程(见 [4.8](4.8-win-collector.md) §4.2「off 保证」)。只有要**停**守护进程时(它不应答、`uninstall`、驱动模式排空完)才走平台次序:macOS 先 `bootout` 再停,Windows 先停监管父进程再停守护进程。
- **在途的连接**(D39):
  - 空闲的连接立即关。
  - 有响应在途的,把响应收全、转完再关:先发 FIN,至多等 5 s。
  - WebSocket 在本轮的结束消息处关。
  - 透传的连接等它自己关。
  - 被改包规则扣着的请求,原样放行。
  - 响应头还没转出时,asight 可以在这条最后的响应上加一行 `Connection: close`,让客户端不再复用这条连接。这一行记在那条记录上,看板上会标出来(不变式 4)。
  - 已经收到的字节全部转完,再发 FIN。客户端还有没读的字节留在缓冲里时,从不 RST。
  - 从不自己造 WebSocket 的结束帧。
  - 除了上面记下来的那一行 `Connection: close`,asight 不往连接里写任何属于自己的字节。
- **`--now`**:不等,立即切断这些 harness 仍经 asight 的连接;被切断的连接记录标 `cut-by-off`。不带名字时:代理模式下门随即关掉、守护进程照旧空转留着;驱动模式下守护进程随即退出。
- **不依赖守护进程**:守护进程不在、卡住或还在启动时,`off` 照常完成;卡住的守护进程先被停掉。
- **不依赖源码**:源码目录没了也能撤,用 `~/.asight/bin/asight-off`,参数与输出都和 `asight off` 相同。
- **安装记录丢了或读不了**:按 asight 写的标记撤。只认这几样:代理块自己的标记、指向 asight 的值、asight 建的开关文件。引流照摘;撤文件那一步要确认(§1.4)。撤完之后,坏的记录文件留在原处,回执写明它在哪。
- **撤不掉的文件**(标记被改坏、文件解析不了):不动它,退出 1,给出备份路径、手动恢复的命令,并说明那样会丢掉什么。
- **看板**:看板由守护进程托管(D66),所以代理模式(macOS / Windows)下 `off` 之后它照旧在;驱动模式(Linux)下不带名字的 `off` 让守护进程排空后退出(D62⑥),看板随之断到下一次 `on`,回执就地写明。

```
Capture is off for all harnesses. asight is no longer on their path.

  claude-code  ~/.claude/settings.json restored
  codex        ~/.codex/.env: asight's lines removed; your later edits are kept

The daemon (pid 4012) keeps running, with no door open.
2 connections are still going through asight; they close when the response
in flight is through.
Still connected through asight, forwarded only: codex (pid 5530).
Cut them now: asight off --now
Certificates stay installed. To remove them: asight uninstall
```

退出码:0 引流已确认摘掉、入口都撤了(还在排空的连接不算没做完)· 1 有没撤掉的 · 2(§1.3)。`--json` 的键见附录 C「off」。

### 3.5 `asight status`

```
asight status [<harness>...] [--failures] [--json]
```

对每个 harness 回答:正在被采集;或者没有,为什么。

- 只读,不写任何文件。
- 没有守护进程时直接读盘;守护进程没响应时照实说出来。

不带名字时,印一屏摘要:

```
Capturing 2 of 4 installed harnesses. Daemon running (pid 4012, up 3h 12m).

  HARNESS       CAPTURED  NOTE
  claude-code   yes
  codex         no        pid 5530 started before capture was on; restart codex
  opencode      off
  z-code        off
  not installed: deepseek-dsh, hermes, kimi-code

  Certificate   installed, trusted by your user, expires 2036-10-15
  Connections   3 open through asight
  Problems      1 in the last 24 hours, latest 10 min ago
  Board         http://127.0.0.1:9800  open it with: asight board

More: asight status codex   asight status --failures   asight doctor
```

- **列哪些 harness**(代理模式 = macOS / Windows,asight 已装):不带名字时,安装记录、开关文件、守护进程知道的 harness 之外,**这台机器上有某个形态在的 harness 也各占一个 `harnesses` 条目**(形态在不在按它的描述符判:[4.11](4.11-collector-model.md) 的 `present`,只看本 OS 的形态),所以 asight 装好之后才装的 harness 也有一行;`--json` 与 `GET /control/status` 是同一份文档,跟着列。文本摘要的表照旧只列 `install` 装过的,其余的由 `not installed:` 一行点名。asight 没装时不找:那时没有能 Set up 或打开的,摘要照旧说还没有 harness 设好。`on` / `off` 不带名字时作用于谁,不读这张表,不变。Linux(驱动模式)照旧只列记录知道的(那里 `setup` 是 `unknown`,已知缺口)。,依据:D65④「某个形态在机器上在」就是发现,采集页那一行就是 Set up 出现的地方;D26② 看板的开关也要那一行(新装、不需要 Set up 的 harness 同样要能从看板打开);一般情况下只有 on / off 两个按钮。只列 `needed` 的那种做法被否:它会藏起由根承载证书的新 harness,用户就没法从看板打开它。

带名字时,每个点名的 harness 印一节细节:

```
codex: on, not captured yet

  Why    pid 5530 started at 09:01, before capture was turned on at 09:12.
         It connects directly until it restarts.
  Fix    Quit every codex window, then run: kill 5530

  Forms
  codex.cli  certificate  in effect (user trust)
             proxy        ~/.codex/.env HTTPS_PROXY = asight :17992
                          (was: none)
  codex.app  certificate  in effect (user trust)
             proxy        same as codex.cli

  Routes
    new processes   codex -> asight :17992 -> system proxy :7897 -> internet
    without asight  codex -> system proxy :7897 -> internet
    pid 5530 now    codex -> api.openai.com (direct)

  If your VPN or proxy routes by process, it sees asight, not codex.
  To change the proxy: edit codex's own settings, then run: asight on codex
```

- **判词**:一个 harness 的每个在跑进程都被采集,才算 `yes`;有一个没有就是 `no`,并给出第一个原因。读不到的写 `unknown` 加原因,从不当成 0 或 none。没有在跑的进程时,按「引流已挂、入口完好、证书生效」来判。原因的说法与修法,和 `doctor` 用同一份发现目录(附录 B)。
- **Problems 只算真问题**:不是 agent 的进程被透传、按设计不解密的连接,都不算。它们放在 `--failures` 的 `Expected` 一段里。
- **Board 一行**:看板在时印它的地址与打开它的命令;不在时印 `not running` 加原因,原因与 §4.3 的几种同一套(没装、守护进程没在跑、端口被占)。**地址不带口令**,`--json` 里也不带:口令只由 `asight board` 印(§4.3);不带口令打开这个地址时,页面只说怎么用 `asight board` 打开([1.5](1.5-states-aesthetics.md) K-30)。看板在不在不影响退出码:它不改变采不采得到。依据:看板也归 `status` 的结果——看板由守护进程托管(D66),它在不在是守护进程的一项事实,`status` 本来就问守护进程,不多一次往返(D62 的 0.5 s 线不变);口令只放在 fragment 里、不进任何日志([4.4](4.4-server.md) §服务形状),而 `status` / `doctor` 的输出是大家会贴出去的东西。
- **`--failures`**:列出最近 24 小时的全部问题。行就是附录 C.3 的 `failures.groups`:一组一行——时间、次数、`src/cli/words.mjs : failureBrief` 那一句、要跑的命令;和看板的采集记录同一批组、同一句(依据:D24 与 [0.1](0.1-engineering-rules.md) §2)。之后是 `Expected` 一段。
- 退出码:
  - 0:每个开着的 harness 都被采集;
  - 1:有开着的 harness 没被采集,包括有进程要重启、根待定或被拒;
  - 3:判断不了;
  - 2:见 §1.3。
- `--json` 印的就是 `asight query status` 的文档(附录 C),退出码按上面的判词给。

### 3.6 `asight uninstall`

```
asight uninstall [--purge-data] [--yes] [--dry-run] [--json]
```

撤掉 `install` 装的一切,再删 asight 自己的文件。

- **先印计划,再确认**(§1.4):要撤的每一项、要删的文件、留下的数据。不在终端里又没有 `--yes`:只印计划,退出 2。
- **前提:采集全部关着**。要同时满足四条:
  - 每个 harness 都是 off;
  - 没有 `on` 写下的项;
  - 守护进程上没有连接;
  - 没有 `on` 期间启动、现在还活着的进程。

  不满足时什么都不改,印 `asight uninstall: capture is still on for codex. Run: asight off`,退出 1。`uninstall` 从不替你 `off`。从核对前提到撤完,一直持着锁。
- **守护进程**:空闲的守护进程由 `uninstall` 停掉。活着却不应答的,算作没关,拒绝。
- **撤的次序**:按装的反序撤(macOS / Windows 见 [4.11](4.11-collector-model.md) §1「uninstall」,Linux 见 [4.6](4.6-process-collector.md)),根的密钥最后删。根的移除被拒、待定、或移除后在用户的信任库里仍查得到(OS 的框没人答应 = 工具自己的退出码不算事实)时:
  - 密钥照删,那张根从此无效;
  - 安装记录只留这一项,下次 `uninstall` 接着撤它;
  - 退出 1,回执里 `still_trusting` 带着这张根(`{what:'root', store, fp256, reason, command}`)、`problems` 一句话、`flows/` 一条 `root-not-removed`,印出移除它的命令;
  - 之后 `status` 与 `doctor` 会报这张孤儿根。
- **备份**:删掉全部备份。撤了、但与原样不逐字节相同的文件,回执逐个列出。
- **采集数据默认保留**:`raw/`(段文件,明文与 `.sealed`)、`collector/flows/`、`audit/`、`replays/`、流量类别的修改记录 `logs/classes.ndjson` 都留着;`index/` 是从 `raw/` 算出来的投影,跟着 `raw/` 走。`--purge-data` 连它们一起删(含 `raw/` 与 `index/`),要确认;而且只在其余各步都成功之后才删。有任何一步没成,数据一个都不删,回执写明,退出 1。留下的每一处都进回执的 `kept:[{what, path, bytes}]`,文本按它渲染(所以文本里的路径与字节数就是盘上的)。
- **守护进程的状态不是数据**:端点文件 `control.json` 与 `ingress.json` 每次 `uninstall` 都删(守护进程此时已停;下次 `install` / `on` 自己再选端口、再写端点)。`collector/flows/` 留着:它是 asight 说过自己做了什么、什么失败了的记录(D38),这次 `uninstall` 自己的最后一行也写在里面。
- **流量类别表不删**(`classes.json`):它说的是以后存什么,不是 asight 对 agent 的影响。它的修改记录是数据,同 `raw/` 一样默认留着、进 `kept`,`--purge-data` 时一起删(不变式 5「卸载不留残」:全部清掉之后 `~/.asight` 不在)。
- **Linux 的能力助手**另要一步:`sudo asight setup-helper --remove`。

```
Uninstalled. asight is no longer on your harnesses' path, and its root
certificate is gone from your trust settings.

  Removed
    root certificate (user trust)
    3 certificate settings
    kimi-code wrapper
    4 backups
  Kept
    your captured data, 1.3 GB in ~/.asight/raw
    your class table, ~/.asight/classes.json

Delete the captured data: asight uninstall --purge-data
```

退出码:0 · 1 · 2(§1.3)。`--json` 的键见附录 C「uninstall」。

### 3.7 `asight doctor`

```
asight doctor [<harness>...] [--json]
```

找出采集与网络上的问题,说清怎么修。带名字时只看这些 harness。

- **看什么**:
  - 每个开着的 harness 有没有被采集,为什么(发现目录见附录 B);
  - 网络:你的代理在不在,asight 接得对不对,出口变没变;
  - 证书:根、密钥、各证书载体;
  - 采集文件与备份是否只有你能读;
  - `~/.asight/bin/asight-off` 是不是当前版本;
  - 没有被认领的备份;
  - `agents.json` 的问题。
- **只读**:不写任何文件,不起也不停守护进程,不联外网(只问本机的守护进程)。跑的系统工具只有只读的查询。
- **没有采集数据不算判断不了**:还没有采集文件时,文件权限这一项写 `no captured data yet`,不让整体变成「判断不了」。
- **每条发现的格式**:一句话说是什么问题、为什么;`Fix` 后面是一行或几行命令,asight 的命令在前,值都填好;`Check` 后面是一条验证命令。**注记(`Note:`)不印 `Fix`**:它不是问题,所以它给的命令印作 `Option`——「没有问题」的判词下面不该出现 `Fix`(依据 D58 的可读性:a note with a fix is a problem, or it is not a note)。
- **标题行的数就是下面编了号的那些**:问题与预期内的发现各报一个数(`asight doctor: 1 problem and 2 expected findings.`),都没有就是 `no problems.`;注记不编号也不计数(否则标题写 1、下面印了 3 条)。退出码不变(按问题判)。
- **同一件事只印一行**:几个 harness 得到同一条注记(同一个 code、同一个理由、没有要做的事)时,文本只印一行,句子里把它们都点名;`--json` 的 `findings` 仍是每个 harness 一条。
- **兜底**:点名的 harness 没有任何发现时,最后给一条提示:`If codex still cannot connect: run asight off codex and try again. If it still fails, asight is not the cause.`

```
asight doctor: 2 problems.

1. codex is not captured: pid 5530 started before capture was turned on.
   Fix    Quit every codex window, then run: kill 5530
   Check  asight status codex

2. z-code's proxy 127.0.0.1:7890 is not running, so z-code cannot connect.
   Fix    Start your proxy, or remove network.proxy from
          ~/.zcode/cli/config.json
   Check  lsof -nP -iTCP:7890 -sTCP:LISTEN

Note: hermes is not set up yet (~/.hermes/.env does not exist).
   Option Run Hermes's own setup, then: asight on hermes
```

退出码:0 没有问题 · 1 有问题 · 3 有要看的东西读不到(说出是哪个、为什么)· 2(§1.3)。`--json` 印的就是 `asight query doctor` 的文档,退出码按上面给。

### 3.8 asight 自己坏了时

不管 asight 的哪个部件坏了,`off` 都能跑完:它不需要守护进程,也不需要源码目录(§3.4)。

| 坏在哪 | 怎么办 |
|---|---|
| 守护进程不在 | `off` / `uninstall` / `status` 照常(`status` 读盘);`on` 拉起它,拉不起就报原因、退出 1。代理模式下本地代理端口随守护进程消失,指向它的 agent 连接被拒、由 agent 自己重试;登录自启会把守护进程与端口一起带回来。等不及:`off <harness>` 撤掉入口,agent 重启后直连 |
| 守护进程卡死或还在启动 | Linux 上新连接已经直连。`off`(带不带名字都一样)先停掉它、确认引流已摘,再撤文件;停不掉也照撤,退出 1,回执给出 pid 与手动停止的命令。`uninstall` 不停它:遇到活着却不应答的守护进程就拒绝,指向 `asight off` |
| Linux 的能力助手缺失或版本不对 | `on` 什么都不挂,提示 `sudo asight setup-helper`;`off` 不受影响 |
| 安装记录坏了或丢了 | 按 asight 写的标记撤(§3.4):引流照摘,改文件那一步要确认。撤净之后坏的记录文件留在原处,回执写明它在哪;`on` 之前由你把它挪开 |
| 两条改状态的命令同时跑 | 靠 `op.lock`:`off` 优先,正在跑的 `on` 见到「关」就停(§3.1) |
| 你在 `on` 之后改过代理入口 | 只撤 asight 写的那部分,回执写「你改过,没动」或「已撤销,但不逐字节相同」,备份留着 |
| asight 写的标记被改坏 | 不动这个文件,退出 1,给出备份路径、手动恢复的命令,并说明那样会丢掉什么 |
| 源码目录没了,或缺依赖 | 用 `~/.asight/bin/asight-off`;`status` 与 `doctor` 报出 `PATH` 上的 asight 指向的文件不存在 |
| 机器上没有 node | 按安装记录里每一项的手动撤销办法做,`install` 的回执印过它们 |
| `~/.asight` 写不进(磁盘满) | 备份写不进就不改你的文件;日志写不进先写 stderr,恢复后第一条记录说明断过(D38) |
| 本平台还没有采集器 | `on` 与 `daemon` 印 `not supported yet`、退出 1;`off` 照常跑,没装过就如实说没有东西要关 |

## 4. 数据

### 4.1 `asight query`(D59)

```
asight query <name> [--<param> <value>...]
asight query
```

读采集数据与 asight 状态的唯一入口。

- 带名字时输出永远是一个 JSON 文档(§1.2)。不带名字时印出名字与参数的表格(不是文档)、退出 0。
- 看板的每个数据请求 `GET /api/<name>?<param>=<value>` 返回同一个文档。
- `status`、`doctor`、`classes` 的 `--json` 也是这个文档。所以 `query` 有多快,看板就有多快。
- **谁答**(D63):`asight query` 先问守护进程的控制面(`GET /query`,经唯一的端点解析器),由它的查询工作进程算——那个进程是温的,还答看板的 `/api/<name>`。**没有守护进程应答时**(拒绝、不存在、令牌不对、没有那条路由、超过一个短的截止),CLI 在自己进程里跑同一份查询代码;只有 **400**(查询核心对这组参数的判决)由 CLI 原样抬起,别的状态码一律按「这条通道答不了」走本地。**守护进程里还没有工作进程时**,它**立刻**回一个「没有温的工作进程」,CLI 就地本地答(于是冷查询从不比本地慢——等一次 fork 加一次冷查询实测 842-1142 ms,本地 548 ms),同一条查询由守护进程在背后交给新 fork 的工作进程把缓存热起来,下一次查询就是温的;「没人查时没有工作进程」(D63)不变:没有查询到来就什么都不 fork。两条路的文档**逐字节相同**(包括 `errors`),本地那条只是慢些;所以读数据从不要求有守护进程在跑。`status` / `doctor` 这两个名字要的是机器此刻的实况,不进工作进程;让查询核心换了答案的环境变量(`ASIGHT_PRICING` 这类)被设置时,CLI 也走本地那条——名单在代码里只有一处。

| 名字 | 参数 | 给什么 |
|---|---|---|
| `status` | `--harness` | 每个 harness 的采集状态、原因、证书、路由、连接、问题(附录 C) |
| `doctor` | `--harness` | 发现列表(附录 B)与结论 |
| `sessions` | `--harness` `--since` `--until` `--limit` `--after` | 会话列表,新的在前:id、harness、项目、标题、起止时间、调用数、大小 |
| `session` | `--id`(必填)`--after` `--limit` | 一个会话的回放视图:按步排列的调用、上下文、cache、资源 |
| `calls` | `--class` `--harness` `--session` `--host` `--ref` `--since` `--until` `--limit` `--after` | 调用列表,任何类别都行:时间、harness、类别、host、端点、状态码、收发字节、保存级别、记录 id;`--host` 按 host 筛;`--ref <记录 id>` 只给那一条(单条请求的逐字详情走同一个形状,不另起名字) |
| `overview` | `--since` `--until` | 统计卡的数:时间窗里的会话数、调用数(总数、推理、只记日志、失败)、线上与存下的字节、按 harness 的会话 / 调用 / 字节 / 最近活动;按 harness × 模型 × 泳道的用量,出自读取侧的按段用量旁注,还没补齐的部分受字节预算约束、读了多少与为何停写在 `coverage` 里 |
| `traffic` | `--since` `--until` `--limit` `--after` | 流量表:每个 (harness, host) 的首见、末见、条数、发出与收回的字节、未记录的条数、按类别的计数;首见与各 harness 的首见取整个索引,与时间窗无关;合计是下限 |
| `block` | `--ref`(必填) | 一段逐字内容(请求体、响应体、上下文块),带保真标注 |
| `classes` | — | 流量类别表;各类在 24 h、7 d、全部时间里的条数与大小;盘上占用;最近的修改 |
| `segments` | `--since` `--until` | 原始层的段:名字、状态(`writing` / `closed` / `sealed`)、记录数、大小、封存后的比例、时间范围、封存的问题 |
| `pricing` | — | 算费用用的价格表,与它的来源 |

- **参数**:
  - 时间参数收 ISO 8601,也收相对时间 `30m` `24h` `7d`。
  - 列表参数收逗号分隔的多个值。
  - 分页:`--limit` 默认 50,最多 500;窗口参数叫 `--after`(看板的 `?after=`,一个参数一个名字;没有别名、不兼容旧名字 —— 用户那台 Mac 会 SIGKILL 所有 argv 里带旧名字的 node 进程,那个名字在它上面没法跑,2026-10-20)。文档里的 `next` 就是下一页的 `--after`,没有下一页时为 `null`;`has_more` 说清还有没有。
- **读不全**(某个段读不出、某条记录坏了):照样给出文档,读不到的列进 `errors: [{where, reason}]`,不静默(D38)。
- **id**:记录 id = `<段>:<序号>`,封存前后不变。会话 id 来自 harness 自己的会话标识([3.4](3.4-session-identity.md))。
- **只读原始记录与可删的索引**(`~/.asight/index/`,丢了就重建;新鲜由守护进程随写维护,D62)。**不需要守护进程**,也不需要先跑别的命令——守护进程在时它来答(D63),不在时 CLI 自己答。
- **段索引每条记录存什么**:id、时间、harness、类别、host、路径、状态码、存下的字节数、线上发出与收回的字节数(没记下的为 null)、会话键、是不是模型调用。`classes` 的条数与大小就是从这里算的。
- **速度目标**(D62:任何随机存取的查询 ≤ 0.5 s,随机存取附近的那些查询 ≤ 50 ms):在附录 D 的参考数据上测,每条都带 p50 与 p95(p95 超了就是超了)。
  - **随机存取 ≤ 0.5 s**(冷启动的进程,从命令行到文档):`sessions` · `session` 第一页 · `block` · `calls` · `classes` · `segments` · `pricing` · `overview` · `traffic` · `raw <段:行>`。相当于面板上点开一个会话就能看到结果。`overview` 与 `traffic` 都只读段索引与用量旁注,或受字节预算约束,所以这条线在附录 D 最大的那份语料上也成立。
  - **附近的查询 ≤ 50 ms**(会话已经打开之后的下一次查询:下一页、同会话另一步的 block、它的 calls):这是 `runQuery` 自己的时间,不含进程启动——命令行一次冷启动在任何平台上都付不起 50 ms(实测 node 自己的启动 + asight 的模块加载:开发机 110 ms、macOS 测试机 90 ms),所以这条的**承诺对象是守护进程的查询工作进程**(D63:看板与 `asight query` 都经它),CLI 的墙上时间 = 这一条 + 一次启动的地板。相当于在面板上点同会话的不同 step,秒出而不卡顿。**采集着也算**:这条线在守护进程正往别的会话追记录时同样成立,所以缓存 **MUST NOT** 按「哪里多了一个字节」整体失效,只能按答案所依赖的东西(该会话自己的记录表)失效。
  - **守护进程的负担**(D63):转发 agent 流量的那个事件循环每条查询花 **≤ 5 ms**,不论文档多大(工作进程的字节流着过去,守护进程不 parse 也不 stringify 大文档);没人查时既没有工作进程也没有定时器。
  - **索引不许在查询时是冷的**:段索引是可重建的投影,保持它新鲜的机制只有一处(守护进程随写增量更新,见 [4.2](4.2-storage-etl.md) §段索引)。读取侧自己建是**唯一的退路**,只在没有守护进程写过这段、用户删了 `index/`、索引格式升版或段被改写时发生(明文段这么建只在内存里,不落盘:那份文件是守护进程的);它**不得静默**——自己建的量超过守护进程一块的活(`KEEPER_CHUNK_BYTES`)就在文档的 `errors` 里留一条 `index-cold`,说清它自己索引了多少、为何会轮到它(D38)。守护进程在的时候,查询最多只跟上最后一小段尾巴(防抖窗口里的那点流量),不再有整段重建这条墙上时间。
  - **测量工具**:`scripts/perf-cli.mjs`(一条命令给出冷/热 p50 · p95、进程内核心时间、CPU 时间与峰值 RSS、以及 node + 模块加载的地板),`scripts/perf-query.mjs` 给封存比与磁盘占用。
- **退出码**:0 给出了文档(带 `errors` 时也是)· 1 给不出文档 · 2 名字或参数错。

### 4.2 `asight classes`(D60)

```
asight classes [<class>] [--json]
asight classes set <class> full|log
asight classes add <class> <host-regex> [<path-regex>] [--harness <harness>]
asight classes rm <class> [<rule>]
asight classes reset
```

决定每类流量存多少。

- **归类规则**:类别表是有序的,一次调用归第一个有规则匹配上它的类别。一条规则由三部分组成:
  - host 的正则,匹配整个 host;
  - 可选的路径正则,从路径开头匹配;
  - 可选的 harness。

  都没匹配上的调用归 `other`。
- **两个保存级别**:`full` = 请求与响应逐字存;`log` = 只存头与大小。
- **内置表**:`llm`(模型调用)· `token-count` · `session-sync` · `telemetry` · `files` · `account` · `other`,级别都是 `full`(D40:默认逐字存全部;`log` 只来自你的修改)。规则以数据的形式随 asight 发布。下面样例里的 `catalog` 与 `telemetry log` 是一位用户改过的表。
- **你的表**:第一次修改时,内置表整份写进 `~/.asight/classes.json`(0600),之后改的都是这一份。`reset` 删掉它,回到内置表。每次修改在 `~/.asight/logs/classes.ndjson` 追加一行:旧值、新值、时间。
- **怎么改**:
  - `add` 把规则加到已有类别的末尾。类别不存在就新建,排在所有内置类别之前,级别是 `full`。这样你加的规则先于内置规则生效。
  - `rm <class> <rule>` 删一条规则,规则号见 `asight classes <class>`;`rm <class>` 删整个类别。
  - `other` 不能删,也不能加规则。
- **生效**:守护进程 1 s 内读到,只管之后开始的调用;已存的数据不变(不变式 2)。
- **与开关无关**:`off`、`uninstall` 都不碰类别表。
- **写错时**:正则不合法、类别名不合 `[a-z0-9-]+`、规则号不存在,都退出 2,文件不动。

### 4.3 `asight board`

```
asight board
```

打开看板。

- 看板**不是一个要你起的服务**:它由守护进程托管(D66 · [4.4](4.4-server.md)),`asight install` 之后每次登录都在。这条命令只做两件事:印出带口令的网址,并用系统默认浏览器打开它。`asight status` 的 Board 一行也指向它,但不带口令(§3.5)。
- 网址 = `http://127.0.0.1:<port>/#t=<口令>`。端口与门的端口一起记在 `~/.asight/collector/ingress.json`,所以网址稳定、可以收藏;口令是 `~/.asight/` 下那份 0600 的每用户口令(D26③),放在 **fragment** 里,所以它不随请求发出去、不进任何日志([4.4](4.4-server.md) §服务形状)。
- 数据面只读,每个请求就是一个 `asight query`(§4.1);改状态走控制面,它与数据面同一个口令、同一个 Host / Origin 门,写之前先回计划(D26)。看板上的写只有:每个 harness 的开关、流量类别、以及某个 harness 需要补装时的 Set up(D65④)。
- **还没 `install`**:守护进程不在,看板也不在。印 `asight board: asight is not installed on this machine. Run: asight install`,退出 1。
- **装过但守护进程没在跑**:按这个系统的自启机制起一个;起不来就印原因与下一步(`asight doctor`),退出 1。
- **看板的端口被别的程序占着**:采集不受影响(守护进程照常转发);印占着它的原因与 `asight doctor` 那一行,退出 1——不换端口。
- 浏览器打不开(没有图形会话,比如经 ssh 跑)时,网址照印、就地说明没能打开,退出 0。
- 网址自占一行:带口令的网址有 68 列以上,和结论放一行就过了 80 列(D58);结论在前一行(依据 D58「80 列、结论在前」)。
- 看板上的性能线见 **D64**:打开会话 ≤ 0.5 s、换 step ≤ 50 ms、其余按钮与面板加载 ≤ 0.5 s(p50 与 p95 都算)。

```

http://127.0.0.1:9800/#t=k3Qv...
```

退出码:0 网址印出来了 · 1 看板不在(没装、守护进程起不来、端口被占)· 2(§1.3)。

## 5. 维护

### 5.1 `asight raw`

原始层按段存(D60,格式见 [4.2](4.2-storage-etl.md)):

- 守护进程往一个段里追加记录。段满 128 MB,或守护进程停下时,这个段关闭。
- 关闭的段由守护进程自动封存:一次一个,在子进程里做。每条记录都核对通过之后,才删掉明文。没封成的段明文留着,守护进程下次启动时再试一次(不循环),`status` 报出来(附录 B `seal-failed`)。封存只归守护进程,没有手动封存的命令。
- 不向后兼容:上一版写在 `~/.asight/collector/capture-<日期>.ndjson` 的记录不读、不搬、不碰,更早的位置也一样(§6);没有转换脚本(用户点名要才做)。

```
asight raw <segment>[:<from>[-<to>]]
```

把段里的记录逐字印到 stdout:NDJSON,字节与采集时相同,封存过的先解开。`<from>` `<to>` 是记录序号,包含两端。只读,root 也能跑。退出码:0;1 段或序号不存在、读不出,原因印在 stderr;2 用法错。

### 5.2 `asight daemon`

```
asight daemon
```

在前台跑采集守护进程。登录自启跑的就是它,平时不用手敲。

- 没跑过 `install` 时拒绝,什么都不写:印 `asight daemon: certificates are not installed. Run: asight install`,退出 1。
- 收到 SIGTERM 或 `Ctrl-C` 时,先排空再退出。
- 已经有另一个守护进程在控制面上应答时:说一句谁在应答(写进 `logs/daemon-err.log`),然后**以 0 退出**——这不是故障,是已经到位;非 0 退出会让平台的重拉机制(launchd 的 `KeepAlive {SuccessfulExit:false}` 每 `ThrottleInterval` 秒一次、Windows 监管父进程按退避)在对方活着的整段时间里一直重试,成一个隐藏的循环(依据 = D62④「空转几乎可忽略」与 4.8 §7 的监管退出规则:0 = 被要求停,不重拉)。
- Windows 的计划任务用 `asight daemon --supervise` 起一个监管它的父进程,同样不用手敲。
- 拒绝 root。
- 退出码:0 正常停止(或已有另一个守护进程在应答);1 起不来,原因写进 stderr 与 `flows/`;70 崩溃。

### 5.3 `sudo asight setup-helper`

```
sudo asight setup-helper [--remove] [--binary <path>]
```

只用于 Linux:装或删 eBPF 能力助手(D36)。这是唯一要 root 的命令。

- `--binary`:用你自己从源码编出的助手。
- 在 macOS / Windows 上:印 `asight setup-helper: not needed on this platform.`,退出 2。
- 不是 root 时:印 `Run it with sudo: sudo asight setup-helper`,退出 2。

`asight help <command>` 与 `asight <command> --help` 印同一份内容:一行用法、两三句说明、选项表、退出码。

### 5.5 `asight update`(D67)

```
asight update [--yes] [--dry-run] [--json]
```

把这台机器上的 asight 换成最新代码,并让机器回到「新版本装好、原来开着的 harness 照样开着」的样子。执行它的是旧代码,旧代码不知道新版本要什么,所以分界线划在「拉代码」上:之前的事归旧代码,之后的事另起一个进程交给新代码(D67①)。

- **只认 git 仓库**:代码所在的目录里有 `.git` 才往下走。别的装法:印 `asight update: this asight is not a git checkout, so it cannot update itself. Update it the way you installed it.`,什么都不改,退出 2(npm 发布的那个版本另加一支,D67②)。
- **先查,查不过什么都不改**,印原因,退出 1:跟踪的文件有改动;当前分支没有上游;`git fetch` 失败;本地有上游没有的提交(不能快进)。
- **已是最新**:HEAD 等于上游,守护进程跑的也是这份代码(它在控制面 `GET /status` 报的 `code` 等于 `asight --version` 的值)→ 印 `asight update: already up to date (0.1.0+1a2b3c4).`,什么都不写,退出 0。HEAD 等于上游、守护进程却跑着别的代码(或不报 `code`)时,只做下面第 4 步里换守护进程那一件。
- **计划与确认**同 §1.4:计划写明从哪个提交到哪个提交、先关后开哪几个 harness;`--dry-run` 只印计划。
- **顺序**:
  1. (旧代码)`off` 现在开着的 harness,把它们的名字写进 `~/.asight/collector/update.json`(`{"from": "<旧的 --version>", "on": ["<harness>", ...]}`,0600)。谁写的入口由谁撤,新代码不用认旧版本写的入口。
  2. (旧代码)`git merge --ff-only` 到上游;`package.json` 或 `package-lock.json` 变了,就在仓库里跑 `npm install --no-audit --no-fund`。第 1 步或合并失败:用还没换掉的旧代码把第 1 步关掉的 harness 再 `on` 回来,删掉 `update.json`,退出 1。`npm install` 失败:代码已经换了,`update.json` 留着,印原因和「修好后再跑一次 `asight update`」,退出 1。
  3. 另起一个进程跑新代码的 `asight update --yes`(原来带 `--json` 就照带);旧进程不再载入任何代码,只等它退出,照搬它的退出码。参数里不带 harness 名字(名单在文件里,D67①)。
  4. (新代码,`update.json` 在 = 有一次更新等着收尾)守护进程跑的不是这份代码时,按 §5.2 停掉它(先排空再退出,与 `uninstall` 停守护进程是同一条路),再经登录自启项拉起;然后跑 `install`;再 `on` `update.json` 里的 harness;都成了才删掉 `update.json`。没收尾完时文件留着:再跑一次 `asight update`,从这一步接着做。
- **代价**(回执里照写):第 1 步到第 4 步之间,这几个 harness 是关着的——这段时间新起的 agent 连接照常能用,只是不被采;换守护进程时还开着的连接会被断开,agent 会重试。
- **从 0.1.0 起向前兼容**(D67④):新版本的 `install` 与 `update` 接手任何 ≥ 0.1.0 版本留下的 `~/.asight`;改这些格式的版本自己认旧格式。从 0.1.0 以前的版本换到 0.1.0 要手动做一次(旧代码里没有 `update`)。
- **回执**:附录 C.2 的 `update` 行。拒绝 root(§1.5)。
- **退出码**:0 更新完,或已是最新;1 没更新成或没收尾完,原因在回执;2 用法错、不是 git 仓库、root、或没人能确认。

## 附录 A · 路由的画法

拓扑是 `status` 与 `doctor` 的解释,不是它们的判词:哪一跳读不到不改退出码。文本与 `--json` 出自同一个对象(附录 C),不各算一遍。

### A.1 画法

- **一条链** = 从 agent 进程到出口的每一跳,用 `->` 连。节点写具体的东西:进程写名字与 `(pid N)`,地址写端口(本机回环只写 `:17992`,§1.1),出口写 `internet` 或 `(direct)`。asight 自己的节点写 `asight`——不写内部机制的名字。代理那一跳只写地址、端口、属主进程名与 pid,不写产品名与模式(D49)。
- **边上的来处**用方括号,说清这一跳是谁安排的:`[ebpf]`、`[system proxy]`、`[.env HTTPS_PROXY, written by asight]`、`[kimi wrapper, switch file by asight]`。没有歧义时省略。
- **放不进 80 列**就逐级降:先去掉所有方括号里的来处;还是太长就只印 `agent -> asight -> <下一跳> -> ...`,整条链留给 `status <harness>`——它本来就是一跳一行,每行 `-> ` 开头。紧凑链从不折行。
- **画新连接的路**:按 agent 现在的设置(它读的环境变量、配置里的代理键、它认的系统代理)与本机网络环境算。在跑的进程启动时的设置与现在不同时,另列一行 `pid 5530 now`。
- **关掉 asight 时的路**:同一份设置去掉 asight 这一跳,`status <harness>` 印它。asight 在路径上时,asight 之后的第一跳必须等于这条链里 agent 之后的第一跳(出口不变);不等时报 `egress-differs`。
- **读不到**:那一跳写 `unknown` 加一句原因(闭集见附录 C),不省这一跳、不写「无」。按别的平台实测推断的标 `inferred`。
- **每个 harness 两个判词**:asight 在不在路径上(是 / 否 / 不知道);被采集没有(是 / 否 + 一个原因码)。只有「被采集」本身不知道时 `status` 才退出 3。
- **永远不印**:代理 URL 里的用户名与密码(打成 `***@`)。
- asight 在路径上时,`status <harness>` 总印一句条件句:`If your VPN or proxy routes by process, it sees asight, not codex.` 只这一句:不为它另设发现码,也不读你 VPN 的规则(D49)。

### A.3 你自己的代理

| 规则 | 内容 |
|---|---|
| 唯一来源 | 「你的代理」= agent 自己会用的那个:它读的环境变量、配置里的代理键、它认的系统代理。asight 没有第二处记它,你不用告诉 asight 两遍 |
| 接上 | `on <harness>` 读它现在的网络设置,把 asight 接在 agent 与它原本的下一跳之间:驱动模式不写任何网络设置,引擎按原目的地转、CONNECT / SOCKS 原样转给你的代理;代理模式把 agent 的代理入口指向 asight,上游按 [4.11](4.11-collector-model.md) §1「on / off」的五步取。计划与回执各印一行接上后的链,凭据打码 |
| 记下接上的是什么 | `on` 在 `~/.asight/netenv.json` 写 `adopted.<harness>`:打码后的链、读到它的文件与键、原值的哈希。**不存原值**(里面可能有密码) |
| 发现漂移 | `status`、`doctor` 与守护进程用同一读法重读设置,与 `adopted` 比。只比**文件**:跑命令的那个 shell 里有没有导出 `HTTPS_PROXY` 不是你改了什么。agent 自己的设置变了 = `proxy-changed`;系统代理变了 = `netenv-changed`(代理模式下守护进程重算上游,不算失败,不碰 agent 的设置)。期望态为 off 的 harness 不报漂移。只有守护进程写 `netenv-change` 事件;`status` 与 `doctor` 只读、只报,不写任何文件 |
| 漂移之后 | `status` 画出新的路,说清 asight 还在不在路径上,并印那一条接上的命令。驱动模式:新进程照常被采,只列「pid N 仍按启动时的设置」;代理模式:字段不再指向 asight = 已绕过 asight,印 `asight on <harness>` |
| 不悄悄覆盖 | 只有你跑的 `on` 会写 agent 的网络设置。`status`、`doctor`、守护进程只读、只报,绝不改回。`on` 要改写你在上次 `on` 之后改过的设置时,先列进计划、再确认(§1.4) |
| `off` 留下你的设置 | `off` 只撤 asight 写的值:字段仍是 asight 的值就回到接上时的原值;你之后改过就不动,回执写 `your later edits are kept`。驱动模式下 `off` 不碰任何网络设置 |
| 不加命令 | 换代理 = 照常改 agent 的设置,需要时再 `asight on <harness>`。没有 `asight proxy` |

**实现要点**

- 要重启的发现(要重启的未信任原因、`negative-cache`):第一步是 harness 描述符里的重启办法(应用里的步骤);设置活在托管进程里时(目前只有 Codex 的 app-server),第二步是填好 pid 的 `kill <pid>`(Windows `Stop-Process -Id <pid>`);那个进程没在跑就没有第二步。
- 命令里的「文件与那一行」取自这个设置自己的来源:来自 shell 变量就给 `unset` / `export`(不指任何文件);来自某个文件就指那个文件与实际命中的键;还没有这个设置(如 PAC 之后要写一个具体地址)才给它读的第一个文件。一个步骤一个动词:删就是删掉某个键,改就是把某个键写成某个值。
- `cause-unknown` 只回答被点名的 harness,且该 harness 没有任何 `problem` / `expected` 发现时才报;不带名字的 `doctor` 不报它。它是条件句,不断言那个 agent 连不上。
- **发现算不出来时**:`doctor --json` 的 `findings` 是 `null`,另带 `findings_error`(一句原因);文本写 `Findings: unknown (<reason>)`,不写「没有」。`null` 与 `[]` 不混:`[]` 是读了、没有发现。退出码不变。

**闭集与数据(D38)**

- 上表的码是闭集:`status` 的原因、`doctor` 的发现、看板的指示用同一组名字,一个名字只定义一处(与 [4.7](4.7-netenv.md) 共用的也一样)。
- 写成 `failure` 事件的:`not-routed` `proxy-dead` `proxy-unsupported` `elevated-agent` `forwarder-down` `upstream-unreachable` `route-loop` `seal-failed`,让期望为开的 harness 采不到的 `proxy-changed`,以及 `cert-root-pending` `cert-root-declined` `cert-root-missing` `cert-bundle-missing` `cert-key-missing` `cert-intermediate-unavailable`。其余只进 `status` / `doctor` 与命令的回执。`upstream-unreachable` 同一形态 60 s 内最多写一条。
- 事件 `netenv-change`:`{event:'netenv-change', harness?, code, from, to}`,`from` / `to` 是打码后的紧凑链;系统代理变了的码是 `netenv-changed`。
- 需要你动手的证书状态(待定、被拒、根不见了、密钥不在)让 `status` 退出 1。
- **名单**(D51):`status` 有无守护进程都自己读 `agents.json`:每个 harness 列生效的名字与来源、被忽略的、文件的问题;每个在跑进程带它命中的名字。坏项不生效、其余照用,不静默。
- harness 描述符里的 `proxy` 是数据:读哪些环境变量与配置键、认不认系统代理(分 HTTP 与 WebSocket)、支持哪些代理协议、不支持时怎样、本平台是实测还是推断、怎么退出与重启。格式以 [4.7](4.7-netenv.md) 为准。

**`planned`**:`install` / `on` / `off` / `uninstall` 停在写之前时(`--dry-run`、需要确认而没有 `--yes`、或 `--json` 下根本不问)用同一个键说「本来要做什么」:一个数组,每项都说清是哪个文件、为了哪个 harness、要动什么——`install` 的项是 `{what, detail, harness?, forms?, carrier?, paths?, keys?}`(`what` 是这一项是关于谁的,`detail` 是英文一句话,`paths` / `keys` 是要写的文件与配置键路径),`on` 的项是 `{harness, route, kind, forms, paths}`,`off` 的项是 `{path, how, harness}`(没有安装记录、只能按 asight 自己的标记撤时),`uninstall` 的项是 `{path, change}`,`change` 说的是删还是改。看板改类别时(命令行的 `classes` 不预演、不问,它只改 `~/.asight` 里的文件)也先回计划([4.4](4.4-server.md) §控制面「先计划后确认」),那份 dry-run 回执的项是 `{class, before, after, paths}`:哪个类别、改前改后的整条记录、要写的两个文件(依据:4.4「`/control/classes`(改动类的 op)走同一套」与本段「每项都说清是哪个文件、要动什么」;`before` 在项里,所以两次请求之间别人改过这个类别,`plan_id` 就对不上)。停在这里的跑退出 1(`--dry-run` 除外:它本就是照预期走的),且没有任何东西被改。

### C.5 每个查询的文档

每个文档都有 `schema: 2` · `command`(= 查询的名字;没有另一个 `query` 键)· `ok` · `errors: [{where, reason}]`(读不全时非空,不静默)。`status` 与 `doctor` 的文档见 C.3 / C.4:`status --json` 印的就是 `query status` 的那个文档,连 `command` 也是 `status`。分页的文档另有 `next`(下一页的 `--after`,没有下一页为 `null`)与 `has_more`。

读段索引的名字(`sessions` · `calls` · `classes` · `segments` · `overview` · `traffic`)都带 `as_of` = 段索引里最新一条调用的时间(每个数都说清截至何时,不变式 4)。

`overview` 与 `traffic` 两行的形状、以及 `as_of` 的这条通则(依据:本附录是形状的权威——[3.5](3.5-query-layer.md) §Goal 把名字、参数与文档形状指回这里;D24 一个数只出自一个文档;D59③ 没有 ETL 也没有 `cache_events`;D62② 只凭段索引或受字节预算约束;「代码从少」——时间窗沿用 `--since` / `--until`,不另立 `--window`)。

| 名字 | 顶层键 |
|---|---|
| `sessions` | `sessions:[{session_id, harness, harness_inferred, provider, project_slug, project_path, title, title_source, entrypoint, calls, logged, probes, other, has_subagent, session_synthesized, last_ts}]` · `next`。`title_source` ∈ `harness-local-store`(来自被测 harness 自己的本地存储,**不是**采集到的线上字节)· `wire` · `null`(没有标题):保真边界就地标明,看板不自己再推一遍(D24 · [4.4](4.4-server.md) §人类标题的来源) |
| `session` | `meta`(同 `sessions` 的一项)· `records:[{id, ts_request, is_llm_call, response:{status}}]` · `analyzed:{lanes:[{…, calls}], stats, …}`(看板读的就是 `analyzed.lanes` 与 `analyzed.stats`;`steps` 与 `streams` 不上线——它们在进程内是同一批对象,序列化就是三份拷贝)· `logged:{count, labels, items:[{id, ts, endpoint, status, request_bytes, response_bytes}], shown}`(只存了头与大小的调用;没有为 `null`)· `probes:{count, series}` · `truncated`(保真边界;没有为 `null`)· `page:{cursor, limit, total, returned, baseline, next, has_more}` |
| `calls` | 带筛选(`--class` / `--host` / `--harness` / `--session` / 时间):`as_of`(段索引里最新一条调用的时间)· `class`(给了 `--class` 时)· `total` · `detail_limit` · `records:[{id, ts, harness, class, host, endpoint, status, sent_bytes, received_bytes, retention, ref, …}]`(只最新的 `detail_limit` 条带体;`received_bytes` 为 `null` = 没记下来,**不写 0**;`retention` ∈ `full` · `log`;`ref` = 记录 id)· `next` · `has_more`。给 `--ref <记录 id>` 时:`records:[那一条]` · `total:1`,形状与上面同一个。什么都不带:`classes:[{class, count}]`。**口径**(依据:D24——与 `sessions` 一项同一个 harness 判定;不变式 4 / D38:读不到不静默):`harness` = 与 `sessions` 一项相同的 harness 判定(先看进程,否则看 UA),`--harness` 按它筛;给了 `--class` / `--host` / `--ref` 任一个才列调用,否则文档是类别表;`--ref` 不认识 → `records:[]` · `total:0` + 一条 `errors` |
| `overview` | `as_of`(同上)· `calls:{total, llm, logged, failed}` · `bytes:{wire, stored}` · `sessions:{total}` · `harnesses:[{harness, sessions, calls, bytes, last_ts}]` · `usage:{coverage:{sessions_read, sessions_in_window, capped_at, reason}, rows:[{harness, model, lane, sessions, calls, failed, no_usage, input, output, cache_read, cache_write, cache_known}]}`。时间窗 = `--since` / `--until`,口径是**最后活动落在窗里的会话整段计入**;除 `usage` 外的数只读段索引,`usage` 读用量旁注、旁注没覆盖到的部分受字节预算约束,读了多少与为何停写在 `coverage` 里(保真边界,[3.5](3.5-query-layer.md) §访问模式)。`cache_write` 为 `null` = 这个服务商没报写缓存数,**不写 0**。按类别的分布与盘上占用只在 `classes` 一处(D24),本文档不重复;每次调用的 cache 断开只在 `session` 的回放里(D59③:它要读记录体)。**口径**(依据:D24——与 `sessions` 文档共用一条计数规则;[1.7](1.7-overview-dashboard.md) 的口径行与主对话缓存命中行;不变式 4;代码从少):窗口——最后一次调用落在 [since, until] 的会话整段计入(它的每一次调用),没有会话的行按它自己的 ts 落在窗里计入;`calls.total` = 计入的行数,`calls.llm` = 存了全文的推理调用(`is_llm` 且不是只记日志,与 `sessions` 一项的 `calls` 同一规则),`calls.logged` = 只记了日志的推理调用,`calls.failed` = 状态缺失或 ≥ 400 的推理调用;`bytes.wire` = 记下了的 Σ发出 + Σ收回(有没记下的就是下限),`bytes.stored` = Σ存下的字节;`harnesses[]` 按 harness 用同一套规则,harness = 会话元数据的 harness 判定,它的 `bytes` 是线上字节;`sessions` 只有 `total`(按窗口口径计入的会话在窗里都活动过,「活动中」恒等于总数,没人读它);`usage.rows[].lane` 取 `session` 的 `analyzed.lanes[].kind` 的闭集,主对话是 `main`;`usage.rows[].calls` 与会话元数据的 `calls` 同一规则;`usage` 的每次调用取自读取侧的用量旁注([4.2](4.2-storage-etl.md) §用量旁注),旁注还没覆盖到的调用按会话最新在前现算、只花它们存下的字节:现算到下一个会让这些字节总数超出预算的会话之前停,之后的会话不再现算,调用全在旁注里的照样计入(依据 [3.5](3.5-query-layer.md) §访问模式:旁注覆盖到的部分不该被一个没覆盖的会话挡住);`coverage.sessions_read` = 每次调用都读到了的会话数,`coverage.capped_at` = 停下时的字节预算、没停为 `null`,`reason` ∈ `byte-budget` · `null`;`usage.rows` 按 `harness`、`model`、`lane` 升序(`null` 在后),所以文档只取决于读到了哪些调用、不取决于它们来自旁注还是现算;一行里没有一次调用报过写缓存计数时该行 `cache_write` 为 `null` |
| `traffic` | `as_of`(同上)· `hosts:[{harness, harness_inferred, host, first_seen, last_seen, requests, sent_bytes, received_bytes, received_unrecorded, classes:{<类别>:条数}}]` · `harness_since:{<harness>:时间}` · `totals:{requests, sent_bytes, received_bytes, is_floor:true}` · `next` · `has_more`。时间窗同 `overview`;`received_bytes` 为 `null` = 没记下来,**不写 0**,`received_unrecorded` 是这一行没记下响应大小的条数;`first_seen` 与 `harness_since` 取**整个索引**、与时间窗无关(「新」的判定靠它,[1.10](1.10-traffic.md));`totals` 恒带 `is_floor:true`(有未记录的就是下限)。**口径**(依据:[1.10](1.10-traffic.md) 的发出 / 收回行与不变式 4;大多数流量没有会话,按会话框窗会把它们漏掉):每条请求按它自己的时间落窗,会话不参与;`hosts` 按 harness、再按 host 升序;`harness` = 会话元数据的 harness 判定,组里任一行是推测的则 `harness_inferred:true`;一行的请求都没记下发出(收回)字节时该行 `sent_bytes`(`received_bytes`)为 `null` |
| `block` | `ref` · `bytes` · `encoding` · `fidelity:{verbatim, note?}` · `truncated` |
| `classes` | `classes:[{class, keep, builtin, rules:[{rule, host, path, harness}], counts:{h24:{calls, bytes}, d7:…, all:…}}]` · `disk:{asight_bytes, records_bytes, sealed_bytes}`(三个都是盘上的字节数:`~/.asight` 全部、`raw/` 里的明文段、`raw/` 里的封存段;明文与封存两个文件都还在的那个段同时计入后两项) · `file` · `last_change` |
| `segments` | `segments:[{segment, state, records, bytes, sealed_bytes, ratio, from, to, problems:[{code, reason}]}]` |

## 附录 D · 性能的参考数据

§4.1 的速度目标在这份数据上测。它由脚本生成(`scripts/gen-dataset.mjs`,新;测量用 `scripts/perf-query.mjs`),**不入库**:一份 1 GB 的夹具不该进 git,而生成器是可读的规格。脚本收一个种子,同一种子两次生成的字节相同。

### D.1 数据集

| 成分 | 形状 |
|---|---|
| harness 组成 | 七个 harness 都有,每个至少两个会话,各自的线格式与 endpoint 按各 harness 已采到的样本 |
| 长会话 | 按实测的 OpenCode 会话的形状:每次调用的上下文约 0.8 MB,每轮涨 7 KB,一个会话 14–300 次调用;含流式回复与 usage |
| 短会话 | 1–5 次调用,数量上占多数(分页与列表的真实形状) |
| 非 LLM 类别 | 每个内置类别都有数据:一个目录一类的 2.7 MB 响应被反复取(每次的线上字节数不同——压缩与分帧不一样),以及大量小包遥测(只存头与大小的那一级也要有) |
| 总量 | 约 1 GB 明文当量,切成多个 128 MB 的段。生成器只写明文:封存是守护进程的事(它一起来就把每个已关闭的段封一遍,D.2 测的就是这个),所以查询是在那之后测的——那时除了守护进程正在写的那一段,段段都已封存 |
| 磁盘上限 | 开发机与每台测试机上峰值不超 3 GB(生成 + 封存核对的明文底本同时在盘上的那一刻);超了就停下来报,不写满磁盘 |

### D.2 测什么

| 指标 | 怎么测 |
|---|---|
| 每个查询的冷启动墙钟时间 | 先建一次索引,记下建索引用了多久;之后带着索引,每条 `asight query <name>` 各跑 5 次、取中位数,每次都是新进程。只这一组,不再测没有索引的一组;macOS 与 Windows 测试机上各跑一轮。要参数的名字取数据集里最大的那个:`session` 用调用最多的会话,`block` 用最大那个段的最后一条记录(最坏情况,也只有它要翻到段尾) |
| 封存比 | 封存后字节 / 明文字节,按段与整体各一个数 |
| 总占用 | `~/.asight` 的大小、其中原始记录与索引各多少;与被测 harness 自己存的量对比 |
| 自动封存 | 守护进程跑起来后,每一个关闭的段是不是都被封存了、每段用了多久、核对是不是通过;失败的段明文还在不在 |

每轮记下数据集的种子、段数与字节数;没有记录的性能数字不算验收。

## 验收(可跑 check)

单元测试走 `npm test`,在沙箱 HOME 里跑,信任库、自启器、进程管理器都注入(0.1 §3「不碰真实机器」);标 [VM] 的在测试机上跑。编号不复用,缺的号是已删条目。

看图验收(D58⑥)不在下面的编号里:每个命令的典型输出由 `scripts/cli-shot.mjs` 渲染成图、定稿前另有 macOS 与 Windows 测试机真终端的截图——这是定稿前的功课,不是一条跑得出红绿的 check。

- **V1 守护进程不在时 `off`**:每个入口回到 `install` 之后的字节,退出 0,全程没拉起守护进程。
- **V2 独立撤销程序**:源码目录挪走后 `~/.asight/bin/asight-off` 撤净同样的入口,输出与 `asight off` 一致。
- **V3 回执 == 实际改动**:回执(与 `--json`)列出的文件集合 == 实际被写的文件集合。
- **V4 [VM] off 保证**:`off` 返回、在途响应结束后强杀守护进程:agent 的新连接零失败,看到上游真实证书,没有本实例的引流。
- **V5 按 harness**:`off claude-code` 只撤它,其余 harness 的入口逐字节不变、仍被采集;`--json` 只印正式名字;`claude` 与 `claude-code` 结果相同。
- **V6 用法错误**:未知命令、未知 harness、未知选项都退出 2,沙箱 HOME 逐字节不变。
- **V7 非终端的 `install`**:不带 `--yes` 只印计划、零写入、退出 2;`--dry-run` 零写入、退出 0、回执与真跑一致;要改的文件比上次确认过的多的 `on` 同理。
- **V8 备份**:目录 0700 / 文件 0600;文件验证回到原样后备份被删;用户改过的那份留下并列出;备份写不进时用户文件逐字节不变。
- **V9 `--json`**:每个命令的输出过 schema 校验;stdout 恰好一个 JSON,stderr 空。
- **V10 读不到就说读不到**:连接数、网络环境、守护进程状态读不到时 `status` 印 `unknown` 加原因,不印 0 或「无」;`--json` 带对应的 `*_error` 与 errno。
- **V11 独立撤销程序的形状**:静态检查 `src/off/` 与生成的 `asight-off` 的 import 全是 `node:*`;生成的文件里没有 `import`、`export`、顶层 `await`(没有扩展名的文件按哪种模块加载,由 Node 版本与上层 package.json 定);顶层重名、非 `node:*` 的 import、循环、`export default` / `export {}` / `export *`、改名的 import 各造一例:生成器拒绝,且一个字节也不写;`checkStandalone` 只在版本行是当前版本、字节与现建的相同、且文件可执行时为真;写不进它时 `install` 在碰任何 agent 文件之前就停。
- **V13 `uninstall` 不代做 `off`**:有 harness 期望为 on 时退出 1、`error.code` 为 `collectors-online`、注入的工具零次调用、HOME 不变;全部 off 后按装的反序撤,根的密钥最后删。
- **V14 其余平台**:没有采集器的平台上 `on` / `daemon` 印 `not supported yet`、退出 1;`off` 照常,没装过就如实说没有东西要关、退出 0。
- **V15 `off` 不碰证书**:七个 harness `install` + `on` 后 `off`:代理入口撤净,而根、密钥、合并包、证书配置键、包装、插件逐字节不变,证书类工具零次调用;之后 `uninstall` 撤净。
- **V16 `install` 之前就在跑的 agent 不被弄断**:被判 `config-after-start`、连接透传、客户端零错误;`on` 与 `status` 列出要重启;重启后被解密;已被采集的进程经 `off` → `on` 仍被解密。
- **V17 [VM] 在途连接**:SSE 流进行中 `off`:客户端收到的字节与 mock 发出的逐字一致,响应结束后连接被关,下一个请求直连;空闲连接在 `off` 返回时已关。
- **V18 [VM] 不带名字的 `off` 之后**:驱动模式没有本用户的守护进程与助手、没有本实例的引流;代理模式没有门在听,而守护进程还活着、照常应答(D62⑥),随后的 `on` 不经 OS 重拉就把门开回来;两边登录自启都还注册着(D61);有透传连接时等它关闭再收尾,`--now` 立即切断。
- **V19 help == 分派**:从 help 文本解析出的命令集合 == 分派表的命令集合;每条 help 的用法行与命令表里的 `usage` 逐字相同,选项集合也相等;没有隐藏别名表。
- **V20 拒绝 root**:以 root 跑 `install` / `on` / `off` / `uninstall` / `daemon` / `classes set|add|rm|reset` 都在读写任何东西之前拒绝、没跑任何 OS 工具;`setup-helper` 非 root 拒绝。
- **V21 幂等、可续**:`on,on` / `off,off` 无副作用;`on` 写到一半崩溃后再 `on` 续完、再 `off` 撤净;每个崩溃点上没有指向没开的端口或缺失文件的入口;已经到位的项(哈希与记下的相同)在第二次 `install` / `on` 之后,`installed_at`、inode 与修改时间都不变。
- **V23 没有 VPN 写入**:清单、备份、回执里没有这类条目;静态扫 `src/netenv/` 没有写路径。
- **V24 安装记录丢了**:非终端不带 `--yes` 的 `off`:引流已摘、用户文件逐字节不变、列出待撤项、退出 1;带 `--yes` 再跑则撤净。
- **V25 按 harness 撤的共用文件**:一个文件同时有代理键与证书键时,`off` 只撤代理那一半,证书那一半逐字节不变;用户在 `on` 期间改过的键原样保留。
- **V26 退出码**:§1.3 的 0 / 1 / 2 / 3 / 70 各一例;同一个码在不同命令里含义相同。
- **V27 不重启**:`on` / `off` / `uninstall` 全程注入的进程管理器记到零次重启 agent 的调用。
- **V28 `state.json` 迁移**:读得动更早的版本,读不出时全部按 off 起并留一条失败记录。
- **V29 `install` 的回执**:含 CA 指纹、字面的 `asight on` / `off` / `status` / `uninstall`、`asight-off` 的绝对路径、代价那一行、每个形态的证书载体或够不到的原因;清单每项有非空的手动撤销办法。
