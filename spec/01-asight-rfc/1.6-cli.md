# asight · RFC 1.6 — 命令行界面

> **这是什么**:asight 命令行的契约:开关模型(`on` / `off` / `status` / `uninstall`)与各自的保证、命令清单、旧采集(过渡期)、跨命令规则、asight 自己坏了时怎么办、VPN 感知的 CLI 一侧、网络拓扑与诊断(§9)。
> **受众**:人(核对「我的 agent 有没有被监听」「asight 出了问题能不能一条命令关掉」是否成立)+ agent(据此改 `bin/asight.mjs` 与采集器命令)。
> **Source-decision**:**D39**(二元开关;4.6 原「注入一次、长期保持,不随开关变化」推翻)· **D43**(引流只有驱动模式与代理模式;VPN 只读、只决定上游;影响超出 agent 的改动由用户点名,§1.7)。承 D31(按进程,不碰系统代理 / 整机流量)· D36(按用户运行,sudo 只在助手)· D37④(信任入口)· D28(只剥哨兵块)· D38(失败不静默)。§9 网络拓扑与诊断 = **D39⑩**。
> **不含 → 去哪查**:采集器内部机制 → [4.6](4.6-process-collector.md);旧采集机制 → [4.1](4.1-capture-sources.md) / [4.5](4.5-distribution.md);改包命令 → [5.1](5.1-intervention.md);代理模式(Windows;macOS 待写)→ [4.8](4.8-win-collector.md);本机网络探测(只读)→ [4.7](4.7-netenv.md)。

## Goal

用户只关心两件事:我的 agent 有没有被监听;asight 出了问题,能不能一条命令关掉。所以开关是二元的:`on` 开始采集;`off` 撤掉 asight 对这些 agent 的全部影响,asight 坏了也能用。每个改动用户机器的命令都打印回执;改用户文件前先备份。

## 1. 开关模型

### 1.1 四个命令与各自的保证

| 命令 | 做什么 | 做完之后保证什么 |
|---|---|---|
| `asight on [harness…]` | 开始采集这些 harness;不带名字 = 本机检测到的全部。首次运行即安装(§1.6)。写信任入口([4.6](4.6-process-collector.md) §身份与信任的表),挂引流(驱动模式 = 本实例的 link;代理模式 = 写各形态的代理入口、拉起 asight 自带内核,[4.8](4.8-win-collector.md);没有新采集器的平台上 `on` 驱动旧采集,见 §4;点名项见 §1.7),启用自启并拉起守护进程。 | 之后新启动的这些 agent 被采集。`on` 之前就在跑的进程照常透传、不被弄断;`on` 的输出与 `status` 逐个点名「重启后才会被采集」,点的是真正发请求的进程(如 Codex 的 app-server 守护进程,不是用户看到的 TUI;[4.6](4.6-process-collector.md) §各 harness 的进程特征)。 |
| `asight off [harness…]` | 撤掉 asight 对这些 agent 的全部影响:引流、信任入口、点名项(§1.7)、旧采集在 VPN / 代理软件里的块。被改过的文件回到改前的样子。不带名字时另外停守护进程、停用自启(§1.4)。 | **off 保证**(§1.2)。 |
| `asight status [harness…]` | 每个 agent:正在被采集;或者没有,为什么。 | 只读。 |
| `asight uninstall [--purge-data]` | 先把全部 harness 的期望态写成 off,停用自启并停守护进程(§1.4 第 4、5 步;由 systemd 停,它不会按 `Restart=on-failure` 拉回),确认引流已摘;再对全部 harness 做 `off`,再删 asight 自己(CA、自启单元、运行目录、安装清单、备份、独立撤销程序;代理模式另删自带内核的可执行文件,[4.8](4.8-win-collector.md) §8)。采集数据默认保留。停守护进程时先摘引流,按 §1.3 关连接(HTTP 在当前响应结束时、WebSocket 在本轮终止消息处);仍开着的透传连接与看不到终止消息的 WebSocket 随守护进程退出被切断,回执写明条数。 | 本用户下零残留(例外见 [4.5](4.5-distribution.md) §C)。整机的能力助手另要一步 `sudo asight setup-helper --remove`。 |

- 没有 `restore`:关与撤是同一件事(不区分 off 与 restore:用户分不清)。
- **信任入口随开关**(推翻 [4.6](4.6-process-collector.md) 原「注入一次、长期保持,不随开关变化」):`on` 写,`off` 撤。理由:Codex、Hermes 的入口替换整个信任库(合并包);合并包坏了或被删,它们连真上游都可能连不上,所以 `off` 必须能把入口撤掉。
- **代价**:信任入口只在 agent 启动时读。`off → on` 之后,已在跑的 agent 要重启一次才被采集。这不会弄断它们:守护进程把「入口在进程启动之后才出现」判为未信任(4.6 §确认信任 `config-after-start`;「之后」按安装清单该条的 `installed_at`),未信任的进程照常透传。`installed_at` 只在 `on` 实际(重新)写入该入口时更新:入口已在、sha 等于 `post_sha256` 时,`on` MUST NOT 写这个文件、MUST NOT 改 `installed_at` 或它的 mtime;否则在跑、已被采集的进程会被判 `config-after-start`,采集静默停掉(R9)。
- **登出后停采(Linux)**:用户级 systemd 单元在该用户最后一次登出时停掉,除非开了 linger;留在 tmux / SSH 里的 agent 之后照常直连、不再被采集(fail-open)。`on` 不替用户开 linger(R8)。linger 没开时,`on` 与 `status` 各印一行「登出后停采(未开 linger)」,并给出开启命令 `loginctl enable-linger <用户名>`;读不到 linger 状态时印「不知道」加原因,不印「已开」(R11)。读法:`/var/lib/systemd/linger/<用户名>` 在不在,只读,与守护进程 `daemon-start` 事件的 `linger` 字段同一读法。守卫:test V39。
- **保存设置不随开关(D40 × D39)**:`~/.asight/retention.json` 与 `~/.asight/logs/retention.ndjson`(`asight keep` 的设置和它的修改记录)说的是之后的调用存什么,不是 asight 对 agent 的影响,也不是采集数据。所以 `off`(带不带名字、带不带 `--now`)不碰它们,off 保证(§1.2)与它们无关,采集关着时设置只是不生效,`on` 之后照旧;`uninstall` 也留着它们(它们不在「asight 自己的文件」那一串里),`--purge-data` 也不删(那删的是采集数据)。理由:CA 轮换的做法是 `uninstall` 再 `on`(D39),操作者为省盘设的 `log` 不该因此悄悄改回全部 `full`。想清掉:`asight keep all all full`(留下文件,全部 `full`),或自己删文件。设置文件不在 `state.json` 里(D40 的取舍:旧 MITM 也读它),所以 `state.json` 的版本、迁移与 `off` 的撤销清单都不涉及它。守卫:V59 · V60。

### 1.2 off 保证

**`off` 返回、且在途响应结束之后,asight 不在这些 agent 的路径上;此后 asight 任何部件死了、卡了,都影响不到它们。** 做不到这条的引流方式不提供。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 11 条),V4 / V17 落地后加测。

**例外(如实写明)**:透传(splice)连接,以及看不到终止消息的 WebSocket 连接(harness 文件没声明终止消息,或这一轮的终止消息解不出、被略去,[4.6](4.6-process-collector.md) §传输与帧级记录「看不到终止消息时」),引擎看不到响应边界,在它们自己关闭之前仍经引擎(§1.3);对这两类,保证只到「新连接直连」为止,在那之前守护进程也不退出(§1.4),除非操作者用 `asight off --now` 立即切断(§1.3)。`off` 的回执与 `status` 单列它们的条数。

**例外二:代理模式(D43 登记;「稳健 = 两句话」)**:`off` 撤掉入口、把该形态在自带内核里切成只转发;`on` 期间启动、读了入口的 agent 重启前仍连着自带内核(只转发,不经引擎、不解密、不记录),守护进程与内核排空到它们退出(§1.4)。内核在那之前死了,它们连不上,直到内核被拉起或它们重启。`off` 的回执与 `status` 写「还有 N 个 agent 连着 asight 的内核(只转发),重启它们之后 asight 就完全退出」;`asight off --now` 立即停内核,回执列出会断的 pid。守卫:test V55。

下表「能否做到」「验证状态」两列是评估,待验证;保证本身与「做不到的不提供」是定下的。

| 引流方式 | 能否做到 off 保证 | 验证状态 | 结论 |
|---|---|---|---|
| 驱动模式:操作系统的按进程机制(Linux eBPF,已有;D43 起只有 Linux 用它) | 预计能:摘钩即可,不碰 agent。Linux 开着时另有两层 fail-open(4.6 §Linux 机制) | Linux 有实验室用例(4.6 S1、S7) | Linux 提供 |
| 代理模式:agent 的代理入口指向 asight 自带内核(只转发、引擎不在时退回上游的 mihomo;Windows、macOS,D43) | 能,有一处例外(上文「例外二」):`on` 期间启动的 agent 重启前仍连着自带内核,只转发 | Windows 实验:各形态经入口进来,代理不在时 fail-closed、回来即恢复(4.8 E9);引擎死后内核 139–215 ms 改走上游(4.8 §3.3 [T0]);排空与 `--now` 待 4.8 W48。macOS 未验证 | Windows 提供(4.8 §4.2);macOS 待实现并在本机验收(D39⑥),在那之前 macOS 跑旧采集 |
| VPN / 代理软件里加 asight 的块 | 能,有条件:`off` 按 D28 只剥哨兵块,热重载后核对生效(D29) | 旧 Clash 块已在用(D29) | 新采集器不做(D43 撤回);只剩旧采集的 Clash 块(过渡期,§4) |
| 自带内核当 TUN 或系统代理 | 整机接管(违 D31④) | — | 不提供 |
| 把 agent 的代理字段指向 asight 引擎 | 不能:agent 只在启动时读代理设置;`off` 之后它要么继续经 asight(asight 一停就断),要么改配置再重启 | Windows 实验已见 asight 一停 agent 就断 | 不提供;指向自带内核是上面的代理模式 |

- `off` 之后,`on` 期间启动的 agent 仍信任 asight CA,直到它重启(入口只在启动时读,4.6 §撤销顺序第 5 步)。这不影响路径:没有引流,它的连接不经 asight。回执列出这些进程(「重启前仍信任」)。

### 1.3 在途连接

`on` 期间已经经引擎中转的连接,TCP 上没法中途改道。规则:`off` 返回后,引擎在每条中转连接的**当前响应结束**时关掉它,agent 的下一个请求就直连。细节:

| 连接的状态 | 引擎怎么做 |
|---|---|
| 空闲(keep-alive,没有请求在途;含引擎已终结 TLS、客户端还没发过请求的连接) | 立即关两侧 |
| 有 HTTP 请求在途(含 SSE;含 CONNECT / SOCKS / `https://` 代理隧道里解密的) | 响应按被动分帧收全、转完,再关两侧。客户端在此之前已发出下一请求的字节:照转、不记录(`off` 返回之后开始的请求零记录,4.6 §开关语义),它的响应结束后再关 |
| 透传(splice,引擎不分帧) | 看不到响应边界,等它自己关闭;`off` 的回执与 `status` 计它的条数(§1.2 例外) |
| WebSocket | 在这一轮的**终止消息**处关:终止消息按 harness 文件以数据声明的模式认([4.6](4.6-process-collector.md) §传输与帧级记录「逻辑调用怎么切」),引擎把含终止消息末帧的那块字节照转完,再按下文「怎么关」关两侧;Codex 下一轮自己重连。`off` 时没有打开的调用 = 空闲,立即关。MUST NOT 自己合成 close 帧(不往连接里写 asight 自己的字节)。harness 没声明终止消息、或这一轮看不到终止消息(同节「看不到终止消息时」),或任一方向的帧已不再被跟踪:同透传,等它自己关闭、计数 |
| 被 [5.1](5.1-intervention.md) 扣留的请求或响应 | `off` 先停用规则(规则保留、不删;不带名字的 `off` 停用全部,带名字的只对这些 harness 的请求停用),把扣留队列里的条目原样放行(不改一字节,审计记 `released-by-off`),再按「有 HTTP 请求在途」处理;`off` 之后新到的请求不再匹配规则。5.1 尚未实现:本行是规则,随 5.1 一起实现,在那之前不适用 |

- **怎么关**:先把已转发的字节写完再 `end()`(发 FIN),等对端关闭,至多 5 s 后才 `destroy()`;MUST NOT 在接收缓冲里还有未读的客户端字节时直接 `destroy()`(会发 RST,客户端可能丢掉已写出、还没收到的最后一段响应)。关连接本身不改任何字节,只由操作者的 `off` 触发,不属 D30 的改包。
- **`Connection: close`**:`off` 落在一条响应还在途时,引擎 MAY 在这条(最后一条)响应上加逐跳头 `Connection: close`,客户端就不再复用这条连接,不会撞上关连接时的复位。它是逐跳头,由操作者的 `off` 引起,不算 D30 的改包,不记 `intervention`。约束:只在这条响应的头还没转给客户端时加(头已转出的,比如正在流的 SSE,加不了,照常在响应结束后关;此时客户端恰在关闭时复用这条连接会看到一次复位,靠它自己重试,[4.6](4.6-process-collector.md) S5 单独计数);只在头部结尾的空行前插入一行 `Connection: close\r\n`,原有的头逐字节不动,响应已带 `close` 时不加;体逐字节不变(`content-length` 不变)。**MUST 记账**:这次调用被记录时,信封带 `asight_added:['connection-close']`(`resp_head_raw` 仍是上游发来的原字节,4.6 §记录);不论记没记(`off` 返回之后才开始的请求不记),`flows/` 的连接行带 `asight_added:[{seq, what:'connection-close'}]`。看板 MUST 在该调用上就地标「asight 加的 · Connection: close」(不变式 4)。除这一行头之外,MUST NOT 为了让客户端断开而改写响应。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 11 条)· test V37。
- **`asight off --now`**:不等在途连接,立即切断这些 harness 仍经引擎的连接(HTTP 在途响应、WebSocket、透传都算);不带名字时守护进程随即退出。这是操作者的显式意图:被切断的 agent 看到连接错误,靠自己重试(Claude Code 对已开始输出的流不重发,4.6 §Linux 机制「fail-open 两层」)。回执写切断的条数(`relayed.cut`);每条被切断的连接在 `flows/` 留连接行,`error.type` 为 `cut-by-off`。守卫:test V36。
- `off` 的输出与 `status` 写「N 条连接仍经 asight 中转,本次响应(或本轮)结束后关闭」(HTTP 在途与等终止消息的 WebSocket);透传与看不到终止消息的 WebSocket 另计「M 条等它自己关闭(`asight off --now` 立即切断)」;读不到写「不知道」加原因。

### 1.4 不带参数的 off

不带参数的 `off` 另外停守护进程、停用自启;之后没有 asight 进程在跑(代理模式的例外:守护进程与自带内核排空到 `on` 期间启动的 agent 都退出,§1.2 例外二)。`on` 重新启用。「asight 进程」的范围与例外见本节末。顺序:

1. 把全部 harness 的期望态写成 off(`state.json`,原子写,R12)。
2. 摘引流,按内核实际态确认。守护进程不在时,确认本实例的助手已不在(link 随它摘掉,4.6 §Linux 机制)。守护进程没响应(`lock` 超过 5 s 没刷新,或控制 socket 5 s 不应答)或还在启动中(有 `lock`、socket 不应答):不等它,先按第 5 步停掉它(助手随之退出、link 摘掉),确认 link 已消失,再进第 3 步。
3. 撤信任入口、代理入口与点名项(§1.7),以及旧采集在 VPN / 代理软件里的块,新旧两代都撤(§4)。代理模式在第 2 步先把自带内核的各形态切成只转发并读回。
4. 停用自启。Linux:`systemctl --user disable`,删 `default.target.wants/` 链接;单元文件是 asight 自己的,留到 `uninstall`。Windows:停用计划任务,或删登录启动项([4.8](4.8-win-collector.md) §7)。
5. 让守护进程排空后退出:按 §1.3 关完连接即退出(干净退出,systemd 不拉回),助手随它退出。`off` 不等它,回执写明守护进程的 pid 与还剩几条;透传连接与看不到终止消息的 WebSocket 还开着时它不退出,回执写「守护进程仍在排空:pid N,还剩 M 条等它们自己关闭;`asight off --now` 立即切断」。`--now`:不排空,按 §1.3 切断后立即退出。**排空期间又 `on`**:这条退出请求撤销,守护进程接着服务(`on` 只拉起没在跑的守护进程,它还活着,`on` 就落在它身上);之后再一次不带参数的 `off` 重新排空。任何时候退出都要求没有 harness 为 on,否则不退(退出是干净退出,systemd 不拉回,会留下 `state.json` 写着 on 而什么都没挂的局面;test `daemon.test.mjs`「/on after POST /off {exit:true}」)。**要停它时**(没响应、`uninstall`;以及不带名字的 `off` 遇到守护进程不在、而自启单元还开着或正等着 `Restart=on-failure` 重启——`systemctl --user is-active` 答 `active` / `activating`,`disable` 不取消那次重启):由自启单元管着时用 `systemctl --user stop asight-collector`(systemd 因此不按 `Restart=on-failure` 把它拉回);单元没管它或 stop 超时:SIGTERM,10 s 不退再 SIGKILL。每次发信号前按 `lock` 的 `start_time` 与 `boot_id` 核对 pid 身份,不符不发;`lock.helper_pid` 还活着一并 SIGTERM。收尾 `systemctl --user reset-failed asight-collector`,确认单元既不是 active 也不是 activating;写一条事件。**Windows**(守护进程由监管父进程管着,[4.8](4.8-win-collector.md) §7):要停它时**先停监管父进程**(核对 `supervisor.lock` 的 pid 与启动时间),再停守护进程;顺序反了父进程会把它拉回来。守护进程以退出码 0 退出时父进程随之退出,非 0 才重拉。代理模式下守护进程另监管只转发的自带内核,`on` 期间启动的 agent 都退出后两者一起退出;`--now` 立即停内核,回执列出会断的 pid([4.8](4.8-win-collector.md) §4.2)。

- 用户在终端里自己起的 `asight serve`(只读看板,不在任何 agent 的路径上)、前台的 `asight capture` / `asight mitm`:`off` 不杀,回执与 `status` 列为「你自己起的 asight 进程仍在跑」。前台的 `capture` / `mitm` 可能正中转 agent 的流量(agent 的 base_url 或代理指向它们),杀掉会弄断那些 agent;它们不是 asight 装的或拉起的,off 保证不管它们。守护进程排空后退出,`--now` 不排空。

### 1.5 按 harness

- `on` / `off` / `status` 都可带 harness 名(§3);不带 = 全部(可按 harness)。
- 期望态按 harness 记。`~/.asight/collector/state.json` 升到 version 2:`{version:2, updated_at, harnesses:{<id>:{desired:'on'|'off', policy:'auto'|'all', extra_hosts:[…], updated_at}}}`(看板「采集关 · 自 T 起」的 T 取它,[4.4](4.4-server.md) `/api/capture-health`)。`policy` 缺省取 `all`(D40:默认解密该进程的全部 TLS;`switch.mjs` 的 `DEFAULT_POLICY` 是唯一一处);写着 `auto` 的保持 `auto`,因为盘上分不出它是旧默认还是操作者选的。读到 version 1 时,把它的 `desired` / `policy` / `extra_hosts` 套到每个已安装的 harness(`policy` 只带过去写着的、写对的 `all` / `auto`,没写或写坏的取缺省)(已安装 = 安装清单点名的 harness;从没装过的不套、也不判);读不出时全部按 off 起,并留失败事件(4.6 §开关语义)。
- Linux:任一 harness 为 on 就挂本实例的 link。期望态为 off 的 harness,其进程从内核 `watch` 表摘掉:不改写、不上报元数据;守护进程不为它们写 `agent-untrusted`(它们本就不是采集目标)。某个 harness 的实际态:有在跑的进程时逐个核对内核 `watch` 表;没有在跑的进程时 = link 已挂且它的入口完好。都不读自己记的标志(4.6 §开关语义)。
- **`off` 的次序**:每次 `off`(带不带名字)都先写期望态,再把该 harness 的进程从 `watch` 表摘掉并读内核确认(全部为 off 时确认 link 已摘;守护进程不在时确认本实例没有 link),之后才撤入口、改写合并包;确认之前 MUST NOT 动入口或合并包。反过来做,进程还在 `watch` 表里时合并包已不含 asight CA,它的新连接拿到 asight 的叶证、被拒、请求失败(Codex 每次连接重读合并包,4.6 §身份与信任)。`on` 的次序见 R9。
- 逐个 `off` 完全部 harness 时:link 已摘,不在任何 agent 的路径上,守护进程与自启仍在(空转);要停它们用不带参数的 `off`。
- 按 harness 撤时,共用文件怎么处理见 [4.6](4.6-process-collector.md) §撤销顺序「按 harness 撤」。

### 1.6 首次 on(即安装)

- 先打印计划:要改的每个文件、asight 自己要建的东西、跳过的 harness 与原因、本机网络环境(§6)、要重启的进程。终端里等确认;不在终端里(stdin 或 stdout 不是 TTY,如 agent 代为安装)没有 `--yes` 时,只打印计划、什么都不改,退出 2。
- 之后的 `on`:要改的文件比上次确认过的(清单顶层 `confirmed_paths`)多出来时(新检测到的 harness、新的 `CODEX_HOME`),只列出多出的那些,再确认。
- 回执写明开、关、看状态、卸载的命令,以及独立撤销程序的路径(装完告知开关命令)。

### 1.7 点名项(D43⑥)

D43⑥:影响超出只属于 agent 的改动从不默认做;用户按形态点名,asight 执行并负责撤销。下表的命令面:只加一个旗标 `--opt-in`,确认仍是 R6 那一次,账仍是同一本清单(多一个字段 `scope`)。

| 规则 | 内容 |
|---|---|
| 哪些算 | 共享的用户级 / 本用户的 OS 设置(用户证书库、登录环境、用户 PATH、shell profile、VS Code 全局设置、应用的快捷方式);还装着非 agent 程序的宿主进程树(VS Code);要管理员的机器级位置(机器 PATH、所有用户的快捷方式、`LocalMachine\Root`、`/etc/ssl`、全系统的信任变量)。只属于 agent 的入口(它自己的配置文件、策略键、插件目录)不算,`on` 自动写。每个形态要哪几项、意味着什么,是 harness 文件的数据,表在各平台单元(Windows:[4.8](4.8-win-collector.md) §2.4) |
| 点名也不做 | 改系统代理、接管整机流量、登录环境或全系统的 `HTTPS_PROXY` 一类代理变量(§8) |
| 默认 | 不做。`on` 的计划另列一段「要你点名的(默认不做)」:每个形态一行,写要改什么、意味着什么(如「本用户的所有程序都会信任 asight 的 CA」「VS Code 的全部流量经 asight 的内核,不是 Kimi 的只转发」)、要不要管理员,以及点名用的整行命令。`status` 对这些形态报 `opt-in-needed` 和同一行命令,不报「不支持」 |
| 怎么点名 | `asight on [harness…] --opt-in <形态>[,<形态>…]`(可重复)。点名的单位是形态:一个形态要几项就一起做。计划把点名的项列进「要改的」,每项带「影响」一行;照常确认(R6)。`--yes` 只替确认,从不替点名 |
| 执行与入账 | asight 自己执行,入账、先备份、回执(R1、R2)。清单每一项带 `scope`:`agent`(自动)· `user`(点名的用户级)· `machine`(点名的机器级)。`status` 在该 harness 下列出「你点名的改动」 |

| 点名持续多久 | 到该 harness 的 `off` 为止:`off` 撤掉它的全部点名项,之后的 `on` 要再点名才做。开着时再跑 `on`(不带 `--opt-in`)不撤已做的点名项(R9) |
| 管理员 | 机器级的一项:计划标「要管理员权限」。asight 从不自己提权、不经手密码,自己也不以提升的令牌或 root 运行(R7)。**要管理员的一项,开或关,正常路径都是:一次确认(改什么、为什么需要管理员)→ 操作系统自己的提权提示**(设置页面的开关可以点击开启或关闭;某个 on / off 需要管理员 / root 权限时,弹窗让用户确认,再由操作系统让用户输密码,而不是给用户一条命令让他自己去做):Windows 是 UAC 的同意框,macOS 是系统的授权对话框,Linux 是 pkexec / polkit,在终端里就是 `sudo` 自己的 tty 提示。asight 起那一步,密码只进操作系统的提示框,asight 永远看不到,也 MUST NOT 自己画密码框。**印出整行命令只是退路**:没有提示可弹时(没有桌面会话、SSH 里无 tty 的独立撤销)才印,由用户自己跑。提示被拒 = 没做,入账(`pending-admin`);步骤之后只读核对,核对到了才记成已做 |
| 撤销 | `off`、`uninstall` 与独立撤销(R3)撤掉全部用户级点名项。机器级的一项同样走「确认 → 操作系统自己的提权提示」(上行的决定管「开或关」);提示被拒 = 没撤掉,留在 `pending-admin`。没有提示可弹时才退回印出确切的提权命令,结果码 `needs-admin`,退出 1;`status` 一直列着它,直到只读核对看到它已不在 |
| 入口还有没有效 | asight 自己定义的入口(PATH 最前的 asight bin 目录里每个命令名一个 shim、启动器、改写的快捷方式;D43⑤),`status` 逐个核对:命令名仍解析到 asight 的 shim(按操作系统的顺序查;Windows 上机器 PATH 在用户 PATH 之前)、快捷方式仍指向 asight 的启动器、在跑的 agent 是经入口启动的。失效报 `shim-not-on-path` · `entry-changed` · `not-via-entry`,`doctor` 给确切的步骤(§9.6) |
| 界面上没有按条撤销 | 撤不撤完全取决于该 harness 的拦截开着还是关着,而不是「要不要改文件」,否则会出现潜在的不一致:任何界面(CLI、看板)都没有按条 / 按文件的「撤掉」。撤销只有每个 agent 的开关:`off` 把它的全部改动(含点名项)撤掉,`on` 再放回来;界面把 asight 改过什么当**信息**显示——按 harness 列在各自的形态下,与 harness 无关的全局改动(CA 文件、代理模式的自带内核与它的自启、几个 harness 共用的机器级项)另立一个「全局」块。`--json` 里每一项的 `undo` 就是 `asight off <harness>`(§9.4),没有按条的撤销动作 |
| 给界面的数据(`--json`) | `status --json` 带 `opt_in`:按 harness 分,每个形态的每一项一个对象(形态、种类、状态、影响、要不要管理员、开启与撤销的命令;形状在 §9.4)。文本从它渲染,不另算(同 V43)。看板的设置页面(D31⑧;UI 单元待写,这里不设计它)显示的点名项与它是同一份,经 [4.4](4.4-server.md) 只读数据面的 `/api/capture-health`(`opt_in` 字段)读;页面上要开启、撤销的,就是这里的 `enable` / `undo` 那两行命令,不另造一套 |

守卫:test V56 · V57 · V58 · V63 · V64;各平台「默认 `on` 不碰共享设置」「机器级只经提权那一步」见 [4.8](4.8-win-collector.md) W63 · W65。

- 在没有新采集器的平台上跑 `on` / `off`,先印一行「本平台 on / off 驱动旧采集(过渡期)」。
- 没有新采集器的平台上,带 harness 名的 `on` / `off` 只认 `claude-code`(等于不带名字);别的名字退出 2,印「本平台只有 claude-code 的旧采集,没有按 harness 的开关」,什么都不碰。`status` 把 `claude-code` 拆成 Desktop(Clash 块 + MITM)与 CLI(旧 steer)两行;CLI 没被采集时写「`on` 不做旧 steer;要采集 CLI 用 `monitor on`」。
- `com.asight.env` 随旧采集整体关闭一起撤:`asight off`、`asight uninstall`、`desktop off`(改 [0.0](0.0-overview.md) §过渡期遗留)。旧采集开着时仍 MUST NOT 单独移除它(会停掉 macOS 上 Desktop 的采集)。必拒 · 审查([0.1](0.1-engineering-rules.md) §6 第 4 条);V12 的 `off codex` 用例落地后加测。

- 旧 MITM 达到 off 保证的条件:先剥 Clash 块、热重载并核对生效(新连接不再进 MITM),再让 launchd 向 MITM 发 SIGTERM:它停止接受新连接,等在途连接自己结束(旧 MITM 不跟踪响应边界,不按 §1.3 逐响应关),至多 10 s,余下的自己切断并计数,在 `mitm-stop` 行写 `cut`;`off` 读这一行当回执的条数(读不到写「不知道」)。**SIGTERM 只经 `launchctl unload com.asight.mitm` 发**:对 `KeepAlive` 的 agent 直接 `kill` 会被 launchd 拉回来;plist 带 `ExitTimeOut` 15,launchd 在 SIGTERM 之后等这么久才 SIGKILL,10 s 的排空在它之内(已装的 plist 要重装一次才带它,`on` 不替用户重启在跑的采集,R8)。**路由没有确认摘掉(核不答、重载被拒、读不回)时不卸 MITM**:Desktop 会被 Clash 指到一个没人听的端口;这时 `off` 的 `ok:false`、退出 1,回执 `relayed` 写「不知道」加原因(MITM 还在服务,不能报 0 条)。同一原因:`com.asight.env`、登录环境里的 `NODE_EXTRA_CA_CERTS` 与旧 CA 也留着 —— MITM 还在跑、路由可能还通,此刻起的 Desktop 没有那份信任就会在 MITM 的证书上 TLS 失败;回执 `skipped` 逐项列出,下一次路由确认摘掉的 `off` 再撤。`com.asight.monitor`(旧 CC-CLI 反代)不受 Clash 路由牵连,照撤。`launchctl unload` 对在跑的 job 可能阻塞到它退出(SIGTERM 之后至多 `ExitTimeOut`),所以这一次 unload 的工具上限是 `drainMs` + 10 s(默认 20 s),不是工具默认的 10 s;卸掉没有以随后的 `launchctl list` 为准,不看 unload 的退出码(见 OPEN)。`--now` 在旧采集上没有用(MITM 的排空是固定的),回执这么说。`off` 在剥块前写 `~/.asight/legacy-off.pending`(`{pid}`),旧 MITM 的 steer 监看见这个 pid 活着就不把块的消失记成 `steer-missing`;`off` 结束删它。旧采集有自己的操作锁 `~/.asight/legacy-op.lock`(R12 的旧采集一半)和日志 `~/.asight/logs/mitm-events.ndjson`(`off-note` / `install-note` / `uninstall-note`,R11)。一台没有任何 asight 证据(没有块、运行时没有、没有账、没有 MITM plist)的 Clash 不会被重载。Merge.yaml 里旧的 `prepend-proxies` / `prepend-rules` 只剥 asight 自己的项(名为 `atrace-mitm` 的代理、目标是 `atrace-mitm` 的规则;D28),用户自己写的同名列表一字不动、也不算 asight 的证据(只修错:旧代码把两个列表整个删掉,不看里面是什么)。核仍列着路由而运行时配置又不在时没有干净的配置可重载:`off` 的 `ok:false`,回执写明这个原因,不卸 MITM。现代码(`desktop off`)剥块后立即卸载的缺陷由 `off` / `uninstall` 的这条顺序修掉;`desktop off` 本身仍是原样的旧命令(§4:不加新功能)。
- `on` / `off` 驱动旧机制时同样守 §5 的规则:回执、改前备份、入账。账记在 `~/.asight/legacy-manifest.json`(格式同采集器的安装清单;不放进 `~/.asight/collector/`,免得看板以为装了新采集器)。旧命令自己(`desktop on` 等)保持原样。旧命令装的东西(`desktop on`、`monitor on` 写的 Clash 哨兵块、`com.asight.*` plist、CC settings 的暂存文件)不在这本账里:它们自己的标记就是它们的账,`off` 直接按标记撤,不走 R3 的按标记撤销确认;这些改动没有改前备份,`status` 与回执标「旧命令装的,无备份」。旧命令保持原样、不补账;经 `on` 装的(含 macOS 上做 `desktop on` 那些事的 `on`)都入账、有备份。所以 §6「VPN / 代理软件里的改动都入账」过渡期只对经 `on` 写的成立。
- **网页开关([4.4](4.4-server.md) · D26)在过渡期**:没有新采集器的平台上,`POST /control/monitoring {action:'off'}` 改为调不带参数的 `asight off`(两代都撤,回执与退出语义同 CLI),不再只调 `atraceOff`。网页的「开」过渡期不变(仍是 `atraceOn` 加 `com.asight.monitor`,即旧 `monitor on`);有新采集器的平台上两个端点都不变,网页的「关」就地标「只管旧 CC-CLI steer,不等于 `asight off`」,直到 [4.4](4.4-server.md) 的按用户隔离落地后改接新的 `on` / `off`。守卫:test V40。
- **`on` 在没有新采集器的平台上怎么写**:顺序是 计划与确认(R6)→ 锁 → `asight-off` 先写(写不进就什么都不改)→ CA(没有才生成)→ Script.js(Merge.yaml 有变化时同)先备份、入账(备份写不进就不改、记 `backup-failed`,此时别的什么都还没动)→ `com.asight.mitm` 与 `com.asight.env` 的 plist 写好并加载 → 最后才是块写入、热重载、向核读回(R9:路由指到的东西先就位,挂引流最后)。plist 没加载成功就不挂路由:没写 Script.js、没重载 Clash,没用上的那份备份与账项撤回,退出 1,回执写明,修好后再跑一次 `on` 补完。读回读不到(核接受了重载却不答代理表)是「不知道」,退出 1,不记 `clash-live`。每一步改动记账(`legacy-clash-block` · `legacy-launch-agent` · `legacy-env`,各带 `undo_by_hand`),已确认的路径记进账的 `confirmed_paths`,下次 `on` 不再问。已在位的(块在核里是活的;plist 在)一律不动 —— 不重写、不 unload、不重新 load(R8、R9);块在文件里而核里没有,或 plist 在而没加载,只补那一步:块补进核时用块自己带的端口(旧 `desktop on --port 9899` 的 MITM 就听在那里;设了 `ASIGHT_MITM_PORT` 才改端口)、不重写 Script.js;只有重写会改变文件的字节时(设了别的端口、手改过的块)才同新写一样先确认、先备份、入账。核不收路由时,耐久的一半(Script.js、账)已在,`on` 退出 1,回执写「NOT live now」与手动重新激活的办法,`off` 能撤。没有 Clash Verge 的机器:退出 1,什么都不建。`on` 建的 CA 目录 `~/.asight/ca` 不进账,`off` 不删(密钥是用户的),`uninstall` 才删。
- **`status` 在没有新采集器的平台上怎么判**:`claude-code` 拆成 Desktop 与 CLI 两行。Desktop 已采集 = Clash 核里有路由 + `com.asight.mitm` 在跑(launchd 里有 pid)+ 登录环境的 `NODE_EXTRA_CA_CERTS` 指向 asight 的 CA,缺一就是「没采集」并点名;读不到的一项是「不知道」加原因,退出 3,不当通过。asight 没往 Clash 里放过路由时,问不到核不算问题。CLI = 旧 steer 在位(暂存文件为证)且 `com.asight.monitor` 在跑;没有 steer 写「没开」加「`on` 不做旧 steer;要采集 CLI 用 `monitor on`」。每一项说是谁写的(账里有:「asight on 写的,备份 …」;没有:「旧命令装的,无备份」),账逐项列出。只读(`launchctl list` / `getenv`、`security find-certificate`、核的 `GET /proxies`)。带 `claude-code` 以外的 harness 名:退出 2。
- **`uninstall` 在没有新采集器的平台上**:先做和 `off` 同一份撤销,全撤净才删 asight 自己的 —— 全部备份(撤时留下的「不逐字节相同」的逐个列出)、账、`~/.asight/ca`、`~/.asight/bin/asight-off`;没撤净就什么都不删,账与备份留给下次,退出 1。采集数据与日志留着;`--purge-data` 删 `~/.asight/` 顶层旧采集写的 `capture*.ndjson`,要确认(R6)。v0 的 `~/.atrace` 不碰。
- 作者的 Mac 跑的是旧采集,会话可能正被它采集。`off`(不带参数,或带 `claude-code`)、`uninstall`、`desktop off`、`monitor off` 都会停掉这台 Mac 上的采集:agent 未经用户同意 MUST NOT 跑它们。必拒 · 审查([0.1](0.1-engineering-rules.md) §5「未经同意…」一行 + §6 第 11 条)。
- v0 的残留(`com.atrace.serve`、`~/.local/share/atrace`、`.atrace-bak`)只报告、不碰;不建议、不调用 `atrace-uninstall`。

| 坏在哪 | 怎么办 |
|---|---|
| 守护进程不在 | `off` / `uninstall` / `status` 照常(`status` 读盘);`on` 拉起它,拉不起报原因、退出 1 |

| 两条命令同时跑 | R12 的锁;`off` 优先 |
| 用户改过入口 | 只撤 asight 的部分,报「已撤销,但不逐字节相同」,备份留着(R2) |
| 哨兵被改坏 | 不动这个文件,`ok:false`、退出 1,给备份路径与手动 `cp` 命令,说明会丢掉什么 |

| `~/.asight` 写不进(磁盘满) | 备份写不进就不改用户文件(R2);日志写不进按 R11 |
| 本平台没有新采集器 | `on` / `off` 驱动旧采集(§4);`daemon` 报「本平台未实现」、退出 1 |

## 6. VPN 感知(CLI 一侧)

机器上装了 VPN 软件,asight 要自动感知,在 CLI 和界面里显示它改了什么地方;力求所有改动可追踪、可撤销。1.6 只定 CLI 一侧的四条要求:

- **探测**:`status`、`doctor`、首次 `on` 探测本机的代理 / VPN 软件:哪个产品、什么模式(规则 / 全局 / TUN / 系统代理)、每个 harness 的流量是否经过它。只读;不读也不印密钥、订阅地址、节点信息。认不出 → 「不知道」加原因,MUST NOT 报「无」。探测结果写 `~/.asight/netenv.json`(0600;只含产品、模式、各 harness 是否经过,不含密钥、订阅地址、节点;不放进 `~/.asight/collector/`,没有新采集器的平台也写)。`status` 与 `doctor` 写它(只在 `~/.asight` 已经存在时:没装过 asight 的机器上它们不建任何东西);`on` 只探测、印在计划与回执里、不写它——回执要列出 `on` 写过的全部文件(V3),再跑一次 `on` 要无副作用(R9),而这个缓存每次都会换时间戳。`ASIGHT_MIHOMO_SOCK` 钉住时只问那个 socket(旧 steer 的约定,测试起真 `bin/asight.mjs` 时靠它不碰这台机器的核)。首版 `src/netenv/` 只认 Clash Verge / mihomo(旧 steer 已在读它),其余报「不知道」加原因;Windows 一侧的产品表见 [4.7](4.7-netenv.md),都只读(D43);探测结果另喂代理模式的上游与拓扑。守卫:test V22(计划)。
- **入账**:新采集器不往任何 VPN / 代理软件里写东西(D43②),没有这类条目。旧采集的 Clash 块经 `on` 写时,和 agent 文件的改动一样记账:安装清单一条、改前备份(R2)、回执一行(R1)、`status` 列出、`off` 撤掉;块用 D28 的哨兵块语义(只剥块、块外一字不动、剥不掉报 `ok:false`)(§4)。守卫:test V23(计划)。
- **核对生效**(只对旧采集的 Clash 块):`status` 与 `off` 对 VPN / 代理软件里的块 MUST 读它实际生效的运行时配置(D29 的做法:经该软件的控制接口读),不只看文件或清单。`off` 即使文件里已没有块也 MUST 热重载并核对,不走「早已还原」的跳过(运行时可能仍留着块:D29 记过重新生成时写进运行时配置的那份);核对不了报「不知道」加原因(`off` 退出 1,`status` 退出 3)。块被 VPN 软件改写或抹掉:`status` 报「块被 <产品> 改动」。守卫:test V23(计划)。
- **看板**:同样的内容显示在「本机网络环境」卡片上,经 [4.4](4.4-server.md) 只读数据面(`/api/capture-health` 的 `netenv` 字段)读 `~/.asight/netenv.json` 与清单(卡片属 D31⑧ 的设置面板,UI 单元待写);点名项(§1.7)也在这个面板里,读同一份 `opt_in`(§9.4)。

**前向引用**:各产品的探测写在 [4.7](4.7-netenv.md)(Windows 一半已写,只读);D31⑤「不依赖、不修改用户的 VPN 软件」不改(D43 撤回了写入的修订)。代理模式里 VPN 只决定 asight 的上游([4.8](4.8-win-collector.md) §2.2)。

## 8. CLI 不该有的

本表各行的强度与守卫以所引规则为准;没有引用规则的行是 SHOULD。

|---|---|
| `restore`,或任何把「关」和「撤」分开的命令 | 用户分不清「关」和「撤」 |
| 把 agent 的代理字段指向 asight 引擎作为引流 | 做不到 off 保证(§1.2);指向自带内核是代理模式(D43) |
| `ca rotate` | 轮换 = `uninstall` 再 `on` |
| 改系统代理、接管整机流量;自带内核开 TUN 或当系统代理;新采集器往 VPN / 代理软件里写任何东西;旧采集不入账地改 | D31④⑤ · D43;旧采集的块按 §6 入账 |
| 没点名就往登录环境写 CA 变量(`launchctl setenv`、`environment.d`、rc 里 `export`);登录环境或全系统的代理变量(点名也不) | D37④ · D43⑥;旧 `com.asight.env` 是过渡期遗留,`off` 撤它 |
| 没点名就把采集器 CA 装进信任库;没有用户自己给的管理员权限就写机器级位置(`/etc/ssl`、`LocalMachine\Root`、机器 PATH);旧 MITM 的 `add-trusted-cert -r trustRoot` | 采集安全 · D43⑥ |

## 9. 网络拓扑与诊断

**来源**(D39⑩):每个 agent harness 的网络情况各画一个简单的拓扑结构,让用户看清数据的流动;把不同情况说清楚,也顺畅适应改 agent 网络配置(例如挂自己的 proxy)的需要,一目了然、容易配置,这些后面会进到 GUI 里。agent 不能正常工作或网络不同时,`asight doctor` 要给出明确的、可执行的指令。另外几条 —— 出口不变;用户直接改了 agent 的代理,asight 能发现,`status` 画出新的流向并给出接上的命令;asight 不悄悄覆盖用户的设置。产品设计取决于用户的具体需求,给出的命令只是例子,不固化成 subcommand。命令面、画法、`--json` 形状、发现目录与码见本单元。

本节跨平台。各引流方式的具体形状见 §9.8。

**实现状态(2026-10-07,计划任务 13,如实写明)**:驱动模式(Linux eBPF)从头到尾做完并有测试:`status` 的「各 harness 的路」与 `status <harness>` 的详细拓扑、`--json` 的 `topology`(经 `netenv.json` 与 `/api/capture-health` 的 `netenv.topology` 给看板同一份)、`on` 接上用户的代理并记 `adopted`、守护进程 5 s 核对里的漂移、`doctor [harness…]` 的发现与 `findings`;V41–V54 各有会变红的断言或指向已有测试(见「本模块新测」)。**没有做的**:Windows 的事实读取已落地(`arch/win32/netfacts.mjs` = `gatherWin32Facts`,2026-10-10,4.8 计划任务 10(a):`archFacts` 契约在 win32 的实现,W29 的行 a–s 有逐字测试;doctor 的逐行发现(W36)与 `on` 的 §11 计划行是任务 10 的 (b)(c),未落)、V48(b)(代理字段的清单项由 Windows 分支写,`off` 只撤 asight 的部分是 R2 已有的机制与测试)、macOS 旧采集的事实读取(行 20 的拓扑与判词用注入的事实测;macOS 上 `status` 暂不印这一段)。

### 9.1 在哪看(不加新命令)

| 命令 | 给什么 |
|---|---|
| `asight status` | 表格之后一段「各 harness 的路」:每个 harness 一行紧凑链;分 HTTP 与 WebSocket 走不同路的,每支一行 |
| `asight status <harness…>` | 另给每个点名的 harness 画详细拓扑:每跳一行;另加「关掉 asight 时的路」「要换代理」两行 |
| `asight doctor [harness…]` | 发现(§9.6):每条写什么、为什么、要跑的命令、怎么验证 |
| `--json` | 同一份 `topology` 对象(§9.4);看板经 `/api/capture-health` 的 `netenv.topology` 读同一份 |

- 不设 `asight net`、`asight proxy`(§8)。理由:拓扑回答的正是 `status` 那一问的「为什么」;多一个动词,用户多记一个,两处输出还会分叉。
- `doctor` 新收 harness 名(规则同 §3):用户的症状是按 agent 说的,如「codex 连不上」。

### 9.2 画法

- **一条链** = 从 agent 进程到出口的每一跳,用 `→` 连。节点写具体的东西:进程(名、pid、版本)、地址与端口、产品与版本、模式(规则 / 全局 / 直连 / TUN / 系统代理)。边写怎么过去(方括号:`[eBPF]` `[系统代理]` `[HTTPS_PROXY]` `[TUN]`);代理模式下 agent 到自带内核那条边写入口与谁写的,如 `[.env HTTPS_PROXY · asight 写的]`、`[kimi shim · 你点名的]`。asight 自己的节点标「asight」。引流模式写在 `status` 那一段的段首,或 `status <h>` 的第一行:「驱动模式(eBPF)」「代理模式」或「旧采集」(D43)。
- **画新连接的路**:按 agent 现在的设置(它会读的环境变量、配置文件里的代理键、它认的系统代理)和本机网络环境算。代理设置只在 agent 启动时读;在跑的进程启动时的设置与现在不同时,另列一行「pid N 仍按启动时的设置:<链>;重启后按上面的路」。
- **关掉 asight 时的路**:同样的设置,去掉 asight 的跳。`status <harness>` 印它。asight 在路径上时,asight 之后的第一跳 MUST 等于这条链里 agent 之后的第一跳(出口不变,§9.5);不等时报 `egress-differs`。
- **读不到**:那一跳写「不知道 · <原因>」(原因是闭集,§9.4),不省略这一跳,不写「无」(R11)。按别的平台实测推断的,标「推断」。
- **判词**:每个 harness 末尾写两件事:asight 在不在路径上(是 / 否 / 不知道);被采集没有(是 / 否 + 原因码,§9.6)。只有「被采集」本身不知道时,`status` 才退出 3;单跳不知道不改退出码。
- **永远不印**:代理 URL 里的用户名与密码(印成 `***@`)、VPN 的 secret、订阅地址、节点名。出口只写「由 <产品> 选」或「直连」。

| 字段 | 闭集 / 规则 |
|---|---|
| `routing` | `driver`(驱动模式)· `proxy`(代理模式)· `legacy`(旧采集)· `none`(全部关着)· `unknown`。D43:一个平台只有一种模式,不再有 `mixed` |
| `nodes[].kind` | `agent` · `proxy`(用户的代理或 VPN 的本地入口)· `asight-engine` · `asight-forwarder`(代理模式的自带内核)· `legacy-mitm` · `upstream`(API 或中转 host)· `egress` · `unknown` |
| `edges[].via` | `direct` · `proxy-http` · `proxy-socks` · `proxy-https` · `system-proxy` · `tun` · `ebpf` · `forward`(自带内核到引擎)· `egress` · `unknown`。边上 `asight: true` = 这条边来自 asight 写的入口,另带 `entry: {where, opt_in}`;文本印「asight 写的」或「你点名的」 |
| `unknown` | 节点或边上 `{reason}`;`reason` ∈ `denied` · `timeout` · `absent` · `unparseable` · `owner-unreadable` · `pac` · `controller-unreadable` · `kernel-filter-invisible` · `env-unreadable`(Windows 读不到别的进程的启动环境,4.8 §10.1);另有 `detail` 放 errno 或探针名 |
| `inferred` | 节点或边上为 `true` 时,文本标「推断」(按别的平台实测) |
| `branches[].name` | `all` · `http` · `ws`(按 harness 文件声明的分支);一个 harness 有多个形态时(Windows),每个形态各一支,另带 `form`(形态 id;4.8 §10.1) |

| 其余 | 每个节点有 `id` `kind` `name`;每条边的 `from` `to` 都是已有节点;`path` 与 `off_path` 第一个都是 `agent`;一条 `path` 里节点不重复(D43 起没有「Clash → asight → Clash」的路) |

- 文本只从这个对象渲染,不另算(V43)。键名与闭集放 `src/cli/schema.mjs`(R5)。`status --json` 带 `topology` 与 `opt_in`(下);`doctor --json` 带 `findings`(§9.6)。
- **拓扑造不出来时**(这个构建没有接上事实读取者,或建图那一步抛了):`status --json` 没有 `topology`,带 **`topology_error`**(一句原因的字符串);文本在原处写「各 harness 的路: 不知道(<原因>)」,什么也不画。表(`harnesses`)与退出码不变:拓扑是 `status` 的解释,不是它的判词(R11:读不到写不知道,不写「无」;§9.2「单跳不知道不改退出码」同理)。

```json
{ "opt_in": { "kimi-code": [
  { "form": "kimi-code.cli", "kind": "optin-user-path", "scope": "user", "admin": false,
    "state": "needed", "code": "opt-in-needed", "reason": null,
    "implies": "本用户所有程序看到的 PATH 顺序变了;只有同名命令 kimi 解析到 asight 的 shim",
    "enable": "asight on kimi-code --opt-in kimi-code.cli", "undo": "asight off kimi-code", "elevated": null }
] } }
```

| 字段 | 闭集 / 规则 |
|---|---|
| `form` | 形态 id(§3 的写法) |
| `kind` | 清单里的种类名;各平台单元定(Windows:[4.8](4.8-win-collector.md) §2.4 的表) |
| `scope` · `admin` | `user` · `machine`;`admin` 为 `true` 当且仅当要管理员权限(= `scope:'machine'`) |
| `state` | `needed`(没点名)· `done`(做了,入口有效)· `broken`(做了,入口失效)· `pending-admin`(等用户给管理员权限)· `needs-admin`(`off` 之后机器级的还没撤)· `unknown`(核对不了) |

| `reason` | `unknown` 时的原因(同 `unknown.reason` 的闭集);其余 `null`。读不到不写「无」(R11) |
| `implies` | 「影响」那一行,与 `on` 的计划里那一行逐字相同(`--yes` 不换它) |
| `enable` · `undo` | 填好值的整行命令:`enable` 含 `--opt-in <形态>`;`undo` 是 `asight off <harness>`,也是唯一的撤销动作(§1.7「界面上没有按条撤销」)。`elevated`:没有提示可弹时的那一整行提权命令(退路,§1.7;有提示可弹的机器上是 `null`——正常路径是确认后操作系统自己的提权提示) |

### 9.5 用户自己的代理

用户的要求:自己的代理照常工作、出口不变;换代理的过程要顺;asight 不悄悄覆盖用户的设置;不为此固化一个子命令。下表是做法:

| 规则 | 内容 |
|---|---|
| 唯一来源 | 「用户的代理」= agent 自己会用的那个:它读的环境变量、配置文件里的代理键、它认的系统代理。读哪些由 harness 文件声明(§9.7)。asight 没有另一处记它,用户不用告诉 asight 两遍。 |
| 接上 | `on <harness>` 读该 harness 现在的网络设置,把 asight 接在 agent 与它原本的下一跳之间;asight 的上游 = 那个下一跳(用户的代理、VPN 或 API host)。驱动模式(eBPF):不写任何网络设置,引擎按原目的地转,CONNECT / SOCKS 原样转给用户的代理(4.6 §引擎 第 3 步)。代理模式:把 agent 的代理入口指向自带内核;上游 = agent 自己的代理(原值),没有就是它跟随且开着的系统代理,再没有就直连(D43;4.8 §2.2)。计划与回执各印一行接上后的链,凭据打码。 |
| 记下接上的是什么 | `on` 在 `~/.asight/netenv.json` 写 `adopted.<harness> = {at, routing, chain, source:[{kind:'env'\|'file'\|'system-proxy', where}], sha256}`。`chain` 是打码后的紧凑链;`sha256` 是原始设置值的哈希,不存原值(原值里可能有密码)。 |
| 发现漂移 | `status`、`doctor` 和守护进程用同一读法重读设置,与 `adopted` 比。守护进程在 4.6 §开关语义的 5 s 核对里一起做,先比这些文件的 inode / 大小 / mtime。设置不同 = `proxy-changed`;本机网络环境变了(VPN 从系统代理改 TUN、退出、升级、新装)= `netenv-changed`。代理模式下系统代理变了(开、关、换端口):守护进程按新的系统代理重载自带内核的配置,写一条 `netenv-change`,不算失败,不碰 agent 的设置。各写一条 `netenv-change` 事件;让期望为开的 harness 采不到时,另写一条 `failure`(§9.7)。没有守护进程的平台上,由 `status` / `doctor` 与上次的 `netenv.json` 比。 |
| 漂移之后 | `status` 画出新的路,说清 asight 还在不在路径上,印那一条接上的命令(已有命令)。eBPF:新进程照常被采,不用做什么,只列「在跑的 pid N 仍按旧设置,重启后按新的」。代理模式:agent 的代理字段被改(不再指向内核)= 它已绕过 asight,印 `asight on <harness>`(把新代理记成上游,再指回内核);系统代理变了不用做什么(上一行)。 |
| 不悄悄覆盖 | 只有操作者跑的 `on` 会写 agent 的网络设置。`status`、`doctor`、守护进程只读、只报,MUST NOT 改回。`on` 要改写用户在上次 `on` 之后改过的网络设置时,像 §1.6「多出来的文件」一样列进计划、再确认(R6);不在终端又没有 `--yes`:只打印计划,退出 2,什么都不写。 |
| `off` 留下用户的设置 | `off` 只撤 asight 写的值(R2「只撤 asight 的部分」):字段仍是 asight 的值,就回到接上时的原值;用户之后改过,就不动,回执写「你改过,没动」。驱动模式下 `off` 不碰任何网络设置。 |
| 不加命令 | 换代理 = 照常改 agent 的设置(或 VPN),需要时再 `on <harness>`。没有 `asight proxy`。以后真有「不改 agent 设置、只换 asight 的上游」的需要,再进 Extensions,并写明是什么需要。 |

**实现要点**:

- `adopted.<harness>` 实际存 `{at, routing, chain, source:[{kind, where, key?}], sha256, file_sha256, file_paths, proxy, vpn, written_sha256?}`:`proxy` 是打码后的设置(`http://***@proxy.corp:8080`;「仍按启动时的设置」要它),`file_sha256` 是只算文件那一部分的哈希(守护进程没有 agent 的环境变量,只能比文件),`file_paths` 是 `on` 读到那些文件的路径(按描述符 `proxy.files` 的顺序;`CLAUDE_CONFIG_DIR`、`CODEX_HOME` 这类由 `on` 所在 shell 的环境定下的路径,守护进程没有那个环境,所以按记下的路径 stat 与读,`on`、`status`、`doctor`、守护进程读的是同一批文件),`vpn` 是 `{product, version, port, tun}`(`netenv-changed` 对它比;模式与 pid 不入,Clash 的规则 / 全局不改 asight 的路),`written_sha256` 只在路由拥有代理字段时有(`on` 写进字段的值的哈希,用来把用户的改动与 asight 自己写的分开)。设置没变的第二次 `on` 不重写(R9,回执的 `created` 里没有 `netenv.json`)。`netenv.json` 的写入合并:探测的键整体替换,`adopted` 与未重画的 harness 的 `topology` 保留。
- 驱动模式的计划与回执各印一行「接上后 <h> 的路: <链>(它的代理设置 <打码>,读自 <文件与键>)」;链是把期望态、link、入口当作已就位(`projectedOn`)算出的新连接的路。`--dry-run` 同样印,不写。
- **漂移只比文件**(`status` / `doctor` 与守护进程同一读法):用户改的是 agent 的配置文件;跑 `status` / `doctor` 的那个 shell 里导出的 `HTTPS_PROXY`、或 `on` 当时的 shell 里有而现在这个没有,都不是用户改了什么,不报 `proxy-changed`(新连接的路仍按这个 shell 读到的画,那是「新进程从这个 shell 启动会走的路」)。**期望态为 off 的 harness 不报漂移**(守护进程不核对,`diagnose` 不给 `proxy-changed` / `netenv-changed`):`off` 之后 asight 不在它的路径上,它的设置怎么改都不是 asight 的事;`off` 不清 `adopted.<h>`(`src/off/` 只 import `node:*`,不碰 `netenv.json`),下一次 `on` 重写它。
- 路由契约(代理模式,由其平台经 `deps.routing` 注入):`{ownsProxyField(h), fieldOf(h) → {path, key}, adopt(h, setting)}`。`on` 在确认之后、`turnOn` 成功之后,对拥有字段的 harness 调 `adopt(h, setting)`(`setting` 带不可枚举的原值 `raw`,只在内存里交给内核当上游;打印、存盘、JSON 里都是打码值),再读字段记 `written_sha256`;`adopt` 抛错 = 这次 `on` 没做完(退出 1,不记 `adopted`)。用户在上次 `on` 之后改了字段(现值的哈希既不是 `written_sha256` 也不是 `file_sha256`):计划里列「你改过的代理设置」,要确认(R6)。字段的清单项、备份与 `off` 的撤销由平台写(R2);本分支只测到这一道接口。
- 守护进程的 5 s 核对只比「每个已接上的 harness 的代理设置文件」(先 stat 的 inode / 大小 / mtime;只读;同一漂移只记一次,重启守护进程后会再记一次),漂移的语义取自**记录本身**(`routing` 为 `proxy`、或带 `written_sha256` 的记录 = 路由拥有代理字段:与 asight 写进去的值比,别的值绕过 asight;其余按 `on` 找到的值比,harness 照旧被采)而不是平台模块的某个属性——守护进程没有自己的 routing,平台模块也不必声明一个(`driftRoutingOf`),不探测 VPN(每 5 s 问一次控制口不算核对)。`netenv-changed`(VPN 与 `adopted.vpn` 不同)只由 `status` / `doctor` 现读现比;一个读不出控制口的 VPN 产品不算变了。代理模式下系统代理的变化由那个平台的监视器调 `recordDrift`(`netenv-changed`,`captured: true`,一条事件、零条 `failure`)。

### 9.6 `doctor` 的发现

每条发现:`{code, class, harness?, what, why, commands:[{run, shell}], verify}`。`class` ∈ 失败(让看板指示变 ⚠,同 D38)· 预期 · 提示。`shell` ∈ `sh` · `powershell` · `gui`(界面操作,写菜单路径)。

- 先给 asight 命令,再给应用或 OS 里的步骤。命令是填好值、可直接复制的整行:pid、端口、路径都填上。某个值读不到时,写「不知道 · 原因」,并给出读它的命令;不留 `<占位符>`。
- `doctor` 只读(V50),一条也不替用户执行(R8)。
- **发现算不出来时**(拓扑没造出来,或这个平台没读事实,或 `diagnose` 抛了):`doctor --json` 的 `findings` 是 `null`,另带 **`findings_error`**(一句原因;拓扑没造出来时就是 `topology_error` 的那句);文本写「发现(网络与采集): 不知道(<原因>)」,不写「没有」。`null` 与 `[]` 不混:`[]` 是读了、没有发现。退出码不变(§2 `doctor` 一行)。

- agent 连不上、又找不到具体原因时,报 `cause-unknown`,第一条命令是 `asight off <harness>`:off 保证(§1.2)之后 asight 不在它的路径上,再试仍连不上,就与 asight 无关。

**实现要点(任务 13)**:

- 驱动模式的 `proxy-changed`(预期类)**没有要跑的命令**(V47 (a)):`commands` 里只有一步「无需操作:…」(`gui`,schema 要求预期类也写做什么,什么都不用做就是做什么),怎么看新的路在 `verify`(`asight status <h>`);代理模式的同一条是失败类,第一条命令 `asight on <h>`。V49 的「asight 的命令在前」只对有命令可跑的发现查。
- **要重启的发现**(未信任原因里要重启的几个、`negative-cache`):第一步是 harness 文件 `proxy.restart.hint`(应用里的步骤);`restart.managed: true`(设置活在它的窗口不会结束的托管进程里,目前只有 Codex 的 app-server)时,第二步是填好 pid 的命令 `kill <pid>`(Windows `Stop-Process -Id <pid>`),pid 取自事实里该进程(`restart.processes` 去掉旗标后的名字对得上的进程,不含 TUI);那个进程没在跑,就没有第二步。
- 命令里「设置的文件与那一行」取自**这个设置自己的来源**(`setting.source[0]`):来自启动它的 shell 的变量就给 `unset` / `export <变量>`(不指任何文件);来自第二个文件就指那个文件和实际命中的键;没有来源(还没有这个设置,如 PAC 之后要写一个具体地址)才给 harness 读的第一个文件,再没有就给它读的第一个环境变量(`behaviour.env`)。一个步骤一个动词:删就是「删掉 <文件> 里的 <键>」,改就是「<文件> 里的 <键> 写成 "<值>"」。
- 目录在 `src/netenv/findings.mjs` 的 `FINDINGS`(每个码一项:类、`asightFirst`、`what` / `why` / `commands` / `verify`)与 `diagnose({facts, topology, harnesses, user})`;`doctor` 与 `status --json` 的 `topology.<h>.findings`(码的列表,给看板)用同一个函数。§9.3 的 24 行各自只给出表里写的码(测试逐行对)。每个未信任原因(4.6 `TRUST_REASONS`)是一条发现:要重启的几个为预期类,其余为失败类,命令是 harness 给的重启办法或守护进程给的提示。
- `cause-unknown` 只回答被点名的 harness(症状是用户按 agent 说的,§9.1),期望态为开、已安装、且这个 harness 没有任何失败类或预期类发现(它们已经说了为什么)时才报;不带名字的 `doctor` 不报它。**它是提示,不是失败,措辞是条件句(「如果 <h> 仍连不上:…」)**:asight 没有一项事实说得出「这个 agent 连不上」(那要读失败记录,而各事件不都带 harness),点名只表明用户的症状;所以对一个被采集、一切正常的 harness 不断言它连不上,也不让看板指示变 ⚠。表里原文写的是「失败」,实现改为提示;要把它做成「有症状才报」,得先有一项读得到的症状(如该 harness 近 24 小时的失败记录),那是另一件事。
- 发现是报告,**不改 `doctor` 的退出码**:退出码仍是 R4 的三个结局(采集文件可被他人读取 = 1 · 无法判定 = 3 · 其余 0),采集器一节(= `status` 的输出,现在加上发现)只是报告(B-7)。计划任务 13 的原文写「有失败类发现就退出 1」,与 §2 `doctor` 一行的「采集器一节只是报告」相冲,实现照 §2。
- `opt-in` 的 `pending-admin` / `needs-admin` 两态,拓扑的判词原因是 `not-routed`(状态原因的闭集里没有 `needs-admin`),发现是 `needs-admin`,命令是该项 `elevated` 的整行。

**事实的形状(`NetFacts`,任务 13;一切打印与 `--json` 的拓扑都由它算出)**——`src/netenv/facts.mjs` 文件头是权威,这里记接口:

- `gatherNetFacts({platform, home, env, harnesses, status, netenv, archFacts, adopted, now, fs, deps})` 把 `status` 已读到的(期望态、守护进程、link、入口、进程)、各 harness 文件的 `proxy` 导出(行为)、现读的代理设置(`readProxySetting`:先文件后环境变量,与 agent 同序;读不出的文件是 `{unknown}`,不是「没有」)、VPN 探测的结果与平台的 `archFacts(ctx)` 拼起来。平台部分返回 `{routing, listeners?, procs?, forwarder?, forms?, systemProxy?, otherRedirector?, fakeIp?, legacy?, tun?, vpn?, unknowns?}`;`vpn?` 是平台自己的 VPN 探测(Windows 4.7 的 `detect()` 经驻留助手;它认识这台机器的产品),两处都有时**以它为准**;抛错(不含测试守卫的拒绝 `ESANDBOX`)让 `routing` 变 `unknown` 并写明原因;没有 `archFacts` 的平台 `routing: 'unknown'`。读不到的事实进 `unknowns: [{fact, reason, detail}]`(闭集 `UNKNOWN_REASONS`),不留空。
- 代理模式的平台(Windows,4.8 §10.1)要给:`routing: 'proxy'`;`forwarder: {pid, up, forms: {<形态>: {h, port, state, upstream, source, clients, upstream_error?}}}`;每个 harness 的 `forms: [{id, setting, systemProxy, follows?, procs, entry: {where, asight, opt_in, intact} | null, optIn: {state, code, enable, form?, elevated?} | null, routeLoop?, route?, entryPlace?}]`;`procs[].elevated`。`routeLoop: true` = 平台拒绝接这个形态(上游会是 asight 自己);`upstream_error` = 引擎拨不通上游(平台的最近 60 s)。`route: {reason, code?, why?, detail?, protocol?}` = 这个形态所在组的采集计划(`planRoutes`)留给 doctor 的判词字段(`code` 缺省等于 `reason`;`upstream-protocol` 在 doctor 里的名字是 `proxy-unsupported`);`entryPlace` = 该组代理入口所在的位置(按 harness 文件的 `proxyEntry` 算:`{kind:'file', file, format:'json'|'dotenv', key}` · `{kind:'shim', command}` · `{kind:'policy', path, name}` · `{kind:'launcher', shortcut}` · `{kind:<组名>}`),doctor 的「把代理设成…」一步按它给文件与键。`reinstall: {npm, release} | null` = 内核的两条重装命令(`forwarder.mjs` 自己的 `reinstallCommands`,在平台一侧按这个构建的钉死清单算——src/netenv 不读 arch 模块,W39 规则 6;钉死清单里没有本机架构的平台包时 null),doctor 的 `forwarder-binary-missing` / `forwarder-digest-mismatch` 行印它(4.8 §10.4),不替你跑。
- Linux(`src/collector/arch/linux/netfacts.mjs`,`routing: 'driver'`)读:各 harness 的进程与 watch 表的判词(`decrypt` / `no-decrypt` / `absent`)、进程启动时的代理(只读**该 harness 自己的** `proxy.env` 里的键、按它的顺序,别的键对它不是设置:claude-code 不读 `ALL_PROXY`,z-code 只认 `ZCODE_HTTP_PROXY`;与现在的设置比;设置来自文件的、文件在进程启动之后才变的,用 `adopted` 里记的)、`ss -ltnpH` 的监听与属主(别人的进程列不出属主 = `owner-unreadable`)、TUN(`ip -j route get 1.1.1.1` 取到去公网的设备,再 `ip -j -d link show dev <设备>` 看是不是 tun;不发包、不解析域名、不上网)。**偏离**:计划写的是 `ip -j rule` 与 `route get <API IP>`;API 的 IP 要解析域名,CLI 不上网(§8),所以用一个代表性的公网地址;Linux 的系统代理(gsettings / kioslaverc)不读(`proxy.measured.linux`:claude-code 是 `lab`——V54 让真的 `claude -p` 经 settings.json `env.HTTPS_PROXY` 指向的 CONNECT 代理出去、测过这条路;其余 harness 是 `inferred`,没有已知的 harness 在 Linux 上跟随它;所以 Linux 上 `doctor claude-code` 不再带「按别的平台实测推断」那条提示,别的 harness 仍带)。**TUN 是事实,不依赖认出 VPN 产品**:去公网的默认路由走 TUN 设备、而探测没认出任何产品(sing-box、v2rayA …)时,`NetFacts.tun` 仍是 `true`,agent 没有自己的代理的那条直连路在 API host 之后画 `[TUN] 出口(不知道 · absent)`,并带一条说明(「没认出是哪个 VPN 产品,出口由谁选不知道」);认出了产品就照旧写「(<产品> 选)」。**NO_PROXY**:读在跑进程自己的 `NO_PROXY` / `no_proxy`(4.6 表里那几个键,只留「它盖住了该 harness 的哪几个 API host」),没有进程就读当前 shell 的;盖住了 API host 而 agent 有自己的代理时,拓扑加一条说明(「`NO_PROXY` 里写了 <host>:<h> 对它可能不经代理直连(各 harness 认不认 `NO_PROXY` 还没逐个测),这里按它的代理设置画」)——不改画出来的路,因为认不认没测过(**OPEN**:实测哪个 harness 认之后,再改成画直连并标「推断」/「实测」)。**`https://` 代理**:agent 自己的设置里的 `https://` 代理,引擎终结外层 TLS 后把里面的 CONNECT 原样转(4.6 §引擎 第 3 步),所以这条边写 `[CONNECT 原样转 · https 代理]`;4.6 表里「透传 · https 代理」那一种是代理 host 不取自该进程自己的设置(守护进程没告诉引擎),Linux 的事实里只有来自环境变量与 harness 文件的代理,画不出它;系统代理里的 `https://`(代理模式)归 4.8。
- `doctor` / `status` 跑的 OS 工具只有只读的查询:Linux `ss` `ip` `gsettings` `ps`,macOS `scutil` `lsof` `ps`,Windows `netstat` `reg query` `schtasks /Query` `where.exe`(不用 `Get-NetTCPConnection`,4.8 E6);`bpftool` 与 `netsh` 只印给用户,不跑。`src/netenv/` 里除 `writeNetenv` 之外没有写调用(4.7 N15 的守卫在 Windows 分支),也没有自己的连接(只有 VPN 核的 unix socket 上的 GET)。
