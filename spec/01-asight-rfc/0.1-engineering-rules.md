# asight · RFC 0.1 — 工程规则

> **这是什么**:写码、写测试、提交、评审时**不允许什么**,以及每条规则靠什么兜底。PR 或设计有争议,先查这里。
> **与 0.0 的分工**:核心不变式在 [0.0](0.0-overview.md)「核心不变式」;本文是这些不变式落到工程层的推论。两处冲突以 0.0 为准,同一 PR 修本文。
> **前置**:[0.0-overview](0.0-overview.md) 决策表。架构、数据结构与管线 → [0.2](0.2-architecture-overview.md)。

等级:**必拒** > **需 RFC** > **SHOULD**。每条必拒都标了守卫:`test` = 违反会让某条测试变红;`审查` = 没有自动守卫,靠 §6 清单在收尾时逐条过。

---

## 0. 总纲

1. **数据结构先于代码**。说不清改动读写的是 [0.2 §2](0.2-architecture-overview.md) 里哪个结构,就还没想清楚。
2. **原始字节是唯一源真相**。DuckDB、看板载荷、缓存都能从原始记录重建,反过来不行。按 session 的分片不是派生(有的 session 只存在于分片里)。封存文件是 NDJSON 行字节的无损容器,随时可逐字还原、逐条 sha256 校验(D35)。(不变式 2)
3. **改包只出于操作者意图**。没有本机操作者的显式操作或显式配置的规则,asight 原样转发,不主动发请求、不改包;每次修改 / 重发都留审计记录,原始与改后都存。(不变式 1 · D30)
4. **provider 知识只在 dissector / adapter 里**。共享层和前端不写 provider 分支;加线格式 = 加一个 dissector,加 harness = 采集侧约定文件(进程特征、信任注入;要插件或 shim 的 harness 另带它的插件 / shim 源文件,也在 `src/collector/harness/` 下)+ 读取侧数据表里的一行(session 键等,在 `src/dissect/`)+ 一行 chip(D37)。(不变式 3 · D25)
5. **不知道就显示不知道**。不拿全零 usage、默认归给 CC、空态冒充「还没采集」这类合理值顶替未知。(不变式 4)
6. **碰用户机器的动作必须用户级、对称可逆**,撤销时只撤自己写的部分。(采集安全 · D22 · D39)
7. **零依赖基线**:运行时只依赖 `@duckdb/node-api`;后端用 `node:http`,前端是单文件 HTML,不打包。(D18)
8. **spec 先于实现**:同一 PR 里先改 spec 再改代码。

## 2. 代码与依赖

- Node ≥ 20,ESM,纯 JS(无 TypeScript、无转译),内置模块写 `node:` 前缀。
- 仓库没有 formatter / linter,各文件分号与引号风格不一:**跟随所在文件**,不做全仓格式化。SHOULD。
- 注释写「为什么」和踩过的坑(参考 `src/paths.mjs` 顶部)。改动推翻了注释里的理由,同步改注释。SHOULD。
- **一个外部事实只写一处(禁止硬编码)**。外部事实 = 绝对路径、端口、版本号、发版日期的分界、实测得来的外部形状(管道名、别的程序会读的文件名)。实测事实住在拥有它的那个模块里,并写明出处(实验室 run、官方文档);别的模块 import 它,不再抄一份。`src/off/` 只许 import `node:*` 与自己,所以两边都要的事实放在 `src/off/`,采集器去 import(例:`src/off/pem.mjs` 的 `SYSTEM_BUNDLES` 与解析 `osBundle`)。`arch/<os>/` 下按平台各写一份的孪生逻辑,spec 本来就允许,不算重复([4.8](4.8-win-collector.md):67、[4.9](4.9-macos-collector.md) §1)。harness 的匹配规则按进程名认、不写安装路径(D51),要覆盖该 harness 的所有版本、所有 CPU 架构与所有装法,实测到的那条路径只当测试样本。**必拒** · test `test/ci/hardcode.test.mjs`(守卫 1:同一个绝对路径 / loopback 端口 / `x.y.z` 版本字面量在 `src/` 里只许出现一次,注释不计;守卫 2:harness 的进程名单只写名字,不含路径分隔符、版本号、架构;解释器名必须带参数模式,参数模式不含版本号与架构;`harness/darwin|win32` 里没有身份数据)。扫描器看不见的种类:SHOULD。
- 新增运行时依赖 = 改 D18 → **需 RFC**。Playwright 不进 `package.json`,真浏览器测试靠 `ASIGHT_PLAYWRIGHT` 显式开启。
- `package.json` 保持 `private`;npm 名 `asight` 已被他人占用(D23),发布前必须先改名。
- **依赖方向**(下层不 import 上层;前端只走 HTTP):
  - `src/capture/` 只依赖 node 内置和 `src/paths.mjs`;
  - `src/dissect/` 是叶子,不 import 任何 src 模块,这样看板和 ETL 才能共用;
  - `src/raw/`(D35 封存器与封存文件读取)只依赖 node 内置、`src/paths.mjs` 和 `src/dissect/`;`etl`、`query`、`server.mjs` 可以 import 它,`capture` 不可以;
  - `adapters / cache / identity / model` → `etl` → `query` → `server.mjs` → `src/cli/`(`bin/asight.mjs` 只调 `src/cli/main.mjs`);`view` 用 `dissect`;`src/cli/legacy-commands.mjs`(`serve` / `etl` / `shard` / `raw` 的函数体)在这些之上,只被 `src/cli/commands.mjs` 的命令表分派;
  - `src/health/`(D38 采集健康:原因码与事件的闭集、读盘与折叠)只依赖 node 内置、`src/paths.mjs`、`src/raw/`(读封存了的 `flows/`)和 `src/off/proc.mjs`(进程的身份与是否活着:`off` 判活读的同一份,不留两份;D39);`src/collector/`、`src/cli/`、`server.mjs` 可以 import 它。它不是 D24 的两条数据路径之一(不读信封、不跑 SQL),只读采集运行元数据;
  - `src/collector/` 可以 import `src/raw/closed.mjs`(记录存储换日时 `markClosed`,4.6 §日志体积预算「已关闭」),`src/raw/` 不 import 它;
  - `src/web/index.html` 不 import 任何 src 模块;
  - `src/off/`(`asight off` 的撤销,D39⑤)只 import `node:*` 与它自己目录里的文件,好生成只用内置模块的独立副本 `~/.asight/bin/asight-off`;`src/collector/`、`src/cli/` 可以 import 它(`src/health/` 只取 `proc.mjs`,见上条),它不 import 任何别的 src 模块。本条守卫:test `test/off/imports.test.mjs`(源码)、`test/off/standalone.test.mjs`(生成的副本,[1.6](1.6-cli.md) V11);
  - `src/collector/` 内部的 `core/` · `arch/<os>/` · `harness/` 三分([4.6](4.6-process-collector.md) §结构):test `test/collector/layering.test.mjs`;`src/netenv/`(只读探测本机网络环境,[4.7](4.7-netenv.md))不 import `arch/` 与 `harness/`,`core/` 里的纯模块(如 `core/codes.mjs`、`core/config-read.mjs`)可读(4.8 W39,同一个 test)。
  其余依赖方向的守卫:审查。
- **现存偏离**(已知债,新代码不要加深):`view/analyze.mjs ↔ view/assemble.mjs` 互相 import;`view ↔ etl` 目录级环(`assemble → etl/orchestrator`,`etl/session-meta → view/assemble`);`capture/desktop-steer.mjs` import `src/off/`(`src/capture/` 里没删净的旧采集模块,与上面第一条不符);`view/assemble.mjs` 的 CC 路径(`assembleSession` 里不走注册表的 `analyzed` 分组、`A.provider = 'cc'`)还留着 anthropic / cc 字面,与 D25「共享层零 provider 分支」不符。

## 3. 测试

- 入口 `npm test`。主线要求 0 失败;等待实现的红灯 / `todo` 测试不进 `main`(§4「`main` 里不留 TODO」)。
- **测试必须能变红**。读到零条记录也打勾的检查等于没检查。新断言 SHOULD 先拿坏输入确认它会红。
- **不碰真实机器**:信任库操作走注入的 runner;涉及 HOME 的用例在 `test/helpers/tmp.mjs` 的 `tmpDir()` 沙箱里跑;Clash 用 `ASIGHT_MIHOMO_SOCK` 指向假 socket。**必拒** · test `test/capture/trust-store.test.mjs`。**自动守卫**:`npm test` 预载 `test/helpers/no-real-os.cjs`,真的 `launchctl` / `systemctl` / `security` / `certutil` / `loginctl`(经 `node:child_process` 或 `src/off/exec.mjs`)在测试进程里一律抛 `ESANDBOX`,桩只能放在临时目录里;被调用方吞掉的拒绝让进程退出 1(`test/helpers/no-real-os.test.mjs`)。
- **夹具是已采原始字节**:`test/fixtures/*.ndjson` 不许手改;要新形状就加夹具,或用 `samples/gen-demo-capture.mjs` 生成。**必拒** · 审查。
- **渲染测试要覆盖产品 D10 信封**,不能只喂 v0 夹具。2026-07-20 审计里「GUI 没接上后端」那一类缺陷,根因就是渲染测试只跑旧夹具。test `test/view/envelope-drift.test.mjs`。
- 实现 spec 覆盖的行为时,把该单元「验收」清单逐条变成待办:落断言 / 指认已有测试 / `N/A + 理由`,三选一。

### 好测试的标准

新测试按这八条写,旧测试遇到再改。

| # | 标准 |
|---|---|
| G1 | **断言用户可观测的结果**:文件字节、退出码、记录内容、对外协议字段。不断言到达结果的路径(调用顺序、内部结构、模块导入),这样重构不会让它变红。 |
| G2 | **输入沿领域的变化轴生成,断言不变量。** 变化轴:版本、架构、安装前缀、大小写、含空格或中文的路径、CRLF、已有用户配置、已有代理。不变量:往返一致、幂等、只碰允许的键、`off` 之后字节相同。 |
| G3 | **替身与真实对端共享一份契约,双向对账**:同一组契约断言既对 fake 跑也对 real 跑。平台模拟只许用真实平台会出现的形状。 |
| G4 | **期望值来自独立来源**:spec、真实采集的字节、手算。不来自被测代码,也不来自另一份实现(旧实现同样不行)。 |
| G5 | **错误路径断言「用户能自救」**:有稳定的原因码或退出码,有填好实际值的修复命令。不要求逐字措辞。 |
| G6 | **外部世界的事实**(路径、版本、端口、产品清单)放在带出处的数据里(见 §2)。测试验证「规则覆盖这一类」,并用生成的变体验证外推;实测样本只当回归种子。 |
| G7 | **在任何干净 checkout 上都能跑。** 依赖私有夹具、浏览器或 VM 的断言,要么有公开的合成替代,要么在门禁里显式报缺口。skip 不算绿。 |
| G8 | **单位价值的成本低**:失败时一屏内能定位;一次无害重构最多让一处变红;不测死代码,不测文档排版。 |

### 约定

等级沿用本文开头:**必拒** 都点名了守卫,其余 SHOULD。

| # | 约定 | 等级 | 守卫 |
|---|---|---|---|
| 1 | 机器输出带原因码而非自然语言;测试对人话只断言其中的实体(路径、名字、数字) | SHOULD | — |
| 2 | 每个 fake 配一套契约测试,同一组断言对 fake 与 real 各跑一遍 | 必拒(只管新增的 fake;现有的 `fakeDaemon` 等是已知债) | 审查 §6 第 13 条 |
| 3 | 平台模拟只用真实平台会产出的形状;读者在一个点上校验形状 | 必拒 | test `test/off/win32-control.test.mjs`(win32 的 `control.json` 必须是命名管道,`off` 拒绝别的形状)· 审查 §6 第 14 条。原计划的扫描「win32 测试不许出现 unix socket」因噪声太大放弃,换成这一处单点形状校验 |
| 4 | 测试走公开入口;只有测试用的导出不增长 | 必拒 | test `test/ci/hardcode.test.mjs` 守卫 4(上限只降不升) |
| 5 | 调用序列 / 命令串的 `deepEqual` 只用在顺序本身是契约的地方,并注明 spec 出处 | SHOULD | — |
| 6 | 外部事实按 §2 处理;测试对各种形态应当生成变体 | 匹配规则必拒;变体生成器 SHOULD | test `test/ci/hardcode.test.mjs` 守卫 1–2 |
| 7 | 不钉计数、不在测试里重述列表 | 新增的计数钉必拒;重述列表 SHOULD | test `test/ci/hardcode.test.mjs` 守卫 3(名单内的文件只许缩减) |
| 8 | 关键不变量用枚举、生成式或蜕变式断言 | SHOULD | — |
| 9 | 不测死代码;从产品入口不可达的模块不许存在 | 必拒 | test `test/ci/reachable.test.mjs` |
| 10 | skip 不算绿:`npm test` 报出的 skip 要在 PR 正文里按原因列出 | SHOULD | — |
| 11 | 重构提交不改期望值;确要改,说明为什么该断言是契约 | 必拒 | 审查 §6 第 12 条 |
| 12 | 按接缝定期做变异抽查 | SHOULD | — |

## 4. 提交与变更规则

**分支生命周期**(按顺序):

1. **在仓库外的 worktree 里开分支**,如 `~/Documents/Source/asight-wt/<task>`。不在主 checkout 上开发:那里可能有别的会话、在跑的采集和本机私有夹具。
2. 只在该分支上开发。每完成一个可独立验证的积木就 commit,失败回退到上一个绿点。
3. **三道门都过**:`npm test`(单元,全新 HOME:`HOME=$(mktemp -d) npm test`)· 回归(bug 修复带一条复现它的测试)· 整机 E2E(采集器在测试机上跑,看板走浏览器)。命令与结果(过 / 败 / 跳过与理由)写进 PR 正文。
4. 自审 diff;非小改动再请一个没有本分支上下文的人按 §6 审。写的人不给自己打分。
5. 开 PR:正文必填,写清改了什么、为什么、怎么验证的。
6. **合入只由人执行**:写代码的一方不自合、不直推 `main`;推功能分支,push ≠ merge。依赖还没合入的 PR 时可以在它的分支上叠加:PR 正文第一行写「先合 #N」,合入顺序写清楚,上一个合入后核对下一个的 base 已转成 `main`。
7. 合入后删掉源分支和 worktree。

- **测试门在本机跑**:`npm test`(单元,用全新的 HOME:`HOME=$(mktemp -d) npm test`)· 回归(bug 修复带一条复现它的测试)· 整机 E2E(采集器在测试机上跑,看板走浏览器)。命令与结果(过 / 败 / 跳过与理由)写进 PR 正文。
- **每个提交 ≤ 400 行**(不计 `package-lock.json` 与新增夹具),且能单独验证;一组相关改动合成一个 PR。单个文件或单份文档拆不到 400 行内时,在 PR 说明里写明理由。
- **每个 PR 带测试**;bug 修复必须带回归测试。只改文档的 PR 除外。
- **`main` 里不留 TODO**:要么做完,要么属于设计未定——写进对应 spec 单元的 OPEN 段落。
- 改 [0.2 §2](0.2-architecture-overview.md) 列出的任何数据结构(信封字段、DuckDB 列、block 词表、看板载荷字段)都是 structural 变更:走硬规则 A 的 grep-spec 自对照,并在 PR 正文里请用户单独确认。
- **新依赖只收宽松许可**:Apache-2.0 / MIT / BSD-2 / BSD-3 / ISC / Zlib。GPL / AGPL / SSPL / BUSL 不收。内核侧 eBPF 程序按内核要求声明 `Dual MIT/GPL`,不算例外。
- 代码里不写死密钥或私有 URL;测试只用假凭据(`sk-ant-oat-FAKE…` 这类)。
- **提交信息**:`<type>(<scope>)[!]: <摘要>`,空一行写正文。**正文必填**:为什么改、证据是什么。type 取 feat / fix / perf / refactor / docs / test / build / chore;`!` 表示破坏性;涉及决策时在摘要里点名 `D<n>`。
- **文档同步**:改了用户可见行为的 PR,在同一个 PR 里更新 `README.md`,并在 `docs/release-notes/<YYYY-MM-DD>.md` 追加一节(一天一个文件,一处改动一个 `##`),写改了什么、为什么、对用户有什么影响。

## 5. 拒绝模式

下面每条都曾经「看起来合理」,并在本仓被否决过。

| ❌ 不要 | 出处 | 等级 · 守卫 |
|---|---|---|
| 让派生层回写或覆盖原始 NDJSON | 不变式 2 | 必拒 · 审查 |
| 在封存器(`src/raw/`)之外改写、截断或删除记录字节(例外:D27③ 的同设备整文件 rename;`asight shard` 的追加与 resplit 替换,去留见 [4.2](4.2-storage-etl.md) OPEN);封存未关闭的分片;未经逐条 + 整文件校验、未 fsync 目录就删原分片 | D35 | 必拒 · test `test/raw/seal.test.mjs`(往返 E1、拒封活跃分片 E6、fsync / rename / unlink 顺序 E5)、`test/raw/seal-crash.test.mjs`(`kill -9`)、`test/raw/seal-late-change.test.mjs`(校验后原文件又变:不删;整分片比对)、`test/raw/legacy-delete.test.mjs`(legacy 删除前逐字节比对、比对后再查、目录 fsync、没有副本不删、删除失败如实记账)、`test/raw/copy-identity.test.mjs`(另一份文件的旧段不当作早先版本)、`test/raw/seal-locks.test.mjs`(段号独占认领、死锁清理)、`test/raw/legacy-guards.test.mjs`(旧根拒绝);其余(封存器之外的改写)靠审查(§6 第 9 条) |
| 搬运原始记录时先 parse 再序列化(分片、迁移、封存、导出) | `src/etl/shard.mjs` 头注释 · D35 | 必拒 · test `test/etl/shard.test.mjs`(分片);封存 `test/raw/seal.test.mjs` E1(逐行 sha256 + 整文件逐字节);导出 `test/raw/cli.test.mjs`(导出 == 原字节)+ `test/raw/export.test.mjs`(每段一个文件,末行无换行不粘连) |

## 6. 收尾审查清单

没有自动守卫的规则都落在这里。收尾时逐条给「过 / 不过 / N/A」(编号稳定,别处按号引用):

1. 有没有不经操作者意图就发请求或改包的路径;修改 / 重发是否都留了审计记录,原始与改后是否都存。
2. 采集端有没有加 session 或 provider 逻辑。
3. 读取失败有没有被折叠成空结果;未知有没有被合理值顶替。跨记录拼接的 call 缺前序记录时是否标 `partial`;采集引起的客户端行为变化是否标 `observer_effect`(D37)。
4. **D53 修订本条:不再有「唯一例外」,要 root / 管理员的项按项标明、由操作系统的提权提示去做,不要 root 的项绝不用 root 做;本条随实现改写。** 碰用户机器的动作是否用户级、对称可逆、只撤自己写的部分。唯一例外是 D36 的能力助手(一次 sudo 安装、可对称移除、不持有任何用户状态);审查时核对它只对调用者 uid 的进程生效(uid 取自 `getuid()`,不收调用者给的 uid)、只装内嵌的 BPF 对象。采集器 CA 另核对:在 `~/.asight/collector/ca/`、私钥 0600、CN 与旧 MITM CA 不同、不读写旧 `~/.asight/ca`、没点名就不进任何信任库(**D55 起**改核:只经 `install` 装进用户级系统信任库这一项、按指纹认、`uninstall` 时撤,见 [0.0](0.0-overview.md) D55)。点名项另核对(D43⑥):默认 `on` 不碰证书库(D55 起证书全部归 `install` / `uninstall`)、登录环境、用户 PATH、机器 PATH、快捷方式与 VS Code 设置;点名项由 asight 执行、入账带 `scope`、先备份、`status` 列出、`off` 与独立撤销撤掉;机器级只经用户自己给管理员权限的那一步(asight 不自己提权、不经手密码),撤不掉的部分印出提权命令;宿主进程树里不是 agent 的连接只转发;机器级点名项的机器 PATH 条目与所有用户的快捷方式的目标只在管理员才写得进的目录里(Windows:`%ProgramData%\asight\machine-bin`),从不落在 `%USERPROFILE%`、`%APPDATA%`、`%LOCALAPPDATA%`、`%TEMP%` 一类用户可写的路径下(否则本用户的任何进程能往管理员与 SYSTEM 的命令查找路径里放同名文件,即 PATH 劫持),目录里的分发器不含凭据,提权那一步是自包含的一整行、不调用户可写目录里的脚本([4.8](4.8-win-collector.md) §2.4、§6.3);新采集器不往任何 VPN 软件里写。 信任注入另核对(D37④):每个 harness 只走 [4.6](4.6-process-collector.md) 表里它自己的入口;替换语义的设置是否只指向该 harness 自己的合并包;有没有往登录环境写 CA 变量(`environment.d`、rc 里的 `export`、`launchctl setenv`)、`NODE_OPTIONS`、`SSL_CERT_DIR`、全局 `SSL_CERT_FILE`;dsh / OpenCode 插件是否只追加 CA(OpenCode 保留调用方的 `tls` / `ca`)、不碰请求 / 响应字节、不联网、不写 agent 配置、只在加上了 CA 时写 pid 标记、读不到 CA 文件时什么都不做;引擎读标记时是否核对启动时间;Kimi 的 shim 目录是否只有 `kimi`;不经信任路径的连接(Z-Code 策略 fetch 以外的请求、OpenCode 插件加载前的请求与 `ws` 路径)是否透传;能写注释的入口是否带哨兵注释;安装前是否列出每个要改的文件;安装清单是否先写后改、每个文件一条日志、不内嵌用户文件内容;用户文件的改前副本只在 `~/.asight/backup/`(目录 0700、文件 0600,`.env` 里有 API key)、验证还原后删(D39③);合并包与 `extra-cc.pem` 是否只取用户 CA 文件里的证书块(私钥等别的块不进 `~/.asight`);引擎是否只终结取自该进程自己代理配置的 `https://` 代理的外层 TLS、别的代理 host 透传(操作者显式选 `all` 的进程除外);卸载是否按 4.6 的五步与「撤一个文件的规则」(dsh 的 patch 文件、shell rc 也走它)、合并包是否改写成去掉 asight CA 的同一份、判活是否只看清单与 `/proc`、有没有整文件回滚、有没有重启进程。
