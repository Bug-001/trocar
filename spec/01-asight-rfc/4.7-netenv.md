# asight · RFC 4.7 — 系统代理感知(D49 · D43 只读)

> **范围**:asight 只读两样东西——agent 自己的代理设置与 OS 系统代理——用来定上游、画拓扑、给 doctor 依据,并在 on 期间跟上它们的变化。Windows / macOS 的读法在本单元 §1;macOS 的落点写在 [4.9](4.9-macos-collector.md) §8,Linux 的事实来源见 [4.6](4.6-process-collector.md)。不识别、不显示 VPN / 代理产品,不感知 TUN(D49)。**D43起只读**:asight 不往任何 VPN / 代理软件里写东西。
> **前置**:D31④⑤ · D38 · D39⑧⑩([1.6](1.6-cli.md) §3.5 · §3.7)· D43 · D49。使用方:[4.8](4.8-win-collector.md)(代理模式的上游 §2.2、拓扑 §10)与 1.6 附录 A 的拓扑和诊断。
> **D49 的意图**:不显示是什么 VPN(对正确性没有贡献);只要 trocar 对系统代理有感知,以防打破用户原本设置的、正确的 proxy 链路。
> **沿革**:D41 曾要求感知并显示 VPN 软件,D43 改为只读;D49 再收窄为只感知代理设置。
> **标注**:本单元的验收编号 N* 只在本单元内有效,编号不复用。

## Goal

- 读 agent 自己的代理与 OS 系统代理,交给代理模式定每个形态的上游([4.11](4.11-collector-model.md) §1 · D43④ · D57④)、拓扑(1.6 附录 A)与 doctor。
- on 期间由守护进程跟上它们的变化。
- 只读:从不写用户的 VPN / 代理软件,不改系统代理(D31⑤ · D43)。
- 不识别产品;不感知 TUN。

## 1. 读什么

| 事实 | 怎么读 |
|---|---|
| agent 自己的代理 | 代理模式(macOS / Windows):按 [4.11](4.11-collector-model.md) §1 的先后读,来源有钩子交给门的值、入口原值 `prior_value`、进程的代理变量;Linux:harness 文件 `proxy` 声明的键、入口原值 `prior_value`、进程 environ |
| 系统代理(Windows) | `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable` · `ProxyServer` · `ProxyOverride` · `AutoConfigURL`(经助手读注册表) |
| 系统代理(macOS) | `scutil --proxy` |
| 系统代理(Linux) | 不读 |
| 代理端口的属主 | 监听表里的进程名与 pid;只用于拓扑与 `proxy-dead` |

读不到的项写「不知道」加原因(1.6 附录 A 的闭集)。事实模块是纯函数加平台给的事实,自己不读文件、不开套接字。

## 2. 用在哪

- **上游规则**:代理模式按 [4.11](4.11-collector-model.md) §1,那里是唯一出处:门只在代理链里插一环,上游是这个 agent 没有 asight 时本来会用的代理。Linux 照旧:只看 agent 自己的设置,都没有就直连。
- **跟上变化**:守护进程每 5 s 核对系统代理,变了写 `netenv-change`,上游随之重算;事件码 `netenv-changed` 的意思收窄为「系统代理变了」(1.6 附录 A)。
- **拓扑**:每条链写上游从哪来(agent 自己的代理 / 系统代理 / 直连),代理那一跳只写地址、端口与属主进程名和 pid,不写产品名(1.6 附录 A)。
- 结果写 `~/.asight/netenv.json`(1.6 §1.7;Windows 上靠用户目录的默认 ACL,4.8 §7),只含 `adopted`(接上记录)与 `topology`。不含代理凭据。

## 3. 不做(D49)

D49 一并撤销:

- 产品表(`products-win32`)与产品 / 版本 / 模式的探测。
- 控制口探测:枚举管道、`GET /version` `GET /configs`、`ASIGHT_MIHOMO_PIPE` `ASIGHT_MIHOMO_SOCK`。
- Clash Verge Rev 适配器与 mihomo 控制口客户端(`createController` · `judgeServer`)。
- TUN 推断:不读默认路由与网卡列表;TUN 等三层 VPN 照常承载 asight 的上游直连。
- 拓扑、`status`、`doctor`、`on` 计划与回执、`netenv.json` 里的产品名与产品结论。
- doctor 的「VPN 变了」发现:`netenv-changed` 只是系统代理 watcher 的事件码。

## 4. 只读(D43)

- 「不依赖」:agent 经引擎自己的回环门(D47),系统代理只决定引擎的上游;系统代理关了 → 直连,由守护进程跟上(4.8 §2.2)。
- asight 不写任何 VPN / 代理软件的文件、不调它们的控制口、不改它们的模式或 TUN、不改系统代理。
- 守卫:N10(所有产品数据目录逐字节不变)、N15(没有写路径:静态加运行时)。

## 5. 码

- `route-loop`:算出的上游是 asight 自己的端口(4.8 §2.2)。
- `netenv-change` / `netenv-changed`:系统代理变了(代理模式 watcher 的事件码)。
- 都写 `where:'netenv'`,名字在 `NET_*` 块(与 1.6 共用,只定义一次)。
- `prior-proxy-unknown`(D57):代理模式下上游第 3 步找不回(父进程已退出、中间隔着 Git Bash),按 [4.11](4.11-collector-model.md) §1 取系统代理,没有才直连;`status` 报「窗口里的代理没接上」。闭集见 [4.11](4.11-collector-model.md) §3 ⑱。
