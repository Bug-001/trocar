> **这是什么**:asight 的代码长什么样——核心数据结构、关键管线、进程与端口、每份状态归谁,以及采集、后端分析、前端呈现三层各自怎么做。这里只给边界和指路,细节在各单元。

## 0. 架构铁律

1. **单机、单用户、所有端口只绑 `127.0.0.1`**。D36 起同一台机器上每个系统用户各一套实例;`127.0.0.1` 不隔离这些用户,见 [4.4](4.4-server.md) OPEN(建议按用户分端口 + 按用户随机 token)。
2. **四层单向**:采集 → 原始 NDJSON → 服务端分析 → 浏览器呈现。下游不回写上游;采集不知道 session;前端不解析 provider 字节。
3. **两条读路径**(D24):看板逐 call 回放 = 服务端直接读源 NDJSON;跨 session 聚合 = DuckDB 上的具名 SQL。DuckDB 是可选的,看板不依赖它。
4. **数据面只读**;写操作只走 `asight serve --control` 才打开的控制面(D26)。

## 1. 总图

```
  被测 agent(进程本身不改;信任按 harness 各走一个入口,D37④)

  Linux · 驱动模式(D43)                 macOS / Windows · 代理模式(D43 · D47)
  agent 不配任何指向 asight 的东西        agent 的代理入口(它自己的配置键 / 启动 shim / 启动器)
      │ eBPF connect4/6:认定的 agent          │ 指向引擎的门:127.0.0.1 上每个入口组一扇
      │ 进程的新连接,目的地改写到引擎         │
      ▼                                       ▼
  采集守护进程(每个系统用户一个,以该用户身份运行;D36)
    引擎(Node,零依赖):接连接 → 问出对端是哪个进程 → 嗅探先到的字节
      · 已确认信任 asight CA 的 agent 进程:终结 TLS,双向被动分帧,逐字旁路记录
      · 其余连接:原样透传,只记元数据
    控制面(本机 socket / 管道) · 开关状态机 · 进程跟踪器与 harness 注册表
      │ 原样转发 ──────────────────────────────────────► 真实 API
      │                                  (出口 = 没有 asight 时它会走的路,D43④:用户自己的代理 / VPN 照旧)
      │ 旁路副本 → 原始信封,逐行追加
      ▼
  ~/.asight/collector/capture-<UTC 日期>.ndjson + flows/(连接行与事件行)   ← 唯一源真相(封存见 D35)
      │                                     │
      │                                     └─► asight etl(可选)→ db/asight.duckdb
      ▼                                                         │
  asight serve :9800                                            │
  读 NDJSON → dissector → 看板装配 ◄──────── 具名 SQL(跨 session)┘
      │ JSON(只读数据面)
      ▼
  浏览器:src/web/index.html
```

> **D52**:asight 不再给 agent 加启动器;命令行的 PATH shim 改为随 `on` 写、随 `off` 撤的代理与证书注入,不再是点名项。

两种引流的共同点:默认只有被识别为 agent 的进程的连接经过 asight,其余连接的字节不经过它(D31④)——Linux 上内核只改写 agent 进程的连接,代理模式下只有被配置去用门的 agent 经过它。差别在认进程的时刻与办法:Linux 由引擎向能力助手查内核表;macOS / Windows 在门 accept 时刻按对端 4 元组向系统定点问出 pid(D47)。asight 不动系统代理、不接管整机流量、不往任何 VPN / 代理软件里写东西。

## 2. 核心数据结构

| 结构 | 一句话 | 在哪 | 谁产 → 谁用 |
|---|---|---|---|
| 原始信封 | 一次上游交互一行 | `~/.asight/collector/capture-<UTC 日期>.ndjson`(活跃分片)· 封存文件(D35)· 更早的 `~/.asight/*.ndjson` 与旧根 `~/.atrace/asight/` 只读 | 采集器 → 封存器 / 分片 / serve / etl |
| block | 上下文里的一块;唯一跨 provider 的统一单元(D25) | 内存 | dissector → 看板装配 / ETL |
| 归一化表 | DuckDB 投影,可从 NDJSON 重建 | `db/asight.duckdb` | etl → query |
| cache 分叉记录 | 这一步从哪块开始和上一步不同、为什么 | 看板载荷 / `cache_events` 表 | analyze / cache-events → 看板 / SQL |
| 看板载荷 | 一个 session 的回放视图 | HTTP JSON | view → index.html |
| 采集健康载荷(D38) | 采集器的失败、当前条件、守护进程状态、已接管的代理与拓扑(adopted · topology) | HTTP JSON(`/api/capture-health`),读自 `flows/` 等运行元数据 | `src/health/` → index.html · `asight status` |

**2.1 原始信封**(`src/capture/envelope.mjs::buildEnvelope`,采集器的 `src/collector/core/record/envelope.mjs` 在其上追加字段)
- `ts` `method` `endpoint`;`req_headers` 逐字,含凭据,所以文件是 0600。
- `req_body`:存原始 UTF-8 **字符串**,不 parse(下游要按字节切块、算哈希);D40 起一切调用同一规则,不分 LLM;不是 UTF-8 的体 `req_body:null` + `req_body_b64`;压缩的体 `req_body_b64` + `req_content_encoding`,解得出时 `req_body` 另存解压后的文本,解不出时 `req_body:null`(LLM 调用的 `req_body` 因此不总是字符串)。操作者设为只记日志的类别 `req_body` 是 `{raw_chars, verbatim:false}`,另带 `body_retention:'log'`。D40 之前采的非 LLM 记录只有 `{raw_chars, verbatim:false}`。
- `resp`:`{status, headers, kind, …}`。`kind:'json'` 存解析后的 `body`(线上原文与重新序列化不等时另存 `raw`);`'sse'` 的 `raw` 是解压后的原文,另带按 Anthropic 形状的重建;`'text'` 存 `raw` 或 `raw_b64`;没有体是 `'empty'`;WebSocket 上的逻辑调用是 `'ws'`(服务端消息逐字,原始帧在 `ws_raw`);上游失败是 `'error'`,并带顶层 `error:true`,失败的一步不会从时间轴上消失。体不完整或没解码时就地标注(`req_truncated` / `req_partial` / `resp.truncated` / `resp.partial` / `*_encoding_error`),由读取侧在显示处标出。
- 观测元数据 `id` `ts_request` `ts_response_start` `ts_response_end` `duration_ms`;派生标签 `is_llm_call`(只认端点 `/v1/messages`、`…/responses`、`…/chat/completions`,另有 Gemini 的 `:generateContent`)、`capture`(Linux = `transparent`,代理模式 = `proxy`;更早的记录里还有 `reverse-proxy` / `mitm`)、`auth_mode`。
- D37 / D40 追加字段(都在 `req_body` 之后):`host` `traffic_class` `body_wire_bytes`;`proc:{pid, exe, agent}` `flow_id` `seq`;WebSocket 的 `transport` `ws_frames` `ws_ext` `ws_raw` `req_extra_messages` `partial` `partial_reasons` `ws_truncated`;`asight_added`(asight 往转给客户端的字节里加了东西时才有)。形状以 [4.6](4.6-process-collector.md) §记录 为准。
- 活跃分片只追加、不按 session 分文件(D20);已关闭的分片可由封存器无损重编码(D35,按 session 分文件,依 D20 的 D35 修订,见 [4.2](4.2-storage-etl.md) §原始层封存);读取端永远兼容 v0 旧字段名 `request_headers / request / response`。

**2.2 block** — `{section, role, kind, content_hash, faithfulness, volatile, cache_control, resource_ref, text_ref}`
- `section` 按装配序 tools → system → messages;Codex 的 `instructions` 归 system,`input[]` 归 messages。
- `faithfulness` ∈ verbatim / opaque(只有签名或密文)/ summarized(compaction 摘要)/ metadata / omitted / truncated。非 verbatim 在 UI 上必须有标。
- `content_hash` = 块逐字字节的 SHA-256(D19),既是去重主键,也是 cache 分叉信号。
- `volatile` = 每次都变的块(CC 的 `x-anthropic-billing-header`),不算 cache break 的责任。

**2.3 归一化表**(DDL:`src/model/ddl.sql`)
`sessions`(会话与血缘)· `calls`(`class` = llm / control,`lane` = main / subagent / monitor / aux / probe;`wire_format` `vendor` `transport` `context_state` `observer_effect` `harness` 记这次调用的线格式、厂商、传输、上下文是否完整、采集引起的客户端行为变化与 harness)· `block_contents`(按 `content_hash` 去重)· `call_blocks`(每个 call 的有序块索引)· `usage`(`input_uncached / cache_read / cache_write / output / reasoning`;`cache_write` 为 NULL 表示该 provider 没有写缓存概念,不能填 0)· `resource_events` · `cache_events`。除 `call_blocks` 外每张表都有 `extra JSON`,收未映射的原生字段,永不丢。

**2.4 cache 分叉记录**
- `cause` ∈ append / volatile-nonce-only / compaction / tool-array-reorder / json-key-reorder / content-changed,认不出是 unknown(另有三种由 adapter 判的成因,见 [3.3](3.3-cache-model.md)),附 `attribution`(谁的锅)与 `fixHint`。
- 地面真相(拿 usage 对账):`read>0` 正常;`read=0, write>0` = TTL 重建;`read=0, write=0` 而前缀逐字相同 = provider 矛盾。

**2.5 看板载荷**(`/api/session`)
- `meta` + 若干 lane;每个 call 带中立 usage `{read, create, fresh, out}`、`comp`(9 段字节构成,每个 call 都带,时间轴才能画全)、`cacheBreak`、`prefixSha256`。
- `flat` 只有块的元数据和 `text_ref`,**不带正文**;展开时再经 `/api/block?ref=` 回源取。窗口外的 call `flat=[]` 并标 `paged_out`。
- 长 session 按 `cursor / limit` 分页;被截掉的部分在 `truncated` 里写明。

## 3. 关键管线

- **P1 采集**:agent 的连接到达引擎(Linux 由 eBPF 改写而来;代理模式从门进来)→ 引擎问出对端进程、按 harness 注册表判是不是 agent、核对它是否确认信任 asight CA → 是:先与上游完成 TLS 再终结客户端 TLS,否则透传 → 两个方向转发的都是收到的原始字节,被动分帧器只读一份副本,调用结束时解压、必要时重建 SSE、`buildEnvelope`,追加一行到 `capture-<日期>.ndjson`。透传的连接、失败与生命周期事件写 `flows/`;上游失败也写一条 `error:true` 信封。记录出错不影响转发。
- **P2 看板回放**(默认路径):`asight serve` 读采集目录(`~/.asight/` + 采集器目录 `~/.asight/collector/` 顶层 + 旧根 `~/.atrace/asight/`,以及 `asight shard` 产出的 `~/.asight/sessions/` 分片;封存文件同样读,D35)→ 按 session 分组 → `assembleSession` 经 dissector 注册表按线格式选 dissector → `analyze()` 切 lane / turn、抽资源 → 逐 call 算 cache 分叉、前缀 SHA-256、中立 usage、`comp` → `sessionView` 开窗 → JSON。认不出线格式的字节计数并标「未识别」,不套任何已知 harness 的身份。
- **P3 ETL**(可选):`asight etl <ndjson|目录>` → 兼容旧形状地读记录 → adapter 的 `detect / parseSession / parseCall / parseBlocks / parseResources`(一种线格式一个 adapter:Anthropic Messages、OpenAI Responses、Chat Completions、Responses over WebSocket,另有一个通用的信封 adapter 收非推理记录)→ 写表(块内容 insert-if-absent)→ 推导 `cache_events`。可 `--rebuild`。
- **P4 开与关**(D39 · [1.6](1.6-cli.md)):**D55 起**证书归安装:`asight install` 一次性在本机生成采集器 CA、装进用户级系统信任库(OS 的框即同意),给这张根实测够不到的运行时写信任项,并写独立撤销程序;`asight on` 先查已安装(没装过就退出 1、提示先 install),再列计划、确认、备份并装自启单元、拉起守护进程;守护进程开引流——Linux 经能力助手挂 eBPF 链接,macOS / Windows 先把门开起来、门立住后才写 agent 的代理入口。`asight off` 撤掉 asight 对 agent 的全部影响,不带参数时另停守护进程与自启;`off` 不依赖守护进程与源码(独立副本 `~/.asight/bin/asight-off`,只管 off)。`asight uninstall` 只在采集全部下线时撤证书、删 CA 私钥与 asight 自己,否则拒绝(码 `collectors-online`),从不代做 off。每一步都有对称的撤销,而且只撤自己写的部分;改用户文件前先存改前副本。

## 4. 进程与接入

| 进程 | 监听 / 通道 | 做什么 | 默认写到 |
|---|---|---|---|
| 采集守护进程(`asight daemon`,自启单元拉起;每个系统用户一个) | 引擎只听回环:Linux = 本实例自己的一个端口(`127.0.0.1` 与 `::1`);macOS / Windows = 每个入口组一扇门(端口记在 `ingress.json`)+ 引擎自己的 ingress 端口。控制面:Linux = `$XDG_RUNTIME_DIR/asight/collector.sock`(0600);macOS = 用户 `$TMPDIR` 下随机名 unix socket;Windows = 随机名命名管道;后两者的名字与 token 在 `control.json` | 认进程、确认信任、解密 / 透传、记录、开关、控制面 | `~/.asight/collector/` |
| 能力助手(仅 Linux) | 守护进程的子进程,经控制通道 | 持有 eBPF 的 bpf_link:装卸程序、改表、按请求查表;不碰任何连接字节;每台机器 `sudo` 装一次(D36) | — |
| 只读助手(仅 Windows) | 守护进程拉起的常驻 PowerShell | 只读:进程与 TCP 连接表的事实 | — |
| `asight serve` | `127.0.0.1:9800` | 看板与 API;校验 Host / Origin;加 `--control` 才开 `/control/*`(另有 CSRF) | — |
| `asight on / off / status / uninstall / doctor / keep` 等 | 一次性命令 | 改状态的(`install` `on` `off` `uninstall` `keep` `daemon`)按用户运行、拒绝 root;`status` / `doctor` 读盘并问控制面 | 见 §5 |

- **Linux · 驱动模式**:agent 的配置里不出现 asight。内核侧 eBPF 把认定为 agent 进程的新连接改写到引擎;fail-open 两层(助手死 → 内核摘钩;引擎死或卡住 → 内核看监听与心跳不再改写)。机制见 [4.6](4.6-process-collector.md)。
- **macOS / Windows · 代理模式**:没有特权钩子、没有内核代理。`on` 把每个 harness 的代理入口(它自己的配置键、PATH 最前的启动 shim、应用的启动器)指向引擎的门;连接到门时引擎按对端套接字问出 pid,按形态判定,是 agent 才解密,其余只转发。引擎就是守护进程,死了由自启机制重拉(macOS = launchd `KeepAlive`;Windows = 监管父进程),期间门是关的,agent 的连接被拒后自己重试。设计见 [4.9](4.9-macos-collector.md)(macOS)、[4.8](4.8-win-collector.md)(Windows,门的核心跨 OS 共用)。

> **D52**:代理入口里没有「应用的启动器」(不再给 agent 加启动器);PATH 最前的启动 shim 随 `on` 写、随 `off` 撤,不再是点名项。

- **信任**:按 harness 各走一个入口,写进该 agent 自己的配置(CC settings `env`、Codex `.env`、Z-Code `config.json`、Hermes `.env`),或用进程内插件(dsh、OpenCode,只追加 CA)、启动 shim(Kimi);替换语义的入口指向每个 harness 自己的合并包。不写登录环境,默认不装任何信任库(D37④ · D43⑥)。见 [4.6](4.6-process-collector.md) §身份与信任。**D55 起**:CA 由 `install` 装、`uninstall` 撤,首选用户级系统信任库(macOS 登录钥匙串的用户信任设置、Windows `CurrentUser\Root`,OS 的框即同意);上述按 harness 的入口只留给这张根实测够不到的运行时,见 [0.0](0.0-overview.md) D55。
- **系统代理感知**:`src/netenv/` 只读 agent 自己的代理与 OS 系统代理(D49),结果给引擎算上游、给 `status` / `doctor` 画拓扑;不识别 VPN / 代理产品,asight 不写进它们(D43)。见 [4.7](4.7-netenv.md)。

## 5. 状态归属(写者与撤销)

| 状态 | 写者 | 位置 | 撤销 / 重建 |
|---|---|---|---|
| 采集流(活跃分片) | 采集守护进程 | `~/.asight/collector/capture-<UTC 日期>.ndjson`(0600) | 只追加,写着时永不改写;封存校验通过后由封存器删除 |
| 封存文件 | 封存器(`src/raw/`,D35) | 按分片的与源同目录;按 session 的在 `sessions/<sid>/`(D20 的 D35 修订) | 只做经校验的无损重编码,随时可逐字还原 |

| DuckDB | `asight etl` | 仓库内 `db/asight.duckdb`(gitignored) | `--rebuild` |

| 代理入口 | `asight on`(按 harness) | agent 自己配置文件里的代理键、命令行 PATH shim(只设代理)、桌面 app 的启动注入(D52);不再有启动器,现存的随替代办法落地撤掉(D52) | `off` 按安装清单逐项撤(`phase: on`),只撤自己写的部分,不整文件回滚 |
| 用户级系统信任根(`system-root`) | `asight install` | macOS 登录钥匙串的用户信任设置、Windows `CurrentUser\Root`;按指纹认 | `uninstall` 按指纹撤(OS 的框);被拒或待定时清单只留这一项,`status` / `doctor` 报孤儿根 |
| 登录环境的增量信任变量(`login-env`) | `asight install` | 按载体各一项:shell rc 的一行(macOS 由 D52② 的同一函数放置)、Windows 用户 `Environment` 注册表值(注册表 API + `WM_SETTINGCHANGE`);只写增量型(`NODE_EXTRA_CA_CERTS` 指向合并包、并入用户原值) | `uninstall` 按载体逐项撤,还原用户原值 |

## 6. 三层怎么做

### 6.1 采集(`src/collector/` · `src/off/` · `src/health/` · `src/netenv/` · `src/cli/`)
- **按 OS 与 harness 分目录**(详见 [4.6](4.6-process-collector.md) §结构):`core/` 平台无关(引擎、分帧、TLS、记录、信任入口、开关状态机、控制面、harness 注册表与进程跟踪器),`arch/<os>/` 平台相关(Linux:eBPF 程序与能力助手;macOS:`lsof` / `ps` / `scutil` 的定点问询;Windows:只读 PowerShell 助手),`harness/` 每个 harness 一个文件(进程特征、信任入口、已知 host、配置读取器)。核心不出现 `process.platform` 分支,也不出现任何 harness 名(`test/collector/layering.test.mjs`)。`daemon.mjs` 是唯一把三者接线的地方。
- **撤销是另一块**:`src/off/` 只依赖 `node:*` 与自己,所以 `asight off` 在 asight 自己坏了时也能用(0.1 §2)。`src/health/` 读盘出采集健康;`src/netenv/` 只读感知代理设置(D49)。
- **共用件**:信封构造、请求体规则、保存级别、`redact`、`sse-reconstruct` 在 `src/capture/`,被采集器引用,同一份实现。
- 透明契约:客户端收到的字节先于记录;记录发生在副本上;记录出错不影响被测程序。
- 自检:`asight doctor`(是否在抓、抓得对不对、凭据文件权限、全机 TLS 是否完好、`asight-off` 副本是否可用);`asight verify` 是 `doctor --only old-ca` 的隐藏别名。
- 详见 [4.1](4.1-capture-sources.md)、[4.5](4.5-distribution.md)、[1.6](1.6-cli.md)。

### 6.2 后端分析(`src/dissect` `src/view` · `src/etl` `src/adapters` `src/cache` `src/identity` `src/query` · `src/server.mjs`)
- **dissector**(`dissect/cc.mjs`、`dissect/openai.mjs`、`dissect/openai-ws.mjs`,经 `dissect/registry.mjs` 按线格式分派):把一种线格式的原始请求拆成 block,看板和 ETL 共用(D25)。读取侧的 harness 表(session 键、请求类别、观测者效应)在 `dissect/harnesses.mjs`。线格式覆盖现状见 `ledger`。
- **看板装配**(`view/`):`analyze.mjs` 切 lane / turn、抽资源、算 cache 分叉与地面真相;`assemble.mjs` 经注册表选 dissector、烤中立 usage 与前缀哈希;`board.mjs` 出项目列表、session 视图、分页和控制面列表。
- **DuckDB 投影**(`etl/`、`adapters/`、`cache/`、`identity/`)。
- **查询与回源**(`query/`):`queries.mjs` 是十来个具名 SQL;`source.mjs` 用 `text_ref` / `raw_ref` 回 NDJSON 或封存文件(D35)取逐字正文;`memo.mjs` 是进程内 LRU。
- **服务**(`server.mjs`):`node:http`,只读 `/api/*` + opt-in `/control/*`,同时托管前端。
- 详见 [3.1](3.1-adapter-contract.md)–[3.5](3.5-query-layer.md)、[4.2](4.2-storage-etl.md)–[4.4](4.4-server.md)。

### 6.3 前端呈现(`src/web/index.html`)
- 一个自包含 HTML,没有构建步骤。轮询 `/api/projects`;选中 session 后按窗口取 `/api/session`;展开块时取 `/api/block`。
- 界面:外壳与顶栏([1.2](1.2-shell-layout.md))· 时间轴、轨道与概览 brush([1.3](1.3-timeline-tracks.md) / [2.1](2.1-track-widget.md))· 中央看板与上下文回放([1.4](1.4-central-board.md) / [2.3](2.3-context-window.md))· call-turn 卡([2.2](2.2-call-turn-card.md))· 资源管理器([2.4](2.4-resource-explorer.md))· 左栏 outline([2.5](2.5-outline-nav.md))· 原始数据面板与控制面侧栏([2.6](2.6-detail-panel.md))· 状态与审美([1.5](1.5-states-aesthetics.md))。
- 只读服务端给的中立字段,不认识 provider;非逐字的块按 `faithfulness` 打标。
- 渲染闸:`test/web/dashboard-render.mjs` 在无浏览器的 DOM shim 里跑整页。
