# asight · RFC 4.2 — 存储 + ETL(源真相 → 分析投影的管道)

> **服务意图(A2)**:同时服务 ①(把 blocks/calls 落表 → 供逐字回放)与 ②(把 usage/cache_events 落表 → 供 cache 叠加)——它是让"逐字源真相"变成"可 SQL 查询的分析投影"的**唯一写路径**(承 D5)。
> **受众**:人(核对派生层不覆盖源、增量不丢数)+ agent(据此实现 ETL orchestrator + DuckDB 落盘)。
> **前置**:源信封(怎么拿到 bytes、NDJSON 长什么样)= [4.1](4.1-capture-sources.md);记录→归一化行的纯函数 = [3.1](3.1-adapter-contract.md);落哪组表 = [3.2](3.2-normalized-model.md);cache 真相规则 = [3.3](3.3-cache-model.md);身份/血缘判定 = [3.4](3.4-session-identity.md);谁读这些表 = [3.5](3.5-query-layer.md)。

## Goal
定义把**原始 NDJSON(源真相)**变成 [3.2](3.2-normalized-model.md) 那组 DuckDB/Parquet 表(`sessions / calls / block_contents / call_blocks / usage / resource_events / cache_events`)的**管道**:注册表分发到 [3.1](3.1-adapter-contract.md) 的 adapter、块内容去重、铸造回源指针、**增量**追加、落盘。**派生表永远可从源重建;源 NDJSON 永不被 ETL 改写**(不变式 2,**必拒**违反;原始层封存器不属 ETL,见 §原始层封存)。

## 前置定义(Definitions)
- **源 NDJSON**:采集源([4.1](4.1-capture-sources.md))写出的 append-only 记录,一行一次上游往返(HTTP 请求,或 WebSocket 上的一次逻辑调用,D37)。产品的**唯一源真相**。**分流归属(承 D20)**:采集源是纯 tee、只按物理源写 append-only 信封流,**不按 session 预分流**;**per-session 归组 / 血缘 = 本层(ETL)用 [3.4](3.4-session-identity.md) 线上信号做**。demo 的 `~/.atrace/projects/<cwd-slug>/<session-id>/{calls,probes,other}.ndjson` + `control/<class>.ndjson` 预分流布局(承 `sessions.mjs`)是 **v0 shortcut**(采集侧分流耦合了身份判定);产品把该归组移入本层,采集只出统一信封流。**D35 修订**:原始层的封存器把已关闭分片按 session 分文件,只读 dissector 声明的请求头 session 键、不解析 body;这只是物理布局,session 身份 / 血缘判定仍在本层。信封字段见 [4.1](4.1-capture-sources.md) / demo `TRACE_SCHEMA.md`。
- **ETL**:读源 → 分发 adapter → 去重 + 铸指针 → upsert 进表。**纯转换 + 幂等**:同一批源两次跑得同一组表。
- **增量 watermark**:每源流已消费到的位置(记录数 / 字节偏移;封存源只按记录数,见 §原始层封存),使新 append 只处理新行,不全量重解。
- **回源指针(`text_ref` / `raw_ref`)**:表里不存全文([3.2](3.2-normalized-model.md) Invariant);存一个能**逐字定位回源 NDJSON**的锚。`raw_ref` → 某记录;`text_ref` → 记录内某块的字段。**AC-1 靠它闭环**。
- **分析投影**:DuckDB/Parquet 表。**可丢弃、可重建**;它 MUST NOT 成为新的真相源。

## Plan(选定方案 + 取舍)
**选定**:**增量 orchestrator** —— 顺序读 append-only 源 → registry 按 `detect` 认领 → 调 adapter 的 `parse*` 出归一化行 → `block_contents` 按 `content_hash` **insert-if-absent** 去重、`call_blocks` 只写整型/hash 映射 → 铸 `text_ref/raw_ref` → 事务 upsert 进 DuckDB → 前进 watermark。ETL **不含任何 provider 解析分支**(那是 [3.1](3.1-adapter-contract.md) 的;把 provider 分支塞进 ETL = 破"适配缝不漏进主干",**需 RFC**)。

**备选(未选)**:① demo 现状——`analyze.mjs` 每次 poll 全量 in-memory 重算(normResp/linearContext/lane/extractResources/cacheBreak)。原型足够、但正是 D5 要治的**反复解析卡顿**:一条几百 call 的 session 每次都从零摊平。② 每次全量重建表(无 watermark)——简单但大 session 下 O(全史) 重扫,增量诉求(D5)落空。
**取舍**:orchestrator + adapter 纯函数 + 增量 watermark = 解析只发生一次、跨 session 查询走 SQL([3.5](3.5-query-layer.md));demo 的 `analyze.mjs` 逻辑**原样搬进 adapter/ETL**,只是从"渲染时算"挪到"入库时算一次"。

demo 的 `analyze.mjs` 已实证每一步的归一化逻辑;产品把它从"渲染时 in-memory"落成"入库时一次 + 增量"。各阶段与目标列的对应:

## 回源指针:`text_ref` / `raw_ref`(AC-1 的技术兑现)
表不存全文;重建靠指针逐字回源。ETL **铸造**这对锚(demo 尚未有——它把全文留在内存;这是产品 ETL 新增的责任):
- `raw_ref` = `<session_id>/<stream_file>#<record.id>`(如 `…/calls.ndjson#req_00042`)——定位一条源记录。`<stream_file>` 是铸造时记录所在文件的 basename(`claude-capture.ndjson`、`capture-<日期>.ndjson`、`calls.ndjson`…;`src/etl/cli.mjs`、`src/view/assemble.mjs` 现即如此)。封存时它作为该记录的**原始流名**记进索引项,resolver 按 (原始流名, id) 匹配;读封存文件的读者给记录标流名(`_stream`)时 MUST 用索引项的原始流名,不用封存文件名。所以物理文件改名、分段、按 session 重组都不改 `raw_ref`,封存前后新铸的 `raw_ref` 也相同(D35)。
- `text_ref` = `raw_ref` + **块在该记录 `req_body` 里的字节区间**(**已落地形态**:`<raw_ref>::<start>-<end>`,如 `…#req_00042::1024-2048`)。〔早稿写作 JSON 路径 `$.request.system[2].text`;实现改用**字节区间**——更贴 [3.2](3.2-normalized-model.md):62「指回该块的完整字节」,且不依赖 JSON 路径解析器、直接 `body.slice(start,end)` 取逐字 bytes。语义等价、字节更精确。〕
- **重建 = 定位源记录(封存文件则经索引解码出原行并校验 sha256,D35)→ 取其 `req_body` → `slice(start,end)`**。这就是 AC-1 的重建算法:由 `call_blocks`⋈`block_contents.text_ref` 拿回每块字节,与源逐字比,**diff=0**(见 `src/query/source.mjs` 惰性 offset-index resolver,承 [4.4](4.4-server.md):88 / D24(i))。
- **按块字段比,不比整包字节**:请求体三个顶层字段(tools/system/messages)的 JSON key/byte 顺序是 SDK 细节、模型不读(承 `analyze.mjs` 注释);真相是 assembly order 下**每块内容的字节**。AC-1 的"逐字"锚在块字段级。

## content_hash 去重(ETL 拥有 insert-if-absent)
- adapter 产出每块的 `content_hash`([3.1](3.1-adapter-contract.md) `parseBlocks`);**去重写入是 ETL 的事**:`block_contents` 按 `content_hash` insert-if-absent,`call_blocks` 只存 `(call_id,seq,content_hash)` 映射(承 [3.2](3.2-normalized-model.md) 取舍)。同内容跨百 call 只存一次 → cache-break 退化成"相邻 call 的 hash 序列 diff"(SQL,[3.5](3.5-query-layer.md))。
- **`content_hash` MUST 是全内容抗碰撞 hash = sha-256 over 块「逐字序列化字节」**(采集所见原始序列化,**非 key 规范化**;承 **D19**、算法钉死在 [3.1](3.1-adapter-contract.md)):它是去重主键,碰撞 = 两个不同块被并成一条 → **派生层丢块**(违反不变式 2,**必拒**)。**键序规范化只供 [3.3](3.3-cache-model.md) 成因分类,MUST NOT 进 hash**(否则 json-key-reorder cache-break 塌进去重、变不可见)。⚠ demo 的 `blkKey`/`hash` 是 32-bit、且只 hash **前 4096 字符**(`blkHashText(b).slice(0,4096)`)——作 cache-break 启发式够,作**去重主键不安全**(两个前 4096 字符相同、尾部不同的长块会被误并)。产品 MUST 换成全内容强 hash。

## 增量(watermark · append-only · 迁移安全)
- 源是 append-only(demo `appendFileSync`)→ 增量 = 记每个源流已消费的**记录数/字节偏移**,只 parse 新行,adapter 幂等 upsert。watermark **MUST 以 `session_id` 为键**,不以路径为键——因为源目录会**改名迁移**(demo `ensureLocation`:slug 从 `_unresolved` 升级为真实 slug 时 `renameSync` 整个 session 文件夹)。以路径为键会在迁移后重复摄入或丢新行。
- 增量结果 MUST 与"全量重建"**逐位一致**(幂等性验收,见下)。watermark 只是加速,不是真相;损坏时 MUST 能丢弃派生表 + watermark、从源全量重建(见 Risk)。
- 多源流:`calls.ndjson`(真推理,主源,喂全部 7 表)是本层焦点;`probes.ndjson`(count_tokens 上下文尺寸测量)喂 `calls.lane='probe'` 的轻量测量序列(承 demo server `series`);`other.ndjson` / `control/<class>.ndjson` 非会话推理,**不进 3.2 会话表**(control 是 session-LESS,归 [4.1](4.1-capture-sources.md) 分类,本层至多留原样待查)。

## 派生不覆盖源(必拒不变式,承不变式 2([0.0](0.0-overview.md) §核心不变式)
- 源 NDJSON = 唯一真相;DuckDB/Parquet = **可重建投影**。ETL **只 append/upsert 派生表,永不写源目录**。(原始层日志 `~/.asight/raw/journal.jsonl` 不是源:它不含记录字节,任何读者都不把它当信封读;ETL 只往里追加「哪个封存文件没读全、为什么」的诊断行,D38。)任何"回写源 / 有损改写源记录"的设计 = **必拒**。
- 表里**不留全文**(存 `text_ref`)——既省空间,又强制"看全文=回源",杜绝派生层与源漂移。

## 原始层封存(D35 · 不属 ETL)

上面的「永不写源目录」约束的是 ETL。源文件上允许的动作只有四种:采集源追加;同设备 rename 整个文件或目录(D27③、demo `ensureLocation`),记录字节不动;`asight shard`(`src/etl/shard.mjs`)往 `sessions/` 追加分片,一次性 resplit 按总字节守恒校验后整文件替换——它是 ETL 模块却写源,与上文冲突,见 OPEN;**原始层的封存器**(`src/raw/`,不在 `src/etl/`,`serve` 也不跑它)把一个已关闭的分片无损重编码成封存文件。封存器不是派生写路径;它对源文件只做这一件事,别的(截断、改写、搬到外部 chunk store)一律不做。动因与实测数见 [4.6](4.6-process-collector.md) §日志体积预算。

- **源真相的单位** = 每条记录那一行 NDJSON 的原始字节,含结尾的 `\n`(前面若有 `\r` 也原样在内);末行没有换行的,索引项标「无换行」。活跃分片仍是未压缩、只追加的 NDJSON(0600、每次写入可见),写的过程中永不封存;「已关闭」的判据见 4.6。
- **封存流程(MUST)**:在目标目录里建临时文件(open 时即 0600,不靠事后 chmod;rename 只在同一文件系统内原子,所以临时文件 MUST 与封存文件同目录)→ 写入并 fsync → 逐条解码**全部**记录,与原行比 sha256 → 按 (分片 id, `line_no`) 从全部封存输出重拼整个分片,比长度与整文件 sha256 → rename 成正式名(实现为 link 到正式名再删临时名:正式名已被另一个封存器占了时 link 失败、换下一个段号,两个封存器永不互相覆盖;审查三 F12)→ fsync 目标目录 → 才删原分片 → fsync 原分片所在目录。一个分片拆进多个封存文件时,全部 rename 并 fsync 各自目录之后才删原分片。目录 fsync 之前就删原分片,断电后可能删除落了盘、rename 没落盘,原始就丢了(违不变式 2)。按这个顺序,任何时刻崩溃或断电都只留下原文件(或两者并存);校验失败保留原文件并报告。「报告」= 封存器的每个非成功结果(拒绝封存未关闭的分片、封存中分片变了、校验不符、中途放弃)在返回或抛出之前写进原始层日志 `~/.asight/raw/journal.jsonl`(只追加、0600、每行 fsync;写不成时返回失败、由调用方打印并以非 0 退出,不抛错盖住原失败),`asight raw journal` 与看板([4.4](4.4-server.md) `/api/capture-health`)都读得出(D38)。不可解析的行、没有信封 id 的行、末尾半行都作为 opaque 记录原样带上。
- **记录编码**:关键帧(行字节本身),或增量 = (指向**同一封存文件**里更早一条记录的回指, ops)。ops 只有两种字节操作,不解析 JSON、与 provider 无关:`COPY(offset,len)` 从前驱的行字节拷贝,`INSERT(字面字节)`;解码得到原行。从一条记录沿回指走到关键帧的步数 MUST ≤ 16(解码一条记录最多重建 17 行;读延迟取决于它)。编码器启发(SHOULD,不属格式):前驱 = 同文件前 32 条里与本条字节公共前缀最长的那条;多段匹配最多 8 段(32 字节窗口的滚动哈希、每 16 字节取样、最短匹配 64 字节);增量 ≥ 本条的 50% 或链将超过 16 时出关键帧。响应体等其他记录同样编码,很少匹配,无妨。
- **分帧**:编码流切成约 4 MiB(编码后字节)的独立帧,各自用 brotli quality 9、lgwin 24(16 MB 窗口)压缩,每帧可单独解码。一条记录 MUST NOT 跨帧,帧只在记录边界切;SHOULD 在当前帧已 ≥ 4 MiB 时切,比 4 MiB 还大的记录单独成帧。v1 用 brotli:CI、`engines`、发布都用 Node 20,而 Node 20 的 `node:zlib` 没有 zstd。
- **文件布局**:头(magic、格式版本)· 帧 · 索引尾 · 定长尾标(索引尾的文件偏移与长度、magic)。读者从文件末尾读定长尾标,找到索引尾。索引尾含三张表和一个校验和。帧表:每帧在文件里的偏移、压缩长度、解码后长度。索引项(每条记录一项):记录 id(`raw_ref` 用的信封 id)、原始流名、帧号、在解码后帧内的偏移与长度、类型(关键帧 / 增量)、回指、行的 sha256、有无换行、原始 (分片 id, `line_no`)。来源分片表:分片 id = 原文件 basename + 封存时测得的整文件 sha256,另记长度,原分片因此能逐字节还原;另记封存时原文件相对封存文件的路径与 (dev, inode, mtime),只供并存期认出「仍是那份原文件」,不参与身份。校验和 = 头 + 索引尾三张表的 sha256。`line_no` = 该行在原分片里从 0 起的行号,opaque 行也计;不叫 `seq`,免得和信封里「连接内第几次请求」的 `seq`([4.6](4.6-process-collector.md))混淆。索引约为原始的 0.03%。D35 之前的旧分片(`sessions/` 里有的 session 只存在于此)封存时,来源分片就是这个分片文件本身;它最初来自哪个采集分片不可知,不记,MUST NOT 编造。
- **读**:`raw_ref` → 按 (原始流名, id) 查索引 → 解码所需的帧(至多沿回指 16 步)→ 重建行 → 校验 sha256 → 切出 `req_body`;`text_ref` 的字节区间不变。所以 `raw_ref` / `text_ref` 跨封存有效,DuckDB 不因封存重建。解码后的帧进有界 LRU(约 8 帧)。三个读者 MUST 读封存文件,流式解码、内存有界,跳过或不认识的文件要报告,MUST NOT 折叠成空:`src/query/source.mjs`、看板装载(`src/server.mjs`)、ETL 读入(`src/etl/ingest.mjs`)。报告的去处(D38):看板 = [4.4](4.4-server.md) `/api/projects` 的 `source`,就地显示,每次装载从盘上重新算出,同一批文件一直在那里报;`asight etl` = stderr 并以非 0 退出,读不全的封存文件另追加一行原始层日志(上条),`/api/capture-health` 读得到。同一文件内 (原始流名, id) 重复(`req_<run>-<seq>` 跨运行会撞,v0 还有 `req_00042`)时,索引查找 MUST 返回「歧义」,MUST NOT 任挑一条——和封存前同名文件里撞 id 的行为一致。
- **一份长期副本**:每条记录只留一份长期副本——所属 session 的封存文件。按 session 分文件依 D20 的 D35 修订:原始层只读 dissector 声明的请求头 session 键,不解析 body,不做身份或血缘判定;取不到键的记录进按分片的封存文件。采集分片只在全部记录都已封存并校验通过后才删。同一 (session, 流) 可以有多个自包含的封存段,resolver 取并集;合并段只能走同样经校验的无损重编码。迁移旧分片时,采集副本与分片副本只在 (id, sha256) 字节一致时才去重。**旧采集流不封存**:`claude-capture.ndjson` / `capture.ndjson` 从不轮转、写者一直持有 O_APPEND fd,`asight shard` 又不断往 `sessions/` 追加;这条旧流照旧运行,等 [4.6](4.6-process-collector.md) 采集器(按日期轮转)取代它之后才封存。其间每条记录仍有两份,D34 预算达不到,用户已接受;MUST NOT 为凑预算删掉任一份,MUST NOT 截断活文件。
- **并存期**:原文件与封存文件并存时(崩溃后,或采集分片与 session 封存文件同时在),读者按封存文件声明的来源分片只用其一、选择一致,并按 (分片 id, `line_no`) 去重;inode 变了,resolver 重建索引。复制或恢复出来的树(inode 变了,大小相同、mtime 差不到 1 s)按同一份原文件算,不读两遍;大小相同而 mtime 也变了的,两份都读并报告「可能重复」(审查三 F4)。封存器与 `asight raw verify` 认「这个副本是这份原文件的」看内容(分片的身份就是它的字节):原文件前 `length` 字节的 sha256 等于记录值;(dev, inode) 只用来省掉这次计算——不同 inode 且更短时必不相等,(dev, inode, 大小, mtime) 全与封存时相同时直接算「是」(调用方删除或校验前一律再逐字节比对)。`asight raw compare` 认「会被删」用的也是这条判断,不用读者的 stat 规则(审查三第二轮)。否则它是另一份文件的副本(如 `asight shard` 在旧段旁新写的 `calls.ndjson`),各自封存、各自校验,永不建议删掉它(它是那些记录唯一的副本;审查三 F3)。只认 inode 不行:复制出来的树会被再封一份,删原文件后每条记录读两遍。
- **按 session 的封存文件在哪被读(审查 F2)**:按 session 的封存文件写在 `~/.asight/sessions/<key>/`(0.2 状态表),它们是某个采集分片的延续。读者服务**那个分片原来所在的目录**时,把 sessions 目录下来源分片在该目录的封存文件一并读入,所以封存前后看到的记录相同(E8),不需要另配一个根。`asight serve` / `asight doctor` 传默认 sessions 目录;`asight raw seal --sessions` 改到别处时,要把那个目录也作为源。只认来源目录是被服务根的封存文件,`asight shard` 的分片副本(来源就在 session 目录里)不会被拉进来;打不开、认不出来源的封存文件照样报告。实现 `src/raw/discover.mjs` 规则 3,test `test/raw/product-layout.test.mjs`、`test/raw/discover.test.mjs : "continuations: …"`。
- **watermark**:ETL 的 watermark 照旧按 session 记已消费的记录数,不按字节偏移。封存器 MUST 保持记录顺序:从封存文件读出的每个 session 的记录序列,与封存前从原分片读出的相同(按 (分片 id, `line_no`)),所以计数跨封存仍对得上,不 reset。读者因此按固定次序读一个目录:先按流(session 目录 = `calls` → `probes` → `other`,其余流按名),同一流内按段号(数值),仍在的原文件排在它那个流的段之后;不按文件名排(审查三 F2)。封存前后读者输出是否相同,由 `asight raw compare <dir>` 在删原文件之前逐 session、逐 control 类比对(经三个读者共用的读函数,审查三 F1)。按字节偏移记位置的消费者(今天只有 `asight shard` 的分片状态)见 OPEN。
- **导出(SHOULD)**:`asight raw export <session>` 把封存文件还原成普通 NDJSON,封存不让用户看不到原始字节(不变式 4)。每个封存段导出成一个文件,session 的放在 `~/.asight/export/<session>/`,不把多个流或段拼进一个文件(末行没有换行的流会和下一个流的首行粘成一行,审查三 F8)。默认写到 `~/.asight/export/`(目录 0700、文件 0600);用户另给的目标同样 0600。

- **凭证脱敏**:`request_headers.authorization='<redacted>'`(承 `verify.mjs`)——源即已脱敏,本层不"复原"。

## 验收(可跑 check · 明确测试要求)

## Edge cases
- **目录迁移**:`_unresolved`→真实 slug 的 `renameSync`(demo `ensureLocation`)——watermark 以 `session_id` 为键,迁移不重摄/不丢。
- **空 / 超大 session**:空 → 无行,不建空壳;超大 → 增量只碰新行,`call_blocks` 行数 = Σ块数但 `block_contents` 去重后远小(承 [3.2](3.2-normalized-model.md) Edge)。
- **半包 / error 记录**:源含 `error`(承 demo 错误记录)→ adapter 出 `calls.error` 行(非成功),ETL 照写,不当 200。
- **compaction 行**:CC 无显式标、由 message_count 骤降推断(confidence medium,[3.4](3.4-session-identity.md));ETL 只持久化 `calls.compaction`,**MUST NOT 误建 fork**(compaction≠fork,[3.4](3.4-session-identity.md) 关键区分)。
- **未认领记录**:无 adapter `detect` → 落"未识别"隔离区 + 计数([3.1](3.1-adapter-contract.md) Invariant),MUST NOT 静默丢。
- **未映射字段**:adapter 的 `extra`/`unmapped_count` 原样入表(承 [3.2](3.2-normalized-model.md) 保真兜底 + D7 钩子);ETL MUST NOT 丢弃 `extra`。

## Risk / 回滚
派生表是**一次性可弃**投影:任何 ETL 逻辑错 → `DROP` 表 + 清 watermark + 从源 NDJSON 全量重建,**源零损失**(不变式 2 的直接红利)。ETL 编排是幂等纯转换 → 可用固化真实源做离线回归。增量 watermark 损坏 → 退化为全量重建,慢但不丢真相。每个可独立验证的积木(去重 / 指针 / 增量)一个 commit,失败回退上一绿点。
