# asight · RFC 4.8 — Windows 采集器(D42 · VPN 块 / 自带转发)

> **状态**:设计已定(**D42**)。其中「自带转发」与 1.6 §1.2、§8 和 0.1 §5 的一条必拒冲突,定案前默认不提供(§2.4)。
> **前置**:D31(按进程,不碰系统代理与整机流量)· D36(按用户运行)· D37(七个 harness、信任入口)· D38(失败不静默)· D39(二元开关、off 保证、VPN 感知、拓扑与诊断,[1.6](1.6-cli.md))· D40(agent 进程的全部流量都解密,另一分支)· D41(本机网络环境,[4.7](4.7-netenv.md))。引擎、记录、开关、改包与 Linux 共用 [4.6](4.6-process-collector.md)。
> **取代**:D31⑥ 的「Windows = WFP / WinDivert」与 4.6 §结构 `arch/win32/(待写)WFP`(理由与实验数据见 §0)。

## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流不靠驱动:

- **VPN 块**(`vpn-block`):本机有 Clash Verge Rev 时,在它的全局脚本里加一个 asight 块。流量本来就进 Verge 的 agent,由块按进程交给 asight 引擎,引擎再交回 Verge,走用户自己的规则。
- **自带转发**(`own-forwarder`):没有可写的 VPN,或某个 agent 的流量不进 VPN 时,asight 把这个 agent 自己的代理入口指向 asight 自带的、只转发的 mihomo。mihomo 把 agent 进程交给引擎,其余照原路走。

开关与 off 保证照 1.6。采集到的数据与 Linux 同一格式,只有 `capture`(哪种引流)和几个路径类字段不同(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1] |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了,块与转发回退到原路(§3.3) |
| 覆盖 | 所有形态 | 有自己代理入口的形态、跟随系统代理的形态;Verge 开 TUN 时全部 [E2][LT] |
| 身份 | 内核给 pid | 进程规则给形态;pid 尽力补(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。缺口如实写:既没有代理入口、又不跟随系统代理的形态,只在 Verge 开 TUN 时采得到;Claude Desktop 与 Kimi 的 VS Code 扩展因信任入口不支持(§6.4)。用户把 Windows 的两种方式叫「with vpn / with no-vpn」,与本单元一致。

## 2. 引流方式与选择

### 2.1 三种

| 方式 | 流量怎么到 asight | asight 写什么 | 引擎的上游 | 什么时候用 |
|---|---|---|---|---|
| `vpn-block` | agent 的连接本来就进 Verge(跟随系统代理、Verge 开 TUN、或 agent 自己的代理指向 Verge);块里的进程规则把它交给 asight 引擎 | Verge 全局 `Script.js` 里一个哨兵块,加 Verge 数据目录里 asight 的规则文件(都入账,4.7 §4);**不写 agent 的网络设置**(1.6 §9.5) | 再进 Verge 的混合端口(CONNECT),走用户自己的规则 | Verge 在跑、规则模式、控制口读得到、`Script.js` 写得进 |
| `own-forwarder`(§2.4) | agent 自己的代理入口改指 asight 自带 mihomo 的该形态端口;mihomo 把 agent 进程交给引擎,其余(agent 的子进程等)照原路 | agent 的代理入口(入账、先备份、`off` 撤)+ 自带 mihomo | 该形态原来的下一跳:直连,或用户原来配的代理 | 没有可写的 VPN;或有 VPN,但这个形态的流量不进它 |
| 不引流 | — | — | — | 两样都不行(没有代理入口、提权、形态不支持)。`status` 报原因码,`doctor` 给办法 |

- asight 从不开 TUN、不改 Verge 的模式、不改系统代理(D31④)。TUN 是用户在自己 VPN 里的选择,`doctor` 只说怎么开。
- 选择按形态做,一台机器上可以两种并存(下文称「混合」)。

### 2.2 按形态选(每次 `on` 重新选)

`route-plan.mjs` 的规则:

1. 读本机网络环境(4.7 探针):Verge 在不在跑、模式、TUN、系统代理、控制口、`Script.js` 可不可写;别的代理软件与它的本地端口。
2. 对每个期望为开、已安装、受支持的形态:
   - 它的连接进得了可写的 Verge(TUN 开着;或系统代理开着且它跟随;或它自己的代理指向 Verge 的端口)→ `vpn-block`;
   - 否则,它有文件里的代理入口,且自带转发已启用 → `own-forwarder`,上游 = 它原来的下一跳;
   - 否则 → 不引流,原因码见下表。
3. 结果写进安装清单(每个形态一条 `route` 项)与 `netenv.json` 的 `adopted.<harness>`(1.6 §9.5)。之后环境变了:`netenv-changed`,`status` 印 `asight on` 重新选;asight 不自己改(1.6 §9.5)。

| 本机网络 | 进得了 Verge 的形态 | 进不了、有代理入口 | 都没有 |
|---|---|---|---|
| Verge · 规则模式 · 系统代理开 · TUN 关 | 跟随系统代理的(及 agent 自己的代理指向 Verge 的)→ `vpn-block` | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 规则模式 · TUN 开 | 全部 → `vpn-block` [LT] | — | — |
| Verge · 规则模式 · 系统代理关 · TUN 关 | 只有 agent 自己的代理指向 Verge 的 | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 全局 / 直连模式 | 块不起作用,不用块 | `own-forwarder`,上游 = 原下一跳(跟随者是 Verge 的端口) | `not-routed` + `clash-mode-bypass` |
| Verge 控制口读不到,或 `Script.js` 写不进 | 当作「别的代理软件」 | 同下一行 | `not-routed` |
| 别的代理软件(GUI.for.SingBox、v2rayN、Clash Party、FlClash……;asight 不往里写,4.7) | — | `own-forwarder`,上游 = 原下一跳(跟随者是那个软件的系统代理端口) | `not-routed` |
| 没有 VPN / 代理软件 | — | `own-forwarder`,上游直连 | `not-routed` |

- 自带转发没启用时(默认,§2.4),第二列一律变成 `not-routed`,`on` 的计划与 `status` 写「自带转发待你决定」。
- 别的 VPN 开着 TUN 时,自带 mihomo 与引擎的直连会被那个 TUN 收进去,出口与 agent 原来一样(按进程规则除外,1.6 `egress-differs`)。

### 2.4 自带转发

- **冲突**:1.6 §1.2 第四行与 §8 第二行(不让 agent 的代理字段指向 asight,做不到 off 保证);0.1 §5「提供做不到 off 保证的引流方式」(必拒)。
- **与被否决的做法的区别**:字段指向的是只转发、能退回直连的 mihomo,不是引擎。`off` 之后它只转发,不经引擎、不解密、不记录。
- **做不到的那部分(如实写)**:`on` 期间启动、读了入口的 agent,重启之前仍经 asight 的 mihomo;mihomo 死了,它们连不上,直到 mihomo 被拉起或 agent 重启(§4.3)。
- **定案之前**:代码照做、照测;默认不提供,环境变量 `ASIGHT_OWN_FORWARDER=1` 才启用。`on` 的计划把本该走它的形态列为「不引流 · 自带转发待你决定」。用户同意后删掉这个开关,同 PR 改 1.6 §1.2 / §8 与 0.1 §5。
- **另一种做法**:Verge 系统代理模式下,让 `on` 把不跟随系统代理的形态的代理入口指向 Verge 的端口(不指向 asight)。off 保证能做到,但 Verge 一退出这些 agent 就连不上,子进程的出口也跟着变。没有选它:它让 agent 依赖用户 VPN 的开关状态。

## 3. 规则块(Verge 与自带 mihomo 同一份代码)

设计来自 L4b 计划的 RS 方案(各项以 [L4b] 实测为准)。生成器是纯函数 `src/netenv/mihomo/rules.mjs`,收到的只是数据(组、进程规则、端口、token),不认识任何 harness。

### 3.1 块里有什么

对每个组 `<g>`(§2.3「块里的组」;自带 mihomo 按形态):

| 名字 | 是什么 |
|---|---|
| `asight-in-<g>` | 出站,`type: http`,`server: 127.0.0.1`,`port: <引擎入口端口>`,`username: <路由>.<g>`,`password: <入口 token>`(§3.2) |
| `asight-re-<g>` | 回退出站,`type: http`,指向「再进入点」:Verge = 它的混合端口;自带 mihomo = 该形态自己的监听端口(§3.3) |
| `asight-fb-<g>` | 组,`type: fallback`,`proxies: [asight-in-<g>, asight-re-<g>]`,`url: http://asight-health.invalid/<g>`,`interval: 10`,`timeout: 2000`,`lazy: false` |
| `asight-sw-<g>` | 组,`type: select`,`proxies: [PASS, asight-fb-<g>]`;第一个是 `PASS` = 默认关 |
| `asight-r-<g>` | 规则提供者,`type: file`,`behavior: classical`,`format: text`,`path: ./asight/route-<g>.txt`,`payload: [DOMAIN,asight-off.invalid]`(文件不在时什么都不匹配) |
| 规则(插在用户规则最前) | `DOMAIN,asight-health.invalid,REJECT`;每组一条 `RULE-SET,asight-r-<g>,asight-sw-<g>` |
| `route-<g>.txt` | 开 = 该组的进程规则(`PROCESS-PATH-REGEX,(?i)…` 在前,`PROCESS-NAME,…` 在后,来自 harness 文件);关 = 空文件 |

- **自带 mihomo** 另有:每个形态一个监听器(`listeners`,`type: mixed`,`127.0.0.1:<端口>`,`rule: in-<g>`),子规则 `in-<g>` = [`DOMAIN,asight-health.invalid,REJECT`,`RULE-SET,asight-r-<g>,asight-sw-<g>`,`MATCH,asight-up-<g>`];`asight-up-<g>` = 该形态原来的下一跳(`DIRECT`,或用户原来的代理)。全局:`allow-lan: false`,不设 `tun`、`dns`,`find-process-mode: always`,控制口只听 `127.0.0.1` 随机端口、随机 secret。
- 名字一律 `asight-` 开头。Verge 的块包在 4.7 的哨兵里;块的代码整体 `try/catch`,出错就原样返回用户的配置(块不生效,复核时报出,4.7 §5)。

### 3.2 身份

- 出站凭据:`username = <路由>.<g>`(`vb.claude-code.cli`、`of.codex.cli` 这样),`password = 入口 token`。token 是每次安装随机的 32 位十六进制,存 `~/.asight/collector/ingress.json`(0600),`uninstall` 删。引擎验 token,不对回 407、记 `ingress-auth-failed`。
- 用标准的 `Proxy-Authorization` 同时带身份与鉴权,http 与 socks5 出站都支持 [E5];不用 `X-Asight-Agent` 头。
- 这是形态级身份,不带 pid;pid 尽力补(§5.3)。

### 3.3 asight 不在时回退

- **引擎活着**:健康检查经 `asight-in-<g>` 到引擎,引擎本地答 `204`,不外发。
- **引擎死了或卡住**:`asight-in` 失败;`asight-re` 再进 mihomo,`asight-health.invalid` 命中第一条 `REJECT` 规则,mihomo 回 `502`。有回应就算活,组选 `asight-re`,流量走用户原来的路(Verge:用户自己的规则;自带:原下一跳)。
- **为什么这样**:`PASS` 过不了健康检查,全死时 fallback 选第一个成员(asight),不能放开 [mihomo `adapter/outboundgroup/fallback.go`][L4b S4];用外网地址做健康检查等于 asight 自己发请求(不变式 1)。
- **窗口期**:最多一个检查间隔加超时(约 12 s),其间新连接失败、agent 自己重试 [E10];在途连接随引擎断(4.6 §Linux 机制「fail-open 两层」的同一代价)。守护进程活着时写 `fallback-active`(失败类)。
- **两个前提**(W40 [WinVM]):mihomo 的回环检测不拦自己的 http 出站再进自己的入口;Verge 的混合端口不要鉴权(要的话回退失败,报 `reenter-auth`)。

### 3.4 防环路

- 块只用进程规则,不用域名规则。引擎是 `node.exe`,`node.exe` 不作任何组的引流键(dsh CLI 只走自带转发的专用端口),所以引擎再进 Verge 的连接不匹配任何组,走用户自己的规则。
- 生成时静态核对:每条进程规则都不匹配引擎的映像路径,也不匹配自带 mihomo 的映像路径;不过就不写块,报 `route-loop`。
- TUN 下照样成立与否,由 [LT] 量(W41)。

### 3.5 整个进程都引过来(D40)与 `Code.exe`

- 进程规则把该进程的全部连接都交给引擎,含非模型流量 [E4]。D40:已信任的解密并逐字存;不能解密的透传并记录。
- `Code.exe` 不作引流键:引它等于把整个 VS Code 扩展宿主的流量都引过来(L4 实测 12 s 内 40 多次 `chatgpt.com`),D40 下还要解密别家扩展的流量。代价:Kimi 的 VS Code 扩展不被采集(它本来也信任不了 asight,§2.3)。

### 3.6 用户组的 `include-all`

- 用户的组带 `include-all` / `include-all-proxies` / `include-all-providers` 时,asight 的出站会被收进去。url-test 组会挑延迟最低的 `asight-in-*`(回环),把用户的全部流量交给 asight;`asight-re-*` 还可能绕成环 [L4b S8]。
- 块在生成配置时给这些组的 `exclude-filter` 追加 `^asight-`。只改 Verge 生成的运行时配置,不改用户的文件。它动的是用户组在运行时的成员。W45 [WinVM]。
- 自带 mihomo 没有用户组,不涉及。

## 4. 开与关

### 4.1 Verge:怎么生效(适配器的四种策略)

| 策略 | 做什么 | 何时可用 | 依据 |
|---|---|---|---|
| `select` | `PUT /proxies/asight-sw-<g> {name}`:开 = `asight-fb-<g>`,关 = `PASS` | 块已在 Verge 的运行时里 | [L4b C3] |
| `provider` | 写 `route-<g>.txt`,再 `PUT /providers/rules/asight-r-<g>` | 块已在运行时;sidecar 模式。服务模式下 Verge 把规则文件拷进服务目录,之后改原文件不生效 [L4b S5] | [L4b C1a] |
| `payload` | D29 的做法:读运行时配置,拼入或剥掉块,`PUT /configs?force=true {payload}`;整份配置只在内存 | 控制口接受这个写 | [L4b C2a]、D29 |
| `none` | 只写文件;回执写「已写入,未生效 · 去 Clash Verge → 订阅,点当前订阅重新激活」 | 上面三种都不行 | D29 兜底 |

- **选哪种**(`pickApply`):块已在运行时 → 单个组的开关用 `select` 加 `provider` 两把钥匙:关只要一把落地就算关,开要两把都落地 [L4b RS]。块不在运行时(首次 `on`;不带参数的 `off` 剥块之后再 `on`)→ `payload`。控制口不能写、或 `payload` 被拒 → `none`。
- **复核**:开 = 该组的 `now` 是 `asight-fb-<g>`,且规则提供者计数大于 0;关 = `now` 是 `PASS`,或计数为 0。读不到写「不知道」,`off` 因此退出 1。不再看 `GET /proxies` 里有没有 asight 的出站:关之后出站可能留在运行时,直到 Verge 下次重新生成 [L4b §5.1]。D29 的这一条只管旧采集。
- 顺序是默认值,[L4b] 量完按结果改(W30–W35)。

### 4.2 自带 mihomo

- 每次开关都向它自己的控制口 `PUT /configs?force=true` [E8]。
- 关 = 换成「只转发」配置:每个形态端口 `MATCH,asight-up-<g>`,没有 `asight-in-*`,引擎不在路径上。

### 4.3 off 保证(照 1.6 §1.2;例外如实写)

| 方式 | `off` 做什么 | 之后保证什么 | 例外 |
|---|---|---|---|
| `vpn-block` | ① 期望态写 off;② 每组 `select` 置 `PASS`、规则文件清空并刷新,复核;③ 不带参数的 `off` 另按 D28 剥 `Script.js` 里的块、删规则文件;④ 引擎按 1.6 §1.3 关在途连接 | 新连接不再匹配 asight 的规则,走用户自己的路;之后 asight 死了也不影响 agent | 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2)。Verge 运行时里留着不起作用的出站与组,到 Verge 下次重新生成为止;mihomo 的 `cache.db` 留一条 `asight-sw-*` 的选择记录(无害;asight 不改它的数据库)[L4b B10]。都列在回执与 `status` 里。控制口读不到:`off` 退出 1,写「asight 可能仍在 Clash 的路径上,去 Clash Verge 重新激活」;Verge 已退出:运行时不在,文件已撤,算做完 |
| `own-forwarder` | ① 期望态写 off;② 撤 agent 的代理入口(只撤 asight 写的值,1.6 §9.5);③ 自带 mihomo 换成只转发配置;④ 引擎关在途连接 | 新启动的 agent 直连原下一跳;引擎不在任何 agent 的路径上 | **`on` 期间启动、读了入口的 agent,重启前仍经自带 mihomo(只转发)**;它死了它们连不上。守护进程留在排空状态,监管 mihomo,直到这些进程都退出,再一起退出。`status`:「还有 N 个 agent 连着 asight 的转发,重启它们之后 asight 就完全退出」。`off --now`:立即停 mihomo,回执列出会断的 pid(操作者的显式意图)。这就是 §2.4 的冲突 |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各组的开关:VPN 块是 `select` 与规则文件;自带转发是 mihomo 配置里的子规则与 agent 的入口。块本身不重写。
- 块里的组按「已装且支持的形态」生成,与期望态无关。所以单个 harness 的开关不用重写块、不用 Verge 重新激活。新装了一个 harness 时,`on` 重写块(走 `payload` 或 `none`)。
- 用户后来自己把某个 agent 的代理指向了 Verge:它的组早在块里,新进程立刻经块,不用跑 asight 命令(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定:块与 mihomo 配置里写死它。端口被别的进程占了:不换端口,记 `engine-port-taken`(失败类),由块的回退接管(§3.3);`doctor` 给查占用者与重选端口的命令(§10.4)。
- 认三种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)· 绝对 URI 的 `GET http://asight-health.invalid/…`(健康检查,答 `204`)。别的开头:关掉,记 `ingress-unknown`。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。
- 引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。这里 CONNECT 是 mihomo 发给 asight 的,asight 就是被问的那个代理,回答它不算替别人回答。mihomo 早已对 agent 答了 `200`,上游失败时 agent 看到连接被关 [mihomo `listener/http/proxy.go`]。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §1.3)。

### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` 取组对应的 harness |
| `form` | 形态 id(如 `codex.app`);区分不了时为组名 |
| `capture` | `vpn-block` · `own-forwarder` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth_ref}` · `{kind:'socks5', host, port, auth_ref}`。VPN 块一律 `http` = Verge 的混合端口;自带转发按该形态接上时的原下一跳 |
| `pid_source` | `single-process` · `socket-table` · `forwarder-connections` · `null` |

- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。

### 5.3 pid 补全(尽力,不挡采集)

| 办法 | 何时用 | 怎么做 |
|---|---|---|
| 单进程 | 该形态此刻只有一个在跑的进程 | 就是它 |
| 套接字表 | 多个进程;系统代理或代理入口方式 | 助手查 `GetExtendedTcpTable` [E6]:该形态的进程里,谁有一条连到入口那一跳(Verge 混合端口,或该形态的自带端口)、还没被认领的连接;只有一个 → 它 |
| 自带 mihomo 的连接表 | 自带转发、多个进程 | asight 自己的 mihomo `GET /connections`(经它的只有 agent 与其子进程),按 host、组、时间取 `sourcePort`,再查套接字表 |
| 从不 | — | Verge 的 `/connections`、`/logs`:含本机所有程序的连接元数据(4.7 §3.2) |

- 预算 250 ms,与连上游并行。超时、不唯一、TUN 下多进程 → `pid:null`,按形态判(§5.4)。
- **代价**(观测者效应):多进程形态的新连接,首字节最多多等 250 ms。`flows/` 连接行记 `pid_ms`。常驻助手的一次表查询约 5 ms [E6];W12 [WinVM] 量 p50 / p90。
- 套接字表读不到(受限令牌、策略禁用 `Add-Type`)→ 一条失败事件 `socktable-unavailable`,之后全按形态判。

### 5.4 信任判定

- **有 pid**:照 4.6 §确认信任,按 pid 判:进程启动时间与入口的 `installed_at`、插件标记、Kimi shim 的父进程。
- **没有 pid**:按形态判。该形态在跑的进程**全部**已信任 → 解密;有一个未信任 → 透传,`not_captured:'untrusted'`,`reason:'pid-unresolved-mixed'`。这样 1.6 §1.1「`off → on` 后在跑的 agent 透传、不被弄断」在没有 pid 时也成立。代价:同一形态的新进程要等旧进程退出才被采集,`status` 点名旧进程。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(<路由>.<组>, host)`。不同形态、不同路由互不毒化 [E15]。
- 条目只在内存:pid 退出、或该形态的进程全退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。只有这几个字段随引流不同:

| 字段 | Linux eBPF | Windows `vpn-block` | Windows `own-forwarder` |
|---|---|---|---|
| `capture` | `transparent` | `vpn-block` | `own-forwarder` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` | 同左 |
| `proc.pid` | 内核给 | 尽力,可为 `null` | 同左 |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` | 同左 |

- 其余字段(请求与响应的原始字节、头、体、`host`、`scheme`、`endpoint`、`transport`、`ws_*`、`asight_added`、各种标注)MUST 逐字节相同。验收:同一 mock 调用分别经 Linux eBPF 与 Windows 两种引流,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?}`(不含凭据)。
- 读取侧:`capture` 多两个值(改 4.1 信封表);观测者效应表(`src/dissect/harnesses.mjs`)对三种新采集器的值都适用;看板就地标引流方式;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

## 6. 信任入口(Windows · D37④ 的 Windows 写法)

规则同 4.6:按 harness 各走一个入口,只让该 agent 信任 asight CA;不写登录环境(`setx`、`HKCU\Environment` 里的 CA 变量、PowerShell `$PROFILE`);不装任何证书库(`CurrentUser\Root`、`LocalMachine\Root` 都不碰)。入口随开关:`on` 写、`off` 撤,入账、先备份(1.6 R2)。

### 6.1 表

| 形态 | asight 写什么 | 语义 · 指向 | 何时生效 | 依据 |
|---|---|---|---|---|
| `claude-code.cli` / `.vscode` | `%USERPROFILE%\.claude\settings.json` 的 `env.NODE_EXTRA_CA_CERTS` | 追加;`asight-ca.pem` 或 `extra-cc.pem`(取法同 4.6) | 启动时;扩展下一条消息即生效 | L1 |
| `codex.*` | `%CODEX_HOME%\.env`(默认 `%USERPROFILE%\.codex\.env`)最上面一个哨兵块,`SSL_CERT_FILE=<合并包>` | 替换;`combined-codex.pem`(§6.2) | 进程启动时读;app 与扩展要重启 | L1、L3 [E13] |
| `opencode.*` | 插件 `%USERPROFILE%\.config\opencode\plugins\asight-ca.js` | 追加;有 `tls.setDefaultCACertificates`(Node 侧车)就用它,没有(Bun)就包 `fetch` 加 `tls:{ca}` | 进程启动时 | L1、L2 |
| `kimi-code.cli` | shim `%USERPROFILE%\.asight\collector\bin\kimi.cmd` + 用户 PATH 最前一项(§6.3) | 追加;shim 设 `NODE_EXTRA_CA_CERTS` | 经 PATH 启动时 | L1 |
| `deepseek-dsh.*` | `%USERPROFILE%\.dsh\cordis.patch.yml` 一行 `- insert: [{id: asight-ca, name: <插件入口绝对路径>}]`(带哨兵注释);插件目录 `%USERPROFILE%\.asight\collector\plugins\dsh\` | 追加;`tls.setDefaultCACertificates`(Node ≥ 22.19) | 每次启动;Desktop 热重载 | L1(写成 `- id/name` 会报「entry not found」) |
| `hermes.cli` | `%LOCALAPPDATA%\hermes\.env` 最上面一个哨兵块,`SSL_CERT_FILE=<合并包>`;按版本加 `HERMES_CA_BUNDLE`(同 4.6) | 替换;`combined-hermes.pem` | 启动时 | L1 [E18] |

- 写进配置文件的路径一律用正斜杠(`C:/Users/<u>/…`):dotenvy 把反斜杠当转义,会静默丢掉 `SSL_CERT_FILE`。
- 自带转发用的代理入口(§2.3 那一列)与信任入口写在同一个文件时放进同一个哨兵块(Codex、Hermes 的 `.env`),分别入账。

### 6.2 合并包(Windows)

- `combined-<harness>.pem` = Node 自带根(`tls.rootCertificates`)∪ Windows 根证书库的导出 ∪ 该 harness 自己配置里的用户 CA ∪ asight CA。
- Windows 根:Node ≥ 22.15 用 `tls.getCACertificates('system')`;更老的由助手只读导出 `Cert:\CurrentUser\Root` 与 `Cert:\LocalMachine\Root`(`roots.mjs`)。只读,从不写。
- 不用 macOS 的 `cert.pem`:企业与杀毒软件的 TLS 检查根只在 Windows 库里。
- Windows 的根按需下载,库里只是子集;Node 自带根补公网。守护进程启动时与每天比一次指纹,变了就原子重建(4.6)。

### 6.3 Kimi 的 shim 与用户 PATH

- shim 是 `kimi.cmd`:设 `NODE_EXTRA_CA_CERTS`(取法同 4.6 的 `extra-kimi.pem` 规则);自带转发开时,启动环境里没有 `HTTPS_PROXY` 才设它(用户自己设了就不覆盖,`status` 报 `not-routed`);再 `"<kimi.exe>" %*`。
- 用户 PATH(`HKCU\Environment\Path`)最前插一项 shim 目录:保持值的类型(`REG_EXPAND_SZ` 还是它);从不用 `setx`(1024 字符截断);写完广播 `WM_SETTINGCHANGE`;撤时只删这一项,从不拿旧值整个写回(D28 的教训)。值在 asight 改过之后又被改过:只删这一项,报「已撤销,但不逐字节相同」。
- 这一项不是 CA 变量,只改 `kimi` 解析到哪个文件(同 Linux rc 那一行)。shim 目录里只有 `kimi.cmd`。
- 只在原生安装(`%USERPROFILE%\.kimi-code\bin\kimi.exe` 在)时装。Smart App Control 开着时不装:被拦的 shim 排在 PATH 最前,`kimi` 就起不来(fail-closed);改报「未信任 · Smart App Control」。

## 7. 守护进程、自启、控制面

- **守护进程** = `node --use-system-ca <asight> daemon`(上游按 Windows 库校验,4.6 §引擎 第 5 步;Node ≥ 22.15)。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(R7 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。
- **自启**:每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`(不用 S4U:S4U 不受 UAC 过滤,是 High 完整性)。动作 = `conhost.exe --headless "<node.exe>" --use-system-ca "<asight.mjs>" daemon`(无窗口 [E20])。设置 = 失败后 1 分钟重启(最多 999 次)、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML`(经 `execTool`)注册并启用;不带参数的 `off` 停用;`uninstall` 删除。不需要管理员。计划任务能否拉起崩溃的长时进程,由 W47 [WinVM] 量;不能时,`asight daemon` 改为一个小的监管父进程(计划里的后备)。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`(只有本用户能读)。CLI 读它再连。名字随机,防同机别的用户先占一个固定名字。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:计划任务拉起;其间 VPN 块与自带 mihomo 都回退到原路(§3.3)。

## 8. 自带 mihomo:来源、许可、监管

- **钉死版本**:`src/collector/arch/win32/mihomo-pin.json` = `{version, assets:{x64:{name, url, size, sha256}, arm64:{…}}, license:'GPL-3.0-only', source}`。首版钉 v1.19.32;只从 `https://github.com/MetaCubeX/mihomo/releases/download/<version>/` 取。摘要在实现时按发布页的 digest 填,两次下载核对一致才写进仓库。
- **怎么拿到**:Windows 的发布包(4.5 GitHub Release)直接带它。npm 装的没有时,`on` 的计划列出「要下载 mihomo <版本>(<大小>,来自 <URL>,sha256 <值>)」,确认后才下载。这是 1.6 R8「CLI 不联网」的例外:操作者确认的、只连钉死地址的一次下载。核对 sha256,不符就删掉,记 `forwarder-digest-mismatch`;带 Authenticode 签名时另核签名者,不带时只认摘要。
- **放哪**:`%USERPROFILE%\.asight\collector\bin\asight-forwarder.exe`(改名,进程名不与用户自己的 mihomo 撞),旁边放 `LICENSE-mihomo.txt` 与源码地址。GPL-3:独立的可执行文件,asight 不链接它,只经命令行与控制口用它;回执写明。
- **监管**:守护进程以分离方式拉起它(守护进程崩了它不跟着死),`forwarder.lock` 记 pid 与启动时间。守护进程重启时认领它:pid、启动时间、控制口 `GET /version` 三者都对得上。它退出了:按 1、2、4…30 s 退避重拉,每次一条 `forwarder-restart`;连续 5 次起不来 → `forwarder-down`(失败类)。asight 不因此改 agent 的设置(1.6 §9.5),`doctor` 给命令。
- **只在需要时跑**:没有形态走自带转发时不下载、不启动。
- 只转发与排空见 §4.3。

## 10. 网络拓扑与诊断(Windows 的形状 · 细化 1.6 §9)

### 10.1 每一跳从哪读

| 跳 | 读什么 |
|---|---|
| agent | 助手的进程快照:映像路径、启动时间、完整性(读不到写「不知道 · denied」) |
| agent 的代理 | harness 文件 `proxy` 声明的配置键(读法同信任 resolver);系统代理(`HKCU\…\Internet Settings` 的 `ProxyEnable` / `ProxyServer` / `AutoConfigURL`)只对声明读它的形态算。别的进程的启动环境读不到(Windows 上不读进程内存):那一跳写「不知道 · env-unreadable」,标「推断」 |
| 端口属主 | 套接字表的 LISTEN 行与属主 pid → 进程快照;产品与版本取 4.7 |
| Verge | 4.7 的只读字段:模式、TUN、混合端口 |
| asight 块 | 安装清单 + 控制口里组的 `now` 与提供者计数(§4.1) |
| 自带 mihomo | `forwarder.lock` + 它自己的控制口:各形态端口与上游 |
| 引擎 | `lock` + 控制管道:入口端口、负缓存 |
| TUN | 助手读网卡(.NET `NetworkInterface`,不经 CIM)与默认路由 |

- 一个 harness 有多个形态时,每个形态各画一支(`branches[].form`,追加进 1.6 §9.4)。

### 10.3 用户自己的代理(1.6 §9.5 在 Windows 上)

- **VPN 块**:不写 agent 的设置。用户把某个 agent 的代理指向 Verge 的端口:它的组早在块里,新进程立刻经块,不用跑 asight 命令;`status` 画出新的路,列「在跑的 pid 仍按启动时的设置,重启后按新的」。指向别处(公司代理、sing-box):它不进 Verge → `not-routed`;自带转发已启用时 `status` 印 `asight on <h>`。
- **自带转发**:`on` 把入口改指 asight 转发,原值记进清单的 `prior_value`(0600;`netenv.json` 只存哈希,1.6 §9.5)。用户之后改了这个键 → `proxy-changed`,失败类(asight 已被绕过);`status` 画新的路并印 `asight on <h>`;不在终端又没有 `--yes` 的 `on` 只出计划(1.6 R6)。`off` 时键仍是 asight 写的值才还原;用户改过就不动(1.6 V48)。
- 不加命令(1.6 §9.5、§8)。
