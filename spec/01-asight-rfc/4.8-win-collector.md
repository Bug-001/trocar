# asight · RFC 4.8 — Windows 采集器(D42 · VPN 块 / 自带转发)

> **状态**:设计已定(**D42**)。其中「自带转发」与 1.6 §1.2、§8 和 0.1 §5 的一条必拒冲突,定案前默认不提供(§2.4)。
> **前置**:D31(按进程,不碰系统代理与整机流量)· D36(按用户运行)· D37(七个 harness、信任入口)· D38(失败不静默)· D39(二元开关、off 保证、VPN 感知、拓扑与诊断,[1.6](1.6-cli.md))· D40(agent 进程的全部流量都解密,另一分支)· D41(本机网络环境,[4.7](4.7-netenv.md))。引擎、记录、开关、改包与 Linux 共用 [4.6](4.6-process-collector.md)。
> **取代**:D31⑥ 的「Windows = WFP / WinDivert」与 4.6 §结构 `arch/win32/(待写)WFP`(理由与实验数据见 §0)。

## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流不靠驱动:

- **VPN 块**(`vpn-block`):本机有 Clash Verge Rev 时,在它的全局脚本里加一个 asight 块。流量本来就进 Verge 的 agent,由块按进程交给 asight 引擎,引擎再交回 Verge,走用户自己的规则。
- **自带转发**(`own-forwarder`):没有可写的 VPN,或某个 agent 的流量不进 VPN 时,asight 把这个 agent 自己的代理入口指向 asight 自带的、只转发的 mihomo。mihomo 把 agent 进程交给引擎,其余照原路走。

开关与 off 保证照 1.6。采集到的数据与 Linux 同一格式,只有 `capture`(哪种引流)和几个路径类字段不同(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1] |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了,块与转发回退到原路(§3.3) |
| 覆盖 | 所有形态 | 有自己代理入口的形态、跟随系统代理的形态;Verge 开 TUN 时全部 [E2][LT] |
| 身份 | 内核给 pid | 进程规则给形态;pid 尽力补(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。缺口如实写:既没有代理入口、又不跟随系统代理的形态,只在 Verge 开 TUN 时采得到;Claude Desktop 与 Kimi 的 VS Code 扩展因信任入口不支持(§6.4)。用户把 Windows 的两种方式叫「with vpn / with no-vpn」,与本单元一致。

| # | 实测 |

## 2. 引流方式与选择

### 2.1 三种

| 方式 | 流量怎么到 asight | asight 写什么 | 引擎的上游 | 什么时候用 |
|---|---|---|---|---|
| `vpn-block` | agent 的连接本来就进 Verge(跟随系统代理、Verge 开 TUN、或 agent 自己的代理指向 Verge);块里的进程规则把它交给 asight 引擎 | Verge 全局 `Script.js` 里一个哨兵块,加 Verge 数据目录里 asight 的规则文件(都入账,4.7 §4);**不写 agent 的网络设置**(1.6 §9.5) | 再进 Verge 的混合端口(CONNECT),走用户自己的规则 | Verge 在跑、规则模式、控制口读得到、`Script.js` 写得进 |
| `own-forwarder`(§2.4) | agent 自己的代理入口改指 asight 自带 mihomo 的该形态端口;mihomo 把 agent 进程交给引擎,其余(agent 的子进程等)照原路 | agent 的代理入口(入账、先备份、`off` 撤)+ 自带 mihomo | 该形态原来的下一跳:直连,或用户原来配的代理 | 没有可写的 VPN;或有 VPN,但这个形态的流量不进它 |
| 不引流 | — | — | — | 两样都不行(没有代理入口、提权、形态不支持)。`status` 报原因码,`doctor` 给办法 |

- asight 从不开 TUN、不改 Verge 的模式、不改系统代理(D31④)。TUN 是用户在自己 VPN 里的选择,`doctor` 只说怎么开。
- 选择按形态做,一台机器上可以两种并存(下文称「混合」)。

### 2.2 按形态选(每次 `on` 重新选)

`route-plan.mjs` 的规则:

1. 读本机网络环境(4.7 探针):Verge 在不在跑、模式、TUN、系统代理、控制口、`Script.js` 可不可写;别的代理软件与它的本地端口。
2. 对每个期望为开、已安装、受支持的形态:
   - 它的连接进得了可写的 Verge(TUN 开着;或系统代理开着且它跟随;或它自己的代理指向 Verge 的端口)→ `vpn-block`;
   - 否则,它有文件里的代理入口,且自带转发已启用 → `own-forwarder`,上游 = 它原来的下一跳;
   - 否则 → 不引流,原因码见下表。
3. 结果写进安装清单(每个形态一条 `route` 项)与 `netenv.json` 的 `adopted.<harness>`(1.6 §9.5)。之后环境变了:`netenv-changed`,`status` 印 `asight on` 重新选;asight 不自己改(1.6 §9.5)。

| 本机网络 | 进得了 Verge 的形态 | 进不了、有代理入口 | 都没有 |
|---|---|---|---|
| Verge · 规则模式 · 系统代理开 · TUN 关 | 跟随系统代理的(及 agent 自己的代理指向 Verge 的)→ `vpn-block` | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 规则模式 · TUN 开 | 全部 → `vpn-block` [LT] | — | — |
| Verge · 规则模式 · 系统代理关 · TUN 关 | 只有 agent 自己的代理指向 Verge 的 | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 全局 / 直连模式 | 块不起作用,不用块 | `own-forwarder`,上游 = 原下一跳(跟随者是 Verge 的端口) | `not-routed` + `clash-mode-bypass` |
| Verge 控制口读不到,或 `Script.js` 写不进 | 当作「别的代理软件」 | 同下一行 | `not-routed` |
| 别的代理软件(GUI.for.SingBox、v2rayN、Clash Party、FlClash……;asight 不往里写,4.7) | — | `own-forwarder`,上游 = 原下一跳(跟随者是那个软件的系统代理端口) | `not-routed` |
| 没有 VPN / 代理软件 | — | `own-forwarder`,上游直连 | `not-routed` |

- 自带转发没启用时(默认,§2.4),第二列一律变成 `not-routed`,`on` 的计划与 `status` 写「自带转发待你决定」。
- 别的 VPN 开着 TUN 时,自带 mihomo 与引擎的直连会被那个 TUN 收进去,出口与 agent 原来一样(按进程规则除外,1.6 `egress-differs`)。

### 2.4 自带转发

- **冲突**:1.6 §1.2 第四行与 §8 第二行(不让 agent 的代理字段指向 asight,做不到 off 保证);0.1 §5「提供做不到 off 保证的引流方式」(必拒)。
- **与被否决的做法的区别**:字段指向的是只转发、能退回直连的 mihomo,不是引擎。`off` 之后它只转发,不经引擎、不解密、不记录。
- **做不到的那部分(如实写)**:`on` 期间启动、读了入口的 agent,重启之前仍经 asight 的 mihomo;mihomo 死了,它们连不上,直到 mihomo 被拉起或 agent 重启(§4.3)。
- **定案之前**:代码照做、照测;默认不提供,环境变量 `ASIGHT_OWN_FORWARDER=1` 才启用。`on` 的计划把本该走它的形态列为「不引流 · 自带转发待你决定」。用户同意后删掉这个开关,同 PR 改 1.6 §1.2 / §8 与 0.1 §5。
- **另一种做法**:Verge 系统代理模式下,让 `on` 把不跟随系统代理的形态的代理入口指向 Verge 的端口(不指向 asight)。off 保证能做到,但 Verge 一退出这些 agent 就连不上,子进程的出口也跟着变。没有选它:它让 agent 依赖用户 VPN 的开关状态。

## 3. 规则块(Verge 与自带 mihomo 同一份代码)

设计来自 L4b 计划的 RS 方案(各项以 [L4b] 实测为准)。生成器是纯函数 `src/netenv/mihomo/rules.mjs`,收到的只是数据(组、进程规则、端口、token),不认识任何 harness。

### 3.1 块里有什么

对每个组 `<g>`(§2.3「块里的组」;自带 mihomo 按形态):

| 名字 | 是什么 |
|---|---|
| `asight-in-<g>` | 出站,`type: http`,`server: 127.0.0.1`,`port: <引擎入口端口>`,`username: <路由>.<g>`,`password: <入口 token>`(§3.2) |
| `asight-re-<g>` | 回退出站,`type: http`,指向「再进入点」:Verge = 它的混合端口;自带 mihomo = 该形态自己的监听端口(§3.3) |
| `asight-fb-<g>` | 组,`type: fallback`,`proxies: [asight-in-<g>, asight-re-<g>]`,`url: http://asight-health.invalid/<g>`,`interval: 10`,`timeout: 2000`,`lazy: false` |
| `asight-sw-<g>` | 组,`type: select`,`proxies: [PASS, asight-fb-<g>]`;第一个是 `PASS` = 默认关 |
| `asight-r-<g>` | 规则提供者,`type: file`,`behavior: classical`,`format: text`,`path: ./asight/route-<g>.txt`,`payload: [DOMAIN,asight-off.invalid]`(文件不在时什么都不匹配) |
| 规则(插在用户规则最前) | `DOMAIN,asight-health.invalid,REJECT`;每组一条 `RULE-SET,asight-r-<g>,asight-sw-<g>` |
| `route-<g>.txt` | 开 = 该组的进程规则(`PROCESS-PATH-REGEX,(?i)…` 在前,`PROCESS-NAME,…` 在后,来自 harness 文件);关 = 空文件 |

- **自带 mihomo** 另有:每个形态一个监听器(`listeners`,`type: mixed`,`127.0.0.1:<端口>`,`rule: in-<g>`),子规则 `in-<g>` = [`DOMAIN,asight-health.invalid,REJECT`,`RULE-SET,asight-r-<g>,asight-sw-<g>`,`MATCH,asight-up-<g>`];`asight-up-<g>` = 该形态原来的下一跳(`DIRECT`,或用户原来的代理)。全局:`allow-lan: false`,不设 `tun`、`dns`,`find-process-mode: always`,控制口只听 `127.0.0.1` 随机端口、随机 secret。
- 名字一律 `asight-` 开头。Verge 的块包在 4.7 的哨兵里;块的代码整体 `try/catch`,出错就原样返回用户的配置(块不生效,复核时报出,4.7 §5)。

### 3.2 身份

- 出站凭据:`username = <路由>.<g>`(`vb.claude-code.cli`、`of.codex.cli` 这样),`password = 入口 token`。token 是每次安装随机的 32 位十六进制,存 `~/.asight/collector/ingress.json`(0600),`uninstall` 删。引擎验 token,不对回 407、记 `ingress-auth-failed`。
- 用标准的 `Proxy-Authorization` 同时带身份与鉴权,http 与 socks5 出站都支持 [E5];不用 `X-Asight-Agent` 头。
- 这是形态级身份,不带 pid;pid 尽力补(§5.3)。

### 3.3 asight 不在时回退

- **引擎活着**:健康检查经 `asight-in-<g>` 到引擎,引擎本地答 `204`,不外发。
- **引擎死了或卡住**:`asight-in` 失败;`asight-re` 再进 mihomo,`asight-health.invalid` 命中第一条 `REJECT` 规则,mihomo 回 `502`。有回应就算活,组选 `asight-re`,流量走用户原来的路(Verge:用户自己的规则;自带:原下一跳)。
- **为什么这样**:`PASS` 过不了健康检查,全死时 fallback 选第一个成员(asight),不能放开 [mihomo `adapter/outboundgroup/fallback.go`][L4b S4];用外网地址做健康检查等于 asight 自己发请求(不变式 1)。
- **窗口期**:最多一个检查间隔加超时(约 12 s),其间新连接失败、agent 自己重试 [E10];在途连接随引擎断(4.6 §Linux 机制「fail-open 两层」的同一代价)。守护进程活着时写 `fallback-active`(失败类)。
- **两个前提**(W40 [WinVM]):mihomo 的回环检测不拦自己的 http 出站再进自己的入口;Verge 的混合端口不要鉴权(要的话回退失败,报 `reenter-auth`)。

### 3.4 防环路

- 块只用进程规则,不用域名规则。引擎是 `node.exe`,`node.exe` 不作任何组的引流键(dsh CLI 只走自带转发的专用端口),所以引擎再进 Verge 的连接不匹配任何组,走用户自己的规则。
- 生成时静态核对:每条进程规则都不匹配引擎的映像路径,也不匹配自带 mihomo 的映像路径;不过就不写块,报 `route-loop`。
- TUN 下照样成立与否,由 [LT] 量(W41)。

### 3.5 整个进程都引过来(D40)与 `Code.exe`

- 进程规则把该进程的全部连接都交给引擎,含非模型流量 [E4]。D40:已信任的解密并逐字存;不能解密的透传并记录。
- `Code.exe` 不作引流键:引它等于把整个 VS Code 扩展宿主的流量都引过来(L4 实测 12 s 内 40 多次 `chatgpt.com`),D40 下还要解密别家扩展的流量。代价:Kimi 的 VS Code 扩展不被采集(它本来也信任不了 asight,§2.3)。

### 3.6 用户组的 `include-all`

- 用户的组带 `include-all` / `include-all-proxies` / `include-all-providers` 时,asight 的出站会被收进去。url-test 组会挑延迟最低的 `asight-in-*`(回环),把用户的全部流量交给 asight;`asight-re-*` 还可能绕成环 [L4b S8]。
- 块在生成配置时给这些组的 `exclude-filter` 追加 `^asight-`。只改 Verge 生成的运行时配置,不改用户的文件。它动的是用户组在运行时的成员。W45 [WinVM]。
- 自带 mihomo 没有用户组,不涉及。

## 4. 开与关

### 4.1 Verge:怎么生效(适配器的四种策略)

| 策略 | 做什么 | 何时可用 | 依据 |
|---|---|---|---|
| `select` | `PUT /proxies/asight-sw-<g> {name}`:开 = `asight-fb-<g>`,关 = `PASS` | 块已在 Verge 的运行时里 | [L4b C3] |
| `provider` | 写 `route-<g>.txt`,再 `PUT /providers/rules/asight-r-<g>` | 块已在运行时;sidecar 模式。服务模式下 Verge 把规则文件拷进服务目录,之后改原文件不生效 [L4b S5] | [L4b C1a] |
| `payload` | D29 的做法:读运行时配置,拼入或剥掉块,`PUT /configs?force=true {payload}`;整份配置只在内存 | 控制口接受这个写 | [L4b C2a]、D29 |
| `none` | 只写文件;回执写「已写入,未生效 · 去 Clash Verge → 订阅,点当前订阅重新激活」 | 上面三种都不行 | D29 兜底 |

- **选哪种**(`pickApply`):块已在运行时 → 单个组的开关用 `select` 加 `provider` 两把钥匙:关只要一把落地就算关,开要两把都落地 [L4b RS]。块不在运行时(首次 `on`;不带参数的 `off` 剥块之后再 `on`)→ `payload`。控制口不能写、或 `payload` 被拒 → `none`。
- **复核**:开 = 该组的 `now` 是 `asight-fb-<g>`,且规则提供者计数大于 0;关 = `now` 是 `PASS`,或计数为 0。读不到写「不知道」,`off` 因此退出 1。不再看 `GET /proxies` 里有没有 asight 的出站:关之后出站可能留在运行时,直到 Verge 下次重新生成 [L4b §5.1]。D29 的这一条只管旧采集。
- 顺序是默认值,[L4b] 量完按结果改(W30–W35)。

### 4.2 自带 mihomo

- 每次开关都向它自己的控制口 `PUT /configs?force=true` [E8]。
- 关 = 换成「只转发」配置:每个形态端口 `MATCH,asight-up-<g>`,没有 `asight-in-*`,引擎不在路径上。

### 4.3 off 保证(照 1.6 §1.2;例外如实写)

| 方式 | `off` 做什么 | 之后保证什么 | 例外 |
|---|---|---|---|
| `vpn-block` | ① 期望态写 off;② 每组 `select` 置 `PASS`、规则文件清空并刷新,复核;③ 不带参数的 `off` 另按 D28 剥 `Script.js` 里的块、删规则文件;④ 引擎按 1.6 §1.3 关在途连接 | 新连接不再匹配 asight 的规则,走用户自己的路;之后 asight 死了也不影响 agent | 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2)。Verge 运行时里留着不起作用的出站与组,到 Verge 下次重新生成为止;mihomo 的 `cache.db` 留一条 `asight-sw-*` 的选择记录(无害;asight 不改它的数据库)[L4b B10]。都列在回执与 `status` 里。控制口读不到:`off` 退出 1,写「asight 可能仍在 Clash 的路径上,去 Clash Verge 重新激活」;Verge 已退出:运行时不在,文件已撤,算做完 |
| `own-forwarder` | ① 期望态写 off;② 撤 agent 的代理入口(只撤 asight 写的值,1.6 §9.5);③ 自带 mihomo 换成只转发配置;④ 引擎关在途连接 | 新启动的 agent 直连原下一跳;引擎不在任何 agent 的路径上 | **`on` 期间启动、读了入口的 agent,重启前仍经自带 mihomo(只转发)**;它死了它们连不上。守护进程留在排空状态,监管 mihomo,直到这些进程都退出,再一起退出。`status`:「还有 N 个 agent 连着 asight 的转发,重启它们之后 asight 就完全退出」。`off --now`:立即停 mihomo,回执列出会断的 pid(操作者的显式意图)。这就是 §2.4 的冲突 |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各组的开关:VPN 块是 `select` 与规则文件;自带转发是 mihomo 配置里的子规则与 agent 的入口。块本身不重写。
- 块里的组按「已装且支持的形态」生成,与期望态无关。所以单个 harness 的开关不用重写块、不用 Verge 重新激活。新装了一个 harness 时,`on` 重写块(走 `payload` 或 `none`)。
- 用户后来自己把某个 agent 的代理指向了 Verge:它的组早在块里,新进程立刻经块,不用跑 asight 命令(§10.3)。
