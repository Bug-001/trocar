## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流不靠驱动:

- **VPN 块**(`vpn-block`):本机有 Clash Verge Rev 时,在它的全局脚本里加一个 asight 块。流量本来就进 Verge 的 agent,由块按进程交给 asight 引擎,引擎再交回 Verge,走用户自己的规则。
- **自带转发**(`own-forwarder`):没有可写的 VPN,或某个 agent 的流量不进 VPN 时,asight 把这个 agent 自己的代理入口指向 asight 自带的、只转发的 mihomo。mihomo 把 agent 进程交给引擎,其余照原路走。

开关与 off 保证照 1.6。采集到的数据与 Linux 同一格式。哪些字段随引流不同见 `capture` 与几个路径类字段(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1] |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了,块与转发回退到原路(§3.3) |
| 覆盖 | 所有形态 | 有自己代理入口的形态、跟随系统代理的形态;Verge 开 TUN 时全部 [E2][LT] |
| 身份 | 内核给 pid | 进程规则给形态;pid 尽力补(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。缺口如实写:既没有代理入口、又不跟随系统代理的形态,只在 Verge 开 TUN 时采得到;Claude Desktop 与 Kimi 的 VS Code 扩展因信任入口不支持(§6.4)。用户把 Windows 的两种方式叫「with vpn / with no-vpn」,与本单元一致。

- **`Redirector` 契约在 Windows 上**(追加写回 4.6):

  | 契约 | Windows |
  |---|---|
  | `attach()` / `detach()` | 按期望态打开 / 关掉各形态的引流(§4) |
  | `status()` | 从 Verge 与自带 mihomo 的控制口读实际态(§4.1 的复核) |
  | `lookup(peer)` | 不用:Windows 没有透明改写,引擎不开透明监听 |
  | `lookupIngress({peer, user, target})` | **新增**:代理入口的连接查元数据(§5.2) |
  | `watch(pid, verdict)` / `unwatch(pid)` | 按 pid 的解密判定表(§5.4) |
  | `heartbeat()` | 空操作:回退靠 mihomo 的健康检查(§3.3) |
  | `scan()` · `exec` / `exit` | 进程快照与差分(`procinfo.mjs`)。命令行晚到另有 **`facts-update`**(同一进程、命令行从「还不知道」变成 `ok` 或 `empty` 时发一次,事实里带 `cmdlineState`):按命令行认形态的(§2.3 的 `node.exe` + dsh、Z-Code)在「还不知道」时不判「不认」,收到 `facts-update` 再判一次;一直是 `empty` 写「不知道 + 原因」(D38)。`scan()` 与差分的基线谁先谁后都不漏:无基线时 `scan()` 自己先取 |
  | `directCount(pid)` | 套接字表里该 pid 不经 asight 的连接数;读不到报 `null` 与原因 |

- **助手**(`helper.mjs` · `helper.ps1`):一个常驻的 Windows PowerShell 5.1(`-NoProfile -NonInteractive -ExecutionPolicy Bypass -File`,不提权),守护进程经 stdin / stdout 的 JSON 行协议问它:`{id, verb, args}` → `{id, ok:true, data}` 或 `{id, ok:false, error}`。助手编完原生代码(`Add-Type`,C# 5)后先发一行 `{ready, proto:1, pid, ps, native}`,客户端在它之后才写请求,超时(默认 2 s;`ps` 是 10 s,第一次 `ps` 要经 CIM 读全部命令行)从写出算(冷机上编译要几百毫秒到几秒);超时的请求在助手(串行)答完它之前不再发同类的新请求,`procinfo` 跳过那一轮而不是排队。**只读,动词是闭集**(W1:客户端在 JS 里先拒绝未知动词,脚本里再核一遍;脚本只含 ASCII,5.1 把没有 BOM 的脚本按 ANSI 读):

  | 动词 | 参数 | 答 |
  |---|---|---|
  | `version` | — | `{proto, pid, ps, os, native, nativeError?, sessionId?}` |
  | `ps` | `{all?, cmdline?}`(默认只列助手所在会话的进程) | `{sessionId, procs:[{pid, ppid, name, exe, cmdline, startedAt, sessionId, integrity, tokenDenied}]}`。`startedAt` 是 Unix 纪元毫秒;`exe` · `cmdline` · `integrity` 读不到为 `null`;`integrity` ∈ `untrusted · low · medium · high · system · protected`;`tokenDenied` = 令牌打不开而映像路径读得到(§10.1)。命令行取自 CIM `Win32_Process`,每个进程只问一次(答案为空最多问三次),CIM 失败后 30 s 不再试;每次 CIM 调用 8 s 超时(短于客户端 `ps` 的 10 s,超时算一次 CIM 失败)。每行另带 `cmdlineState` ∈ `ok` · `pending`(问了、还没有答案) · `cim-backoff`(CIM 失败后的 30 s) · `empty`(问了三次都没有) · `not-asked`(`cmdline:false`):`cmdline:null` 在 `pending` / `cim-backoff` 时是「还不知道」,在 `empty` / `not-asked` 时是「没有」 |
  | `tcp-table` | `{pids?, remotePort?, localPort?, states?}`(过滤;全空 = 全部) | `{rows:[{pid, state, family, localAddr, localPort, remoteAddr, remotePort}]}`。v4 与 v6 都读,任一读不到就整个报错(半张表会让「恰好一个」建立在缺的数据上);`state` 用 MIB_TCP_STATE 的名字(`listen` · `established` · `close-wait` …) |
  | `reg-read` | `{hive, key, names}` | `{keyExists, values:{<名>:{kind, value}}}`,值不展开环境变量、`kind` 如实给(`REG_EXPAND_SZ` 还是它,§6.3)。**白名单**:`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(4.7 §3);`HKCU\Environment` 的 `Path`;`HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy` 的 `VerifiedAndReputablePolicyState`(Smart App Control)。白名单外、或不给名字(= 全读),拒绝 |
  | `net-if` | — | `{interfaces:[{id, name, description, type, up, index, addrs, gateways}]}`:.NET `NetworkInterface`,不经 CIM,不含 MAC |
  | `route` | `{dest?}`(默认 `1.1.1.1`) | `{dest, ifIndex, iface}`:去该 IPv4 地址会走的网卡(`GetBestInterface`,只查路由表,不发包) |
  | `token` | — | `{pid, elevated, elevationType, integrity, system, sessionId}`:助手自己的令牌(R7 的判据) |
  | `roots` | — | `{counts, certs:[{sha256, pem, stores}]}`:`CurrentUser\Root` 与 `LocalMachine\Root` 只读导出,按 DER 的 SHA-256 去重(约 430 KB,调用方放宽超时) |
  | `pipe-server` | `{name}` | `{exists, serverPid, exe, startedAt}`:以只读客户端打开该命名管道,问服务端 pid |

  - **失败的记法**:助手起不来(spawn 失败、退出、不发 ready、协议号不符、策略挡了脚本)= `helper-start-failed`(§12);`Add-Type` 编不过(策略、编译器被拦、临时目录写不了)时 ready 行带 `native:false` 与原因,助手仍在、仍答不需要原生部分的动词(`reg-read` `net-if` `roots` `version`),但记一条 `helper-start-failed`(带 `nativeError`),因为没有它就看不到进程、读不到连接表与令牌;这几个动词之后各自报 `native-unavailable`;起来之后死了 = 既有的 `helper-down`(带 `exit` 与 stderr 末 20 行,4.6)。每次死亡一条,在途的调用都拒绝;主动关掉不记。
  - **`ps` 与提权**(§10.1):`elevated` = 完整性 ≥ High,或令牌打不开而映像路径读得到(标「推断」)。映像路径读不到的进程不当 `exec`,报一次 `facts-error` 并列进 `unreadable()`(同 Linux 的 D-30)。同会话里「以其他用户运行」起的进程令牌也打不开,会被判提权(推断),它本来就不是本用户的 agent。

## 2. 引流方式与选择

### 2.1 三种

| 方式 | 流量怎么到 asight | asight 写什么 | 引擎的上游 | 什么时候用 |
|---|---|---|---|---|
| `vpn-block` | agent 的连接本来就进 Verge(跟随系统代理、Verge 开 TUN、或 agent 自己的代理指向 Verge);块里的进程规则把它交给 asight 引擎 | Verge 全局 `Script.js` 里一个哨兵块,加 Verge 数据目录里 asight 的规则文件(都入账,4.7 §4);**不写 agent 的网络设置**(1.6 §9.5) | 再进 Verge 的混合端口(CONNECT),走用户自己的规则;例外:用户点名 agent 映像的按进程规则不再匹配(再进的是引擎 `node.exe`),出口可能变,报 `egress-differs`(§3.4) | Verge 在跑、规则模式、`find-process-mode` 不是 `off`、控制口读得到、`Script.js` 写得进 |
| `own-forwarder`(§2.4) | agent 自己的代理入口改指 asight 自带 mihomo 的该形态端口;mihomo 把 agent 进程交给引擎,其余(agent 的子进程等)照原路 | agent 的代理入口(入账、先备份、`off` 撤)+ 自带 mihomo | 该形态原来的下一跳:直连,或用户原来配的代理 | 没有可写的 VPN;或有 VPN,但这个形态的流量不进它 |
| 不引流 | — | — | — | 两样都不行(没有代理入口、提权、形态不支持)。`status` 报原因码,`doctor` 给办法 |

- asight 从不开 TUN、不改 Verge 的模式、不改系统代理(D31④)。TUN 是用户在自己 VPN 里的选择,`doctor` 只说怎么开。
- 选择按形态做,一台机器上可以两种并存(下文称「混合」)。

### 2.2 按形态选(每次 `on` 重新选)

`route-plan.mjs` 的规则:

1. 读本机网络环境(4.7 探针):Verge 在不在跑、模式、`find-process-mode`、TUN、系统代理、控制口、`Script.js` 可不可写;别的代理软件与它的本地端口。`find-process-mode: off` 时块里的进程规则全部不起作用:当作「进不了 Verge」,原因码 `find-process-off`;asight 不改这个设置,`doctor` 给 `gui` 步骤(4.7 §5)。
2. 对每个期望为开、已安装、受支持的形态:
   - 它的连接进得了可写的 Verge(TUN 开着;或系统代理开着且它跟随;或它自己的代理指向 Verge 的端口)→ `vpn-block`;
   - 否则,它有文件里的代理入口,且自带转发已启用 → `own-forwarder`,上游 = 它原来的下一跳;
   - 否则 → 不引流,原因码见下表。
3. 结果写进安装清单(每个形态一条 `route` 项)与 `netenv.json` 的 `adopted.<harness>`(1.6 §9.5)。之后环境变了:`netenv-changed`,`status` 印 `asight on` 重新选;asight 不自己改(1.6 §9.5)。

| 本机网络 | 进得了 Verge 的形态 | 进不了、有代理入口 | 都没有 |
|---|---|---|---|
| Verge · 规则模式 · 系统代理开 · TUN 关 | 跟随系统代理的(及 agent 自己的代理指向 Verge 的)→ `vpn-block` | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 规则模式 · TUN 开 | 全部 → `vpn-block` [LT] | — | — |
| Verge · 规则模式 · 系统代理关 · TUN 关 | 只有 agent 自己的代理指向 Verge 的 | `own-forwarder`,上游直连 | `not-routed` |
| Verge · 全局 / 直连模式 | 块不起作用,不用块 | `own-forwarder`,上游 = 原下一跳(跟随者是 Verge 的端口) | `not-routed` + `clash-mode-bypass` |
| Verge 控制口读不到,或 `Script.js` 写不进 | 当作「别的代理软件」 | 同下一行 | `not-routed` |
| 别的代理软件(GUI.for.SingBox、v2rayN、Clash Party、FlClash……;asight 不往里写,4.7) | — | `own-forwarder`,上游 = 原下一跳(跟随者是那个软件的系统代理端口) | `not-routed` |
| 没有 VPN / 代理软件 | — | `own-forwarder`,上游直连 | `not-routed` |

- 自带转发没启用时(默认,§2.4),第二列一律变成 `not-routed`,`on` 的计划与 `status` 写「自带转发待你决定」。

### 2.4 自带转发

- **冲突**:1.6 §1.2 第四行与 §8 第二行(不让 agent 的代理字段指向 asight,做不到 off 保证);0.1 §5「提供做不到 off 保证的引流方式」(必拒)。
- **与被否决的做法的区别**:字段指向的是只转发、能退回直连的 mihomo,不是引擎。`off` 之后它只转发,不经引擎、不解密、不记录。
- **做不到的那部分(如实写)**:`on` 期间启动、读了入口的 agent,重启之前仍经 asight 的 mihomo;mihomo 死了,它们连不上,直到 mihomo 被拉起或 agent 重启(§4.3)。
- **定案之前**:代码照做、照测(W42 / W48 / W49 开着它跑);默认不提供,环境变量 `ASIGHT_OWN_FORWARDER=1` 才启用。`on` 的计划把本该走它的形态列为「不引流 · 自带转发待你决定」,并印一行怎么现在就试(`set ASIGHT_OWN_FORWARDER=1` 后再 `asight on`)。用户同意后默认改为开、留 `ASIGHT_OWN_FORWARDER=0` 作关闭开关,同 PR 改 1.6 §1.2 / §8 与 0.1 §5。
- **默认关的代价(如实写)**:没有 VPN 时 `on` 什么都不采;有 Verge 时只采 Hermes 与 Codex 的 HTTP(§2.2)。用户的目标「with vpn and with no-vpn」在默认配置下只做到前一半的一部分。评审(2026-10-07)建议默认开;它与上面的必拒冲突,列 OPEN 1。
- **启用时**:`on` 的计划与 `off` 的回执都印这条例外:「`on` 期间启动的 agent,`off` 之后重启之前仍经 asight 的转发(只转发)」(§4.3)。
- **另一种做法**:Verge 系统代理模式下,让 `on` 把不跟随系统代理的形态的代理入口指向 Verge 的端口(不指向 asight)。off 保证能做到,但 Verge 一退出这些 agent 就连不上,子进程的出口也跟着变。没有选它:它让 agent 依赖用户 VPN 的开关状态。

## 3. 规则块(Verge 与自带 mihomo 同一份代码)

设计来自 L4b 计划的 RS 方案(各项以 [L4b] 实测为准;回退部分见 §3.3)。生成器是纯函数 `src/netenv/mihomo/rules.mjs`,收到的只是数据(组、进程规则、端口、token),不认识任何 harness。

### 3.1 块里有什么

对每个组 `<g>`(§2.3「块里的组」;自带 mihomo 按形态):

| 名字 | 是什么 |
|---|---|
| `asight-in-<g>` | 出站,`type: http`,`server: 127.0.0.1`,`port: <引擎入口端口>`,`username: <路由>.<g>`,`password: <入口 token>`(§3.2) |
| `asight-re-<g>` | 回退出站,`type: http`,指向「再进入点」:Verge = 它的混合端口;自带 mihomo = 该形态自己的监听端口(§3.3) |
| `asight-fb-<g>` | 组,`type: fallback`,`proxies: [asight-in-<g>, asight-re-<g>]`,`url: http://127.0.0.1:<再进端口>/asight-health/<g>`(本机探测,§3.3),`interval: 30`,`timeout: 2000`,`lazy: true`;不设 `expected-status`(有回应就算活) |
| `asight-sw-<g>` | 组,`type: select`,`proxies: [PASS, asight-fb-<g>]`;第一个是 `PASS` = 默认关 |
| `asight-r-<g>` | 规则提供者,`type: file`,`behavior: classical`,`format: text`,`path: ./asight/route-<g>.txt`,`payload: [DOMAIN,asight-off.invalid]`(文件不在时什么都不匹配) |
| 规则(插在用户规则最前) | `AND,((DST-PORT,<再进端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT`(只为 `asight-re` 的探测,§3.3);每组一条 `RULE-SET,asight-r-<g>,asight-sw-<g>` |
| `route-<g>.txt` | 开 = 该组的进程规则(`PROCESS-PATH-REGEX,…`;harness 文件允许时另有 `PROCESS-NAME,…` 在后,§2.3);关 = 空文件 |

- **自带 mihomo** 另有:每个形态一个监听器(`listeners`,`type: mixed`,`127.0.0.1:<端口>`,`rule: in-<g>`),子规则 `in-<g>` = [`AND,((DST-PORT,<该形态端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT`,`RULE-SET,asight-r-<g>,asight-sw-<g>`,`MATCH,asight-up-<g>`];监听器的 `rule:` 子规则在 v1.19.32 上可用 [合约];`asight-up-<g>` = 该形态原来的下一跳(`DIRECT`,或用户原来的代理)。全局:`allow-lan: false`,不设 `tun`、`dns`,`find-process-mode: always`,控制口只听 `127.0.0.1` 随机端口、随机 secret。
- 名字一律 `asight-` 开头。Verge 的块包在 4.7 的哨兵里;块的代码整体 `try/catch`,出错就原样返回用户的配置(块不生效,复核时报出,4.7 §5)。

### 3.2 身份

- 出站凭据:`username = <路由>.<g>`(`vb.claude-code.cli`、`of.codex.cli` 这样),`password = 入口 token`。token 是每次安装随机的 32 位十六进制,存 `~/.asight/collector/ingress.json`(0600),`uninstall` 删。引擎验 token,不对回 407、记 `ingress-auth-failed`。
- 用标准的 `Proxy-Authorization` 同时带身份与鉴权,http 与 socks5 出站都支持 [E5];不用 `X-Asight-Agent` 头。
- 这是形态级身份,不带 pid;pid 尽力补(§5.3)。

### 3.3 asight 不在时回退(本机探测)

**原设计不成立(已删)**:原写「健康检查 `http://asight-health.invalid/<g>`,引擎本地答 `204`;再进点命中 `REJECT`,mihomo 回 `502` 算活」。真 mihomo 上两个成员都判死 [源码][合约]:
- http 出站的探测总是先 `CONNECT host:80`,再在隧道里发 `HEAD`(unified-delay 开时两次)[源码 `adapter/outbound/http.go`、`adapter/adapter.go`]。引擎照 §5.1 旧写法先连上游,`.invalid` 解析失败,回 `502` → `asight-in` 死。
- mihomo 的 http 入口在匹配规则之前就对 CONNECT 答 `200`;`REJECT` 是读即 EOF 的空连接,隧道里的 `HEAD` 拿到 EOF → `asight-re` 也死 [源码 `listener/http/proxy.go`、`adapter/outbound/reject.go`]。
- 两个都死时 fallback 留在第一个成员 `asight-in`:引擎一死,块引的流量全断(fail-closed)。

**现在的做法**:探测地址指向「再进点」自己,两个成员都能在本机答:

| | `asight-in-<g>`(经引擎) | `asight-re-<g>`(再进点) |
|---|---|---|
| 探测怎么走 | mihomo 对引擎入口发 `CONNECT 127.0.0.1:<再进端口>`(带 `<路由>.<g>` 与 token) | mihomo 对再进点发 `CONNECT 127.0.0.1:<再进端口>`;块的第一条规则 `AND,((DST-PORT,<再进端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT` 把它直连到再进点自己 |
| 谁答 | 引擎认出这个目标(§5.1):答 `200`,隧道里每个 `/asight-health/<g>` 请求答 `204`;不连上游、不记录 | 再进点的 http 入口收到相对路径的 `HEAD`,答 `400`、不外连 [源码 `listener/http/proxy.go`];不设 `expected-status`,有回应就算活 |
| 引擎死了 | 端口没人听,连接被拒 → 死 | 照样答 → 活 |

- **全程不出本机**:探测只到 `127.0.0.1`,不连任何外网地址,不用用户的出口。探测是 mihomo 按 asight 写的配置发的本机请求,不是对外的请求(不变式 1、D30)。用外网地址(如 `generate_204`)做探测被否决:每个间隔都经用户的出口发一次请求,等于 asight 自己发请求。
- **实测 [合约]**:引擎活着时两个成员都活,组选 `asight-in`;杀掉引擎后 2 s 内组改选 `asight-re`。引擎死后到来的那条 agent 连接没失败:mihomo 拨号被拒后立即做一次健康检查,隧道再拨一次就走了 `asight-re` [源码 `adapter/outboundgroup/groupbase.go` `onDialFailed`、`tunnel/tunnel.go` `retry`]。**这一条只在该组上一次健康检查已过去 1 秒以上时成立**,见下面「窗口期」。自带 mihomo 的形态监听器(带 `rule:` 子规则)同样成立。全程零外连。[合约] 是 `test/netenv/mihomo-contract.test.mjs`(W57),跑在开发机的 mihomo v1.19.32(darwin)上,重复 20 余次稳定;Windows 上的 Verge 2.5.7 与自带 mihomo 的复测见下面 [T0],产品落地后 W40 再测一次。
- **mihomo 发的字节 [合约]**:探测的 `CONNECT` 带 `User-Agent: Go-http-client/1.1`、`Proxy-Connection: Keep-Alive`、`Host`、`Proxy-Authorization`,**头的顺序每次不同**(Go 的 map 顺序),隧道里是一或两个 `HEAD /asight-health/<g>`(`unified-delay` 关 / 开)各带 `Host` 与 `User-Agent`。引擎与它的测试不能依赖头的顺序。夹具 `test/netenv/fixtures/mihomo-probe.bytes` 是其中一次的原样字节(再进点端口归一成 18000)。
- **窗口期**:引擎进程死了(端口关):下一条连接触发检查,连接本身由 mihomo 重拨 [合约]。**例外(量到的)**:mihomo 一秒内最多做一次组检查(`singleDo`)。引擎恰好在一次检查后 1 秒内死掉时,这条连接触发不了新检查,只能带退避地重拨已死的引擎:开发机 10 次里 9 次在 1.1–2.9 s 后经 `asight-re` 成功,1 次十次重拨用完、隧道在 mihomo 已答 `200` 之后被关,agent 看到连接断开并自己重试。组在窗口过后的**下一条连接**上翻到 `asight-re`(没有流量时要等下一个间隔,30 s);agent 会重试,所以流量一般有。这就是「fail-open」在第一条连接上的真实代价,`status` 与回执不得写成「引擎死了不影响任何连接」。引擎卡住(端口开着不答):最多一个间隔加超时(约 32 s),其间新连接超时、agent 自己重试。在途连接随引擎断(4.6 §Linux 机制「fail-open 两层」的同一代价)。守护进程活着时,组选了 `asight-re` 就写 `fallback-active`(失败类)。
- **实测 [T0](Windows)**:
  - **Verge 2.5.7**(sidecar;`unified-delay` 开,所以引擎一次探测连接里见 2 个 `HEAD`):引擎活着,两个成员都活,组选 `asight-in`;杀掉引擎后 552 ms 组改选 `asight-re`,其间的 18 条新连接 0 条失败、0 条超过 1 s;引擎回来后调一次 `GET /group/asight-fb-<g>/delay`(200),1 ms 内回到 `asight-in`;提供者列表里 `ruleCount` 为 1,`GET /providers/rules/<名>` 回 405;块的探测、再进点探测与 agent 的连接共 0 条离开 `127.0.0.1`。
- **`lazy: true`**:只在组被用过之后才定时探测。关着的组(开关在 `PASS`)、`off` 之后留在 Verge 运行时里的组都不探测。
- **引擎(重)启动之后**:组可能还停在 `asight-re`,要等下一次探测才回到 `asight-in`(最多一个间隔),其间不采。核心(重)载入配置时的第一次检查与规则提供者的载入赛跑,`asight-re` 也可能先被判死(开发机上见过一次),下面的刷新一并解决 [合约]。守护进程在引擎起来后对每个开着的组调一次 `GET /group/asight-fb-<g>/delay?url=<该组自己的探测地址>&timeout=2000`(地址必须与组的 `url` 相同,mihomo 按地址记活不活 [源码 `hub/route/groups.go`];控制口白名单内,只对 `asight-` 组;探测同样只到本机),立即刷新;复核读 `now`(§4.1)。
- **代价(如实写)**:用户的 Verge 开着 `unified-delay` 时,`asight-re` 的第二次 `HEAD` 撞上已关的连接,Verge 日志里每次探测多一行 error(「failed to get the second response」);不影响判活 [合约]。第一条 `AND … DIRECT` 规则让任何进程经 Verge 连 Verge 自己端口的连接直连(本来也是本机连接)。
- **两个前提**(W40 [WinVM]):mihomo 的回环检测只登记 DIRECT 出站,不拦 http 出站再进自己的入口 [源码 `component/loopback`];Verge 的混合端口不要鉴权(要的话回退失败,报 `reenter-auth`)。

### 3.4 防环路

- 块只用进程规则,不用域名规则。引擎是 `node.exe`,`node.exe` 不作任何组的引流键(dsh CLI 只走自带转发的专用端口),所以引擎再进 Verge 的连接不匹配任何组,走用户自己的规则。
- 生成时静态核对:每条进程规则都不匹配引擎的映像路径,也不匹配自带 mihomo 的映像路径;不过就不写块,报 `route-loop`。
- TUN 下照样成立与否,由 [LT] 量(W41)。
- **出口不同(`egress-differs`,1.6 §9.6)**:同一个原因的另一面。用户自己有点名 agent 映像的按进程规则(如 `PROCESS-NAME,codex.exe,<某组>`)时,再进 Verge 的是引擎 `node.exe`,那条规则不再匹配,agent 的出口可能变(目标是出口不变,1.6 §9.5)。检测:适配器读运行时规则 `GET /rules`(白名单内的读),只在内存里挑出 `PROCESS-*` 规则里匹配某个形态映像名或路径的,留下规则序号与类型,别的(含规则指向的组与节点名)当场丢掉;有就给该形态报 `egress-differs`(提示类),`doctor` 给办法(§10.4)。asight 不改用户的规则。W59。

### 3.5 整个进程都引过来(D40)与 `Code.exe`

- 进程规则把该进程的全部连接都交给引擎,含非模型流量 [E4]。D40:已信任的解密并逐字存;不能解密的透传并记录。
- **进程查找的代价**:块的规则排在用户规则最前,Verge 的 `find-process-mode` 是 `strict` 时,经 Verge 的每条连接(不只 agent 的)都要先查一次属主进程(L4:查找是惰性的,但只要有进程规则被求值就对所有连接查)。这是整机经 Verge 的连接的延迟,不是字节经过 asight(D31④ 仍成立)。代价没量过:W61 [WinVM] 量块开 / 关时 200 条连接的建连延迟 p50 / p99。
- `Code.exe` 不作引流键:引它等于把整个 VS Code 扩展宿主的流量都引过来(L4 实测 12 s 内 40 多次 `chatgpt.com`),D40 下还要解密别家扩展的流量。代价:Kimi 的 VS Code 扩展不被采集(它本来也信任不了 asight,§2.3)。

### 3.6 用户组的 `include-all`

- 用户的组带 `include-all` / `include-all-proxies` / `include-all-providers` 时,asight 的出站会被收进去。url-test 组会挑延迟最低的 `asight-in-*`(回环),把用户的全部流量交给 asight;`asight-re-*` 还可能绕成环 [L4b S8]。
- 块在生成配置时给这些组的 `exclude-filter` 追加 `^asight-`。只改 Verge 生成的运行时配置,不改用户的文件。它动的是用户组在运行时的成员。W45 [WinVM]。
- 自带 mihomo 没有用户组,不涉及。

## 4. 开与关

### 4.1 Verge:怎么生效(适配器的四种策略)

| 策略 | 做什么 | 何时可用 | 依据 |
|---|---|---|---|
| `select` | `PUT /proxies/asight-sw-<g> {name}`:开 = `asight-fb-<g>`,关 = `PASS` | 块已在 Verge 的运行时里 | [L4b 演练]:`PUT` 回 204,约 18 ms |
| `provider` | 写 `route-<g>.txt`,再 `PUT /providers/rules/asight-r-<g>` | 块已在运行时;sidecar 模式。服务模式下 Verge 可能把规则文件拷进服务目录,之后改原文件不生效(预期,[L4b] S5 未量) | [L4b 演练]:sidecar 下 `PUT` 回 204 |
| `payload` | D29 的做法:读运行时配置,拼入或剥掉块,`PUT /configs?force=true {payload}`;整份配置只在内存 | 控制口接受这个写 | [L4b 演练]:204,405–475 ms,约 437 KB;D29 |
| `none` | 只写文件;回执写「已写入,未生效 · 去 Clash Verge → 订阅,点当前订阅重新激活」 | 上面三种都不行 | D29 兜底 |

- **选哪种**(`pickApply`):块已在运行时 → 单个组的开关用 `select` 加 `provider` 两把钥匙:关只要一把落地就算关,开要两把都落地(预期,[L4b] RS)。块不在运行时(首次 `on`;不带参数的 `off` 剥块之后再 `on`)→ `payload`。控制口不能写、或 `payload` 被拒 → `none`。
- **复核**:开 = `asight-sw-<g>` 的 `now` 是 `asight-fb-<g>`,且规则提供者计数大于 0;关 = `now` 是 `PASS`,或计数为 0。计数读提供者**列表** `GET /providers/rules`,取 `providers["asight-r-<g>"].ruleCount`,列表里别的(用户的提供者名)当场丢掉:v1.19.32 没有 `GET /providers/rules/<名字>`,只有 `PUT`,读它回 405 [源码 `hub/route/provider.go`][L4b 演练]。另读 `GET /proxies/asight-fb-<g>` 的 `now`:守护进程活着而它是 `asight-re-<g>` → `fallback-active`(§3.3)。读不到写「不知道」,`off` 因此退出 1。不再看 `GET /proxies` 里有没有 asight 的出站:关之后出站可能留在运行时,直到 Verge 下次重新生成 [L4b §5.1]。D29 的这一条只管旧采集。
- **实测 [T0]**:30 s 以上的流与每 100 ms 一条的新连接同时跑,切换时新连接换路的延迟:Verge 上 `select`(`PASS` ↔ `asight-fb-<g>`)、清空 / 恢复路由文件并 `PUT /providers/rules/asight-r-<g>` 共四种,33–82 ms,1 s 之后没有一条还按旧状态走,在途的流(35 个块)一个没断;自带 mihomo 上同样四种加「`PUT /configs?force=true` 重载为只转发配置」,43–102 ms(两次),流(42 个块)一个没断。`payload`:块不在运行时,`PUT /configs?force=true` 204、78 ms、437,413 字节;剥块 204、64 ms,运行时里 `asight` 为 0。**顺序成立**:块在运行时用 `select` + `provider`,不在用 `payload`(W30–W35 在产品实现后复测)。切换时偶见一条新连接慢约 0.5 s;同样的延迟在不切换、只跑只读命令时也出现,是起命令本身的负载,不是切换的代价。
- **Verge 重启之后块没生效**:期望为开,`asight-sw-<g>` 的 `now` 却是 `PASS`(`cache.db` 被清,或用户关了 `store-selected`;也可能是用户自己在 Verge 里切的)。守护进程不自己切回(4.7 Goal「从不悄悄改回」),报 `vpn-block-not-live`(子因 `select-reset`),`status` 印 `asight on`。要不要让守护进程在「核心重启过」时自动重放 asight 自己的两把钥匙,列 OPEN 11。**[T0] 量过:会保住**。`store-selected`(Verge 默认开)时 `asight-sw-<g>` 的选择跨重启:块放在 `Script.js` 里,重启后块在运行时、`now` 起初是 `PASS`(没人选过);选 `asight-fb-<g>` 后再重启一次,`now` 仍是 `asight-fb-<g>`。`Script.js` 还原后逐字节回到原样(sha256 前 12 位 `d60fb84abefb`、96 字节),再重启一次,运行时里没有块。所以「重放」只在用户关了 `store-selected` 或清了 `cache.db` 时才有用(OPEN 11);W32 在产品实现后复测。Verge 读到的设置:`find-process-mode` 为 `strict`,`unified-delay` 开,`store-selected` 开,模式 `rule`,TUN 关,`allow-lan` 关。

### 4.2 自带 mihomo

- 每次开关都向它自己的控制口 `PUT /configs?force=true` [E8]。

### 4.3 off 保证(照 1.6 §1.2;例外如实写)

| 方式 | `off` 做什么 | 之后保证什么 | 例外 |
|---|---|---|---|
| `vpn-block` | ① 期望态写 off;② 每组 `select` 置 `PASS`、规则文件清空并刷新,复核;③ 不带参数的 `off` 另按 D28 剥 `Script.js` 里的块、删规则文件;④ 引擎按 1.6 §1.3 关在途连接 | 新连接不再匹配 asight 的规则,走用户自己的路;之后 asight 死了也不影响 agent | 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2)。Verge 运行时里留着不起作用的出站与组,到 Verge 下次重新生成为止;mihomo 的 `cache.db` 留一条 `asight-sw-*` 的选择记录(无害;asight 不改它的数据库)[L4b B10]。都列在回执与 `status` 里。控制口读不到:`off` 退出 1,写「asight 可能仍在 Clash 的路径上,去 Clash Verge 重新激活」;Verge 已退出:运行时不在,文件已撤,算做完 |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各组的开关:VPN 块是 `select` 与规则文件;自带转发是 mihomo 配置里的子规则与 agent 的入口。块本身不重写。别的 harness 的组的 `now`、`Script.js` 都不变(W55)。
- 块里的组按「已装且支持的形态」生成,与期望态无关。所以单个 harness 的开关不用重写块、不用 Verge 重新激活。新装了一个 harness 时,`on` 重写块(走 `payload` 或 `none`)。
- 用户后来自己把某个 agent 的代理指向了 Verge:它的组早在块里,新进程立刻经块,不用跑 asight 命令(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定:块与 mihomo 配置里写死它。端口被别的进程占了:守护进程不自己换(块与 mihomo 配置里写死了它),记 `engine-port-taken`(失败类),由块的回退接管(§3.3);不带参数的 `off` 之后再 `on` 才重选端口、重写块。`doctor` 给查占用者的命令与这两步(§10.4)。
- 认两种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)。别的开头:关掉,记 `ingress-unknown`。(原有的「绝对 URI 的 `GET http://asight-health.invalid/…`」已删:mihomo 的探测从不这样发,§3.3。)
- **健康探测**(§3.3):凭据对、目标恰是该组的再进点 `127.0.0.1:<再进端口>` 的 CONNECT 是 mihomo 的探测。引擎答 `200`,不连上游;隧道里每个 `HEAD` 或 `GET /asight-health/<g>` 答 `204 No Content`(`Content-Length: 0`,保持连接,unified-delay 会连发两次);别的请求关掉。不进 `flows/`、不写信封。测试夹具用 mihomo 实际发的字节(`CONNECT` 加隧道里的 `HEAD`,[合约] 录下)。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。
- 别的 CONNECT:引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。这里 CONNECT 是 mihomo 发给 asight 的,asight 就是被问的那个代理,回答它不算替别人回答。mihomo 早已对 agent 答了 `200`,上游失败时 agent 看到连接被关 [mihomo `listener/http/proxy.go`]。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §1.3)。
- **实现细节**:
  - 开头:一个连接 10 s 内读不全开头记 `ingress-unknown`(`reason` 写「没有开头」或「CONNECT 不全」);开头之前就走掉的连接不记(没有谁问过什么)。CONNECT 的目标不是 `host:port`(IPv6 要方括号)记 `ingress-unknown`。SOCKS5 的问候里没有用户名密码一项 → 回 `[5,0xff]`,记 `ingress-auth-failed`(`reason` 写「没有给用户名密码」);SOCKS5 的非 CONNECT 命令回 `07`,记 `ingress-unknown`。
  - 鉴权:token 先验、常数时间(两边先取 SHA-256 再比),验过才查 `lookupIngress`;查不到(`null`)= 用户名不认识,同样是 407 / SOCKS5 回 `02`,记 `ingress-auth-failed`。失败记录带 `peer` 与截短的用户名,**从不带 token**(对的错的都不带)。`lookupIngress` 抛错 → 回 `502` 与 `where:'engine'` 的 `loader-down`(或 `loader-timeout`),与透明入口查不到 redirector 时同一套码。
  - 健康隧道里每次读一个请求头,等不到下一个请求 30 s 后关(静默);收到的不是 `HEAD`/`GET /asight-health/<这个组>` 记 `ingress-unknown`(`reason` 写「健康隧道里的非探测请求」)并关掉。
  - 上游拨通之前客户端走了:销毁上游,不写连接行(没有 flow,什么也没丢)。上游成功之后到 `200` 之前不会有字节写给客户端。
  - `engine.close()` 先关掉不是 flow 的入口连接(握手中、健康隧道),再等 flow 收尾:它们不是 agent 的字节,留着只会让 `close()` 等到它们的空闲超时。
  - `engine.listen({port, hosts, ingress:{port}})` 返回 `{port, ingressPort}`;redirector 没有 `lookup`(Windows)就不开透明监听,`port:null`;要入口就要 redirector 有 `lookupIngress` 且 `createEngine` 给了 `ingressToken`,否则抛 `TypeError`。`engine.stats().ingress` = `{connections, flows, health, authFailed, unknown, refused, unreachable}`(`W42` 的「入口计数」),只在开了入口时有。


### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` 取组对应的 harness |
| `form` | 形态 id(如 `codex.app`);区分不了时为组名 |
| `capture` | `vpn-block` · `own-forwarder` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth_ref}` · `{kind:'socks5', host, port, auth_ref}`。VPN 块一律 `http` = Verge 的混合端口;自带转发按该形态接上时的原下一跳 |
| `pid_source` | `single-process` · `socket-table` · `null`(原有的 `forwarder-connections` 已删,§5.3) |
| `negKey` | 负缓存的键(§5.5) |

- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。
- **一条 agent 连接只拨一次上游**(评审 2026-10-07 后补):入口拨好的上游连接交给 `handleFlow` 用(每条连接一个包装,第一次取时给它,不再拨)。之后 4.6 的「让路」要重拨(解密不成改透传,把 ClientHello 原样发给新上游)时:上游不带凭据(直连、Verge 的混合端口)才重拨;上游带用户的代理凭据,就关掉这条连接,同 4.6 隧道连接的做法:asight 不主动再发一次用户的凭据(不变式 1)。W15。

### 5.3 pid 补全(尽力,不挡采集)

| 办法 | 何时用 | 怎么做 |
|---|---|---|
| 单进程 | 该形态此刻只有一个在跑的进程 | 就是它 |
| 套接字表 | 多个进程;系统代理或代理入口方式 | 助手查 `GetExtendedTcpTable` [E6]:该形态的进程里,有连到入口那一跳(Verge 混合端口,或该形态的自带端口)的连接(任何状态、任何一条)的进程**恰好一个** → 它;两个以上 → `null`。不再用「还没被认领的连接」:`on` 之前开的长连接、开关在 `PASS` 时开的连接永远不会被认领,这个判断会过期,把流量算到别的进程头上 |
| 从不 | — | Verge 与自带 mihomo 的 `/connections`、`/logs`:Verge 的含本机所有程序的连接元数据(4.7 §3.2);自带 mihomo 的也不用,上面的办法够了 |

- 预算 250 ms,与连上游并行。超时、不唯一、TUN 下多进程 → `pid:null`,按形态判(§5.4)。宁可 `null`,不可错:错的 pid 会让引擎解密一个不信任 asight 的进程的连接,把它弄断(§5.4 的承诺)。
- 超过预算不记失败(慢,不是不可用);读不到才记 `socktable-unavailable`,每次调用一条,由记录器折叠。`hop` 可带 `address` 收窄到该远端地址;不带时只比远端端口:真属主的那一行一定在表里,多出的行只会让答案变成「不唯一」,不会变成错的。助手只被问候选进程的行,答案在 JS 里再过滤一遍(助手不照做也不影响)。
- 在 Verge 块里,引擎的对端是 `verge-mihomo.exe`,不是 agent;上面的办法只看 agent 一侧到 Verge 端口的连接。这条路没量过:W43 [WinVM] 用真值核对(同一形态 3 个进程,2 个已信任、1 个未信任,200 条并发连接,另有 `on` 之前就开着的长连接),错认必须是 0。
- **代价**(观测者效应):多进程形态的新连接,首字节最多多等 250 ms。`flows/` 连接行记 `pid_ms`。常驻助手的一次表查询约 5 ms [E6];W43 [WinVM] 量 p50 / p90。
- 套接字表读不到(受限令牌、策略禁用 `Add-Type`)→ 一条失败事件 `socktable-unavailable`,之后全按形态判。

### 5.4 信任判定

- **有 pid**:照 4.6 §确认信任,按 pid 判:进程启动时间与入口的 `installed_at`、插件标记、Kimi shim 的父进程。
- **没有 pid**:按形态判。该形态在跑的进程**全部**已信任 → 解密;有一个未信任 → 透传,`not_captured:'untrusted'`,`reason:'pid-unresolved-mixed'`。这样 1.6 §1.1「`off → on` 后在跑的 agent 透传、不被弄断」在没有 pid 时也成立。代价:同一形态的新进程要等旧进程退出才被采集,`status` 点名旧进程。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(<路由>.<组>, host)`。不同形态、不同路由互不毒化 [E15]。
- 负缓存的失败事件与清除事件都带 `neg_key`(有 pid 时是 `"<pid>"`,没有时是 `"<路由>.<组>"`)。读取侧(`src/health/flows.mjs`)按 `(neg_key ?? pid, host)` 归并,清除按 `neg_key` 清;否则两个都没有 pid 的形态会撞在 `(null, host)` 上(评审 2026-10-07;写回 4.6 §记录)。W17。
- 条目只在内存:pid 退出、或该形态的进程全退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。下表写明哪几个字段随引流不同:

| 字段 | Linux eBPF | Windows `vpn-block` | Windows `own-forwarder` |
|---|---|---|---|
| `capture` | `transparent` | `vpn-block` | `own-forwarder` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` | 同左 |
| `proc.pid` | 内核给 | 尽力,可为 `null` | 同左 |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` | 同左 |

- 其余字段(请求与响应的原始字节、头、体、`host`、`scheme`、`endpoint`、`transport`、`ws_*`、`asight_added`、各种标注)MUST 逐字节相同。验收:同一 mock 调用分别经 Linux eBPF 与 Windows 两种引流,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?}`(不含凭据)。
- **代理前导**:入口收到的 CONNECT 是 mihomo 发的、带 asight 的 token,不是 agent 的字节;引擎发给上游代理的前导是 asight 写的。两者都不记成 `prelude`(4.6 的 `prelude` 只记 agent 自己发、代理自己答的字节;不变式 4)。连接行改记 `ingress` 与 `upstream`(含上游代理的回应状态码 `upstream.reply`)。所以 agent 自己配了代理时,Linux 的行有 `prelude`、Windows 的没有;W14 / W50 的比较只比信封,另比一次「直连上游」的连接行去掉上述字段后相等。
- 读取侧:`capture` 多两个值(改 4.1 信封表);观测者效应表(`src/dissect/harnesses.mjs`)对三种新采集器的值都适用;看板就地标引流方式;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

### 6.2 合并包(Windows)

- `combined-<harness>.pem` = Node 自带根(`tls.rootCertificates`)∪ Windows 根证书库的导出 ∪ 该 harness 自己配置里的用户 CA ∪ asight CA。

- **包里的每张证书都先用 Node 的 `X509Certificate` 解析一遍**,解析不了的丢掉、计数,回执与 `status` 各一行(「Windows 根里 N 张证书解析不了,没放进包」)。Codex 用 rustls,一张怪证书可能让它整包拒绝、哪都连不上;**[T0] 量过**(Codex 0.160.1 对本机 TLS mock,服务端证书由 asight 替身 CA 签):真导出的 Windows 根(`CurrentUser\Root` 265 张 + `LocalMachine\Root` 265 张,去重 261 张,433,748 字节,全部能被 .NET 解析)加替身 CA,Codex 连得上(`SSL_CERT_FILE` 与 `CODEX_CA_CERTIFICATE` 都认);只有根、没有替身 CA,连不上(90 s 里不停重连,一个请求也没到 mock);**根 + 一块解析不了的证书,连不上,坏块在替身 CA 之前或之后都一样:一块坏证书让整个包作废**。所以先过滤是必须的(上一条)。Node 的 `tls.getCACertificates('system')` 给 467 张,比两个根库去重后的 261 张多,守护进程与合并包取的是前者(Node 自己的系统集),这一差别的原因没细查。W20。

## 7. 守护进程、自启、控制面

- **守护进程** = `node <asight> daemon`。上游的信任集照 4.6 §引擎 第 5 步自己拼:Windows 系统库这一份由 `windowsRoots()` 给(Node ≥ 22.15 用 `tls.getCACertificates('system')`,更老的由助手只读导出,§6.2)。不加 `--use-system-ca`(原稿加了):那个选项要 Node ≥ 22.15,更老的 Node 上守护进程每次登录都以「bad option」退出;信任集已经自己拼了,选项是多余的。`on` 先查 `process.versions.node`,低于计划的下限(Node 20)就拒绝并给 `doctor` 一行。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(R7 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。
- **自启**:每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`(不用 S4U:S4U 不受 UAC 过滤,是 High 完整性)。动作 = `conhost.exe --headless "<node.exe>" "<asight.mjs>" daemon`(无窗口 [E20])。设置 = 失败后 1 分钟重启(最多 999 次)、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML`(经 `execTool`)注册并启用;不带参数的 `off` 停用;`uninstall` 删除。
- **「不需要管理员」没证实过**(如实写):测到的只是管理员账户的过滤令牌 [E20 的限定];标准用户能不能注册带登录触发器的任务、`RestartOnFailure` 能不能拉起被杀的守护进程,都没量。**[T0] 量过一半**(没有新建账户:创建账户只有操作者能做,所以**本地标准用户仍没量**)。以普通用户、Medium 完整性(管理员账户的过滤令牌,`IsInRole(Administrator)` 为假)从非提升进程跑:`schtasks /Create /XML` 注册成功(登录触发、本用户、`InteractiveToken`、不是 `HighestAvailable`——`schtasks /Query /XML` 对默认的 `LeastPrivilege` 不印 `RunLevel`、`RestartOnFailure` 都在);`/Run` 起来的进程在登录会话 2 里,父进程是 `conhost.exe`。**`RestartOnFailure` 拉不起被杀的守护进程**:杀掉守护进程(`node`)、杀掉任务自己的进程(`conhost --headless`)、守护进程自己以退出码 3 退出,三种各等 100 s(间隔设的 1 分钟),都没有被重新拉起;任务的 `Last Result` 分别是 0、-1、0,即 `conhost --headless` 把子进程的退出码吞成了 0。**所以任务只负责登录时拉起一次,崩溃后的重拉必须由监管父进程做**(见下一条,不再只是后备)。W47 在产品实现后在标准用户上补测。
- **自启的后备**:`schtasks /Create` 被拒绝 → `on` 自动改用 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的一项(值名 `asight-collector`,入账、先记原值,`off` / `uninstall` 只删这一项),动作同上,但 `asight daemon` 以「监管父进程」方式跑:一个小父进程拉起真正的守护进程,它退出就按 1、2、4…60 s 退避重拉。回执写「计划任务注册被拒,改用登录启动项」并给原因,事件 `task-register-failed`(失败类,但 `on` 不失败)。**[T0] 已显示计划任务拉不起被杀的守护进程**(上一条):监管父进程是默认做法,不只是计划任务注册被拒时的后备;任务的 `RestartOnFailure` 照写(多一层不坏),但不当作重拉的依据。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`。CLI 读它再连。名字随机,防同机别的用户先占一个固定名字。
- **文件权限**:Windows 上「0600」没有意义。asight 的文件都在 `%USERPROFILE%` 下,靠用户目录默认的 ACL(本用户、SYSTEM、Administrators);asight 不另设 ACL,单元测试在 win32 上不断言权限位。用 `icacls` 核一次(W26)。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:计划任务(或后备的监管父进程)拉起;其间 VPN 块与自带 mihomo 都回退到原路(§3.3)。

## 8. 自带 mihomo:来源、许可、监管

- **钉死版本**:`src/collector/arch/win32/mihomo-pin.json` = `{version, assets:{x64:{variant, name, url, size, sha256, exe:{name, size, sha256}}, arm64:{…}}, license:'GPL-3.0-only', source}`。首版钉 v1.19.32;只从 `https://github.com/MetaCubeX/mihomo/releases/download/<version>/` 取。变体写明:x64 用 `windows-amd64-compatible`(不挑 CPU 指令集),arm64 用 `windows-arm64`。压缩包与**解出来的 exe** 两个摘要都钉:实现时按发布页的 digest 填,两次独立下载、解压后核对一致才写进仓库。**[T0] 能钉的先钉**:发布页(GitHub API 的 `digest` 字段)给出的压缩包 `mihomo-windows-amd64-compatible-v1.19.32.zip` 22,525,067 字节、sha256 `974a4d7ad69aed27aa2e8f91d61113573c14dadb14562c63e58effabf59816f0`;`mihomo-windows-arm64-v1.19.32.zip` 20,194,736 字节、sha256 `7a4f6e58af9a120920935f2150cf642d945085fdb3e753314505b334234e1d1e`。**官方包本身没下载、没在 Windows 上跑**:下载并执行外部文件只有操作者能放行,T0 的执行者没有这个授权。核对那一次要做的是两次独立下载、`tar.exe -xf`、解出 exe 的大小与 sha256、Authenticode 状态、起一次;**exe 的大小与 sha256 因此仍待填**,`mihomo-pin.json` 的这两项实现前要跑。Verge 带的 `verge-mihomo.exe`(同为 v1.19.32 的 Windows 核心)**未签名**(`NotSigned`);拷成 `asight-forwarder.exe` 后在 Medium 完整性下起来、控制口答。
- **怎么拿到**:Windows 的发布包(4.5 GitHub Release)直接带它。npm 装的没有时,`on` 的计划列出「要下载 mihomo <版本>(<大小>,来自 <URL>,sha256 <值>)」,确认后才下载。这是 1.6 R8「CLI 不联网」的例外:操作者确认的、只连钉死地址的一次下载。核对 sha256,不符就删掉,记 `forwarder-digest-mismatch`;带 Authenticode 签名时另核签名者,不带时只认摘要。解压用系统自带的 `tar.exe -xf`(Windows 10 1803 起自带,能解 zip),解出来的 exe 再核一次摘要。
- **下载走用户的网络**:Node 的 `fetch` 不认系统代理,只能经 VPN 上 GitHub 的用户会下载失败。下载经本机的系统代理(读 `HKCU\…\Internet Settings` 的 `ProxyServer`;没有时用 Verge 的混合端口),用 Node 内建的 `http` 发 CONNECT,不加依赖;都不行 → 不下载,`doctor` 给一行手动下载的地址、放置路径与核对摘要的命令(`certutil -hashfile <文件> SHA256`)。
- **放哪**:`%USERPROFILE%\.asight\collector\bin\asight-forwarder.exe`(改名,进程名不与用户自己的 mihomo 撞),旁边放 `LICENSE-mihomo.txt` 与源码地址。GPL-3:独立的可执行文件,asight 不链接它,只经命令行与控制口用它;回执写明。
- **监管**:守护进程以分离方式拉起它(守护进程崩了它不跟着死),`forwarder.lock` 记 pid 与启动时间。守护进程重启时认领它:pid、启动时间、控制口 `GET /version` 三者都对得上。它退出了:按 1、2、4…30 s 退避重拉,每次一条 `forwarder-restart`;连续 5 次起不来 → `forwarder-down`(失败类)。起不来时先分类:Smart App Control 开着(同 §6.3 的注册表读法)→ 原因 `smart-app-control`,未签名的 `asight-forwarder.exe` 很可能被它拦了;别的照实记 `forwarder-start-failed` 加 errno。测到的环境里 `VerifiedAndReputablePolicyState` = 0(关)。关着,所以那个未签名的核心照样起来,这**证明不了**开着时也行;开着时的情形仍按 `smart-app-control` 处理,没测。asight 不因此改 agent 的设置(1.6 §9.5),`doctor` 给命令。
- **只在需要时跑**:没有形态走自带转发时不下载、不启动。
- 只转发与排空见 §4.3。

### 10.1 每一跳从哪读

| 跳 | 读什么 |
|---|---|

| 自带 mihomo | `forwarder.lock` + 它自己的控制口:各形态端口与上游 |

### 10.3 用户自己的代理(1.6 §9.5 在 Windows 上)

- **VPN 块**:不写 agent 的设置。用户把某个 agent 的代理指向 Verge 的端口:它的组早在块里,新进程立刻经块,不用跑 asight 命令;`status` 画出新的路,列「在跑的 pid 仍按启动时的设置,重启后按新的」。指向别处(公司代理、sing-box):它不进 Verge → `not-routed`;自带转发已启用时 `status` 印 `asight on <h>`。
- **自带转发**:`on` 把入口改指 asight 转发,原值记进清单的 `prior_value`(0600;`netenv.json` 只存哈希,1.6 §9.5)。用户之后改了这个键 → `proxy-changed`,失败类(asight 已被绕过);`status` 画新的路并印 `asight on <h>`;不在终端又没有 `--yes` 的 `on` 只出计划(1.6 R6)。`off` 时键仍是 asight 写的值才还原;用户改过就不动(1.6 V48)。
- 不加命令(1.6 §9.5、§8)。

## 验收(可跑 check)

单元测试走 `npm test`,沙箱 HOME,助手、`execTool`、网络、注册表都注入。[WinVM] 在 Windows 测试机上跑(脚本化);[L4b] / [LT] 是已计划的实验,结论回写 §3 / §4。现在都是**计划**,每条在实现 PR 里落成会变红的断言。

1. **W1 助手只读**:动词是闭集;未知动词报错;`helper.ps1` 里没有写动词(静态扫:`Set-ItemProperty` `New-Item` `Remove-` `netsh` `schtasks` `setx` `Register-`);**原生部分也扫**(PowerShell 动词扫看不到 `Add-Type` 里的 C#):`DllImport` 恰是 17 个只读函数(dll 与名字都对,不许 `EntryPoint`),`OpenProcess` / `OpenProcessToken` / `CreateFile` 只用读的访问掩码,C# 里没有文件、注册表、起进程、杀进程、写内存、网络;两种扫描都有植入的反例;助手死了 → `helper-down`,读法改报「不知道」。
2. **W2 进程差分**:注入两次快照:新 pid → `exec`,消失 → `exit`;同 pid 换了启动时间 = 一次 `exit` 加一次 `exec`;命令行先 `null`(`pending`)后到 → 一条 `exec`(带 `cmdlineState`)加一条 `facts-update`,不丢;监听器抛错与畸形行不丢这一轮其余的事件;先 `scan()` 后 `start()` 之间新建的进程是 `exec`,不被基线吞掉。
