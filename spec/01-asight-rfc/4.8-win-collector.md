## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流只有**代理模式**(D43):

- asight 让每个 agent 用 asight 自带的本地代理内核(钉死版本的 mihomo,改名 `asight-forwarder.exe`,下文称「内核」):`on` 把 agent 的代理入口指向内核里该形态所在组的监听端口。内核按进程把 agent 的连接交给引擎,别的(agent 的子进程等)只转发。
- 引擎的上游 = 没有 asight 时 agent 会走的那一跳:它自己的代理;否则它跟随且开着的系统代理;否则直连(§2.2)。用户的出口(节点、域名规则)不变。
- 内核从不开 TUN、从不当系统代理;asight 不往任何 VPN 产品里写东西(4.7 只读)。
- 只属于这个 agent 的入口,`on` 自动写;影响超出 agent 的(用户 PATH、快捷方式、证书库、VS Code 设置、机器级位置),由用户在 `on` 里按形态点名(1.6 §1.7,本单元 §2.4)。

开关与 off 保证照 1.6(代理模式的例外登记在 1.6 §1.2「例外二」)。稳健只做两件事——asight 自己足够稳健,用户能手动从命令行撤销 asight:监管与回退(§4.3、§8);`asight off [agent]` 在 asight 坏了时也能跑(§4.2)。采集到的数据与 Linux 同一格式。哪些字段随引流不同见 `capture` 与几个路径类字段(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1](标准用户上的自启没量过,§7);点名的证书库一项会弹 Windows 的确认框,机器级的点名项要用户自己给管理员权限(§2.4)。**自带内核也是未签名的 exe**:Smart App Control 开着时它可能起不来(§8 预检,OPEN 19);测到的只是它关着的情形 |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了,内核退回上游(§3.3);内核死了,守护进程拉起它,等不及就 `asight off <h>`(§4.3) |
| 覆盖 | 所有形态 | 有代理入口的形态:自动写的,或用户点名的(§2.3、§2.4) |
| 身份 | 内核给 pid | 监听端口与凭据给形态,进程规则分开 agent 与它的子进程;pid 尽力补(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。D43 又删掉了 VPN 块:它只对 Clash Verge Rev 写得进,Verge 升级两次弄坏同类的写法(D28、D29),切换要 552 ms,进程规则看不到提权的 agent、还会把同名的形态一起引过来 [E3][E7];而代理模式在实测里 16 个形态有 15 个到了 mock(L5),没到的那个是 Claude Desktop 的信任,不是引流。还采不到的形态如实写(§6.4)。用户原先的「with vpn / with no-vpn」两种叫法随之取消:VPN 只决定上游(§2.2)。

- **`Redirector` 契约在 Windows 上**(追加写回 4.6):

  | 契约 | Windows |
  |---|---|
  | `attach()` / `detach()` | 按期望态写入口,把内核里各形态切到开或只转发(§4)。**异步**:`attach` 先让内核读回「开」、之后才写代理入口,读不回就一条入口不写、带内核的码拒绝;`detach` 先切只转发并读回、再撤入口,切不了也照撤再拒绝(细则见下) |
  | `status()` | 从内核的控制口读实际态(§4.1 的复核),另带入口的复核:`{attached, links, hb_age_ms:null, drops:null, kernel, forwarder, entries}`;Windows 没有心跳与环形缓冲的丢包,两项给 `null` |
  | `lookup(peer)` | 不用:Windows 没有透明改写,引擎不开透明监听 |
  | `lookupIngress({peer, user, target})` | **新增**:代理入口的连接查元数据(§5.2);异步(要问套接字表) |
  | `watch(pid, verdict)` / `unwatch(pid)` | 按 pid 的解密判定表(§5.4) |
  | `heartbeat()` | 空操作:回退靠内核的健康检查(§3.3) |
  | `configure(enginePort)` | 空操作:守护进程在第一次 `on` 之前调它(4.6),Windows 没有内核程序要告诉引擎端口;内核配置的引擎端口来自 `ingress.json`,守护进程监听的就是它(评审 2026-10-07 晚:Windows 的 redirector 原先没有这个方法) |
  | `scan()` · `exec` / `exit` | 进程快照与差分(`procinfo.mjs`)。命令行晚到另有 **`facts-update`**(同一进程、命令行从「还不知道」变成 `ok` 或 `empty` 时发一次,事实里带 `cmdlineState`):按命令行认形态的(§2.3 的 `node.exe` + dsh、Z-Code)在「还不知道」时不判「不认」,收到 `facts-update` 再判一次;一直是 `empty` 写「不知道 + 原因」(D38)。`scan()` 与差分的基线谁先谁后都不漏:无基线时 `scan()` 自己先取 |
  | `directCount(pid)` | 套接字表里该 pid 不经 asight 的连接数(建立了的、且不是连到某个组的回环监听端口的);**异步**,答 `{count, error}`,读不到是 `count:null` 与原因,不是 0;调用方(守护进程的 `status()`)一律 `await` |
  | `form-exit` · `helper-error` | **新增事件**:一个形态的最后一个进程走了(`{form, neg_key:'of.<f>'}`,引擎清该形态的负缓存,§5.5);助手失败(`procinfo` 的 `poll-error`,`code` 取它的 `cause`) |

- **`redirector.mjs` 的细则**(W12 · W16 · W72):`createWin32Redirector({ helper, procWatcher, groups, home, ownerOf, routes, ingress, authOf, onFailure, forwarder, entries, gate, ownImages, hostsOf, carried, now })` 是一个 EventEmitter,不开 socket、不起进程、不写文件与注册表、不认识 harness(`groups` 是 `groupsOf(descriptors)` 交来的数据,静态扫描钉着)。内核、入口的写入方、属主查询、登录的解析、计划都是注入的,接线只在 `daemon.mjs`。
  - **进程表**装本会话的**全部**进程,不只是 agent 的:没有进程规则的形态(dsh CLI,§3.5)接下它端口上**任何**进程的连接,属主只能在全部进程里找。每个进程带 `matchForm` 的答案(`form` · `pending` · `path-unknown` · `none`;`home` 传 `%USERPROFILE%`)。`exec` / `facts-update` 入表,`exit` 出表并带走它的判定,形态的最后一个进程走了发 `form-exit`(在 `exit` 之后);`scan()` 之后,表里有、扫描里没有、又不是扫描开始之后才见到的进程当它已走。
  - **判定表**:`watch(pid, {decrypt, agent})` 存 tracker 对该 pid 的判定(§5.4);只有 `decrypt === true` 是信任,没判过的 pid 是「未信任」。接线在守护进程:tracker 每判完一个 pid 推给 `watch`,命令行晚到的形态在 `facts-update` 之后再判一次。
  - **`attach()`**:内核得到整份配置(`kernelGroupsOf`:计划有答案、有端口、有能带的形态、有上游可转的组;`auth:false` 的入口配带凭据的上游就不带;`on` 取自计划;关着的组只在 `carried` 里,见下面那条)→ `forwarder.reload` 读回 → **然后**才 `entries.write` 开着的组、`entries.undo` 计划说关的组。计划里没有答案的组既不写也不撤:计划还没出来,不能把入口撤了。内核起不来或读回不是所问(§4.1 的复核)→ 抛 Error,带 `code`(`forwarder-start-failed` · `forwarder-binary-missing` · `forwarder-digest-mismatch` · `fallback-active`)与 `readBack`,**一条入口都没写也没撤**,`on` 退出 1。某组的入口写不进是该组的 `{ok:false, reason}`,不抛;计划说 `on`、内核却不带的组(没有端口 `no-port` · 没有能带的形态 `no-supported-form` · 没有上游 `no-upstream` · 不收凭据的端口配了带凭据的上游 `login-on-open-port`)既不写也不撤,在 `entries.skipped: [{g, reason}]` 里说出来、`ok` 为假(D38:不静默地少采);崩在读回与入口之间,再 `attach()` 就是同一次重载与同一批入口(写入口的一方幂等)。
  - **`detach()`**:内核切只转发并读回(内核没在跑就不管:没有东西指着它)→ 所有组的入口撤销(计划里有没有都撤,撤的只是 asight 写的)。内核切不了、计划建不出来也照撤入口,之后才带内核的码抛出(`off` 永远手工撤,4.3)。
  - **`entries`** = `{ write(list), undo(list), check(list) }`,`list` 是 `[{g, harness, entry}]`(`write` 的 `entry` 是 `'auto'` 或 `'opt-in'`;`undo` 与 `check` 的列表里计划说关的组 `entry:null`),答 `[{g, ok, reason?}]`。Codex 与 Hermes 的入口并进信任入口写的那一块,那一道关(W19 的四个条件,计划 Task 8)是 `attach()` 的 **`gate({g, harness, entry}) → {ok, reason?}`**,必传(没传 `attach()` 抛 TypeError,不当作「都放行」):对要写的每个组问一次,拒绝的组不交给 `entries.write`,在 `entries.written` 里是该组的 `{g, ok:false, gated:true, reason}`(内核照样开着、`ok` 为假,回执说哪个组没指向 asight);`gate` 抛错算拒绝。redirector 不认识 harness,哪些组要关由守护进程的接线说(8(c)),写入方自己也可以拒绝(评审 2026-10-08:原先把这道关整个推给写入方,写入方没建时没有任何测试会因它红)。
  - **`kernelGroupsOf({ groups, routes, groupPorts, authOf, hostsOf, carried })`**(同文件导出):计划的答案变成 `buildForwarderConfig` 的 `groups`;**关着的组只在 `carried` 名单里才带**(装过 / 点过名,入口可能还在;没装没点名的组一个监听端口都不开,§2.2,审计 F7 → W77;名单由守护进程交,不传就是「没有」);组上游的登录在这里由 `authOf` 解进配置(除清单外,登录只在这里与 §5.2 的单条连接里出现);宿主进程树的形态没有 host 就拒绝(不然整个程序的连接都交给引擎,§3.5)。

## 2. 代理模式:入口与上游(D43)

### 2.1 一种模式

| | 是什么 |
|---|---|
| 流量怎么到 asight | 该形态的代理入口指向内核里它所在组的监听端口 `127.0.0.1:<端口>`(带凭据,§3.2);内核按进程把 agent 的连接交给引擎(§3.1),子进程等只转发 |
| asight 写什么 | 该形态的代理入口与信任入口(§2.3、§6)。只属于 agent 的,`on` 自动写;影响超出 agent 的,用户点名才写(§2.4)。都入账、先备份、`off` 撤(1.6 R2)。**代理入口就是引流,所以 MUST 在内核已按该形态读回「开」之后才写**(1.6 R9:挂引流最后;信任入口先写):内核起不来(找不到或摘要不符、Smart App Control、端口被占)时一个代理入口也不写;`off` 反过来,先把内核切成只转发并读回,再撤入口(§4.1)。W12 |
| 引擎的上游 | §2.2 的规则。内核里每个组一个 `asight-up-<g>` 出站(只转发与回退用它),引擎拨的是同一个上游(§5.2) |
| 什么时候不采 | 形态没有能用的入口、要点名而没点名、agent 提权、跟随的系统代理是 PAC:`status` 报原因码,`doctor` 给办法(§10) |

- 内核从不开 TUN、不当系统代理,不改系统代理与 VPN 的任何设置(D31④ · D43);只有指向它的 agent 经过它。
- 用户的 VPN 开着 TUN 时,引擎直连的上游照旧被 TUN 收进去,出口与 agent 原来一样。
- 用户的 VPN 看到的连接来源是 asight(内核或引擎的 `node.exe`),不是 agent:它点名 agent 的按进程规则不再匹配,域名规则照旧。D43 定只标一句,放在一处:`status <h>` 印一行(1.6 §9.2);`on` 的计划里不重复。

### 2.2 上游规则(每次 `on` 定;系统代理变了守护进程跟上)

D43:asight 的出口 = 没有 asight 时 agent 会走的那条路。`upstream.mjs` 按序取:

1. **agent 自己的代理**:`on` 写入口之前,该形态入口里的原值(harness 文件 `proxy` 声明的键;记进清单的 `prior_value`,0600)。别的进程的启动环境读不到(§10.1),登录环境只读 `HKCU\Environment` 里的代理变量(只读;点名也不写,D43)。**读不到的一种**(评审 2026-10-07 后补):只设在你终端里、由这个终端起的 agent 才会用的代理(没写进任何文件或 `HKCU\Environment`),asight 看不见;这个形态的上游会按 2、3 算,出口可能与关掉 asight 时不同。所以凡上游按 2 或 3 算出来的形态,`on` 的计划与 `status <h>` 在上游那一行注明「读不到你终端里的 HTTPS_PROXY」;`asight on` 自己的环境里有 `*_PROXY` 时(值打码)计划多一行提示:agent 若从这个终端起,它的上游可能不是下面写的。不为它另设码(OPEN 20)。
2. 否则,该形态**跟随系统代理**(harness 文件 `proxy.systemProxy`)且系统代理开着:`ProxyServer` 里的那一项(按协议分写的取 `https=`,没有就取通用的一项);目标命中 `ProxyOverride` 的直连(译成绕过表,见下)。系统代理是 PAC(`AutoConfigURL`)→ 不接这个形态,`not-routed`(asight 不执行 PAC)。**「是 PAC」这一判断是假设**:`AutoConfigURL` 里有非空的地址就算 PAC,不管 `ProxyEnable`(4.7 用同一条);关掉「使用设置脚本」之后注册表里的旧地址会不会留着没量过(标志在 `Connections` 那个二进制块里,不在助手的白名单上),OPEN 27。旧地址若留着,手动代理开着加一个过期脚本地址的用户,所有跟随者会是 `not-routed` · `system-proxy-pac`:失败得安全,给的原因却不对。
3. 否则**直连**。用户开着 TUN 或别的 L3 VPN 时,由系统照旧送进去。

| 本机网络 | 跟随系统代理的形态 | 不跟随的 | agent 自己配了代理的 |
|---|---|---|---|
| Verge · 系统代理开 · TUN 关(规则、全局、直连模式都一样) | 系统代理 `127.0.0.1:7897` | 直连 | 它自己的代理 |
| Verge · TUN 开 | 系统代理开着时同上;关着时直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| v2rayN · 系统代理开 | v2rayN 的本地端口 | 直连 | 它自己的代理 |
| 别的 TUN VPN · 系统代理关 | 直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| 没有 VPN | 直连 | 直连 | 它自己的代理 |
| 系统代理是 PAC | 不接 · `not-routed` | 直连 | 它自己的代理 |

- **一个形态只有一个上游**。原本分两路的,接上后都走那一个:Codex 的 HTTP 跟随系统代理、WebSocket 直连 [E2][E16],接上后 WebSocket 也经系统代理,报 `egress-differs`(提示,1.6 §9.6)。
- 上游不能是 asight 自己的端口(内核的监听端口、引擎入口):`on` 不接这个形态,报 `route-loop`(原值多半是上次 `on` 没撤干净留下的)。
- **系统代理变了**(开、关、换端口):守护进程在 5 s 核对里读 `Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(§9),重算跟随它的形态的上游,重载内核配置(§4.1),写一条 `netenv-change`;不碰 agent 的设置,不算失败(1.6 §9.5)。**重算后的答案(去掉 `hint`)与 `last` 相同的变化不重载内核**:助手忙着一次慢的 `ps` 时,2 s 的 `reg-read` 会超时,读不到算一次变化、读回来又算一次(§2.2「读与盯」),上游其实没动,不该为它重载两次(`hint` 的出现与消失只改 `status` 的字)。W71。
- `on` 之后系统代理改成 PAC:上游留在上一次的值,报 `system-proxy-pac`(提示);要按 PAC 走就 `asight off <h>`(OPEN 17)。
- **agent 自己的代理变了**(入口不再是 asight 写的值):agent 已绕过 asight,`proxy-changed`,`status` 印 `asight on <h>`(1.6 §9.5、§10.3)。
- 带凭据的上游:凭据只在清单与内核配置里(0600),只用于这个 agent 的连接(§5.2,D30)。
- **绕过表**(评审 2026-10-07 后补):没有 asight 时,命中系统代理的 `ProxyOverride` 的目标、或命中 agent 自己代理的 `NO_PROXY`(同一入口里的原值,harness 文件 `proxy.noProxyKey`)的目标,agent 是直连的(内网模型网关常见)。所以每个组带一张绕过表:`<local>`(没有点的主机名)· `*.corp.com`(后缀)· `10.*` 一类(IP 段)· 精确主机。译不了的写法(中间带通配符等)不进表,`status` 写「N 条绕过规则 asight 读不懂,按走上游处理」(OPEN 21)。命中绕过表的目标:交给引擎时由引擎直连(`lookupIngress` 按 CONNECT 目标判,§5.2),只转发时由内核直连(§3.1 子规则 ②⑤)。这些连接照常被采集,出口还是 agent 原来的那一跳。
  - **译法**(`translateBypass(文本, 'wininet' | 'no-proxy')`):`ProxyOverride`(`;` 分隔)里 `<local>` → `local`;`*.corp.com` → `domain-suffix`;`10.*` · `10.1.*` · `10.1.2.*` → `ip-cidr`(`/8` · `/16` · `/24`),四段齐全 → `/32`(地址字面量不会被域名规则命中);裸主机名 → `domain`(WinINET 里它只命中自己)。`NO_PROXY`(逗号或空白分隔)里裸名与前导点 → `domain-suffix`(curl、Go、Python、undici 都把它读成该域与其子域),`10.0.0.0/8` 一类的 CIDR → `ip-cidr`;`<local>` 不是 NO_PROXY 的写法,CIDR 不是 WinINET 的。名字 `localhost` 另加一行 `ip-cidr 127.0.0.0/8`:内核自带的 hosts 表在规则求值前已把它换成 127.0.0.1(§3.1 末),只有名字永远命中不了。两边的 `*.corp.com` 都读成后缀,也盖住 `corp.com` 本身(WinINET 自己不盖:已知的、只会多直连的差别)。读不懂的不进表、计入 `untranslated`:名字中间的通配符、端口、协议头、`*`、IPv6(`::1`、`[::1]`、IPv6 段;规则生成器只有 IPv4 的 `IP-CIDR`)、`<-loopback>`、生成器不收的名字。每一行都过 `bypassRuleOf`,所以用户的任何写法都不会让内核配置抛错;同一行说两遍只算一行。`bypassHit(表, 目标)` 是引擎(`lookupIngress`)与内核的规则文本共用的一份判法:`local` = 没有点的名字(IP 字面量除外),后缀按点的边界,范围只收 IPv4 字面量(测试用同一张表对两边各判一遍)。
- **上游的协议**(W5):`http://`、`socks5://`、`socks5h://`(后两者同一种:都把域名交给代理解析)接得上。`https://`(到代理那一跳是 TLS)与 `socks4` 等 v1 不支持:`on` 不接这个形态,`not-routed`,doctor 码 `proxy-unsupported`(1.6 §9.6)并写明协议,不悄悄改走别的出口(OPEN 21)。
- **`upstream.mjs` 的细则**(W5 · W71):`upstreamFor({ group, prior, noProxy, systemProxy, hkcuEnv, ownPorts, envNames, branches, last })` 每组一个答案 `{ kind, host, port, credentialed?, auth_ref?, source, egressDiffers?, hint?, reason?, why?, protocol?, bypass, untranslated, envUnreadable, unknown? }`;`reason`(`not-routed` · `route-loop`)时没有 `kind`:没有可拨的。
  - **读法**:不带协议头的 `host:port` 按 HTTP 代理读(curl 与 Python 的客户端也这样读);端口缺省 http 80、socks5 1080;IPv6 去掉方括号;含空白或控制字符的值不读(URL 解析器会悄悄吞掉换行,读出半个值)= `not-routed` · `upstream-unparseable`;**规则生成器不收的地址也不读**(判的是生成器自己那条检查,`upstreamOf`,不另抄一份:`http://a,b:3128` 的 host 带逗号,URL 解析器放行、生成器抛,放进去就是每次 `on` 与每次重载都抛),同为 `upstream-unparseable`。`planRoutes` 给出的上游,生成器一律收:用户的任何一行代理设置都不会让 `on` 失败。`https://`、`socks4`、`socks4a`、不带 5 的 `socks`、别的协议头 = `not-routed` · `upstream-protocol` 带 `protocol`(doctor 码 `proxy-unsupported`)。
  - **凭据是引用**:答案里没有用户名与口令,`credentialed:true` 加 `auth_ref`(`prior:<组>` = 清单里这个组入口的 `prior_value`,`hkcu-env:<变量名>`);`proxyAuthOf(解出的文本)` 是读它们的唯一一处。系统代理的 `ProxyServer` 里带凭据 = `not-routed` · `upstream-unparseable` · `detail:'credentials-in-system-proxy'`(WinINET 不从这个值取凭据,读了就不是没有 asight 时那个客户端)。
  - **`ProxyServer`**:`https=` 的那一项优先,其次是不带协议名的那一项,与它们的先后无关;两者都没有而有 `socks=` → `not-routed` · `upstream-protocol` · `socks`(WinINET 对 `socks=` 的用法没量过,v1 不跟);只有 `http=` `ftp=` 一类 → 直连(WinINET 不代理 HTTPS,asight 也不);`ProxyEnable` 不是开(没有值也算关)→ 不看 `ProxyServer`;开着而没有任何一项 → 直连。
  - **登录环境**:只在入口没有原值时读,取 harness 的 `proxy.env` 里按它的顺序第一个有值的(只认 `HTTPS_PROXY` `HTTP_PROXY` `ALL_PROXY`,值名不分大小写);它的 `NO_PROXY` 跟着它,入口里的 `NO_PROXY` 优先。读不到(助手超时等)→ 答案的 `unknown` 里一项 `{what:'login-environment', reason}`,规则照常往下走。
  - **`egressDiffers`** 只在上游是系统代理、该组 `followsSystemProxy.http` 为真而 `ws` 为假、**且 harness 的 `proxy.branches` 含 `ws`** 时出(组的数据里 `ws:false` 既可能是「WebSocket 不跟」也可能是「没有 WebSocket」,只有分支表说得清;Hermes、Claude Desktop、Kimi 扩展没有 WebSocket 分支,不报)。
  - **系统代理读不到**(助手超时、被拒):跟随者 = `not-routed` · `why:'system-proxy-unreadable'` · `detail:<原因>`,不当「直连」猜;不跟随的组不受影响。**`on` 之后**的变化带 `last`:系统代理变成 PAC 或读不到时,跟随者留在 `last` 的上游并带 `hint:'system-proxy-pac'` / `'system-proxy-unreadable'`(OPEN 17);`last` 不是上游(没有 `kind`)就没有可留的,照旧 `not-routed`。
  - **自己的端口**:回环地址(`localhost`、`::1`、`127.0.0.0/8`)加 `ownPorts` 里的端口 = `route-loop`;适用于入口原值、登录环境与系统代理三处。
  - **读与盯**(同在 `upstream.mjs`,只读):`readSystemProxy({helper})` 读 `Internet Settings` 的四个值 → `{ok:true, enable, server, override, autoConfigUrl}`(`enable` 只有类型是 `REG_DWORD`、值是 1 才是 true,是 0 才是 false;文本 `"1"` 或别的类型、别的数都是 null,与没设一样当关,WinINET 怎么读一个文本的 `ProxyEnable` 没量过,OPEN 27;没设的值是 null;键不在 = 全 null,也算读到了),`readHkcuEnv({helper})` 读登录环境的四个代理变量 → `{ok:true, values}`(只收设成非空文本的);读不到 = `{ok:false, reason, detail}`,`reason` 取 1.6 §9.4 的闭集:助手超时 `timeout`、助手不在了 `absent`、被拒或出错 `denied`、答案不是注册表读 `unparseable`;两个读取器从不抛。`watchSystemProxy({helper, everyMs: 5000, initial})`:第一次读是基线、不发事件(调用方已经读过就传 `initial`,免得两次读之间的变化被吞进基线);四个值任何一个变了(只 `ProxyOverride` 变了也算),或由能读变成读不到、或反过来,发一次 `change {before, after, changed}`(读不到时 `changed` 是四个名字全列);连续读不到不算变化;上一次读还没回来时下一拍等它、不重复读;**有一次 `reg-read` 超时而助手还没答它时(`helper.abandoned('reg-read') > 0`)跳过这一拍**(§1:助手是串行的,超时的请求在它答完之前不再发同类的新请求,不然只是排在它后面、同样超时;`procinfo` 对 `ps` 同样;还没有基线时基线也等助手空下来再读);`stop()` 之后不再读不再发,在途的那次读丢掉;监听器抛错不影响别的监听器、交给 `onError`。守护进程(计划 Task 8)据此用 `upstreamFor({systemProxy: after, last})` 重算跟随者的上游、重载内核。`ProxyOverride` 是用户自己的内网主机清单:`probe.mjs` 的 `detect()` 不复制它,不进 `netenv.json`。
- **`route-plan.mjs` 的细则**(W5):`planRoutes({ netenv, groups, desired, optIns, manifest, ctx, procs, last })` 把 `upstreamFor` 的答案与入口的门放在一起,每个组一个结果,键是组 id;`groupsOf(descriptors)` 把各 harness 的 `desc.win32` 摊成 `[{ g, harness, group, forms, proxy }]`(没有组的形态,如 `hermes.desktop`,不在任何一组里)。
  - **输入**:`netenv` = `{ systemProxy, hkcuEnv, ownPorts }`,即 `readSystemProxy()` 与 `readHkcuEnv()` 读到的、加 asight 自己的端口(内核的监听端口、引擎入口、控制口);**`ownPorts` 必传**,缺了抛 `TypeError`(看不见环路的计划不是计划),它不是 4.7 的 `netenv.json`(那一份不复制 `ProxyOverride`,绕过表要用它)。`desired` = `state.json` v2 的 `harnesses`(没有的 harness 算关)。`optIns` = 用户点名、asight 有记录的组或形态 id(点名一个组里的任一形态就是点名这个组)。`manifest` 与 `ctx` 给 `priorOf`;`procs` = `[{ pid, match, elevated }]`,`match` 是 `matchForm` 对这个进程的答案;`last` = `{ <组 id>: 该组上一次的结果 }`(`planRoutes` 自己的返回值就行):**只有上一次 `on:true` 的组才有可留的上游**,上一次关着或没接上的组的 `answer` 只是「若接上会拨到哪」的算式、不是它拨过的:用户在那之后把系统代理改成 PAC 再 `asight on`,不能把这个组接到用户已经不用的上游(`not-routed` · `system-proxy-pac`,与没有 `last` 时相同)。守卫在 `planRoutes` 里、不靠调用者筛;传进来的不是结果(没有 `on`,例如把 `answer` 当 `last`)抛 `TypeError`,不静默当成「没有可留的」。
  - **原值从哪读**(§2.2 ① 与 §10.1 写的两处是同一件事):`priorOf({ harness, group, ctx, manifest })`。清单里有这个组入口的记录(**按 harness 与入口认**:该 harness 写的、键或变量是代理键、不是同一文件里信任入口的;**不按 `files(ctx)` 认**——那份列表跟着调用者的环境走(`CODEX_HOME`、`CLAUDE_CONFIG_DIR`、在跑的 codex),重算上游的守护进程的环境不是跑 `on` 的那个 shell 的,按列表认会让后者写过的文件在前者眼里没有记录)时,`prior_value` 就是原值,**哪怕是 null**:用户原来没有代理,文件里现在是 asight 自己的地址,不去读文件;同一个文件有两条记录时取最早的(它记着用户原来有的,后一条记的是 asight 自己先前的地址)。没有记录就读文件:第一次 `on`,内核配置要先有上游,而入口要等内核读回之后才写(§2.1)。有多个文件(每个 Codex home、每个 Hermes profile 一个)时,先按清单里的先后看有记录的文件,再按组列文件的顺序看调用者的 `files(ctx)` 里没有记录的,取第一个有代理的。文件读不到或解析不了是「不知道」:`unknown: [{ what:'agent-proxy', reason:'denied' | 'unparseable', detail? }]`(原因取 1.6 §9.4 的闭集,`detail` 是 errno,不带路径),别的文件照读。**只有 `proxyEntry.kind:'file'` 的组有原值**;点名项的入口(策略值、shim、启动器、应用设置)由写它们的那一步入账(Task 14),所以点名了的 `claude-code.desktop` 与 `z-code.desktop` 的上游在 Task 14 接上之前不看它们已有的代理设置。原值可能带用户的凭据:它只交给 `upstreamFor` 与解 `auth_ref` 的人,不进任何输出。
  - **结果**:`{ g, harness, entry, on, reason, code?, why?, detail?, protocol?, upstream, bypass, untranslated, envUnreadable, egressDiffers?, hint?, unknown?, forms, answer }`。`entry` = `'auto'`(asight 自己写:agent 自己的文件)· `'opt-in'`(用户点了名)· `null`;`on` = `entry` 不是 null(内核里这个组的形态走引擎);`upstream` 是 `{ kind, host?, port?, credentialed?, auth_ref?, source }` 或 null(没有可拨的),**关着的组也算——但只在它装过、点过名**(它的入口可能还在,内核替关了之后还活着的 agent 转发到它;守护进程把这份名单交给重定向器,不传就是「没有」)。**没装过、也没点过名的组,内核一个监听端口都不给它开**:没点名的 Claude Desktop 的免鉴权端口是最尖的那例——一个没有任何用户在后面的开口(2026-10-08 审计 F7;也不进 `entries.skipped`,计划已经说了它为什么关);`answer` 是 `upstreamFor` 的原答案(带绕过表,没有凭据),守护进程靠它比「系统代理动没动上游」,它所在的结果下一次当 `last[g]`(接上的组才留)。`egressDiffers` 只在组接上之后出(「接上后」,§2.2)。
  - **`reason` 的先后**就是用户能动手的先后:`desired-off`(这个 harness 关着)→ `opt-in-needed`(点名项没点名)→ 上游的 `not-routed`(`why`:`system-proxy-pac` · `system-proxy-unreadable` · `upstream-protocol`(`protocol`)· `upstream-unparseable`)或 `route-loop`(`detail` 是 `host:port`)→ `form-unsupported`(收不了凭据的入口配了带凭据的上游)。都没有 = null,组接上。`code` 是 doctor 的名字,与 `reason` 同,只有 `upstream-protocol` 是 `proxy-unsupported`。
  - **形态的结果**:`forms[<形态 id>] = { reason, elevatedPids?, unknownPaths? }`:`reason` 先取组的(组里每个形态都一样),没有就看进程:这个形态有提权的进程 → `elevated-agent`(完整性或令牌读不到的 `elevated:null` 不算;内核同为 Medium,认不出它,只转发,§10.2 行 h),否则有进程的映像认得、路径没测过 → `form-path-unknown`(**路径认不出是哪个形态,所以那个映像的每个候选形态都带这条路径的形状**,形状已被 `matchForm` 遮了用户名)。这两条不改组拿到的入口与上游:接上的组里,只是那个进程没被采。`pending`(命令行还没来)与不是 agent 的进程什么也不算。

### 3.1 内核里有什么

对每个**开着、或装过 / 点过名而关着**(§2.2)的受支持入口组 `<g>`(§2.3)与组里的每个形态 `<f>`(评审 2026-10-07 后改:原先把组当形态,读同一个入口文件的形态共用不了端口):

| 名字 | 是什么 |
|---|---|
| `asight-l-<g>` | 监听器,`type: mixed`,`listen: 127.0.0.1`,`port: <该组端口>`,`users` = [`<g>` 与 `re.<g>`,口令都是监听口令](§3.2;收不了凭据的专用端口不设,§3.2),`rule: in-<g>` |
| `in-<g>` | 子规则,按序:① `AND,((DST-PORT,<该组端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT`(只为 `asight-re` 的探测,§3.3);② 绕过表的再进版:每条绕过(§2.2)一行 `AND,((IN-USER,re.<g>),(<绕过规则>)),DIRECT`,没有绕过就没有;③ `IN-USER,re.<g>,asight-up-<g>`(回退再进来的连接直接走上游);④ 开着时组里每个形态一行:该形态的进程规则 → `asight-fb-<f>`(没有进程规则的形态,组里至多一个,放在 ④ 的最后:`MATCH,asight-fb-<f>`);⑤ 每条绕过一行 `<绕过规则>,DIRECT`(只转发的连接在这里直连;交给引擎的连接由引擎按目标直连,§5.2);⑥ `MATCH,asight-up-<g>` |
| `asight-in-<f>` | 出站,`type: http`,`server: 127.0.0.1`,`port: <引擎入口端口>`,`username: of.<f>`,`password: <入口 token>` |
| `asight-re-<g>` | 回退出站,`type: http`,指向该组自己的监听端口,`username: re.<g>`,`password: <监听口令>`(§3.3) |

- 绕过规则的写法(`<绕过规则>`):`DOMAIN-SUFFIX,<后缀>` · `DOMAIN,<主机>` · `IP-CIDR,<段>,no-resolve` · `DOMAIN-REGEX,^[^.]+$`(`<local>`)。**嵌在 `AND` 里的 `IN-USER` 与 `DOMAIN-REGEX` 已在真核心(v1.19.32,darwin)上量过(计划 Task 7,W72 [合约]):载入,并且绕过目标在只转发与再进两种路径上都不到上游代理**,所以不需要「不带 `AND` 的写法」那条退路。两处写法要紧:① 写成独立规则行(⑤ 与目标)时 `no-resolve` 在目标之后(`IP-CIDR,<段>,DIRECT,no-resolve`);在目标之前核心读不了,**那个监听器整个缺席**,不报错;`AND` 里面没有目标,写 `IP-CIDR,<段>,no-resolve`。② 再进连接的目标若是名字,要能被解析才到得了 `DIRECT`;`localhost` 在核心的内置 hosts 里,到规则求值时它已经是 `127.0.0.1`、名字没了,所以 `<local>` 的 `DOMAIN-REGEX` 对它不起作用(测试不要拿它当名字目标;要让 `localhost` 与别的回环目标直连得另有 IP 规则:翻译表已定(§2.2「译法」),名字 `localhost` 另加一行 `ip-cidr 127.0.0.0/8`,再进的 `localhost:<端口>` 到 ② 时已是 `127.0.0.1`,由这一行直连。**这一前提在真核心上量过**(`mihomo-contract.test.mjs` 里一条用 `translateBypass('localhost', 'wininet')` 自己的答案:回退接上、再进的 `localhost:<端口>`,有范围行 = 不到上游,只有名字行 = 走上游;mihomo v1.19.32)。

- 组里没有开着的形态时:子规则只有 ① ② ③ ⑤ ⑥(没有绕过表就没有 ② ⑤),没有 `asight-in-<f>` 与 `asight-fb-<f>`,引擎不在它的路径上。全部关着时文本里没有引擎端口与入口 token。一个组里的形态同属一个 harness,所以同开同关。
- 全局只有:`mode: rule`、`bind-address` 与每个监听器都是 `127.0.0.1`、`allow-lan: false`、`find-process-mode: always`、`log-level: warning`(连接行会写出用户访问的主机,不要)、`profile.store-selected: false`、`geo-auto-update: false` 加 `geox-url` 全指向 `127.0.0.1:9`(不下载数据库)、控制口 `127.0.0.1:<端口>` 与 secret(端口与 secret 每次由调用方随机给)。不设 `tun`、`dns`、`unified-delay` 和任何别的入站;各端口(控制口、引擎、各形态)互不相同。
- 名字一律 `asight-` 开头。文本是 JSON(YAML 的流式写法):核心读得了(W57),测试不要 YAML 库。文本含控制口 secret、两个口令与上游的凭据:守护进程写 0600、不进日志。
- 进程规则只在 asight 自己的监听器上求值,所以进程查找的代价只落在经内核的连接上,不碰别的程序。
- 形态的端口:首次 `on` 在 17991–18989 里给每个组选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定(agent 的入口里写死它)。被占了:那个监听器开不了,报 `forwarder-start-failed`(`reason:'port-taken'`,带端口);不自己换端口(agent 的入口里写死了它),不带参数的 `off` 之后再 `on` 才重选。`ingress.json` 的内容:`{enginePort, groupPorts:{<组>:端口}, ingressToken, listenerToken}`(0600,先写临时名再改名);已有的端口与口令之后每次原样复用,新组得新端口、旧的不动,`on codex` 只点名一部分组也不丢别的组的端口;引擎端口在 17990–18989、组端口在 17991–18989、互不相同,选的时候向 `isFree` 问(`127.0.0.1` 与 `::1`),一个区间没有空闲口 → `EADDRINUSE`、不写文件。文件信不过(不是 JSON、端口越界或重复、口令不是 32 位十六进制或两个相同)→ 整份重来并告诉调用方原因(`regenerated`):各组的入口里写着旧端口,所以调用方 MUST 在内核读回之后重写**所有**已装的代理入口(§4.1),不能只写这次点名的。不带参数的 `off` 与 `uninstall` 删这个文件。

### 3.2 身份

- **agent 到内核**:代理入口的 URL 带用户名与口令(`http://<g>:<监听口令>@127.0.0.1:<端口>`);HTTP 代理客户端都在第一个请求就带 Basic 凭据 [E5]。不带凭据,内核回 `407`;凭据不对或用户名不认识,内核回 **`403`**(真核心 v1.19.32 上量出来的,计划 Task 7 的 [合约];引擎自己的入口仍是 `407`,§5.1)。两种都不碰上游,引擎入口与上游零连接(W70)。监听口令是每次安装随机的 32 位十六进制,与入口 token 不同,存 `~/.asight/collector/ingress.json`(0600),`uninstall` 删。
- **收不了凭据的入口**(Claude Desktop 的 `egressProxyUrl` 只收地址):该形态一个专用端口,不设 `users`。这时本机任何进程都能用这个端口,所以它的上游 MUST 不带凭据;上游要凭据时不接这个形态,报 `form-unsupported`,原因写明(另一种做法见 OPEN 25)。W70。
- **内核到引擎**:出站凭据 `username = of.<f>`(如 `of.claude-code.vscode`:同组的 `claude-code.cli` 是 `of.claude-code.cli`,引擎因此不靠 pid 就分得出),`password = 入口 token`。引擎验 token,不对回 407、记 `ingress-auth-failed`。用标准的 `Proxy-Authorization` 同时带身份与鉴权,不用 `X-Asight-Agent` 头。
- 这是形态级身份,不带 pid;pid 尽力补(§5.3)。

### 3.3 asight 不在时回退(本机探测)

读法(评审 2026-10-07 后补):下文 §3.3 与 §5.1 里的 `asight-in-<g>`、`asight-fb-<g>`、`of.<g>`、`/asight-health/<g>` 在组里有多个形态时,都读作按形态 `<f>` 的那个(§3.1);再进点 `asight-re-<g>`、`re.<g>`、监听口令按组。

**原设计不成立(已删)**:原写「健康检查 `http://asight-health.invalid/<g>`,引擎本地答 `204`;再进点命中 `REJECT`,mihomo 回 `502` 算活」。真 mihomo 上两个成员都判死 [源码][合约]:
- http 出站的探测总是先 `CONNECT host:80`,再在隧道里发 `HEAD`(unified-delay 开时两次)[源码 `adapter/outbound/http.go`、`adapter/adapter.go`]。引擎照 §5.1 旧写法先连上游,`.invalid` 解析失败,回 `502` → `asight-in` 死。
- mihomo 的 http 入口在匹配规则之前就对 CONNECT 答 `200`;`REJECT` 是读即 EOF 的空连接,隧道里的 `HEAD` 拿到 EOF → `asight-re` 也死 [源码 `listener/http/proxy.go`、`adapter/outbound/reject.go`]。
- 两个都死时 fallback 留在第一个成员 `asight-in`:引擎一死,引过来的流量全断(fail-closed)。

**现在的做法**:探测地址指向「再进点」自己,两个成员都能在本机答:

| | `asight-in-<f>`(经引擎) | `asight-re-<g>`(再进点) |
|---|---|---|
| 探测怎么走 | 内核对引擎入口发 `CONNECT 127.0.0.1:<再进端口>`(带 `of.<f>` 与入口 token) | 内核对再进点(该组自己的监听端口)发 `CONNECT 127.0.0.1:<再进端口>`(带 `re.<g>` 与监听口令);子规则的第一条 `AND,((DST-PORT,<再进端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT` 把它直连到再进点自己 |
| 谁答 | 引擎认出这个目标(§5.1):答 `200`,隧道里每个 `/asight-health/<f>` 请求答 `204`;不连上游、不记录 | 再进点的 http 入口收到相对路径的 `HEAD`,答 `400`、不外连 [源码 `listener/http/proxy.go`];不设 `expected-status`,有回应就算活 |
| 引擎死了 | 端口没人听,连接被拒 → 死 | 照样答 → 活 |

- **全程不出本机**:探测只到 `127.0.0.1`,不连任何外网地址,不用用户的出口。探测是 mihomo 按 asight 写的配置发的本机请求,不是对外的请求(不变式 1、D30)。用外网地址(如 `generate_204`)做探测被否决:每个间隔都经用户的出口发一次请求,等于 asight 自己发请求。
- **实测 [合约]**:引擎活着时两个成员都活,组选 `asight-in`;杀掉引擎后 2 s 内组改选 `asight-re`。引擎死后到来的那条 agent 连接没失败:mihomo 拨号被拒后立即做一次健康检查,隧道再拨一次就走了 `asight-re` [源码 `adapter/outboundgroup/groupbase.go` `onDialFailed`、`tunnel/tunnel.go` `retry`]。**这一条只在该组上一次健康检查已过去 1 秒以上时成立**,见下面「窗口期」。自带 mihomo 的形态监听器(带 `rule:` 子规则)同样成立。全程零外连。[合约] 是 `test/netenv/mihomo-contract.test.mjs`(W57),跑在开发机的 mihomo v1.19.32(darwin)上,重复 20 余次稳定;Windows 上的 Verge 2.5.7 与自带 mihomo 的复测见下面 [T0],产品落地后 W40 再测一次。**T5 起合约测试载入的是生成器自己的输出**(`buildForwarderConfig`,当时还有 VPN 块用的 `buildBlock`;自带内核那一形态在 Mac 上只叠了认人的设置:监听器要用户名、`asight-re` 带再进用户、`find-process-mode` 关,因为替身与引擎是同一个进程,进程规则分不开它们),并增加三条:带点的组 id(`claude-code.cli`,产品的 id 都带点:监听器名、子规则名、出站与组名、提供者名、探测路径、入口用户名里都有)整套再跑一遍;生成的「只转发」与「开」配置文本**原样**载入真核心(选择在 `PASS`、组在、提供者读到路由文件、引擎不在时组改选 `asight-re`、没有引擎出站、家目录里没有数据库;`PASS` 开关与路由文件 D43 起不用,开关改为重载整份配置,§4.1)。开发机 v1.19.32(darwin)上 8 条全绿;录下的探测字节与生成器出的出站一致。

### 3.4 防环路

- 内核的进程规则只匹配 agent 的映像。生成时静态核对:每条进程规则都不匹配引擎的映像路径,也不匹配内核的映像路径;不过就不出配置,报 `route-loop`。`buildForwarderConfig()` 用 `ownImages`(引擎与内核的映像路径)自己做这项核对,不过抛 `RouteLoopError`(`code:'route-loop'`、`rule`、`imageIndex`)。**`ownImages` 必传**:漏传抛 `TypeError`(2026-10-07 评审:曾经漏传就悄悄不核对);只有没有引擎可环回的夹具才明写 `ownImages: null`。进程名按基名、路径与正则都不分大小写、正则不锚定(与 mihomo 一致,读得更宽)。组 id 只含字母、数字与 `. - _`(它是 Basic 用户名与探测路径的一部分,不含 `:`);进程模式里有逗号、换行或内联标志(`(?i)`)的拒收。
- 上游不能是 asight 自己的端口(§2.2):`upstream.mjs` 核对,命中就不接这个形态,报 `route-loop`。
- 用户的 VPN 开着 TUN 时,引擎与内核的直连照旧进 TUN,再由用户的规则出去;asight 的端口都在 `127.0.0.1`,TUN 不收回环,不成环(W41)。
- 用户的 VPN 看到的来源是 asight,不是 agent(§2.1 末):按进程点名 agent 的规则不再匹配,点名 asight 自己进程的规则会改变上游的出口。两样都只有那一行,不另设码,也不去读 VPN 的规则找它们(只在合适位置标一句;OPEN 24)。

### 3.5 整个进程都引过来(D40)与宿主进程树

- 进程规则把该进程经内核的全部连接都交给引擎,含非模型流量 [E4]。D40:已信任的解密并逐字存;不能解密的透传并记录。

## 4. 开与关

### 4.1 怎么生效

- 每次开关都向内核自己的控制口 `PUT /configs?force=true`,换成新的整份配置 [E8]:开的形态有 ③,关的形态只有 ② 与 ④。没有选择开关,没有规则文件。
- **实测 [T0]**:自带内核上「重载为只转发配置」与 30 s 以上的流、每 100 ms 一条的新连接同时跑:新连接换路 43–102 ms(两次),1 s 之后没有一条还按旧状态走,在途的流(42 个块)一个没断。
- **配置文本(T5,W12)**:`buildForwarderConfig({ groups, enginePort, token, listenerToken, controller, ownImages })`。`groups[]` = `{ g, port, upstream, bypass, auth, on, forms: [{ f, rules, hosts }] }`:`rules` 是该形态的进程规则(没有进程规则的形态为空,组里至多一个),`hosts` 只有宿主进程树里的形态有(§3.5),`bypass` 是 §2.2 的绕过表,`auth:false` 是收不了凭据的专用端口(§3.2)。每个组一个监听器 `asight-l-<g>` 与子规则 `in-<g>`,每个形态一个 `asight-in-<f>` 与 `asight-fb-<f>`(§3.1)。
- **复核**:重载之后读回。开 = `GET /proxies/asight-fb-<f>` 在、`now` 是 `asight-in-<f>`;关 = 不在。守护进程活着而 `now` 是 `asight-re-<g>` → `fallback-active`(§3.3)。读不到写「不知道」,`off` 因此退出 1。重载与内核被监管重拉之后,守护进程刷新每个开着的形态的探测(§3.3)。
- 内核不在(还没拉起、监管重拉中):`on` 拉起它再重载;`off` 只撤入口,内核起来时读到的就是只转发的配置。
- **`on` 的次序**(W12):信任入口 → 找到并核对内核、拉起它(§8)→ 载入配置并读回「开」→ 代理入口(§2.1)。读不回、内核起不来:一个代理入口也不写,回执写原因,`on` 退出 1;崩在任一步之后再 `on` 续完(1.6 R9)。`redirector.attach()` 做的就是后两步(实现:`redirector.test.mjs`,W12 次序:入口先于读回的变异与「不 ok 也写」都红)。`off` 反过来:内核切只转发并读回 → 撤代理入口 → 撤信任入口与点名项。

### 4.2 off 保证(照 1.6 §1.2;例外如实写)

| `off` 做什么 | 之后保证什么 | 例外(1.6 §1.2「例外二」) |
|---|---|---|
| ① 期望态写 off;② 内核里这些形态换成只转发并读回;③ 撤代理入口与信任入口(只撤 asight 写的值,1.6 §9.5)与点名项(机器级的印提权命令,§2.4);④ 引擎按 1.6 §1.3 关在途连接 | 新启动的 agent 走原来的路;引擎不在任何 agent 的路径上 | **`on` 期间启动、读了入口的 agent,重启前仍经内核(只转发,不经引擎、不解密、不记录)**;内核死了它们连不上。守护进程留在排空状态,监管内核,直到这些进程都退出,再一起退出。`status`:「还有 N 个 agent 连着 asight 的内核,重启它们之后 asight 就完全退出」。`off --now`:立即停内核,回执列出会断的 pid(操作者的显式意图)。`uninstall` 遇上排空:照 `--now` 停它,等它退出(最多 5 s)再删 `asight-forwarder.exe`;仍删不掉(文件被占)→ 留下文件,回执写原因与「重启电脑后再跑 `asight uninstall`」,退出 1 |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。
- **监管父进程先停**(评审 2026-10-07 后补):不带参数的 `off` 与 `uninstall` 要停守护进程时,先停监管父进程(核对 `supervisor.lock` 的 pid 与启动时间后停,经 `execTool`),再停守护进程;顺序反了,父进程会把刚停的守护进程拉回来,「之后没有 asight 进程」(1.6 §1.4)就不成立。守护进程排空完以退出码 0 退出,父进程随之退出(§7)。独立撤销同样先停父进程。
- 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2 第一条例外)。
- **独立撤销**:守护进程不在、源码也不在时,独立副本 `~/.asight/bin/asight-off` 做同样的撤销(1.6 R3;`src/off/win32.mjs`)。先停监管父进程。内核还在跑:经它的控制口切成只转发(凭 `forwarder.lock` 与配置里的 secret);控制口不答就停掉它。两种都在回执里写「没有守护进程替它排空」并列出连着它的 pid。W54。

### 4.3 稳健:用户的两句话

稳健只守两条:trocar 自己足够稳健,且用户随时能手动从命令行撤销 trocar。只做这两件,不另加机制:

1. **稳健**:守护进程监管内核(§8:退避重拉,连续 5 次起不来报 `forwarder-down`);监管父进程监管守护进程(§7)。引擎不在时内核退回上游(§3.3),agent 照常连通、不被采,`status` 照实写。W40 · W49。
2. **命令行撤销**:`asight off [agent]` 在守护进程坏了、源码不在时也能跑(§4.2 独立撤销)。内核死了、agent 连不上时,`doctor` 给的第一条就是它(1.6 §9.6 `forwarder-down`)。撤了之后重启那个 agent,它就不经 asight。W54 · W55。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各形态的子规则与入口;重载整份配置,别的形态的监听器、子规则与上游逐字节不变,在途连接不断 [T0](W55)。
- 新装了一个 harness:`on` 给它的形态选端口、加监听器。
- 用户自己改了某个 agent 的代理:`proxy-changed`,`on <h>` 把新值记成上游再指回内核(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定:内核配置里写死它。端口被别的进程占了:守护进程不自己换,记 `engine-port-taken`(失败类;触发点是 `engine.listen` 的 `EADDRINUSE`,由守护进程接线处写;W73),由内核的回退接管(§3.3);不带参数的 `off` 之后再 `on` 才重选端口。`doctor` 给查占用者的命令与这两步(§10.4)。
- 认两种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)。别的开头:关掉,记 `ingress-unknown`。(原有的「绝对 URI 的 `GET http://asight-health.invalid/…`」已删:mihomo 的探测从不这样发,§3.3。)
- **健康探测**(§3.3):凭据对、目标恰是该组的再进点 `127.0.0.1:<再进端口>` 的 CONNECT 是 mihomo 的探测。引擎答 `200`,不连上游;隧道里每个 `HEAD` 或 `GET /asight-health/<f>` 答 `204 No Content`(`Content-Length: 0`,保持连接,unified-delay 会连发两次);别的请求关掉。不进 `flows/`、不写信封。测试夹具用 mihomo 实际发的字节(`CONNECT` 加隧道里的 `HEAD`,[合约] 录下)。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。
- 别的 CONNECT:引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。这里 CONNECT 是内核发给 asight 的,asight 就是被问的那个代理,回答它不算替别人回答。mihomo 早已对 agent 答了 `200`,上游失败时 agent 看到连接被关 [mihomo `listener/http/proxy.go`]。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §1.3)。
- **实现细节**:
  - 开头:一个连接 10 s 内读不全开头记 `ingress-unknown`(`reason` 写「没有开头」或「CONNECT 不全」);开头之前就走掉的连接不记(没有谁问过什么)。CONNECT 的目标不是 `host:port`(IPv6 要方括号)记 `ingress-unknown`。SOCKS5 的问候里没有用户名密码一项 → 回 `[5,0xff]`,记 `ingress-auth-failed`(`reason` 写「没有给用户名密码」);SOCKS5 的非 CONNECT 命令回 `07`,记 `ingress-unknown`。
  - 鉴权:token 先验、常数时间(两边先取 SHA-256 再比),验过才查 `lookupIngress`;查不到(`null`)= 用户名不认识,同样是 407 / SOCKS5 回 `02`,记 `ingress-auth-failed`。失败记录带 `peer` 与用户名,**从不带 token**(对的错的都不带):用户名只在形如 `of.<形态>` 且不含 token 时照写(截短),否则写占位 `(not a route name)`——客户端把 token 放进了用户名一栏、或给了没有冒号的凭据,都不能让它落进 `flows/`;`lookupIngress` 抛错时 `reason` 里的用户名同此。`lookupIngress` 抛错 → 回 `502` 与 `where:'engine'` 的 `loader-down`(或 `loader-timeout`),与透明入口查不到 redirector 时同一套码;**例外**:抛的错带 `code:'upstream-unavailable'`(redirector 说「拨不通上游」:没有登录、没有可拨的上游)→ 同样回 `502`,记 `where:'ingress'` 的 `upstream-unavailable`(带 `why`),不记 `loader-down`:后者在 `helper` 一类,doctor 会让读的人去重启助手,而这里与助手无关。
  - 健康隧道里每次读一个请求头,等不到下一个请求 30 s 后关(静默);收到的不是 `HEAD`/`GET /asight-health/<这个组>` 记 `ingress-unknown`(`reason` 写「健康隧道里的非探测请求」)并关掉。
  - 上游拨通之前客户端走了:销毁上游,不写连接行(没有 flow,什么也没丢)。上游成功之后到 `200` 之前不会有字节写给客户端。
  - `engine.close()` 先关掉不是 flow 的入口连接(握手中、健康隧道),再等 flow 收尾:它们不是 agent 的字节,留着只会让 `close()` 等到它们的空闲超时。
  - `engine.listen({port, hosts, ingress:{port}})` 返回 `{port, ingressPort}`;redirector 没有 `lookup`(Windows)就不开透明监听,`port:null`;要入口就要 redirector 有 `lookupIngress` 且 `createEngine` 给了 `ingressToken`,否则抛 `TypeError`。`engine.stats().ingress` = `{connections, flows, health, authFailed, unknown, refused, unreachable}`(`W42` 的「入口计数」),只在开了入口时有。

### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` 取形态对应的 harness |
| `form` | 形态 id(如 `codex.app`),取自 `of.<f>`:组里每个形态在内核里有自己的出站(§3.1),所以不靠 pid 也知道是哪个形态 |
| `capture` | `proxy` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth_ref}` · `{kind:'socks5', host, port, auth_ref}`。按该组的上游规则(§2.2);CONNECT 目标命中该组的绕过表时是 `{kind:'direct'}`(§2.2,W72)。`lookupIngress` 把 `auth_ref`(清单里的 `prior_value`)解成 `auth:{username, password}` 交给入口;入口只在拨这一条 agent 连接的前导里用它,交给 `handleFlow` 的 meta 里只剩 `credentialed:true`,凭据不进 flow、不进任何记录 |
| `pid_source` | `single-process` · `socket-table` · `null`(原有的 `forwarder-connections` 已删,§5.3) |
| `negKey` | 负缓存的键(§5.5)。`lookupIngress` 没给时入口自己补:有 pid 取 `"<pid>"`,否则取认证用的 `of.<形态>`;不补的话没有 pid 的连接会共用 `null` 一个键,互相毒化 |

- **`lookupIngress` 的答案**(W16 · W72):`user` 不是 `of.<f>`、没有这个形态、计划里没有这个组的答案,或没有 `target` → `null`(入口答认证失败)。目标是该组自己的监听端口(`127.0.0.1:<组端口>`,换端口或换地址就是 agent 的连接)→ `{health:true, group:<形态 id>}`(内核探测 `asight-in-<f>` 用的:入口答它,不拨、不记;所以只有 `on` 之后、引擎在时才答,读回才是「开」);**该组在计划里不是 `on` 时这个探测是 `null`**(内核的回退组收不到探测,保留回退的路)。**该组不是 `on`、而来的是 agent 的连接**(计划已翻成关、内核的重载还没落地的那一小段;重载失败时可长到回退组的 30 s 探测翻过去):不答 `null`(那是 `407`,agent 看到认证失败),而是**照样接**:meta 为 `{pid:null, decrypt:false, form, upstream:<该组的上游,绕过表与登录照常>, negKey:'of.<形态>', skip:{not_captured:'untracked', reason:'group-off'}}`,不查套接字表;该组没有上游可拨(`upstream` 为 `null`)才答 `null`。别的目标 → meta:`{pid, agent, decrypt, capture:'proxy', form, exe, upstream, pid_source, pid_ms, negKey, skip?}`。`upstream` 先于查 pid 算(拨不通的连接不该等表);`skip` 只在不解密、而 tracker 对这个 pid 没有一行可说原因时有:`{not_captured:'untrusted', reason:'pid-unresolved-mixed'}`(没有 pid、该形态有进程未信任,§5.4)或 `{not_captured:'untracked', reason}`(`pid-unresolved` · `no-process-of-form` · `not-a-process-of-form`,§5.4;`reason` 是自由文本,不在闭集里,`not_captured` 在闭集里)。上游拨不通(`no-upstream`:该组没有上游可拨;`upstream-credentials-unavailable`:带登录的上游读不到登录)→ **拒绝**,Error 带 `code:'upstream-unavailable'` 与 `why`,消息里没有登录;入口写自己的 `upstream-unavailable` 失败(`where:'ingress'`,§12)并回 502。`auth_ref` 只在拨这一条连接时解:`resolveLogin(ref, { groups, ctx, manifest, hkcuEnv })`(`route-plan.mjs`;`prior:<组>` 走 `priorOf`,所以第一次 `on` 的文件与之后的清单给同一个登录,`hkcu-env:<名>` 取这次读到的注册表环境,文本经 `proxyAuthOf`;找不到是 `null`,不抛、不猜),守护进程把四项绑好当 `authOf` 交进来。
- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。
- **上游怎么拨**:`direct` 直连目标(域名由系统解析);`http` 向 `host:port` 发 `CONNECT <目标> HTTP/1.1`(带 `Proxy-Authorization: Basic` 当且仅当有凭据),2xx 成功,别的状态把代理的回应原样转给 agent;`socks5` 做问候(有凭据报 `0,2`,没有报 `0`)、RFC 1929、CONNECT(目标是 IPv4 / IPv6 字面量用 ATYP 1 / 4,其余用域名 ATYP 3),`rep ≠ 0` 回 `02`。代理回成功时与回应同一块到的上游字节留着、按序交给 flow(算上游先说话,4.6)。拨不通(拒连、解析失败、代理中途关)→ `502` / SOCKS5 失败回复,连接行 `decision:'error'`、`not_captured:'error'`、`error:{type, message, side:'upstream'}`;代理拒绝 → 连接行 `decision:'tunnel'`、`not_captured:'proxy-refused'`、`reason:'proxy-status-<n>'` / `'socks5-reply-<n>'` / `'socks5-auth-failed'` / `'socks5-no-acceptable-method'`、`upstream.reply`。这两种行是没有 flow 的连接的唯一记录(`stats().ingress.unreachable` / `.refused` 各计一次)。代理的回应第一行不是 HTTP 状态行(解析不出三位状态码)算拨不通、不算拒绝:`502`、行 `error.type:'bad_proxy_reply'`,代理的字节不转给 agent。**等代理没有时限**(D31:不能因为代理慢就断 agent),但不静默(D38):连代理与握手合计超过 `upstreamSlowMs`(5 s)还没回应,记一次 `upstream-slow`(`phase:'proxy-reply'`,`host` = 目标,不带 `flow_id`——这时还没有 flow——也不带凭据),连接照等;客户端先走了就不记。
- **拨不通要报**(W73):拨上游失败(拒连、解析失败、代理中途关)时,除连接行外另写一条失败 `upstream-unreachable`(`where:'netenv'`,经注入的 `onFailure`;同一形态 60 s 内最多一条,免得一个断掉的代理写出成千上万条),并进该形态的 `status` 原因(1.6 §9.7);doctor 给 `proxy-dead` 同样的查端口命令。上游代理拒绝(`proxy-refused`)是另一回事,不报它。
- **一条 agent 连接只拨一次上游**(评审 2026-10-07 后补):入口拨好的上游连接交给 `handleFlow` 用(每条连接一个包装,第一次取时给它,不再拨)。之后 4.6 的「让路」要重拨(解密不成改透传,把 ClientHello 原样发给新上游)时:上游不带凭据(直连、不要凭据的本机代理端口)才重拨;上游带用户的代理凭据,就关掉这条连接,同 4.6 隧道连接的做法:asight 不主动再发一次用户的凭据(不变式 1)。W15。关掉的那一行是 `decision:'error'`、`not_captured:'upstream-cert'`、`error:{type:'upstream_cert', side:'upstream'}`;之后该 (pid 或形态, host) 已进负缓存,客户端的重试直接透传(`negative-cache`)。不带凭据时第二次拨是新的一轮握手(直连:再连一次;`http` / `socks5`:再发一遍前导),重拨失败 → 连接行 `decision:'error'`,客户端的连接关掉;重拨等着时客户端先走了 → 代理一答就销毁新拨的上游,行同样是 `decision:'error'`、`error:{type:'closed_before_decision', side:'client'}`(没有拼接过,不写 `splice`)——代理一直不答时这条新连接留到它答或关(不设时限,D31)。

### 5.3 pid 补全(尽力,不挡采集)

| 办法 | 何时用 | 怎么做 |
|---|---|---|
| 单进程 | 该形态此刻只有一个进程(进程表里的) | 套接字表照样查一次,只为排除「表里还没有的进程」(见下);它是持有者、别人不是 → 它,`pid_source:'single-process'`。不再「不读表就是它」:进程表落后真实世界一个轮询(约 2 s),第二个终端刚起的头几条连接来自表里还没有的进程,不读表会把它们算到旧进程头上(评审 2026-10-07 晚) |
| 套接字表 | 多个进程 | 助手查 `GetExtendedTcpTable` [E6]:连到该形态所在组的监听端口的连接(任何状态、任何一条;`pid 0` 的行是 TIME_WAIT 的残留,没有属主,不算)的**全部持有者**里,**没有一个是进程表里没有的进程**,且该形态的候选进程里**恰好一个** → 它;候选里两个以上、或有一个不认识的持有者 → `null`(进程表里有、却不是候选的持有者是同组别的形态或不是 agent 的进程,它们的进程规则把连接交给了别处,不算,所以同组的两个形态共用一个端口也分得开)。不再用「还没被认领的连接」:连到该组监听端口的连接里,有些永远到不了引擎,所以永远不会被认领:`on` 之前开的长连接、形态只转发时(`off` 之后、`on` 期间启动的进程)开的连接、进程规则不匹配的子进程的连接。「还没被认领」的集合因此只增不减,会把流量算到别的进程头上(评审 2026-10-07;D43 去掉了 `PASS` 开关,理由改写成这几类只转发的连接) |
| 从不 | — | 用户 VPN 与内核的 `/connections`、`/logs`:用户 VPN 的含本机所有程序的连接元数据(4.7 §3.2);内核的也不用,上面的办法够了 |

- 预算 250 ms,与连上游并行。超时、不唯一 → `pid:null`,按形态判(§5.4)。宁可 `null`,不可错:错的 pid 会让引擎解密一个不信任 asight 的进程的连接,把它弄断(§5.4 的承诺)。
- **实现的限**(计划 Task 8(b),如实写):属主查询在入口拨上游**之前**做(`lookupIngress` 返回之后入口才拨),不是「与连上游并行」:新连接首字节最多多等 250 ms,`pid_ms` 如实记这段;要并行就得改入口的契约,不在此处做。进表之前的进程(启动不足一个快照间隔,约 2 s)的连接:套接字表里它是一个表外的持有者,所以 `pid:null`,专用端口上算 `untracked` · `pid-unresolved`(透传并记一行),不会被当成别的进程、也不会被当成 dsh。**有进程规则的形态,在按形态判出 `no-process-of-form` 之前,重定向器先向观察者按需要一次 `poll`**(2026-10-08 审计 F6 落地;与 2 s 定时器同一步差分,新进程由它作为 `exec` 入表、tracker 当场判):落了表,这个进程的**第一条**连接就被判,不用等进表之后的下一条;至多一秒要一次、至多等一秒;观察者没有 `poll`、已在一次差分中、超时、或查了没有人,答案照旧(按形态判,宁可 `null` 不可错),不因它多记失败。
- 超过预算不记失败(慢,不是不可用);读不到才记 `socktable-unavailable`,每次调用一条,由记录器折叠。`hop` 可带 `address` 收窄到该远端地址;不带时只比远端端口:真属主的那一行一定在表里,多出的行只会让答案变成「不唯一」,不会变成错的。助手只被问候选进程的行,答案在 JS 里再过滤一遍(助手不照做也不影响)。
- 引擎的对端是内核,不是 agent;上面的办法只看 agent 一侧到监听端口的连接。这条路没量过:W43 [WinVM] 用真值核对(同一形态 3 个进程,2 个已信任、1 个未信任,200 条并发连接,另有 `on` 之前就开着的长连接),错认必须是 0。
- **代价**(观测者效应):每个形态的新连接(单进程的也要读一次表,见上),首字节最多多等 250 ms。`flows/` 连接行记 `pid_ms`。常驻助手的一次表查询约 5 ms [E6];W43 [WinVM] 量 p50 / p90。
- 套接字表读不到(受限令牌、策略禁用 `Add-Type`)→ 一条失败事件 `socktable-unavailable`,之后全按形态判。

### 5.4 信任判定

- **谁产生判定**(评审 2026-10-08 补;计划 Task 8(v);W76):redirector 的判定表只有 `watch(pid, {decrypt, agent})` 推进来的行,**推的是 tracker**(4.6),所以下面「按 pid 判」之前,tracker 要在 Windows 上真的判得出来。8(b) 建好 redirector 时这件事没有人管:`registry.match` 按 `descriptor.signatures[facts.os]` 认进程,七个 harness 没有一个有 `signatures.win32`(`desc.win32` 不进 `createRegistry`),Windows 的 agent 一律 `no-match`;就算认出来,tracker 对 `facts.env === null` 的进程一票否决(`environ-unreadable`),而 Windows 的进程 `env` 一律是 `null`(§10.1:不读别的进程的环境),所以入口文件与 `installed_at` 这一层根本到不了。结果是 redirector 的判定表永远是空的、什么都透传:fail-safe,但 Windows 上没有任何东西会被解密。Task 8(v) 已落地(2026-10-08):(1) **认形态只有一份规则**:守护进程把 `matchForm`(同一个函数,同一份形态数据)交给 registry(`createRegistry(descriptors, { osMatch: { win32 } })`,认出的名字不是已注册的 harness 会抛,而不是当「不是 agent」),tracker 认出的 harness 与 redirector 认出的形态同源,不另抄一份 `signatures.win32`;(2) **环境读不到是本 OS 的常态**时(进程事实声明 `envRead:false`,Windows 的 `procinfo` 给),tracker 不因 `env === null` 否决,按入口文件(Hermes 在 `desc.win32.layers` 里自己声明,根是 `%LOCALAPPDATA%\hermes`;其余 harness 的 Linux `layers` 在 Windows 形的用户目录里读的就是那些文件,测试钉着)、`installed_at`(tracker 收 `osLayers[os](descriptor)` 选层,守护进程接线)、插件标记、Kimi shim 的父进程判;Linux 上读不到 environ 仍然否决(`environ-unreadable` 的那条测试不动);(3) dsh / OpenCode 的标记与 `startedAt` 的比较带定死的容差 2000 ms(`MARKER_TOLERANCE_MS`,Linux 的 `/proc` 整数仍是逐字相等:不传容差);(4) tracker 也听 `facts-update`(命令行晚到的形态),同一 pid 再判一次。仍然是 fail-safe:任何一步不确定 → 未信任 → 透传。
- **环境读不到时的取舍**:启动环境读不到,用户在 Windows 用户环境里自己的 `SSL_CERT_FILE` / `NODE_EXTRA_CA_CERTS` 不读、也不作为否决的理由——asight 的 Windows 信任入口全是覆写/块写(agent 把文件盖过它的启动环境),装入时用户看得见的 CA 已并进合并包;但 `fill` 型的层(它的值只在进程自己的环境缺这个名字时才生效,「生效」与「被进程自己的变量挡住」在 Windows 上分不开)**不作为信任的来源**(tracker 对 `envRead:false` 的进程核第二遍:把 fill 层拿掉就不信任的,判未信任,`env-unreadable-fill`;今天没有 asight 入口的信任经它给出,代价为零)。残余,如实记下:比文件更优先的环境名(Hermes 旧版的 `HERMES_CA_BUNDLE`、Z-Code 的 `ZCODE_AGENT_CA_CERT`)同样看不见,设了它的用户会按文件判成信任——这一类待量,量到再定。
- **有 pid**:照 4.6 §确认信任,按 pid 判:进程启动时间与入口的 `installed_at`、插件标记、Kimi shim 的父进程。
- **专用端口、没有进程规则**(dsh CLI,§3.5):pid 是该形态的进程且已信任才解密,别的(子进程、补不出 pid)透传。属主在**所有**进程里找(该端口接下任何进程的连接);候选 = 全部进程**除去同组别的形态的进程**(它们的进程规则把连接交给了各自的形态,dsh Desktop 开着连接时不该让 dsh CLI 找不到自己);补不出 pid(含这条连接来自进程表里还没有的进程)→ `untracked` · `pid-unresolved`;pid 是别的进程(dsh 的子进程、别的程序)→ `untracked` · `not-a-process-of-form`;两种都留**恰好一行**元数据(D40:解不了密就透传并记)。
- **没有 pid**:按形态判。该形态在跑的进程**全部**已信任 → 解密;有一个未信任(没判过、命令行还不知道的也算)→ 透传,`not_captured:'untrusted'`,`reason:'pid-unresolved-mixed'`;该形态没有任何在跑的进程 → 先按 §5.3 的按需刷一次表,刷完仍没有才透传,`untracked` · `no-process-of-form`。这样 1.6 §1.1「`off → on` 后在跑的 agent 透传、不被弄断」在没有 pid 时也成立。代价:同一形态的新进程要等旧进程退出才被采集,`status` 点名旧进程。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(of.<形态>, host)`。不同形态互不毒化 [E15]。
- 负缓存的失败事件与清除事件都带 `neg_key`(有 pid 时是 `"<pid>"`,没有时是 `"of.<形态>"`)。读取侧(`src/health/flows.mjs`)按 `(neg_key ?? pid, host)` 归并,清除按 `neg_key` 清;否则两个都没有 pid 的形态会撞在 `(null, host)` 上(评审 2026-10-07;写回 4.6 §记录)。W17。
- 条目只在内存:pid 退出、或该形态的进程全退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。下表写明哪几个字段随引流不同:

| 字段 | Linux 驱动模式(eBPF) | Windows 代理模式 |
|---|---|---|
| `capture` | `transparent` | `proxy` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` |
| `proc.pid` | 内核给 | 尽力,可为 `null` |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` |

- 其余字段(请求与响应的原始字节、头、体、`host`、`scheme`、`endpoint`、`transport`、`ws_*`、`asight_added`、各种标注)MUST 逐字节相同。验收:同一 mock 调用分别经 Linux 驱动模式与 Windows 代理模式,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?, reply?}`(不含凭据;`reply` = 上游代理的回应状态码,`http` 是 HTTP 状态,`socks5` 是 REP 字节;直连没有)。`bytes_up` / `bytes_down` 仍是 agent 自己那条连接上的字节(4.6 §记录):经入口的连接不含入口读走的开头(CONNECT 或 SOCKS5 握手)与 asight 回给 mihomo 的 `200` / SOCKS 回复(那些是 asight 与 mihomo 之间的字节,不是 agent 的)。W14 的行比较因此连字节数也相等(`bytes_down` 里叶证的 ECDSA 签名长度会差一两个字节,不算)。`capture` 不进连接行,只进信封(Task 2(b) 接线:`flow.mjs` 的 `startTee` 要把 `meta.capture` 带进交换记录的 `flow`)。
- **代理前导**:入口收到的 CONNECT 是内核发的、带 asight 的 token,不是 agent 的字节;引擎发给上游代理的前导是 asight 写的。两者都不记成 `prelude`(4.6 的 `prelude` 只记 agent 自己发、代理自己答的字节;不变式 4)。连接行改记 `ingress` 与 `upstream`(含上游代理的回应状态码 `upstream.reply`)。所以 agent 自己配了代理时,Linux 的行有 `prelude`、Windows 的没有;W14 / W50 的比较只比信封,另比一次「直连上游」的连接行去掉上述字段后相等。
- 读取侧:`capture` 多一个值 `proxy`(改 4.1 信封表;Linux 已写进数据的 `transparent` 不动,不变式 2);观测者效应表(`src/dissect/harnesses.mjs`)对两种值都适用;看板就地标引流方式;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

## 6. 信任入口(Windows · D37④ 的 Windows 写法)

规则同 4.6:按 harness 各走一个入口,只让该 agent 信任 asight CA;默认不写登录环境(`setx`、`HKCU\Environment` 里的 CA 变量、PowerShell `$PROFILE`),不装任何证书库(`CurrentUser\Root`、`LocalMachine\Root`)。例外只有用户点名的(§2.4,D43⑥):Claude Desktop 的 `CurrentUser\Root`、VS Code 与 Z-Code Desktop 的应用设置、机器级证书库;`HTTPS_PROXY` 一类代理变量点名也不写进登录环境。入口随开关:`on` 写、`off` 撤,入账、先备份(1.6 R2)。

- 写进配置文件的路径一律用正斜杠(`C:/Users/<u>/…`):dotenvy 把反斜杠当转义,会静默丢掉 `SSL_CERT_FILE`。
- **用户目录有空格是常态**(`C:\Users\John Smith`、`OneDrive - Contoso`):`.env` 块里这样的值写成双引号包起来的(`SSL_CERT_FILE="C:/Users/John Smith/.asight/…/combined-codex.pem"`),dotenvy 与 python-dotenv 读回整条路径;清单里记的仍是不带引号的路径。值里有 `"` `$` 反引号 `\` 或换行时写不了,`on` 在动任何文件之前就拒绝并说出是哪个值(这样的用户目录少见,拒绝是响的,不会静默丢入口)。Linux 的块不带这个选项,仍只写不带空格的绝对路径(4.6)。
- **CRLF 的文件**(Windows 上的编辑器多半这么存 `.env`):块的每一行用文件本来的行尾,所以编辑器不会把它改成两种行尾混着;用户自己的同名键(`SSL_CERT_FILE`、`HTTPS_PROXY`、`NO_PROXY`)照样被关掉、`prior_value` 照样记下(行尾的 `\r` 不算值);用户的编辑器之后把行尾改成 LF 或 CRLF,`off` 还是找得到块。

- **插件源码与标记**(Task 4):Windows 的插件是 `harness/plugins/win32/dsh.mjs` 与 `opencode.js`,不读 `/proc`(Windows 没有),只 import `node:fs` 与 `node:tls`。标记文件 `<标记目录>/<pid>` 里是 `String(Math.round(performance.timeOrigin))`,即本进程启动的毫秒数,先写临时文件再改名。引擎拿它与助手给的 `startedAt` 比,**带容差 2000 ms**(`MARKER_TOLERANCE_MS`;Linux 的 `/proc` 值是整数、逐字相等,不传容差,这里是毫秒取整不会逐字相等,Task 8(v) 定)。没有 `tls.setDefaultCACertificates`、带 `--use-openssl-ca`、CA 文件缺失或不是 PEM → 什么都不加、不写标记、不抛。OpenCode 的插件在 Node 侧车上用 `setDefaultCACertificates`,在 Bun 上包 `fetch`(追加 asight 的 CA,请求与响应原样经过,不读 body),两样都没有就什么都不做。
- 代理入口(§2.3)与信任入口写在同一个文件时放进同一个哨兵块(Codex、Hermes 的 `.env`),分别入账:`joinBlock`(默认关)把后来的行并进已有的块,用户自己的同名键照样被关掉、`prior_value` 照样记下,撤销各自后进先出(`text-edit.mjs` `joinDotenvBlock`;W19 的门槛 ①–④ 已落地,Task 8(v) 那一轮)。
- 点名的信任项(Claude Desktop、Kimi 的 VS Code 扩展、Z-Code Desktop、机器级证书库)见 §2.4。

### 6.2 合并包(Windows)

- `combined-<harness>.pem` = Node 自带根(`tls.rootCertificates`)∪ Windows 根证书库的导出 ∪ 该 harness 自己配置里的用户 CA ∪ asight CA。
- Windows 根:Node ≥ 22.15 用 `tls.getCACertificates('system')`;更老的由助手只读导出 `Cert:\CurrentUser\Root` 与 `Cert:\LocalMachine\Root`(`roots.mjs`)。只读,从不写。Node 24 上 `tls.getCACertificates` 与 `tls.setDefaultCACertificates` 都有(dsh 与 OpenCode 的插件路径可用),`getCACertificates('system')` 给的证书全部能被 `X509Certificate` 解析。

- **包里的每张证书都先用 Node 的 `X509Certificate` 解析一遍**,解析不了的丢掉、计数,回执与 `status` 各一行(「Windows 根里 N 张证书解析不了,没放进包」)。Codex 用 rustls,一张怪证书可能让它整包拒绝、哪都连不上;**[T0] 量过**(Codex 0.160.1 对本机 TLS mock,服务端证书由 asight 替身 CA 签):真导出的 Windows 根(`CurrentUser\Root` 265 张 + `LocalMachine\Root` 265 张,去重 261 张,433,748 字节,全部能被 .NET 解析)加替身 CA,Codex 连得上(`SSL_CERT_FILE` 与 `CODEX_CA_CERTIFICATE` 都认);只有根、没有替身 CA,连不上(90 s 里不停重连,一个请求也没到 mock);**根 + 一块解析不了的证书,连不上,坏块在替身 CA 之前或之后都一样:一块坏证书让整个包作废**。所以先过滤是必须的(上一条)。Node 的 `tls.getCACertificates('system')` 给 467 张,比两个根库去重后的 261 张多,守护进程与合并包取的是前者(Node 自己的系统集),这一差别的原因没细查。W20。

### 6.3 shim 与用户 PATH(点名项)

- asight 的 bin 目录里每个命令名一个 shim:`kimi.cmd` 设 `NODE_EXTRA_CA_CERTS`(取法同 4.6 的 `extra-kimi.pem` 规则)与 `HTTPS_PROXY`(内核里该形态所在组的端口,带凭据);`opencode.cmd` 只设 `HTTPS_PROXY`(信任走插件);再 `"<真二进制>" %*`。启动环境里已有别的 `HTTPS_PROXY` 时不覆盖(那是用户这一次的选择),这一次不采。
- 用户 PATH(`HKCU\Environment\Path`)最前插一项 shim 目录:保持值的类型(`REG_EXPAND_SZ` 还是它);从不用 `setx`(1024 字符截断);写完广播 `WM_SETTINGCHANGE`;撤时只删这一项,从不拿旧值整个写回(D28 的教训)。值在 asight 改过之后又被改过:只删这一项,报「已撤销,但不逐字节相同」。**kimi 与 opencode 共用这一项**(评审 2026-10-07 后补):按引用计数,`off kimi-code` 只删 kimi 自己的 shim 文件,PATH 里这一项与 shim 目录在最后一个 shim 撤掉时才删,不弄坏另一个 harness(`shim-not-on-path`)。W55 · W64。
- 这一项改的是本用户所有程序看到的 PATH 顺序,所以是点名项(D43⑥;Linux 的 rc 那一行同理)。shim 目录专用,只放 agent 命令的 shim。
- **机器 PATH 在前**:Windows 先读机器 PATH,再读用户 PATH。用户 PATH 最前的 shim 只赢得过装在用户 PATH 目录里的真二进制(npm 全局 `%APPDATA%\npm`、pipx / uv、scoop、winget Links)。真二进制在机器 PATH 里时 shim 输,`status` 报 `shim-not-on-path`;要赢只能把一个目录放到机器 PATH 最前,那是机器级的点名项,要用户自己给管理员权限(§2.4)。
- **机器级用的不是用户的 shim 目录**(W65):`%USERPROFILE%\.asight\collector\bin` 本用户的任何进程都能写,放到机器 PATH 最前,等于让这个用户的任何进程往管理员与 SYSTEM 的命令查找路径里放同名文件(PATH 劫持)。所以机器级的点名项由提权这一步另建 `%ProgramData%\asight\machine-bin`(只有 SYSTEM 与 Administrators 能写,Users 只读与执行),里面是分发器:`kimi.cmd`、`opencode.cmd`,不含任何凭据,逻辑只有一条:运行者自己的 shim `%USERPROFILE%\.asight\collector\bin\<命令>.cmd` 在就调它,不在就执行点名时记下的真二进制的绝对路径(`status` 核对它还在,不在报 `entry-changed`)。机器 PATH 里放这个目录,不放用户的目录。别的用户与服务各用自己的用户目录,没点名的走真二进制,不经这个用户的内核。所有用户的开始菜单快捷方式(`opencode.desktop`)同理,指向这个目录里的启动器。
- Kimi 只在原生安装(`%USERPROFILE%\.kimi-code\bin\kimi.exe` 在)时装。Smart App Control 开着时不装:被拦的 shim 排在 PATH 最前,`kimi` 就起不来(fail-closed);改报「未信任 · Smart App Control」。

## 7. 守护进程、自启、控制面

- **守护进程** = `node <asight> daemon`。上游的信任集照 4.6 §引擎 第 5 步自己拼:Windows 系统库这一份由 `windowsRoots()` 给(Node ≥ 22.15 用 `tls.getCACertificates('system')`,更老的由助手只读导出,§6.2)。不加 `--use-system-ca`(原稿加了):那个选项要 Node ≥ 22.15,更老的 Node 上守护进程每次登录都以「bad option」退出;信任集已经自己拼了,选项是多余的。`on` 先查 `process.versions.node`,低于计划的下限(Node 20)就拒绝并给 `doctor` 一行。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(R7 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。 **判据**(W25):`on` 与 `daemon` 用助手的 `token` 动词,`elevated` 或 `system` 为真就拒(`elevated-token`,`where:'start'`);`off` 与 `uninstall` 起不了助手(独立副本没有它,而 `off` 要在 asight 坏了时也能跑),改经 `execTool` 跑 `whoami /groups /fo csv /nh`,按 SID 判:完整性标签 `S-1-16-12288` 及以上(High、System)或 SYSTEM 的 `S-1-5-18`;SID 各语言相同,不看组名。**读不到令牌不是拒绝**:助手死了、答的不是布尔、`whoami` 起不来或没给出完整性标签,都记「不知道」加原因、往下走(助手自己的失败另有 `helper-start-failed`;一个因为 `whoami` 坏了就不肯撤销的 `off` 不是撤销)。`on` 的 Node 预检答 `{ok, have, min, doctor}`,读不到 Node 的版本也不算通过。
- **自启**:每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`(不用 S4U:S4U 不受 UAC 过滤,是 High 完整性)。动作 = `conhost.exe --headless "<node.exe>" "<asight.mjs>" daemon --supervise`(无窗口 [E20];`--supervise` = 任务拉起的是**监管父进程**,由它拉起真正的守护进程 `node <asight> daemon` 并在它非 0 退出时重拉,下面「监管父进程的退出规则」:任务自己不重拉,[T0])。设置 = 失败后 1 分钟重启(最多 999 次)、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML`(经 `execTool`)注册并启用;不带参数的 `off` 停用;`uninstall` 删除。 **任务 XML 与单元的形状**(W24):XML 的字段是上面这些(动作的参数以 `daemon --supervise` 结尾),外加 `StopIfGoingOnBatteries false` · `AllowHardTerminate` · `StartWhenAvailable`(T0 里注册成功的那一份)。它声明 `UTF-16`,而 `on` 写下的任务文件(入账)是 UTF-8 的字节,所以 `enable` 把它复制成带字节序标记的 UTF-16LE 副本交给 `schtasks`,读完即删。单元的形状与 Linux 的 `userUnit` 相同:`{path, links:[], text(env), enable({now}), start(), reload(), disable(), remove()}`,各动词答 `{code, out, err}`。`enable({now})` = `/Create /XML … /F`,`now` 为真(缺省;已有守护进程在答时 `on` 传假)再 `/Run`。**`start()`(`--no-autostart`:只这一次,登录时不起)不注册任务**:带登录触发器的任务就是自启,所以它直接分离地起 `conhost.exe --headless … daemon --supervise`,没有窗口。`reload()` 什么都不做(再 `enable` 时的 `/F` 已覆盖改写)。**登录时只留一条启动路径**(评审 2026-10-07 后补):`enable` 注册任务成功后,把 asight 先前后备写下的 Run 值取下(是 asight 的才动;账里有用户自己的原值就按原类型放回);改用后备时,先前注册的任务 `/Change /DISABLE`。做不到的以 `warn` 交给调用方写进回执,`on` 不因此失败(两条都在时父进程是单例,第二个起来的立刻离开)。`disable()` = `/Change /DISABLE`,`remove()` = `/Delete /F`,任务不在就是已经如所求(先 `/Query` 看,不靠解析本地化的报错文字);**`/Query` 没跑起来(超时、被挡、起不来:没有退出码)不是「不在」**,是失败(`off` / `uninstall` 报失败、数字的非零退出码、不凭猜测去改任务),否则任务仍登记着、下次登录又起 asight 而回执说成功(D38)。退出码 1 仍当「不在」:那是唯一没法不解析文字就分开的含糊(「找不到」与「服务没起」),由测试机量一次(W47)。Windows 的任务没有自己的环境变量,所以安装 shell 里的 `NODE_EXTRA_CA_CERTS` 不会带给任务拉起的守护进程(它信任系统库,§6.2)。**直接起的守护进程(`start()`、后备带 `now`)同样不带**:它拿安装 shell 的环境,去掉改变信任与外连的那几类(Node 的 CA / TLS / 代理开关 `NODE_EXTRA_CA_CERTS` `NODE_OPTIONS` `NODE_USE_SYSTEM_CA` `NODE_USE_ENV_PROXY` `NODE_TLS_REJECT_UNAUTHORIZED`、OpenSSL 的 `SSL_CERT_FILE` / `SSL_CERT_DIR`、`*_PROXY` 一族,不分大小写),这样同一个守护进程不因「怎么起的」而信任与外连不同;别的变量留着(用户级的 `CODEX_HOME` 之类登录时本来就有)。余下的差别如实写:用户自己在用户级设的 `NODE_OPTIONS` 与 `*_PROXY`,登录会带、直接起不带。
- **「不需要管理员」没证实过**(如实写):测到的只是管理员账户的过滤令牌 [E20 的限定];标准用户能不能注册带登录触发器的任务、`RestartOnFailure` 能不能拉起被杀的守护进程,都没量。**[T0] 量过一半**(没有新建账户:创建账户只有操作者能做,所以**本地标准用户仍没量**)。以普通用户、Medium 完整性(管理员账户的过滤令牌,`IsInRole(Administrator)` 为假)从非提升进程跑:`schtasks /Create /XML` 注册成功(登录触发、本用户、`InteractiveToken`、不是 `HighestAvailable`——`schtasks /Query /XML` 对默认的 `LeastPrivilege` 不印 `RunLevel`、`RestartOnFailure` 都在);`/Run` 起来的进程在登录会话 2 里,父进程是 `conhost.exe`。**`RestartOnFailure` 拉不起被杀的守护进程**:杀掉守护进程(`node`)、杀掉任务自己的进程(`conhost --headless`)、守护进程自己以退出码 3 退出,三种各等 100 s(间隔设的 1 分钟),都没有被重新拉起;任务的 `Last Result` 分别是 0、-1、0,即 `conhost --headless` 把子进程的退出码吞成了 0。**所以任务只负责登录时拉起一次,崩溃后的重拉必须由监管父进程做**(见下一条,不再只是后备)。W47 在产品实现后在标准用户上补测。
- **自启的后备**:`schtasks /Create` 被拒绝 → `on` 自动改用 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的一项(值名 `asight-collector`,入账、先记原值,`off` / `uninstall` 只删这一项),动作同上(同一条 `conhost.exe --headless … daemon --supervise` 命令行,Run 值里放的就是它):一个小父进程拉起真正的守护进程,它退出就按 1、2、4…60 s 退避重拉。回执写「计划任务注册被拒,改用登录启动项」并给原因,事件 `task-register-failed`(失败类,但 `on` 不失败)。 **细则**(W24):① 「被拒」= `schtasks /Create` 起得来而拒绝,或起不来(没有这个程序、被策略挡);任务文件本身读不到不算(没有向 schtasks 要过什么,那是 `on` 的前置错误,不改用 Run 值)。② 写之前先 `reg query` 那一个值:是别人的字符串(REG_SZ / REG_EXPAND_SZ)→ 记成 `prior`(类型与内容),然后覆盖;是 asight 上次写的(命令以 `daemon --supervise` 结尾)→ 不当 prior,回给调用方 `ours: true`,调用方保留清单里已有的 `prior`;**不是字符串的值(REG_DWORD 等)不碰**:放回不去的东西不覆盖,`on` 报错(读出来不是原样的字符串也是:见③)。③ 写完再读回核对(生效要复核):读回不同 = 失败,但条目仍交给调用方入账(撤销幂等)。**`reg query` 的输出是 reg.exe 按控制台代码页写的(简体中文 Windows 上是 cp936),`execTool` 按 UTF-8 解码,所以值里的非 ASCII 字符(用户目录是中文名时 Node 与 asight 的路径就有)读回是 U+FFFD**:核对时 ASCII 部分逐字节相等、每一段非 ASCII 字符不限读成什么;写的是纯 ASCII 时仍逐字节。读出来的原值带 U+FFFD(放回去不会是原样)→ 同「非字符串」一样不覆盖、`on` 报错(②)。值两端的空白经 `execTool` 的 trim 丢掉,命令行不在乎。④ 入账条目 `{kind:'run-key', hive, key, name, value, prior}` 由 `enable()` 的返回值带给调用方(`ledger`);`task-register-failed` 记录也在返回值里(`event`),由调用方写进 `flows/`;`enable({now})` 的 `now` 为真时,Run 值要到下次登录才跑,所以直接分离地起一次监管的守护进程;起不来 = 失败。⑤ 撤销(`disable()` / `remove()`)只动这一个值:是 asight 的 → 有 `prior` 就按原类型放回,没有就 `reg delete … /v asight-collector /f`;不是 asight 的 → 留着(回执 `left`);不在 → 已如所求。任务与 Run 值都处理,不管上次 `on` 用的是哪条路。**[T0] 已显示计划任务拉不起被杀的守护进程**(上一条):监管父进程是默认做法,不只是计划任务注册被拒时的后备;任务的 `RestartOnFailure` 照写(多一层不坏),但不当作重拉的依据。
- **监管父进程的退出规则**(W24 · W28 · W46):守护进程以退出码 0 退出 = 被要求停(`off` 排空完、`uninstall`、`off --now`):父进程随之退出,不重拉;非 0 或被杀(没有退出码)才按退避重拉。父进程把自己的 pid 与启动时间写进 `supervisor.lock`。不带参数的 `off` 与 `uninstall` 要停它时,**先停父进程**,再停守护进程(§4.2);`schtasks /Change /DISABLE` 不结束正在跑的实例,所以不能只靠它。这样「`off` 之后没有 asight 进程」(1.6 §1.4)成立,`off` 也不会被父进程撤销。 **细则**(W24):① 父进程拉起的是 `node <asight> daemon`(不带 `--supervise`:带了就是又一个父进程);退避 1、2、4、8、16、32、60 s 封顶,**守护进程这次活满 60 s 才死,退避从头算**(不然一个月里崩过七次的守护进程,往后每次崩都要等 60 s;规格原来没写重置)。② `supervisor.lock` = `{pid, startedAt}`(一行 JSON,`startedAt` 是本进程的启动时间,Unix 纪元毫秒,取「现在减进程已运行时间」;核对的一方与 `forwarder.lock` 一样容 2 s);先写锁再拉守护进程;结束时只删自己的锁(别的父进程的锁不动);锁写不了只记一行日志,照常监管(`off` 找不到它是已说出口的代价)。**父进程是单例**(评审 2026-10-07 后补):锁以独占方式建;锁已在时核对持有者(`pid` 与启动时间,容 2 s;Windows 经 `execTool` 跑一条固定的 `Get-Process` 问那个 pid 的启动时间):还在跑 = 这是第二个父进程,记一行日志、不拉起守护进程、退出码 0、不动持有者的锁(否则它拉起的守护进程撞上第一个的控制端点以 1 退出,被它无限重拉,而 `off` 只找得到锁里那一个);不在了(硬结束留下的旧锁、pid 被复用、启动时间对不上)或核对不了(记原因,按「不在」算:宁可多起一个也不要起不来)= 接手。③ 守护进程起不来(`spawn` 抛、没有 pid 的 `error`)当成一次失败,同样退避并记一行日志;有 pid 的 `error`(杀不掉、发不出消息)进程还活着,等它的 `exit`,不另起第二个。④ 父进程收到 SIGINT / SIGTERM / SIGHUP(控制台关了)或 `stop()`:结束守护进程、不再重拉、退出码 0、删锁。`off` 在 Windows 上是 `taskkill` 硬结束父进程,走不到这一步(所以先停父进程再按 `lock` 停守护进程,§4.2)。⑤ 守护进程那边写 `crash` / `unclean-stop`,父进程自己没有闭集里的码,只写 stderr(`conhost --headless` 下没有控制台,等于没有:重拉的事实靠守护进程重启时的 `unclean-stop` 记录)。入口:`runSupervisor({ asight, dir })`(`asight daemon --supervise` 调它,返回退出码)。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`。CLI 读它再连。读的一方遇到不是 JSON 的 `control.json` 只说「不是 JSON」,**不带解析器的消息**(它会引出出错处周围的字符,损坏的文件里可能就有 token 的头几位)。名字随机,防同机别的用户先占一个固定名字。 **token 怎么用**(W26):每个请求带头 `x-asight-token: <64 位十六进制>`;服务端在查路由之前先核它(定时安全比较),缺或错一律 401,不说有哪些路由。管道名与 token 一起在第一次启动时生成(8 与 32 字节随机),`control.json` 一次写成(临时名 → 链入;两个进程同时启动时后到的读先到的;文件系统不能链入时退回改名,那时同一瞬间的两次启动各留各的,抢到管道的守护进程才是文件该写的那个,第二个启动发现管道被占),内容不是端点的(坏了、被改了)由写的一方换一份、读的一方(CLI)得到错误。服务端对管道路径不建目录、不设文件模式、不删文件(管道没有这些)。
- **文件权限**:Windows 上「0600」没有意义。asight 的文件都在 `%USERPROFILE%` 下,靠用户目录默认的 ACL(本用户、SYSTEM、Administrators);asight 不另设 ACL,单元测试在 win32 上不断言权限位。用 `icacls` 核一次(W26)。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:监管父进程拉起(计划任务只在登录时拉起一次);其间内核退回上游(§3.3)。

## 8. 自带内核:来源、许可、监管

- **构建脚本只留 `--pin`**(D44;W75):`scripts/kernel-payload.mjs` 的构建包一半(下载、解压、生成平台包与 tarball、`main-package.json`)删除;只留 `--pin` 模式——由维护者在更新 pin 时跑,两次独立下载,印压缩包与解包 exe 的大小与 sha256 供填 pin(两次的 exe 必须一致),什么也不写。它不在 `files` 里、不随包发,不是 CLI,不受 R8 约束。原 2026-10-07 构建流程的纪律(tar 解 zip 用系统 bsdtar、先核许可证文本、都对了才写第一个文件)随构建一半作废,摘要核对由 `on` 一侧的下载核对(D44)与 `--pin` 模式继承。
- **放哪**:`%USERPROFILE%\.asight\collector\kernel\asight-forwarder.exe`(专用目录,不在 shim 的 bin 目录里;文件名就是 `asight-forwarder.exe`,进程名不与用户自己的 mihomo 撞),旁边放 `LICENSE-mihomo.txt` 与 `SOURCE-mihomo.txt`。**为什么复制一份、不直接从包目录里跑**:Windows 不许替换或删除正在跑的 exe,而内核在排空时(§4.2)可以活得比一次 `off` 久得多;从 `node_modules` 里跑,期间的 `npm i -g` 升级或 `npm uninstall` 会因文件被占而失败,正在跑的内核还会和包目录一起悬空。复制出来的这份归 asight(入账 `forwarder-binary`,`uninstall` 删,§4.2),包目录归 npm。回执写明它是独立的 GPL-3 程序(聚合,asight 不链接它)。
- **监管**:守护进程以分离方式拉起它(守护进程崩了它不跟着死),`forwarder.lock` 记 pid 与启动时间。守护进程重启时认领它:pid、启动时间、控制口 `GET /version` 三者都对得上。它退出了:按 1、2、4…30 s 退避重拉,每次一条 `forwarder-restart`;连续 5 次起不来 → `forwarder-down`(失败类)。起不来时先分类:Smart App Control 开着(同 §6.3 的注册表读法)→ 原因 `smart-app-control`,未签名的 `asight-forwarder.exe` 很可能被它拦了;别的照实记 `forwarder-start-failed` 加 errno。测到的环境里 `VerifiedAndReputablePolicyState` = 0(关)。关着,所以那个未签名的核心照样起来,这**证明不了**开着时也行;开着时的情形仍按 `smart-app-control` 处理,没测。asight 不因此改 agent 的设置(1.6 §9.5),`doctor` 给命令。
- **监管的细则**(计划 Task 7 定;W28 W74):
  - `forwarder.lock` = `{pid, startedAt, endpoint, config}`(0600;`endpoint` 是 `tcp:127.0.0.1:<控制口>`,`config` 是配置文件的路径,secret 只在那份 0600 的配置里)。**认领**要四样都对:pid 活着;启动时间(助手的 `ps`)与锁里的相差不超过 2 s,**读不到启动时间就不认领**(宁可不认);锁里的配置读得了、它的控制口等于锁的 `endpoint`;`GET /version` 答。认领后用**那个内核自己配置里**的控制口与 secret(不是这次新随机的),此后 `reload` 的文本按这套凭据生成,守护进程不会把自己锁在门外。启动时间对不上 = 这个 pid 已是别人的,不碰它、锁留给下一次启动替换;pid 没了 → 清锁。被认领的内核死了照样按退避重拉(用磁盘上的配置),认领之后守护进程再 `reload` 带上形态表。**助手读不到启动时间**(超时、已死,或答的不是数)与 `null` 同样处理(评审 2026-10-07 后补;W28):内核照常被跟踪、锁照写、`startedAt:null`,不算一次起不来(它已经答了 `/version`),这样的锁以后不会被认领(宁可不认);`adopt` 遇到同样的读不到答 `start-time-unreadable`,不抛。`procStart` 是 `createForwarder` 的必传项:接线忘了它,写出的锁就没有人能认领。
  - **一次只做一件事**(评审 2026-10-07 后补;W28):`start` · `reload` · `adopt` · `stopNow`、监管的重拉与排空的最后一次停,一个接一个做。`stopNow` 先记下「要停」再排队:正在进行的重拉在内核答了(或读完启动时间)之后看到它,杀掉自己拉起的子进程并等它退出,不登记它、不写锁,所以 `stopNow` 返回时不会还有内核活着(否则 `uninstall` 的 `removeBinary` 删不掉或留下孤儿);`start` / `reload` 等进行中的重拉结束,再按那时有没有内核决定重载还是拉起,所以不会拉起第二个;排到队首的重拉若发现内核已经在了,什么也不做。
  - **退避**:1、2、4、8、16、30 s(封顶)。每次重拉前先核拷贝(W27 ④),核不过是一次失败,照样计数、不拉起;每次一条 `forwarder-restart`(带 `attempt` 与 `delay_ms`);第 5 次连续失败记一次 `forwarder-down`(`where:'netenv'`,带 `attempts`),之后照旧每 30 s 试;**稳定运行 30 s 才把计数清零**(之前的失败都算「连续」)。`stopNow()` 取消正在等的重拉。
  - **启动前先问 `isFree`** 这份配置要开的每个端口(各组端口与控制口):被占 → 不 spawn,`forwarder-start-failed`、`reason:'port-taken'`、`port`;这个原因**从不**记成 `smart-app-control`。别的起不来:内核退出了(`exit` 带退出码或信号)· 控制口在 `startTimeoutMs`(缺省 10 s)内不答 · `spawn` 抛的 errno;Smart App Control 开着或在评估时这三种都记 `reason:'smart-app-control'`,错误原文留在 `because`。
  - **重载**:`PUT /configs?force=true`;新文本里新开的端口先问 `isFree`(被占 → 不发 PUT);核心拒绝 → 只报状态码(核心的话可能引用用户的配置,控制口客户端扣下);配置文件在核心接受之后才写。读回逐形态:`on`(组选 `asight-in-<f>`)· `fallback`(选 `asight-re-<g>`:引擎不在)· `off`(没有这个组)· `missing`(要 on 而没有组)· `still-on`(要 off 而还在)· `unknown`(写明原因);只有每个形态都与要的一样才 `ok`,调用方据此才写入口(§4.1)。
  - **排空**:`drain({pidsInWindow})` 之后内核留着,每秒看一次窗口里的 pid,最后一个走了才停内核(期间内核死了会被拉回:它们还要用),`status` 报个数;`off --now` 的 `stopNow()` 立即停,返回仍活着的窗口 pid,**同时结束排空**(`done` 以 `{stopped, now:true}` 结束,`status` 不再数那些 pid)。**`on` 把排空收回**(评审 2026-10-07 后补;W28):`start` / `reload` 带任一形态为开就取消排空,`done` 以 `{stopped:false, cancelled:true}` 结束,守护进程据此不退出,窗口里的 pid 之后走光也不停内核(新写的代理入口指着它);形态全关的 `reload` 不取消;`on` 失败时守护进程再 `drain`。排空只有一个:再来一次 `drain` 把它的 pid 并进去、拿到同一个 `done`。`uninstall`:`stopNow()`,等它退出(≤ 5 s),`removeBinary()`(被占 → `{removed:false, reason:<errno>}`,回执写原因,退出 1),`removeState()`(配置、内核的家目录、锁)。
- **Smart App Control 预检**(W74):未签名的 `asight-forwarder.exe` 在 Smart App Control 开着时很可能被拦,而代理模式没有它就没有引流;测到的只是它关着的情形,开着的没测。所以 `on` 先只读 `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy` 的 `VerifiedAndReputablePolicyState`(0 = 关,1 = 开,2 = 评估 [预期];键或值不存在 = 关,系统没有这项策略;读不到写「不知道」加原因:`timeout` 助手超时 · `denied` 助手死了或被拒 · `unparseable` 值不是 0、1、2,带原值):开或评估时,计划里写「Smart App Control 开着:未签名的 asight-forwarder.exe 很可能起不来,代理模式用不了」,仍让用户确认、仍去试(失败时上一条把原因记成 `smart-app-control`,一个代理入口也不写,§4.1)。asight 不改这个系统安全设置、也不替用户选;`doctor` 只写事实与选择(§10.4),不给改它的命令。OPEN 19。
- **代理模式总要它**(D43):首次 `on` 就要有。全部关着、也没有排空中的 agent 时不启动。
- 只转发与排空见 §4.2。
