# asight · RFC 4.8 — Windows 后端(4.11 的 win32 一面 · D47:引擎即代理)

> **状态**:采集器模型(install / on / off / uninstall、两类入口、上游五步、解密判定、持有者)在 [4.11](4.11-collector-model.md)(**D57**)。**本单元只写 Windows 后端**:认进程与读进程环境、常驻助手的动词、CNG 里的根密钥、`CurrentUser\Root`、系统代理的读取、自启、控制面、`doctor` 的命令、拓扑的事实;另有 §5 引擎的代理入口,两种 OS 共用。引流是 **D43**:Windows 只有代理模式,只读感知系统代理(D49)。采集路径是 **D47**:引擎是本机唯一的本地代理,每个入口组一扇引擎自己的回环门,身份在 accept 时刻从套接字读;门的文本在 [4.6](4.6-process-collector.md) §代理模式的门。
> **前置**:D31(按进程,不碰系统代理与整机流量)· D36(按用户运行)· D37(七个 harness)· D38(失败不静默)· D39(二元开关、off 保证、拓扑与诊断,[1.6](1.6-cli.md))· D40(全解密)· D43 · D47 · D49([4.7](4.7-netenv.md),只读)· D51(按名字认进程)· D55(证书归 install)· D57。引擎、记录、开关、改包与 Linux 共用 [4.6](4.6-process-collector.md)。
> **取代**:D31⑥ 的「Windows = WFP / WinDivert」(理由与实验数据见 §0)。
> **标注**:[E*] = §0 表里的 Windows 实测;「预期」= 没量过;[T0] = spike 阶段的实测。本单元的验收编号 W1… 只在本单元内有效;不使用的编号列在验收节末,不复用。

## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。install、on、off、uninstall 各做什么,入口写在哪,上游怎么取,什么时候解密,都按 [4.11](4.11-collector-model.md);本单元写 Windows 上这些事靠什么读、靠什么写。asight 不往任何 VPN 产品里写东西,不改系统代理,不识别、不显示 VPN 产品(D49)。

稳健只做两件事——asight 自己足够稳健,用户能手动从命令行撤销 asight:监管(§4.3、§7);`asight off [agent]` 在 asight 坏了时也能跑(§4.2)。哪些记录字段随引流不同见 §5.6(`capture` 与几个路径类字段)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1](标准用户上的自启没量过,§7);`install` 装 `CurrentUser\Root` 时 Windows 弹自己的「是 / 否」框;没有要管理员的步骤(D57) |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了 = 门死了,监管父进程重拉守护进程(§4.3);重拉期间 agent 连接被拒、其自身重试即到 |
| 覆盖 | 所有形态 | 每个形态都有 4.11 §1 的一个入口:第 1 类写进 agent 自己的配置,第 2 类是开关文件 |
| 身份 | 内核给 pid | 引擎在 accept 时刻对套接字定点提问(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。D43又删掉了 VPN 块:它只对 Clash Verge Rev 写得进,Verge 升级两次弄坏同类的写法,切换要 552 ms,进程规则看不到提权的 agent、还会把同名的形态一起引过来 [E3];而代理模式在实验室里 16 个形态有 15 个到了 mock(L5),没到的那个是 Claude Desktop 的信任,不是引流。还采不到的情形如实写(4.11 §1「没覆盖的」)。没有「with vpn / with no-vpn」之分:VPN 只决定上游(§2.2)。

- **助手**(`helper.mjs` · `helper.ps1`):一个常驻的 Windows PowerShell 5.1(`-NoProfile -NonInteractive -ExecutionPolicy Bypass -File`,不提权),守护进程经 stdin / stdout 的 JSON 行协议问它:`{id, verb, args}` → `{id, ok:true, data}` 或 `{id, ok:false, error}`。助手编完原生代码(`Add-Type`,C# 5)后先发一行 `{ready, proto:1, pid, ps, native}`,客户端在它之后才写请求,超时(默认 2 s;`ps` 是 10 s,第一次 `ps` 要经 CIM 读全部命令行)从写出算;超时的请求在助手(串行)答完它之前不再发同类的新请求。**只读,动词是闭集**(W1:客户端在 JS 里先拒绝未知动词,脚本里再核一遍;脚本只含 ASCII):

  | 动词 | 参数 | 答 |
  |---|---|---|
  | `version` | — | `{proto, pid, ps, os, native, nativeError?, sessionId?}` |
  | `proc-env` | `{pid, names}` | `{pid, startedAt, env:{<名>:<值>\|null}, cwd}`:一次读同用户进程的 PEB,答点名的环境变量与当前目录,从不交出整个环境;别的会话、提权的进程读不到 → `{error}`(`env-unreadable` 只指这种真失败);调用方按 pid + 启动时间缓存,一个进程只读一次 |
  | `ps` | `{all?, cmdline?}`(默认只列助手所在会话的进程) | `{sessionId, procs:[{pid, ppid, name, exe, cmdline, startedAt, sessionId, integrity, tokenDenied}]}`。`startedAt` 是 Unix 纪元毫秒;`exe` · `cmdline` · `integrity` 读不到为 `null`;命令行取自 CIM `Win32_Process`,每个进程只问一次(答案为空最多问三次),CIM 失败后 30 s 不再试;每次 CIM 调用 8 s 超时。每行另带 `cmdlineState` ∈ `ok` · `pending` · `cim-backoff` · `empty` · `not-asked` |
  | `tcp-table` | `{pids?, remotePort?, localPort?, states?}`(过滤;全空 = 全部) | `{rows:[{pid, state, family, localAddr, localPort, remoteAddr, remotePort}]}`。GetExtendedTcpTable 直读(原生 P/Invoke,非 CIM);v4 与 v6 都读,任一读不到就整个报错;`state` 用 MIB_TCP_STATE 的名字(`listen` · `established` · `close-wait` …) |
  | `reg-read` | `{hive, key, names}` | `{keyExists, values:{<名>:{kind, value}}}`,值不展开环境变量、`kind` 如实给(`REG_DWORD` `REG_SZ` `REG_EXPAND_SZ` …)。**白名单**(只放守护进程要读的):`HKCU\…\Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(4.7 §1);`…\Internet Settings\Connections` 的 `DefaultConnectionSettings`(WPAD 的标志位);策略 `ProxySettingsPerUser`,与它为 0 时 HKLM 的同四个值(§2.2)。白名单外、或不给名字(= 全读),拒绝。登录环境变量、策略键与 Smart App Control 不经助手:命令行以用户身份用 `reg.exe` 读(`policy.mjs`,§2.2、§6.3) |
  | `net-if` | — | `{interfaces:[…]}`:.NET `NetworkInterface`,不经 CIM,不含 MAC |
  | `route` | `{dest?}`(默认 `1.1.1.1`) | `{dest, ifIndex, iface}`:`GetBestInterface`,只查路由表,不发包 |
  | `token` | — | `{pid, elevated, elevationType, integrity, system, sessionId}`:助手自己的令牌(1.6 §1.5 的判据) |
  | `roots` | — | `{counts, certs:[{sha256, pem, stores}]}`:`CurrentUser\Root` 与 `LocalMachine\Root` 只读导出,按 DER 的 SHA-256 去重 |
  | `pipe-server` | `{name}` | `{exists, serverPid, exe, startedAt}`:以只读客户端打开该命名管道,问服务端 pid |

  - **失败的记法**:助手起不来(spawn 失败、退出、不发 ready、协议号不符、策略挡了脚本、原生代码编不过)= `helper-start-failed`(§12);起来之后死了 = 既有的 `helper-down`(带 `exit` 与 stderr 末 20 行,4.6)。每次死亡一条,在途的调用都拒绝;主动关掉不记。
  - **`ps` 与提权**(§10.1):`elevated` = 完整性 ≥ High,或令牌打不开而映像路径读得到(标「推断」)。


## 2. 入口与上游的 Windows 读取器

### 2.1 一种模式

入口、上游与解密的规则在 [4.11](4.11-collector-model.md);两种 OS 共用的门在 [4.6](4.6-process-collector.md) §代理模式的门。

- asight 不开 TUN、不当系统代理,不改系统代理与 VPN 的任何设置(D31④ · D43);只有指向门的 agent 经过它。
- 用户的 VPN 开着 TUN 时,引擎直连的上游照旧被 TUN 收进去,出口与 agent 原来一样。
- 若用户的 VPN / 代理按进程分流,它看到的连接来源是 asight(引擎的 `node.exe`),不是 agent:它点名 agent 的按进程规则不再匹配,域名规则照旧。D43 定只标一句,D49 起不再依赖探测:asight 在路径上就印(1.6 附录 A);放在一处:`status <h>` 印一行;`on` 的计划里不重复。

### 2.2 上游五步在 Windows 上读什么

上游按连接取,认出进程之后才算(4.11 §3 ⑥)。

- **第 3 步 · 进程环境**:读 agent 的**当前**环境(助手 `proc-env`,§1);Windows 的变量名不分大小写。值等于 asight 的某一扇门就跳过,沿创建它的进程一级级往上找:父进程取 `ps` 行的 `ppid`;父进程的启动时间晚于子进程(pid 已被复用)、父进程已退出、或中间隔着 Git Bash 这类自带环境的壳时,算「不知道」(4.11 §1 第 5 步,`prior-proxy-unknown`)。
- **第 4 步 · 系统代理**:只对跟随系统代理的形态(描述符 `proxy.systemProxy`)。读 `HKCU\…\Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`;策略 `ProxySettingsPerUser=0` 时读 HKLM 的 Internet Settings;WPAD 自动检测(`Connections\DefaultConnectionSettings` 的标志位 `0x8`)开着按 PAC 处理,不当直连。「是 PAC」:`AutoConfigURL` 里有非空的地址就算,不管 `ProxyEnable`(4.7 用同一条;OPEN 27)。PAC → 跟随者 `not-routed` · `system-proxy-pac`(asight 不执行 PAC)。WinHTTP 的静态代理不读:这些形态的客户端都不用它(依 D49①)。
- **持久环境变量与策略**(4.11 §3 ⑤ ⑩):`NO_PROXY` 里「用户原来的值」另并上 `HKCU\Environment` 与 `HKLM\…\Session Manager\Environment` 里的值;描述符声明的策略键(Claude Code 的托管设置、Claude Desktop 的托管配置)也在这里读。两者都由命令行以用户身份用 `reg.exe` 读(`policy.mjs`),只读描述符声明的键,不经助手。

| 本机网络 | 跟随系统代理的形态 | 不跟随的 | agent 自己配了代理的 |
|---|---|---|---|
| Verge · 系统代理开 · TUN 关 | 系统代理 `127.0.0.1:7897` | 直连 | 它自己的代理 |
| Verge · TUN 开 | 系统代理开着时同上;关着时直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| v2rayN · 系统代理开 | v2rayN 的本地端口 | 直连 | 它自己的代理 |
| 别的 TUN VPN · 系统代理关 | 直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| 没有 VPN | 直连 | 直连 | 它自己的代理 |
| 系统代理是 PAC | 不接 · `not-routed` | 直连 | 它自己的代理 |

- **一条连接只有一个上游**。原本分两路的,接上后都走那一个:Codex 的 HTTP 跟随系统代理、WebSocket 直连 [E2][E16],接上后 WebSocket 也经系统代理,报 `egress-differs`(提示,1.6 附录 B)。
- **asight 自己的值不是上游**:值是 asight 某一扇门的地址,或带 asight 的形状(userinfo 是组凭据的形状、主机是回环,端口不论新旧)= 上一次 asight 留下的残留,任何一步都跳过它(`isAsightDoor`,4.11 P7)。
- **系统代理变了**(开、关、换端口):守护进程每 5 s 读上面那几个值(§9),变了写一条 `netenv-change`;之后的新连接按新值取上游。不写入口、不碰 agent 的设置,不算失败(1.6 附录 A)。W71。
- `on` 之后系统代理改成 PAC:跟随者的上游留在上一次读到的值,报 `system-proxy-pac`(提示);要按 PAC 走就 `asight off <h>`(OPEN 17)。
- **agent 自己的代理变了**(入口不再是 asight 写的值):agent 已绕过 asight,`proxy-changed`,`status` 印 `asight on <h>`(1.6 附录 A、§10.3)。
- 带凭据的上游:凭据只在清单里(0600),只用于这个 agent 的连接(§5.2,D30)。
- **绕过表**(评审 2026-10-07 后补):没有 asight 时,命中系统代理的 `ProxyOverride` 的目标、或命中 agent 自己代理的 `NO_PROXY`(同一入口里的原值)的目标,agent 是直连的(内网模型网关常见)。所以每个组带一张绕过表:`<local>`(没有点的主机名)· `*.corp.com`(后缀)· `10.*` 一类(IP 段)· 精确主机。译不了的写法不进表,`status` 写「N 条绕过规则 asight 读不懂,按走上游处理」(OPEN 21)。命中绕过表的目标:引擎直连(`lookupIngress` 按 CONNECT 目标判,`bypassHit`,§5.2)。这些连接照常被采集,出口还是 agent 原来的那一跳。
  - **译法**(`translateBypass(文本, 'wininet' | 'no-proxy')`):`ProxyOverride`(`;` 分隔)里 `<local>` → `local`;`*.corp.com` → `domain-suffix`;`10.*` · `10.1.*` · `10.1.2.*` → `ip-cidr`(`/8` · `/16` · `/24`),四段齐全 → `/32`;裸主机名 → `domain`(WinINET 里它只命中自己)。`NO_PROXY`(逗号或空白分隔)里裸名与前导点 → `domain-suffix`,`10.0.0.0/8` 一类的 CIDR → `ip-cidr`。名字 `localhost` 另加一行 `ip-cidr 127.0.0.0/8`。读不懂的不进表、计入 `untranslated`。每一行都过 `bypassRuleOf`(`core/upstream-shape.mjs`),所以用户的任何写法都不会让计划抛错。`bypassHit(表, 目标)` 是共享核心拨上游时用的同一份判法。
- **上游的协议**(W5):`http://`、`socks5://`、`socks5h://`(后两者同一种:都把域名交给代理解析)接得上。`https://`(到代理那一跳是 TLS)与 `socks4` 等 v1 不支持:`on` 不接这个形态,`not-routed`,doctor 码 `proxy-unsupported`(1.6 附录 B)并写明协议,不悄悄改走别的出口(OPEN 21)。
  - **读法**:不带协议头的 `host:port` 按 HTTP 代理读;端口缺省 http 80、socks5 1080;IPv6 去掉方括号;含空白或控制字符的值不读 = `not-routed` · `upstream-unparseable`;**校验器不收的地址也不读**(判的是 `core/upstream-shape.mjs` 的 `upstreamOf`,不另抄一份:`http://a,b:3128` 的 host 带逗号,URL 解析器放行、校验器抛),同为 `upstream-unparseable`。`https://`、`socks4`、`socks4a`、不带 5 的 `socks`、别的协议头 = `not-routed` · `upstream-protocol` 带 `protocol`。
  - **凭据是引用**:答案里没有用户名与口令,只有 `credentialed:true` 与 `auth_ref`(从哪取:清单里的 `prior_value`,或进程环境里的值);拨这一条连接时才取(§5.2),`proxyAuthOf(解出的文本)` 是读它们的唯一一处。系统代理的 `ProxyServer` 里带凭据 = `not-routed` · `upstream-unparseable` · `detail:'credentials-in-system-proxy'`。
  - **`ProxyServer`**:`https=` 的那一项优先,其次是不带协议名的那一项;只有 `socks=` → `not-routed` · `upstream-protocol` · `socks`;只有 `http=` `ftp=` 一类 → 直连;`ProxyEnable` 不是开 → 不看 `ProxyServer`。
  - **`egressDiffers`** 只在上游是系统代理、该形态描述符的 `proxy.systemProxy.http` 为真而 `ws` 为假、且 `proxy.branches` 含 `ws` 时出。
  - **系统代理读不到**(助手超时、被拒):跟随者 = `not-routed` · `why:'system-proxy-unreadable'` · `detail:<原因>`,不当「直连」猜。**`on` 之后**的变化带 `last`:系统代理变成 PAC 或读不到时,跟随者留在 `last` 的上游并带 `hint`(OPEN 17)。
  - **读与盯**(只读):`readSystemProxy({helper})` 读 `Internet Settings` 的四个值(另带 WPAD 标志与 `ProxySettingsPerUser`);读不到 = `{ok:false, reason, detail}`,`reason` 取 1.6 附录 A 的闭集。`watchSystemProxy({helper, everyMs: 5000, initial})`:第一次读是基线、不发事件;四个值任何一个变了,或由能读变成读不到、或反过来,发一次 `change`;连续读不到不算变化;上一次读还没回来时下一拍等它;**有一次 `reg-read` 超时而助手还没答它时跳过这一拍**(助手是串行的);`stop()` 之后不再读不再发。

### 2.3 形态与入口组

每个形态的入口、证书载体、信任来源与何时生效都是描述符的数据(4.11 §2),本单元不另列。**入口组 = 路由 id**:共用一个路由的形态共用一个入口、一扇门(一个文件键只装得下一个 URL);门的端口、口令都按组。形态 id 写成 `<harness>.<形态>`。

- **认进程**(D51;4.6 §识别进程):规则只有一份——registry 编好的名单(预设 + `~/.asight/agents.json`),`registry.match` OS 无关;门(§5.3 的 `identify`)与 tracker 都问它,Windows 不另有匹配表。win32 的事实多一样 `cmdlineState`:为 `pending` / `cim-backoff`、且名字在任一名单上时答 `pending`(还不知道,不是不认:参数、读 argv 的排除项与 Chromium 角色都要读命令行;只有不读 argv 的排除项可先答 `excluded`),门 `cmdline-pending` 只转发、**不缓存**这个答案,该进程的下一条连接再问(W78);`empty` / `not-asked` 时按没有参数判。`install` 把同一份名单编进清单的 `liveness.<h>.identity`,持有者按它判(4.11 P12,D50①),不另有一份。这些进程表的事实也是持有者判定的 Windows 后端。
- 描述符名单里的名字在 VM 上量过的真路径与命令行(用户目录打码)是 `test/helpers/proc-seeds.mjs` 的回归种子,不是规则:名单的规范化(4.6)对每条种子给出描述符里的名字;没量过的装法(winget、厂商安装脚本、商店、scoop)名字相同即认,实测留给 W62。

## 3. 引擎的门(Windows 接线)

照 [4.6](4.6-process-collector.md) §代理模式的门。Windows 的差别:

- **PAC 组的门**(`auth:false`)在 accept 时只放行属主用户与守护进程相同(按 SID)的进程,别的拒绝并记录(4.11 §3 ③)。
- **引擎崩溃**由监管父进程重拉守护进程(§4.3、§7)。
- **端口区间**:`on` 在 17991–18989 里给每组选一个空闲端口(引擎自己的 ingress 端口见 §5.1)。

## 4. 开与关

### 4.1 怎么生效

- **`on <h>`**:命令行先请守护进程开这一组的门(`attach()`,引擎的 `listen({groups})`,幂等)并读回,再写第 1 类入口、建开关文件(4.11 §3 ①;W12)。门开不了:一个入口也不写,回执写原因,`on` 退出 1;崩在任一步之后再 `on` 续完(1.6 §3.1 的幂等 · §3.2)。
- **`off <h>`**:命令行撤入口、删开关文件;守护进程让这一组的门只转发,持有者都退出、也没有开着的连接之后关门(4.11 §3 ②)。
- **复核**:`attach()` 的答案是事实(门开了哪些、开不了的组与原因),不靠读回什么外部进程;`status()` 的 `attached` = 开着的组里有门在。

### 4.2 off 保证(照 1.6 §3.1;例外如实写)

| `off` 做什么 | 之后保证什么 | 例外(1.6 §3.1 第 2 种例外) |
|---|---|---|
| ① 期望态写 off;② 撤第 1 类入口、删开关文件(只撤 asight 写的值);③ 门在持有者都退出前只转发;④ 引擎按 1.6 §3.1 关在途连接 | 新启动的 agent 走原来的路;持有者都退出后引擎不在任何 agent 的路径上 | **持有者**(on 期间启动、还活着、可能读过入口的进程,闲着的也算;4.11 §3 ②)重启前仍连着门(只转发,不经引擎解密、不记录)。`status`:「还有 N 个 agent 连着 asight 的门,重启它们之后 asight 就完全退出」。`off --now`:立即断开,回执列出会断的 pid(操作者的显式意图) |

- **监管父进程先停**(评审 2026-10-07 后补):不带参数的 `off` 与 `uninstall` 要停守护进程时,先停监管父进程(核对 `supervisor.lock` 的 pid 与启动时间后停),再停守护进程;顺序反了,父进程会把刚停的守护进程拉回来。
- 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §3.1 第一条例外)。
- **独立撤销**:守护进程不在、源码也不在时,独立副本 `~/.asight/bin/asight-off` 做同样的撤销(1.6 §3.4;`src/off/win32.mjs`)。先停监管父进程。W54。

### 4.3 稳健:用户的两句话

稳健只守两条:trocar 自己足够稳健,且用户随时能手动从命令行撤销 trocar。只做这两件,不另加机制:

1. **稳健**:监管父进程监管守护进程(§7,退避重拉)。引擎死了 = 门死了,守护进程被父进程拉起、门随之重开;重拉期间 agent 连接被拒、其自身重试即到,`status` 照实写(0.0 D47)。W47 · W49。
2. **命令行撤销**:`asight off [agent]` 在守护进程坏了、源码不在时也能跑(§4.2 独立撤销)。撤了之后重启那个 agent,它就不经 asight。W54 · W55。
3. **卡住(没死)**:同样不另加机制,不设看门狗、不撤入口;门照收连接,agent 等着;`status` 与看板按 D38⑥ 判「没响应」,第 2 条照常可用(依本节开头两条与 0.0 D47 的「引擎稳定」前提;macOS 同)。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 的入口与它那几组的门;别的 harness 的门、上游与入口不变,在途连接不断(W55)。
- 新装了一个 harness:`on` 给它的组选端口、开门(前提:它的 install 项都在,4.11 §3 ⑪)。
- 用户自己改了某个 agent 的代理:`proxy-changed`,`on <h>` 把新值记成上游再指回门(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`),另加每组的门(§3)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定。端口被别的进程占了:守护进程不自己换,记 `engine-port-taken`(失败类;触发点是 `engine.listen` 的 `EADDRINUSE`;W73);下一次 `on` 换一个空闲端口并改写入口(4.6 §代理模式的门)。`doctor` 给查占用者的命令(§10.4)。
- 认两种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)。别的开头:关掉,记 `ingress-unknown`。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。完全不带 `Proxy-Authorization` 的 CONNECT 是 Basic 认证的第一步(RFC 7235),不是凭据不对:回 `407` 质询(`Proxy-Authenticate: Basic`),计数 `challenged`,不记失败行;凭据不对(token 不符、用户名不认识)才记 `ingress-auth-failed`(VS Code 的 Chromium 网络服务先不带凭据,收到 407 后由主进程用 `http.proxy` 里的 user:token 重发;1.140 的 `doResolveProxyCredentials` 实读)。`auth:false` 的门收没有 `Proxy-Authorization` 的 CONNECT(门的三重授权在进程判定上,§3)。
- 别的 CONNECT:引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §3.1)。
- **实现细节**:
  - 开头:一个连接 10 s 内读不全开头记 `ingress-unknown`;CONNECT 的目标不是 `host:port`(IPv6 要方括号)记 `ingress-unknown`。SOCKS5 的问候里没有用户名密码一项 → 回 `[5,0xff]`,记 `ingress-auth-failed`;SOCKS5 的非 CONNECT 命令回 `07`,记 `ingress-unknown`。
  - 鉴权:token 先验、常数时间(两边先取 SHA-256 再比),验过才查 `lookupIngress`;查不到(`null`)= 未知用户,同样是 407 / SOCKS5 回 `02`,记 `ingress-auth-failed`。失败记录带 `peer` 与用户名,**从不带 token**:用户名只在形如路由名且不含 token 时照写(截短),否则写占位 `(not a route name)`。`lookupIngress` 抛错 → 回 `502` 与 `where:'engine'` 的 `loader-down`(或 `loader-timeout`);**例外**:抛的错带 `code:'upstream-unavailable'` → 同样回 `502`,记 `where:'ingress'` 的 `upstream-unavailable`(带 `why`)。
  - 上游拨通之前客户端走了:销毁上游,不写连接行。上游成功之后到 `200` 之前不会有字节写给客户端。
  - `engine.close()` 先关掉不是 flow 的入口连接(握手中的),再等 flow 收尾。
  - `engine.listen({port, hosts, ingress:{port}, groups})` 返回 `{port, ingressPort, groupPorts}`;redirector 没有 `lookup`(Windows)就不开透明监听,`port:null`;要入口就要 redirector 有 `lookupIngress` 且 `createEngine` 给了 `ingressToken`,否则抛 `TypeError`。`engine.stats().ingress` = `{connections, flows, health, authFailed, unknown, refused, unreachable}`(W42),只在开了入口时有。

### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` = 按名单认出的 harness(不是门的;D51⑥) |
| `door` | 门组 id(如 `codex.env`):连接来的那扇门。身份就在套接字上(§5.3),不靠凭据声称;新行不再带 `form`(读取侧容忍旧行带它) |
| `capture` | `proxy` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth}` · `{kind:'socks5', host, port, auth}`。按 4.11 §1 的五步,认出进程之后取(4.11 §3 ⑥;Windows 的读取器见 §2.2);CONNECT 目标命中绕过表时是 `{kind:'direct'}`(W72)。`lookupIngress` 把 `auth_ref`(清单里的 `prior_value`)解成 `auth:{username, password}` 交给入口;入口只在拨这一条 agent 连接的前导里用它,交给 `handleFlow` 的 meta 里只剩 `credentialed:true`,凭据不进 flow、不进任何记录 |
| `pid_source` | `socket-table` · `null` |
| `negKey` | 负缓存的键(§5.5)。有 pid 取 `"<pid>"`,否则取门名(组 id);不补的话没有 pid 的连接会共用 `null` 一个键,互相毒化 |

- **`lookupIngress` 的答案**(共享门核心;W16 · W72):`user` 不是本引擎的一扇门(组 id)、计划里没有这个组的答案,或没有 `target` → `null`(入口答认证失败)。目标是该组自己的门端口(127.0.0.1:<组端口>)→ `null`(一个通过门到门自己的环:没有正当的流量这么问)。**该组已经 `off`、门因为还有持有者而开着**(4.11 §3 ②):不答 `null`(那是 `407`),而是**照样接**:meta 为 `{pid:null, decrypt:false, door:<组 id>, upstream:<该组的上游,绕过表与登录照常>, negKey:<组 id>, skip:{not_captured:'untracked', reason:'group-off'}}`,不查套接字表;该组没有上游可拨才答 `null`。别的目标 → meta:`{pid, agent, decrypt, capture:'proxy', door, exe, upstream, pid_source, pid_ms, negKey, skip?}`。`upstream` 在认出进程之后算(第 1、3 步按进程取);认不出进程时只用第 2、4、5 步(4.11 §3 ⑥);`skip` 只在不解密、而表上没有一行可说原因时有:`{not_captured:'untracked', reason}`(`pid-unresolved` · `facts-unavailable` · `other-user` · `outside-host-set` · `agent-helper` · `cmdline-pending` · `not-an-agent` · `ambiguous` · `harness-off`,§5.3;`reason` 是自由文本,`not_captured` 在闭集里)。上游拨不通(`no-upstream`:该组没有上游可拨;`upstream-credentials-unavailable`:带登录的上游读不到登录)→ **拒绝**,Error 带 `code:'upstream-unavailable'` 与 `why`,消息里没有登录;入口写自己的 `upstream-unavailable` 失败(`where:'ingress'`,§12)并回 502。`auth_ref` 只在拨这一条连接时解:`resolveLogin(ref, …)`(清单里的 `prior_value`,或按 pid 缓存的那份进程环境;文本经 `proxyAuthOf`;找不到是 `null`,不抛、不猜),守护进程把它绑好当 `authOf` 交进来。
- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。
- **上游怎么拨**:`direct` 直连目标(域名由系统解析);`http` 向 `host:port` 发 `CONNECT <目标> HTTP/1.1`(带 `Proxy-Authorization: Basic` 当且仅当有凭据),2xx 成功,别的状态把代理的回应原样转给 agent;`socks5` 做问候、RFC 1929、CONNECT(目标是 IPv4 / IPv6 字面量用 ATYP 1 / 4,其余用域名 ATYP 3),`rep ≠ 0` 回 `02`。代理回成功时与回应同一块到的上游字节留着、按序交给 flow(算上游先说话,4.6)。拨不通 → `502` / SOCKS5 失败回复,连接行 `decision:'error'`、`not_captured:'error'`、`error:{type, message, side:'upstream'}`;代理拒绝 → 连接行 `decision:'tunnel'`、`not_captured:'proxy-refused'`、`reason:'proxy-status-<n>'` / `'socks5-reply-<n>'` 等、`upstream.reply`。代理的回应第一行不是 HTTP 状态行算拨不通、不算拒绝:`502`、行 `error.type:'bad_proxy_reply'`。**等代理没有时限**(D31),但不静默(D38):连代理与握手合计超过 `upstreamSlowMs`(5 s)还没回应,记一次 `upstream-slow`;客户端先走了就不记。
- **拨不通要报**(W73):拨上游失败时,除连接行外另写一条失败 `upstream-unreachable`(`where:'netenv'`;同一形态 60 s 内最多一条),并进该形态的 `status` 原因(1.6 附录 C);doctor 给 `proxy-dead` 同样的查端口命令。上游代理拒绝(`proxy-refused`)是另一回事,不报它。
- **一条 agent 连接只拨一次上游**(评审 2026-10-07 后补):入口拨好的上游连接交给 `handleFlow` 用。之后 4.6 的「让路」要重拨时:上游不带凭据才重拨;上游带用户的代理凭据,就关掉这条连接,同 4.6 隧道连接的做法(不变式 1)。W15。不带凭据时第二次拨是新的一轮握手,重拨失败 → 连接行 `decision:'error'`,客户端的连接关掉。

### 5.3 身份:accept 时刻、从套接字读(0.0 D47;W4)

引擎的门收下连接,**peer 4 元组就是 agent 的出站套接字**(中间没有别人):两问定点、无扫描——

| 问 | 怎么做 | 答不出 |
|---|---|---|
| 谁(pid) | 助手 `tcp-table`(GetExtendedTcpTable,~5 ms [E6]):`{localPort: <peer 端口>, states:['established']}`,本地端等于 peer 地址:端口的那行答 pid(`pid 0` 的行是 TIME_WAIT 残留,不算;引擎自己的 pid 排除)。预算 250 ms,与拨上游并行 | 无行、多行、慢、读不到 → `pid:null`,连接 splice `untracked`(`pid-unresolved`),**绝不猜**:错的 pid 会让引擎解密一个不信任 asight 的进程,把它弄断(4.8 W4)。超过预算不记失败(慢不是不可用);读不到才记 `socktable-unavailable`,每次调用一条,由记录器折叠 |
| 是什么(哪个 harness) | 该 pid 的助手 `ps` 行(映像路径、命令行、启动时间、完整性):`identify`(= `registry.match`)按名单判(§2.3,4.6 §识别进程)。**按 pid+startedAt 记住,一生问一次**(同一 pid 复用为新进程 = 新的启动时间 = 再问;`pending` 不记) | 门依次判 pid → 事实 → 本用户 → 宿主树 → 名单 → 期望态 → 信任判定(§5.4):pid 没了(连接刚建立进程就退出的竞赛)、事实问不到 → `facts-unavailable`,同上 splice;本用户(win32 的助手快照只含本会话,这一道恒过);宿主进程树组、名字在 `hosts.processes` 而目标不在它的 host 集上 → 只转发(`outside-host-set`,§3);命中排除项 → `agent-helper`;不在名单上 → 只转发(`not-an-agent`,另一条折叠的 `process-unknown`);两个 harness 都认领 → `ambiguous`;认出的 harness 期望态为关 → `harness-off`。**名单上的 agent 连到别家的门照判**:按它自己的 harness 判信任,`agent` 记它的 harness,上游取这扇门组的(这个进程不经 asight 时会用的那个)(取代「非本门本组的形态 → 只转发」这一安全臂,理由 D51⑥:判据是进程自己,不是它连的门) |

- 没有进程快照的差分监视(`exec` / `exit` / `facts-update` 的 2 s 轮询)、lsof 式候选集、demand-poll 与去抖(0.0 D47:不做进程扫描)。peer 进程按定义活着(它刚连上),一连接两问即全部成本;`flows/` 连接行记 `pid_ms`。
- 命令行还是 `pending` 时(`cmdlineState`):accept 时刻没有「以后再判」——名字在任一名单上,这一问就答 `pending`(参数、排除项与 Chromium 角色都还读不到),连接 `cmdline-pending` splice(宁可少采,不可采错),**这个答案不缓存**;该进程的下一条连接再问一次(CIM 的答案通常已到;W78)。
- **判定等人**:门把新 pid 的事实作为 `exec` 说出,lookup 等 tracker 的 `watch()`(默认 5 s 上限;等不到 = 墓碑 `{decrypt:false}`,一生等一次、不按连接等,tracker 事后答了就盖掉)。
- **验收**:W43 [WinVM] 用真值核对(同一形态 3 个进程,2 个已信任、1 个未信任,200 条并发连接,另有 `on` 之前就开着的长连接),错认必须是 0;另量 p50 / p90。

### 5.4 信任判定

- 判定 = [4.11](4.11-collector-model.md) P11,按描述符判;Windows 只供事实(§5.3 的 `ps` 行,`proc-env` 的环境与当前目录)。判定按 pid + 启动时间记,pid 复用的新进程不继承旧进程的判定。
- **提权的进程**(保守规则,E3):完整性 ≥ High(或推断提权)的进程不解密,`elevated-agent`(§10.2 行 h)。套接字表与映像路径对提权进程读得到,这个判决是保守取舍不是能力缺口。
- **没有 pid**:连接 splice `untracked` · `pid-unresolved`,一行元数据(D40:解不了密就透传并记)。1.6 §3.1「`off → on` 后在跑的 agent 透传、不被弄断」由此成立。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(门名, host)`——门名即组 id,组内每个形态一个入口,不同组互不毒化 [E15]。
- 负缓存的失败事件与清除事件都带 `neg_key`(有 pid 时是 `"<pid>"`,没有时是组 id)。读取侧(`src/health/flows.mjs`)按 `(neg_key ?? pid, host)` 归并,清除按 `neg_key` 清。W17。
- 条目只在内存:pid 退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。

| 字段 | Linux 驱动模式(eBPF) | Windows 代理模式 |
|---|---|---|
| `capture` | `transparent` | `proxy` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` |
| `proc.pid` | 内核给 | 尽力,可为 `null` |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` |

- 其余字段 MUST 逐字节相同。验收:同一 mock 调用分别经 Linux 驱动模式与 Windows 代理模式,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?, reply?}`(不含凭据;`reply` = 上游代理的回应状态码)。`bytes_up` / `bytes_down` 仍是 agent 自己那条连接上的字节:经入口的连接不含入口读走的开头(CONNECT 或 SOCKS5 握手)与 asight 的回应(那些是 asight 与客户端之间的字节,不是 agent 的)。
- **代理前导**:入口收到的 CONNECT 是客户端(经入口指向)发的、带门的口令,不是 agent 的字节;引擎发给上游代理的前导是 asight 写的。两者都不记成 `prelude`(不变式 4)。
- 读取侧:`capture` 多一个值 `proxy`;观测者效应表对两种值都适用;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

## 6. 证书(Windows)

证书归 `install` / `uninstall`(4.11 §1)。本节只写 Windows 上的做法。

### 6.1 根的密钥:不可导出的 CNG 密钥(4.11 P1)

- 一次性的 `custody.ps1`,不进常驻助手(4.11 §3 ⑯):动词 `create` · `exists` · `issue` · `remove`,每次调用起一个 PowerShell、做完就退。
- 密钥 P-256,`ExportPolicy=None`;有 TPM 时放进 Microsoft Platform Crypto Provider,没有时用软件 KSP(R3-W1)。用 `X509SignatureGenerator` 签(R3-W2);`issue` 自己拼中间证书(pathLen 0、只用于服务器认证、7 天、颁发者是根),不收调用方给的待签内容(4.11 CM3)。
- 根标「只用于服务器认证」,所以 Windows 不认它签的代码。
- 剩余风险:本用户名下的程序能直接调用这把密钥签出被信任的证书,也能删掉它,只是拿不走私钥(4.11 §1)。

### 6.2 用户级根(4.11 P3)

- 装:`certutil -user -addstore Root <根>`;Windows 弹「是 / 否」框,框就是同意。撤:`certutil -user -delstore Root <thumbprint>`。
- 查(装前判在不在、撤前判在不在):`certutil -user -store Root` 列出用户自己的整库,按指纹找;不看「按指纹查一张」的退出码——同一条查询在 VM 上按调用方退出 0、`CRYPT_E_NOT_FOUND` 或 `NTE_NOT_FOUND`。列不出来(起不来、超时、非 0)是错误,不当「不在」(D38)。
- 从不写 `LocalMachine` 的任何库;没有要管理员的步骤(D57)。

### 6.3 安装目录包装

- 照 4.11 P8。Windows 的包装是 `wrapper.cs` 在 `install` 时用系统自带的 `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 编出的小程序;目标是 PE 原生可执行文件(Kimi 的 `kimi.exe`)。包管理器生成的 `.cmd` / `.ps1` / sh 启动脚本不放包装,`status` 报 `not-users-file` 并写明原因(4.11 §3 ⑯)。
- **Smart App Control**:`install` 先以用户身份读它的策略值(`reg.exe`,`VerifiedAndReputablePolicyState`);开着时不放包装(被拦的包装会让 `kimi` 起不来),`status` 报 `smart-app-control`。

### 6.4 合并包与引擎的 Windows 根

- Windows 上只有 Z-Code 的合并包:Node 自带的根 + asight 根,不含 Windows 根(4.11 §1 install 第 4 条)。
- `windowsRoots`(`src/off/os-roots.mjs`)只给引擎验上游用(§7;4.11 §3 ⑭):Node ≥ 22.15 用 `tls.getCACertificates('system')`,更老的由助手 `roots` 动词只读导出 `CurrentUser\Root` 与 `LocalMachine\Root`。每张证书先用 Node 的 `X509Certificate` 解析一遍,解析不了的丢掉、计数,回执与 `status` 各一行(`system-roots-unparsable`);[T0] 量过:一块解析不了的证书让 rustls 整包拒绝。不用 macOS 的 `cert.pem`:企业与杀毒软件的 TLS 检查根只在 Windows 库里。

## 7. 守护进程、自启、控制面

- **守护进程** = `node <asight> daemon`。上游的信任集照 4.6 §引擎 第 5 步自己拼:Windows 系统库这一份由 `windowsRoots()` 给。`on` 先查 `process.versions.node`,低于下限(Node 20)就拒绝并给 `doctor` 一行。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(1.6 §1.5 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。**判据**(W25):四个命令同一个判据——经 `execTool` 跑 `whoami /groups /fo csv /nh`,按 SID 判:完整性标签 `S-1-16-12288` 及以上或 SYSTEM 的 `S-1-5-18`(未拆分令牌的例外照 D53③ 读 UAC 设置)。`on` 与 `daemon` 原来为这一问起一个助手,它的 C# 编译是 `on` 里最贵的一步(Windows 测试机实测 2026-10-17:`on` 5.8 s 里占 1.2 s,守护进程应答前再占 0.6 s,超了 5 s 的启动预算);`off` 与 `uninstall` 本来就起不了助手。**读不到令牌不是拒绝**:记「不知道」加原因、往下走。**每次启动**:让 `custody.ps1 issue` 签一张中间证书(4.11 P2);它答 `no-key`(密钥不在)就记 `cert-key-missing`、门只转发、`status` 提示再跑一次 `asight install`。不先单问 `exists`:每问一次是一个 PowerShell(VM 上 0.4–0.6 s),在守护进程应答 `on` 之前。
- **自启**(D61:由 `install` 注册并拉起守护进程,`uninstall` 删掉;`on` / `off` 不碰):每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`。动作 = `conhost.exe --headless "<node.exe>" "<asight.mjs>" daemon --supervise`(无窗口 [E20];`--supervise` = 任务拉起的是**监管父进程**,由它拉起真正的守护进程并在它非 0 退出时重拉)。设置 = 失败后 1 分钟重启、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML` 注册并启用;不带参数的 `off` 停用;`uninstall` 删除。**任务 XML 与单元的形状**(W24):`enable` 把它复制成带字节序标记的 UTF-16LE 副本交给 `schtasks`,读完即删。单元的形状与 Linux 的 `userUnit` 相同。**登录时只留一条启动路径**:`enable` 注册任务成功后,把 asight 先前后备写下的 Run 值取下;改用后备时,先前注册的任务 `/Change /DISABLE`。`disable()` = `/Change /DISABLE`,`remove()` = `/Delete /F`;**`/Query` 没跑起来不是「不在」**,是失败(退出码 1 仍当「不在」,W47)。**`off` 与 `uninstall` 自己也动任务**(2026-10-12 补):注册不随清单走,`off` 的第 5 步与 `uninstall` 在清单撤销之外**直接** `schtasks /Change /TN \asight\collector /DISABLE`(uninstall:`/Delete /F`)。
- **「不需要管理员」没证实过**(如实写):实验室每次都是管理员账户的过滤令牌 [E20 的限定];标准用户能不能注册带登录触发器的任务、`RestartOnFailure` 能不能拉起被杀的守护进程,都没量。**[T0] 量过的半边**:`RestartOnFailure` 拉不起被杀的守护进程,**所以任务只负责登录时拉起一次,崩溃后的重拉必须由监管父进程做**。W47 在产品实现后在标准用户上补测。
- **自启的后备**:`schtasks /Create` 被拒 → `install` 自动改用 `HKCU\…\Run` 的一项(值名 `asight-collector`,入账、先记原值),动作同上;回执写「计划任务注册被拒,改用登录启动项」并给原因,事件 `task-register-failed`(失败类,但 `on` 不失败)。**细则**(W24):「被拒」= `schtasks /Create` 起得来而拒绝,或起不来;写之前先 `reg query` 那一个值;写完再读回核对(生效要复核);**`reg query` 的输出是 reg.exe 按控制台代码页写的**,核对时 ASCII 部分逐字节相等、每一段非 ASCII 字符不限读成什么。入账条目 `{kind:'run-key', hive, key, name, value, prior}`。
- **监管父进程的退出规则**(W24 · W28 · W46):守护进程以退出码 0 退出 = 被要求停:父进程随之退出,不重拉;非 0 或被杀才按退避重拉。父进程把自己的 pid 与启动时间写进 `supervisor.lock`。不带参数的 `off` 与 `uninstall` 要停它时,**先停父进程**,再停守护进程。**细则**:① 退避 1、2、4、8、16、32、60 s 封顶,**守护进程这次活满 60 s 才死,退避从头算**。② `supervisor.lock` = `{pid, startedAt}`;**父进程是单例**:锁以独占方式建;锁已在时核对持有者,还在跑 = 第二个父进程,退出码 0。③ 守护进程起不来当成一次失败,同样退避;④ 父进程收到 SIGINT / SIGTERM / SIGHUP 或 `stop()`:结束守护进程、不再重拉、退出码 0、删锁。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`。CLI 读它再连。**token 怎么用**(W26):每个请求带头 `x-asight-token: <64 位十六进制>`;服务端在查路由之前先核它(定时安全比较),缺或错一律 401。
- **文件权限**:Windows 上「0600」没有意义。asight 的文件都在 `%USERPROFILE%` 下,靠用户目录默认的 ACL;asight 不另设 ACL,单元测试在 win32 上不断言权限位。实验室用 `icacls` 核一次(W26)。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:监管父进程拉起;门(引擎的 listener)随引擎死、随重拉开。

## 8. 卸载时清理的遗留目录

`uninstall --purge-data` 的清单(1.6 §3.6)包含采集器目录里的 `kernel\`、`kernel-archive\`、`forwarder\`:旧版本的安装可能留下它们,现行采集器不创建也不读;清掉它们是清理遗留,不停任何在跑的东西。`off` 不碰它们;安装清单里 `kind:'forwarder-binary'` 的条目由 uninstall 按清单撤。

## 9. 本机网络环境:Windows 一侧

系统代理与 agent 自己的代理的读法在 [4.7](4.7-netenv.md) §1(D49;只读)。本单元的上游只读系统代理与 agent 原值(§2.2),不识别产品,拓扑(§10)据此画。守护进程的 5 s 核对(4.6 §开关语义)另读 `HKCU\…\Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`:变了写 `netenv-change`,之后的新连接按新值取上游(§2.2);另看各入口文件、开关文件、插件的大小与 mtime,与包装的哈希(入口还有没有效,§10.4 `entry-changed`)。asight 从不写用户的 VPN / 代理软件(4.7 N15)。

### 10.1 每一跳从哪读

| 跳 | 读什么 |
|---|---|
| agent | 助手的进程快照:映像路径、启动时间、完整性(读不到写「不知道 · denied」)、创建链(父进程,§2.2)。**提权的判法**:完整性读得到且 ≥ High → 提权;令牌打不开而映像路径读得到 → 判提权,标「推断」 |

| agent 的代理与上游 | 4.11 §1 的五步:钩子值、清单的 `prior_value`、进程的当前环境(`proc-env`,沿创建链往上找)、系统代理(只对跟随者)、直连;找不回写「不知道 · `prior-proxy-unknown`」 |
| 端口属主 | 套接字表的 LISTEN 行与属主 pid → 进程快照 |
| 引擎与门 | `ingress.json`(引擎入口与各组端口的形状)+ 守护进程的 `/status` 回答(哪些门开着、每个 agent 的信任、负缓存);`forwarder` 字段按 4.8 §10 的形状填:**asight 本地代理这一跳就是引擎的门**(pid 是守护进程的,up = 守护进程答了) |

- 一个 harness 有多个形态时,每个形态各画一支(`branches[].form`,1.6 附录 A)。
- **进程的环境与当前目录**:助手 `proc-env` 一次读出(§1),只答描述符点名的变量,从不读整个环境;读不到(别的会话、提权的进程)写「不知道 · env-unreadable」,判未信任、只转发,不猜。macOS 同(4.9 §5.2)。
