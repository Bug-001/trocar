# asight · RFC 4.8 — Windows 采集器(D43 代理模式 · D47:引擎即代理)

> **状态**:设计已定。结构(助手、引擎的代理入口、信任入口、自启)是 **D42**;引流是 **D43**:Windows 只有代理模式;只读感知系统代理(D49),系统代理只决定上游;影响超出 agent 的改动由用户点名。采集路径是 **D47 及其 win32 孪生**:**引擎是本机唯一的本地代理**——每个入口组一扇引擎自己的回环门,身份在 accept 时刻从套接字读。
> **前置**:D31(按进程,不碰系统代理与整机流量)· D36(按用户运行)· D37(七个 harness、信任入口)· D38(失败不静默)· D39(二元开关、off 保证、系统代理感知、拓扑与诊断,[1.6](1.6-cli.md))· D40(agent 进程的全部流量都解密,另一分支)· D49(系统代理感知,[4.7](4.7-netenv.md),只读)· D43(两种模式、上游规则、点名项,[1.6](1.6-cli.md) §1.7)· **D47(采集路径:引擎自任代理、内核退役、accept 时刻的套接字;win32 孪生同款)**。引擎、记录、开关、改包与 Linux 共用 [4.6](4.6-process-collector.md)。
> **取代**:D31⑥ 的「Windows = WFP / WinDivert」(理由与实验数据见 §0)。
> **标注**:[E*] = §0 表里的 Windows 实测;「预期」= 没量过;[T0] = spike 阶段的实测。本单元的验收编号 W1… 只在本单元内有效;不使用的编号列在验收节末,不复用。

## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流只有**代理模式**(D43),采集路径是 D47 的形状:

- **引擎是本机唯一的本地代理**:每个入口组一扇引擎自己的回环门(§3),`on` 把 agent 的代理入口指向它。连接到达门时,身份从套接字本身读(§5.3):谁(pid)、是什么(形态),agent 的连接交给引擎解密,别的(子进程、家族之外的程序)只转发。
- 引擎的上游 = 没有 asight 时 agent 会走的那一跳:它自己的代理;否则它跟随且开着的系统代理;否则直连(§2.2)。用户的出口(节点、域名规则)不变。
- asight 不往任何 VPN 产品里写东西(4.7 只读),不改系统代理。不识别、不显示 VPN 产品(D49)。
- 只属于这个 agent 的入口,`on` 自动写;影响超出 agent 的(用户 PATH、快捷方式、证书库、VS Code 设置、机器级位置),由用户在 `on` 里按形态点名(1.6 §1.7,本单元 §2.4)。

开关与 off 保证照 1.6(代理模式的例外登记在 1.6 §1.2「例外二」)。稳健只做两件事——asight 自己足够稳健,用户能手动从命令行撤销 asight:监管(§4.3、§7);`asight off [agent]` 在 asight 坏了时也能跑(§4.2)。采集到的数据与 Linux 同一格式。哪些字段随引流不同见 `capture` 与几个路径类字段(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1](标准用户上的自启没量过,§7);点名的证书库一项会弹 Windows 的确认框,机器级的点名项要用户自己给管理员权限(§2.4) |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了 = 门死了,监管父进程重拉守护进程(§4.3);重拉期间 agent 连接被拒、其自身重试即到 |
| 覆盖 | 所有形态 | 有代理入口的形态:自动写的,或用户点名的(§2.3、§2.4) |
| 身份 | 内核给 pid | 引擎在 accept 时刻对套接字定点提问(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。D43又删掉了 VPN 块:它只对 Clash Verge Rev 写得进,Verge 升级两次弄坏同类的写法,切换要 552 ms,进程规则看不到提权的 agent、还会把同名的形态一起引过来 [E3];而代理模式在实验室里 16 个形态有 15 个到了 mock(L5),没到的那个是 Claude Desktop 的信任,不是引流。还采不到的形态如实写(§6.4)。没有「with vpn / with no-vpn」之分:VPN 只决定上游(§2.2)。

  | 契约 | Windows |
  |---|---|

  | `lookupIngress({peer, user, target})` | 门的连接查元数据(§5.2);`user` 是门名(组 id);异步(要问套接字表) |
  | `watch(pid, verdict)` / `unwatch(pid)` | 按 pid 的解密判定表(§5.4) |
  | `heartbeat()` | 空操作:引擎就是代理,它死了门一起死,监管父进程重拉守护进程(§4.3) |
  | `configure(enginePort)` | 空操作:门的端口来自 `ingress.json`,守护进程监听的就是引擎自己 |
  | `scan()` | 门遇到过的进程的事实(按 pid+startedAt 记;不扫全机,0.0 D47) |
  | `directCount(pid)` | 套接字表里该 pid 不经 asight 的连接数(经助手,**异步**,答 `{count, error}`,读不到是 `count:null` 与原因,不是 0;调用方一律 `await`) |

- **共享核心 + 适配器**:`core/engine/door-redirector.mjs` 的 `createDoorRedirector({ …, matchForm, directCount, companion, hostsOf })` 持有 OS 无关的全部——门的生命周期、accept 时刻身份与缓存、判定的 announce-and-wait、上游的拨法决定(绕过表命中即 direct)、splice/decrypt 决定。`arch/win32/redirector.mjs` 只添 Windows 的三样后端:`matchForm`(forms.mjs)、`directCount`(助手 tcp-table)、`companion`(常驻助手:ready 行、close、协议号)。darwin 的适配器是同一个核心的另一件衣服([4.9](4.9-macos-collector.md) §1)。
- **助手**(`helper.mjs` · `helper.ps1`):一个常驻的 Windows PowerShell 5.1(`-NoProfile -NonInteractive -ExecutionPolicy Bypass -File`,不提权),守护进程经 stdin / stdout 的 JSON 行协议问它:`{id, verb, args}` → `{id, ok:true, data}` 或 `{id, ok:false, error}`。助手编完原生代码(`Add-Type`,C# 5)后先发一行 `{ready, proto:1, pid, ps, native}`,客户端在它之后才写请求,超时(默认 2 s;`ps` 是 10 s,第一次 `ps` 要经 CIM 读全部命令行)从写出算;超时的请求在助手(串行)答完它之前不再发同类的新请求。**只读,动词是闭集**(W1:客户端在 JS 里先拒绝未知动词,脚本里再核一遍;脚本只含 ASCII):

  | 动词 | 参数 | 答 |
  |---|---|---|
  | `version` | — | `{proto, pid, ps, os, native, nativeError?, sessionId?}` |
  | `ps` | `{all?, cmdline?}`(默认只列助手所在会话的进程) | `{sessionId, procs:[{pid, ppid, name, exe, cmdline, startedAt, sessionId, integrity, tokenDenied}]}`。`startedAt` 是 Unix 纪元毫秒;`exe` · `cmdline` · `integrity` 读不到为 `null`;命令行取自 CIM `Win32_Process`,每个进程只问一次(答案为空最多问三次),CIM 失败后 30 s 不再试;每次 CIM 调用 8 s 超时。每行另带 `cmdlineState` ∈ `ok` · `pending` · `cim-backoff` · `empty` · `not-asked` |
  | `tcp-table` | `{pids?, remotePort?, localPort?, states?}`(过滤;全空 = 全部) | `{rows:[{pid, state, family, localAddr, localPort, remoteAddr, remotePort}]}`。GetExtendedTcpTable 直读(原生 P/Invoke,非 CIM);v4 与 v6 都读,任一读不到就整个报错;`state` 用 MIB_TCP_STATE 的名字(`listen` · `established` · `close-wait` …) |
  | `reg-read` | `{hive, key, names}` | `{keyExists, values:{<名>:{kind, value}}}`,值不展开环境变量、`kind` 如实给(`REG_DWORD` `REG_SZ` `REG_EXPAND_SZ` …)。**白名单**:`HKCU\…\Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(4.7 §1);`HKCU\Environment` 的 `Path` 与代理变量(§2.2);机器 PATH;Smart App Control 的策略值;harness 文件声明的策略键里的值(Claude Desktop,§2.4)。白名单外、或不给名字(= 全读),拒绝 |
  | `net-if` | — | `{interfaces:[…]}`:.NET `NetworkInterface`,不经 CIM,不含 MAC |
  | `route` | `{dest?}`(默认 `1.1.1.1`) | `{dest, ifIndex, iface}`:`GetBestInterface`,只查路由表,不发包 |
  | `token` | — | `{pid, elevated, elevationType, integrity, system, sessionId}`:助手自己的令牌(R7 的判据) |
  | `roots` | — | `{counts, certs:[{sha256, pem, stores}]}`:`CurrentUser\Root` 与 `LocalMachine\Root` 只读导出,按 DER 的 SHA-256 去重 |
  | `pipe-server` | `{name}` | `{exists, serverPid, exe, startedAt}`:以只读客户端打开该命名管道,问服务端 pid |

  - **失败的记法**:助手起不来(spawn 失败、退出、不发 ready、协议号不符、策略挡了脚本、原生代码编不过)= `helper-start-failed`(§12);起来之后死了 = 既有的 `helper-down`(带 `exit` 与 stderr 末 20 行,4.6)。每次死亡一条,在途的调用都拒绝;主动关掉不记。
  - **`ps` 与提权**(§10.1):`elevated` = 完整性 ≥ High,或令牌打不开而映像路径读得到(标「推断」)。

## 2. 代理模式:入口与上游(D43)

### 2.1 一种模式

| | 是什么 |
|---|---|
| 流量怎么到 asight | 该形态的代理入口指向**引擎里它所在组的门** `127.0.0.1:<端口>`(带凭据,§3);门在 accept 时刻按套接字身份把 agent 的连接交给引擎(§5.3),子进程等只转发 |
| asight 写什么 | 该形态的代理入口与信任入口(§2.3、§6)。只属于 agent 的,`on` 自动写;影响超出 agent 的,用户点名才写(§2.4)。都入账、先备份、`off` 撤(1.6 R2)。**代理入口就是引流,所以 MUST 在该组的门立住之后才写**(1.6 R9:挂引流最后;信任入口先写):门立不起来(端口被占)时一个代理入口也不写;`off` 反过来,先撤入口、无人携带的门关掉,carried 的门保持只转发(§4.1)。W12 |
| 引擎的上游 | §2.2 的规则。引擎为每条 agent 连接拨该组的上游(§5.2) |
| 什么时候不采 | 形态没有能用的入口、要点名而没点名、agent 提权、跟随的系统代理是 PAC:`status` 报原因码,`doctor` 给办法(§10) |

- asight 不开 TUN、不当系统代理,不改系统代理与 VPN 的任何设置(D31④ · D43);只有指向门的 agent 经过它。
- 用户的 VPN 开着 TUN 时,引擎直连的上游照旧被 TUN 收进去,出口与 agent 原来一样。
- 若用户的 VPN / 代理按进程分流,它看到的连接来源是 asight(引擎的 `node.exe`),不是 agent:它点名 agent 的按进程规则不再匹配,域名规则照旧。D43 定只标一句,D49 起不再依赖探测:asight 在路径上就印(1.6 §9.2);放在一处:`status <h>` 印一行;`on` 的计划里不重复。

### 2.2 上游规则(每次 `on` 定;系统代理变了守护进程跟上)

D43:asight 的出口 = 没有 asight 时 agent 会走的那条路。`upstream.mjs` 按序取:

1. **agent 自己的代理**:`on` 写入口之前,该形态入口里的原值(harness 文件 `proxy` 声明的键;记进清单的 `prior_value`,0600)。别的进程的启动环境读不到(§10.1),登录环境只读 `HKCU\Environment` 里的代理变量(只读;点名也不写,D43)。**读不到的一种**(评审 2026-10-07 后补):只设在你终端里、由这个终端起的 agent 才会用的代理,asight 看不见;这个形态的上游会按 2、3 算,出口可能与关掉 asight 时不同。所以凡上游按 2 或 3 算出来的形态,`on` 的计划与 `status <h>` 在上游那一行注明「读不到你终端里的 HTTPS_PROXY」;`asight on` 自己的环境里有 `*_PROXY` 时(值打码)计划多一行提示。不为它另设码(OPEN 20)。
2. 否则,该形态**跟随系统代理**(harness 文件 `proxy.systemProxy`)且系统代理开着:`ProxyServer` 里的那一项(按协议分写的取 `https=`,没有就取通用的一项);目标命中 `ProxyOverride` 的直连(译成绕过表,见下)。系统代理是 PAC(`AutoConfigURL`)→ 不接这个形态,`not-routed`(asight 不执行 PAC)。「是 PAC」这一判断是假设:`AutoConfigURL` 里有非空的地址就算 PAC,不管 `ProxyEnable`(4.7 用同一条;OPEN 27)。
3. 否则**直连**。用户开着 TUN 或别的 L3 VPN 时,由系统照旧送进去。

| 本机网络 | 跟随系统代理的形态 | 不跟随的 | agent 自己配了代理的 |
|---|---|---|---|
| Verge · 系统代理开 · TUN 关 | 系统代理 `127.0.0.1:7897` | 直连 | 它自己的代理 |
| Verge · TUN 开 | 系统代理开着时同上;关着时直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| v2rayN · 系统代理开 | v2rayN 的本地端口 | 直连 | 它自己的代理 |
| 别的 TUN VPN · 系统代理关 | 直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| 没有 VPN | 直连 | 直连 | 它自己的代理 |
| 系统代理是 PAC | 不接 · `not-routed` | 直连 | 它自己的代理 |

- **一个形态只有一个上游**。原本分两路的,接上后都走那一个:Codex 的 HTTP 跟随系统代理、WebSocket 直连 [E2][E16],接上后 WebSocket 也经系统代理,报 `egress-differs`(提示,1.6 §9.6)。
- 上游不能是 asight 自己的端口(组的门、引擎入口):`on` 不接这个形态,报 `route-loop`(原值多半是上次 `on` 没撤干净留下的)。
- **系统代理变了**(开、关、换端口):守护进程在 5 s 核对里读 `Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(§9),重算跟随它的形态的上游;**重算后的答案(去掉 `hint`)与 `last` 相同的变化什么都不动**,不同才把门与入口带到新计划(一次 attach:门幂等重开、入口同址重写为 no-op),写一条 `netenv-change`;不碰 agent 的设置,不算失败(1.6 §9.5)。W71。
- `on` 之后系统代理改成 PAC:上游留在上一次的值,报 `system-proxy-pac`(提示);要按 PAC 走就 `asight off <h>`(OPEN 17)。
- **agent 自己的代理变了**(入口不再是 asight 写的值):agent 已绕过 asight,`proxy-changed`,`status` 印 `asight on <h>`(1.6 §9.5、§10.3)。
- 带凭据的上游:凭据只在清单里(0600),只用于这个 agent 的连接(§5.2,D30)。
- **绕过表**(评审 2026-10-07 后补):没有 asight 时,命中系统代理的 `ProxyOverride` 的目标、或命中 agent 自己代理的 `NO_PROXY`(同一入口里的原值)的目标,agent 是直连的(内网模型网关常见)。所以每个组带一张绕过表:`<local>`(没有点的主机名)· `*.corp.com`(后缀)· `10.*` 一类(IP 段)· 精确主机。译不了的写法不进表,`status` 写「N 条绕过规则 asight 读不懂,按走上游处理」(OPEN 21)。命中绕过表的目标:引擎直连(`lookupIngress` 按 CONNECT 目标判,`bypassHit`,§5.2)。这些连接照常被采集,出口还是 agent 原来的那一跳。
  - **译法**(`translateBypass(文本, 'wininet' | 'no-proxy')`):`ProxyOverride`(`;` 分隔)里 `<local>` → `local`;`*.corp.com` → `domain-suffix`;`10.*` · `10.1.*` · `10.1.2.*` → `ip-cidr`(`/8` · `/16` · `/24`),四段齐全 → `/32`;裸主机名 → `domain`(WinINET 里它只命中自己)。`NO_PROXY`(逗号或空白分隔)里裸名与前导点 → `domain-suffix`,`10.0.0.0/8` 一类的 CIDR → `ip-cidr`。名字 `localhost` 另加一行 `ip-cidr 127.0.0.0/8`。读不懂的不进表、计入 `untranslated`。每一行都过 `bypassRuleOf`(`core/upstream-shape.mjs`),所以用户的任何写法都不会让计划抛错。`bypassHit(表, 目标)` 是共享核心拨上游时用的同一份判法。
- **上游的协议**(W5):`http://`、`socks5://`、`socks5h://`(后两者同一种:都把域名交给代理解析)接得上。`https://`(到代理那一跳是 TLS)与 `socks4` 等 v1 不支持:`on` 不接这个形态,`not-routed`,doctor 码 `proxy-unsupported`(1.6 §9.6)并写明协议,不悄悄改走别的出口(OPEN 21)。
- **`upstream.mjs` 的细则**(W5 · W71):`upstreamFor({ group, prior, noProxy, systemProxy, hkcuEnv, ownPorts, envNames, branches, last })` 每组一个答案 `{ kind, host, port, credentialed?, auth_ref?, source, egressDiffers?, hint?, reason?, why?, protocol?, bypass, untranslated, envUnreadable, unknown? }`;`reason`(`not-routed` · `route-loop`)时没有 `kind`:没有可拨的。
  - **读法**:不带协议头的 `host:port` 按 HTTP 代理读;端口缺省 http 80、socks5 1080;IPv6 去掉方括号;含空白或控制字符的值不读 = `not-routed` · `upstream-unparseable`;**校验器不收的地址也不读**(判的是 `core/upstream-shape.mjs` 的 `upstreamOf`,不另抄一份:`http://a,b:3128` 的 host 带逗号,URL 解析器放行、校验器抛),同为 `upstream-unparseable`。`https://`、`socks4`、`socks4a`、不带 5 的 `socks`、别的协议头 = `not-routed` · `upstream-protocol` 带 `protocol`。
  - **凭据是引用**:答案里没有用户名与口令,`credentialed:true` 加 `auth_ref`(`prior:<组>` = 清单里这个组入口的 `prior_value`,`hkcu-env:<变量名>`);`proxyAuthOf(解出的文本)` 是读它们的唯一一处。系统代理的 `ProxyServer` 里带凭据 = `not-routed` · `upstream-unparseable` · `detail:'credentials-in-system-proxy'`。
  - **`ProxyServer`**:`https=` 的那一项优先,其次是不带协议名的那一项;只有 `socks=` → `not-routed` · `upstream-protocol` · `socks`;只有 `http=` `ftp=` 一类 → 直连;`ProxyEnable` 不是开 → 不看 `ProxyServer`。
  - **登录环境**:只在入口没有原值时读,取 harness 的 `proxy.env` 里按它的顺序第一个有值的(只认 `HTTPS_PROXY` `HTTP_PROXY` `ALL_PROXY`,值名不分大小写);它的 `NO_PROXY` 跟着它。读不到 → 答案的 `unknown` 里一项。
  - **`egressDiffers`** 只在上游是系统代理、该组 `followsSystemProxy.http` 为真而 `ws` 为假、且 harness 的 `proxy.branches` 含 `ws` 时出。
  - **系统代理读不到**(助手超时、被拒):跟随者 = `not-routed` · `why:'system-proxy-unreadable'` · `detail:<原因>`,不当「直连」猜。**`on` 之后**的变化带 `last`:系统代理变成 PAC 或读不到时,跟随者留在 `last` 的上游并带 `hint`(OPEN 17)。
  - **自己的端口**:回环地址加 `ownPorts` 里的端口(引擎入口与各组的门)= `route-loop`。
  - **读与盯**(只读):`readSystemProxy({helper})` 读 `Internet Settings` 的四个值;`readHkcuEnv({helper})` 读登录环境的四个代理变量;读不到 = `{ok:false, reason, detail}`,`reason` 取 1.6 §9.4 的闭集。`watchSystemProxy({helper, everyMs: 5000, initial})`:第一次读是基线、不发事件;四个值任何一个变了,或由能读变成读不到、或反过来,发一次 `change`;连续读不到不算变化;上一次读还没回来时下一拍等它;**有一次 `reg-read` 超时而助手还没答它时跳过这一拍**(助手是串行的);`stop()` 之后不再读不再发。
- **`route-plan.mjs` 的细则**(W5):`planRoutes({ netenv, groups, desired, optIns, manifest, ctx, procs, last })` 把 `upstreamFor` 的答案与入口的门放在一起,每个组一个结果,键是组 id;`groupsOf(descriptors)` 把各 harness 的 `desc.win32` 摊成 `[{ g, harness, group, forms, proxy }]`。
  - **输入**:`netenv` = `{ systemProxy, hkcuEnv, ownPorts }`;**`ownPorts` 必传**,缺了抛 `TypeError`(看不见环路的计划不是计划)。`desired` = `state.json` v2 的 `harnesses`。`optIns` = 用户点名、asight 有记录的组或形态 id(守护进程的重算从 manifest 的 `optin-*` 条目取——否则 `off` 后重启守护进程,launcher 指着没有门的死端口,4.9 §6.4 接线臂的孪生)。`manifest` 与 `ctx` 给 `priorOf`;`procs` = `[{ pid, match, elevated }]`,`match` 是 `matchForm` 对这个进程的答案;`last` = 上一次的结果:**只有上一次 `on:true` 的组才有可留的上游**。传进来的不是结果(没有 `on`)抛 `TypeError`。
  - **原值从哪读**:`priorOf({ harness, group, ctx, manifest })`。清单里有这个组入口的记录(**按 harness 与入口认,不按 `files(ctx)` 认**——那份列表跟着调用者的环境走)时,`prior_value` 就是原值,**哪怕是 null**;同一个文件有两条记录时取最早的。没有记录就读文件(第一次 `on`)。文件读不到或解析不了是「不知道」:`unknown: [{ what:'agent-proxy', reason, detail? }]`。**只有 `proxyEntry.kind:'file'` 的组有原值**。原值可能带用户的凭据:它只交给 `upstreamFor` 与解 `auth_ref` 的人,不进任何输出。
  - **结果**:`{ g, harness, entry, on, reason, code?, why?, detail?, protocol?, upstream, bypass, untranslated, envUnreadable, egressDiffers?, hint?, unknown?, forms, answer }`。`on` = `entry` 不是 null(该组的门开着、形态走引擎);`upstream` 是 `{ kind, host?, port?, credentialed?, auth_ref?, source }` 或 null,**关着的组也算——但只在它装过、点过名**(它的入口可能还在,carried 的门替关了之后还活着的 agent 转发到上游;守护进程把这份名单交给重定向器,不传就是「没有」)。**没装过、也没点过名的组,一扇门都不给它开**:没点名的 Claude Desktop 的免鉴权端口是最尖的那例——一个没有任何用户在后面的开口;`answer` 是 `upstreamFor` 的原答案(带绕过表,没有凭据),守护进程靠它比「系统代理动没动上游」。
  - **`reason` 的先后**就是用户能动手的先后:`desired-off` → `opt-in-needed` → 上游的 `not-routed`(`why`:`system-proxy-pac` · `system-proxy-unreadable` · `upstream-protocol` · `upstream-unparseable`)或 `route-loop`(`detail` 是 `host:port`)→ `form-unsupported`(收不了凭据的入口配了带凭据的上游)。都没有 = null,组接上。`code` 是 doctor 的名字,与 `reason` 同,只有 `upstream-protocol` 是 `proxy-unsupported`。
  - **形态的结果**:`forms[<形态 id>] = { reason, elevatedPids?, unknownPaths? }`:`reason` 先取组的,没有就看进程:这个形态有提权的进程 → `elevated-agent`(§5.4 的保守规则),否则有进程的映像认得、路径没测过 → `form-path-unknown`。这两条不改组拿到的入口与上游:接上的组里,只是那个进程没被采。

## 3. 引擎的门(4.9 §3 的跨 OS 核心 + Windows 接线)

**引擎是本机唯一的本地代理**(0.0 D47)。`engine.listen({ groups: [{ id, port, auth, token }] })` 给每个入口组开一扇**回环门**(127.0.0.1:ingress.json 的组端口),由同一个 proxy ingress 回答:门知道自己的组(`user` = 组 id)、自己的口令(`token` = listener token;`auth:false` = 不收口令——Claude Desktop 的策略值一类入口收不下凭据的形状),CONNECT/SOCKS5/407/204 的协议半照 §5.1。`engine.closeGroups(ids)` 是另一半:计划不再携带的门停止接受、在途连接照常排空。绑定按组幂等(已开的门答端口不重开),attach 可反复问。

- **门的凭据 = 入口里写的那个**:`http://<g>:<listenerToken>@127.0.0.1:<组端口>`。错口令 = 407;引擎自己的 ingress token 不是门的事。引擎自己的 ingress 端口(enginePort + ingress token)继续听(ingress.json 的形状不变),仅作兼容与自检。
- **`auth:false` 门的三重授权**:① 用户点名了该组;② 只回环 bind;③ 引擎的逐进程判定——套接字身份不是本门本组的形态 → 只转发、不解密、不记录(§5.3)。上游带凭据时拒开(`login-on-open-port`,开口的端口永不借出用户的登录)。W70。
- **门的生死 = 计划 + carried**:计划开的组开其门;`off` 时入口全撤、carried(装过、点过名)的组门保持**只转发**(计划已说 off,`lookupIngress` 服务不拒:`group-off` splice);off 且无人携带的门关(无主回环端口是开口)。`uninstall`/裸 `off` 删 ingress.json。
- **引擎崩 = 监管父进程重拉守护进程**(§4.3):门随引擎死、随重拉开;期间 agent 的连接被拒、其自身重试即到。没有 fallback 层。
- **组端口**:首次 `on` 在 17991–18989 里给每个组选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定(agent 的入口里写死它)。被占了:那扇门开不了,`on` 带 `engine-port-taken` / 门开失败的码拒绝、一个代理入口也不写;不自己换端口,不带参数的 `off` 之后再 `on` 才重选。`ingress.json` 的内容:`{enginePort, groupPorts:{<组>:端口}, ingressToken, listenerToken}`(0600,先写临时名再改名);已有的端口与口令之后每次原样复用;文件信不过(不是 JSON、端口越界或重复、口令不对)→ 整份重来并告诉调用方原因(`regenerated`):各组的入口里写着旧端口,所以调用方 MUST 在门立住之后重写**所有**已装的代理入口。不带参数的 `off` 与 `uninstall` 删这个文件。
- **宿主进程树的 host 集在这扇门上判**:宿主进程树的形态(点名项,§2.4;Kimi 的 VS Code 扩展住在 `Code.exe` 的扩展宿主里,`http.proxy` 让 VS Code 全部扩展的连接都到它的专用门)只有到它的 **host 集**的连接交给引擎;`Code.exe` 的别的连接在 `lookupIngress` 里只转发——不解密、不记录(`outside-host-set`;D43⑥,点名文字与 `status` 写明)。**host 集**(OPEN 22)= Kimi 的默认 API host(harness 文件的数据)∪ Kimi 扩展自己的设置里配的 base URL 的 host(只读,`on` 与 `status` 时重读;读哪份文件、哪几个键由 harness 文件声明的读取器定)∪ 该 harness 的 `extra_hosts`(操作者手加的,1.6 §1.5)。经中转站的 Kimi 连接因此自动在集里,不用手写名单(D31「中转站自动覆盖」的精神)。按名字匹配,精确或后缀;地址字面量、`localhost`、通配符、端口一类匹配不到的写法不进集,列在 `dropped`,`status` 如实写出(OPEN 28)。**读不到那份设置**(权限、解析不了):集里只有默认 host 与 `extra_hosts`,`status` 不静默(D38),写「读不到 Kimi 扩展的设置(原因):只采默认 host(列出)与 `extra_hosts`;到你在那里配的中转站 host 的连接不采」,原因取 1.6 §9.4 `unknown.reason` 的闭集;文件不存在 = 没配中转站,不算读不到。`status` 重读的集与门上的集不同(用户在 `on` 之后改了那份设置):写一行与 `asight on kimi-code`,`status` 自己不改任何东西。不另设码。W69。
- **专用门、按连接判**(dsh CLI):`node.exe` 映像不唯一,没有可指认它的进程规则;它所在组的门上每条连接由 accept 时刻的套接字身份判(§5.3、§5.4):pid 是该形态的进程且已信任 → 解密;是别的进程(dsh 的子进程)或补不出 pid → 只转发,`flows/` 里只有一行元数据(D40)。

## 4. 开与关

### 4.1 怎么生效

- 每次开关都是一次 `attach()` / `detach()`(共享门核心):计划里开的组开其门(引擎的 `listen({groups})`,幂等)、关的组撤入口;无人携带的门 `closeGroups`。
- **复核**:`attach()` 的答案是事实(门开了哪些、入口写了哪些、跳过了哪些组与原因),不靠读回什么外部进程;`status()` 的 `attached` = 计划开的组里有门在。
- **`on` 的次序**(W12):信任入口 → 门的端口(ingress.json)→ 开门(携带的组幂等重开)→ 代理入口(§2.1)。门开不了:一个代理入口也不写,回执写原因,`on` 退出 1;崩在任一步之后再 `on` 续完(1.6 R9)。`off` 反过来:撤代理入口 → 撤信任入口与点名项 → 无人携带的门关掉、carried 的门保持只转发。
- **接线臂**(4.9 §6.4 的孪生):守护进程的重算必须认「清单里有记录的点名」——`planRoutes` 的 `optIns` 与 carried 列表从 manifest 的 `optin-*` 条目取;**且 5 s 检查重算计划、计划移动时带门跟上**(否则 `off` 后重启守护进程,launcher 指着没有门的死端口)。

### 4.2 off 保证(照 1.6 §1.2;例外如实写)

| `off` 做什么 | 之后保证什么 | 例外(1.6 §1.2「例外二」) |
|---|---|---|
| ① 期望态写 off;② 撤代理入口与信任入口(只撤 asight 写的值)与点名项(机器级的印提权命令);③ carried 的门保持只转发,无人携带的门关;④ 引擎按 1.6 §1.3 关在途连接 | 新启动的 agent 走原来的路;引擎不在任何 agent 的路径上 | **`on` 期间启动、读了入口的 agent,重启前仍连着 carried 的门(只转发,不经引擎、不解密、不记录)**;门随守护进程退出而关后它们要重启。`status`:「还有 N 个 agent 连着 asight 的门,重启它们之后 asight 就完全退出」。`off --now`:立即断开,回执列出会断的 pid(操作者的显式意图) |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。
- **监管父进程先停**(评审 2026-10-07 后补):不带参数的 `off` 与 `uninstall` 要停守护进程时,先停监管父进程(核对 `supervisor.lock` 的 pid 与启动时间后停),再停守护进程;顺序反了,父进程会把刚停的守护进程拉回来。
- 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2 第一条例外)。
- **独立撤销**:守护进程不在、源码也不在时,独立副本 `~/.asight/bin/asight-off` 做同样的撤销(1.6 R3;`src/off/win32.mjs`)。先停监管父进程。W54。

### 4.3 稳健:用户的两句话

稳健只守两条:trocar 自己足够稳健,且用户随时能手动从命令行撤销 trocar。只做这两件,不另加机制:

1. **稳健**:监管父进程监管守护进程(§7,退避重拉)。引擎死了 = 门死了,守护进程被父进程拉起、门随之重开;重拉期间 agent 连接被拒、其自身重试即到,`status` 照实写(0.0 D47)。W47 · W49。
2. **命令行撤销**:`asight off [agent]` 在守护进程坏了、源码不在时也能跑(§4.2 独立撤销)。撤了之后重启那个 agent,它就不经 asight。W54 · W55。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各形态的门与入口;别的形态的门、上游与入口不变,在途连接不断(W55)。
- 新装了一个 harness:`on` 给它的形态选端口、开门。
- 用户自己改了某个 agent 的代理:`proxy-changed`,`on <h>` 把新值记成上游再指回门(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`),另加每组的门(§3)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定。端口被别的进程占了:守护进程不自己换,记 `engine-port-taken`(失败类;触发点是 `engine.listen` 的 `EADDRINUSE`;W73);不带参数的 `off` 之后再 `on` 才重选端口。`doctor` 给查占用者的命令(§10.4)。
- 认两种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)。别的开头:关掉,记 `ingress-unknown`。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。`auth:false` 的门收没有 `Proxy-Authorization` 的 CONNECT(门的三重授权在进程判定上,§3)。
- 别的 CONNECT:引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §1.3)。
- **实现细节**:
  - 开头:一个连接 10 s 内读不全开头记 `ingress-unknown`;CONNECT 的目标不是 `host:port`(IPv6 要方括号)记 `ingress-unknown`。SOCKS5 的问候里没有用户名密码一项 → 回 `[5,0xff]`,记 `ingress-auth-failed`;SOCKS5 的非 CONNECT 命令回 `07`,记 `ingress-unknown`。
  - 鉴权:token 先验、常数时间(两边先取 SHA-256 再比),验过才查 `lookupIngress`;查不到(`null`)= 未知用户,同样是 407 / SOCKS5 回 `02`,记 `ingress-auth-failed`。失败记录带 `peer` 与用户名,**从不带 token**:用户名只在形如路由名且不含 token 时照写(截短),否则写占位 `(not a route name)`。`lookupIngress` 抛错 → 回 `502` 与 `where:'engine'` 的 `loader-down`(或 `loader-timeout`);**例外**:抛的错带 `code:'upstream-unavailable'` → 同样回 `502`,记 `where:'ingress'` 的 `upstream-unavailable`(带 `why`)。
  - 上游拨通之前客户端走了:销毁上游,不写连接行。上游成功之后到 `200` 之前不会有字节写给客户端。
  - `engine.close()` 先关掉不是 flow 的入口连接(握手中的),再等 flow 收尾。
  - `engine.listen({port, hosts, ingress:{port}, groups})` 返回 `{port, ingressPort, groupPorts}`;redirector 没有 `lookup`(Windows)就不开透明监听,`port:null`;要入口就要 redirector 有 `lookupIngress` 且 `createEngine` 给了 `ingressToken`,否则抛 `TypeError`。`engine.stats().ingress` = `{connections, flows, health, authFailed, unknown, refused, unreachable}`(W42),只在开了入口时有。

### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` 取形态对应的 harness |
| `form` | 形态 id(如 `codex.app`),取自 accept 时刻的 `matchForm`(§5.3):身份就在套接字上,不靠凭据声称 |
| `capture` | `proxy` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth}` · `{kind:'socks5', host, port, auth}`。按该组的上游规则(§2.2);CONNECT 目标命中该组的绕过表时是 `{kind:'direct'}`(W72)。`lookupIngress` 把 `auth_ref`(清单里的 `prior_value`)解成 `auth:{username, password}` 交给入口;入口只在拨这一条 agent 连接的前导里用它,交给 `handleFlow` 的 meta 里只剩 `credentialed:true`,凭据不进 flow、不进任何记录 |
| `pid_source` | `socket-table` · `null` |
| `negKey` | 负缓存的键(§5.5)。有 pid 取 `"<pid>"`,否则取门名(组 id);不补的话没有 pid 的连接会共用 `null` 一个键,互相毒化 |

- **`lookupIngress` 的答案**(共享门核心;W16 · W72):`user` 不是本引擎的一扇门(组 id)、计划里没有这个组的答案,或没有 `target` → `null`(入口答认证失败)。目标是该组自己的门端口(127.0.0.1:<组端口>)→ `null`(一个通过门到门自己的环:没有正当的流量这么问)。**该组不是 `on`、而来的是 agent 的连接**(计划已翻成关、门还开着的那一小段——carried 的门):不答 `null`(那是 `407`),而是**照样接**:meta 为 `{pid:null, decrypt:false, form:null, upstream:<该组的上游,绕过表与登录照常>, negKey:<组 id>, skip:{not_captured:'untracked', reason:'group-off'}}`,不查套接字表;该组没有上游可拨才答 `null`。别的目标 → meta:`{pid, agent, decrypt, capture:'proxy', form?, exe, upstream, pid_source, pid_ms, negKey, skip?}`。`upstream` 先于查 pid 算(拨不通的连接不该等表);`skip` 只在不解密、而表上没有一行可说原因时有:`{not_captured:'untracked', reason}`(`pid-unresolved` · `not-a-process-of-form` · `outside-host-set`,§5.3;`reason` 是自由文本,`not_captured` 在闭集里)。上游拨不通(`no-upstream`:该组没有上游可拨;`upstream-credentials-unavailable`:带登录的上游读不到登录)→ **拒绝**,Error 带 `code:'upstream-unavailable'` 与 `why`,消息里没有登录;入口写自己的 `upstream-unavailable` 失败(`where:'ingress'`,§12)并回 502。`auth_ref` 只在拨这一条连接时解:`resolveLogin(ref, { groups, ctx, manifest, hkcuEnv })`(`route-plan.mjs`;`prior:<组>` 走 `priorOf`,`hkcu-env:<名>` 取这次读到的注册表环境,文本经 `proxyAuthOf`;找不到是 `null`,不抛、不猜),守护进程把四项绑好当 `authOf` 交进来。
- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。
- **上游怎么拨**:`direct` 直连目标(域名由系统解析);`http` 向 `host:port` 发 `CONNECT <目标> HTTP/1.1`(带 `Proxy-Authorization: Basic` 当且仅当有凭据),2xx 成功,别的状态把代理的回应原样转给 agent;`socks5` 做问候、RFC 1929、CONNECT(目标是 IPv4 / IPv6 字面量用 ATYP 1 / 4,其余用域名 ATYP 3),`rep ≠ 0` 回 `02`。代理回成功时与回应同一块到的上游字节留着、按序交给 flow(算上游先说话,4.6)。拨不通 → `502` / SOCKS5 失败回复,连接行 `decision:'error'`、`not_captured:'error'`、`error:{type, message, side:'upstream'}`;代理拒绝 → 连接行 `decision:'tunnel'`、`not_captured:'proxy-refused'`、`reason:'proxy-status-<n>'` / `'socks5-reply-<n>'` 等、`upstream.reply`。代理的回应第一行不是 HTTP 状态行算拨不通、不算拒绝:`502`、行 `error.type:'bad_proxy_reply'`。**等代理没有时限**(D31),但不静默(D38):连代理与握手合计超过 `upstreamSlowMs`(5 s)还没回应,记一次 `upstream-slow`;客户端先走了就不记。
- **拨不通要报**(W73):拨上游失败时,除连接行外另写一条失败 `upstream-unreachable`(`where:'netenv'`;同一形态 60 s 内最多一条),并进该形态的 `status` 原因(1.6 §9.7);doctor 给 `proxy-dead` 同样的查端口命令。上游代理拒绝(`proxy-refused`)是另一回事,不报它。
- **一条 agent 连接只拨一次上游**(评审 2026-10-07 后补):入口拨好的上游连接交给 `handleFlow` 用。之后 4.6 的「让路」要重拨时:上游不带凭据才重拨;上游带用户的代理凭据,就关掉这条连接,同 4.6 隧道连接的做法(不变式 1)。W15。不带凭据时第二次拨是新的一轮握手,重拨失败 → 连接行 `decision:'error'`,客户端的连接关掉。

### 5.3 身份:accept 时刻、从套接字读(0.0 D47;W4)

引擎的门收下连接,**peer 4 元组就是 agent 的出站套接字**(中间没有别人):两问定点、无扫描——

| 问 | 怎么做 | 答不出 |
|---|---|---|
| 谁(pid) | 助手 `tcp-table`(GetExtendedTcpTable,~5 ms [E6]):`{localPort: <peer 端口>, states:['established']}`,本地端等于 peer 地址:端口的那行答 pid(`pid 0` 的行是 TIME_WAIT 残留,不算;引擎自己的 pid 排除)。预算 250 ms,与拨上游并行 | 无行、多行、慢、读不到 → `pid:null`,连接 splice `untracked`(`pid-unresolved`),**绝不猜**:错的 pid 会让引擎解密一个不信任 asight 的进程,把它弄断(4.8 W4)。超过预算不记失败(慢不是不可用);读不到才记 `socktable-unavailable`,每次调用一条,由记录器折叠 |
| 是什么(形态) | 该 pid 的助手 `ps` 行(映像路径、命令行、启动时间、完整性):`matchForm` 按它判(§2.3)。**按 pid+startedAt 记住,一生问一次**(同一 pid 复用为新进程 = 新的启动时间 = 再问) | pid 没了(连接刚建立进程就退出的竞赛)→ `null`,同上 splice。**非本门本组的形态 / 无形态 → 只转发**(`not-a-process-of-form`,`auth:false` 门的安全臂);宿主进程树的形态、目标不在它的 host 集上 → 只转发(`outside-host-set`,§3) |

- 没有进程快照的差分监视(`exec` / `exit` / `facts-update` 的 2 s 轮询)、lsof 式候选集、demand-poll 与去抖(0.0 D47:不做进程扫描)。peer 进程按定义活着(它刚连上),一连接两问即全部成本;`flows/` 连接行记 `pid_ms`。
- 命令行还是 `pending` 的形态(`cmdlineState`):accept 时刻没有「以后再判」——要命令行的形态这一问就不认,连接 splice(宁可少采,不可采错);该进程的下一条连接会再问一次(CIM 的答案通常已到)。
- **判定等人**:门把新 pid 的事实作为 `exec` 说出,lookup 等 tracker 的 `watch()`(默认 5 s 上限;等不到 = 墓碑 `{decrypt:false}`,一生等一次、不按连接等,tracker 事后答了就盖掉)。
- **验收**:W43 [WinVM] 用真值核对(同一形态 3 个进程,2 个已信任、1 个未信任,200 条并发连接,另有 `on` 之前就开着的长连接),错认必须是 0;另量 p50 / p90。

### 5.4 信任判定

- **谁产生判定**(评审 2026-10-08 补;W76):门核心的判定表只有 `watch(pid, {decrypt, agent})` 推进来的行,**推的是 tracker**(4.6)。(1) **认形态只有一份规则**:守护进程把 `matchForm` 交给 registry(`createRegistry(descriptors, { osMatch: { win32 } })`),tracker 认出的 harness 与门认出的形态同源;(2) **环境读不到是本 OS 的常态**时(进程事实声明 `envRead:false`,Windows 的 `procinfo` 给),tracker 不因 `env === null` 否决,按入口文件(Hermes 在 `desc.win32.layers` 里自己声明)、`installed_at`(`osLayers[os](descriptor)` 选层)、插件标记、Kimi shim 的父进程判;Linux 上读不到 environ 仍然否决;(3) dsh / OpenCode 的标记与 `startedAt` 的比较带定死的容差 2000 ms(`MARKER_TOLERANCE_MS`);(4) 门遇见新 pid 即 `exec`,tracker 判一次。仍然是 fail-safe:任何一步不确定 → 未信任 → 透传。
- **环境读不到时的取舍**:启动环境读不到,用户在 Windows 用户环境里自己的 `SSL_CERT_FILE` / `NODE_EXTRA_CA_CERTS` 不读、也不作为否决的理由;但 `fill` 型的层**不作为信任的来源**(tracker 对 `envRead:false` 的进程核第二遍:把 fill 层拿掉就不信任的,判未信任,`env-unreadable-fill`)。残余,如实记下:比文件更优先的环境名(Hermes 旧版的 `HERMES_CA_BUNDLE`、Z-Code 的 `ZCODE_AGENT_CA_CERT`)同样看不见,设了它的用户会按文件判成信任——这一类待量,量到再定。
- **有 pid**:照 4.6 §确认信任,按 pid 判:进程启动时间与入口的 `installed_at`、插件标记、Kimi shim 的父进程。
- **提权的进程**(保守规则,E3):完整性 ≥ High(或推断提权)的进程不解密,`elevated-agent`(§10.2 行 h)。套接字表与映像路径对提权进程读得到,这个判决是保守取舍不是能力缺口。
- **没有 pid**:连接 splice `untracked` · `pid-unresolved`,一行元数据(D40:解不了密就透传并记)。1.6 §1.1「`off → on` 后在跑的 agent 透传、不被弄断」由此成立。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(门名, host)`——门名即组 id,组内每个形态一个入口,不同组互不毒化 [E15]。
- 负缓存的失败事件与清除事件都带 `neg_key`(有 pid 时是 `"<pid>"`,没有时是组 id)。读取侧(`src/health/flows.mjs`)按 `(neg_key ?? pid, host)` 归并,清除按 `neg_key` 清。W17。
- 条目只在内存:pid 退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。

| 字段 | Linux 驱动模式(eBPF) | Windows 代理模式 |
|---|---|---|
| `capture` | `transparent` | `proxy` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` |
| `proc.pid` | 内核给 | 尽力,可为 `null` |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` |

- 其余字段 MUST 逐字节相同。验收:同一 mock 调用分别经 Linux 驱动模式与 Windows 代理模式,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?, reply?}`(不含凭据;`reply` = 上游代理的回应状态码)。`bytes_up` / `bytes_down` 仍是 agent 自己那条连接上的字节:经入口的连接不含入口读走的开头(CONNECT 或 SOCKS5 握手)与 asight 的回应(那些是 asight 与客户端之间的字节,不是 agent 的)。
- **代理前导**:入口收到的 CONNECT 是客户端(经入口指向)发的、带门的口令,不是 agent 的字节;引擎发给上游代理的前导是 asight 写的。两者都不记成 `prelude`(不变式 4)。
- 读取侧:`capture` 多一个值 `proxy`;观测者效应表对两种值都适用;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

## 6. 信任入口(Windows · D37④ 的 Windows 写法)

规则同 4.6:按 harness 各走一个入口,只让该 agent 信任 asight CA;默认不写登录环境(`setx`、`HKCU\Environment` 里的 CA 变量、PowerShell `$PROFILE`),不装任何证书库。例外只有用户点名的(§2.4,D43⑥)。入口随开关:`on` 写、`off` 撤,入账、先备份(1.6 R2)。

### 6.1 表

| 形态 | asight 写什么 | 语义 · 指向 | 何时生效 | 依据 |
|---|---|---|---|---|
| `claude-code.cli` / `.vscode` | `%USERPROFILE%\.claude\settings.json` 的 `env.NODE_EXTRA_CA_CERTS` | 追加;`asight-ca.pem` 或 `extra-cc.pem`(取法同 4.6) | 启动时;扩展下一条消息即生效 | L1 |
| `codex.*` | `%CODEX_HOME%\.env` 最上面一个哨兵块,`SSL_CERT_FILE=<合并包>` | 替换;`combined-codex.pem`(§6.2) | 进程启动时读;app 与扩展要重启 | L1、L3 [E13] |
| `opencode.*` | 插件 `%USERPROFILE%\.config\opencode\plugins\asight-ca.js` | 追加;有 `tls.setDefaultCACertificates`(Node 侧车)就用它,没有(Bun)就包 `fetch` 加 `tls:{ca}` | 进程启动时 | L1、L2 |
| `kimi-code.cli` | shim `%USERPROFILE%\.asight\collector\bin\kimi.cmd` + 用户 PATH 最前一项(点名项,§6.3) | 追加;shim 设 `NODE_EXTRA_CA_CERTS` | 经 PATH 启动时 | L1 |
| `deepseek-dsh.*` | `%USERPROFILE%\.dsh\cordis.patch.yml` 一行 `- insert: [{id: asight-ca, name: ./asight-ca.mjs}]`(带哨兵注释);插件文件放在它旁边 `%USERPROFILE%\.dsh\asight-ca.mjs`(asight 的文件,入账,`off` 删)。写相对路径,与 L1 一致 | 追加;`tls.setDefaultCACertificates`(Node ≥ 22.19) | 每次启动;Desktop 热重载 | L1 |
| `hermes.cli` | `%LOCALAPPDATA%\hermes\.env` 最上面一个哨兵块,`SSL_CERT_FILE=<合并包>`;按版本加 `HERMES_CA_BUNDLE`(同 4.6) | 替换;`combined-hermes.pem` | 启动时 | L1 [E18];只测通了 Anthropic 路径 |
| `z-code.*` | `%USERPROFILE%\.zcode\cli\config.json` 的 `network.caCertFile` | 替换;`combined-z-code.pem`,绝对路径 | 新 session | L1 |

- 写进配置文件的路径一律用正斜杠(`C:/Users/<u>/…`):dotenvy 把反斜杠当转义,会静默丢掉 `SSL_CERT_FILE`。
- **用户目录有空格是常态**:`.env` 块里这样的值写成双引号包起来的,dotenvy 与 python-dotenv 读回整条路径;清单里记的仍是不带引号的路径。值里有 `"` `$` 反引号 `\` 或换行时写不了,`on` 在动任何文件之前就拒绝并说出是哪个值。
- **CRLF 的文件**:块的每一行用文件本来的行尾;用户自己的同名键照样被关掉、`prior_value` 照样记下(行尾的 `\r` 不算值)。
- **托管设置(机器级)Windows 上没读,是一处已知的缺口**:Claude Code 在 Windows 上的机器级 `managed-settings.json` 位置没量过,机器级托管的值会盖过 asight 的两个用户级键,而 `on` 不会提示(OPEN 26)。
- **插件源码与标记**:Windows 的插件是 `harness/plugins/win32/dsh.mjs` 与 `opencode.js`,不读 `/proc`(Windows 没有),只 import `node:fs` 与 `node:tls`。标记文件 `<标记目录>/<pid>` 里是 `String(Math.round(performance.timeOrigin))`。引擎拿它与助手给的 `startedAt` 比,**带容差 2000 ms**。
- 代理入口(§2.3)与信任入口写在同一个文件时放进同一个哨兵块,分别入账:`joinBlock`(默认关)把后来的行并进已有的块,撤销各自后进先出(W19 的门槛 ①–④)。

### 6.2 合并包(Windows)

- `combined-<harness>.pem` = Node 自带根(`tls.rootCertificates`)∪ Windows 根证书库的导出 ∪ 该 harness 自己配置里的用户 CA ∪ asight CA。
- Windows 根:Node ≥ 22.15 用 `tls.getCACertificates('system')`;更老的由助手只读导出 `Cert:\CurrentUser\Root` 与 `Cert:\LocalMachine\Root`(`src/off/os-roots.mjs` 的 `windowsRoots`)。只读,从不写。
- 不用 macOS 的 `cert.pem`:企业与杀毒软件的 TLS 检查根只在 Windows 库里。
- `off` 重建缺失的合并包([4.6](4.6-process-collector.md) 撤销顺序第 2 步)用同一个读取器,但只有 `getCACertificates('system')` 这一条路:独立撤销不起助手(1.6 R3,守护进程可能已不在)。Node < 22.15 时退回 Node 根,回执与 `flows/` 写明(D38)。
- Windows 的根按需下载,库里只是子集;Node 自带根补公网。守护进程启动时与每天比一次指纹,变了就原子重建(4.6)。
- **包里的每张证书都先用 Node 的 `X509Certificate` 解析一遍**,解析不了的丢掉、计数,回执与 `status` 各一行(`system-roots-unparsable`;怎么说见 [4.6](4.6-process-collector.md)「合并包」)。[T0] 量过:一块解析不了的证书让 Codex(rustls)整包拒绝。W20。

### 6.3 shim 与用户 PATH(点名项)

> **D51 修订本节**:asight 不再给 agent 加入口或启动器(PATH shim、shell rc 里的 PATH 行、桌面启动器、快捷方式),用户照常启动 agent 也要被采;下文的这几种入口随替代办法落地撤掉,本节随实现改写。

- asight 的 bin 目录里每个命令名一个 shim:`kimi.cmd` 设 `NODE_EXTRA_CA_CERTS` 与 `HTTPS_PROXY`(该形态所在组的门,带凭据);`opencode.cmd` 只设 `HTTPS_PROXY`;再 `"<真二进制>" %*`。启动环境里已有别的 `HTTPS_PROXY` 时不覆盖(那是用户这一次的选择),这一次不采。
- 用户 PATH(`HKCU\Environment\Path`)最前插一项 shim 目录:保持值的类型;从不用 `setx`(1024 字符截断);写完广播 `WM_SETTINGCHANGE`;撤时只删这一项,从不拿旧值整个写回。**kimi 与 opencode 共用这一项**:按引用计数。W55 · W64。
- **机器 PATH 在前**:Windows 先读机器 PATH,再读用户 PATH。真二进制在机器 PATH 里时 shim 输,`status` 报 `shim-not-on-path`;要赢只能把一个目录放到机器 PATH 最前,那是机器级的点名项(§2.4)。
- **机器级用的不是用户的 shim 目录**(W65):`%ProgramData%\asight\machine-bin`(只有 SYSTEM 与 Administrators 能写),里面是分发器:不含任何凭据,逻辑只有一条:运行者自己的 shim 在就调它,不在就执行点名时记下的真二进制的绝对路径。别的用户与服务各用自己的用户目录,没点名的走真二进制。
- Kimi 只在原生安装(`%USERPROFILE%\.kimi-code\bin\kimi.exe` 在)时装。Smart App Control 开着时不装:被拦的 shim 排在 PATH 最前,`kimi` 就起不来(fail-closed);改报「未信任 · Smart App Control」。

## 7. 守护进程、自启、控制面

- **守护进程** = `node <asight> daemon`。上游的信任集照 4.6 §引擎 第 5 步自己拼:Windows 系统库这一份由 `windowsRoots()` 给。`on` 先查 `process.versions.node`,低于下限(Node 20)就拒绝并给 `doctor` 一行。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(R7 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。**判据**(W25):`on` 与 `daemon` 用助手的 `token` 动词;`off` 与 `uninstall` 起不了助手,改经 `execTool` 跑 `whoami /groups /fo csv /nh`,按 SID 判:完整性标签 `S-1-16-12288` 及以上或 SYSTEM 的 `S-1-5-18`。**读不到令牌不是拒绝**:记「不知道」加原因、往下走。
- **自启**:每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`。动作 = `conhost.exe --headless "<node.exe>" "<asight.mjs>" daemon --supervise`(无窗口 [E20];`--supervise` = 任务拉起的是**监管父进程**,由它拉起真正的守护进程并在它非 0 退出时重拉)。设置 = 失败后 1 分钟重启、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML` 注册并启用;不带参数的 `off` 停用;`uninstall` 删除。**任务 XML 与单元的形状**(W24):`enable` 把它复制成带字节序标记的 UTF-16LE 副本交给 `schtasks`,读完即删。单元的形状与 Linux 的 `userUnit` 相同。**登录时只留一条启动路径**:`enable` 注册任务成功后,把 asight 先前后备写下的 Run 值取下;改用后备时,先前注册的任务 `/Change /DISABLE`。`disable()` = `/Change /DISABLE`,`remove()` = `/Delete /F`;**`/Query` 没跑起来不是「不在」**,是失败(退出码 1 仍当「不在」,W47)。**`off` 与 `uninstall` 自己也动任务**(2026-10-12 补):注册不随清单走,`off` 的第 5 步与 `uninstall` 在清单撤销之外**直接** `schtasks /Change /TN \asight\collector /DISABLE`(uninstall:`/Delete /F`)。
- **「不需要管理员」没证实过**(如实写):实验室每次都是管理员账户的过滤令牌 [E20 的限定];标准用户能不能注册带登录触发器的任务、`RestartOnFailure` 能不能拉起被杀的守护进程,都没量。**[T0] 量过的半边**:`RestartOnFailure` 拉不起被杀的守护进程,**所以任务只负责登录时拉起一次,崩溃后的重拉必须由监管父进程做**。W47 在产品实现后在标准用户上补测。
- **自启的后备**:`schtasks /Create` 被拒 → `on` 自动改用 `HKCU\…\Run` 的一项(值名 `asight-collector`,入账、先记原值),动作同上;回执写「计划任务注册被拒,改用登录启动项」并给原因,事件 `task-register-failed`(失败类,但 `on` 不失败)。**细则**(W24):「被拒」= `schtasks /Create` 起得来而拒绝,或起不来;写之前先 `reg query` 那一个值;写完再读回核对(生效要复核);**`reg query` 的输出是 reg.exe 按控制台代码页写的**,核对时 ASCII 部分逐字节相等、每一段非 ASCII 字符不限读成什么。入账条目 `{kind:'run-key', hive, key, name, value, prior}`。
- **监管父进程的退出规则**(W24 · W28 · W46):守护进程以退出码 0 退出 = 被要求停:父进程随之退出,不重拉;非 0 或被杀才按退避重拉。父进程把自己的 pid 与启动时间写进 `supervisor.lock`。不带参数的 `off` 与 `uninstall` 要停它时,**先停父进程**,再停守护进程。**细则**:① 退避 1、2、4、8、16、32、60 s 封顶,**守护进程这次活满 60 s 才死,退避从头算**。② `supervisor.lock` = `{pid, startedAt}`;**父进程是单例**:锁以独占方式建;锁已在时核对持有者,还在跑 = 第二个父进程,退出码 0。③ 守护进程起不来当成一次失败,同样退避;④ 父进程收到 SIGINT / SIGTERM / SIGHUP 或 `stop()`:结束守护进程、不再重拉、退出码 0、删锁。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`。CLI 读它再连。**token 怎么用**(W26):每个请求带头 `x-asight-token: <64 位十六进制>`;服务端在查路由之前先核它(定时安全比较),缺或错一律 401。
- **文件权限**:Windows 上「0600」没有意义。asight 的文件都在 `%USERPROFILE%` 下,靠用户目录默认的 ACL;asight 不另设 ACL,单元测试在 win32 上不断言权限位。实验室用 `icacls` 核一次(W26)。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:监管父进程拉起;门(引擎的 listener)随引擎死、随重拉开。

## 12. 闭集(D38)

放 `src/health/codes.mjs` 单独一块 `ROUTE_WHERE` · `ROUTE_EVENTS` · `ROUTE_CODES` · `ROUTE_FAILURE_CODES` · `ROUTE_TRUST_REASONS` · `ROUTE_STATUS_REASONS`,外加 `CAPTURE_KINDS`(信封 `capture` 的闭集)。与 1.6、4.7 共用的名字只定义一次,放在 `NET_*` 块里。`test/health/codes.test.mjs` 的 W38 数共用名字在文件里的字面量,多一个就红。**内核一族的码与事件(forwarder-start-failed · forwarder-restart · forwarder-digest-mismatch · forwarder-binary-missing · forwarder-download-failed · forwarder-start/stop/draining · forwarder-download-started/ok · probes-refreshed · fallback-active · pid-unresolved-mixed · where:'forwarder' · kernel-not-off)不在任何闭集里**(W38 的反向断言)。`forwarder-down` 在 `NET_*`:拓扑用它说「asight 的本地代理一跃不在」(引擎 / 门不在,§10.2 行 i)。
