## Goal

Windows 上每个用户一个采集守护进程,与 Linux 同一个引擎、同一种记录。引流只有**代理模式**(D43):

- asight 让每个 agent 用 asight 自带的本地代理内核(钉死版本的 mihomo,改名 `asight-forwarder.exe`,下文称「内核」):`on` 把 agent 的代理入口指向内核里该形态所在组的监听端口。内核按进程把 agent 的连接交给引擎,别的(agent 的子进程等)只转发。
- 引擎的上游 = 没有 asight 时 agent 会走的那一跳:它自己的代理;否则它跟随且开着的系统代理;否则直连(§2.2)。用户的出口(节点、域名规则)不变。
- 内核从不开 TUN、从不当系统代理;asight 不往任何 VPN 产品里写东西(4.7 只读)。
- 只属于这个 agent 的入口,`on` 自动写;影响超出 agent 的(用户 PATH、快捷方式、证书库、VS Code 设置、机器级位置),由用户在 `on` 里按形态点名(1.6 §1.7,本单元 §2.4)。

开关与 off 保证照 1.6(代理模式的例外登记在 1.6 §1.2「例外二」)。稳健只做两件事——asight 自己足够稳健,用户能手动从命令行撤销 asight:监管与回退(§4.3、§8);`asight off [agent]` 在 asight 坏了时也能跑(§4.2)。采集到的数据与 Linux 同一格式。哪些字段随引流不同见 `capture` 与几个路径类字段(§5.6)。

## 0. 为什么不用 WFP / WinDivert(修订 D31⑥)

| | WFP 驱动 / WinDivert | 本单元(用户态) |
|---|---|---|
| 权限与签名 | WFP 驱动要 EV 证书 + WHCP 签名;WinDivert 要管理员装驱动;未签名的组件会被 Smart App Control 拦 | 不提权、无 UAC、无防火墙提示,不碰系统代理 [E1](标准用户上的自启没量过,§7);点名的证书库一项会弹 Windows 的确认框,机器级的点名项要用户自己给管理员权限(§2.4)。**自带内核也是未签名的 exe**:Smart App Control 开着时它可能起不来(§8 预检,OPEN 19);测到的只是它关着的情形 |
| 出错时 | 驱动 bug = 整机蓝屏,不是 fail-open | 引擎死了,内核退回上游(§3.3);内核死了,守护进程拉起它,等不及就 `asight off <h>`(§4.3) |
| 覆盖 | 所有形态 | 有代理入口的形态:自动写的,或用户点名的(§2.3、§2.4) |
| 身份 | 内核给 pid | 监听端口与凭据给形态,进程规则分开 agent 与它的子进程;pid 尽力补(§5.3)[E5][E6] |

结论:删掉 WFP / WinDivert。D43 又删掉了 VPN 块:它只对 Clash Verge Rev 写得进,Verge 升级两次弄坏同类的写法(D28、D29),切换要 552 ms,进程规则看不到提权的 agent、还会把同名的形态一起引过来 [E3][E7];而代理模式在实测里 16 个形态有 15 个到了 mock(L5),没到的那个是 Claude Desktop 的信任,不是引流。还采不到的形态如实写(§6.4)。用户原先的「with vpn / with no-vpn」两种叫法随之取消:VPN 只决定上游(§2.2)。

## 2. 代理模式:入口与上游(D43)

### 2.1 一种模式

| | 是什么 |
|---|---|
| 流量怎么到 asight | 该形态的代理入口指向内核里它所在组的监听端口 `127.0.0.1:<端口>`(带凭据,§3.2);内核按进程把 agent 的连接交给引擎(§3.1),子进程等只转发 |
| asight 写什么 | 该形态的代理入口与信任入口(§2.3、§6)。只属于 agent 的,`on` 自动写;影响超出 agent 的,用户点名才写(§2.4)。都入账、先备份、`off` 撤(1.6 R2)。**代理入口就是引流,所以 MUST 在内核已按该形态读回「开」之后才写**(1.6 R9:挂引流最后;信任入口先写):内核起不来(找不到或摘要不符、Smart App Control、端口被占)时一个代理入口也不写;`off` 反过来,先把内核切成只转发并读回,再撤入口(§4.1)。W12 |
| 引擎的上游 | §2.2 的规则。内核里每个组一个 `asight-up-<g>` 出站(只转发与回退用它),引擎拨的是同一个上游(§5.2) |
| 什么时候不采 | 形态没有能用的入口、要点名而没点名、agent 提权、跟随的系统代理是 PAC:`status` 报原因码,`doctor` 给办法(§10) |

- 内核从不开 TUN、不当系统代理,不改系统代理与 VPN 的任何设置(D31④ · D43);只有指向它的 agent 经过它。
- 用户的 VPN 开着 TUN 时,引擎直连的上游照旧被 TUN 收进去,出口与 agent 原来一样。
- 用户的 VPN 看到的连接来源是 asight(内核或引擎的 `node.exe`),不是 agent:它点名 agent 的按进程规则不再匹配,域名规则照旧。D43 定只标一句,放在一处:`status <h>` 印一行(1.6 §9.2);`on` 的计划里不重复。

### 2.2 上游规则(每次 `on` 定;系统代理变了守护进程跟上)

D43:asight 的出口 = 没有 asight 时 agent 会走的那条路。`upstream.mjs` 按序取:

1. **agent 自己的代理**:`on` 写入口之前,该形态入口里的原值(harness 文件 `proxy` 声明的键;记进清单的 `prior_value`,0600)。别的进程的启动环境读不到(§10.1),登录环境只读 `HKCU\Environment` 里的代理变量(只读;点名也不写,D43)。**读不到的一种**(评审 2026-10-07 后补):只设在你终端里、由这个终端起的 agent 才会用的代理(没写进任何文件或 `HKCU\Environment`),asight 看不见;这个形态的上游会按 2、3 算,出口可能与关掉 asight 时不同。所以凡上游按 2 或 3 算出来的形态,`on` 的计划与 `status <h>` 在上游那一行注明「读不到你终端里的 HTTPS_PROXY」;`asight on` 自己的环境里有 `*_PROXY` 时(值打码)计划多一行提示:agent 若从这个终端起,它的上游可能不是下面写的。不为它另设码(OPEN 20)。
2. 否则,该形态**跟随系统代理**(harness 文件 `proxy.systemProxy`)且系统代理开着:`ProxyServer` 里的那一项(按协议分写的取 `https=`,没有就取通用的一项);目标命中 `ProxyOverride` 的直连(译成绕过表,见下)。系统代理是 PAC(`AutoConfigURL`)→ 不接这个形态,`not-routed`(asight 不执行 PAC)。
3. 否则**直连**。用户开着 TUN 或别的 L3 VPN 时,由系统照旧送进去。

| 本机网络 | 跟随系统代理的形态 | 不跟随的 | agent 自己配了代理的 |
|---|---|---|---|
| Verge · 系统代理开 · TUN 关(规则、全局、直连模式都一样) | 系统代理 `127.0.0.1:7897` | 直连 | 它自己的代理 |
| Verge · TUN 开 | 系统代理开着时同上;关着时直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| v2rayN · 系统代理开 | v2rayN 的本地端口 | 直连 | 它自己的代理 |
| 别的 TUN VPN · 系统代理关 | 直连(进 TUN) | 直连(进 TUN) | 它自己的代理 |
| 没有 VPN | 直连 | 直连 | 它自己的代理 |
| 系统代理是 PAC | 不接 · `not-routed` | 直连 | 它自己的代理 |

- **一个形态只有一个上游**。原本分两路的,接上后都走那一个:Codex 的 HTTP 跟随系统代理、WebSocket 直连 [E2][E16],接上后 WebSocket 也经系统代理,报 `egress-differs`(提示,1.6 §9.6)。
- 上游不能是 asight 自己的端口(内核的监听端口、引擎入口):`on` 不接这个形态,报 `route-loop`(原值多半是上次 `on` 没撤干净留下的)。
- **系统代理变了**(开、关、换端口):守护进程在 5 s 核对里读 `Internet Settings` 的 `ProxyEnable` `ProxyServer` `ProxyOverride` `AutoConfigURL`(§9),重算跟随它的形态的上游,重载内核配置(§4.1),写一条 `netenv-change`;不碰 agent 的设置,不算失败(1.6 §9.5)。W71。
- `on` 之后系统代理改成 PAC:上游留在上一次的值,报 `system-proxy-pac`(提示);要按 PAC 走就 `asight off <h>`(OPEN 17)。
- **agent 自己的代理变了**(入口不再是 asight 写的值):agent 已绕过 asight,`proxy-changed`,`status` 印 `asight on <h>`(1.6 §9.5、§10.3)。
- 带凭据的上游:凭据只在清单与内核配置里(0600),只用于这个 agent 的连接(§5.2,D30)。
- **绕过表**(评审 2026-10-07 后补):没有 asight 时,命中系统代理的 `ProxyOverride` 的目标、或命中 agent 自己代理的 `NO_PROXY`(同一入口里的原值,harness 文件 `proxy.noProxyKey`)的目标,agent 是直连的(内网模型网关常见)。所以每个组带一张绕过表:`<local>`(没有点的主机名)· `*.corp.com`(后缀)· `10.*` 一类(IP 段)· 精确主机。译不了的写法(中间带通配符等)不进表,`status` 写「N 条绕过规则 asight 读不懂,按走上游处理」(OPEN 21)。命中绕过表的目标:交给引擎时由引擎直连(`lookupIngress` 按 CONNECT 目标判,§5.2),只转发时由内核直连(§3.1 子规则 ②⑤)。这些连接照常被采集,出口还是 agent 原来的那一跳。
- **上游的协议**(W5):`http://`、`socks5://`、`socks5h://`(后两者同一种:都把域名交给代理解析)接得上。`https://`(到代理那一跳是 TLS)与 `socks4` 等 v1 不支持:`on` 不接这个形态,`not-routed`,doctor 码 `proxy-unsupported`(1.6 §9.6)并写明协议,不悄悄改走别的出口(OPEN 21)。

### 2.4 点名项(Windows 的写法;规则见 1.6 §1.7)

D43⑥:影响超出 agent 的改动从不默认做;`on` 的计划列出它要什么、意味着什么;用户点名,asight 执行、入账(`scope`)、先备份、`status` 列出、`off` 与独立撤销撤掉。点名用的旗标是 `--opt-in <形态>`。

| 形态 | asight 做什么 | 影响(点名文字照写) | 撤 | `scope` |
|---|---|---|---|---|

## 3. 自带内核的配置

生成器是纯函数 `src/netenv/mihomo/rules.mjs` 的 `buildForwarderConfig()`,收到的只是数据(组与形态、端口、进程规则、上游、绕过表、凭据、token),不认识任何 harness。D43 起它只为 asight 自己的内核出配置;往用户 VPN 里写块的那一半(Verge 用的 `buildBlock`、`buildScriptJs`、`spliceRuntime` 与运行时文本)删掉(计划 Task 6r)。回退部分按评审改过(§3.3)。

### 3.1 内核里有什么

对每个已装、受支持的入口组 `<g>`(§2.3)与组里的每个形态 `<f>`(评审 2026-10-07 后改:原先把组当形态,读同一个入口文件的形态共用不了端口):

| 名字 | 是什么 |
|---|---|
| `asight-l-<g>` | 监听器,`type: mixed`,`listen: 127.0.0.1`,`port: <该组端口>`,`users` = [`<g>` 与 `re.<g>`,口令都是监听口令](§3.2;收不了凭据的专用端口不设,§3.2),`rule: in-<g>` |
| `in-<g>` | 子规则,按序:① `AND,((DST-PORT,<该组端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT`(只为 `asight-re` 的探测,§3.3);② 绕过表的再进版:每条绕过(§2.2)一行 `AND,((IN-USER,re.<g>),(<绕过规则>)),DIRECT`,没有绕过就没有;③ `IN-USER,re.<g>,asight-up-<g>`(回退再进来的连接直接走上游);④ 开着时组里每个形态一行:该形态的进程规则 → `asight-fb-<f>`(没有进程规则的形态,组里至多一个,放在 ④ 的最后:`MATCH,asight-fb-<f>`);⑤ 每条绕过一行 `<绕过规则>,DIRECT`(只转发的连接在这里直连;交给引擎的连接由引擎按目标直连,§5.2);⑥ `MATCH,asight-up-<g>` |
| `asight-in-<f>` | 出站,`type: http`,`server: 127.0.0.1`,`port: <引擎入口端口>`,`username: of.<f>`,`password: <入口 token>` |
| `asight-re-<g>` | 回退出站,`type: http`,指向该组自己的监听端口,`username: re.<g>`,`password: <监听口令>`(§3.3) |
| `asight-fb-<f>` | 组,`type: fallback`,`proxies: [asight-in-<f>, asight-re-<g>]`,`url: http://127.0.0.1:<该组端口>/asight-health/<f>`,`interval: 30`,`timeout: 2000`,`lazy: true`;不设 `expected-status`(有回应就算活) |
| `asight-up-<g>` | 出站:`direct`,或上游代理(`http` / `socks5`;凭据只写在这一个出站里)。值按 §2.2 |

- 绕过规则的写法(`<绕过规则>`):`DOMAIN-SUFFIX,<后缀>` · `DOMAIN,<主机>` · `IP-CIDR,<段>,no-resolve` · `DOMAIN-REGEX,^[^.]+$`(`<local>`)。**嵌在 `AND` 里的 `IN-USER` 与 `DOMAIN-REGEX` 没在真核心上量过**,W72 的 [合约] 一半在真 mihomo 上核;核不过就改成不带 `AND` 的写法(再进连接另设一个只给回退用的监听用户),不改这里的语义。

- 组里没有开着的形态时:子规则只有 ① ② ③ ⑤ ⑥(没有绕过表就没有 ② ⑤),没有 `asight-in-<f>` 与 `asight-fb-<f>`,引擎不在它的路径上。全部关着时文本里没有引擎端口与入口 token。一个组里的形态同属一个 harness,所以同开同关。
- 全局只有:`mode: rule`、`bind-address` 与每个监听器都是 `127.0.0.1`、`allow-lan: false`、`find-process-mode: always`、`log-level: warning`(连接行会写出用户访问的主机,不要)、`profile.store-selected: false`、`geo-auto-update: false` 加 `geox-url` 全指向 `127.0.0.1:9`(不下载数据库)、控制口 `127.0.0.1:<端口>` 与 secret(端口与 secret 每次由调用方随机给)。不设 `tun`、`dns`、`unified-delay` 和任何别的入站;各端口(控制口、引擎、各形态)互不相同。
- 名字一律 `asight-` 开头。文本是 JSON(YAML 的流式写法):核心读得了(W57),测试不要 YAML 库。文本含控制口 secret、两个口令与上游的凭据:守护进程写 0600、不进日志。
- 进程规则只在 asight 自己的监听器上求值,所以进程查找的代价只落在经内核的连接上,不碰别的程序。
- 形态的端口:首次 `on` 在 17991–18989 里给每个组选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定(agent 的入口里写死它)。被占了:那个监听器开不了,报 `forwarder-start-failed`(`reason:'port-taken'`,带端口);不自己换端口(agent 的入口里写死了它),不带参数的 `off` 之后再 `on` 才重选。

### 3.2 身份

- **agent 到内核**:代理入口的 URL 带用户名与口令(`http://<g>:<监听口令>@127.0.0.1:<端口>`);HTTP 代理客户端都在第一个请求就带 Basic 凭据 [E5]。凭据不对,内核回 `407`,不碰上游(W70)。监听口令是每次安装随机的 32 位十六进制,与入口 token 不同,存 `~/.asight/collector/ingress.json`(0600),`uninstall` 删。
- **收不了凭据的入口**(Claude Desktop 的 `egressProxyUrl` 只收地址):该形态一个专用端口,不设 `users`。这时本机任何进程都能用这个端口,所以它的上游 MUST 不带凭据;上游要凭据时不接这个形态,报 `form-unsupported`,原因写明(另一种做法见 OPEN 25)。W70。
- **内核到引擎**:出站凭据 `username = of.<f>`(如 `of.claude-code.vscode`:同组的 `claude-code.cli` 是 `of.claude-code.cli`,引擎因此不靠 pid 就分得出),`password = 入口 token`。引擎验 token,不对回 407、记 `ingress-auth-failed`。用标准的 `Proxy-Authorization` 同时带身份与鉴权,不用 `X-Asight-Agent` 头。
- 这是形态级身份,不带 pid;pid 尽力补(§5.3)。

### 3.3 asight 不在时回退(本机探测)

读法(评审 2026-10-07 后补):下文 §3.3 与 §5.1 里的 `asight-in-<g>`、`asight-fb-<g>`、`of.<g>`、`/asight-health/<g>` 在组里有多个形态时,都读作按形态 `<f>` 的那个(§3.1);再进点 `asight-re-<g>`、`re.<g>`、监听口令按组。

**原设计不成立(已删)**:原写「健康检查 `http://asight-health.invalid/<g>`,引擎本地答 `204`;再进点命中 `REJECT`,mihomo 回 `502` 算活」。真 mihomo 上两个成员都判死 [源码][合约]:
- http 出站的探测总是先 `CONNECT host:80`,再在隧道里发 `HEAD`(unified-delay 开时两次)[源码 `adapter/outbound/http.go`、`adapter/adapter.go`]。引擎照 §5.1 旧写法先连上游,`.invalid` 解析失败,回 `502` → `asight-in` 死。
- mihomo 的 http 入口在匹配规则之前就对 CONNECT 答 `200`;`REJECT` 是读即 EOF 的空连接,隧道里的 `HEAD` 拿到 EOF → `asight-re` 也死 [源码 `listener/http/proxy.go`、`adapter/outbound/reject.go`]。
- 两个都死时 fallback 留在第一个成员 `asight-in`:引擎一死,引过来的流量全断(fail-closed)。

**现在的做法**:探测地址指向「再进点」自己,两个成员都能在本机答:

| | `asight-in-<f>`(经引擎) | `asight-re-<g>`(再进点) |
|---|---|---|
| 探测怎么走 | 内核对引擎入口发 `CONNECT 127.0.0.1:<再进端口>`(带 `of.<f>` 与入口 token) | 内核对再进点(该组自己的监听端口)发 `CONNECT 127.0.0.1:<再进端口>`(带 `re.<g>` 与监听口令);子规则的第一条 `AND,((DST-PORT,<再进端口>),(IP-CIDR,127.0.0.1/32,no-resolve)),DIRECT` 把它直连到再进点自己 |
| 谁答 | 引擎认出这个目标(§5.1):答 `200`,隧道里每个 `/asight-health/<f>` 请求答 `204`;不连上游、不记录 | 再进点的 http 入口收到相对路径的 `HEAD`,答 `400`、不外连 [源码 `listener/http/proxy.go`];不设 `expected-status`,有回应就算活 |
| 引擎死了 | 端口没人听,连接被拒 → 死 | 照样答 → 活 |

- **全程不出本机**:探测只到 `127.0.0.1`,不连任何外网地址,不用用户的出口。探测是 mihomo 按 asight 写的配置发的本机请求,不是对外的请求(不变式 1、D30)。用外网地址(如 `generate_204`)做探测被否决:每个间隔都经用户的出口发一次请求,等于 asight 自己发请求。
- **实测 [合约]**:引擎活着时两个成员都活,组选 `asight-in`;杀掉引擎后 2 s 内组改选 `asight-re`。引擎死后到来的那条 agent 连接没失败:mihomo 拨号被拒后立即做一次健康检查,隧道再拨一次就走了 `asight-re` [源码 `adapter/outboundgroup/groupbase.go` `onDialFailed`、`tunnel/tunnel.go` `retry`]。**这一条只在该组上一次健康检查已过去 1 秒以上时成立**,见下面「窗口期」。自带 mihomo 的形态监听器(带 `rule:` 子规则)同样成立。全程零外连。[合约] 是 `test/netenv/mihomo-contract.test.mjs`(W57),跑在开发机的 mihomo v1.19.32(darwin)上,重复 20 余次稳定;Windows 上的 Verge 2.5.7 与自带 mihomo 的复测见下面 [T0],产品落地后 W40 再测一次。**T5 起合约测试载入的是生成器自己的输出**(`buildForwarderConfig`,当时还有 VPN 块用的 `buildBlock`;自带内核那一形态在 Mac 上只叠了认人的设置:监听器要用户名、`asight-re` 带再进用户、`find-process-mode` 关,因为替身与引擎是同一个进程,进程规则分不开它们),并增加三条:带点的组 id(`claude-code.cli`,产品的 id 都带点:监听器名、子规则名、出站与组名、提供者名、探测路径、入口用户名里都有)整套再跑一遍;生成的「只转发」与「开」配置文本**原样**载入真核心(选择在 `PASS`、组在、提供者读到路由文件、引擎不在时组改选 `asight-re`、没有引擎出站、家目录里没有数据库;`PASS` 开关与路由文件 D43 起不用,开关改为重载整份配置,§4.1)。开发机 v1.19.32(darwin)上 8 条全绿;录下的探测字节与生成器出的出站一致。
- **mihomo 发的字节 [合约]**:探测的 `CONNECT` 带 `User-Agent: Go-http-client/1.1`、`Proxy-Connection: Keep-Alive`、`Host`、`Proxy-Authorization`,**头的顺序每次不同**(Go 的 map 顺序),隧道里是一或两个 `HEAD /asight-health/<g>`(`unified-delay` 关 / 开)各带 `Host` 与 `User-Agent`。引擎与它的测试不能依赖头的顺序。夹具 `test/netenv/fixtures/mihomo-probe.bytes` 是其中一次的原样字节(再进点端口归一成 18000)。
- **窗口期**:引擎进程死了(端口关):下一条连接触发检查,连接本身由 mihomo 重拨 [合约]。**例外(量到的)**:mihomo 一秒内最多做一次组检查(`singleDo`)。引擎恰好在一次检查后 1 秒内死掉时,这条连接触发不了新检查,只能带退避地重拨已死的引擎:开发机 10 次里 9 次在 1.1–2.9 s 后经 `asight-re` 成功,1 次十次重拨用完、隧道在 mihomo 已答 `200` 之后被关,agent 看到连接断开并自己重试。组在窗口过后的**下一条连接**上翻到 `asight-re`(没有流量时要等下一个间隔,30 s);agent 会重试,所以流量一般有。这就是「fail-open」在第一条连接上的真实代价,`status` 与回执不得写成「引擎死了不影响任何连接」。引擎卡住(端口开着不答):最多一个间隔加超时(约 32 s),其间新连接超时、agent 自己重试。在途连接随引擎断(4.6 §Linux 机制「fail-open 两层」的同一代价)。守护进程活着时,组选了 `asight-re` 就写 `fallback-active`(失败类)。

### 3.4 防环路

- 内核的进程规则只匹配 agent 的映像。生成时静态核对:每条进程规则都不匹配引擎的映像路径,也不匹配内核的映像路径;不过就不出配置,报 `route-loop`。`buildForwarderConfig()` 用 `ownImages`(引擎与内核的映像路径)自己做这项核对,不过抛 `RouteLoopError`(`code:'route-loop'`、`rule`、`imageIndex`)。**`ownImages` 必传**:漏传抛 `TypeError`(2026-10-07 评审:曾经漏传就悄悄不核对);只有没有引擎可环回的夹具才明写 `ownImages: null`。进程名按基名、路径与正则都不分大小写、正则不锚定(与 mihomo 一致,读得更宽)。组 id 只含字母、数字与 `. - _`(它是 Basic 用户名与探测路径的一部分,不含 `:`);进程模式里有逗号、换行或内联标志(`(?i)`)的拒收。
- 上游不能是 asight 自己的端口(§2.2):`upstream.mjs` 核对,命中就不接这个形态,报 `route-loop`。
- 用户的 VPN 开着 TUN 时,引擎与内核的直连照旧进 TUN,再由用户的规则出去;asight 的端口都在 `127.0.0.1`,TUN 不收回环,不成环(W41)。
- 用户的 VPN 看到的来源是 asight,不是 agent(§2.1 末):按进程点名 agent 的规则不再匹配,点名 asight 自己进程的规则会改变上游的出口。两样都只有那一行,不另设码,也不去读 VPN 的规则找它们(只在合适位置标一句;OPEN 24)。

## 4. 开与关

### 4.1 怎么生效

- 每次开关都向内核自己的控制口 `PUT /configs?force=true`,换成新的整份配置 [E8]:开的形态有 ③,关的形态只有 ② 与 ④。没有选择开关,没有规则文件。
- **实测 [T0]**:自带内核上「重载为只转发配置」与 30 s 以上的流、每 100 ms 一条的新连接同时跑:新连接换路 43–102 ms(两次),1 s 之后没有一条还按旧状态走,在途的流(42 个块)一个没断。
- **配置文本(T5,W12)**:`buildForwarderConfig({ groups, enginePort, token, listenerToken, controller, ownImages })`。`groups[]` = `{ g, port, upstream, bypass, auth, on, forms: [{ f, rules, hosts }] }`:`rules` 是该形态的进程规则(没有进程规则的形态为空,组里至多一个),`hosts` 只有宿主进程树里的形态有(§3.5),`bypass` 是 §2.2 的绕过表,`auth:false` 是收不了凭据的专用端口(§3.2)。每个组一个监听器 `asight-l-<g>` 与子规则 `in-<g>`,每个形态一个 `asight-in-<f>` 与 `asight-fb-<f>`(§3.1)。
- **复核**:重载之后读回。开 = `GET /proxies/asight-fb-<f>` 在、`now` 是 `asight-in-<f>`;关 = 不在。守护进程活着而 `now` 是 `asight-re-<g>` → `fallback-active`(§3.3)。读不到写「不知道」,`off` 因此退出 1。重载与内核被监管重拉之后,守护进程刷新每个开着的形态的探测(§3.3)。
- 内核不在(还没拉起、监管重拉中):`on` 拉起它再重载;`off` 只撤入口,内核起来时读到的就是只转发的配置。
- **`on` 的次序**(W12):信任入口 → 找到并核对内核、拉起它(§8)→ 载入配置并读回「开」→ 代理入口(§2.1)。读不回、内核起不来:一个代理入口也不写,回执写原因,`on` 退出 1;崩在任一步之后再 `on` 续完(1.6 R9)。`off` 反过来:内核切只转发并读回 → 撤代理入口 → 撤信任入口与点名项。

### 4.2 off 保证(照 1.6 §1.2;例外如实写)

| `off` 做什么 | 之后保证什么 | 例外(1.6 §1.2「例外二」) |
|---|---|---|
| ① 期望态写 off;② 内核里这些形态换成只转发并读回;③ 撤代理入口与信任入口(只撤 asight 写的值,1.6 §9.5)与点名项(机器级的印提权命令,§2.4);④ 引擎按 1.6 §1.3 关在途连接 | 新启动的 agent 走原来的路;引擎不在任何 agent 的路径上 | **`on` 期间启动、读了入口的 agent,重启前仍经内核(只转发,不经引擎、不解密、不记录)**;内核死了它们连不上。守护进程留在排空状态,监管内核,直到这些进程都退出,再一起退出。`status`:「还有 N 个 agent 连着 asight 的内核,重启它们之后 asight 就完全退出」。`off --now`:立即停内核,回执列出会断的 pid(操作者的显式意图)。`uninstall` 遇上排空:照 `--now` 停它,等它退出(最多 5 s)再删 `asight-forwarder.exe`;仍删不掉(文件被占)→ 留下文件,回执写原因与「重启电脑后再跑 `asight uninstall`」,退出 1 |

- 「这些进程」= 该形态里启动时间落在入口的 `installed_at` 与撤销时刻之间的进程(Windows 上不读别的进程的环境)。
- **监管父进程先停**(评审 2026-10-07 后补):不带参数的 `off` 与 `uninstall` 要停守护进程时,先停监管父进程(核对 `supervisor.lock` 的 pid 与启动时间后停,经 `execTool`),再停守护进程;顺序反了,父进程会把刚停的守护进程拉回来,「之后没有 asight 进程」(1.6 §1.4)就不成立。守护进程排空完以退出码 0 退出,父进程随之退出(§7)。独立撤销同样先停父进程。
- 透传连接与看不到终止消息的 WebSocket 等它们自己关(1.6 §1.2 第一条例外)。
- **独立撤销**:守护进程不在、源码也不在时,独立副本 `~/.asight/bin/asight-off` 做同样的撤销(1.6 R3;`src/off/win32.mjs`)。先停监管父进程。内核还在跑:经它的控制口切成只转发(凭 `forwarder.lock` 与配置里的 secret);控制口不答就停掉它。两种都在回执里写「没有守护进程替它排空」并列出连着它的 pid。W54。

### 4.3 稳健:用户的两句话

稳健只守两条:trocar 自己足够稳健,且用户随时能手动从命令行撤销 trocar。只做这两件,不另加机制:

1. **稳健**:守护进程监管内核(§8:退避重拉,连续 5 次起不来报 `forwarder-down`);监管父进程监管守护进程(§7)。引擎不在时内核退回上游(§3.3),agent 照常连通、不被采,`status` 照实写。W40 · W49。
2. **命令行撤销**:`asight off [agent]` 在守护进程坏了、源码不在时也能跑(§4.2 独立撤销)。内核死了、agent 连不上时,`doctor` 给的第一条就是它(1.6 §9.6 `forwarder-down`)。撤了之后重启那个 agent,它就不经 asight。W54 · W55。

### 4.4 按 harness 开关

- `on` / `off <harness>` 只动该 harness 各形态的子规则与入口;重载整份配置,别的形态的监听器、子规则与上游逐字节不变,在途连接不断 [T0](W55)。
- 新装了一个 harness:`on` 给它的形态选端口、加监听器。
- 用户自己改了某个 agent 的代理:`proxy-changed`,`on <h>` 把新值记成上游再指回内核(§10.3)。

## 5. 引擎的代理入口(核心 · 跨 OS)

### 5.1 入口

- 引擎多听一个回环端口 `ingressPort`(`127.0.0.1` 与 `::1`)。首次 `on` 在 17990–18989 里选一个空闲的,存 `~/.asight/collector/ingress.json`,之后固定:内核配置里写死它。端口被别的进程占了:守护进程不自己换,记 `engine-port-taken`(失败类;触发点是 `engine.listen` 的 `EADDRINUSE`,由守护进程接线处写;W73),由内核的回退接管(§3.3);不带参数的 `off` 之后再 `on` 才重选端口。`doctor` 给查占用者的命令与这两步(§10.4)。
- 认两种开头:`CONNECT host:port`(带 `Proxy-Authorization: Basic`)· SOCKS5(用户名 / 密码认证)。别的开头:关掉,记 `ingress-unknown`。(原有的「绝对 URI 的 `GET http://asight-health.invalid/…`」已删:mihomo 的探测从不这样发,§3.3。)
- **健康探测**(§3.3):凭据对、目标恰是该组的再进点 `127.0.0.1:<再进端口>` 的 CONNECT 是 mihomo 的探测。引擎答 `200`,不连上游;隧道里每个 `HEAD` 或 `GET /asight-health/<f>` 答 `204 No Content`(`Content-Length: 0`,保持连接,unified-delay 会连发两次);别的请求关掉。不进 `flows/`、不写信封。测试夹具用 mihomo 实际发的字节(`CONNECT` 加隧道里的 `HEAD`,[合约] 录下)。
- 鉴权不过:CONNECT 回 `407`,SOCKS5 回认证失败;不碰上游。
- 别的 CONNECT:引擎先连上游,再回 `200`;上游失败时回上游代理的真实回应或 `502`,不先答成功(4.6 §引擎 第 3 步的精神:不伪装)。这里 CONNECT 是内核发给 asight 的,asight 就是被问的那个代理,回答它不算替别人回答。mihomo 早已对 agent 答了 `200`,上游失败时 agent 看到连接被关 [mihomo `listener/http/proxy.go`]。
- 之后这条连接与 Linux 的透明连接一样交给 `handleFlow`:读 ClientHello、解密或透传、被动分帧、记录(4.6 §引擎 第 2–6 步)。`off` 之后关在途连接也一样(1.6 §1.3)。
- **实现细节**:
  - 开头:一个连接 10 s 内读不全开头记 `ingress-unknown`(`reason` 写「没有开头」或「CONNECT 不全」);开头之前就走掉的连接不记(没有谁问过什么)。CONNECT 的目标不是 `host:port`(IPv6 要方括号)记 `ingress-unknown`。SOCKS5 的问候里没有用户名密码一项 → 回 `[5,0xff]`,记 `ingress-auth-failed`(`reason` 写「没有给用户名密码」);SOCKS5 的非 CONNECT 命令回 `07`,记 `ingress-unknown`。
  - 鉴权:token 先验、常数时间(两边先取 SHA-256 再比),验过才查 `lookupIngress`;查不到(`null`)= 用户名不认识,同样是 407 / SOCKS5 回 `02`,记 `ingress-auth-failed`。失败记录带 `peer` 与用户名,**从不带 token**(对的错的都不带):用户名只在形如 `of.<形态>` 且不含 token 时照写(截短),否则写占位 `(not a route name)`——客户端把 token 放进了用户名一栏、或给了没有冒号的凭据,都不能让它落进 `flows/`;`lookupIngress` 抛错时 `reason` 里的用户名同此。`lookupIngress` 抛错 → 回 `502` 与 `where:'engine'` 的 `loader-down`(或 `loader-timeout`),与透明入口查不到 redirector 时同一套码。
  - 健康隧道里每次读一个请求头,等不到下一个请求 30 s 后关(静默);收到的不是 `HEAD`/`GET /asight-health/<这个组>` 记 `ingress-unknown`(`reason` 写「健康隧道里的非探测请求」)并关掉。
  - 上游拨通之前客户端走了:销毁上游,不写连接行(没有 flow,什么也没丢)。上游成功之后到 `200` 之前不会有字节写给客户端。
  - `engine.close()` 先关掉不是 flow 的入口连接(握手中、健康隧道),再等 flow 收尾:它们不是 agent 的字节,留着只会让 `close()` 等到它们的空闲超时。
  - `engine.listen({port, hosts, ingress:{port}})` 返回 `{port, ingressPort}`;redirector 没有 `lookup`(Windows)就不开透明监听,`port:null`;要入口就要 redirector 有 `lookupIngress` 且 `createEngine` 给了 `ingressToken`,否则抛 `TypeError`。`engine.stats().ingress` = `{connections, flows, health, authFailed, unknown, refused, unreachable}`(`W42` 的「入口计数」),只在开了入口时有。

### 5.2 元数据与上游

`lookupIngress({peer, user, target})` 返回 4.6 的 `FlowMeta`,另加几项:

| 字段 | 值 |
|---|---|
| `dst` | `{address: <CONNECT 目标 host>, port}` |
| `pid` · `agent` · `decrypt` | §5.3、§5.4;`agent` 取形态对应的 harness |
| `form` | 形态 id(如 `codex.app`),取自 `of.<f>`:组里每个形态在内核里有自己的出站(§3.1),所以不靠 pid 也知道是哪个形态 |
| `capture` | `proxy` |
| `upstream` | `{kind:'direct'}` · `{kind:'http', host, port, auth_ref}` · `{kind:'socks5', host, port, auth_ref}`。按该组的上游规则(§2.2);CONNECT 目标命中该组的绕过表时是 `{kind:'direct'}`(§2.2,W72)。`lookupIngress` 把 `auth_ref`(清单里的 `prior_value`)解成 `auth:{username, password}` 交给入口;入口只在拨这一条 agent 连接的前导里用它,交给 `handleFlow` 的 meta 里只剩 `credentialed:true`,凭据不进 flow、不进任何记录 |
| `pid_source` | `single-process` · `socket-table` · `null`(原有的 `forwarder-connections` 已删,§5.3) |
| `negKey` | 负缓存的键(§5.5)。`lookupIngress` 没给时入口自己补:有 pid 取 `"<pid>"`,否则取认证用的 `of.<形态>`;不补的话没有 pid 的连接会共用 `null` 一个键,互相毒化 |

- 经 `http` / `socks5` 上游时,引擎自己发代理前导。这是 asight 替 agent 走 agent 原本就会走的那个代理;用户代理的凭据(在清单 `prior_value` 里,0600)只用于这一条 agent 连接,从不用于健康检查或 asight 自己的任何请求(D30)。上游代理拒绝 → `not_captured:'proxy-refused'`(4.6 闭集)。
- **上游怎么拨**:`direct` 直连目标(域名由系统解析);`http` 向 `host:port` 发 `CONNECT <目标> HTTP/1.1`(带 `Proxy-Authorization: Basic` 当且仅当有凭据),2xx 成功,别的状态把代理的回应原样转给 agent;`socks5` 做问候(有凭据报 `0,2`,没有报 `0`)、RFC 1929、CONNECT(目标是 IPv4 / IPv6 字面量用 ATYP 1 / 4,其余用域名 ATYP 3),`rep ≠ 0` 回 `02`。代理回成功时与回应同一块到的上游字节留着、按序交给 flow(算上游先说话,4.6)。拨不通(拒连、解析失败、代理中途关)→ `502` / SOCKS5 失败回复,连接行 `decision:'error'`、`not_captured:'error'`、`error:{type, message, side:'upstream'}`;代理拒绝 → 连接行 `decision:'tunnel'`、`not_captured:'proxy-refused'`、`reason:'proxy-status-<n>'` / `'socks5-reply-<n>'` / `'socks5-auth-failed'` / `'socks5-no-acceptable-method'`、`upstream.reply`。这两种行是没有 flow 的连接的唯一记录(`stats().ingress.unreachable` / `.refused` 各计一次)。代理的回应第一行不是 HTTP 状态行(解析不出三位状态码)算拨不通、不算拒绝:`502`、行 `error.type:'bad_proxy_reply'`,代理的字节不转给 agent。**等代理没有时限**(D31:不能因为代理慢就断 agent),但不静默(D38):连代理与握手合计超过 `upstreamSlowMs`(5 s)还没回应,记一次 `upstream-slow`(`phase:'proxy-reply'`,`host` = 目标,不带 `flow_id`——这时还没有 flow——也不带凭据),连接照等;客户端先走了就不记。
- **拨不通要报**(W73):拨上游失败(拒连、解析失败、代理中途关)时,除连接行外另写一条失败 `upstream-unreachable`(`where:'netenv'`,经注入的 `onFailure`;同一形态 60 s 内最多一条,免得一个断掉的代理写出成千上万条),并进该形态的 `status` 原因(1.6 §9.7);doctor 给 `proxy-dead` 同样的查端口命令。上游代理拒绝(`proxy-refused`)是另一回事,不报它。
- **一条 agent 连接只拨一次上游**(评审 2026-10-07 后补):入口拨好的上游连接交给 `handleFlow` 用(每条连接一个包装,第一次取时给它,不再拨)。之后 4.6 的「让路」要重拨(解密不成改透传,把 ClientHello 原样发给新上游)时:上游不带凭据(直连、不要凭据的本机代理端口)才重拨;上游带用户的代理凭据,就关掉这条连接,同 4.6 隧道连接的做法:asight 不主动再发一次用户的凭据(不变式 1)。W15。关掉的那一行是 `decision:'error'`、`not_captured:'upstream-cert'`、`error:{type:'upstream_cert', side:'upstream'}`;之后该 (pid 或形态, host) 已进负缓存,客户端的重试直接透传(`negative-cache`)。不带凭据时第二次拨是新的一轮握手(直连:再连一次;`http` / `socks5`:再发一遍前导),重拨失败 → 连接行 `decision:'error'`,客户端的连接关掉;重拨等着时客户端先走了 → 代理一答就销毁新拨的上游,行同样是 `decision:'error'`、`error:{type:'closed_before_decision', side:'client'}`(没有拼接过,不写 `splice`)——代理一直不答时这条新连接留到它答或关(不设时限,D31)。

### 5.3 pid 补全(尽力,不挡采集)

| 办法 | 何时用 | 怎么做 |
|---|---|---|
| 单进程 | 该形态此刻只有一个在跑的进程 | 就是它 |
| 套接字表 | 多个进程 | 助手查 `GetExtendedTcpTable` [E6]:该形态的进程里,有连到该形态所在组的监听端口的连接(任何状态、任何一条)的进程**恰好一个** → 它;两个以上 → `null`。不再用「还没被认领的连接」:连到该组监听端口的连接里,有些永远到不了引擎,所以永远不会被认领:`on` 之前开的长连接、形态只转发时(`off` 之后、`on` 期间启动的进程)开的连接、进程规则不匹配的子进程的连接。「还没被认领」的集合因此只增不减,会把流量算到别的进程头上(评审 2026-10-07;D43 去掉了 `PASS` 开关,理由改写成这几类只转发的连接) |
| 从不 | — | 用户 VPN 与内核的 `/connections`、`/logs`:用户 VPN 的含本机所有程序的连接元数据(4.7 §3.2);内核的也不用,上面的办法够了 |

- 预算 250 ms,与连上游并行。超时、不唯一 → `pid:null`,按形态判(§5.4)。宁可 `null`,不可错:错的 pid 会让引擎解密一个不信任 asight 的进程的连接,把它弄断(§5.4 的承诺)。
- 超过预算不记失败(慢,不是不可用);读不到才记 `socktable-unavailable`,每次调用一条,由记录器折叠。`hop` 可带 `address` 收窄到该远端地址;不带时只比远端端口:真属主的那一行一定在表里,多出的行只会让答案变成「不唯一」,不会变成错的。助手只被问候选进程的行,答案在 JS 里再过滤一遍(助手不照做也不影响)。
- 引擎的对端是内核,不是 agent;上面的办法只看 agent 一侧到监听端口的连接。这条路没量过:W43 [WinVM] 用真值核对(同一形态 3 个进程,2 个已信任、1 个未信任,200 条并发连接,另有 `on` 之前就开着的长连接),错认必须是 0。
- **代价**(观测者效应):多进程形态的新连接,首字节最多多等 250 ms。`flows/` 连接行记 `pid_ms`。常驻助手的一次表查询约 5 ms [E6];W43 [WinVM] 量 p50 / p90。
- 套接字表读不到(受限令牌、策略禁用 `Add-Type`)→ 一条失败事件 `socktable-unavailable`,之后全按形态判。

### 5.4 信任判定

- **有 pid**:照 4.6 §确认信任,按 pid 判:进程启动时间与入口的 `installed_at`、插件标记、Kimi shim 的父进程。
- **专用端口、没有进程规则**(dsh CLI,§3.5):pid 是该形态的进程且已信任才解密,别的(子进程、补不出 pid)透传。
- **没有 pid**:按形态判。该形态在跑的进程**全部**已信任 → 解密;有一个未信任 → 透传,`not_captured:'untrusted'`,`reason:'pid-unresolved-mixed'`。这样 1.6 §1.1「`off → on` 后在跑的 agent 透传、不被弄断」在没有 pid 时也成立。代价:同一形态的新进程要等旧进程退出才被采集,`status` 点名旧进程。

### 5.5 负缓存的键

- 有 pid:`(pid, host)`(4.6)。没有 pid:`(of.<形态>, host)`。不同形态互不毒化 [E15]。
- 负缓存的失败事件与清除事件都带 `neg_key`(有 pid 时是 `"<pid>"`,没有时是 `"of.<形态>"`)。读取侧(`src/health/flows.mjs`)按 `(neg_key ?? pid, host)` 归并,清除按 `neg_key` 清;否则两个都没有 pid 的形态会撞在 `(null, host)` 上(评审 2026-10-07;写回 4.6 §记录)。W17。
- 条目只在内存:pid 退出、或该形态的进程全退出、或引擎重启时清掉;`status` 列出。

### 5.6 记录:与 Linux 同一种格式

不同平台上的数据格式必须一样:信封、`flows/`、D35 封存、读取侧都照 4.6 §记录。下表写明哪几个字段随引流不同:

| 字段 | Linux 驱动模式(eBPF) | Windows 代理模式 |
|---|---|---|
| `capture` | `transparent` | `proxy` |
| `dst` | agent `connect()` 的目的地 `ip:port` | 入口收到的 CONNECT 目标 `host:port` |
| `proc.pid` | 内核给 | 尽力,可为 `null` |
| `proc.exe` | `/proc/<pid>/exe` | 进程快照的映像路径;没有 pid 时为 `null` |

- 其余字段(请求与响应的原始字节、头、体、`host`、`scheme`、`endpoint`、`transport`、`ws_*`、`asight_added`、各种标注)MUST 逐字节相同。验收:同一 mock 调用分别经 Linux 驱动模式与 Windows 代理模式,信封去掉 `ts*`、`id`、`flow_id`、`seq` 和上表四个字段后 `deepEqual`(W14 单元、W50 [VM]+[WinVM])。
- `flows/` 连接行追加 `ingress:{route, group}`、`pid_source`、`pid_ms`、`upstream:{kind, host?, port?, reply?}`(不含凭据;`reply` = 上游代理的回应状态码,`http` 是 HTTP 状态,`socks5` 是 REP 字节;直连没有)。`bytes_up` / `bytes_down` 仍是 agent 自己那条连接上的字节(4.6 §记录):经入口的连接不含入口读走的开头(CONNECT 或 SOCKS5 握手)与 asight 回给 mihomo 的 `200` / SOCKS 回复(那些是 asight 与 mihomo 之间的字节,不是 agent 的)。W14 的行比较因此连字节数也相等(`bytes_down` 里叶证的 ECDSA 签名长度会差一两个字节,不算)。`capture` 不进连接行,只进信封(Task 2(b) 接线:`flow.mjs` 的 `startTee` 要把 `meta.capture` 带进交换记录的 `flow`)。
- **代理前导**:入口收到的 CONNECT 是内核发的、带 asight 的 token,不是 agent 的字节;引擎发给上游代理的前导是 asight 写的。两者都不记成 `prelude`(4.6 的 `prelude` 只记 agent 自己发、代理自己答的字节;不变式 4)。连接行改记 `ingress` 与 `upstream`(含上游代理的回应状态码 `upstream.reply`)。所以 agent 自己配了代理时,Linux 的行有 `prelude`、Windows 的没有;W14 / W50 的比较只比信封,另比一次「直连上游」的连接行去掉上述字段后相等。
- 读取侧:`capture` 多一个值 `proxy`(改 4.1 信封表;Linux 已写进数据的 `transparent` 不动,不变式 2);观测者效应表(`src/dissect/harnesses.mjs`)对两种值都适用;看板就地标引流方式;`proc.pid` 为 `null` 的调用不按 pid 做任何事(3.4 本就不按 pid 切 session)。

## 6. 信任入口(Windows · D37④ 的 Windows 写法)

规则同 4.6:按 harness 各走一个入口,只让该 agent 信任 asight CA;默认不写登录环境(`setx`、`HKCU\Environment` 里的 CA 变量、PowerShell `$PROFILE`),不装任何证书库(`CurrentUser\Root`、`LocalMachine\Root`)。例外只有用户点名的(§2.4,D43⑥):Claude Desktop 的 `CurrentUser\Root`、VS Code 与 Z-Code Desktop 的应用设置、机器级证书库;`HTTPS_PROXY` 一类代理变量点名也不写进登录环境。入口随开关:`on` 写、`off` 撤,入账、先备份(1.6 R2)。

- **用户目录有空格是常态**(`C:\Users\John Smith`、`OneDrive - Contoso`):`.env` 块里这样的值写成双引号包起来的(`SSL_CERT_FILE="C:/Users/John Smith/.asight/…/combined-codex.pem"`),dotenvy 与 python-dotenv 读回整条路径;清单里记的仍是不带引号的路径。值里有 `"` `$` 反引号 `\` 或换行时写不了,`on` 在动任何文件之前就拒绝并说出是哪个值(这样的用户目录少见,拒绝是响的,不会静默丢入口)。Linux 的块不带这个选项,仍只写不带空格的绝对路径(4.6)。
- **CRLF 的文件**(Windows 上的编辑器多半这么存 `.env`):块的每一行用文件本来的行尾,所以编辑器不会把它改成两种行尾混着;用户自己的同名键(`SSL_CERT_FILE`、`HTTPS_PROXY`、`NO_PROXY`)照样被关掉、`prior_value` 照样记下(行尾的 `\r` 不算值);用户的编辑器之后把行尾改成 LF 或 CRLF,`off` 还是找得到块。

- **插件源码与标记**(Task 4):Windows 的插件是 `harness/plugins/win32/dsh.mjs` 与 `opencode.js`,不读 `/proc`(Windows 没有),只 import `node:fs` 与 `node:tls`。标记文件 `<标记目录>/<pid>` 里是 `String(Math.round(performance.timeOrigin))`,即本进程启动的毫秒数,先写临时文件再改名。引擎拿它与助手给的 `startedAt` 比,**带容差**(Linux 的 `/proc` 值是整数,这里是毫秒取整,不会逐字相等;容差由 Task 8 定)。没有 `tls.setDefaultCACertificates`、带 `--use-openssl-ca`、CA 文件缺失或不是 PEM → 什么都不加、不写标记、不抛。OpenCode 的插件在 Node 侧车上用 `setDefaultCACertificates`,在 Bun 上包 `fetch`(追加 asight 的 CA,请求与响应原样经过,不读 body),两样都没有就什么都不做。
- 代理入口(§2.3)与信任入口写在同一个文件时放进同一个哨兵块(Codex、Hermes 的 `.env`),分别入账。
- 点名的信任项(Claude Desktop、Kimi 的 VS Code 扩展、Z-Code Desktop、机器级证书库)见 §2.4。

### 6.2 合并包(Windows)

- `combined-<harness>.pem` = Node 自带根(`tls.rootCertificates`)∪ Windows 根证书库的导出 ∪ 该 harness 自己配置里的用户 CA ∪ asight CA。
- Windows 根:Node ≥ 22.15 用 `tls.getCACertificates('system')`;更老的由助手只读导出 `Cert:\CurrentUser\Root` 与 `Cert:\LocalMachine\Root`(`roots.mjs`)。只读,从不写。Node 24 上 `tls.getCACertificates` 与 `tls.setDefaultCACertificates` 都有(dsh 与 OpenCode 的插件路径可用),`getCACertificates('system')` 给的证书全部能被 `X509Certificate` 解析。
- 不用 macOS 的 `cert.pem`:企业与杀毒软件的 TLS 检查根只在 Windows 库里。
- Windows 的根按需下载,库里只是子集;Node 自带根补公网。守护进程启动时与每天比一次指纹,变了就原子重建(4.6)。
- **包里的每张证书都先用 Node 的 `X509Certificate` 解析一遍**,解析不了的丢掉、计数,回执与 `status` 各一行(「Windows 根里 N 张证书解析不了,没放进包」)。Codex 用 rustls,一张怪证书可能让它整包拒绝、哪都连不上;**[T0] 量过**(Codex 0.160.1 对本机 TLS mock,服务端证书由 asight 替身 CA 签):真导出的 Windows 根(`CurrentUser\Root` 265 张 + `LocalMachine\Root` 265 张,去重 261 张,433,748 字节,全部能被 .NET 解析)加替身 CA,Codex 连得上(`SSL_CERT_FILE` 与 `CODEX_CA_CERTIFICATE` 都认);只有根、没有替身 CA,连不上(90 s 里不停重连,一个请求也没到 mock);**根 + 一块解析不了的证书,连不上,坏块在替身 CA 之前或之后都一样:一块坏证书让整个包作废**。所以先过滤是必须的(上一条)。Node 的 `tls.getCACertificates('system')` 给 467 张,比两个根库去重后的 261 张多,守护进程与合并包取的是前者(Node 自己的系统集),这一差别的原因没细查。W20。

### 6.3 shim 与用户 PATH(点名项)

- asight 的 bin 目录里每个命令名一个 shim:`kimi.cmd` 设 `NODE_EXTRA_CA_CERTS`(取法同 4.6 的 `extra-kimi.pem` 规则)与 `HTTPS_PROXY`(内核里该形态所在组的端口,带凭据);`opencode.cmd` 只设 `HTTPS_PROXY`(信任走插件);再 `"<真二进制>" %*`。启动环境里已有别的 `HTTPS_PROXY` 时不覆盖(那是用户这一次的选择),这一次不采。
- 用户 PATH(`HKCU\Environment\Path`)最前插一项 shim 目录:保持值的类型(`REG_EXPAND_SZ` 还是它);从不用 `setx`(1024 字符截断);写完广播 `WM_SETTINGCHANGE`;撤时只删这一项,从不拿旧值整个写回(D28 的教训)。值在 asight 改过之后又被改过:只删这一项,报「已撤销,但不逐字节相同」。**kimi 与 opencode 共用这一项**(评审 2026-10-07 后补):按引用计数,`off kimi-code` 只删 kimi 自己的 shim 文件,PATH 里这一项与 shim 目录在最后一个 shim 撤掉时才删,不弄坏另一个 harness(`shim-not-on-path`)。W55 · W64。
- 这一项改的是本用户所有程序看到的 PATH 顺序,所以是点名项(D43⑥;Linux 的 rc 那一行同理)。shim 目录专用,只放 agent 命令的 shim。
- **机器 PATH 在前**:Windows 先读机器 PATH,再读用户 PATH。用户 PATH 最前的 shim 只赢得过装在用户 PATH 目录里的真二进制(npm 全局 `%APPDATA%\npm`、pipx / uv、scoop、winget Links)。真二进制在机器 PATH 里时 shim 输,`status` 报 `shim-not-on-path`;要赢只能把一个目录放到机器 PATH 最前,那是机器级的点名项,要用户自己给管理员权限(§2.4)。
- **机器级用的不是用户的 shim 目录**(W65):`%USERPROFILE%\.asight\collector\bin` 本用户的任何进程都能写,放到机器 PATH 最前,等于让这个用户的任何进程往管理员与 SYSTEM 的命令查找路径里放同名文件(PATH 劫持)。所以机器级的点名项由提权这一步另建 `%ProgramData%\asight\machine-bin`(只有 SYSTEM 与 Administrators 能写,Users 只读与执行),里面是分发器:`kimi.cmd`、`opencode.cmd`,不含任何凭据,逻辑只有一条:运行者自己的 shim `%USERPROFILE%\.asight\collector\bin\<命令>.cmd` 在就调它,不在就执行点名时记下的真二进制的绝对路径(`status` 核对它还在,不在报 `entry-changed`)。机器 PATH 里放这个目录,不放用户的目录。别的用户与服务各用自己的用户目录,没点名的走真二进制,不经这个用户的内核。所有用户的开始菜单快捷方式(`opencode.desktop`)同理,指向这个目录里的启动器。
- Kimi 只在原生安装(`%USERPROFILE%\.kimi-code\bin\kimi.exe` 在)时装。Smart App Control 开着时不装:被拦的 shim 排在 PATH 最前,`kimi` 就起不来(fail-closed);改报「未信任 · Smart App Control」。

## 7. 守护进程、自启、控制面

- **守护进程** = `node <asight> daemon`。上游的信任集照 4.6 §引擎 第 5 步自己拼:Windows 系统库这一份由 `windowsRoots()` 给(Node ≥ 22.15 用 `tls.getCACertificates('system')`,更老的由助手只读导出,§6.2)。不加 `--use-system-ca`(原稿加了):那个选项要 Node ≥ 22.15,更老的 Node 上守护进程每次登录都以「bad option」退出;信任集已经自己拼了,选项是多余的。`on` 先查 `process.versions.node`,低于计划的下限(Node 20)就拒绝并给 `doctor` 一行。以安装它的用户、Medium 完整性运行;令牌是提升的或是 SYSTEM 时拒绝启动(R7 的 Windows 写法)。`on` / `off` / `uninstall` 同样拒绝提升的令牌。
- **自启**:每个用户一个计划任务 `\asight\collector`。触发 = 本用户登录;主体 = 本用户,`LogonType Interactive`,`RunLevel LeastPrivilege`(不用 S4U:S4U 不受 UAC 过滤,是 High 完整性)。动作 = `conhost.exe --headless "<node.exe>" "<asight.mjs>" daemon`(无窗口 [E20])。设置 = 失败后 1 分钟重启(最多 999 次)、不限运行时长、用电池时不停、只跑一个实例。`on` 用 `schtasks /Create /XML`(经 `execTool`)注册并启用;不带参数的 `off` 停用;`uninstall` 删除。
- **「不需要管理员」没证实过**(如实写):测到的只是管理员账户的过滤令牌 [E20 的限定];标准用户能不能注册带登录触发器的任务、`RestartOnFailure` 能不能拉起被杀的守护进程,都没量。**[T0] 量过一半**(没有新建账户:创建账户只有操作者能做,所以**本地标准用户仍没量**)。以普通用户、Medium 完整性(管理员账户的过滤令牌,`IsInRole(Administrator)` 为假)从非提升进程跑:`schtasks /Create /XML` 注册成功(登录触发、本用户、`InteractiveToken`、不是 `HighestAvailable`——`schtasks /Query /XML` 对默认的 `LeastPrivilege` 不印 `RunLevel`、`RestartOnFailure` 都在);`/Run` 起来的进程在登录会话 2 里,父进程是 `conhost.exe`。**`RestartOnFailure` 拉不起被杀的守护进程**:杀掉守护进程(`node`)、杀掉任务自己的进程(`conhost --headless`)、守护进程自己以退出码 3 退出,三种各等 100 s(间隔设的 1 分钟),都没有被重新拉起;任务的 `Last Result` 分别是 0、-1、0,即 `conhost --headless` 把子进程的退出码吞成了 0。**所以任务只负责登录时拉起一次,崩溃后的重拉必须由监管父进程做**(见下一条,不再只是后备)。W47 在产品实现后在标准用户上补测。
- **自启的后备**:`schtasks /Create` 被拒绝 → `on` 自动改用 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的一项(值名 `asight-collector`,入账、先记原值,`off` / `uninstall` 只删这一项),动作同上,但 `asight daemon` 以「监管父进程」方式跑:一个小父进程拉起真正的守护进程,它退出就按 1、2、4…60 s 退避重拉。回执写「计划任务注册被拒,改用登录启动项」并给原因,事件 `task-register-failed`(失败类,但 `on` 不失败)。**[T0] 已显示计划任务拉不起被杀的守护进程**(上一条):监管父进程是默认做法,不只是计划任务注册被拒时的后备;任务的 `RestartOnFailure` 照写(多一层不坏),但不当作重拉的依据。
- **监管父进程的退出规则**(W24 · W28 · W46):守护进程以退出码 0 退出 = 被要求停(`off` 排空完、`uninstall`、`off --now`):父进程随之退出,不重拉;非 0 或被杀(没有退出码)才按退避重拉。父进程把自己的 pid 与启动时间写进 `supervisor.lock`。不带参数的 `off` 与 `uninstall` 要停它时,**先停父进程**,再停守护进程(§4.2);`schtasks /Change /DISABLE` 不结束正在跑的实例,所以不能只靠它。这样「`off` 之后没有 asight 进程」(1.6 §1.4)成立,`off` 也不会被父进程撤销。
- **控制面**:命名管道 `\\.\pipe\asight-<16 位随机十六进制>`。名字与随机 token 写 `%USERPROFILE%\.asight\collector\control.json`。CLI 读它再连。名字随机,防同机别的用户先占一个固定名字。
- **文件权限**:Windows 上「0600」没有意义。asight 的文件都在 `%USERPROFILE%` 下,靠用户目录默认的 ACL(本用户、SYSTEM、Administrators);asight 不另设 ACL,单元测试在 win32 上不断言权限位。用 `icacls` 核一次(W26)。
- **lock** 同 4.6(pid、启动时间;`boot_id` 换成系统启动时间)。
- **登出**:计划任务的进程随会话结束,下次登录拉起。Windows 没有 linger,不提示。
- **守护进程死了**:监管父进程拉起(计划任务只在登录时拉起一次);其间内核退回上游(§3.3)。

## 8. 自带内核:来源、许可、监管

- **钉死版本**:`src/collector/arch/win32/mihomo-pin.json` = `{version, assets:{x64:{variant, package, name, url, size, sha256, exe:{name, size, sha256}}, arm64:{…}}, license:'GPL-3.0-only', licenseFile:{name, sha256}, source}`。`package` 是该平台包的 npm 名,`exe` 是包里那个文件(`exe.name` 就是 `asight-forwarder.exe`);`name` `url` `size` `sha256` 是官方压缩包的,**只有构建脚本用(见下面「构建脚本才下载」),CLI 运行时从不读它们去联网**,运行时只认 `package` 与 `exe`;`licenseFile` 是仓库里 `LICENSE-mihomo.txt`(钉死 tag 上 mihomo 自己的 LICENSE,GPL-3.0 全文)的名字与摘要;`source` 是钉死 tag 的源码地址。首版钉 v1.19.32;官方压缩包只从 `https://github.com/MetaCubeX/mihomo/releases/download/<version>/` 取,且只由构建脚本取。变体写明:x64 用 `windows-amd64-compatible`(不挑 CPU 指令集),arm64 用 `windows-arm64`。压缩包与**解出来的 exe** 两个摘要都钉:实现时按发布页的 digest 填,两次独立下载、解压后核对一致才写进仓库。**[T0] 能钉的先钉**:发布页(GitHub API 的 `digest` 字段)给出的压缩包 `mihomo-windows-amd64-compatible-v1.19.32.zip` 22,525,067 字节、sha256 `974a4d7ad69aed27aa2e8f91d61113573c14dadb14562c63e58effabf59816f0`;`mihomo-windows-arm64-v1.19.32.zip` 20,194,736 字节、sha256 `7a4f6e58af9a120920935f2150cf642d945085fdb3e753314505b334234e1d1e`。**官方包本身没下载、没在 Windows 上跑**:下载并执行外部文件只有操作者能放行,T0 的执行者没有这个授权。核对那一次要做的是两次独立下载、`tar.exe -xf`、解出 exe 的大小与 sha256、Authenticode 状态、起一次;**exe 的大小与 sha256 因此仍待填**:由构建脚本的 `--pin` 模式做(两次独立下载、解压、核对一致)后填进 `mihomo-pin.json`;没填(`null`)之前 `ensureBinary` 拒绝,写 `forwarder-binary-missing`(`reason:'not-pinned'`)。Verge 带的 `verge-mihomo.exe`(同为 v1.19.32 的 Windows 核心)**未签名**(`NotSigned`);拷成 `asight-forwarder.exe` 后在 Medium 完整性下起来、控制口答。
- **怎么拿到**(内核随 asight 装,不在首次 `on` 时从官方发布页下载;取代原先按 1.6 R8 例外下载的写法,OPEN 4):**`on` 从不下载**,1.6 R8「CLI 不联网」里关于下载的那条例外撤掉了。内核放在**每平台一个的可选 npm 包**里(同 esbuild 的做法):包用 `os` / `cpu` 限定,npm 只装与本机相符的那一个(`win32-x64` · `win32-arm64`,包名取 pin 的 `package`);包里是解出来的 `asight-forwarder.exe`、`LICENSE-mihomo.txt`(GPL-3.0 全文)与 `SOURCE-mihomo.txt`(钉死 tag 的源码地址)。Windows 的 GitHub Release 带的是同一批包的 tarball([4.5](4.5-distribution.md) §A):离线装 = `npm i -g <主包>.tgz <平台包>.tgz`,得到同一棵目录,所以只有一处查找(平台包的目录),Release 不是第二条路径。**许可**:GPL-3.0-only。它是独立的可执行文件,asight 不链接它、不 import 它,只经命令行与控制口用它(聚合),asight 自己的许可不受影响;包本身按 GPL-3.0 分发,所以随包带许可证全文与源码地址(「聚合」的说法另见 0.1 §4 为它写的一条例外);回执写明。
- **`ensureBinary()` = 找到、核对、复制;不联网**(W27):① 从 asight 自己的安装位置解析平台包(`createRequire` 找 `<package>/package.json`);找不到(例如 `npm i --omit=optional`)→ `forwarder-binary-missing`,`reason:'package-not-installed'`;架构不在 pin 里 → `unsupported-arch`;pin 的 `exe.sha256` 是 `null` → `not-pinned`。② 核包里那个 exe 的大小与 sha256 对 pin 的 `exe`;不符 → `forwarder-digest-mismatch`(`of:'package'`),不复制、不启动,**不碰包目录**(那是 npm 的东西)。③ 复制到下面「放哪」的位置,核复制出来那份的 sha256,`LICENSE-mihomo.txt` 与 `SOURCE-mihomo.txt` 一起放过去;目标已在且摘要对就不重写。④ **每次拉起内核之前**(首次 `on`、监管的每一次重拉)都核一遍 `kernel\` 里那份的 sha256 对 pin;不符 → 不拉起,`forwarder-digest-mismatch`(`of:'copy'`);不在 → `forwarder-binary-missing`(`reason:'file-missing'`)。重拉不从包里补一份:那份是跑过的东西,被改了或不见了是要报的失败,`on` 才补。⑤ 找不到或不符时,回执与 `doctor` 写**重装命令**(字面量,两条都写,因为 asight 看不出自己是怎么装的:npm 装的 `npm install --global <主包名>@<版本> --include=optional`;Release 装的 `npm install --global <主包>.tgz <平台包>.tgz`),asight 不替用户跑它(1.6 R8)。⑥ **`on` 的计划有内核这一行**(只读的 `locateKernel()`:找到且摘要对 / 没找到 / 不符,带重装命令);没找到或不符时 `on` 在写任何东西之前退出 1:没有下载可等,这是确定的前置条件,不必先写信任入口再失败。不看 Authenticode 签名:钉死的 sha256 比签名者更严,内核本来就未签名(Smart App Control 一条)。
- **构建脚本才下载**(W75):`scripts/kernel-payload.mjs` 由维护者发布时跑,不在 `files` 里、不随包发,不是 CLI,不受 R8 约束。它读 pin,从官方压缩包地址下载(维护者的机器与网络),核压缩包摘要,用系统 `tar -xf` 解(bsdtar 能解 zip:macOS,Windows 10 1803 起自带),核解出来的 exe 的摘要,再生成两个平台包的目录(`package.json` 由 pin 与主包版本生成)与它们的 `npm pack` tarball,npm 发布与 Release 用同一份;exe 与生成的包都不入 git(默认输出到 `dist/kernel/<包名>/`,`.gitignore` 里有 `dist/` 与 `*.exe`)。`--pin` 模式只印两次独立下载的 exe 大小与 sha256,供填进 pin。主包只在发布到 npm 时才在清单里加 `optionalDependencies`(两个平台包,版本 = 主包版本);私有阶段只有 Release 的 tarball。包名随主包的发布名定(4.5 阻断);首版用 `asight-kernel-win32-x64` 与 `asight-kernel-win32-arm64`,发布名定了一起改,pin 的 `package` 是唯一出处。
- **放哪**:`%USERPROFILE%\.asight\collector\kernel\asight-forwarder.exe`(专用目录,不在 shim 的 bin 目录里;文件名就是 `asight-forwarder.exe`,进程名不与用户自己的 mihomo 撞),旁边放 `LICENSE-mihomo.txt` 与 `SOURCE-mihomo.txt`。**为什么复制一份、不直接从包目录里跑**:Windows 不许替换或删除正在跑的 exe,而内核在排空时(§4.2)可以活得比一次 `off` 久得多;从 `node_modules` 里跑,期间的 `npm i -g` 升级或 `npm uninstall` 会因文件被占而失败,正在跑的内核还会和包目录一起悬空。复制出来的这份归 asight(入账 `forwarder-binary`,`uninstall` 删,§4.2),包目录归 npm。回执写明它是独立的 GPL-3 程序(聚合,asight 不链接它)。
- **监管**:守护进程以分离方式拉起它(守护进程崩了它不跟着死),`forwarder.lock` 记 pid 与启动时间。守护进程重启时认领它:pid、启动时间、控制口 `GET /version` 三者都对得上。它退出了:按 1、2、4…30 s 退避重拉,每次一条 `forwarder-restart`;连续 5 次起不来 → `forwarder-down`(失败类)。起不来时先分类:Smart App Control 开着(同 §6.3 的注册表读法)→ 原因 `smart-app-control`,未签名的 `asight-forwarder.exe` 很可能被它拦了;别的照实记 `forwarder-start-failed` 加 errno。测到的环境里 `VerifiedAndReputablePolicyState` = 0(关)。关着,所以那个未签名的核心照样起来,这**证明不了**开着时也行;开着时的情形仍按 `smart-app-control` 处理,没测。asight 不因此改 agent 的设置(1.6 §9.5),`doctor` 给命令。
- **Smart App Control 预检**(W74):未签名的 `asight-forwarder.exe` 在 Smart App Control 开着时很可能被拦,而代理模式没有它就没有引流;测到的只是它关着的情形,开着的没测。所以 `on` 先只读 `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy` 的 `VerifiedAndReputablePolicyState`(0 = 关,1 = 开,2 = 评估 [预期];读不到写「不知道」加原因):开或评估时,计划里写「Smart App Control 开着:未签名的 asight-forwarder.exe 很可能起不来,代理模式用不了」,仍让用户确认、仍去试(失败时上一条把原因记成 `smart-app-control`,一个代理入口也不写,§4.1)。asight 不改这个系统安全设置、也不替用户选;`doctor` 只写事实与选择(§10.4),不给改它的命令。OPEN 19。
- **代理模式总要它**(D43):首次 `on` 就要有。全部关着、也没有排空中的 agent 时不启动。
- 只转发与排空见 §4.2。

## 10. 网络拓扑与诊断(Windows 的形状 · 细化 1.6 §9)

跨平台规则(画法、`--json` 形状、用户自己的代理、发现目录)以 1.6 §9 为准,这里只写 Windows 的部分。

### 10.1 每一跳从哪读

| 跳 | 读什么 |
|---|---|
| agent | 助手的进程快照:映像路径、启动时间、完整性(读不到写「不知道 · denied」)、父进程(经不经入口,§2.4)。**提权的判法**:完整性读得到且 ≥ High → 提权;令牌打不开(拒绝)而映像路径读得到(`PROCESS_QUERY_LIMITED_INFORMATION` 跨完整性也能开)→ 判提权,标「推断」 |
| 入口 | 安装清单 + 文件读回:入口还是 asight 写的值吗;点名项的核对(§2.4) |
| agent 的代理与上游 | harness 文件 `proxy` 声明的配置键(读法同信任 resolver)与清单的 `prior_value`;系统代理(`HKCU\…\Internet Settings` 的 `ProxyEnable` / `ProxyServer` / `AutoConfigURL`)只对声明跟随它的形态算。别的进程的启动环境读不到(Windows 上不读进程内存):那一跳写「不知道 · env-unreadable」,标「推断」 |
