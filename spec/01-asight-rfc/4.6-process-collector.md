# asight · RFC 4.6 — 按进程透明采集器(D31 落地 · Linux 先行)

> **状态**:设计已定(**D32**,2026-10-05;**D36** 同日修订:撤回专用账号,采集守护进程按用户运行,特权只在能力助手)。Linux 先实现、先在测试机上验收;macOS / Windows 只定接口,机制后补。
> **前置**:方向 = D31(按进程、agent 无感、不碰 base_url / 系统代理 / VPN);改包 = D30 + [5.1](5.1-intervention.md);信封 = [4.1](4.1-capture-sources.md) §统一原始信封(D10)。
> **取代**:落地并在本机验收后,[4.1](4.1-capture-sources.md) 的 base_url 反代、Clash steer、按 host 解密退役。过渡期两套并存,互不接线。

## Goal

每个系统用户一个常驻、稳定的采集守护进程,以该用户身份运行:认出该用户自己的 agent 进程,把它们的新连接引到本地引擎,解密、逐字记录,再原样转发。开关只改变守护进程自己的行为,agent 不重启、看不出差别。任何部件崩溃,agent 的流量都直接走原路(fail-open)。唯一带特权的部分是守护进程拉起的能力助手,每台机器 sudo 装一次(D36)。

## 结构:平台相关 / 平台无关 / harness 相关 分目录

仿 Linux 内核的 `arch/`:加一个平台只动 `arch/<os>/`,加一个 harness 只动 `harness/`。

```
src/collector/
  core/                 平台无关:引擎、记录、开关、控制面、改包
    engine/             接连接 → 查元数据 → 嗅探 → 解密 / 透传 / CONNECT 隧道
    http1/              HTTP/1.1 被动分帧(双向)、SSE 逐字
    ws/                 WebSocket 旁路记录:分帧、解掩码、permessage-deflate(D37)
    tls/                CA 与叶证(node:crypto 自签,零依赖)
    record/             信封写入、flows / audit / replays 流
    intervene/          规则、扣留队列、重发(D30)
    trust/              信任入口:注入计划、安装日志与撤销、合并包(D37④)
    registry.mjs        按 harness 描述匹配进程(本身不含任何 harness 名)
    switch.mjs          开关状态机(期望态 vs 内核实际态)
    control.mjs         本机控制面(unix socket)
  arch/linux/           eBPF 程序、C redirector(能力助手)、/proc 读取、用户级 systemd 单元(可选)
  arch/darwin/          (待写)Network Extension 透明代理
  arch/win32/           (待写)WFP
  harness/              每个 harness 一个文件:进程特征、信任入口与其 resolver、已知 API host、配置读取器(D37;session 键等读取侧约定在 src/dissect/harnesses.mjs,见 3.1)
    plugins/            dsh、OpenCode 的信任插件源码(D37④)
    shims/              Kimi 的启动 shim 模板(D37④)
```

平台层对核心只暴露一个接口 `Redirector`:`attach() / detach() / status() / watch(pid, verdict) / unwatch(pid) / lookup(peer) → {dst, pid, agent} / heartbeat()`,外加进程事件流 `exec / exit`。核心不出现任何 `process.platform` 分支。

**特权钩子按 OS 各写一份,引擎侧契约到处一样(D36)**:内核钩子在每个 OS 上都要特权;钩子以上(引擎、记录、开关、改包)各 OS 相同。引擎只经 `src/collector/core/redirector.mjs` 的 `Redirector` 契约用钩子,这份契约各 OS 一样。Linux 上钩子是守护进程拉起、带 file capabilities 的能力助手(下文);macOS / Windows 上预计是 OS 托管的扩展 / 服务,引擎经本地通道接入,后设计。

## Linux 机制

**内核侧(`arch/linux/bpf/`,C + libbpf CO-RE)**

| 程序 | 挂点 | 作用 |
|---|---|---|
| `connect4` / `connect6` | 根 cgroup `cgroup/connect4|6` | 当前 tgid 在 `watch` 表且判定为「解密」、不是守护进程自己的 tgid、当前 uid(`bpf_get_current_uid_gid()`)等于本实例的 uid(存在配置 map 里)、是 TCP、和引擎同一 netns、引擎在听、监听 socket 属本实例(内核核对它的属主 uid `sk_uid` 等于本实例 uid,具体读法实验室确认)且心跳新鲜 → 把目的地改写到引擎端口,原目的地连同当前 pid、uid 按 socket cookie 存进 `orig_dst`。在 `watch` 表但判定为「不解密」→ 不改写,只经 ringbuf 报 `{pid, 目的地}`,写进 `flows/`(D31「其余照常放行、只记元数据」)。uid 不符的一律不改写、不上报;监听 socket 不属本实例(别的用户抢绑了引擎端口)时也不改写,agent 直连 |
| `sockops` | 根 cgroup | 连接建立时把 `orig_dst[cookie]` 搬到按 (客户端源地址, 源端口) 索引的 `by_port`,供引擎 accept 后查。uid 只在 `connect4/6` 的进程上下文里取,随 `orig_dst` 带过来,只作记账。`by_port` 条目只用一次:引擎查到即删,客户端 socket 关闭时(`BPF_SOCK_OPS_STATE_CB`)也删;不删的话,别的用户复用同一源端口连引擎会撞上残留条目,被当成本实例的 agent |
| `exec` / `exit` | `tp_btf/sched_process_exec|exit` | 只处理本实例 uid 的进程,别的用户的事件在内核里丢掉。exec:先在内核里删掉该 tgid 的旧判定,再把 `{pid, filename}` 经 ringbuf 交给用户态重新判定;exit:删表项 |

exec / exit 用 `tp_btf`,不用经典 tracepoint:经典 tracepoint 要读 tracefs,得额外的 `cap_dac_read_search`,不在助手的三项能力里;`tp_btf` 不需要(实验室探测确认)。

**用户态(`arch/linux/redirector/`,C · 能力助手)**:由守护进程以子进程拉起。文件属 `root:root`、0755,只带 `cap_bpf,cap_net_admin,cap_perfmon+ep`,不设组、不 setuid;调用者 uid 就是助手自己的真实 uid(file capabilities 不改 uid)。内核在 exec 带 file capabilities 的程序时会清掉此前设好的 parent-death 信号(prctl(2)),守护进程在 fork 后替它设的不算数,所以助手启动后第一件事是自己调 `prctl(PR_SET_PDEATHSIG)`,再比对 `getppid()` 与 argv 传来的守护进程 pid,不符就退出;控制通道 EOF 是第二个退出条件。它持有全部 bpf_link,**不 pin**:进程一退,内核自动摘钩,agent 新连接直连(fail-open 的第一层)。它只做三件事:装卸程序、改表、按请求查表;不碰任何连接字节。它只装自己内嵌的 BPF 对象,MUST NOT 接受调用者给的 BPF 对象或文件路径;MUST 只对调用者 uid 的进程生效:配置 map 里的本实例 uid 由助手取自己的 `getuid()` 填写,行协议与 argv MUST NOT 接受 uid 字段(Linux 分支现有 `config` 行里的 `engine_uid` 要去掉);内核侧逐次核对,见上表。

**为什么不用 nftables / TUN**:nftables 的 REDIRECT 规则在守护进程死后仍在,连接打到死端口 = fail-closed;mitmproxy 的 TUN 方案要用户态 TCP 栈,Node 里没有。改写 connect 目的地 + bpf_link 自动摘钩是唯一同时满足「只碰 agent 连接」和「崩了就放行」的做法。

**fail-open 两层**:redirector 死 → 内核摘钩;引擎死 → 监听 socket 消失,`connect4` 用 `bpf_sk_lookup_tcp` 发现没人在听就不改写;引擎卡住 → 引擎每 500 ms 经 `Redirector.heartbeat()` 发心跳(助手写进内核表),`connect4` 只在心跳 2 s 内新鲜时改写;心跳由引擎发,卡住的引擎才会被发现。已经由引擎终结的 TLS 连接会随引擎一起断,agent 自己重试(Claude Code 对已开始输出的流不重发);这一点如实写进 UI 与审计,不假装能避免。

## 引擎(`core/engine/`)

引擎在本实例自己的端口上同时听 `127.0.0.1` 与 `::1`(端口按实例分配,见 OPEN),两族都占住,引擎在跑时别的用户没法在另一族上抢绑;引擎不在跑时靠上表的监听属主核对。每条被引来的连接:

1. accept 后立刻按对端地址和端口向 redirector 查 `{原目的地, pid, agent}`,同时向原目的地发起 TCP 连接。查不到的连接没有原目的地可转,也不是本用户的 flow:直接关掉,不记录、不过改包规则。
2. 先到的字节决定走向:上游先说话 → 透传;客户端发 TLS ClientHello → 读 SNI / ALPN;发 `CONNECT host:port` → 走 CONNECT 隧道;发 SOCKS4 / 4a / 5 前导 → 同 CONNECT 处理(D37);发明文 HTTP 请求行 → 明文分帧。
3. **CONNECT 隧道**(agent 用 `HTTPS_PROXY` 指向 Clash 等本地代理时):把客户端的 CONNECT 原样发给原目的地(那个代理),把代理的真实回应原样转回,成功后再对隧道里的 TLS 做第 2 步判断。MUST NOT 自己合成 `200 Connection Established`。上游出口因此仍走用户自己的代理 / VPN。
   **SOCKS4 / 4a / 5(D37)**:Kimi、Hermes、Z-Code 会用。前导原样发给代理、代理的真实回应原样转回,MUST NOT 合成成功;前导里的认证字节是代理凭据,按 [4.1](4.1-capture-sources.md) 存 0600。**`https://` 代理(D37,v1 做)**:Kimi 与 Codex 的 WebSocket 拨号器会用;客户端先和代理 host 握外层 TLS。只在该代理 host 取自这个进程自己的代理配置(环境里的 `HTTPS_PROXY` / `ALL_PROXY` 或 harness 文件声明的配置项)时才终结外层 TLS(属解密策略 `auto`,与 base_url host 同类),里面的 CONNECT 照上条转发,隧道里的 TLS 再走第 2 步;其余代理 host 透传并在 `flows/` 记「未采 · https 代理」。这个标签只标在守护进程按进程交给引擎的代理表里、不满足终结条件的条目上(`own:false`);守护进程没告诉引擎的 `https://` 代理,在引擎看来就是一条普通 TLS,按普通透传只记元数据,不标它。**解密策略 `all` 例外**:操作者对某进程显式选了 `all` 时,该进程的一切 TLS 都终结,包括不在它自己代理配置里的 `https://` 代理(引擎在解开之前认不出它是代理);默认 `auto` 下仍只终结该进程自己配置的代理。引擎与代理的外层握手证书校验失败(如代理用私有 CA)时同第 5 步:重放客户端字节、透传、进负缓存,不伪装成功。Hermes 从 `ALL_PROXY` 取 socks5;dsh 拒绝 SOCKS、直连;Codex 的模型 HTTP 忽略 SOCKS。
4. **解密的条件(全部满足)**:该进程已确认信任 asight CA(见「身份与信任」)· 这条连接不在该 harness 声明的「不经信任路径」之列(同节;`all` 下也一样)· ALPN 含 `http/1.1` 或未带 ALPN · 目标 host 命中解密策略 · 不在负缓存里。否则透传,只记元数据。
5. 解密时先和上游完成 TLS(SNI 与客户端一致,ALPN 定为 `http/1.1`,按系统根证书校验),再用按 SNI 现签的叶证和客户端握手。**上游证书校验失败**(如中转站或代理用私有 CA):引擎丢掉自己与上游的这次握手,MUST NOT 在这条未经校验的连接上写任何客户端字节,直接销毁它;再向原目的地另开一条 TCP 连接,把已缓冲的客户端字节(ClientHello)原样重放过去,之后两边透传。引擎为了分清证书失败与网络失败,可以让握手做完再查校验结果,这不等于关掉校验。客户端自己校验上游的真实证书,asight 不伪装任何东西(D31 fail-open);`flows/` 记 `not_captured:'upstream-cert'`,该 (pid, host) 进负缓存。**隧道里**(CONNECT / SOCKS / `https://` 代理之后):只关掉这一条客户端连接,同样记 `upstream-cert`、该 (pid, host) 进负缓存,客户端重试的连接直接透传。MUST NOT 重发客户端的代理前导:前导里有 `Proxy-Authorization` 或 SOCKS 用户名密码,重发等于 asight 没有操作者意图、自己拿 agent 的代理凭据发请求(违不变式 1 / D30)。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 1 条),W12 落地后加测。另一种做法见 OPEN。网络失败(连不上、超时、上游中途断开)仍关掉客户端连接,不替上游伪装成功。客户端拒绝叶证 → 计入负缓存。**拒绝的判据(D37 更正)**:见到 ClientHello、客户端没发任何应用数据、随后关闭或 RST,不论有无 alert、不论 client Finished 是否到达——Node 不发 alert:TLS 1.3 下引擎只看到 ECONNRESET,TLS 1.2 下握手完成后客户端零数据关闭;只认 `unknown_ca` / `bad_certificate` alert 对 Node / Bun 永远不触发。
**负缓存**(关闭原 OPEN「负缓存的键与阈值」):键 `(pid, host)`。同一 (pid, host) 连续 2 次判为拒绝才写入(中间一次解密成功就重新计数;被放弃的 Happy Eyeballs 并行连接没有 ClientHello,不计);上游证书校验失败一次就写入。命中负缓存的连接,引擎照常接下、原样透传,只在 `flows/` 记元数据。MUST NOT 为此通知 redirector,也不停止内核对该进程的改写:内核只能按进程停、分不了 host,停了会连该进程已信任的别的 host 一起丢采。**生存期**:条目只在内存里,不设 TTL;进程退出时,守护进程让引擎清掉该 pid 的条目和未满阈值的计数(`engine.forgetPid(pid)`),pid 被复用时不继承;引擎重启后全部清空。`status` 列出当前条目。所以 `upstream-cert` 写入的条目在该进程余下的生命里一直透传,上游之后换好证书也不重试,重启该 agent 才重试。已知局限,如实写明:CC 沙箱代理替工具中转的 socket 也来自 claude 的 pid,工具连某个 host 被拒两次,claude 自己到该 host 的连接也不再解密;OpenCode 的 `ws` 路径没被 resolver 认出时,引擎解密它、客户端拒绝叶证,被拒的 ws 请求断掉,连续 2 次后 (pid, API host) 进负缓存,同 host 上 fetch 路径的采集也一起停掉。这两种情况 `status` 都 MUST 如实报「因负缓存停采」。
6. 解密后两个方向都走**被动分帧**:引擎转发的是收到的原始字节,分帧器只读一份副本来切出「一次请求 / 一次响应」。不重新序列化、不改大小写、不改 chunk 边界;`101 Switching Protocols` 之后原始字节照转,旁路副本交 `ws/` 按 §传输与帧级记录 记录(D37)。没有改包规则命中时,请求边收边转,零额外延迟。

**解密策略(进程内按 host)**:默认 `auto` = harness 声明的已知 API host ∪ harness 文件声明的读取器从该进程环境变量**和 agent 自己的配置文件**读到的 base_url / 中转 host(D37:Codex 不读 `OPENAI_BASE_URL`,看 `config.toml` 的 `openai_base_url` 与自定义 provider;OpenCode `opencode.json`;Kimi `config.toml` / `KIMI_*`;dsh `DEEPSEEK_BASE_URL` 与 `DEEPSEEK_SEARCH_BASE_URL`;Hermes `config.yaml` / `.env` 与辅助模型的 host;Z-Code 的 provider 配置;CC 的 settings `env`)∪ 该进程代理配置里的 `https://` 代理 host(见上文第 3 步)∪ 操作者手加的 host;`all` = 该进程的一切 TLS 都解密。默认不选 `all`,原因是 Claude Code / Codex 的沙箱会替工具命令中转 npm、git 流量,那些 TLS 的客户端是子进程:有的信任 asight CA,有的不信任,取决于入口和子进程自己的运行时(见 §身份与信任「信任面」);不信任的会被解密弄断。中转站 host 来自 agent 自己的配置,用户不用登记。

## 传输与帧级记录(D37)

Codex 内建 `openai` provider 默认走 `wss://…/responses`(握手是不带 ALPN 的 HTTP/1.1 Upgrade);不记帧,Codex 就是零内容。

- **转发不变**:引擎照转收到的原始字节,不重组、不改帧边界、不改扩展协商;记录只读旁路副本。
- **分帧**:两个方向都按 RFC 6455 解析;客户端帧解掩码;分片消息重组,中间夹的 ping / pong / close 照记、不并进消息。
- **permessage-deflate**:扩展参数取自上游 101 的 `Sec-WebSocket-Extensions`(不是客户端的报价);每方向从第一帧起维护一个持续的 `node:zlib` inflateRaw 流,支持 context takeover 与 `*_no_context_takeover`(零新依赖,D32③)。经引擎中转的连接从第一帧起都在引擎手里,inflate 上下文不会断(`off` 期间也维护,见下);缺了前序消息的调用标 `partial`(见下),原始帧照存。
- **信封**:一次逻辑调用一条信封,追加字段 `transport:'ws'`、`flow_id`、`ws_frames:[首帧号, 末帧号]`、`ws_ext`(101 的扩展头原文)、`ws_raw`(该调用两个方向的原始帧,能逐字重建线上字节,形状与边界见下);`req_body` = 解压后的客户端消息文本(调用的第一条客户端数据消息;没有客户端消息的调用为 `null`);`req_headers` = 升级请求的逐字头,按请求头取 session 键的分片器与 D35 封存器据此读到 Codex 的 `session-id`;`resp` = `{kind:'ws', messages:[…]}`(服务端消息序列,逐字)。不是 UTF-8 文本的消息:首条客户端消息存 `req_body:null` + `req_body_b64`(解压后的消息字节,不带 `req_content_encoding`,与 §记录 的 HTTP 压缩体区分),其余消息存 `{b64}`。
- **升级与中断**:升级本身不单独成信封;每条调用的信封都带升级请求与 101 的逐字头(`req_head_raw` / `resp_head_raw`)。升级被拒(如 `426`)是一次普通 HTTP 往返。一条调用也没有的 WebSocket 连接只在 `flows/` 留 `transport:'ws'` 与帧数、尾帧等汇总。调用在终止消息之前因连接关闭或上游中断而结束:写一条 `error:true` 信封,`resp = {status:null, kind:'error', error, partial:{kind:'ws', messages}}`,与 HTTP 中断同形([4.1](4.1-capture-sources.md) §中断也记);它的帧随这条信封,不进 `ws.tail_raw`。
- **`ws_raw` 的形状与边界(关闭原 OPEN「WebSocket 原始帧放哪」)**:放进信封,不拆成第二处。每帧一项 `{i, d, h, p?|m?}`:`i` = 连接内帧号(两个方向共用一个计数);`d` = `'c'`(客户端 → 服务端)或 `'s'`;`h` = 帧头字节的 base64(含掩码键);载荷二选一:`p` = 解掩码后载荷的 base64(控制帧、压缩帧、本信封不携带其消息的帧),`m = [k, 偏移]` = 本信封该方向第 k 条消息字节的切片(未压缩数据帧,文本不存两遍;客户端方向先数 `req_body`,再按到达顺序数 `req_extra_messages`)。存解掩码后的载荷,是因为掩码键随机,掩码后的字节压不动,也做不了 D35 的字节级增量;重建时按帧头里的掩码键再掩一遍。两者都没有 = 载荷未保留,读时 MUST 就地标「非逐字」(不变式 4)。**边界**:没有打开的调用时到达的服务端消息自成一条信封(`req_body:null`);两次调用之间的帧(ping / pong 等)随下一条信封的 `ws_raw`;连接关闭时,最后一条调用之后、不属于任何调用的帧(close 帧等)记在 `flows/` 的 `ws.tail_raw`。`off` 期间到达、不属于在记调用的帧不留(见下「开关」)。帧号连续时,把一条连接的各信封 `ws_raw` 与 `ws.tail_raw` 按帧号拼起来,即逐字重建线上字节;帧号有缺口处,是 `off` 期间没记的帧或没写成的信封,其后的调用标 `partial`(见下)。**非 LLM 路径**:按 [4.1](4.1-capture-sources.md) 非 LLM 调用的规则,客户端消息只存元数据(`{raw_chars, verbatim:false}`),其帧不留载荷,`ws_raw` 重建不了这个方向,读时 MUST 就地标「非逐字」(不变式 4)。要过 D34 的体积预算:E7 在一个 Codex WebSocket 会话上也跑。
- **逻辑调用怎么切(已定 · 2026-10-05)**:D20 与 [0.1](0.1-engineering-rules.md) §5 禁止在采集端解析 provider。做法:harness 文件以**数据**声明终止消息的字节模式(Codex:`response.completed` / `response.failed` / `response.incomplete` / `error`;`response.incomplete` 结束被打断的一轮),核心见到它就写信封、不含任何 provider 代码;一条客户端数据消息加上它之后到终止消息的全部服务端消息合成一条信封。声明了模式时,调用打开期间(尚未见终止消息)又到的客户端数据消息(如 Codex 的 `response.interrupt`)不另起调用,记在该调用信封的 `req_extra_messages` 里。没声明模式的连接退回「到下一条客户端数据消息或 close 为止」,代价是每轮最后一条回复要等用户下一条消息或连接关闭才落盘(Codex 连接可开 60 分钟)。模式只用来切信封,不用来分 session、不解释内容、不改字节,核心里没有 provider 代码,所以不算 D20 禁止的「采集端解析 provider」;harness 文件本就以数据声明进程特征与已知 host(D31②)。没选「只按下一条客户端消息切」:每轮最后一条回复要等很久才落盘,看板看不到刚结束的一轮。命名与校验仍由 Responses-WS dissector 在读时做。
- **`partial`**:信封顶层 `partial:true` + `partial_reasons`(`off-window` / `write-failed` / `decode-failed` 的子集),表示这条连接上更早的消息缺了。采集端不解析 provider,判断不了哪条调用依赖缺失的消息,所以同一连接上缺口之后的每条调用都标;能否收窄由读时 dissector 判(如不带 `previous_response_id` 的全量调用)。读取侧把信封的 `partial:true` 读成 `context_state='partial'`,收窄了才不标([3.1](3.1-adapter-contract.md))。读时才发现的缺失(少了某个文件)由 dissector 标 `context_state='partial'`,不改原始记录,信封的 `partial` 字段不变。顶层 `partial` 只说这条连接的上下文有缺口,本信封自己的字节是全的;本信封字节不全另有标注,不是一回事:响应没收完是 `error:true` + `resp.partial`,HTTP 请求体是 `req_truncated` / `req_partial`(§记录),WebSocket 调用超上限是 `ws_truncated`(下条)。
- **大小上限**:单次 WebSocket 调用累计 64 MiB(与 HTTP 体现有的上限一致);超出后的消息存 `{omitted_bytes}`,其帧不留载荷,信封标 `ws_truncated:true`,读时 MUST 就地标「已截断」(不变式 4)。
- **开关**:一次调用记不记,在它的第一帧时按当时的开关决定(与 HTTP 在请求开始时取样一致):`on` 时开始的调用即使中途 `off` 也整条记下,`off` 时开始的调用整条不记。`off` 期间,经引擎中转的 WebSocket 连接继续维护每方向的 inflate 状态(只在内存,不记录);这期间到达的帧,除属于 `on` 时开始的调用外一律不留,再 `on` 后也不随下一条信封补记;再 `on` 后,缺了 `off` 期间前序消息的调用标 `partial`(`off-window`)。
- **v1 不做**:WebSocket 上的改包([5.1](5.1-intervention.md));HTTP/2——引擎只答 `http/1.1`,七个 harness 都落在 HTTP/1.1,只给 h2 的连接透传,`flows/` 记元数据,标「未采 · h2」(显示处见 §记录);QUIC / HTTP3、AF_UNIX(`ANTHROPIC_UNIX_SOCKET`、`claude ssh`)、语音 WebRTC 到不了引擎,由进程级检测(环境里的 `BUN_FEATURE_FLAG_EXPERIMENTAL_HTTP2_CLIENT` / `…_HTTP3_CLIENT`、`BUN_OPTIONS`、`ANTHROPIC_UNIX_SOCKET`)在 agent 状态行标出;上游的 `Alt-Svc: h3` 原样转发,剥掉它属改包(D30),没有操作者意图不做;Bedrock event-stream、Vertex、Gemini 线格式没有 dissector,字节按现有 `isLlmCall` 规则照存,读时落「未识别」隔离并标注。
- **请求体压缩**:CC(被 `CLAUDE_CODE_GZIP_REQUEST_BODIES` 强制时 gzip)、Codex(ChatGPT 登录的 HTTP 路径 zstd)会压缩请求体。压缩字节逐字存(base64 + `content-encoding`,字段见 §记录);gzip 用 `node:zlib` 解。采集端从不解 zstd 请求体:只存线上字节,标「压缩请求体未解码」,不随录制它的 Node 版本变化;读取侧在自己的 Node 有 zstd 时再解(Node 20 的 `node:zlib` 没有)。响应侧不变。实验室用 API key,碰不到 zstd,不挡 R2。

## 身份与信任

- **识别进程**:`harness/*.mjs` 给出特征(Linux:`/proc/<pid>/exe` 的路径模式、`argv` 模式;macOS 预留:Team ID + 签名标识)。只认真正发 API 请求的进程,不认 npm 包装层(Codex、OpenCode 的 node 启动器不发请求)。exec 事件到达后通常在毫秒内完成判定(实验室给出实测值);启动时和每次开启时扫一遍 `/proc` 里本实例 uid 的进程(别的用户的 exe / environ 本来也读不到)。exec 后立刻连网、快过判定的进程会漏掉首条连接——漏的是采集,不是 agent 的连接(它照常直连);实验室测量漏采率。
- **子进程与嵌套 agent**:判据是**进程自己**,不看它的父进程是谁。子进程只要自己匹配 harness 特征表,就是一个独立的 agent,单独采集——一个 agent 启动另一个 agent(如 claude 拉起 codex,或任意 harness 互相调用)天然覆盖。同一进程内的 subagent(如 Claude Code 的 subagent,与主 agent 同进程、靠请求头区分)本来就在该进程的流量里。不匹配特征表的子进程(MCP server、shell 工具、沙箱进程)只记元数据;harness 文件可以显式声明某个子进程也算(如 Gemini CLI 的 relaunch 子进程)。嵌套关系(谁启动了谁)记在 `flows/` 的 `parent_pid` / `parent_agent` 里,供看板标注。

- **替换语义的设置**(`SSL_CERT_FILE`、`HERMES_CA_BUNDLE`、`REQUESTS_CA_BUNDLE`、`CURL_CA_BUNDLE`、`ZCODE_AGENT_CA_CERT`、Z-Code 的 `network.caCertFile` 与桌面 `httpProxyCaCertPath`、Hermes `config.yaml` 的 `ssl_ca_cert`)MUST NOT 指向只含 asight CA 的文件,也 MUST NOT 指向别的 harness 的合并包;MUST NOT 设全局 `SSL_CERT_FILE`(会改变本用户所有 OpenSSL、Python、Bun 进程的信任)。守卫:审查([0.1](0.1-engineering-rules.md) §5 · §6 第 4 条),T10 落地后加测。用户在同一入口已有值时,把它合并进该 harness 的文件,原值记进安装清单的 `prior_value`,卸载时还原。CC 的 `extra-cc.pem` 是追加语义,不含根证书,不是合并包,不受本条约束。
- **同名键**:dotenv 入口里安装时已有同名键(如 Codex `.env` 里靠后的 `SSL_CERT_FILE=`)时,asight 照样把块写在最上面,再把用户那一行注释掉(行首加哨兵前缀),两处改动都记进日志;那行的值记进 `prior_value` 并并进合并包。不注释掉的话,后读到的同名行可能盖过 asight 的块。Hermes 同样处理。dotenvy、python-dotenv 对同名键与坏行的实际行为由实验室 ①、③ 核对。
- **进程内插件:有界例外(D37④)**:dsh 与 OpenCode 没有只对自己生效的数据入口,用插件。这与 [1.1](1.1-product-definition.md):11「不改被测程序」冲突,是有意接受的例外;边界如下,每条都是 MUST:
  1. 插件只把 asight CA **追加**进本进程的信任,不替换、不删减已有的根。OpenCode 的包装保留调用方已有的 `tls` 字段和 `ca`,只在后面追加 asight CA。
  2. MUST NOT 读、改或发送任何请求 / 响应字节。OpenCode 的 fetch 包装只在 `tls.ca` 里追加 asight CA,请求与响应原样传递。
  3. 自己不发任何网络请求。
  4. 不写 agent 的配置。
  5. 唯一的写:一个按 pid 的「信任已生效」标记,供引擎确认信任(插件的效果在 environ 里看不到)。只在 CA 真的加上了时写;没加上就不写,也不另外输出(「不另外输出」见 OPEN)。
  6. 读不到 `asight-ca.pem`(缺失、不可读、不是 PEM)时什么都不做:不抛错、不加 CA、不写标记。卸载第 3 步删掉它之后、第 4 步删插件之前,或卸载中途崩溃后,插件仍可能被加载,不能因此让 agent 起不来。

  **标记**:文件 `~/.asight/collector/run/trust/<pid>`,内容是该进程的启动时间(Linux:`/proc/self/stat` 第 22 字段)。引擎 MUST 核对 `/proc/<pid>/stat` 里的启动时间,不符就当没有:pid 被复用后,旧标记会让引擎解密一个不信任 asight CA 的进程(违 T7)。pid 退出后标记作废,引擎可以删;卸载时随运行时目录删掉。

  dsh:先检测有没有 `tls.setDefaultCACertificates`(Node ≥ 22.19;dsh 在 22.18 上也能起),没有就什么都不做;`--use-openssl-ca` 下也不加(那时这个调用会替换默认根)。这两种情况都不写标记,插件自己也不输出;原因由 resolver 从该进程的 Node 版本和 argv / `NODE_OPTIONS` 里的 `--use-openssl-ca` 推出,报在 `status` 里(Node 版本怎么取由实验室 ⑤ 定)。「插件什么都不输出、原因由 resolver 推出」= 「什么都不做并报告」的落地读法(见 OPEN)。OpenCode:`--pure` 跳过插件,该进程即「未信任」;安装时 MUST 告知,只要有任何插件,OpenCode 首次运行会 npm install `@opencode-ai/plugin`,多一次 registry 拉取。这次 install 可能还在 OpenCode 的配置目录写文件(`package.json`、锁文件、`node_modules` 等,具体由实验室 ⑥ 定):这些文件是 OpenCode 写的,安装时一并告知,安装清单记下这些路径装之前在不在;卸载不删它们(它们也可能服务用户自己的插件),把装之前不在的报成「asight 的插件引起的残留,未删」;S10 / T11 的「撤净」不含它们。这两个 harness 的观测者效应标签写「asight 代码运行在该 agent 进程内」。守卫:审查([0.1](0.1-engineering-rules.md) §5 · §6 第 4 条),T13 落地后加测。
- **信任面(D37④)**:信任 asight CA 的只有被注入的 agent 进程及其子进程,不含本用户的其他程序。经环境生效的入口(CC、Codex、Hermes、Kimi shim;Z-Code 自己把合并包写进子进程的环境),子进程都继承这个变量:Bash 工具、hooks、MCP stdio server、LSP、git / curl。子进程信不信任 asight CA 取决于它自己的运行时:`NODE_EXTRA_CA_CERTS`(CC、Kimi)只有 Node 子进程认,git / curl 不认;`SSL_CERT_FILE` 指向的合并包(Codex、Hermes),基于 OpenSSL 的客户端(多数 Python、git、curl)都认;Z-Code 把子进程的 `NODE_EXTRA_CA_CERTS`、`SSL_CERT_FILE`、`REQUESTS_CA_BUNDLE`、`CURL_CA_BUNDLE`、`GIT_SSL_CAINFO` 都写成合并包。上界就是「被注入的 agent 及其全部子进程」,这是已接受的代价;asight 不为把子进程剥掉而再改 agent 的其他配置。插件入口(dsh、OpenCode)不进环境,子进程不继承。CA 不轮换、无名称约束,私钥在同 uid 可读的路径上:任何同 uid 的代码都偷得走,包括被注入的 agent 自己(如被提示注入后);偷走后,网络路径上的攻击者(中转站、不可信的网络)在 CA 有效期内(当前实现 `src/collector/core/tls/ca.mjs` 默认 10 年)能对这些进程冒充任意 host,包括子进程的包管理与 git 拉取。没有轮换,唯一的恢复是卸载再重装(换一张 CA)、这些进程各重启一次;要不要恢复 `asight ca rotate` 见 OPEN。D36 的前提「只有被注入的 agent 进程信任它」由此成立(含其子进程)。
- **标记与安装**(D37④):安装 MUST 先列出要改的每个文件,再动手。按格式做最小插入、不重排:能写注释的格式(dotenv、YAML、shell rc、shim、插件文件)用醒目的哨兵注释块(D28 式),一眼认得出、好卸。CC 的 `settings.json` 与 Z-Code 的 `config.json` 是纯 JSON,写不了注释,加标记键又可能被 schema 拒,所以 asight 的键只靠值(`~/.asight/` 下的绝对路径)加安装清单认出。这是局限,如实写明:用户打开这两个 JSON,看不出哪个键是 asight 加的。JSON 按文本插入键,rename 前先解析校验,原子替换。每个入口记进安装清单,卸载逐项撤销(§安装清单与卸载,S10、T11)。
- **观测者效应(D37⑤)**:注入本身会改变部分客户端行为,开关关着也一样:CC 见到 `NODE_EXTRA_CA_CERTS` 就不再按 flag gzip 请求体;Codex 设了 `SSL_CERT_FILE` 后模型 HTTP 从 native-tls 换成 rustls、ALPN 报 `[h2,http/1.1]`;Z-Code 设了 `caCertFile` 后从 undici 换成 `node:https`,每次请求一个新 Agent、不带 ALPN(推断,见 OPEN);OpenCode 有了插件,首次运行多一次 npm 拉取;dsh、OpenCode 的插件让 asight 代码运行在 agent 进程内。这些以数据列在读取侧的 harness 表([3.1](3.1-adapter-contract.md)),ETL 对经注入信任采到的调用写 `calls.observer_effect`([3.2](3.2-normalized-model.md)),显示处 MUST 标注(R5)。
- **确认信任**:引擎只在确认该进程信任 asight CA 时解密。文件入口与插件入口都不出现在 agent 进程的 `/proc/<pid>/environ` 里(CC、Codex、Hermes 启动后才 putenv;Z-Code、dsh、OpenCode 根本不进环境);那里只看得到 shim 设的值,和用户自己在 shell 里 export 的值。所以每个 harness 有一个 resolver,以操作者身份运行(D36 起这些文件直接可读),按该 harness 的优先级链算出实际生效的值,再读那个文件:文件可读、其中的证书含 asight CA 的指纹,才算信任(合并包不是 CA 的路径,MUST NOT 只比路径)。插件入口看按 pid 的「信任已生效」标记,并核对启动时间(见上)。matcher MUST 排除 dsh 的 subprocess runner 与 PTC 子进程(见上表)。注入之前就在跑的 agent 一直透传,直到它重启;`status` / `doctor` MUST 逐个报「运行中但未信任」及原因:入口缺失或被改走;进程早于注入(Codex app-server 守护进程在 `.env` 块写入之前就已启动;OpenCode serve、multiplex 模式的 Hermes gateway 同理);被遮住(CC:仓库层、managed 层、Desktop 启动环境;Z-Code:`ZCODE_AGENT_CA_CERT`(空值也算)、桌面设置 `httpProxyCaCertPath`、项目文件;Hermes:managed 层 `/etc/hermes/.env`(或 `$HERMES_MANAGED_DIR/.env`)里的 `SSL_CERT_FILE`、release 构建上的 `HERMES_CA_BUNDLE`;Codex:shell 里的 `CODEX_CA_CERTIFICATE`;Codex、Hermes:安装后用户在同一 `.env` 里又加、且按该解析器的规则后读生效的同名键);OpenCode 带 `--pure`;dsh 的 Node 低于 22.19 或在 `--use-openssl-ca` 下;Kimi 没经 shim 启动,或是 npm 装的(不装 shim),或装 shim 的前提不满足(没有 `~/.kimi-code/bin/kimi` 或安装器那行 PATH)。只有部分连接透传的也报:OpenCode 开着 `ws` 路径时,它的 API host 透传(见下)。
- **不经信任路径**(D37④):同一个已信任的进程里,有的连接不走被注入的那条路,仍用默认根:Z-Code 策略 fetch 以外的 `globalThis.fetch`(如下载 provider release);OpenCode 插件加载之前的请求(如 models.dev)与 `ws` 路径。这些连接 MUST 透传、不解密,解密策略是 `all` 时也一样;否则客户端拒绝叶证,agent 的请求断掉。harness 文件以数据声明这些 host,具体有哪些由实验室 ②、⑥ 定。和信任路径共用 host 的(OpenCode 的 `ws` 路径与 fetch 去同一个 API host,按 host 分不开):resolver 认出该进程开着 `ws` 路径时,这些 API host 对它一律透传,`status` 报「未采 · ws 路径不经插件」;怎么从进程外认出由实验室 ⑥ 定,没认出时的后果见 §引擎 第 5 步「负缓存」。
- **CA**:v3 根证书(BasicConstraints CA:TRUE、KeyUsage keyCertSign、SKI),私钥 `~/.asight/collector/ca/ca.key`,属该用户、0600,无名称约束。CN 与旧 MITM 的 `atrace local MITM CA` 不同,MUST NOT 复用或覆盖旧的 `~/.asight/ca`(两张同 CN 的 CA 曾让 Desktop 断网)。叶证 P-256、有效期 199 天、回溯 2 天、带 AKI,每次守护进程启动生成一个内存中的叶证密钥,按 SNI 缓存。CA 装好后永不轮换(agent 只在启动时读一次;有效期与私钥被偷的后果见上「信任面」,要不要轮换见 OPEN)。MUST NOT 装进任何系统级或用户级信任库。

## 特权助手与按用户运行(D36)

- **按用户运行**:守护进程以安装它的用户身份运行,不是 root,也不换账号(D32⑦ 的专用账号 `asight-engine` 已被 D36 撤回)。CA、期望态、采集、安装清单都在该用户的 `~/.asight/` 下。同一台机器上每个系统用户各装一套,各自只认自己 uid 的 agent 进程。
- **特权只在助手**:能力助手(上文的 redirector)是唯一带特权的部分。每台机器一次 `sudo` 安装,助手升级后再一次;日常开关和采集不要密码。本机所有用户都能执行它,但它只对调用者自己 uid 的进程生效,与 [5.1](5.1-intervention.md) §安全边界「自己机器上、自己账号下」一致。
- **守护进程不绕回自己**:它与 agent 同 uid,`connect4/6` 改按 tgid 排除它自己的连接(验收 S11)。
- **代价(如实写明)**:被测 agent 与守护进程同 uid,所以 agent 读得到 CA 私钥、能 ptrace 守护进程、能改或删采集文件。D31 原先用「私钥只有 root 可读」弥补「CA 不加名称约束」,这条不再成立。现在接受它的理由:这张 CA 不在任何信任库里,只有本用户被注入的 agent 进程及其子进程信任它(D37④ 只经按 harness 的入口注入、不写登录环境,这一前提成立,见 §身份与信任「信任面」);私钥被偷的后果,如实写明(更正 D36 原先的「私钥被偷只帮得上同 uid 的代码」):任何同 uid 的代码都偷得走,包括被注入的 agent 自己;偷走后,网络路径上的攻击者(中转站、不可信的网络)在 CA 有效期内(当前实现默认 10 年)能对被注入的 agent 及其子进程冒充任意 host,受益的不止同 uid 的代码。没有轮换,唯一的恢复是卸载再重装、这些进程各重启一次;要不要恢复轮换、缩短有效期未定(OPEN)。助手是带 file capabilities 的 exec,内核把它标成不可 dump,agent 不能 ptrace 助手。
- **残余风险**:助手对本机所有用户可达,别的用户可以占满根 cgroup 上每个挂点的程序名额(内核上限 64 个),让其他用户的采集挂不上钩(fail-open:agent 照常直连,只是没采到;状态按内核实际态如实报告)。共用 `127.0.0.1` 的看板 / API 与 D26 控制端点不隔离用户:别的用户读得到采集,开了 `--control` 时还能改开关;所以 [4.4](4.4-server.md) 转接本守护进程控制面的入口在按用户隔离落地前 MUST NOT 上线(见 §控制面、[4.4](4.4-server.md) OPEN)。

## 安装清单与卸载(必须干净 · 见验收 S10)

安装分两级,卸载只按安装清单删,不按猜测删:

- **按用户**(不要 sudo):清单 `~/.asight/collector/install-manifest.json`,如实列出 asight 为该用户创建了什么:目录、文件、改过的每个信任入口文件(见下面的「信任入口的日志与撤销」)、asight 自己建的信任入口文件(dsh 的插件目录 `~/.asight/collector/plugins/dsh/`、OpenCode 的插件文件 `~/.config/opencode/plugins/asight-ca.js`、Kimi 的 shim `~/.asight/collector/bin/kimi`)、用户级自启单元。`asight uninstall` 只撤这一级。
- **整机**(sudo,一台机器一次):只有能力助手,装在 root 所有、各用户可执行的固定路径(路径见 OPEN)。整机清单就是这张固定路径表,另一步 sudo 移除只删表里的路径;移除前报告本机还有哪些用户的实例在用它。

1. 按用户卸载的顺序:停守护进程(助手随之退出)→ 确认本实例的 bpf link 已消失 → 按下面「信任入口的日志与撤销」的五步撤信任 → 停用并删除用户级自启单元 → 删 CA 私钥与运行时目录(含信任标记目录);CA 目录等保留下来的合并包都删掉之后才删。
2. 一个用户卸载,不影响同机其他用户的实例。
3. **采集数据属于用户**:卸载默认保留,只有显式的 `--purge-data` 才删(v0 的 `atrace-uninstall` 曾连采集一起 `rm -rf`,不再重演)。
4. 幂等,且对安装到一半的状态安全:连跑两次、或安装中途崩溃后再卸载,都成功且不留残余(保留下来等进程退出的合并包、OpenCode 的 npm install 残留除外,见下)。安装清单先写后改(见下「日志」);它记的每一项(包括保留下来的合并包)都撤净之后,才删清单本身,所以第二次卸载仍找得到第一次留下的东西。

**信任入口的日志与撤销(D37④ · 标记好认好卸、安装先列文件,不整文件回滚沿用 D28;下面的日志字段、撤一个文件的规则、五步顺序、判活与先写后改按调研定)**

- **日志**:安装清单里,每个改过的文件一条 `{path, existed_before, mode, pre_sha256, post_sha256, ops, prior_value, installed_at}`。`ops` 是一串 splice `{offset, removed, inserted}`:最上面的块是一个;注释掉用户的同名键行(见 §身份与信任「同名键」)或替换 JSON 里用户原有的值是另一个,它的 `removed` 只会是 asight 管的那个键的行或值,是路径,不是密钥。`prior_value` 只在 asight 换掉了用户原值时有,它是一个路径,从不是密钥。**MUST NOT 复制用户文件**:Codex 与 Hermes 的 `.env` 里有 API key。合并包与 `extra-cc.pem` 只取用户 CA 文件里的证书块,不算复制(见 §身份与信任「合并包」)。**先写日志再改文件**:每改一个文件之前,先把意图(`path`、`existed_before`、`pre_sha256`、要做的 `ops`)写进清单并 fsync,改完再补 `post_sha256`;安装中途崩溃留下的「只有意图」的条目,卸载照样找得到。清单另记 OpenCode 那次 npm install 可能写的路径装之前在不在(见 §身份与信任)。
- **撤一个文件的规则**(第 1 步与第 4 步的每个文件都按它,包括 dsh 的 patch 文件和 shell rc):
  - sha 等于 `pre_sha256`(`existed_before` 为假时:文件不在):已经是安装前的样子,跳过,报「早已还原」;第二次卸载走到这里,MUST NOT 误报「不逐字节相同」。
  - sha 等于 `post_sha256`:反向做 `ops`(`existed_before` 为假就删掉该文件和 asight 建的目录),再断言 sha 等于 `pre_sha256`,这是逐字节还原。
  - 只有意图、没有 `post_sha256`(安装中途崩溃):sha 等于按 `ops` 算出的结果,就同上反向做;否则走下一条。
  - 其余(用户在安装后改过它,如 `hermes config set`、Z-Code 的设置同步、CC 自己重写 settings、用户在 rc 或 patch 文件里加了行):只去掉 asight 的块、行,或仍是 asight 值的那个键,把注释掉的用户同名行恢复原样,还原 `prior_value`,报「已撤销,但不逐字节相同」;asight 以外的内容逐字节不变。asight 建的文件里只剩 asight 的骨架(空文件、空的 insert 列表)时删掉整个文件(dsh 遇到空 patch 文件起不来);还有用户的内容就留着。
  - MUST NOT 用整文件快照回滚(D28)。
- **撤销顺序**:
  1. 按上面的规则撤 CC、Codex、Z-Code、Hermes 的配置入口。
  2. 把每个替换语义的合并包改写成「去掉 asight CA 的同一份」:Node 根、OS 根、并进去的用户 CA 都留着,在跑的进程下次重读时照样连得上用户自己的代理或中转站。还有加载过它的进程活着,就保留并报告这些 pid,再跑一次卸载时按同一判据重判,没有了才删。**判活不靠守护进程,也不靠入口文件**(此时守护进程已停、入口已撤,都不再指向合并包),只看安装清单与 `/proc`:本 uid 有一个活着的进程满足任一条就算——(a) 匹配 harness `<h>` 的特征表,且启动时间晚于该入口的 `installed_at`;运行中会重读入口的(Z-Code 每个新 session、Hermes 非 multiplex 的 gateway 每轮、CLI 的 `/reload`)不看启动时间,活着就算;(b) `/proc/<pid>/environ` 里有该合并包的路径(从 agent 继承了它的子进程)。提前删的后果:Z-Code 每次调用都抛错,Hermes 的 Anthropic 客户端构造时抛错,Codex 的 WebSocket 卡住、之后回落 HTTP。用户自己把别的设置(如 Z-Code 桌面的 `httpProxyCaCertPath`)指向了 asight 的文件时,同样保留并报告,asight 不改那个设置。
  3. 删追加语义用的 `asight-ca.pem`,以及第 1 步撤掉 CC 入口之后的 `extra-cc.pem`(Node、Bun、CC 遇到缺文件只告警;插件按 §身份与信任 插件第 6 条什么都不做)。
  4. 删 Kimi 的 shim 与 shim 目录,按上面的规则撤 rc 里的 PATH 行;按上面的规则撤 dsh 的 patch 行,删插件目录 `~/.asight/collector/plugins/dsh/`;删 OpenCode 的插件文件 `~/.config/opencode/plugins/asight-ca.js`。OpenCode 那次 npm install 写的文件只报不删(见 §身份与信任)。
  5. 报告在跑的进程,MUST NOT 重启任何进程:追加语义的入口(CC、Kimi shim、dsh / OpenCode 插件)只在启动时读,报「重启前仍信任」;Codex 下次建 HTTP 客户端或 WebSocket 连接、Linux 上 main 构建的 Hermes 下次握手时重读合并包,第 2 步之后从那一次起不再信任 asight,照此报告;Z-Code 新建或恢复的 session 起不再信任,进行中的 session 用的是缓存的 PEM,结束前仍信任;没证实会重读的(Hermes 的 release 构建、macOS)按「重启前仍信任」报。

原 OPEN「采集文件归属」由 D36 解决:守护进程以用户身份写 0600 文件,满足 [4.1](4.1-capture-sources.md) 的「除属主外无人可读」。

## 开关语义(必须精确,见验收 S 组)

| | 开(`on`) | 关(`off`) |
|---|---|---|
| 内核 | 本实例的 `connect4/6`、`sockops` 三个 link 已挂,返回前确认 | 本实例的三个 link 已摘,返回前确认;`exec/exit` 跟踪不摘(只维护进程表,不碰流量) |
| 新连接 | 被判定解密的 agent 进程的新连接全部经过引擎 | 一律直连,agent 看到的是上游真实证书 |
| 已有连接 | 开之前建立的直连不受影响,也不采集 | 开期间建立的连接继续由引擎原样中转直到关闭(TCP 连接无法中途改道),但 `off` 返回之后才开始的请求不再记录 |
| 记录 | 每次请求 / 响应一条信封 | `off` 返回之后才开始的请求与 WebSocket 调用零记录;之前开始的照常记完(见上行与 §传输与帧级记录「开关」) |

- 状态 MUST 来自内核实际态(redirector 按本实例自己的 link id 读 link 信息,同机其他用户的 link 不算),不来自自己记的标志;期望态与实际态不一致时如实报告。
- 幂等:重复 `on` / `off` 无副作用。期望态写进操作者目录,守护进程重启后按它恢复。
- 状态里给出每个 agent 进程「仍在直连、因此没被采集」的连接数(从 `/proc/<pid>/fd` 对 `/proc/net/tcp*`),让「为什么开了还没采到」可见。

## 记录(D10 信封 · 只追加字段)

一次请求 / 响应一条信封,写到 `~/.asight/collector/capture-<日期>.ndjson`(0600,属操作者)。新字段全部追加在 `req_body` 之后(分片器从首个 `"req_headers":{` 扫到 `"req_body"` 取 session id):

- `capture:'transparent'` · `host` · `scheme` · `dst`(原目的地 ip:port)· `proc:{pid, exe, agent}` · `flow_id` · `seq`(连接内第几次请求)
- `req_head_raw` / `resp_head_raw`:请求行 / 状态行加头部的原始字节(latin1),重发据此逐字重建;`resp.headers`
- 响应体逐字:解压后的原文(SSE 原始帧不再丢 `event:` / `id:` / 注释),跨 chunk 的多字节 UTF-8 用 StringDecoder 拼接
- 改包相关:只在发生干预时多一个 `intervention` 字段(含 `origin`、字节补丁 `edits`、`base_sha256` / `result_sha256`),没有干预的信封不带它;形状见 [5.1](5.1-intervention.md) §记录与标注
- `transport`:只有 WebSocket 信封带(`'ws'`)。不带 `transport` 的信封就是 HTTP,HTTP 信封不加这个字段;ETL 把缺省读成 `calls.transport='http'`([3.2](3.2-normalized-model.md))
- 压缩的请求体(只对 LLM 端点,非 LLM 仍只存 `{raw_chars}`):`req_body_b64` = 线上压缩字节,`req_content_encoding` = `content-encoding` 头原文;解出来时 `req_body` = 解压后的文本;解不出时(zstd 一律如此,见 §传输与帧级记录)`req_body:null` + `req_encoding_error`,读取侧按 `req_content_encoding` 自己解 `req_body_b64`,解不出才标。WebSocket 信封也用 `req_body_b64`,装的是不是 UTF-8 文本的首条客户端消息(解压后的消息字节),不带 `req_content_encoding`(见 §传输与帧级记录)
- 不完整的标注,各说一件事:顶层 `partial` / `partial_reasons` = 这条连接更早的消息缺了,缺的是上下文,本信封的字节是全的;`ws_truncated` 与 `ws_raw` 里没留载荷的帧 = 本信封的字节不全;`req_encoding_error` = 字节是全的(在 `req_body_b64`),只是采集端没解码。HTTP 上本信封字节不全另用 `resp.partial`(响应没收完)与 `req_truncated` / `req_partial`(请求体),和顶层 `partial` 不是一回事。读取侧与看板 MUST 就地标「不完整」「已截断」「压缩请求体未解码」「非逐字」(不变式 4)

透传连接、解密失败、心跳与开关事件写 `flows/`,审计写 `audit/`,重发写 `replays/`,都放子目录,现有看板只读顶层 `*.ndjson`,不会把它们当信封。`flows/` 里的「未采」(只给 h2、`https://` 代理未终结、上游证书校验失败 `not_captured:'upstream-cert'`、命中负缓存、QUIC、AF_UNIX)与「运行中但未信任」由 D31⑧ 的设置面板(agent 列表,UI 单元待写)读出、就地显示,在那之前由 `asight collector status` 报出(不变式 4)。`isLlmCall` 改为按路径后缀判定(querystring 不参与,如 Kimi 的 `/coding/v1/messages?beta=true`),`/anthropic/v1/messages` 这类中转站前缀也算推理请求。WebSocket 信封见 §传输与帧级记录;承载对话的旁路调用请求体逐字、标 `body_retention:'verbatim'`(D37,[4.1](4.1-capture-sources.md))。**接线**:采集器目录 `~/.asight/collector/` 顶层的 `*.ndjson` 也 MUST 是看板源;[4.4](4.4-server.md):129 现在只非递归读一个目录,随实现改,不改则 R2 过不了。

## 日志体积预算(D34 · 硬目标;格式 = D35)

asight 存在盘上的采集日志,体量 MUST 和被测 harness 自己留的会话日志在同一量级,不能大出一个数量级。实测动因(2026-10-05,作者机器):Claude Code 自己的 `~/.claude/projects` 约 1.5 GB,而 asight 的 `~/.asight` 约 70 GB——其中采集流 39.6 GB,另约 32 GB 是 `src/etl/shard.mjs` 拷出的按 session 副本(`~/.asight/sessions/*/calls.ndjson`)。大了约 45 倍,其中一份是重复副本。D35 的目标是每条记录只留一份长期副本,要等按 session 的布局定下才成立(见 [4.2](4.2-storage-etl.md) OPEN)。

**根因**:对话是追加式的,每次调用把越来越长的 `messages[]`+`tools` 整个再写一遍,一个 n 次调用的会话原始体积约 Σ 正比于 n²。DuckDB 侧早已按 `content_hash` 去重(见 [3.2](3.2-normalized-model.md):18),涨的纯粹是原始 NDJSON。

**手段 = D35 封存格式**(格式与封存器规则见 [4.2](4.2-storage-etl.md) §原始层封存):
- 活跃分片保持未压缩 `.ndjson` 追加写(`createEnvelopeWriter` 的 0600 + 每条 fsync 可见的崩溃安全不动),写的过程中 MUST NOT 被封存。
- **「已关闭」的判据**:写者已写出显式的关闭标记、fsync 并释放了 fd。MUST NOT 凭文件名里的日期或 mtime 推断——跨午夜的 SSE 响应可能还在写。D35 之前写的文件没有关闭标记,走 [4.2](4.2-storage-etl.md) OPEN 里操作者显式触发的旧文件入口。
- 封存器属原始层(`src/raw/`),不在 `src/etl/`。MUST NOT 把记录字节搬出原始层放进外部 chunk store(源真相会变成两份、丢一份就全毁,违 [4.2](4.2-storage-etl.md):8/53);封存文件本身是 NDJSON 行字节的无损容器,不算搬出。
- 三个读者 MUST 能读封存文件:`src/query/source.mjs`(现在把压缩文件当 `compressed` 静默跳过,`source.mjs`:139/153)、看板装载、ETL 读入。看板 loader 把整个 session JSON.parse 进内存的上限(877 MB 可开、2.4 GB OOM)是另一个已知缺口,封存解决不了;下面 E3 的随机读只覆盖 resolver。loader 读封存文件时 MUST NOT 把整个文件缓冲进内存。
- **选型已定(D35)**:brotli q9、lgwin 24、约 4 MiB 独立帧;不用外部 `zstd` 可执行。zstd(level 3、窗口 ≥ 2^22)是 Extension:不再支持 Node 20 后换用(实测更小也更快)。

**实测(2026-10-05,三个真实 Claude Code 会话分片 2.58 GB / 1.14 GB / 0.59 GB,共 15,185 条记录)**:
- 请求体占原始字节的 97.8–98.8%,响应 1.0–1.6%。
- 只压帧不够,帧要小到内存可控就压不下去:brotli q9 + 16 MB 帧 = 原始的 3.86 / 4.28 / 23.9%,但热读让 RSS 涨 286–374 MB;4 MB 帧单压只到 10–12%,在有 12.5 MB 单条记录的那个会话上是 24–38%。早先的 2.7% 是整个文件一个窗口,换成可随机读的帧后不成立。
- 单段拼接的增量不够(未压缩仍占原始的 37–50%):Claude Code 每轮挪动 `cache_control` 标记(扩展型记录里,字节公共前缀止于 `cache_control` 标记的有 7,033/7,154、1,358/1,426、543/547 条);相邻两条请求有 93–99.5% 改了 system 第 0 块(约 170 字节里改 47–68 字节),52–97% 改了顶层 `diagnostics` 字段;19–53% 的请求根本不是扩展(新线程、compaction),但它们和近期请求共享 system / tool 字节,只有 4–8% 成了关键帧。
- 选定配置(多段增量、链 ≤ 16、在前 32 条里找前驱、brotli q9 4 MiB 帧):原始的 2.74 / 2.28 / 5.26%(加权 2.96%)。唯一留有 Claude Code 日志的那个会话,原始是其日志(26.3 MB 含 subagent)的 43 倍,封存后 0.98 倍(只比主文件是 2.62 倍);实验的合计口径下,原始是 25 倍,封存后 0.74 倍。2.58 GB 分片上随机读:冷 p95 16.2 ms、热 p95 12.8 ms,RSS 冷涨 42 MB、热涨 159 MB。封存 13.9 s + 校验 1.6 s,峰值 RSS 317 MB。60 万次以上记录校验 0 不符。
- Codex 样本(经 HTTP 的 14 条记录)同样每次重发完整历史,`previous_response_id` 用了 0 次。

**验收(S 组之外,E 组)**:标 [npm test] 的计划落在 `test/raw/seal.test.mjs`(待建);标 [基准] 的是脚本,在生成的 ≥ 2 GB 分片上跑,不进 `npm test`;E7 在私有数据上手动跑。
1. [npm test] 无损往返:封存后每条记录解码出的行字节与原行 sha256 相同(全部记录,不抽样);夹具含重复 id、不可解析的行、末尾半行。
2. [npm test] `raw_ref` / `text_ref` 封存前后解出相同字节(AC-1 走封存文件),DuckDB 不重建;夹具含同一 session 跨两个分片、两边 id 重复,按 session 封存后各自仍解到原字节。
3. [基准] ≥ 2 GB 分片上随机读 1,000 个 `raw_ref`:冷(新进程、LRU 为空,不清 OS page cache)p95 ≤ 200 ms、热 p95 ≤ 20 ms、峰值 RSS 增长 ≤ 256 MB,全程不解码整个文件。
4. [基准] 封存一个 2.5 GB 分片 ≤ 15 分钟,用默认堆。
5. [npm test] 封存中途 `kill -9`(rename 前;一个分片拆成多个封存文件时,两次 rename 之间;rename 后、删原分片前):原文件完好(或与封存文件并存,读者只用其一)。断电后的持久性靠目录 fsync,`kill -9` 测不到:用注入的 fs 断言调用顺序(文件 fsync → rename → 目标目录 fsync → unlink → 源目录 fsync),其余靠审查([0.1](0.1-engineering-rules.md) §6 第 9 条)。
6. [npm test] 活跃分片永不被封存:对未关闭的分片调用封存器 MUST 拒绝。

8. [npm test] 看板的 session 列表与记录集、ETL 的表在封存前后相同,watermark 不变;与封存并发的 poll 不重复、不缺记录。
9. [npm test] 封存文件、临时文件、导出文件都是 0600,`doctor` ④b 扫得到封存文件与默认导出目录。

## 控制面

守护进程在 `$XDG_RUNTIME_DIR/asight/collector.sock`(0600,属操作者)上提供 JSON over HTTP:`status / on / off / agents / flows`,以及 [5.1](5.1-intervention.md) 的规则、扣留队列、重发。CLI `asight collector …` 走它;看板的设置面板以后经 [4.4](4.4-server.md) 服务端转接,继续带 D26 的 Host / Origin / CSRF 门。这些门挡浏览器,挡不住同机别的用户的本地进程;转接后他们就能替本用户设定改包规则、用本用户的凭据重发(违不变式 1)。所以在 [4.4](4.4-server.md) OPEN 的按用户隔离落地之前,这条转接 MUST NOT 上线,控制只走本 socket。

6. 连接中途 `on→off→on`:客户端零错误;`off` 期间开始的调用零记录,`on` 时开始、跨进 `off` 的调用整条记下;之后缺前序消息的调用标 `partial`(`partial_reasons` 含 `off-window`),ETL 读成 `context_state='partial'`;`off` 期间到达、不属于在记调用的帧不出现在任何信封或 `ws.tail_raw` 里。
7. 一条连接上多轮:拼出的上下文与 mock 侧状态逐字一致(`context_state='reconstructed'`)。
8. SOCKS4 / 4a / 5 前导:同 T6 的 CONNECT 断言。`https://` 代理:代理 host 取自该进程的 `HTTPS_PROXY` 时外层 TLS 被终结、隧道内照 T6 断言并被记录;代理表里 `own:false` 的代理 host 与只给 `h2` 的连接透传,`flows/` 有元数据,`status` 报「未采」;不在代理表里的 `https://` 代理按普通 TLS 透传,只记元数据,不标「https 代理」;同一进程改选 `all` 后,不在代理表里的 `https://` 代理外层 TLS 也被终结、隧道内照 T6 断言并被记录。
9. 不信任 asight CA 的 Node 客户端,TLS 1.2 与 1.3 各一:被判为拒绝(无 alert 也算);同一 (pid, host) 连续 2 次后进负缓存,此后它的连接经引擎原样透传,客户端看到上游的真实证书;拒绝 → 一次解密成功 → 拒绝,不进负缓存(中间成功重新计数);引擎没向 redirector 发任何停止改写的请求,该进程到别的 host 的连接照常解密;`status` 报该 (pid, host)「因负缓存停采」;该 pid 退出后(`forgetPid`)条目与计数都清掉,复用同一 pid 的进程到该 host 照常解密。
10. 一轮结束后连接仍开着、客户端不再发消息:该轮最后一条回复在终止消息到达后 1 s 内落盘。
11. 开着拦截、规则命中一条 WebSocket 消息:转发字节 == 收到字节,不进扣留队列,审计与 UI 带「WebSocket:v1 不支持改包」([5.1](5.1-intervention.md) 第 6 条)。
12. 上游证书校验失败(mock 上游用系统根不认的私有 CA;直连、`https://` 代理外层、CONNECT 隧道内各一):直连与外层:校验失败的那条上游连接上 mock 没收到任何客户端字节;客户端发出的字节逐字到达新开的上游连接,客户端收到的是上游的真实证书;信任该私有 CA 的客户端经透传完成一次往返,字节逐字;`flows/` 记 `not_captured:'upstream-cert'`,该 (pid, host) 进负缓存,下一条连接直接透传、不再试上游 TLS。CONNECT 隧道内:只有这一条客户端连接被关掉,mock 代理只收到一次前导(引擎没重发前导),`flows/` 记 `upstream-cert`,客户端重试的连接直接透传、往返逐字。上游连不上或中途断开(网络失败):客户端连接被关掉,引擎不向它注入任何字节。
13. 调用打开期间客户端又发数据消息(如 `response.interrupt`):它记在该调用的 `req_extra_messages`,不另起信封;该轮以 `response.incomplete` 结束时信封照常写出;`response.failed` 同样结束一条调用。
14. 调用边界与整条连接重建:没有打开的调用时 mock 主动推一条服务端消息 → 它自成一条信封,`req_body:null`;两次调用之间的 ping / pong 出现在下一条信封的 `ws_raw` 里;连接关闭时最后一条调用之后的帧在 `flows/` 的 `ws.tail_raw`;把该连接全部信封的 `ws_raw` 与 `ws.tail_raw` 按帧号拼起来 == 线上字节;客户端方向的 `m` 切片先数 `req_body`、再数 `req_extra_messages`;升级本身没有单独的信封,每条调用的信封都带升级请求与 101 的头。
15. 中断与二进制:调用在终止消息前被上游 RST 打断 → 一条 `error:true` 信封,已收到的服务端消息在 `resp.partial.messages`,它的帧不在 `ws.tail_raw` 里;首条客户端消息是二进制 → `req_body:null` + `req_body_b64`(== 解压后的消息字节),其余二进制消息存 `{b64}`。
16. 非 LLM 的 WebSocket 路径(mock 在非推理端点上开 WebSocket):客户端消息只存 `{raw_chars, verbatim:false}`,其帧在 `ws_raw` 里没有载荷;读取侧就地标「非逐字」;转发字节 == 收到字节。
17. 单次调用超过 64 MiB:超出后的消息存 `{omitted_bytes}`、其帧没有载荷,信封 `ws_truncated:true`,读取侧就地标「已截断」;转发字节 == 收到字节,客户端零错误。

**M · 同机多用户([VM] · 两个 uid A、B 各装一套 · 计划,随 Linux 分支落地)**
1. 各自的 agent 只被自己的守护进程采集:A 的记录里没有 B 的请求,反之亦然。
2. B 的进程直连 A 的引擎端口时,A 查不到它:不记录、不过改包规则,连接被关掉。两种连法都测:从 `127.0.0.2` 连;A 的 agent 某条经引擎的连接关闭后,B 从同一 `127.0.0.1` 源端口连(撞不上残留的 `by_port` 条目)。
3. B 的 pid 进不了 A 的改写:即使出现在 A 的 `watch` 表里(pid 复用,或人为写入),`connect4/6` 因 uid 不符不改写、不上报。
4. A `off`、或 A 的助手被 `kill -9`:B 的 link 还在,B 照常采集。
5. A 的助手收不到 B 的 exec / exit 事件(内核里按 uid 过滤)。
6. 给助手传 BPF 对象或文件路径的请求被拒,它只装内嵌对象。
7. B 起助手,经控制通道或 argv 传 A 的 uid:请求被拒或被忽略,A 的 agent 连接一条也不被 B 的程序改写。
8. B 抢先绑 A 引擎端口的另一族地址(如 `[::1]`),或 A 的引擎被 kill 后 2 s 内 B 抢绑同一端口:A 的 agent 新连接直连,B 的监听收到 0 条连接。
