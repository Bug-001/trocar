## Goal

每个系统用户一个常驻、稳定的采集守护进程,以该用户身份运行:认出该用户自己的 agent 进程,把它们的新连接引到本地引擎,解密、逐字记录,再原样转发。开关只改变守护进程自己的行为,agent 不重启、看不出差别。任何部件崩溃,agent 的流量都直接走原路(fail-open)。唯一带特权的部分是守护进程拉起的能力助手,每台机器 sudo 装一次(D36)。

## 结构:平台相关 / 平台无关 / harness 相关 分目录

仿 Linux 内核的 `arch/`:加一个平台只动 `arch/<os>/`,加一个 harness 只动 `harness/`。

```
src/collector/
  core/                 平台无关:引擎、记录、开关、控制面、改包
    engine/             接连接 → 查元数据 → 嗅探 → 解密 / 透传 / CONNECT 隧道
    http1/              HTTP/1.1 被动分帧(双向)、SSE 逐字
    ws/                 WebSocket 旁路记录:分帧、解掩码、permessage-deflate(D37)
    tls/                CA 与叶证(node:crypto 自签,零依赖)
    record/             信封写入、flows / audit / replays 流
    intervene/          规则、扣留队列、重发(D30)
    trust/              信任入口:注入计划、安装日志与撤销、合并包(D37④)
    registry.mjs        按 harness 描述匹配进程(本身不含任何 harness 名)
    switch.mjs          开关状态机(期望态 vs 内核实际态)
    control.mjs         本机控制面(unix socket)
  arch/linux/           eBPF 程序、C redirector(能力助手)、/proc 读取、用户级 systemd 单元(可选)
  arch/darwin/          (待写)Network Extension 透明代理
  arch/win32/           (待写)WFP
  harness/              每个 harness 一个文件:进程特征、信任入口与其 resolver、已知 API host、配置读取器(D37;session 键等读取侧约定在 src/dissect/harnesses.mjs,见 3.1)
    plugins/            dsh、OpenCode 的信任插件源码(D37④)
    shims/              Kimi 的启动 shim 模板(D37④)
```

平台层对核心只暴露一个接口 `Redirector`:`attach() / detach() / status() / watch(pid, verdict) / unwatch(pid) / lookup(peer) → {dst, pid, agent} / heartbeat()`,外加进程事件流 `exec / exit`。核心不出现任何 `process.platform` 分支。

**特权钩子按 OS 各写一份,引擎侧契约到处一样(D36)**:内核钩子在每个 OS 上都要特权;钩子以上(引擎、记录、开关、改包)各 OS 相同。引擎只经 `src/collector/core/redirector.mjs` 的 `Redirector` 契约用钩子,这份契约各 OS 一样。Linux 上钩子是守护进程拉起、带 file capabilities 的能力助手(下文);macOS / Windows 上预计是 OS 托管的扩展 / 服务,引擎经本地通道接入,后设计。

## Linux 机制

**内核侧(`arch/linux/bpf/`,C + libbpf CO-RE)**

| 程序 | 挂点 | 作用 |
|---|---|---|
| `connect4` / `connect6` | 根 cgroup `cgroup/connect4|6` | 当前 tgid 在 `watch` 表且判定为「解密」、不是守护进程自己的 tgid、当前 uid(`bpf_get_current_uid_gid()`)等于本实例的 uid(存在配置 map 里)、是 TCP、和引擎同一 netns、引擎在听、监听 socket 属本实例(内核核对它的属主 uid `sk_uid` 等于本实例 uid,具体读法实验室确认)且心跳新鲜 → 把目的地改写到引擎端口,原目的地连同当前 pid、uid 按 socket cookie 存进 `orig_dst`。在 `watch` 表但判定为「不解密」→ 不改写,只经 ringbuf 报 `{pid, 目的地}`,写进 `flows/`(D31「其余照常放行、只记元数据」)。uid 不符的一律不改写、不上报;监听 socket 不属本实例(别的用户抢绑了引擎端口)时也不改写,agent 直连 |
| `sockops` | 根 cgroup | 连接建立时把 `orig_dst[cookie]` 搬到按 (客户端源地址, 源端口) 索引的 `by_port`,供引擎 accept 后查。uid 只在 `connect4/6` 的进程上下文里取,随 `orig_dst` 带过来,只作记账。`by_port` 条目只用一次:引擎查到即删,客户端 socket 关闭时(`BPF_SOCK_OPS_STATE_CB`)也删;不删的话,别的用户复用同一源端口连引擎会撞上残留条目,被当成本实例的 agent |
| `exec` / `exit` | `tp_btf/sched_process_exec|exit` | 只处理本实例 uid 的进程,别的用户的事件在内核里丢掉。exec:先在内核里删掉该 tgid 的旧判定,再把 `{pid, filename}` 经 ringbuf 交给用户态重新判定;exit:删表项 |

exec / exit 用 `tp_btf`,不用经典 tracepoint:经典 tracepoint 要读 tracefs,得额外的 `cap_dac_read_search`,不在助手的三项能力里;`tp_btf` 不需要(实验室探测确认)。

**用户态(`arch/linux/redirector/`,C · 能力助手)**:由守护进程以子进程拉起。文件属 `root:root`、0755,只带 `cap_bpf,cap_net_admin,cap_perfmon+ep`,不设组、不 setuid;调用者 uid 就是助手自己的真实 uid(file capabilities 不改 uid)。内核在 exec 带 file capabilities 的程序时会清掉此前设好的 parent-death 信号(prctl(2)),守护进程在 fork 后替它设的不算数,所以助手启动后第一件事是自己调 `prctl(PR_SET_PDEATHSIG)`,再比对 `getppid()` 与 argv 传来的守护进程 pid,不符就退出;控制通道 EOF 是第二个退出条件。它持有全部 bpf_link,**不 pin**:进程一退,内核自动摘钩,agent 新连接直连(fail-open 的第一层)。它只做三件事:装卸程序、改表、按请求查表;不碰任何连接字节。它只装自己内嵌的 BPF 对象,MUST NOT 接受调用者给的 BPF 对象或文件路径;MUST 只对调用者 uid 的进程生效:配置 map 里的本实例 uid 由助手取自己的 `getuid()` 填写,行协议与 argv MUST NOT 接受 uid 字段(Linux 分支现有 `config` 行里的 `engine_uid` 要去掉);内核侧逐次核对,见上表。

**为什么不用 nftables / TUN**:nftables 的 REDIRECT 规则在守护进程死后仍在,连接打到死端口 = fail-closed;mitmproxy 的 TUN 方案要用户态 TCP 栈,Node 里没有。改写 connect 目的地 + bpf_link 自动摘钩是唯一同时满足「只碰 agent 连接」和「崩了就放行」的做法。

**fail-open 两层**:redirector 死 → 内核摘钩;引擎死 → 监听 socket 消失,`connect4` 用 `bpf_sk_lookup_tcp` 发现没人在听就不改写;引擎卡住 → 引擎每 500 ms 经 `Redirector.heartbeat()` 发心跳(助手写进内核表),`connect4` 只在心跳 2 s 内新鲜时改写;心跳由引擎发,卡住的引擎才会被发现。已经由引擎终结的 TLS 连接会随引擎一起断,agent 自己重试(Claude Code 对已开始输出的流不重发);这一点如实记录(断开的每条在途连接在 `flows/` 留连接行,引擎没在的时段留事件行;守护进程本身被 `kill -9` 或断电时引擎就是它,没有谁能当场为那些连接留行,改由下次启动的「上次没有干净退出」事件写明当时经引擎的在途连接被切断、条数不明)并在看板显示,不假装能避免(D38)。

## 引擎(`core/engine/`)

引擎在本实例自己的端口上同时听 `127.0.0.1` 与 `::1`(端口按实例分配,见 OPEN),两族都占住,引擎在跑时别的用户没法在另一族上抢绑;引擎不在跑时靠上表的监听属主核对。每条被引来的连接:

1. accept 后立刻按对端地址和端口向 redirector 查 `{原目的地, pid, agent}`,同时向原目的地发起 TCP 连接。查不到的连接没有原目的地可转:直接关掉,不写信封、不过改包规则,但在 `flows/` 留一条失败事件(`where:'engine'`,`code` 为 `lookup-miss` / `loader-down` / `loader-timeout`,带对端地址与端口,不含任何字节;同一处同一 `code` 10 s 内合成一条)。查不到的可能是别的用户连错了端口(M2),也可能是本用户自己的 flow(`by_port` 条目被挤掉、`off` 竞态、助手已死或卡住);引擎分不清,一律记(D38)。
2. 先到的字节决定走向:上游先说话 → 透传;客户端发 TLS ClientHello → 读 SNI / ALPN;发 `CONNECT host:port` → 走 CONNECT 隧道;发 SOCKS4 / 4a / 5 前导 → 同 CONNECT 处理(D37);发明文 HTTP 请求行 → 明文分帧。
3. **CONNECT 隧道**(agent 用 `HTTPS_PROXY` 指向 Clash 等本地代理时):把客户端的 CONNECT 原样发给原目的地(那个代理),把代理的真实回应原样转回,成功后再对隧道里的 TLS 做第 2 步判断。MUST NOT 自己合成 `200 Connection Established`。上游出口因此仍走用户自己的代理 / VPN。
   **SOCKS4 / 4a / 5(D37)**:Kimi、Hermes、Z-Code 会用。前导原样发给代理、代理的真实回应原样转回,MUST NOT 合成成功;前导里的认证字节是代理凭据,按 [4.1](4.1-capture-sources.md) 存 0600。**`https://` 代理(D37,v1 做)**:Kimi 与 Codex 的 WebSocket 拨号器会用;客户端先和代理 host 握外层 TLS。只在该代理 host 取自这个进程自己的代理配置(环境里的 `HTTPS_PROXY` / `ALL_PROXY` 或 harness 文件声明的配置项)时才终结外层 TLS(属解密策略 `auto`,与 base_url host 同类),里面的 CONNECT 照上条转发,隧道里的 TLS 再走第 2 步;其余代理 host 透传并在 `flows/` 记「未采 · https 代理」。这个标签只标在守护进程按进程交给引擎的代理表里、不满足终结条件的条目上(`own:false`);守护进程没告诉引擎的 `https://` 代理,在引擎看来就是一条普通 TLS,按普通透传只记元数据,不标它。**解密策略 `all` 例外(D40 起 `all` 是默认)**:策略是 `all` 时,该进程的一切 TLS 都终结,包括不在它自己代理配置里的 `https://` 代理(引擎在解开之前认不出它是代理);操作者选了 `auto` 时仍只终结该进程自己配置的代理。引擎与代理的外层握手证书校验失败(如代理用私有 CA)时同第 5 步:重放客户端字节、透传、进负缓存,不伪装成功。Hermes 从 `ALL_PROXY` 取 socks5;dsh 拒绝 SOCKS、直连;Codex 的模型 HTTP 忽略 SOCKS。
4. **解密的条件(全部满足)**:该进程已确认信任 asight CA(见「身份与信任」)· 这条连接不在该 harness 声明的「不经信任路径」之列(同节;`all` 下也一样)· ALPN 含 `http/1.1` 或未带 ALPN · 目标 host 命中解密策略 · 不在负缓存里。否则透传,只记元数据。
5. 解密时先和上游完成 TLS(SNI 与客户端一致,ALPN 定为 `http/1.1`,按系统根证书校验;信任集是三份的并集,没有谁覆盖谁:操作系统信任库(企业 / TLS 检查 CA 装在这里;Node 有 `tls.getCACertificates('system')` 时取它,再并上第一份存在的系统 PEM 包,如 `/etc/ssl/certs/ca-certificates.crt`、`/etc/pki/tls/certs/ca-bundle.crt`,Node 20 只有后者)∪ Node 自带根 ∪ 引擎进程自己的 `NODE_EXTRA_CA_CERTS`;启动时取一次。中转站用私有 CA 时照 Node 的办法(`NODE_EXTRA_CA_CERTS`)信任,不另设 asight 变量(协调者 2026-10-06 定,Plan 3a gate G8;守卫 `test/collector/core/upstream-trust.test.mjs`)。守护进程由用户级自启单元拉起时,systemd `--user` 不带登录 shell 的 export,所以单元用 `Environment=` 带上安装时 shell 里的 `NODE_EXTRA_CA_CERTS`(绝对路径、不在 `~/.asight/` 下时才带;只给守护进程,不进登录环境,也不是 asight 自设的变量),与在那个 shell 里手动 `asight collector start` 看到的一样;装后 shell 里的值变了要重装。系统库一份也读不到时照常用其余两份,并写失败记录 `system-roots-unavailable`。已知局限:Node 20 读不到 macOS 连接,把已缓冲的客户端字节(ClientHello)原样重放过去,之后两边透传。引擎为了分清证书失败与网络失败,可以让握手做完再查校验结果,这不等于关掉校验。客户端自己校验上游的真实证书,asight 不伪装任何东西(D31 fail-open);`flows/` 记 `not_captured:'upstream-cert'`,该 (pid, host) 进负缓存。**隧道里**(CONNECT / SOCKS / `https://` 代理之后):只关掉这一条客户端连接,同样记 `upstream-cert`、该 (pid, host) 进负缓存,客户端重试的连接直接透传。MUST NOT 重发客户端的代理前导:前导里有 `Proxy-Authorization` 或 SOCKS 用户名密码,重发等于 asight 没有操作者意图、自己拿 agent 的代理凭据发请求(违不变式 1 / D30)。守卫:审查([0.1](0.1-engineering-rules.md) §6 第 1 条),W12 落地后加测。另一种做法见 OPEN。网络失败(连不上、超时、上游中途断开)仍关掉客户端连接,不替上游伪装成功。客户端拒绝叶证 → 计入负缓存,该连接的 `flows/` 记 `reason:'client-rejected-leaf'`(在该连接的记录写出之前就定下)。**签不出叶证**(引擎内部错误):同「上游证书校验失败」让路 —— 直连时新开连接、重放 ClientHello、透传,隧道里只关这一条;`flows/` 记 `not_captured:'leaf-error'`,不进负缓存(是 asight 自己的错,不是该 host 的属性),另写失败记录 `leaf-error`。**拒绝的判据(D37 更正)**:见到 ClientHello、客户端没发任何应用数据、随后关闭或 RST,不论有无 alert、不论 client Finished 是否到达——Node 不发 alert:TLS 1.3 下引擎只看到 ECONNRESET,TLS 1.2 下握手完成后客户端零数据关闭;只认 `unknown_ca` / `bad_certificate` alert 对 Node / Bun 永远不触发。**上游要客户端证书(mTLS;D40)**:`all` 下 agent 连的 host 不再限于已知 API,企业网关、MCP 服务可能要求客户端证书;引擎替客户端先和上游握手、拿不出证书,上游用 alert 拒绝(TLS 1.3 `certificate_required`;TLS 1.2 `handshake_failure` / `bad_certificate` / `no_certificate`;Node 的错误码 `ERR_SSL_…ALERT_…`,OpenSSL 版本不同前缀不同,按尾部认)。这是「不能解密」,不是网络失败,不能关掉客户端了事。**TLS 1.2**:拒绝在握手完成之前到,客户端还没被动过 → 同「上游证书校验失败」让路(销毁这次握手、新开连接、重放 ClientHello、透传),客户端自己的握手带着自己的证书抵达真 host,没有失败连接;隧道里同样只关这一条、不重发前导。**TLS 1.3**:alert 在握手完成之后才到,客户端已经握在 asight 的叶证上、挪不走也重放不了,这一条连接失败;但立即写负缓存(一个 alert 是明确的回答,不是猜测,不等 2 次),之后该 (pid, host) 的连接透传、带着客户端自己的证书成功。两种都在 `flows/` 记 `not_captured:'upstream-handshake'`(失败类,`reason` 带 Node 的错误码)、写一条 `negative-cache` 失败事件(`cause:'upstream-handshake'`)。上游**已经发过数据**之后才到的 alert 不算这条,不进负缓存;网络失败(重置、超时、拒绝连接)照旧关掉客户端。已知局限:只在 HTTP 层表示「要客户端证书」的服务(如 nginx `ssl_verify_client on` 握手完成后回 400)在 TLS 上看不出来,引擎照常解密,agent 拿到的是那个 400,不是它直连带证书得到的结果,见 OPEN。
**负缓存**(关闭原 OPEN「负缓存的键与阈值」):键 `(pid, host)`。同一 (pid, host) 连续 2 次判为拒绝才写入(中间一次解密成功就重新计数;被放弃的 Happy Eyeballs 并行连接没有 ClientHello,不计);上游证书校验失败一次就写入。命中负缓存的连接,引擎照常接下、原样透传,只在 `flows/` 记元数据。MUST NOT 为此通知 redirector,也不停止内核对该进程的改写:内核只能按进程停、分不了 host,停了会连该进程已信任的别的 host 一起丢采。**生存期**:条目只在内存里,不设 TTL;进程退出时(或 exec 成不匹配特征表的程序而离开进程表时,见 §确认信任),守护进程让引擎清掉该 pid 的条目和未满阈值的计数(`engine.forgetPid(pid)`),pid 被复用时不继承;引擎重启后全部清空。`status` 列出当前条目。所以 `upstream-cert` 写入的条目在该进程余下的生命里一直透传,上游之后换好证书也不重试,重启该 agent 才重试。已知局限,如实写明:CC 沙箱代理替工具中转的 socket 也来自 claude 的 pid,工具连某个 host 被拒两次,claude 自己到该 host 的连接也不再解密;OpenCode 的 `ws` 路径没被 resolver 认出时,引擎解密它、客户端拒绝叶证,被拒的 ws 请求断掉,连续 2 次后 (pid, API host) 进负缓存,同 host 上 fetch 路径的采集也一起停掉。这两种情况 `status` 都 MUST 如实报「因负缓存停采」。
6. 解密后两个方向都走**被动分帧**:引擎转发的是收到的原始字节,分帧器只读一份副本来切出「一次请求 / 一次响应」。不重新序列化、不改大小写、不改 chunk 边界;`101 Switching Protocols` 之后原始字节照转,旁路副本交 `ws/` 按 §传输与帧级记录 记录(D37)。没有改包规则命中时,请求边收边转,零额外延迟。

**解密策略(进程内按 host · D40 修订)**:默认 `all` = 该进程的一切 TLS 都解密([0.0](0.0-overview.md) D40①:看 agent 在模型调用之外做了什么)。两种策略都只作用于已确认信任 asight CA 的 agent 进程,第 4 步的其余条件(不经信任路径、ALPN、负缓存)照旧。**`all` 的代价(如实写明)**:Claude Code / Codex 的沙箱会替工具命令中转 npm、git 等流量,这些 TLS 的客户端是子进程,socket 却属 agent 进程;子进程不信任 asight CA 时拒绝叶证。按第 5 步,该 (pid, host) 连续 2 次拒绝后进负缓存,之后原样透传;所以每个 (agent pid, host) 最多 2 条连接失败(工具多半报一次网络错误,由 agent 重试;上游要客户端证书的 host 最多 1 条、TLS 1.2 下 0 条,见第 5 步),每次一行 `client-rejected-leaf` 连接行,写入负缓存一条 `negative-cache` 事件(D38)。工具与 agent 自己连同一个 host 时,agent 那条也随之不再解密(第 5 步「已知局限」)。不匹配特征表的子进程自己连出去的连接不经引擎,不受影响(§身份与信任「子进程与嵌套 agent」)。**选择与旧安装**:策略存在操作者目录的期望态里(`state.json`;按 harness 的形状由并行的 D39 定);没写过策略的安装取 `all`;盘上已写着 `auto` 的保持 `auto`(分不出是旧默认还是操作者选的),`status` 显示当前策略。**`auto`**(D40 起是操作者显式选的收窄,用于隐私或绕开上述代价;保留与否)= harness 声明的已知 API host ∪ harness 文件声明的读取器从该进程环境变量**和 agent 自己的配置文件**读到的 base_url / 中转 host(D37:Codex 不读 `OPENAI_BASE_URL`,看 `config.toml` 的 `openai_base_url` 与自定义 provider;OpenCode `opencode.json`;Kimi `config.toml` / `KIMI_*`;dsh `DEEPSEEK_BASE_URL` 与 `DEEPSEEK_SEARCH_BASE_URL`;Hermes `config.yaml` / `.env` 与辅助模型的 host;Z-Code 的 provider 配置;CC 的 settings `env`)∪ 该进程代理配置里的 `https://` 代理 host(见上文第 3 步)∪ 操作者手加的 host。D40 之前默认是 `auto`,理由正是上面的代价(子进程信不信任 asight CA 取决于入口和它自己的运行时,见 §身份与信任「信任面」);设计上选择看全,代价按 D38 记录、可见。中转站 host 来自 agent 自己的配置,用户不用登记。

## 传输与帧级记录(D37)

Codex 内建 `openai` provider 默认走 `wss://…/responses`(握手是不带 ALPN 的 HTTP/1.1 Upgrade);不记帧,Codex 就是零内容。

- **转发不变**:引擎照转收到的原始字节,不重组、不改帧边界、不改扩展协商;记录只读旁路副本。
- **分帧**:两个方向都按 RFC 6455 解析;客户端帧解掩码;分片消息重组,中间夹的 ping / pong / close 照记、不并进消息。
- **permessage-deflate**:扩展参数取自上游 101 的 `Sec-WebSocket-Extensions`(不是客户端的报价);每方向从第一帧起维护一份解压上下文(一个持续的 `node:zlib` inflateRaw 流,或与之等价的:每条消息单独 inflate、把上一段 32 KiB 窗口当字典带入),支持 context takeover 与 `*_no_context_takeover`(零新依赖,D32③)。某条消息解压失败时清掉该方向的窗口,MUST NOT 带着旧窗口继续解出错误文本;之后依赖上下文的消息按解压失败处理(见下「大小上限」与 `partial`)。经引擎中转的连接从第一帧起都在引擎手里,inflate 上下文不会断(`off` 期间也维护,见下);缺了前序消息的调用标 `partial`(见下),原始帧照存。
- **信封**:一次逻辑调用一条信封,追加字段 `transport:'ws'`、`flow_id`、`ws_frames:[首帧号, 末帧号]`、`ws_ext`(101 的扩展头原文)、`ws_raw`(该调用两个方向的原始帧,能逐字重建线上字节,形状与边界见下);`req_body` = 解压后的客户端消息文本(调用的第一条客户端数据消息;没有客户端消息的调用为 `null`);`req_headers` = 升级请求的逐字头,按请求头取 session 键的分片器与 D35 封存器据此读到 Codex 的 `session-id`;`resp` = `{kind:'ws', messages:[…]}`(服务端消息序列,逐字)。不是 UTF-8 文本的消息(二进制消息,即 opcode 2,不论字节是否合法 UTF-8;或 opcode 1 但字节不是合法 UTF-8):首条客户端消息存 `req_body:null` + `req_body_b64`(解压后的消息字节,不带 `req_content_encoding`,与 §记录 的 HTTP 压缩体区分),其余消息存 `{b64}`。首条客户端消息单条超上限被分帧器略去、或解压失败时同样存 `req_body:null`,不另加字段(也不带 `req_body_b64`)。解压失败时它的压缩帧仍以 `p` 存在 `ws_raw` 里;单条消息超上限被分帧器略去时,分帧器没留它的载荷,它的帧只留帧头(无 `p` / `m`),读时标「非逐字」。与「没有客户端消息」的信封靠两点区分:`ws_raw` 里有该调用的客户端数据帧,且信封带 `ws_truncated`(超上限)或 `partial_reasons` 含 `decode-failed`(解压失败)。
- **升级与中断**:升级本身不单独成信封;每条调用的信封都带升级请求与 101 的逐字头(`req_head_raw` / `resp_head_raw`)。升级被拒(如 `426`)是一次普通 HTTP 往返。一条调用也没有的 WebSocket 连接只在 `flows/` 留 `transport:'ws'` 与帧数、尾帧等汇总。每条切到 WebSocket 的连接,`flows/` 记录都带 `transport:'ws'` 与 `ws = {frames, calls, recorded, partial, dropped_frames, tail_raw?, broken?, failures?}`(帧数、调用数(记与不记都计)、写成的信封数、其中标 `partial` 的数、`off` 时丢掉的帧数、尾帧、停止解析的方向及原因、采集失败计数)。客户端在 101 到达前就发的帧、与 101 同一个 chunk 里的服务端帧,都从第一帧起交给 `ws/`。调用在终止消息之前因连接关闭或上游中断而结束:写一条 `error:true` 信封,`resp = {status:null, kind:'error', error, partial:{kind:'ws', messages}}`,与 HTTP 中断同形([4.1](4.1-capture-sources.md) §中断也记);它的帧随这条信封,不进 `ws.tail_raw`。
- **`ws_raw` 的形状与边界(关闭原 OPEN「WebSocket 原始帧放哪」)**:放进信封,不拆成第二处。每帧一项 `{i, d, h, p?|m?}`:`i` = 连接内帧号(两个方向共用一个计数);`d` = `'c'`(客户端 → 服务端)或 `'s'`;`h` = 帧头字节的 base64(含掩码键);载荷二选一:`p` = 解掩码后载荷的 base64(控制帧、压缩帧、本信封不携带其消息的帧),`m = [k, 偏移]` = 本信封该方向第 k 条消息字节的切片,偏移按字节计(未压缩数据帧,文本不存两遍;客户端方向先数 `req_body`,再按到达顺序数 `req_extra_messages`;服务端方向数 `resp.messages`,出错的信封数 `resp.partial.messages`)。存解掩码后的载荷,是因为掩码键随机,掩码后的字节压不动,也做不了 D35 的字节级增量;重建时按帧头里的掩码键再掩一遍。两者都没有 = 载荷未保留,读时 MUST 就地标「非逐字」(不变式 4)。**边界**:服务端消息按收全时归属:收全时没有打开的调用的服务端消息自成一条信封(`req_body:null`),收全即写盘;在客户端消息打开调用之后才收全的,并进那条调用(`off` 时开始、又不是在该调用打开期间开始的除外:不并入、丢弃,当时开着的调用与之后的调用都标 `off-window`,见下「开关」);连接结束时还没收全的消息,其帧随仍开着的调用,没有开着的调用则进 `ws.tail_raw`;两次调用之间的帧(ping / pong 等)随下一条调用,写进它的 `ws_raw`;下一条调用不记(`off` 时开始)时随它一起丢;数据帧随它所属消息的调用,控制帧按到达位置归属,所以一条分片消息跨过调用边界时,相邻两条信封的 `ws_frames` 区间可能重叠,读者找帧号缺口 MUST 看 `ws_raw[].i`,不看 `ws_frames` 区间;连接关闭时,最后一条调用之后、不属于任何调用的帧(close 帧等)记在 `flows/` 的 `ws.tail_raw`。`off` 期间到达、不属于在记调用的帧不留(见下「开关」)。某方向停止解析后(协议错误或记录器内部错误),该方向之后的字节不再分帧、不编帧号,帧号连续也不代表逐字:当时开着的与之后的调用都标 `ws_truncated`,停止本身写失败记录(见 §记录「采集失败不静默」)。除此之外,帧号连续时,把一条连接的各信封 `ws_raw` 与 `ws.tail_raw` 按帧号拼起来,即逐字重建线上字节(`src/collector/core/ws/raw.mjs` 的 `rebuildWsWire`,可只重建一个方向);帧号有缺口处,是 `off` 期间没记的帧或没写成的信封;缺的帧里有数据消息时,其后的调用标 `partial`(见下),只缺控制帧不标(控制帧不承载上下文)。**非 LLM 路径(D40 修订)**:与 LLM 路径相同,两个方向的消息逐字、帧留载荷,`ws_raw` 能逐字重建。保存级别为 `log` 的调用(§记录「保存级别」)两个方向的消息都只存 `{raw_chars, verbatim:false}`、帧不留载荷,`ws_raw` 重建不了,读时 MUST 就地标「只记日志」(不变式 4);D40 之前的非 LLM 调用只有客户端消息是这个形状,读时标「本条采于 D40 之前,只存了长度」。要过 D34 的体积预算:E7 在一个 Codex WebSocket 会话上也跑。
- **逻辑调用怎么切(已定 · 2026-10-05)**:D20 与 [0.1](0.1-engineering-rules.md) §5 禁止在采集端解析 provider。做法:harness 文件以**数据**声明终止消息的字节模式(Codex:`response.completed` / `response.failed` / `response.incomplete` / `error`;`response.incomplete` 结束被打断的一轮),核心见到它就写信封、不含任何 provider 代码;一条客户端数据消息加上它之后到终止消息的全部服务端消息合成一条信封。声明了模式时,调用打开期间(尚未见终止消息)又到的客户端数据消息(如 Codex 的 `response.interrupt`)不另起调用,记在该调用信封的 `req_extra_messages` 里。没声明模式的连接退回「到下一条客户端数据消息或 close 为止」,代价是每轮最后一条回复要等用户下一条消息或连接关闭才落盘(Codex 连接可开 60 分钟)。模式只用来切信封,不用来分 session、不解释内容、不改字节,核心里没有 provider 代码,所以不算 D20 禁止的「采集端解析 provider」;harness 文件本就以数据声明进程特征与已知 host(D31②)。没选「只按下一条客户端消息切」:每轮最后一条回复要等很久才落盘,看板看不到刚结束的一轮。**看不到终止消息时**:这条调用的某条服务端消息解压失败、或单条消息超上限被分帧器略去(它可能正是终止消息),或服务端方向已不再跟踪,这条调用就改在下一条客户端数据消息处切,与没声明模式的连接相同,这条调用的验收 W10 1 s 落盘不成立;否则之后每一轮都会并进同一条信封。因调用累计超额度而存成 `{omitted_bytes}` 的消息不在此列:它照常解压、照常认终止消息,W10 照常成立。连接正常关闭时按最后一条调用自己判断:它本身看不到终止消息(或服务端方向已不再跟踪),就照常写成、不算 `error`;否则仍是终止消息之前中断,按「升级与中断」写 `error:true`。命名与校验仍由 Responses-WS dissector 在读时做。
- **`partial`**:信封顶层 `partial:true` + `partial_reasons`(`off-window` / `write-failed` / `decode-failed` 的子集,按这个固定顺序排列),表示这条连接上更早的消息缺了。超上限被略去的消息不算缺口:它只让所在信封带 `ws_truncated`,不让之后的调用标 `partial`(内容丢了,但缺的是这条信封自己的字节,不是上下文)。采集端不解析 provider,判断不了哪条调用依赖缺失的消息,所以同一连接上缺口之后的每条调用都标;能否收窄由读时 dissector 判(如不带 `previous_response_id` 的全量调用)。读取侧把信封的 `partial:true` 读成 `context_state='partial'`,收窄了才不标([3.1](3.1-adapter-contract.md))。读时才发现的缺失(少了某个文件)由 dissector 标 `context_state='partial'`,不改原始记录,信封的 `partial` 字段不变。顶层 `partial` 只说这条连接的上下文有缺口,本信封自己的字节是全的;本信封字节不全另有标注,不是一回事:响应没收完是 `error:true` + `resp.partial`,HTTP 请求体是 `req_truncated` / `req_partial`(§记录),WebSocket 调用超上限是 `ws_truncated`(下条)。
- **大小上限**:单次 WebSocket 调用累计 64 MiB(与 HTTP 体现有的上限一致;按该调用已保留消息的线上载荷字节计,被略去的消息不占额度;连接结束时未收完的消息不计额度,帧载荷照留(每方向至多一条),调用已超额度时则不留);超出后的消息存 `{omitted_bytes}`,其帧不留载荷,信封标 `ws_truncated:true`,读时 MUST 就地标「已截断」(不变式 4)。这是**预期类**:不写事件,顶栏不变 ⚠,见验收 F5。**单条消息本身就超过上限时**,分帧器照样跟住帧边界、丢掉超出部分的载荷而不缓冲,该方向之后的帧照常解析与记录;这条消息同样存 `{omitted_bytes}`。该方向开了 permessage-deflate 且有 context takeover 时,跳过的消息让解压窗口断了,之后依赖上下文的消息记为解压失败(原始字节存 `{b64, decode_error}`,调用标 `partial`,原因 `decode-failed`);`*_no_context_takeover` 或未压缩的方向不受影响。
- **开关**:一次调用记不记,在它的第一帧时按当时的开关决定(与 HTTP 在请求开始时取样一致;「第一帧」是打开这条调用的那条消息的第一帧,即客户端消息或自成一条信封的服务端消息的第一帧,更早开始、收全后才并进来的服务端消息随这条调用记或不记):`on` 时开始的调用即使中途 `off` 也整条记下,`off` 时开始的调用整条不记。`off` 期间,经引擎中转的 WebSocket 连接继续维护每方向的 inflate 状态(只在内存,不记录);这期间到达的帧,除属于 `on` 时开始的调用外一律不留,再 `on` 后也不随下一条信封补记;再 `on` 后,缺了 `off` 期间前序消息的调用标 `partial`(`off-window`)。
- **v1 不做**:WebSocket 上的改包([5.1](5.1-intervention.md));HTTP/2——引擎只答 `http/1.1`,七个 harness 都落在 HTTP/1.1,只给 h2 的连接透传,`flows/` 记元数据,标「未采 · h2」(显示处见 §记录);QUIC / HTTP3、AF_UNIX(`ANTHROPIC_UNIX_SOCKET`、`claude ssh`)、语音 WebRTC 到不了引擎,由进程级检测(环境里的 `BUN_FEATURE_FLAG_EXPERIMENTAL_HTTP2_CLIENT` / `…_HTTP3_CLIENT`、`BUN_OPTIONS`、`ANTHROPIC_UNIX_SOCKET`)在 agent 状态行标出;上游的 `Alt-Svc: h3` 原样转发,剥掉它属改包(D30),没有操作者意图不做;Bedrock event-stream、Vertex、Gemini 线格式没有 dissector,字节按现有 `isLlmCall` 规则照存,读时落「未识别」隔离并标注。
- **请求体压缩**:CC(被 `CLAUDE_CODE_GZIP_REQUEST_BODIES` 强制时 gzip)、Codex(ChatGPT 登录的 HTTP 路径 zstd)会压缩请求体。压缩字节逐字存(base64 + `content-encoding`,字段见 §记录);gzip 用 `node:zlib` 解。采集端从不解 zstd 请求体:只存线上字节,标「压缩请求体未解码」,不随录制它的 Node 版本变化;读取侧在自己的 Node 有 zstd 时再解(Node 20 的 `node:zlib` 没有)。响应侧不变。实验室用 API key,碰不到 zstd,不挡 R2。

## 身份与信任

- **识别进程**:`harness/*.mjs` 给出特征(Linux:`/proc/<pid>/exe` 的路径模式、`argv` 模式;macOS 预留:Team ID + 签名标识)。只认真正发 API 请求的进程,不认 npm 包装层(Codex、OpenCode 的 node 启动器不发请求)。exec 事件到达后通常在毫秒内完成判定(实验室给出实测值);启动时和每次开启时扫一遍 `/proc` 里本实例 uid 的进程(别的用户的 exe / environ 本来也读不到)。exec 后立刻连网、快过判定的进程会漏掉首条连接——漏的是采集,不是 agent 的连接(它照常直连);实验室测量漏采率。
- **子进程与嵌套 agent**:判据是**进程自己**,不看它的父进程是谁。子进程只要自己匹配 harness 特征表,就是一个独立的 agent,单独采集——一个 agent 启动另一个 agent(如 claude 拉起 codex,或任意 harness 互相调用)天然覆盖。同一进程内的 subagent(如 Claude Code 的 subagent,与主 agent 同进程、靠请求头区分)本来就在该进程的流量里。不匹配特征表的子进程(MCP server、shell 工具、沙箱进程)不被采集;harness 文件可以显式声明某个子进程也算(如 Gemini CLI 的 relaunch 子进程)。**已知缺口(D38 审查 P1)**:原意是这些子进程「只记元数据」,但 Linux 内核侧只认 `watch` 表里的 tgid(`connect4/6` 查 `watch_map`),也只有 exec 钩子、没有 fork 钩子;不匹配特征表的子进程从不进 `watch` 表,fork 之后不 exec 的 worker 同样不进,所以它们的连接照常直连,`flows/` 里**一行记录也没有**(没有元数据行,也没有计数),看板与 `status` 都看不到它们。补法(fork 钩子按祖先 agent 计 `child-direct` 计数,约 30 行 C + 15 行 JS)在那之前本条按此如实写明,不声称记了元数据。嵌套关系(谁启动了谁)记在 `flows/` 的 `parent_pid` / `parent_agent` 里,供看板标注。

- **进程内插件:有界例外(D37④)**:dsh 与 OpenCode 没有只对自己生效的数据入口,用插件。这与 [1.1](1.1-product-definition.md):11「不改被测程序」冲突,是有意接受的例外;边界如下,每条都是 MUST:
  1. 插件只把 asight CA **追加**进本进程的信任,不替换、不删减已有的根。OpenCode 的包装保留调用方已有的 `tls` 字段和 `ca`,只在后面追加 asight CA。
  2. MUST NOT 读、改或发送任何请求 / 响应字节。OpenCode 的 fetch 包装只在 `tls.ca` 里追加 asight CA,请求与响应原样传递。
  3. 自己不发任何网络请求。
  4. 不写 agent 的配置。
  5. 唯一的写:一个按 pid 的「信任已生效」标记,供引擎确认信任(插件的效果在 environ 里看不到)。只在 CA 真的加上了时写;没加上就不写,也不另外输出(「不另外输出」见 OPEN)。
  6. 读不到 `asight-ca.pem`(缺失、不可读、不是 PEM)时什么都不做:不抛错、不加 CA、不写标记。卸载第 3 步删掉它之后、第 4 步删插件之前,或卸载中途崩溃后,插件仍可能被加载,不能因此让 agent 起不来。

  **标记**:文件 `~/.asight/collector/run/trust/<pid>`,内容是该进程的启动时间(Linux:`/proc/self/stat` 第 22 字段)。引擎 MUST 核对 `/proc/<pid>/stat` 里的启动时间,不符就当没有:pid 被复用后,旧标记会让引擎解密一个不信任 asight CA 的进程(违 T7)。pid 退出后标记作废,引擎可以删;卸载时随运行时目录删掉。插件先写同目录的 `.<pid>.tmp` 再 rename 成 `<pid>`,引擎不会读到写了一半的标记;标记目录由安装建好,守护进程还没起过时插件也写得进去。插件在 exec 之后才运行,标记总晚于 exec 出现:插件入口的进程从 exec 到标记出现、最多到启动后 10 s,判 `marker-pending`(未信任、只观察,这段时间里的连接直连,与 exec 竞态同类),不写 `agent-untrusted`;标记出现即重判;10 s 到了仍没有,才按原因判(dsh 的 Node 版本或 `--use-openssl-ca`,都推不出时 `no-marker`)并记一条 `agent-untrusted`。已知效应:OpenCode 首次带插件运行时先 npm install `@opencode-ai/plugin` 再加载插件,实验室 ⑥ 实测从启动到标记 20–50 s,超过 10 s,所以这一次先记一条 `no-marker`,标记出现后再记一条 `agent-trusted`;这期间的模型请求还没开始,没有漏采(为如实记录,要不要给 OpenCode 首次运行放宽宽限)。

  dsh:先检测有没有 `tls.setDefaultCACertificates`(Node ≥ 22.19;dsh 在 22.18 上也能起),没有就什么都不做;`--use-openssl-ca` 下也不加(那时这个调用会替换默认根)。这两种情况都不写标记,插件自己也不输出;原因由 resolver 从该进程的 Node 版本和 argv / `NODE_OPTIONS` 里的 `--use-openssl-ca` 推出,报在 `status` 里(Node 版本怎么取由实验室 ⑤ 定)。「插件什么都不输出、原因由 resolver 推出」= 「什么都不做并报告」的落地读法(见 OPEN)。OpenCode:`--pure` 不挡配置目录里的文件插件(见上表,实验室 ⑥),安装时 MUST 告知用户「带 `--pure` 也会加载 asight 插件」,只要有任何插件,OpenCode 首次运行会 npm install `@opencode-ai/plugin`,多一次 registry 拉取。这次 install 可能还在 OpenCode 的配置目录写文件(`package.json`、锁文件、`node_modules` 等,具体由实验室 ⑥ 定):这些文件是 OpenCode 写的,安装时一并告知,安装清单记下这些路径装之前在不在;卸载不删它们(它们也可能服务用户自己的插件),把装之前不在的报成「asight 的插件引起的残留,未删」;S10 / T11 的「撤净」不含它们。这两个 harness 的观测者效应标签写「asight 代码运行在该 agent 进程内」。守卫:审查([0.1](0.1-engineering-rules.md) §5 · §6 第 4 条),T13 落地后加测。
- **信任面(D37④)**:信任 asight CA 的只有被注入的 agent 进程及其子进程,不含本用户的其他程序。经环境生效的入口(CC、Codex、Hermes、Kimi shim;Z-Code 自己把合并包写进子进程的环境),子进程都继承这个变量:Bash 工具、hooks、MCP stdio server、LSP、git / curl。子进程信不信任 asight CA 取决于它自己的运行时:`NODE_EXTRA_CA_CERTS`(CC、Kimi)只有 Node 子进程认,git / curl 不认;`SSL_CERT_FILE` 指向的合并包(Codex、Hermes),基于 OpenSSL 的客户端(多数 Python、git、curl)都认;Z-Code 把子进程的 `NODE_EXTRA_CA_CERTS`、`SSL_CERT_FILE`、`REQUESTS_CA_BUNDLE`、`CURL_CA_BUNDLE`、`GIT_SSL_CAINFO` 都写成合并包。上界就是「被注入的 agent 及其全部子进程」,这是已接受的代价;asight 不为把子进程剥掉而再改 agent 的其他配置。插件入口(dsh、OpenCode)不进环境,子进程不继承。CA 不轮换、无名称约束,私钥在同 uid 可读的路径上:任何同 uid 的代码都偷得走,包括被注入的 agent 自己(如被提示注入后);偷走后,网络路径上的攻击者(中转站、不可信的网络)在 CA 有效期内(当前实现 `src/collector/core/tls/ca.mjs` 默认 10 年)能对这些进程冒充任意 host,包括子进程的包管理与 git 拉取。没有轮换,唯一的恢复是卸载再重装(换一张 CA)、这些进程各重启一次;要不要恢复 `asight ca rotate` 见 OPEN。D36 的前提「只有被注入的 agent 进程信任它」由此成立(含其子进程)。
- **标记与安装**(D37④):安装 MUST 先列出要改的每个文件,再动手(含用户级自启单元、它带的 `NODE_EXTRA_CA_CERTS`,以及 `systemctl --user enable` 建的 `default.target.wants/` 链接)。按格式做最小插入、不重排:能写注释的格式(dotenv、YAML、shell rc、shim、插件文件)用醒目的哨兵注释块(D28 式),一眼认得出、好卸。CC 的 `settings.json` 与 Z-Code 的 `config.json` 是纯 JSON,写不了注释,加标记键又可能被 schema 拒,所以 asight 的键只靠值(`~/.asight/` 下的绝对路径)加安装清单认出。这是局限,如实写明:用户打开这两个 JSON,看不出哪个键是 asight 加的。JSON 按文本插入键,rename 前先解析校验,原子替换。每个入口记进安装清单,卸载逐项撤销(§安装清单与卸载,S10、T11)。
- **观测者效应(D37⑤)**:注入本身会改变部分客户端行为,开关关着也一样:CC 见到 `NODE_EXTRA_CA_CERTS` 就不再按 flag gzip 请求体;Codex 设了 `SSL_CERT_FILE` 后模型 HTTP 从 native-tls 换成 rustls、ALPN 报 `[h2,http/1.1]`;Z-Code 设了 `caCertFile` 后从 undici 换成 `node:https`,每次请求一个新 Agent、不带 ALPN(推断,见 OPEN);OpenCode 有了插件,首次运行多一次 npm 拉取;dsh、OpenCode 的插件让 asight 代码运行在 agent 进程内。这些以数据列在读取侧的 harness 表([3.1](3.1-adapter-contract.md)),ETL 对经注入信任采到的调用写 `calls.observer_effect`([3.2](3.2-normalized-model.md)),显示处 MUST 标注(R5)。

- **确认信任**:引擎只在确认该进程信任 asight CA 时解密。文件入口与插件入口都不出现在 agent 进程的 `/proc/<pid>/environ` 里(CC、Codex、Hermes 启动后才 putenv;Z-Code、dsh、OpenCode 根本不进环境);那里只看得到 shim 设的值,和用户自己在 shell 里 export 的值。所以每个 harness 有一个 resolver,以操作者身份运行(D36 起这些文件直接可读),按该 harness 的优先级链算出实际生效的值,再读那个文件:文件可读、其中的证书含 asight CA 的指纹,才算信任(合并包不是 CA 的路径,MUST NOT 只比路径)。插件入口看按 pid 的「信任已生效」标记,并核对启动时间(见上)。matcher MUST 排除 dsh 的 subprocess runner 与 PTC 子进程(见上表)。注入之前就在跑的 agent 一直透传,直到它重启;`status` / `doctor` MUST 逐个报「运行中但未信任」及原因,判定写成 `flows/` 的事件(`agent-untrusted`,每个 pid 与原因一条;之后转为信任时一条 `agent-trusted`,进程退出时一条 `agent-exit`;exec 成不匹配特征表的程序、或重判时抛错,该 pid 同样离开进程表,同样一条 `agent-exit`(`via` 为 `exec` / `judge-error`;退出与 rescan 发现已不在为 `exit` / `rescan`),它的条件与负缓存条目随之清掉,D38),由看板显示(D38):入口缺失或被改走;入口指向的 `asight-ca.pem` / 合并包缺失、读不出或不含 asight CA;配置文件读不出或解析不了(读不出与「不存在」分开报);插件入口没有标记而原因推不出(写 `no-marker`,不冒充别的原因);进程早于注入(Codex app-server 守护进程在 `.env` 块写入之前就已启动;OpenCode serve、multiplex 模式的 Hermes gateway 同理);被遮住(CC:仓库层、managed 层、Desktop 启动环境;Z-Code:`ZCODE_AGENT_CA_CERT`(空值也算)、桌面设置 `httpProxyCaCertPath`、项目文件;Hermes:managed 层 `/etc/hermes/.env`(或 `$HERMES_MANAGED_DIR/.env`)里的 `SSL_CERT_FILE`、release 构建上的 `HERMES_CA_BUNDLE`;Codex、Hermes:安装后用户在同一 `.env` 里又加、且按该解析器的规则后读生效的同名键);dsh 的 Node 低于 22.19 或在 `--use-openssl-ca` 下;Kimi 没经 shim 启动,或是 npm 装的(不装 shim),或装 shim 的前提不满足(没有 `~/.kimi-code/bin/kimi` 或安装器那行 PATH)。只有部分连接透传的也报:OpenCode 开着 `ws` 路径时,它的 API host 透传(见下)。
- **不经信任路径**(D37④):同一个已信任的进程里,有的连接不走被注入的那条路,仍用默认根:Z-Code 策略 fetch 以外的 `globalThis.fetch`(如下载 provider release);OpenCode 插件加载之前的请求(如 models.dev)与 `ws` 路径。这些连接 MUST 透传、不解密,解密策略是 `all` 时也一样;否则客户端拒绝叶证,agent 的请求断掉。harness 文件以数据声明这些 host,具体有哪些由实验室 ②、⑥ 定。和信任路径共用 host 的(OpenCode 的 `ws` 路径与 fetch 去同一个 API host,按 host 分不开):resolver 认出该进程开着 `ws` 路径时,这些 API host 对它一律透传,`status` 报「未采 · ws 路径不经插件」;怎么从进程外认出由实验室 ⑥ 定,没认出时的后果见 §引擎 第 5 步「负缓存」。
- **CA**:v3 根证书(BasicConstraints CA:TRUE、KeyUsage keyCertSign、SKI),私钥 `~/.asight/collector/ca/ca.key`,属该用户、0600,无名称约束。CN 与旧 MITM 的 `atrace local MITM CA` 不同,MUST NOT 复用或覆盖旧的 `~/.asight/ca`(两张同 CN 的 CA 曾让 Desktop 断网)。叶证 P-256、有效期 199 天、回溯 2 天、带 AKI,每次守护进程启动生成一个内存中的叶证密钥,按 SNI 缓存。CA 装好后永不轮换(agent 只在启动时读一次;有效期与私钥被偷的后果见上「信任面」,要不要轮换见 OPEN)。守护进程启动时核对 CA:两个文件都读得出、私钥与证书配对(签一张探针叶证、用 CA 公钥验)、在有效期内;不过关就不挂钩(agent 照常直连;那段时间也就没有元数据行,由条件「CA 不可用 · 自 T 起」代替),在 `flows/` 留失败事件(`code:'ca-invalid'`,哪个文件、errno 或哪一项不符),`status` 与看板报「CA 不可用」,MUST NOT 报成「未安装」;之后每天再核对一次,不过关同样记。某次核对由不过关转为过关(私钥放回、证书换好)时,守护进程按这次读到的 CA 重建叶证签发者与信任核对,写一条状态事件 `ca-ok`,条件「CA 不可用」随之消失,此后 `on` 才挂得上;不重建的话,`status` 说 CA 可用、`on` 挂上了,引擎却仍拿启动时那个签不出叶证的签发者,每条解密连接都按 `leaf-error` 让路(D38 审查 D1-2)。叶证缓存按 `notAfter` 换新,不发过期叶证(D38)。MUST NOT 装进任何系统级或用户级信任库。

## 特权助手与按用户运行(D36)

- **按用户运行**:守护进程以安装它的用户身份运行,不是 root,也不换账号(D32⑦ 的专用账号 `asight-engine` 已被 D36 撤回)。CA、期望态、采集、安装清单都在该用户的 `~/.asight/` 下。同一台机器上每个系统用户各装一套,各自只认自己 uid 的 agent 进程。
- **特权只在助手**:能力助手(上文的 redirector)是唯一带特权的部分。每台机器一次 `sudo` 安装,助手升级后再一次;日常开关和采集不要密码。本机所有用户都能执行它,但它只对调用者自己 uid 的进程生效,与 [5.1](5.1-intervention.md) §安全边界「自己机器上、自己账号下」一致。
- **守护进程不绕回自己**:它与 agent 同 uid,`connect4/6` 改按 tgid 排除它自己的连接(验收 S11)。
- **代价(如实写明)**:被测 agent 与守护进程同 uid,所以 agent 读得到 CA 私钥、能 ptrace 守护进程、能改或删采集文件。D31 原先用「私钥只有 root 可读」弥补「CA 不加名称约束」,这条不再成立。现在接受它的理由:这张 CA 不在任何信任库里,只有本用户被注入的 agent 进程及其子进程信任它(D37④ 只经按 harness 的入口注入、不写登录环境,这一前提成立,见 §身份与信任「信任面」);私钥被偷的后果,如实写明(更正 D36 原先的「私钥被偷只帮得上同 uid 的代码」):任何同 uid 的代码都偷得走,包括被注入的 agent 自己;偷走后,网络路径上的攻击者(中转站、不可信的网络)在 CA 有效期内(当前实现默认 10 年)能对被注入的 agent 及其子进程冒充任意 host,受益的不止同 uid 的代码。没有轮换,唯一的恢复是卸载再重装、这些进程各重启一次;要不要恢复轮换、缩短有效期未定(OPEN)。助手是带 file capabilities 的 exec,内核把它标成不可 dump,agent 不能 ptrace 助手。
- **残余风险**:助手对本机所有用户可达,别的用户可以占满根 cgroup 上每个挂点的程序名额(内核上限 64 个),让其他用户的采集挂不上钩(fail-open:agent 照常直连,只是没采到;状态按内核实际态如实报告)。共用 `127.0.0.1` 的看板 / API 与 D26 控制端点不隔离用户:别的用户读得到采集,开了 `--control` 时还能改开关;所以 [4.4](4.4-server.md) 转接本守护进程控制面的入口在按用户隔离落地前 MUST NOT 上线(见 §控制面、[4.4](4.4-server.md) OPEN)。

## 安装清单与卸载(必须干净 · 见验收 S10)

安装分两级,卸载只按安装清单删,不按猜测删:

- **按用户**(不要 sudo):清单 `~/.asight/collector/install-manifest.json`,如实列出 asight 为该用户创建了什么:目录、文件、改过的每个信任入口文件(见下面的「信任入口的日志与撤销」)、asight 自己建的信任入口文件(dsh 的插件目录 `~/.asight/collector/plugins/dsh/`、OpenCode 的插件文件 `~/.config/opencode/plugins/asight-ca.js`、Kimi 的 shim `~/.asight/collector/bin/kimi`)、用户级自启单元。`asight uninstall` 只撤这一级。
- **整机**(sudo,一台机器一次):只有能力助手,装在 root 所有、各用户可执行的固定路径(路径见 OPEN)。整机清单就是这张固定路径表,另一步 sudo 移除只删表里的路径;移除前报告本机还有哪些用户的实例在用它。

1. 按用户卸载的顺序:停守护进程(助手随之退出)→ 确认本实例的 bpf link 已消失 → 按下面「信任入口的日志与撤销」的五步撤信任 → 停用并删除用户级自启单元 → 删 CA 私钥与运行时目录(含信任标记目录);CA 目录等保留下来的合并包都删掉之后才删。
2. 一个用户卸载,不影响同机其他用户的实例。
3. **采集数据属于用户**:卸载默认保留,只有显式的 `--purge-data` 才删(v0 的 `atrace-uninstall` 曾连采集一起 `rm -rf`,不再重演)。`flows/`(连接行与失败事件)算采集数据,同样保留;卸载自己的失败记录在 `--purge-data` 删完之后才写,所以卸载之后仍查得到装卸时出了什么错(D38)。
4. 幂等,且对安装到一半的状态安全:连跑两次、或安装中途崩溃后再卸载,都成功且不留残余(保留下来等进程退出的合并包、OpenCode 的 npm install 残留,以及第 5 条里撤不掉的入口、它指向的合并包与安装清单除外,见下)。安装清单先写后改(见下「日志」);它记的每一项(包括保留下来的合并包)都撤净之后,才删清单本身,所以第二次卸载仍找得到第一次留下的东西。
5. **安装 / 卸载不静默(D38)**:安装与卸载的结果和每一条警告(某入口写不进或撤不掉、「已撤销,但不逐字节相同」「早已还原」、「重启前仍信任」的 pid、保留下来的合并包、没并进合并包或 `extra-cc.pem` 的用户 CA 块及其类型与所在文件)除了打印,MUST 写成 `flows/` 的事件(`install-note` / `uninstall-note`;出错写 `failure`),看板显示上次安装 / 卸载留下了什么。每次安装 / 卸载最后都写一条结果行(`kind:'result'`,带 `outcome` 与计数;没有警告的干净卸载也写,失败时 `outcome:'failed'`),同一次运行写的每一行带同一个 `run`;看板取最新一行的 `run` 作「上次」,所以一次干净的卸载不会让上一次的警告冒充「上次」(D38 审查 D1-5)。有一项没撤掉(入口文件已解析不了、路径成了链接)时:卸载退出码非 0,安装清单留着(下一次卸载还要找它);那个入口若是替换语义,它指向的合并包按「撤销顺序」第 2 步改写成去掉 asight CA 的同一份并保留,否则 agent 下次启动就断网;`asight-ca.pem` 照常删(追加语义的 agent 缺文件只告警,留着反而让它继续信任 asight CA)。事件写不成时退到 stderr,不因此中止卸载;`--purge-data` 而且全部撤净时,提示只打印、不写进 `flows/`(采集器目录什么都不留;有残留或失败时照写,写在清除之后);还没有采集器目录时(没装过、以 root 拒绝)只在命令输出里报。

**信任入口的日志与撤销(D37④ · 标记好认好卸、安装先列文件,不整文件回滚沿用 D28;下面的日志字段、撤一个文件的规则、五步顺序、判活与先写后改按调研定)**

- **日志**:安装清单里,每个改过的文件一条 `{path, existed_before, mode, pre_sha256, post_sha256, ops, prior_value, installed_at}`。`ops` 是一串 splice `{offset, removed, inserted}`:最上面的块是一个;注释掉用户的同名键行(见 §身份与信任「同名键」)或替换 JSON 里用户原有的值是另一个,它的 `removed` 只会是 asight 管的那个键的行或值,是路径,不是密钥。`prior_value` 只在 asight 换掉了用户原值时有,它是一个路径,从不是密钥。**MUST NOT 复制用户文件**:Codex 与 Hermes 的 `.env` 里有 API key。合并包与 `extra-cc.pem`、`extra-kimi.pem` 只取用户 CA 文件里的证书块,不算复制(见 §身份与信任「合并包」)。**先写日志再改文件**:每改一个文件之前,先把意图(`path`、`existed_before`、`pre_sha256`、要做的 `ops`)写进清单并 fsync,改完再补 `post_sha256`;安装中途崩溃留下的「只有意图」的条目,卸载照样找得到。清单另记 OpenCode 那次 npm install 可能写的路径装之前在不在(见 §身份与信任)。
- **撤一个文件的规则**(第 1 步与第 4 步的每个文件都按它,包括 dsh 的 patch 文件和 shell rc):
  - sha 等于 `pre_sha256`(`existed_before` 为假时:文件不在):已经是安装前的样子,跳过,报「早已还原」;第二次卸载走到这里,MUST NOT 误报「不逐字节相同」。
  - sha 等于 `post_sha256`:反向做 `ops`(`existed_before` 为假就删掉该文件和 asight 建的目录),再断言 sha 等于 `pre_sha256`,这是逐字节还原。
  - 只有意图、没有 `post_sha256`(安装中途崩溃):sha 等于按 `ops` 算出的结果,就同上反向做;否则走下一条。
  - 其余(用户在安装后改过它,如 `hermes config set`、Z-Code 的设置同步、CC 自己重写 settings、用户在 rc 或 patch 文件里加了行):只去掉 asight 的块、行,或仍是 asight 值的那个键,把注释掉的用户同名行恢复原样,还原 `prior_value`,报「已撤销,但不逐字节相同」;asight 以外的内容逐字节不变。asight 建的文件里只剩 asight 的骨架(空文件、空的 insert 列表)时删掉整个文件(dsh 遇到空 patch 文件起不来);还有用户的内容就留着。
  - MUST NOT 用整文件快照回滚(D28)。
- **撤销顺序**:
  1. 按上面的规则撤 CC、Codex、Z-Code、Hermes 的配置入口。
  2. 把每个替换语义的合并包改写成「去掉 asight CA 的同一份」:Node 根、OS 根、并进去的用户 CA 都留着,在跑的进程下次重读时照样连得上用户自己的代理或中转站。还有加载过它的进程活着,就保留并报告这些 pid,再跑一次卸载时按同一判据重判,没有了才删。合并包在却读不出(ENOENT 以外的错误,如 EACCES、EIO)时没有被改写,仍含 asight CA:这是没撤掉的一项,不是「已不在」——`failure` 事件带 errno,结果行 `outcome:'left'`,退出码非 0,安装清单留着;有进程可能加载过它时保留并报「仍含 asight CA」,MUST NOT 说成「去掉了 asight CA」;没有进程用它就照删(收尾审查 RV-2)。**判活不靠守护进程,也不靠入口文件**(此时守护进程已停、入口已撤,都不再指向合并包),只看安装清单与 `/proc`:本 uid 有一个活着的进程满足任一条就算——(a) 匹配 harness `<h>` 的特征表,且启动时间晚于该入口的 `installed_at`;运行中会重读入口的(Z-Code 每个新 session、Hermes 非 multiplex 的 gateway 每轮、CLI 的 `/reload`)不看启动时间,活着就算;(b) `/proc/<pid>/environ` 里有该合并包的路径(从 agent 继承了它的子进程)。提前删的后果:Z-Code 每次调用都抛错,Hermes 的 Anthropic 客户端构造时抛错,Codex 的 WebSocket 卡住、之后回落 HTTP。用户自己把别的设置(如 Z-Code 桌面的 `httpProxyCaCertPath`)指向了 asight 的文件时,同样保留并报告,asight 不改那个设置。
  3. 删追加语义用的 `asight-ca.pem`,以及第 1 步撤掉 CC 入口之后的 `extra-cc.pem`、Kimi shim 指向的 `extra-kimi.pem`(Node、Bun、CC 遇到缺文件只告警;插件按 §身份与信任 插件第 6 条什么都不做)。
  4. 删 Kimi 的 shim 与 shim 目录,按上面的规则撤 rc 里的 PATH 行;按上面的规则撤 dsh 的 patch 行,删插件目录 `~/.asight/collector/plugins/dsh/`;删 OpenCode 的插件文件 `~/.config/opencode/plugins/asight-ca.js`。OpenCode 那次 npm install 写的文件只报不删(见 §身份与信任)。
  5. 报告在跑的进程,MUST NOT 重启任何进程:追加语义的入口(CC、Kimi shim、dsh / OpenCode 插件)只在启动时读,报「重启前仍信任」;Codex 下次建 HTTP 客户端或 WebSocket 连接、Linux 上 main 构建的 Hermes 下次握手时重读合并包,第 2 步之后从那一次起不再信任 asight,照此报告;Z-Code 新建或恢复的 session 起不再信任,进行中的 session 用的是缓存的 PEM,结束前仍信任;没证实会重读的(Hermes 的 release 构建与读不到 install stamp 的、macOS)按「重启前仍信任」报。只报可能读到过入口的进程:匹配该 harness,且启动晚于该 harness 入口的 `installed_at`(运行中重读入口的同第 2 步,不看启动时间;CC 也算:安装前就在跑的 CC 在新连接上已用上 settings 里加的值,实验室 ④);Kimi 只报 environ 里 `NODE_EXTRA_CA_CERTS` 指向 asight 文件的(经 shim 启动的)。每个报出的进程在 `flows/` 留一条 `uninstall-note`(`code: still-trusting`);`--purge-data` 时 `flows/` 随采集一起删,不留(此时 CA 私钥已删,仍信任它的进程没人能冒充)。

原 OPEN「采集文件归属」由 D36 解决:守护进程以用户身份写 0600 文件,满足 [4.1](4.1-capture-sources.md) 的「除属主外无人可读」。

## 开关语义(必须精确,见验收 S 组)

| | 开(`on`) | 关(`off`) |
|---|---|---|
| 内核 | 本实例的 `connect4/6`、`sockops` 三个 link 已挂,返回前确认 | 本实例的三个 link 已摘,返回前确认;`exec/exit` 跟踪不摘(只维护进程表,不碰流量) |
| 新连接 | 被判定解密的 agent 进程的新连接全部经过引擎 | 一律直连,agent 看到的是上游真实证书 |
| 已有连接 | 开之前建立的直连不受影响,也不采集 | 开期间建立的连接继续由引擎原样中转直到关闭(TCP 连接无法中途改道),但 `off` 返回之后才开始的请求不再记录 |
| 记录 | 每次请求 / 响应一条信封 | `off` 返回之后才开始的请求与 WebSocket 调用零记录;之前开始的照常记完(见上行与 §传输与帧级记录「开关」) |

- 状态 MUST 来自内核实际态(redirector 按本实例自己的 link id 读 link 信息,同机其他用户的 link 不算),不来自自己记的标志;期望态与实际态不一致时如实报告。每次开关、挂钩 / 摘钩失败都写成 `flows/` 的事件;不一致不靠有人跑 `status` 才发现:守护进程每 5 s 核对一次期望态、内核实际态与内核侧计数,变了就写事件,看板据此显示「采集关 · 自 T 起」或「期望开、内核未挂」;同一次核对还看每个已信任的在跑 agent 赖以信任的那个文件(inode、大小、mtime)变没变,变了就按 §确认信任 重判,转为未信任时 `agent-untrusted` 另带 `cause:'entry-changed'`(只会收回信任:在跑的进程会不会重读那个文件因 harness 而异,判不准就按未信任)。期望态文件读不出(不是「不存在」)时按 `off` 起,但 MUST 留一条失败事件说明,不悄悄变成 `off`(D38)。
- 幂等:重复 `on` / `off` 无副作用。期望态写进操作者目录,守护进程重启后按它恢复。
- 状态里给出每个 agent 进程「仍在直连、因此没被采集」的连接数(从 `/proc/<pid>/fd` 对 `/proc/net/tcp*`),让「为什么开了还没采到」可见;读不到(`EACCES`、`hidepid`)时报「不知道」与 errno,MUST NOT 报 0(D38)。

## 记录(D10 信封 · 只追加字段)

一次请求 / 响应一条信封,写到 `~/.asight/collector/capture-<日期>.ndjson`(0600,属操作者)。`<日期>` 是写出这条信封时的 UTC 日期,不是请求开始时间(`ts` 照旧记在信封里):信封在调用结束时才写,跨午夜的调用因此进新一天的文件;时钟不回拨时,前一天的文件过了午夜不再追加,写者在新一天第一次写出时关掉前一天文件的 fd;[4.2](4.2-storage-etl.md):49 按 session 计记录数的 watermark 要的正是「早的文件不在晚的文件之后再长」。新字段全部追加在 `req_body` 之后(分片器从首个 `"req_headers":{` 扫到 `"req_body"` 取 session id):

- `capture:'transparent'` · `host` · `scheme` · `dst`(原目的地 ip:port)· `proc:{pid, exe, agent}` · `flow_id` · `seq`(连接内第几次请求;WebSocket 上是第几次逻辑调用;记与不记的都计数,所以 `seq` 有空号说明那几次没记下(`off` 期间开始,或没写成);升级请求本身不成信封,`101` 之后第一条逻辑调用沿用升级请求的号,之后的调用接着这条连接的计数往下排,同一 `flow_id` 上不重号,也不因升级多出空号)
- `req_head_raw` / `resp_head_raw`:请求行 / 状态行加头部的原始字节(latin1),重发据此逐字重建;`resp.headers`
- 响应体逐字:解压后的原文(SSE 原始帧不再丢 `event:` / `id:` / 注释),跨 chunk 的多字节 UTF-8 用 StringDecoder 拼接
- **`raw` 就是线上字节,不是一个有损的读法**(审查 2026-10-07 发现两处违反,已修;不变式 2):文本的 BOM 保留(`TextDecoder` 不加 `ignoreBOM` 会把 12 字节的回复存成 9 个字符,没有标注);不是合法 UTF-8 的 SSE 流存 `raw_b64`(此前存了带 U+FFFD 的 `raw`),不是合法 UTF-8 的 JSON 回复也不再解析(此前经 U+FFFD 解析成一个有损的 `body`),存 `kind:'text'` + `raw_b64`;`raw_b64` 的 SSE 与文本一样被读取侧标「响应体不是 UTF-8 文本」。旧采集的 `bodyResp` 同一规则。JSON 回复仍存解析后的对象、不是线上原字节,那是 [4.1](4.1-capture-sources.md)「保真边界」⑤,未定(见 4.1 Extensions)。守卫:`test/collector/core/body.test.mjs`(两条)、`test/capture/response-body.test.mjs`(新旧两条路径同形)。
- 体不完整时就地标注(不变式 4):每个方向的体最多存 64 MiB(引擎 `maxBodyBytes`),超出只存前缀。响应体超上限标 `resp.truncated:true` + `resp.body_bytes`;响应没收完(上游断开、中止)时信封 `error:true`,收到的部分在 `resp.partial` 下。请求体(`req_body` 是字符串,无处内嵌标记)在信封顶层标:超上限标 `req_truncated:true` + `req_body_bytes`(存下的前缀字节数,即上限,不是线上体长);请求体没收完信封就写出时标 `req_partial`,取值 `'early-response'`(请求体传完前上游已给最终响应,如 413 / 401)、`'aborted'`(连接中止)、`'framer-error'`(请求分帧出错)。两类标注可同时出现;完整的请求不带这些字段
- 改包相关:只在发生干预时多一个 `intervention` 字段(含 `origin`、字节补丁 `edits`、`base_sha256` / `result_sha256`),没有干预的信封不带它;形状见 [5.1](5.1-intervention.md) §记录与标注
- `transport`:只有 WebSocket 信封带(`'ws'`)。不带 `transport` 的信封就是 HTTP,HTTP 信封不加这个字段;ETL 把缺省读成 `calls.transport='http'`([3.2](3.2-normalized-model.md))
- 压缩的请求体(D40 起对一切端点,不再只对 LLM):`req_body_b64` = 线上压缩字节,`req_content_encoding` = `content-encoding` 头原文;解出来时 `req_body` = 解压后的文本;解不出时(zstd 一律如此,见 §传输与帧级记录)`req_body:null` + `req_encoding_error`,读取侧按 `req_content_encoding` 自己解 `req_body_b64`,解不出才标。解压后的字节不是合法 UTF-8 也算解不出(`req_body:null` + `req_encoding_error`,不存有损的文本)。请求体本身不全(`req_truncated` / `req_partial`)时采集端不解码、不带 `req_encoding_error`:`req_body:null`,`req_body_b64` = 已收到的线上字节,不全由 `req_truncated` / `req_partial` 说明。WebSocket 信封也用 `req_body_b64`,装的是不是 UTF-8 文本的首条客户端消息(解压后的消息字节),不带 `req_content_encoding`(见 §传输与帧级记录)
- **压缩请求体的解码上限**(D40 起任何 host 都能发压缩体,原来只有推理端点会):采集端与读取侧各自解码,**推理调用**解压后上限 256 MiB(原有,此前只写在实现笔记里),**不是推理的调用**上限 1 MiB(`NON_INFERENCE_MAX_DECODED_BYTES`,`src/capture/request-body.mjs` 与 `src/dissect/request-body.mjs` 两处同一个数,看板对一个体也只显示 1 MiB)。超出时不解码、不丢字节:`req_body:null`,线上字节照旧在 `req_body_b64`,采集端写 `req_encoding_error`(「decoded body over the N-byte capture limit …」),读取侧在 `_reqBodyDecodeError` 里写同样的话,看板就地标「压缩请求体未解码」(不变式 4)。原因:204 KB 的 gzip 能解成 200 MiB 的 `req_body`,含大量转义时那一行 NDJSON 超过 V8 的字符串上限、整个调用采不下来;12 条 9 KB 的 zstd 记录在读取侧占了 2.4 GB 堆。取舍:超过 1 MiB 的非推理压缩体在看板上只显示「未解码」与字节数,字节本身(逐字的真相)都在,不丢;要放宽这个数是一行改动。守卫:`test/capture/envelope.test.mjs`「a compressed body that decodes past 1 MiB on a call that is not inference …」、`test/dissect/request-body.test.mjs`(两条:一条看内存,一条走 `readRecords`)。
- 不完整的标注,各说一件事:顶层 `partial` / `partial_reasons` = 这条连接更早的消息缺了,缺的是上下文,本信封的字节是全的;`ws_truncated` 与 `ws_raw` 里没留载荷的帧 = 本信封的字节不全;`req_encoding_error` = 字节是全的(在 `req_body_b64`),只是采集端没解码。HTTP 上本信封字节不全另用 `resp.partial`(响应没收完)与 `req_truncated` / `req_partial`(请求体),和顶层 `partial` 不是一回事。读取侧与看板 MUST 就地标「不完整」「已截断」「压缩请求体未解码」「非逐字」(不变式 4)。**这些标注与顶栏的 ⚠ 是两回事**:标注逐调用、就地显示,说的是**这次调用**缺了什么;顶栏只看失败类事件(下面「失败不静默」与验收 F5):WebSocket 上解不出、写失败、因出错丢了数据消息是失败类、顶栏 ⚠,64 MiB 上限处的截断是预期类、只有标注。
- **请求体与保存级别(D40)**:
  - 请求体规则对一切调用相同,唯一实现在 `src/capture/envelope.mjs`:合法 UTF-8 → `req_body` = 原文字符串;不是 UTF-8 且未压缩 → `req_body:null` + `req_body_b64`(线上字节,不带 `req_content_encoding`;与 WebSocket 非文本首条消息同一约定);压缩 → 上条。追加字段 `traffic_class`、`body_wire_bytes`、`body_retention`(定义见 [4.1](4.1-capture-sources.md) §统一原始信封 D40 行);`host` 本节已有。

**失败不静默(D38 · ;下面的落点与字段)**:

- **连接行**:字节没逐字记进信封的每一行 MUST 带 `not_captured`,取值是闭集,分两类。失败类(出了错才没采到,看板指示据此变 ⚠):`untrusted`(附 resolver 原因)· `untracked`(内核报了、守护进程的进程表里没有)· `client-rejected-leaf` · `negative-cache`(`reason` = 写入它的原因)· `upstream-cert`(`reason` = Node 的校验错误码)· `upstream-handshake`(上游用 alert 拒绝了引擎自己的握手,多半是要客户端证书;`reason` = Node 的错误码,D40 审查)· `leaf-error` · `h2`(只给 h2;只在本会解密的 host 上标)· `malformed-hello` · `ws-not-recorded`(只在 WebSocket 旁路接线之前)。预期类(按设计不采,计数、列出,不变 ⚠):`policy`(解密策略外的 host)· `not-trust-path` · `https-proxy`(`own:false`)· `proxy-refused`(代理回了非 2xx,原样转回)· `upstream-first` · `unknown-protocol`(附首字节)· `upgrade-not-followed`(非 WebSocket 的 101、隧道内 CONNECT 2xx 之后不再分帧)· `error`(决定之前就断开、超时、网络失败;另带 `error = {type, message, side}`)。判据(测试照此扫全部连接行):`decision` 不是 `decrypt`(隧道看内层决定 `inner`),或客户端拒绝了叶证 ⇒ `not_captured` 在闭集里。解密了、但有信封没写成的行带 `write_failed`(次数)。QUIC、AF_UNIX、WebRTC 到不了引擎,没有连接行,按进程写成事件行(`agent-transport`,见 §事件与码的名字)。
- **连接行的细节**:每条连接的「未采」与解密失败只记在它自己的连接行里(`not_captured` / `reason` / `error`),不再写一遍事件行;事件行收两类:没有连接行可挂的失败,和 asight 自身出错。`h2` 行带 `reason:'alpn-h2-only'`;引擎按值计数,见 `engine.stats().notCaptured = {h2, httpsProxy, upstreamCert, negative, leafError}`。连接两侧任一 socket 出错(含路由决定之前:连不上上游、与上游握手失败、客户端复位),该连接行带 `error = {type, message, side:'client'|'upstream'}`(第一个错误);引擎自己收尾的(`engine_error`、首字节超时)`side:'engine'`。`handleFlow` 同步抛错时同样写 `decision:'error'` 的连接行与带 `flow_id` 的 `engine-error` 事件。连接收尾时还开着的 HTTP 交换以该连接的第一个错误写出,没有错误时才是 `{type:'ECONNRESET', message:'flow closed'}`。`bytes_up` / `bytes_down` = agent 在它自己那条连接上发出 / 收到的线上字节数:含 CONNECT 等代理前导,解密的连接按 TLS 记录(密文与握手)计,与透传的连接同一口径。
- **连接行怎么落码**:按连接的走向,先命中的为准:进程没确认信任(`meta.decrypt` 为假)→ `untrusted`(`reason` = resolver 的原因,由守护进程给);ClientHello 解析不了 → `malformed-hello`;解密策略不命中 → `policy`。守护进程的 `policy(meta, host)` 能说得更细时不返回 `false`,改返回 `{not_captured, reason}`,引擎只认三个码:`not-trust-path`(该 harness 声明的不经信任路径)、`untracked`(内核引来的 pid 不在进程表里:已退出、被重扫删掉)、`untrusted`(表里有、未信任,带 resolver 原因);别的值一律记 `policy`。`policy()` 对未信任进程抛错时照记 `untrusted`,另写 `engine-error`;命中负缓存 → `negative-cache`;只给 h2 → `h2`;上游先说话 → `upstream-first`;首字节认不出(含隧道里又见 CONNECT / SOCKS 前导)→ `unknown-protocol`,`reason` = `first-byte 0x<hh>`(ClientHello 的 ALPN 既无 `h2` 也无 `http/1.1` 时同记此码,`reason` = `alpn <列表>`);代理回了非 2xx → `proxy-refused`,`reason` = `proxy-status-<码>`;明文 HTTP 同样按 `untrusted` / `policy` 落码。解密了的连接上 HTTP 分帧出错(之后的字节不再分帧、不再记录)→ 行上带 `framer_error = {side:'request'|'response', message}`,同一件事另有 `framer-error` 事件;非 WebSocket 的 `101` 或 CONNECT 2xx 之后不再分帧 → 行上补 `upgrade-not-followed`,`reason` = 停在哪个回应(`101 <Upgrade 头>` / `CONNECT <状态码>`)。客户端拒绝叶证的行 `not_captured:'client-rejected-leaf'`,`reason` 同值,另带 `error = {type, message, side:'client'}`:引擎只看得到客户端怎么走的,看不到客户端自己的证书校验码(如 `SELF_SIGNED_CERT_IN_CHAIN` 只在客户端),所以 `type` = 引擎这一侧的错误码——客户端发来 TLS alert 时是它(如 `ERR_SSL_TLSV1_ALERT_UNKNOWN_CA`),复位时 `ECONNRESET`,不带错误地关掉(Node 客户端握手之后才查证书、不发 alert)时 `closed_without_app_data`(验收 F1(b) 的「客户端一侧的错误码」即此)。隧道(CONNECT、SOCKS、终结了外层 TLS 的 `https://` 代理)的行 `decision:'tunnel'`,隧道里的字节怎么走记在 `inner`(`'decrypt'` / `'splice'`),`reason` 只放原因;代理拒绝时没有 `inner`。路由决定之前一侧不带错误地关闭,记 `error = {type:'closed_before_decision', message, side}`;决定之前断开、首字节超时、引擎内部异常、网络失败(含引擎与上游的 TLS 握手出错)的行 `not_captured:'error'`。**首字节计时器**(5 s)只管到任一侧说出第一个字节为止;之后引擎等上游的 TLS 握手或代理回应不设时限,MUST NOT 因为等待而断开 agent 的连接(否则慢的上游或代理会让 agent 断网,违 D31 fail-open);等过 5 s 写一条 `upstream-slow` 事件,连接照常。
- **代理前导**:CONNECT 与 SOCKS4 / 4a / 5 连接的行带 `prelude = {kind:'connect'|'socks4'|'socks4a'|'socks5', target, client_b64, proxy_b64}`:两个方向的前导逐字字节(含 `Proxy-Authorization` 与 RFC 1929 用户名密码,属凭据,`flows/` 文件 0600,见 [4.1](4.1-capture-sources.md) §凭据处置),`target` = 前导里的 `host:port`。引擎按消息读前导的副本,每条消息收全才原样、按序转发,从不替代理回答;客户端不等回应就把后续消息一起发来时,后面的消息等代理答完前一条再转。代理拒绝(SOCKS4 回应码不是 90、SOCKS5 回应码不是 0、认证失败、没有可接受的方法)→ `not_captured:'proxy-refused'`,`reason` = `socks4-reply-<n>` / `socks5-reply-<n>` / `socks5-auth-failed` / `socks5-no-acceptable-method`,拒绝原样转回客户端。引擎不跟的部分(GSSAPI 等别的认证方法、BIND / UDP ASSOCIATE、不是 SOCKS 的字节)从那里起整段透传,`not_captured:'unknown-protocol'`,`reason` = `socks4: …` / `socks5: …`;已转发的前导照记。某条前导消息只到了一部分、之后 5 s 没有新字节(首字节恰是 0x04 / 0x05 的别的协议在等对端):同样按不跟处理,攒着的字节原样转出,`reason` 含 `incomplete`,引擎不替任何一方扣住字节。一条消息收全、已转出,引擎等对端回答时还扣着另一方多发、尚未转出的字节,而对端 5 s 没有新字节(别的协议的开头恰好读成一条完整的 SOCKS 消息、对端在等其余字节;或急性子客户端遇上 5 s 不答的代理)同样如此:按不跟处理,两个方向扣着的字节都原样、按序转出,`reason` 含 `incomplete`;扣着的字节不因对端之外那一方继续发字节而一直等下去。等对端回答时什么字节都没扣着,仍按上条「首字节计时器」不设时限、只记 `upstream-slow`。前导没走完连接就断了时,行是 `error`,不带 `prelude`。`target` 里的 IPv6 地址用压缩写法加方括号(`[::1]:443`),与 CONNECT 的写法一致。CONNECT 被拒(非 2xx)后客户端在同一连接上再发 CONNECT(如 `407` 之后带 `Proxy-Authorization` 重试):照第一个一样跟,拒绝的回应体照转;`prelude` 记全部前导往返(每个方向按时间顺序拼接),`not_captured` / `reason` 按最后一次的结果。代理回成功时与回应同一块到的上游字节,算上游先说话(`upstream-first`)。
- **`https://` 代理**(落实 §引擎 第 3 步):守护进程经 `describe()` 的 `FlowExtras.proxies = [{scheme, host, port, own, source}]` 给出该进程的代理表(`own` = 取自该进程自己的代理配置,`source` = 出处,如 `env:HTTPS_PROXY`)。直连(不在隧道里)的 TLS 连接,表里 `scheme:'https'`、host 与 SNI(无 SNI 时原目的地址;不分大小写)一致、端口与原目的端口一致的条目就是它的代理,行上带 `via_proxy = {scheme:'https', host, port, source, terminated}`。终结外层 TLS 的条件:`own:true`(属 `auto`,解密策略不命中也终结),或解密策略命中该代理 host(如 `all`);另须满足第 4 步其余条件(进程已确认信任、ClientHello 可解析、ALPN、不在负缓存)。不终结时:`own:false` 且策略不命中 → `not_captured:'https-proxy'`,`reason:'proxy-not-own'`,计入 `stats().notCaptured.httpsProxy`;其余按没满足的条件落码(`untrusted` / `malformed-hello` / `negative-cache` / `h2`)。**解开之后**:任何被终结的 TLS(代理表里的,或解密策略命中、不在表里的,如 `all` 下的 `https://` 代理)都按客户端先说的字节再分流:是 `CONNECT` → 照第 3 步转发、记 `prelude`,行 `decision:'tunnel'` + `inner`,`via_proxy.terminated:true`(不在表里的 `source:null`);否则就是被解密的调用本身,照常交给交换记录。外层握手证书校验失败同第 5 步(让路、`upstream-cert`、进负缓存,之后同一代理的连接 `negative-cache`)。
- **事件行**:`{ts, event, where?, code?, reason, suppressed?, folded?, …}`。`event`、`where` 与 asight 自己起名的 `code` 是闭集,在 `src/health/codes.mjs` 一处定义,写者与读者都从这里取,测试核对写出的都在集里;Node 的 errno 照原样放 `code`;自由文本只进 `reason`。失败事件:信任未确认或启动后才改的配置(`agent-untrusted`,每个 pid 与原因一条)、asight CA 不可用(`ca-invalid`)、合并包缺失或重建失败、负缓存写入、助手退出(退出码或信号、助手 stderr 末几行)与出错、协议版本不符、挂钩 / 摘钩失败、心跳失败或两次心跳间隔超过 2 s、内核侧丢弃与放行的计数上涨(无监听、心跳过期、map 写失败、ringbuf 满)、期望态与实际态不一致、引擎的失败(`lookup-miss` / `loader-down` / `loader-timeout`、`describe-error`、`engine-error`、`leaf-error`、`flow-write-failed`、`system-roots-unavailable`、`upstream-ca-unreadable`、`trust-store-error`、`framer-error`、`unpaired-response`、`upstream-slow`)、WebSocket 记录器的失败(`write-failed` / `decode-failed` / `broken` / `recorder-error` / `pattern-invalid`,带 `flow_id`)、记录写不进去、期望态文件读写失败、安装 / 卸载出错、守护进程拒绝启动或上次没有干净退出。状态事件:`daemon-start`(pid、启动时间、boot_id、版本、是否前台运行)、`daemon-stop`(信号或原因;SIGHUP 即关终端或登出,按正常停止写)、开关的期望态与实际态、`agent-exit`、`agent-trusted`、负缓存清除、CA 恢复可用(`ca-ok`)、`install-note` / `uninstall-note`。能力助手死后不重启,`helper-down` 到守护进程重启为止一直成立。写法:`src/collector/core/events.mjs` 的 `appendEvent`,自己开描述符写,记录存储坏了也报得出;同一处同一 `code` 10 s 内只记一行,折叠了几次在窗口结束或停止时补写(负缓存写入除外,每次各成一行,见下「事件与码的名字」)。不另开目录:采集器的失败只写 `flows/` 一处。还没有采集器目录时(没装过、以 root 拒绝)只在命令输出里报。计时(心跳间隔、查表超时)用单调时钟;日文件只往当前这一天写,时钟回拨时不回头追加更早一天的文件。记录存储与守护进程的事件写者都按见过的最晚日期选文件;记录存储换日时先 fsync、关闭前一天的 `capture-*.ndjson`、`audit/`、`replays/` 日文件,再对它们调 `markClosed`(D35 关闭标记);记录存储建起时(守护进程启动)对日期早于当天、还没有关闭标记的这几类日文件同样先 fsync 再调 `markClosed`:上次停在前一天、这次在新一天起的守护进程不经过换日,不补的话那天的文件永远封存不了(那时没有别的写者持着它们:一个用户只有一个守护进程;D38);`flows/` 日文件另有事件写者自己开描述符写,不由记录存储关(是否封存仍是 OPEN)。记录存储每次写前比对描述符与路径的 inode,文件被改名或删除时重开、写一条 `code:'file-replaced'`(`where:'record'`,带 `file`),不往孤儿 inode 里写。

## 日志体积预算(D34 · 硬目标;格式 = D35)

asight 存在盘上的采集日志,体量 MUST 和被测 harness 自己留的会话日志在同一量级,不能大出一个数量级。实测动因(2026-10-05,作者机器):Claude Code 自己的 `~/.claude/projects` 约 1.5 GB,而 asight 的 `~/.asight` 约 70 GB——其中采集流 39.6 GB,另约 32 GB 是 `src/etl/shard.mjs` 拷出的按 session 副本(`~/.asight/sessions/*/calls.ndjson`)。大了约 45 倍,其中一份是重复副本。D35 的目标是每条记录只留一份长期副本,要等按 session 的布局定下才成立(见 [4.2](4.2-storage-etl.md) OPEN)。

**根因**:对话是追加式的,每次调用把越来越长的 `messages[]`+`tools` 整个再写一遍,一个 n 次调用的会话原始体积约 Σ 正比于 n²。DuckDB 侧早已按 `content_hash` 去重(见 [3.2](3.2-normalized-model.md):18),涨的纯粹是原始 NDJSON。

**手段 = D35 封存格式**(格式与封存器规则见 [4.2](4.2-storage-etl.md) §原始层封存):
- 活跃分片保持未压缩 `.ndjson` 追加写(`createEnvelopeWriter` 的 0600 + 每条 fsync 可见的崩溃安全不动),写的过程中 MUST NOT 被封存。
- **「已关闭」的判据**:写者已写出显式的关闭标记、fsync 并释放了 fd。MUST NOT 凭文件名里的日期或 mtime 推断——文件虽按写入时刻的日期选(§记录),换日后到新一天第一次写出之前,写者仍持着前一天文件的 fd,时钟也可能回拨。D35 之前写的文件没有关闭标记,走 [4.2](4.2-storage-etl.md) OPEN 里操作者显式触发的旧文件入口。
- 封存器属原始层(`src/raw/`),不在 `src/etl/`。MUST NOT 把记录字节搬出原始层放进外部 chunk store(源真相会变成两份、丢一份就全毁,违 [4.2](4.2-storage-etl.md):8/53);封存文件本身是 NDJSON 行字节的无损容器,不算搬出。
- 三个读者 MUST 能读封存文件:`src/query/source.mjs`(现在把压缩文件当 `compressed` 跳过,看板与 `asight etl` 报出但不读,`buildResolver()` 里的 `listFiles()`)、看板装载、ETL 读入。看板 loader 把整个 session JSON.parse 进内存的上限(877 MB 可开、2.4 GB OOM)是另一个已知缺口,封存解决不了;下面 E3 的随机读只覆盖 resolver。loader 读封存文件时 MUST NOT 把整个文件缓冲进内存。
- **选型已定(D35)**:brotli q9、lgwin 24、约 4 MiB 独立帧;不用外部 `zstd` 可执行。zstd(level 3、窗口 ≥ 2^22)是 Extension:不再支持 Node 20 后换用(实测更小也更快)。

**实测(2026-10-05,三个真实 Claude Code 会话分片 2.58 GB / 1.14 GB / 0.59 GB,共 15,185 条记录)**:
- 请求体占原始字节的 97.8–98.8%,响应 1.0–1.6%。
- 只压帧不够,帧要小到内存可控就压不下去:brotli q9 + 16 MB 帧 = 原始的 3.86 / 4.28 / 23.9%,但热读让 RSS 涨 286–374 MB;4 MB 帧单压只到 10–12%,在有 12.5 MB 单条记录的那个会话上是 24–38%。早先的 2.7% 是整个文件一个窗口,换成可随机读的帧后不成立。
- 单段拼接的增量不够(未压缩仍占原始的 37–50%):Claude Code 每轮挪动 `cache_control` 标记(扩展型记录里,字节公共前缀止于 `cache_control` 标记的有 7,033/7,154、1,358/1,426、543/547 条);相邻两条请求有 93–99.5% 改了 system 第 0 块(约 170 字节里改 47–68 字节),52–97% 改了顶层 `diagnostics` 字段;19–53% 的请求根本不是扩展(新线程、compaction),但它们和近期请求共享 system / tool 字节,只有 4–8% 成了关键帧。
- 选定配置(多段增量、链 ≤ 16、在前 32 条里找前驱、brotli q9 4 MiB 帧):原始的 2.74 / 2.28 / 5.26%(加权 2.96%)。唯一留有 Claude Code 日志的那个会话,原始是其日志(26.3 MB 含 subagent)的 43 倍,封存后 0.98 倍(只比主文件是 2.62 倍);实验的合计口径下,原始是 25 倍,封存后 0.74 倍。2.58 GB 分片上随机读:冷 p95 16.2 ms、热 p95 12.8 ms,RSS 冷涨 42 MB、热涨 159 MB。封存 13.9 s + 校验 1.6 s,峰值 RSS 317 MB。60 万次以上记录校验 0 不符。
- Codex 样本(经 HTTP 的 14 条记录)同样每次重发完整历史,`previous_response_id` 用了 0 次。

**D40 的体积影响(精确数可算,见第 2 条)**:
- 记录数上非 LLM 占 70 %(旧采集尾部 27,122 条中 19,067 条),但多数很小;按字节,上面实测里请求体占原始的 97.8–98.8 %,几乎都是 LLM 请求。

## 控制面

守护进程在 `$XDG_RUNTIME_DIR/asight/collector.sock`(0600,属操作者)上提供 JSON over HTTP:`status / on / off / agents / flows`,以及 [5.1](5.1-intervention.md) 的规则、扣留队列、重发。CLI `asight collector …` 走它;看板的设置面板以后经 [4.4](4.4-server.md) 服务端转接,继续带 D26 的 Host / Origin / CSRF 门。这些门挡浏览器,挡不住同机别的用户的本地进程;转接后他们就能替本用户设定改包规则、用本用户的凭据重发(违不变式 1)。所以在 [4.4](4.4-server.md) OPEN 的按用户隔离落地之前,这条转接 MUST NOT 上线,控制只走本 socket。看板显示采集健康不靠这条转接,只读盘([4.4](4.4-server.md) `/api/capture-health`),所以守护进程没在跑时看板照样说得出「没在跑 · 最后记录于 T」。保存设置([0.0](0.0-overview.md) D40⑥)不经本 socket:CLI 与看板直接写 `~/.asight/retention.json`,守护进程热读;看板写入走 [4.4](4.4-server.md) D26 opt-in 控制面的 `POST /control/retention`(同样的 Host / Origin / CSRF 门),不转接本 socket,所以不受上句「MUST NOT 上线」的约束——它改的是存什么,不会替用户设定改包规则或重发;同机别的用户能否改它,与 D26 的监测开关是同一个缺口,见 [4.4](4.4-server.md) OPEN。**`lock`**(`~/.asight/collector/lock`,0600;守护进程启动时写,正常停止时删):`{pid, start_time, boot_id, helper_pid, engine_port, socket}`,`start_time` 取 `/proc/self/stat` 第 22 字段,`boot_id` 取 `/proc/sys/kernel/random/boot_id`;守护进程每 1 s 刷新它的 mtime。读者(看板、`status`、卸载)只在 pid 活着、它的启动时间与 boot_id 都对得上时算「在跑」(pid 会被复用,重启后 lock 还在;与 §身份与信任 标记的启动时间核对同理);对得上但超过 5 s 没刷新算「没响应」(事件循环卡住、死锁);lock 读不出算「状态不明」并报出(D38)。
