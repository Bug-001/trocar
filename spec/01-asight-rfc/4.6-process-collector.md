# asight · RFC 4.6 — 按进程透明采集器(D31 落地 · Linux 先行)

> **状态**:设计已定(**D32**,2026-10-05;**D36** 同日修订:撤回专用账号,采集守护进程按用户运行,特权只在能力助手)。Linux 先实现、先在测试机上验收;macOS / Windows 只定接口,机制后补。
> **前置**:方向 = D31(按进程、agent 无感、不碰 base_url / 系统代理 / VPN);改包 = D30 + [5.1](5.1-intervention.md);信封 = [4.1](4.1-capture-sources.md) §统一原始信封(D10)。
> **取代**:落地并在本机验收后,[4.1](4.1-capture-sources.md) 的 base_url 反代、Clash steer、按 host 解密退役。过渡期两套并存,互不接线。

## Goal

每个系统用户一个常驻、稳定的采集守护进程,以该用户身份运行:认出该用户自己的 agent 进程,把它们的新连接引到本地引擎,解密、逐字记录,再原样转发。开关只改变守护进程自己的行为,agent 不重启、看不出差别。任何部件崩溃,agent 的流量都直接走原路(fail-open)。唯一带特权的部分是守护进程拉起的能力助手,每台机器 sudo 装一次(D36)。

## 结构:平台相关 / 平台无关 / harness 相关 分目录

仿 Linux 内核的 `arch/`:加一个平台只动 `arch/<os>/`,加一个 harness 只动 `harness/`。

```
src/collector/
  core/                 平台无关:引擎、记录、开关、控制面、改包
    engine/             接连接 → 查元数据 → 嗅探 → 解密 / 透传 / CONNECT 隧道
    http1/              HTTP/1.1 被动分帧(双向)、SSE 逐字
    tls/                CA 与叶证(node:crypto 自签,零依赖)
    record/             信封写入、flows / audit / replays 流
    intervene/          规则、扣留队列、重发(D30)
    registry.mjs        按 harness 描述匹配进程(本身不含任何 harness 名)
    switch.mjs          开关状态机(期望态 vs 内核实际态)
    control.mjs         本机控制面(unix socket)
  arch/linux/           eBPF 程序、C redirector(能力助手)、/proc 读取、用户级 systemd 单元(可选)
  arch/darwin/          (待写)Network Extension 透明代理
  arch/win32/           (待写)WFP
  harness/              每个 harness 一个文件:进程特征、信任注入方式、已知 API host
```

平台层对核心只暴露一个接口 `Redirector`:`attach() / detach() / status() / watch(pid, verdict) / unwatch(pid) / lookup(peer) → {dst, pid, agent} / heartbeat()`,外加进程事件流 `exec / exit`。核心不出现任何 `process.platform` 分支。

**特权钩子按 OS 各写一份,引擎侧契约到处一样(D36)**:内核钩子在每个 OS 上都要特权;钩子以上(引擎、记录、开关、改包)各 OS 相同。引擎只经 `src/collector/core/redirector.mjs` 的 `Redirector` 契约用钩子,这份契约各 OS 一样。Linux 上钩子是守护进程拉起、带 file capabilities 的能力助手(下文);macOS / Windows 上预计是 OS 托管的扩展 / 服务,引擎经本地通道接入,后设计。

## Linux 机制

**内核侧(`arch/linux/bpf/`,C + libbpf CO-RE)**

| 程序 | 挂点 | 作用 |
|---|---|---|
| `connect4` / `connect6` | 根 cgroup `cgroup/connect4|6` | 当前 tgid 在 `watch` 表且判定为「解密」、不是守护进程自己的 tgid、当前 uid(`bpf_get_current_uid_gid()`)等于本实例的 uid(存在配置 map 里)、是 TCP、和引擎同一 netns、引擎在听且心跳新鲜 → 把目的地改写到引擎端口,原目的地按 socket cookie 存进 `orig_dst`。在 `watch` 表但判定为「不解密」→ 不改写,只经 ringbuf 报 `{pid, 目的地}`,写进 `flows/`(D31「其余照常放行、只记元数据」)。uid 不符的一律不改写、不上报 |
| `sockops` | 根 cgroup | 连接建立时把 `orig_dst[cookie]` 连同 socket 的 uid(`bpf_get_socket_uid`)搬到按 (客户端源地址, 源端口) 索引的 `by_port`,供引擎 accept 后查;查到的 uid 不等于本实例 uid 就当查不到 |
| `exec` / `exit` | `tp_btf/sched_process_exec|exit` | 只处理本实例 uid 的进程,别的用户的事件在内核里丢掉。exec:先在内核里删掉该 tgid 的旧判定,再把 `{pid, filename}` 经 ringbuf 交给用户态重新判定;exit:删表项 |

exec / exit 用 `tp_btf`,不用经典 tracepoint:经典 tracepoint 要读 tracefs,得额外的 `cap_dac_read_search`,不在助手的三项能力里;`tp_btf` 不需要(实验室探测确认)。

**用户态(`arch/linux/redirector/`,C · 能力助手)**:由守护进程以子进程拉起。文件属 `root:root`、0755,只带 `cap_bpf,cap_net_admin,cap_perfmon+ep`,不设组、不 setuid;调用者 uid 就是助手自己的真实 uid(file capabilities 不改 uid)。内核在 exec 带 file capabilities 的程序时会清掉此前设好的 parent-death 信号(prctl(2)),守护进程在 fork 后替它设的不算数,所以助手启动后第一件事是自己调 `prctl(PR_SET_PDEATHSIG)`,再比对 `getppid()` 与 argv 传来的守护进程 pid,不符就退出;控制通道 EOF 是第二个退出条件。它持有全部 bpf_link,**不 pin**:进程一退,内核自动摘钩,agent 新连接直连(fail-open 的第一层)。它只做三件事:装卸程序、改表、按请求查表;不碰任何连接字节。它只装自己内嵌的 BPF 对象,MUST NOT 接受调用者给的 BPF 对象或文件路径;MUST 只对调用者 uid 的进程生效(uid 写进配置 map,内核侧逐次核对,见上表)。

**为什么不用 nftables / TUN**:nftables 的 REDIRECT 规则在守护进程死后仍在,连接打到死端口 = fail-closed;mitmproxy 的 TUN 方案要用户态 TCP 栈,Node 里没有。改写 connect 目的地 + bpf_link 自动摘钩是唯一同时满足「只碰 agent 连接」和「崩了就放行」的做法。

**fail-open 两层**:redirector 死 → 内核摘钩;引擎死 → 监听 socket 消失,`connect4` 用 `bpf_sk_lookup_tcp` 发现没人在听就不改写;引擎卡住 → 引擎每 500 ms 经 `Redirector.heartbeat()` 发心跳(助手写进内核表),`connect4` 只在心跳 2 s 内新鲜时改写;心跳由引擎发,卡住的引擎才会被发现。已经由引擎终结的 TLS 连接会随引擎一起断,agent 自己重试(Claude Code 对已开始输出的流不重发);这一点如实写进 UI 与审计,不假装能避免。

## 引擎(`core/engine/`)

每条被引来的连接:

1. accept 后立刻按对端地址和端口向 redirector 查 `{原目的地, pid, agent}`,同时向原目的地发起 TCP 连接。查不到(或 uid 不符)的连接没有原目的地可转,也不是本用户的 flow:直接关掉,不记录、不过改包规则。
2. 先到的字节决定走向:上游先说话 → 透传;客户端发 TLS ClientHello → 读 SNI / ALPN;发 `CONNECT host:port` → 走 CONNECT 隧道;发明文 HTTP 请求行 → 明文分帧。
3. **CONNECT 隧道**(agent 用 `HTTPS_PROXY` 指向 Clash 等本地代理时):把客户端的 CONNECT 原样发给原目的地(那个代理),把代理的真实回应原样转回,成功后再对隧道里的 TLS 做第 2 步判断。MUST NOT 自己合成 `200 Connection Established`。上游出口因此仍走用户自己的代理 / VPN。
4. **解密的条件(全部满足)**:该进程已确认信任 asight CA(见「身份与信任」)· ALPN 含 `http/1.1` 或未带 ALPN · 目标 host 命中解密策略 · 不在负缓存里。否则透传,只记元数据。
5. 解密时先和上游完成 TLS(SNI 与客户端一致,ALPN 定为 `http/1.1`,按系统根证书校验),再用按 SNI 现签的叶证和客户端握手。上游握手失败就关掉客户端连接,不替上游伪装成功。客户端以 `unknown_ca` / `bad_certificate` 拒绝叶证 → 记入负缓存 `(pid, host)` 并通知 redirector 对该进程停止改写,此后直连。
6. 解密后两个方向都走**被动分帧**:引擎转发的是收到的原始字节,分帧器只读一份副本来切出「一次请求 / 一次响应」。不重新序列化、不改大小写、不改 chunk 边界;`101 Switching Protocols` 之后按字节透传并记录元数据。没有改包规则命中时,请求边收边转,零额外延迟。

**解密策略(进程内按 host)**:默认 `auto` = harness 声明的已知 API host ∪ 从该进程环境变量读到的 base_url host(`ANTHROPIC_BASE_URL`、`OPENAI_BASE_URL` 等,由 harness 文件列出)∪ 操作者手加的 host;`all` = 该进程的一切 TLS 都解密。默认不选 `all`,原因是 Claude Code / Codex 的沙箱会替工具命令中转 npm、git 流量,那些 TLS 的客户端是子进程,不信任 asight CA,解密会把它们弄断。中转站 host 来自 agent 自己的配置,用户不用登记。

## 身份与信任

- **识别进程**:`harness/*.mjs` 给出特征(Linux:`/proc/<pid>/exe` 的路径模式、`argv` 模式;macOS 预留:Team ID + 签名标识)。只认真正发 API 请求的进程,不认 npm 包装层(Codex、OpenCode 的 node 启动器不发请求)。exec 事件到达后通常在毫秒内完成判定(实验室给出实测值);启动时和每次开启时扫一遍 `/proc` 里本实例 uid 的进程(别的用户的 exe / environ 本来也读不到)。exec 后立刻连网、快过判定的进程会漏掉首条连接——漏的是采集,不是 agent 的连接(它照常直连);实验室测量漏采率。
- **子进程与嵌套 agent**:判据是**进程自己**,不看它的父进程是谁。子进程只要自己匹配 harness 特征表,就是一个独立的 agent,单独采集——一个 agent 启动另一个 agent(如 claude 拉起 codex,或任意 harness 互相调用)天然覆盖。同一进程内的 subagent(如 Claude Code 的 subagent,与主 agent 同进程、靠请求头区分)本来就在该进程的流量里。不匹配特征表的子进程(MCP server、shell 工具、沙箱进程)只记元数据;harness 文件可以显式声明某个子进程也算(如 Gemini CLI 的 relaunch 子进程)。嵌套关系(谁启动了谁)记在 `flows/` 的 `parent_pid` / `parent_agent` 里,供看板标注。
- **信任注入**:按运行时写环境变量,指向本用户目录里的 CA 证书 `~/.asight/collector/ca/asight-ca.pem`。Node / Bun → `NODE_EXTRA_CA_CERTS`;Claude Code → 写进 `~/.claude/settings.json` 的 `env`(它在设置变化时会重读);Codex → `CODEX_CA_CERTIFICATE`。**MUST NOT 用 `SSL_CERT_FILE` 指向只含 asight CA 的文件**:rustls 会因此丢掉全部系统根证书,透传的连接全断。注入一次、长期保持,不随开关变化;卸载时先撤变量再删文件(Codex 读不到文件会直接报错退出)。
- **确认信任**:引擎在决定解密前读该进程的 `/proc/<pid>/environ`(Claude Code 另读其 settings),相应变量指向 asight CA 才算信任。注入之前就在跑的 agent 不会有这个变量 → 一直透传,直到它自己重启。
- **CA**:v3 根证书(BasicConstraints CA:TRUE、KeyUsage keyCertSign、SKI),私钥 `~/.asight/collector/ca/ca.key`,属该用户、0600,无名称约束。CN 与旧 MITM 的 `atrace local MITM CA` 不同,MUST NOT 复用或覆盖旧的 `~/.asight/ca`(两张同 CN 的 CA 曾让 Desktop 断网)。叶证 P-256、有效期 199 天、回溯 2 天、带 AKI,每次守护进程启动生成一个内存中的叶证密钥,按 SNI 缓存。CA 装好后永不轮换(agent 只在启动时读一次)。MUST NOT 装进任何系统级或用户级信任库。

## 特权助手与按用户运行(D36)

- **按用户运行**:守护进程以安装它的用户身份运行,不是 root,也不换账号(D32⑦ 的专用账号 `asight-engine` 已被 D36 撤回)。CA、期望态、采集、安装清单都在该用户的 `~/.asight/` 下。同一台机器上每个系统用户各装一套,各自只认自己 uid 的 agent 进程。
- **特权只在助手**:能力助手(上文的 redirector)是唯一带特权的部分。每台机器一次 `sudo` 安装,助手升级后再一次;日常开关和采集不要密码。本机所有用户都能执行它,但它只对调用者自己 uid 的进程生效,与 [5.1](5.1-intervention.md) §安全边界「自己机器上、自己账号下」一致。
- **守护进程不绕回自己**:它与 agent 同 uid,`connect4/6` 改按 tgid 排除它自己的连接(验收 S11)。
- **代价(如实写明)**:被测 agent 与守护进程同 uid,所以 agent 读得到 CA 私钥、能 ptrace 守护进程、能改或删采集文件。D31 原先用「私钥只有 root 可读」弥补「CA 不加名称约束」,这条不再成立。现在接受它的理由:这张 CA 不在任何信任库里,只有本用户被注入了变量的 agent 进程信任它;私钥被偷只帮得上同 uid 的代码,而同 uid 的代码本来就读得到 agent 的凭据和采集。助手是带 file capabilities 的 exec,内核把它标成不可 dump,agent 不能 ptrace 助手。
- **残余风险**:助手对本机所有用户可达,别的用户可以占满根 cgroup 上的挂载名额,让其他用户的采集挂不上钩(fail-open:agent 照常直连,只是没采到;状态按内核实际态如实报告)。共用 `127.0.0.1` 的看板 / API 不隔离用户,见 [4.4](4.4-server.md) OPEN。

## 安装清单与卸载(必须干净 · 见验收 S10)

安装分两级,卸载只按安装清单删,不按猜测删:

- **按用户**(不要 sudo):清单 `~/.asight/collector/install-manifest.json`,如实列出 asight 为该用户创建了什么:目录、文件、注入的环境变量条目、用户级自启单元。`asight uninstall` 只撤这一级。
- **整机**(sudo,一台机器一次):只有能力助手。另由一步 sudo 移除;移除前报告本机还有哪些用户的实例在用它。

1. 按用户卸载的顺序:停守护进程(助手随之退出)→ 确认本实例的 bpf link 已消失 → 撤环境变量注入(只撤 asight 加的键,用户的其他设置一字不动),**先于**删 CA 文件(Codex 读不到 CA 文件会直接报错退出)→ 停用并删除用户级自启单元 → 删 CA 目录与运行时目录。
2. 一个用户卸载,不影响同机其他用户的实例。
3. **采集数据属于用户**:卸载默认保留,只有显式的 `--purge-data` 才删(v0 的 `atrace-uninstall` 曾连采集一起 `rm -rf`,不再重演)。
4. 幂等,且对安装到一半的状态安全:连跑两次、或安装中途崩溃后再卸载,都成功且不留残余。

原 OPEN「采集文件归属」由 D36 解决:守护进程以用户身份写 0600 文件,满足 [4.1](4.1-capture-sources.md) 的「除属主外无人可读」。

## 开关语义(必须精确,见验收 S 组)

| | 开(`on`) | 关(`off`) |
|---|---|---|
| 内核 | 本实例的 `connect4/6`、`sockops` 三个 link 已挂,返回前确认 | 本实例的三个 link 已摘,返回前确认;`exec/exit` 跟踪不摘(只维护进程表,不碰流量) |
| 新连接 | 被判定解密的 agent 进程的新连接全部经过引擎 | 一律直连,agent 看到的是上游真实证书 |
| 已有连接 | 开之前建立的直连不受影响,也不采集 | 开期间建立的连接继续由引擎原样中转直到关闭(TCP 连接无法中途改道),但 `off` 返回之后才开始的请求不再记录 |
| 记录 | 每次请求 / 响应一条信封 | 零新记录 |

- 状态 MUST 来自内核实际态(redirector 按本实例自己的 link id 读 link 信息,同机其他用户的 link 不算),不来自自己记的标志;期望态与实际态不一致时如实报告。
- 幂等:重复 `on` / `off` 无副作用。期望态写进操作者目录,守护进程重启后按它恢复。
- 状态里给出每个 agent 进程「仍在直连、因此没被采集」的连接数(从 `/proc/<pid>/fd` 对 `/proc/net/tcp*`),让「为什么开了还没采到」可见。

## 记录(D10 信封 · 只追加字段)

一次请求 / 响应一条信封,写到 `~/.asight/collector/capture-<日期>.ndjson`(0600,属操作者)。新字段全部追加在 `req_body` 之后(分片器从首个 `"req_headers":{` 扫到 `"req_body"` 取 session id):

- `capture:'transparent'` · `host` · `scheme` · `dst`(原目的地 ip:port)· `proc:{pid, exe, agent}` · `flow_id` · `seq`(连接内第几次请求)
- `req_head_raw` / `resp_head_raw`:请求行 / 状态行加头部的原始字节(latin1),重发据此逐字重建;`resp.headers`
- 响应体逐字:解压后的原文(SSE 原始帧不再丢 `event:` / `id:` / 注释),跨 chunk 的多字节 UTF-8 用 StringDecoder 拼接
- 改包相关:`origin`(`agent`/`asight`)、`client_req_body` / `client_resp`(仅在与上游实际收发不同时出现)、`intervention`,定义见 [5.1](5.1-intervention.md)

透传连接、解密失败、心跳与开关事件写 `flows/`,审计写 `audit/`,重发写 `replays/`,都放子目录,现有看板只读顶层 `*.ndjson`,不会把它们当信封。`isLlmCall` 改为按路径后缀判定,`/anthropic/v1/messages` 这类中转站前缀也算推理请求。

## 控制面

守护进程在 `$XDG_RUNTIME_DIR/asight/collector.sock`(0600,属操作者)上提供 JSON over HTTP:`status / on / off / agents / flows`,以及 [5.1](5.1-intervention.md) 的规则、扣留队列、重发。CLI `asight collector …` 走它;看板的设置面板以后经 [4.4](4.4-server.md) 服务端转接,继续带 D26 的 Host / Origin / CSRF 门。

## 验收(可跑 check)

单元测试走 `npm test`(不需要 root);标 **[VM]** 的在 Linux 测试机(Ubuntu 24.04 · 内核 6.8 上验收过)跑:先用 root 装一次能力助手,守护进程以普通用户运行,只有装 / 卸助手要 root。支持的最低内核 5.15,且 cgroup2 统一挂载(用到 `tp_btf`、BPF link、`CAP_BPF` / `CAP_PERFMON` 与根 cgroup 挂钩)。上游一律是 `test/lab/mock-upstream/`,不碰真实 API。

**S · 开关干净(必过)**
1. [VM] `off`:`bpftool link` 里没有本实例的 cgroup link(按本实例的 link id 查,同机其他用户的 link 不算);受管进程连 mock 看到的是 mock 的真实证书指纹;零新记录。
2. [VM] `on`:受管进程的每条新连接都被记录,记录的请求 / 响应字节与 mock 字节日志逐字节相等。
3. [VM] 未受管进程(同样的 curl / node 脚本,不在 harness 表里)在 `on` 时也不经过引擎:真实证书、零记录。
4. [VM] 长 SSE 流进行中切换:`on→off`、`off→on` 都不打断它,客户端收到的字节与 mock 发出的一致。
5. [VM] 负载下 100 次快速切换:客户端零错误,每个响应逐字正确;记录只来自 `on` 期间建立的连接;每次返回后状态 == 内核实际态。
6. [VM] 幂等:`on,on` / `off,off` 无副作用。
7. [VM] `kill -9` 助手:本实例的 link 消失、同机其他用户的 link 不动,新连接直连、零错误;状态报「降级」。`kill -9` 守护进程而助手还活着:助手因 PDEATHSIG / `getppid` 核对随即退出,本实例的 link 消失。
8. [VM] `kill -9` 引擎:新连接不出现 `ECONNREFUSED`;已在引擎里的连接如实断开并留错误记录。
9. [VM] 重启守护进程:期望态恢复。
10. [VM] 卸载干净:按用户卸载(不要 sudo)后,环境变量注入的键已撤,`settings.json` 里用户的其他键逐字节不变;本用户的 CA 目录、用户级自启单元、运行时目录不存在;`bpftool link` 里没有本实例的 link;采集数据默认保留,`--purge-data` 才删;同机另一个用户的实例照常采集。再移除助手(sudo)后:盘上没有 asight 的带 file capabilities 的二进制(`getcap` 查不到)、没有 pin。连跑 `安装 → 卸载 → 安装 → 卸载` 全程干净。
11. [VM] 守护进程自己的连接从不被改写:它与 agent 同 uid,它连 mock 上游的连接仍直连,不绕回自己(按 tgid 排除)。

**T · 透明**
1. 被动分帧:content-length / chunked / 连接关闭定界 / `HEAD` / `204` / `304` / `1xx` / 流水线 / 升级,转发字节 == 收到字节。
2. 上游中途 RST / FIN:不向客户端注入任何字节;写一条带部分内容的错误信封;不挂住。
3. 客户端中途断开:同步断开上游。
4. SSE 跨 chunk 的多字节字符逐字还原;`event:` / `id:` / 注释保留。
5. 证书:签出的 CA / 叶证过 `openssl verify -x509_strict`;客户端只信任 asight CA 时握手成功。
6. CONNECT 隧道:代理的回应原样转回;代理拒绝(非 2xx)时客户端收到的就是代理的回应。
7. 不信任 asight CA 的受管进程:从不被解密;注入过信任的同一程序被解密。
8. ALPN 只给 `h2` 的连接:透传。

**R · 识别**
1. harness 表命中真正发请求的进程,不命中包装层;exec 后的首条连接漏采率有测量值,且漏采时 agent 的连接照常成功。
2. [VM] 七个 harness(Claude Code · Codex · OpenCode · Kimi Code · DeepSeek `dsh` · Hermes · Z-Code)各自对 mock 跑一轮真实会话,记录里能看到它们的推理请求。

**M · 同机多用户([VM] · 两个 uid A、B 各装一套)**
1. 各自的 agent 只被自己的守护进程采集:A 的记录里没有 B 的请求,反之亦然。
2. B 的进程直连 A 的引擎端口(包括从 `127.0.0.2` 连、源端口与 A 的 agent 撞号)时,A 查不到它:不记录、不过改包规则,连接被关掉。
3. B 的 pid 进不了 A 的改写:即使出现在 A 的 `watch` 表里(pid 复用,或人为写入),`connect4/6` 因 uid 不符不改写、不上报。
4. A `off`、或 A 的助手被 `kill -9`:B 的 link 还在,B 照常采集。
5. A 的助手收不到 B 的 exec / exit 事件(内核里按 uid 过滤)。
6. 给助手传 BPF 对象或文件路径的请求被拒,它只装内嵌对象。

**I · 改包**:见 [5.1](5.1-intervention.md) §验收。

## OPEN

- macOS(钩子的总体形态见上文「特权钩子按 OS 各写一份」):Network Extension 能否看到 agent 到 `127.0.0.1:7897` 的回环连接、能否和 VPN 的 TUN 模式共存;需要 Tart 虚拟机里关 SIP 实测。
- Codex 默认走 WebSocket(`responses_websockets`):v1 先透传 + 元数据;帧级记录(含 permessage-deflate)另立。
- Codex 设了 `CODEX_CA_CERTIFICATE` 后会改用 rustls 并在 ALPN 里带 `h2`;引擎只回 `http/1.1` 时它能否正常降级,需实测。
- 首条连接的漏采若不可接受,改用 BPF-LSM(`bprm_committed_creds` + task storage)在 exec 时于内核里打标。采用它可能要改助手的能力集合,还要开机参数 `lsm=bpf`,也就要再 sudo 一次(未验证)。
- **登出后守护进程的存活**:用户级 systemd 单元在该用户最后一次登出时停掉,除非开了 linger;留在 tmux / SSH 里的 agent 会悄悄失去采集(fail-open),与 D31①「常驻」有出入。建议默认:安装时提议 `loginctl enable-linger`;linger 关着时 `status` / `doctor` 报出来。
- **同机多用户共用 `127.0.0.1`**:看板 / API 端口不隔离用户,见 [4.4](4.4-server.md) OPEN(建议默认:按用户分端口 + 按用户随机 token)。
