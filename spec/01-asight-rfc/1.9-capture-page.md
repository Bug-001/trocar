# asight · RFC 1.9 — 采集页

> **服务意图(A2)**:D38(采集失败在看板上看得到)· D31⑧(看得到 asight 在采哪些 agent、各用什么方式)· D37(七个 harness 逐个看)。采集正不正常是意图 ①② 的前提:没采到的调用,回放台上就没有。
> **受众**:人(打开采集页,知道每个 agent 有没有在被记录;没有的话为什么、怎么办)+ agent(据此实现 `src/web/v2/capture/**`,不另造状态,不画做不到的控件)。
> **前置**:[1.5](1.5-states-aesthetics.md)(看板词表、标记、关键状态矩阵、标签表、轮询与「未刷新」规则)· [1.2](1.2-shell-layout.md)(侧栏、页头、路由、agent chip 与 `harnessKey()`)· [1.6](1.6-cli.md)(按 harness 的开关、`status` 的判词、网络拓扑与点名项的数据形状)· [4.4](4.4-server.md)(`/api/status`、`POST /control/harness`、控制面的令牌)· [4.6](4.6-process-collector.md)(信任、开关语义、安装清单、事件与码)· [0.0](0.0-overview.md) D18c(看板 v2 成为产品看板)。
> **标注**:本单元的界面细节(行从哪来、状态句的先后与措辞、命令放在哪、砍掉的清单)是界面层决定。来源列里的「[见 4.4]」「[见 4.8]」是 spec 标记,含义见 [1.5](1.5-states-aesthetics.md) §数据规则,界面上从不出现。

## Goal

采集页回答一个问题:**我的每个 agent 都在被记录吗?没有的话,为什么,该怎么办?** 采集记录(子页)回答:**最近 24 小时采集出过什么错?**

两条硬约束:

1. 页上每个元素都有真实来源:`/api/status` 今天就有的字段、[4.4](4.4-server.md) §看板 v2 需要的补充 里的 `status` 的 `changed[]`、[1.6](1.6-cli.md)加的字段,或固定文字。做不到的控件不画([1.5](1.5-states-aesthetics.md) §数据规则)。
2. D38:采集服务的状态永不留空;失败带原因、看得到;不当告警(D38⑦)。

D31⑧ 说的「设置面板」落在这一页(D18c):每个 agent 的状态、asight 为它改了什么、本机网络环境、点名项,都在这里。

## 前置定义(Definitions)

- **采集页**:`#/capture`,侧栏「采集」下的「agent」子项。**采集记录**:`#/capture/log`,同组的「采集记录」子项。
- **采集服务**(看板词表):采集守护进程加引擎([4.6](4.6-process-collector.md))。界面上不说「守护进程」。
- **旧采集**(看板词表):过渡期的旧 MITM 与反代([4.1](4.1-capture-sources.md) §过渡期)。它的记录不带 harness。
- **检测到的 agent**:本页认得出的 agent,即下文「行从哪来」各来源的并集。没出现在任何来源里的 harness 没有行,也不写「没装」(没装的不显示)。
- **期望态**与**实际**:期望态是用户要它开还是关(`state.json`);实际是它的进程此刻有没有经过 asight、被记录。两者分开说:开关说的是期望,「被采集」说的是此刻的实际。
- **缓存的判词**:1.6 的 `asight status` / `doctor` / `on` 写进 `~/.asight/netenv.json` 的每个 harness 的结论(`netenv.topology[h]`)。它是那一刻的结论,不是实时的。
- **技术细节**:每块里收起的一节(`core/ui.mjs : techDetails`),放原因码、pid、路径、拓扑、命令。正文不出现这些([1.5](1.5-states-aesthetics.md) 看板词表)。

## Plan(选定方案 + 取舍)

**选定**:一张 agent 表(第一行是采集服务,之后每个检测到的 agent 一行)、一个旧采集块、一张本机网络环境卡、一块「asight 在这台电脑上做的改动」;采集记录另成一页。每个 agent 一行一个控件:开关,或(缺安装环节的东西时)Set up(§开关)。

**备选(未选)**:

- 原型的一行里又有开关、又有做同一件事的按钮(还有「重启」「单独开启…」):一个动作只留一个入口;重启、点名、提权没有端点,按「做不到的控件不画」只写状态与命令。
- 页头一句「6 个 agent:3 个在采…」:否决,这类话不出现在标题或小标题里;计数去总览页([1.7](1.7-overview-dashboard.md))。
- 采集服务停了时页顶一条横幅加「重新开启采集」:看板没有拉起采集服务的接口;全站不设横条([1.2](1.2-shell-layout.md))。这件事写在采集服务那一行。
- 给看板的 harness 表里每一个都列一行、写「没装」:否决,没装的不显示。
- 每个改动旁一个「撤掉」:否决,撤不撤完全取决于该 agent harness 的开关。
- 本页另开一条读路取实时判词:本页只读 `/api/status` 与 [1.6](1.6-cli.md) 写下的缓存,不绕过具名查询(不变式 3)。

**取舍**:能做的就给控件(开关、Set up),做不到的只说事实与命令——能做的事不丢一条命令让人自己去做。装与卸留在命令行(D55① · D61①),所以页面上不出现它们的按钮。

## 每个 agent 一行

**行从哪来**(并集;每个 id 先过 `core/chips.mjs : harnessKey()`,同一个 harness 的两种拼法只出一行):

| 来源 | 字段 | 说明 |
|---|---|---|
| 最近 24 小时采到过或失败过 | `collector.agents[].agent` | 拼法是 `proc.agent` 的(`claude-code` 一类) |
| 现在有问题 | `collector.conditions[].agent` | |
| 失败组里最近一次 | `collector.failures[].last.agent` | 24 小时内带 agent 的失败都已进 `agents[]`,这一项只是保险 |
| asight 为它写过东西 | `status` 的 `changed[]` `collector.changes.entries[].harness` · `files[].harness` | 有 `status` 的 `changed[]` 之后,装过的 harness 不论最近有没有活动都有行 |
| 有按 harness 的开关 | `collector.switch.harnesses` 的键 | |
| 有缓存的判词 | `netenv.topology` 的键 | 总览页「<agent>:<状态句>」一项可按它跳过来,必须有行 |
| 有点名项 | `opt_in` 的键 | 见 §展开 |

**一行的元素**:

| 元素 | 显示什么 | 来源 |
|---|---|---|
| agent | 图标 + 名字;认不出的 id → 保留的虚线方块图形 +「未识别的 agent」 | `harnessKey(id)` + `core/chips.mjs`(owner [1.2](1.2-shell-layout.md)) |
| 期望态 | 「开着」/「关着」(开关的当前值) | `collector.switch.harnesses[id].desired` |
| 状态句 | 按下面的先后取第一条 | 见下 |
| 最近采到 | 「N 分钟前采到 ›」→ `#/sessions?h=<h>`;没有时「24 小时内没采到」,不是链接 | `collector.agents[].last_captured` |
| 最近失败 | 「最近一次失败 T · 采集记录 ›」→ `#/capture/log?h=<h>`;没有时不画 | `collector.agents[].last_failure` |
| 展开 | 行头可点,键盘可达,`aria-expanded` | 固定 |

**状态句的先后**(取第一条成立的)。实现是 `core/capture-verdict.mjs : agentVerdicts()`,总览页「<agent>:<状态句>」一项用同一句([1.7](1.7-overview-dashboard.md)):

1. 采集服务没在跑或没响应(`collector.daemon.state` 为 `not-running` / `not-responding`)→「等采集服务恢复」。原因只在采集服务行写一次,不在每行重复。
2. 这个 harness 的期望态是关 →「关着」。
3. 这个 agent 现在有问题(`collector.conditions[]` 里 `agent` 是它):
   - `kind:'untrusted'` 且 `code` 是 `config-after-start` 或 `env-frozen` →「重启 <agent> 后生效」。不画按钮([见 4.8])。
   - `kind:'untrusted'`、其余与 harness 无关的码 →「没在采:<码的话>」(`labels/capture.mjs`,键是 `src/health/codes.mjs` `TRUST_REASONS` 的通用部分)。
   - `kind:'untrusted'`、harness 自己定义的码 →「没在采:<码自带的话>」:有 harness 自带的说法 时用 `text`,之前用服务端的 `reason` 原样,码在技术细节。前端不拿这些码当键(不变式 3,[1.5](1.5-states-aesthetics.md) §数据规则;守卫 `test/web-v2/labels-complete.test.mjs`、`test/web-v2/harness-seam.test.mjs`)。
   - `kind:'negative-cache'` →「没在采:它的一个进程不认 asight 的证书」。
   - 同一 agent 有几条:取上面次序里的第一条,句尾加「· 另有 N 项」。
4. 有缓存的判词(`netenv.topology[h]`),且它的 `at` 不早于 `collector.switch.harnesses[id].updated_at`:`captured:true` →「在采 · 截至 T」(只在 `collector.daemon.state === 'running'` 时;否则「不知道 · 截至 T」);`captured:false` 且 `reason:'forwarder-down'` →「可能连不上网 · 截至 T」(与总览页那一项同一个判据,[1.7](1.7-overview-dashboard.md));`reason` 是 `config-after-start` / `env-frozen` →「重启 <agent> 后生效 · 截至 T」;`captured:false` 其余 →「没在采:<原因> · 截至 T」;`captured:null` →「不知道 · 截至 T」。没有缓存,或缓存早于开关的最近一次改动 →「不知道(没有最近的状态)」。
5. 连这个 harness 的判词也没有:有 `last_captured` →「没有发现问题」;没有 →「最近 24 小时没采到」。**MUST NOT** 从「没有失败记录」推出「在采」(D38② · 不变式 4)。

`<原因>` 的话:与 harness 无关的码(1.6 `status` 的原因与 `doctor` 的网络码)由 `labels/capture.mjs` 给;harness 自己定义的码同第 3 条。认不出的码 →「原因未知」,码原样放技术细节。

**行的次序**:可能连不上网 > 没在采、重启后生效 > 不知道 > 在采、没有发现问题 > 关着。同一档按 `core/chips.mjs` 的 harness 顺序,认不出的 id 排最后、按出现的先后。采集服务没在跑时各行都是「等采集服务恢复」,按 harness 顺序。

## 展开

有问题的行(第 3 条,第 4 条里不是「在采」的)默认展开;其余默认收起。最多三节:

1. **为什么 · 怎么办**(只在有问题的行上)。为什么 = 状态句里那个码的话;怎么办 = 同一码的「怎么办」话(`labels/capture.mjs`;harness 自己定义的码用自带的话,harness 自带的说法 之前用服务端 `reason` 原样)。`netenv.topology[h].findings` 的每个码再各加一句。重启类写「重启 <agent>,新启动的进程会被采集」,不画按钮。末句:问题来自实时条件(第 3 条)时写「处理之后,这一行会自己更新」;来自缓存的判词(第 4 条)时写「处理之后重新检查一次(命令见技术细节)」。
2. **asight 为它改了**。只是信息,没有撤销控件。
   - 每个改过的文件一行:路径(等宽)· 改了什么(`keys` 用「.」连起来,或 `what`,等宽、原样)· 范围(`scope`:`agent`「自动」· `user`「你点名的 · 用户级」· `machine`「你点名的 · 机器级」)· 有 `backup` 时「备份在 <路径>」· 状态(「完好」/ `entry-missing`「不在了」/ `entry-changed`「你之后改过」)。来源:`status` 的 `changed[]` `collector.changes.entries[]`(`harness` 是它的)。
   - asight 为它建的文件一行:用途(按 `role` 取话,§改动块)+ 路径。来源:`status` 的 `changed[]` `collector.changes.files[]`(`harness` 是它的)。
   - 一句固定的话:「关掉它的采集时一并移除」(代理入口随开关写撤,D57③)。这句**只在这一行里出现一次**,机器范围的改动块不再重复它。
   - **点名项**(`opt_in[id]`,1.6 §1.7 / §9.4):只读列表,每项一行:形态(`form` 原样,等宽)· 状态(`needed`「还没点名」· `done`「已点名」· `broken`「已点名,但入口失效」· `pending-admin`「等管理员」· `needs-admin`「关掉之后还没撤,要管理员」· `unknown`「不知道:<原因>」)· 影响(`implies` 原样)· `admin` 为真时「要管理员」。`enable` / `undo` / `elevated` 三行命令只在技术细节。没有控件([见 4.8])。看板经 `/api/status` 的 `opt_in` 读点名项;端点没给这个字段时这个列表不画(按字段在不在判断)。
   - 安装时替换了用户原来的值的,加一行「替换了你原来的值」+ 路径;原值说明(服务端 `reason`,只是路径,从不是密钥,[4.6](4.6-process-collector.md) §安装清单与卸载)在技术细节。来源:`collector.install.install[]` 里 `kind:'prior-value'`、`harness` 是它的(今天就有)。
   - `status` 的 `changed[]` 不在、也没有上一条时,整节不画,不写「没有改动」。
3. **技术细节**:条件的码、pid、host(负缓存)、自 T 起;采集服务没在跑时,停下之前它的条件也在这里,带「截至 T」(`collector.conditions_as_of`);引流方式(`routing`:`driver`「驱动模式」· `proxy`「代理模式」· `legacy`「旧采集」· `none`「全部关着」· `unknown`「不知道」);每一支的路(`branches[].path` 的节点用 `name`,边用 `via` 的话,读不到的一跳写「不知道 · <原因>」,`inferred` 标「推测」);`running[]` 的 pid 与 `note` 原样;`notes[]` 原样;`findings` 的码;代理模式下一句「按进程分流的转发软件看到的来源是 asight,不是 <agent>」(不写任何产品名,D49);命令;「复制诊断信息」(复制这一行用到的字段,JSON)。

## 条件的话

`collector.conditions[].kind` 是 `src/health/flows.mjs : foldFlows()` 写出的七种。词在 `labels/capture.mjs : CONDITION_KIND`,按 kind 取:

| `kind` | 落在哪 | 话 |
|---|---|---|
| `untrusted` | 它的 agent 行 | 按 `code`(§每个 agent 一行 第 3 条) |
| `negative-cache` | 它的 agent 行 | 「它的一个进程不认 asight 的证书」 |
| `ca-invalid` | 采集服务行 | 「asight 的证书不能用」 |
| `degraded` | 采集服务行 | 「采集服务没有完整的系统权限,部分程序可能采不到」;修法与命令在技术细节 |
| `helper-version` | 采集服务行 | 「采集服务的系统组件版本不对,部分程序可能采不到」;修法与命令在技术细节 |
| `state-mismatch` | 采集服务行 | 「期望 <desired>,实际 <actual>」(两个值按开关的话) |
| `retention` | 采集服务行 | 「保存设置读不出,所有调用先按『全部』保存 · 去设置 ›」→ `#/settings/storage`([1.11](1.11-settings.md),D40) |
| 认不出的 kind | 采集服务行 | 「原因未知」,kind 原样放技术细节 |

不带 `agent` 的 `untrusted` / `negative-cache` 也落在采集服务行,写「一个认不出是哪个 agent 的进程…」。

## 开关 · 装好了但还没接上(D65)

一行的右边恰好一个控件,状态仍然写成文字(一个动作一个入口,不再是「开关 + 一个做同一件事的按钮」)。两种形态取其一:

| 这个 agent 的状态 | 来源 | 这一行给什么 |
|---|---|---|
| 正常 | `/api/status` 里这个 harness 的接上状态 | **开关**:开 = 之后新建的连接被采。拨动 → `POST /control/harness`,按 [4.4](4.4-server.md) 的计划—确认协议:先回要改哪些文件的计划,确认框第一行写后果、接着逐个列文件、焦点在「取消」;确认后同一请求带 `confirm`。回执写在这一行里,页面不跳、焦点留在开关上 |
| 这个 agent 还缺安装环节的东西(它装在 asight 之后,或它自己的更新盖掉了 asight 放的证书载体) | 同上([4.11](4.11-collector-model.md)) | **Set up**:跑幂等的 `install`,只补这个 harness 缺的载体(已信任的根不再问任何东西);走同一套计划—确认协议。做完之后,这一行回到开关 |

- 开关只表示**用户想要什么**;实际在不在采仍由状态句说(状态句与开关不一致时,状态句为准)。
- **Set up 不在 D64 的 0.5 s 线里**(D64:写载体、必要时问 OS 要信任,本身就慢):按下后立刻出在办的状态与 `aria-busy`,做完给回执。
- 需要管理员的那一项(Linux 的能力助手,D53)由命令行做:页面写清要跑哪条命令,不画假的授权框。
- 看板由守护进程托管、`asight install` 之后才存在([4.4](4.4-server.md) · [1.6](1.6-cli.md)),所以页面上没有装与卸的按钮:它们只在命令行(D55① · D61①)。

## Edge cases

- **同一个 agent 两种拼法**(`collector.agents[]` 与 `status` 的 `changed[]` 写 `claude-code`,路由是 `?h=cc`,会话头链过来也是 `cc`):过 `harnessKey()` 后是一行,`?h=` 打开的就是它。
- **采集器没装、只有旧采集**(本分支的 macOS):agent 表只有采集服务一行,下面一句「这台电脑上只有旧采集,它的记录分不出是哪个 agent」;旧采集块照常。
- **装了但 24 小时没活动,且没有 `status` 的 `changed[]`**:没有 agent 行;agent 表下一句「最近 24 小时采集服务没有记下任何 agent」。有 `status` 的 `changed[]` 之后不会出现这种情况。
- **期望态读不出**(`switch.desired:null` 带 `error`):采集服务行期望态写「不知道:<原因>」;agent 行第 2 条不成立,往下判。
- **清单读不出**(`installed:null`):状态句按 `summary`(「不知道」不盖住更坏的,[4.4](4.4-server.md));改动块展开。
- **缓存的判词与开关不同步**:用户改了开关、还没跑过 `status`,缓存的 `at` 早于开关的 `updated_at` → 「不知道(没有最近的状态)」,不显示旧结论。
- **一个组的 `last` 没有 agent**:多数采集器内部的失败如此,「谁」写「采集服务」。
- **`legacy.sources[].source` 是没见过的值**:名字写「旧采集 · <source 原样>」。
- **503 之后又读成功**:agent 行回来,人展开过的照旧展开。
- **服务端连不上、或回 503 以外的错误**:按 [1.5](1.5-states-aesthetics.md) 的「连不上 asight 服务 · 重试」与「未刷新」规则,上一次读到的内容照旧显示、带「截至 T」。
- **`?h=` 写错**:toast,页面不变。

## Risk / 回滚

- 纯前端,读一个已有端点;`status` 的 `changed[]` 是加字段。回滚 = 撤掉 `src/web/v2/capture/**` 的提交,数据与服务端不受影响。
- 风险一:把没采到说成在采。由 MUST「『在采』只在采集器 ok」与第一代不写「在采」压住(验收 #1、#3)。
- 风险二:给出会做错事的命令(本分支 `asight off` 是旧命令)。由契约代与 `cli-commands.test.mjs` 压住(验收 #6、#15)。
- 风险三:新码没有话。认不出的给「原因未知」并把码写出来;标签表与服务端闭集的一致由 `labels-complete.test.mjs` 压住([1.5](1.5-states-aesthetics.md))。

## OPEN

本单元没有自己的 OPEN。看板能不能直接开关采集,等 [4.4](4.4-server.md) §OPEN「同一台机器上几个系统用户共用 `127.0.0.1`」那一条对「经本服务转接采集器控制」的结论;定下之前本页按 §开关 的「定下之前」发布。

## Extensions

- 开关、重启、点名、提权、开机自启的按钮:等 4.4 §OPEN 的结论(开关)与 Windows 任务 14 的接口(其余)。按钮出现时仍守 §开关 的确认规则与「重启」流程。
- 实时的逐个 agent 判词(不靠 `status` 写下的缓存):要经守护进程 socket,同样等 4.4 §OPEN。
- 入口子行与进程数:等采集器记下进程种类与按进程的判词。
- 采集记录按 agent 精确筛选:要服务端按 agent 分组。
- 点名项的开关:在点名项只读列表之上,接口同第一条。
