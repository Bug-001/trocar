## 0. 为什么不用 Network Extension / Endpoint Security

| | Network Extension 透明代理 / 滤器 | EndpointSecurity | 代理模式(本单元) |
|---|---|---|---|
| 权限 | 系统扩展:Apple Developer Program 账号 + 带 network-extension entitlement 的签名 + 公证,用户在系统设置里手动批准 | 专属 entitlement(实际只发给 MDM) | 零特权、零系统件、零开发者账号 |
| 出错形态 | 扩展崩在系统网络栈里,不是 fail-open | 同左 | 引擎死 → launchd 重拉守护进程;重拉期间 agent 连接被拒、重试即到,`status` 如实报 |
| 覆盖 | 全机流量的过滤点,与 D31④「其余连接的字节不经过 asight」相逆 | 同左 | 只有被配置去用它的 agent 经过它 |
| 认进程 | 有,但为全机过滤而设计 | 有 | 引擎在 accept 时刻对套接字定点提问(§5.3) |

## 2. 入口与上游(承 4.8 §2,只写差异)

### 2.1 一种模式、入口组、写入口的次序

照 4.8 §2.1:入口指向**引擎里该组的门**(`http://<g>:<listenerToken>@127.0.0.1:<组端口>`;`auth:false` 组给裸地址),W12 次序 = **门先立、入口后写**(写早了 = 指着死端口),不采时报码、「读不到你终端里的 HTTPS_PROXY」提示、`status <h>` 的「看到的来源是 asight」一句照 4.8(asight 在路径上就印)。

### 2.2 上游(排序照 D43④;读取器换 darwin)

- ① agent 自己配置的代理(入口原值,`prior_value`)→ ② 跟随且开着的系统代理 → ③ 直连;一个形态一个上游;`egress-differs` / `route-loop` / PAC → `not-routed` 照 4.8 §2.2。**上游由引擎拨**(§5.2):meta 带上游与凭据,引擎为这一条连接拨它。
- **系统代理读取 = `scutil --proxy`**:`HTTPSEnable`+`HTTPSProxy`+`HTTPSPort` 给 https 的上游;`ProxyAutoConfigEnable` 开 → PAC → `not-routed`。
- **绕过表方言 `scutil`**:`ExceptionsList`(数组)逐项进表;`<local>` 与裸主机名按 4.8 `translateBypass` 的 `no-proxy` 风格同款语义。agent 自己的 `NO_PROXY` 同 4.8。
- 系统代理变化由守护进程 5 s 核对(`netenv-change` 语义),重算上游 → 计划移动时把门与入口带到新计划(同一次 attach:门幂等重开、入口同址重写为 no-op),不写任何 VPN(4.7)。

### 2.3 形态(darwin 表;机制照 4.8 §2.3)

> **D51 修订本节对进程的识别**:认 agent 进程看可执行文件名(预设 + 用户自定义的白名单,不分大小写、去掉 `.exe`),解释器托管的 agent 再加一个与版本无关的特征;不写安装路径;名字决定是不是 agent,信任入口确实生效才解密。下文按路径写的匹配随实现改写。

## 3. 引擎的门(4.8 §5.1 的 `ingress` 半 + D47 的 `groups` 半)

**引擎是本机唯一的本地代理**(0.0 D47:引擎稳定时不必为引擎挂掉另加兜底;采集器自己当 proxy server)。`engine.listen({ groups: [{ id, port, auth, token }] })` 给每个入口组开一扇**回环门**(127.0.0.1:ingress.json 的组端口),由同一个 proxy ingress 回答:门知道自己的组(`user` = 组 id)、自己的口令(`token` = listener token;`auth:false` = 不收口令——desktop-launcher 的形状,4.8 §3 的 `auth:false` 门),CONNECT/SOCKS5/407/204 的协议半照 4.8 §5.1。`engine.closeGroups(ids)` 是另一半:计划不再携带的门停止接受、在途连接照常排空。绑定按组幂等(已开的门答端口不重开),attach 可反复问。

- **口的凭据 = 入口里写的那个**:`http://<g>:<listenerToken>@127.0.0.1:<组端口>`。错口令 = 407;引擎自己的 ingress token 不是门的事。
- **`auth:false` 门的三重授权**照 4.8 §3:① 用户点名了该组;② 只回环 bind;③ 引擎的逐进程判定——套接字身份不是本门本组的形态 → 只转发、不解密、不记录(§5.3)。上游带凭据时拒开(`login-on-open-port`,开口的端口永不借出用户的登录)。
- **引擎自己的 ingress 端口**(enginePort + ingress token)继续听(ingress.json 的形状不变),仅作形状兼容与引擎自检。
- **门的生死 = 计划 + carried**:计划开的组开其门;`off` 时入口全撤、carried(装过、点过名)的组门保持**只转发**(路由计划已说 off,`lookupIngress` 服务不拒:`group-off` splice);off 且无人携带的门关(无主回环端口是开口)。`uninstall`/裸 `off` 删 ingress.json(4.8 §5.1 同款)。
- **引擎崩 = launchd 重拉守护进程**(这是已接受的代价,0.0 D47):门随引擎死、随重拉开;期间 agent 的连接被拒、其自身重试即到。没有 fallback 层。

## 4. 开与关(承 4.8 §4 + launchd 语义)

- on/off 次序、off 的排空与 `--now`、按 harness 隔离:照 4.8 §4(attach 先开携带组的门,再写开组的入口;detach 撤全部入口、关无人携带的门)。
- **自启 = LaunchAgent**(`~/Library/LaunchAgents/com.asight.collector.plist`,`RunAtLoad`+`KeepAlive`)。launchd 的 KeepAlive 会重拉被杀进程,所以**不建监管父进程**;off 停守护进程的次序因此是**先 `launchctl bootout`(摘自启,保证不被拉回)再停进程**,回执按 1.6 §1.4 写。登出行为:LaunchAgent 随 GUI 会话,登出即停(与 Linux linger 的差异如实标注;v1 接受,OPEN 6)。
- 入口的写入与撤销只走通用机制(`prior_value`、改前备份、逐字节还原),不为任何其它采集机制开并存特例。
- `asight on` / `off` / `status` / `uninstall` / `daemon` 在 darwin 驱动本单元的采集器(1.6 §4)。

## 5. 引擎的代理入口(承 4.8 §5——跨 OS 核心;§5.3/§5.4 是 D47 的 darwin 形状)

- §5.1 入口协议(CONNECT/SOCKS5/健康探测 204/407)、§5.2 上游拨法(direct/http/socks5、一条连接只拨一次、凭据只进前导)、§5.5 负缓存、§5.6 同一格式(`capture:'proxy'`):照 4.8。
- **§5.3 身份 = accept 时刻、从套接字读**(0.0 D47)。引擎的门收下连接,peer 4 元组**就是** agent 的出站套接字(中间没有内核):两问定点、无扫描——
  1. **谁**:`lsof -nP -Fpcn -iTCP@<peer addr>:<peer port>`,本地端等于 peer 的那行答 pid;无行、多行、慢、读不出 → null,连接 splice `untracked`(`pid-unresolved`),绝不猜(4.8 W4)。
  2. **是什么**:该 pid 的 `ps -p` 行(命令行、lstart、ppid)+ `lsof -p <pid> -Fn` 第一条 `ftxt`(真执行文件)。`matchForm` 按它判形态;**非本门本组的形态 / 无形态 → 只转发**(`not-a-process-of-form`,开口门的安全臂)。
  没有 ps 扫描表、lsof 候选集、demand-poll、去抖(0.0 D47:不做进程扫描)。peer 进程按定义活着(它刚连上),一连接两问即全部成本(定点 ~28–30 ms + ~15 ms,`[本机]` 实验②)。
- **§5.4 判定**:core 缝照 4.8 W76(`registry.osMatch`、`envRead:false` 不否决、`osLayers`、标记容差)。新形态的裁缝:**门把新 pid 的事实作为 `exec` 说出,lookup 等 tracker 的 `watch()`**(默认 5 s 上限;等不到 = 墓碑 `{decrypt:false}`,一生等一次、不按连接等,tracker 事后答了就盖掉)。pid 的 verdict 按 pid+startedAt 记——pid 复用(另一生)不继承死进程的信任。
- **引擎对上游的 TLS 验证用合并集(§6.2 同一份)**:darwin 上 Node 的默认验证集不含钥匙串里后加的根;引擎连上游的 CA = 合并集(MA5)。

**CC-Desktop 要采**,默认不开、用户级点名开启:信任 = login keychain(`security add-trusted-cert`,用户域,系统授权对话框,§2.4)。代理入口 **已实测定案(2026-10-12,[MacVM] 实测)**:

1. **env 门全死**:`HTTPS_PROXY/https_proxy/HTTP_PROXY/http_proxy/ALL_PROXY/all_proxy` 一视同仁被无视——env 真实存在于每个进程(`ps eww` 验过),是网络栈不读:模型流量全部走 Chromium network service(`Claude Helper --type=utility`),macOS 上它只读系统代理设置。`NODE_EXTRA_CA_CERTS` 对模型流量同理死路。系统代理路径不做(改 `scutil` 波及整机,D43⑥ 点名也不做)。
2. **switch 门活**:启动参数 `--proxy-server` 被 Electron 透传给 Chromium,claude.ai + api.anthropic.com + 全部遥测 100% 进本地门(实测 18 CONNECT / 10 域名,QUIC 同步消失)。**所以 Desktop 的代理入口 = named launcher 附加 Chromium switch,不是 env 块、不是系统代理。**

**desktop-launcher 点名项(2026-10-12 定案,§2.4 表一行)**:

- **形态**:`claude-code.desktop` 组下的用户级点名项 `desktop-launcher`,写一个启动器 `~/.asight/collector/bin/claude-desktop-asight`(shell stub,0755):`exec` 真 bundle 二进制——`/Applications/Claude.app/Contents/MacOS/Claude`,`~/Applications/…` 为次(取先在的那个;都不在 = refuse:Desktop 没装)——附加 `--proxy-server=http://127.0.0.1:<desktop 组端口>`(ingress.json 的组端口 = 引擎门,`proxyUrl` 对 `auth:false` 组给的裸地址)+ `--proxy-bypass-list='127.0.0.1,localhost,<-loopback>'`,用户的额外参数原样透传。直接 exec bundle 二进制(实测 run3 同款路径,已证);`open -a Claude --args` 的便宜形态不采用。
- **鉴权设计(记录在案)**:Chromium 不认 `--proxy-server` 里内嵌的凭据 → desktop 组的引擎门**不带凭据**(4.8 §3 的 `auth:false` 门,不是新变体)。它的授权 = 三件事叠起来:① 用户点名了本项(D43⑥);② 门只回环 bind(§3);③ 引擎的逐进程判定照常——**套接字身份覆盖 app 内的 Claude 家族**(主二进制 + `Frameworks/` 的 Helper 家族,§2.3 的路径表;模型套接字的真属主 `Claude Helper --type=utility` 由此过形态匹配,实测),家族之外的 CONNECT 只转发、不解密、不记录(§5.3 的 `not-a-process-of-form` 臂)。上游带凭据时拒开(4.8 §3)。
- **needs_restart 语义**:launcher 只影响**经它启动**的 Desktop 实例;一个在跑的 Desktop 不被碰——要采它,退出再用 launcher 启动。回执与 doctor 写明这句话。
- **信任**:引用 §2.4 的 keychain-login 项,本项不建任何新信任机制;没装 keychain CA 时引擎对 Desktop 流量一律不解密,launcher 只做转发。**tracker 侧的接线**:Desktop 家族进程的信任判定**只走 keychain 门,不走 settings env 门**——`d.darwin.layers` 对 desktop 家族(命令行含 Claude.app 家族路径)返回**一把合成层**:存在 = manifest 里该 harness 的 `optin-keychain-cert` 条目已确认,`since` = 该条目的 `installed_at`(config-after-start 照判);不存在(未点名 / 对话框被拒 / 已撤)= 无层 = `var-missing` 不信任——**即使 `~/.claude/settings.json` 因 cli 形态在采而恰好持有 CA 也不借道**。cli/vscode 形态照旧走 base 层(settings env),互不串门。
- **off/undo**:删 launcher 文件(kind `optin-desktop-launcher`);keychain 项的装卸是那一个点名项自己的事。
- **接线臂**:守护进程的重算必须认「清单里有记录的点名」——`planRoutes` 的 `optIns` 与 carried 列表从 manifest 的 `optin-*` 条目取;**且 5 s 检查重算计划、计划移动时带门跟上**(否则 `off` 后重启守护进程,launcher 指着没有门的死端口)。(win32 同款,4.8 §4.1。)

**验收 DEFINITIONS(只定义;状态不在本单元)**:L1 launcher 落盘 + manifest 条目 + 回执一行;L2 经它启动 → CONNECT 到达引擎的 desktop 门;L3 off → launcher 删除;L4 无凭据的门仅回环。
