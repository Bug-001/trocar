## 0. 为什么不用 Network Extension / Endpoint Security(对照 4.8 §0 的骨架)

| | Network Extension 透明代理 / 滤器 | EndpointSecurity | 代理模式(本单元) |
|---|---|---|---|
| 权限 | 系统扩展:Apple Developer Program 账号 + 带 network-extension entitlement 的签名 + 公证,用户在系统设置里手动批准 | 专属 entitlement(实际只发给 MDM) | 零特权、零系统件、零开发者账号 |
| 出错形态 | 扩展崩在系统网络栈里,不是 fail-open | 同左 | 引擎死 → 内核退上游(4.8 §3.3);内核死 → agent 断到重拉,`status` 如实报 |
| 覆盖 | 全机流量的过滤点,与 D31④「其余连接的字节不经过 asight」相逆 | 同左 | 只有被配置去用它的 agent 经过它 |
| 认进程 | 有,但为全机过滤而设计 | 有 | 内核进程规则 `[本机]` 实验① |

## 2. 入口与上游(承 4.8 §2,只写差异)

### 2.1 一种模式、入口组、写入口的次序

照 4.8 §2.1 逐字:入口指向内核里该组(`of.<形态>` 凭据)、W12 次序(内核读回「开」之前零入口)、不采时报码、「读不到你终端里的 HTTPS_PROXY」提示、`status <h>` 的 VPN 来源一句(4.8 §2.1 末)。

### 2.2 上游(排序照 D43④;读取器换 darwin)

- ① agent 自己配置的代理(入口原值,`prior_value`)→ ② 跟随且开着的系统代理 → ③ 直连;一个形态一个上游;`egress-differs` / `route-loop` / PAC → `not-routed` 照 4.8 §2.2。
- **系统代理读取 = `scutil --proxy`**:`HTTPSEnable`+`HTTPSProxy`+`HTTPSPort` 给 https 的上游(`HTTPEnable`+`HTTPProxy` 给 http,按 4.8 §2.2 的分别处理);`ProxyAutoConfigEnable` 开 → PAC → `not-routed`(scutil 有独立标志,无 Windows OPEN 27 的类型歧义)。
- **绕过表方言 `scutil`**:`ExceptionsList`(数组)逐项进表;`<local>` 与裸主机名按 4.8 `translateBypass` 的 `no-proxy` 风格同款语义;译不了的计数、`status` 报。agent 自己的 `NO_PROXY` 同 4.8。
- 系统代理变化由守护进程 5 s 核对(4.8 §9 的 `netenv-change` 语义),重算上游 → 重载内核,不写任何 VPN(4.7)。

## 3. 自带内核(承 4.8 §3,逐字复用 + 三处差异)

`buildForwarderConfig` 与监听器 / 子规则 ①–⑥ / `asight-in-<f>` / fallback 组 `asight-fb-<f>` / 再进点 `asight-re-<g>` / 本机健康探测 / `ingress.json` / 防环路 `ownImages` / 宿主 host 集,全部照 4.8 §3(其中 AND 内 `IN-USER` 与 `DOMAIN-REGEX`、localhost 直连前提,`[合约]` 本来就在 darwin 内核上量过)。差异:

1. **`ownImages` 必须是真实映像路径**(引擎与内核是两个独立进程)。`[合约]` 的 Mac 冒烟因替身与引擎同进程而关了 `find-process-mode`;`[本机]` 实验① 已在真内核上验证地基:官方 v1.19.32 darwin-arm64,`match ProcessPathRegex(^/usr/bin/curl$) using sink` 命中并分流,`(node)` 反证组走 DIRECT 不误伤,进程识别 `(curl)`/`(node)` 正确。产品内核配置的进程规则在 [MacVM] 用真实 `ownImages` 重验(MA1)。
2. **预检 = Gatekeeper(不是 Smart App Control)**。`[本机]` 实验③:官方 darwin 二进制 adhoc linker-signed;curl / npm 下载不带 `com.apple.quarantine`;自然状态与手工加隔离属性**均可执行**;`spctl --assess` 拒绝(exit 3)但只影响 `.app` 双击,不影响 CLI exec。预检仍做(与摘要核对同一道):每次拉起前核 sha256 对 pin(4.8 §8);再查自有副本的 `com.apple.quarantine`,存在即 `xattr -d` 自愈并写一条 `flows/` 事件;都不过 → `gatekeeper` 码(§12),回执带重装命令。
3. **二进制名 `asight-forwarder`(无 `.exe`)**,复制到 `~/.asight/collector/kernel/`;「正在跑的 exe 换不掉」的 Windows 理由不成立,但「复制一份归 asight 所有、升级不悬空、`uninstall` 可删」照 4.8 §8 保留。

## 4. 开与关(承 4.8 §4 + launchd 语义 + 与旧采集并存)

- on/off 次序、整份重载(`PUT /configs?force=true`)与读回、off 的排空与 `--now`、按 harness 隔离:照 4.8 §4。
- **自启 = LaunchAgent**(`~/Library/LaunchAgents/com.asight.collector.plist`,`RunAtLoad`+`KeepAlive`)。launchd 的 KeepAlive 会重拉被杀进程(与 Windows 计划任务相反),所以**不建监管父进程**;off 停守护进程的次序因此是**先 `launchctl bootout`(摘自启,保证不被拉回)再停进程**,回执按 1.6 §1.4 写;内核的监管(`forwarder.lock`、1,2,4…30 s 退避、连续 5 次 → `forwarder-down`)照 4.8 §8。登出行为:LaunchAgent 随 GUI 会话,登出即停(与 Linux linger 的差异如实标注;v1 接受,OPEN 6)。
- **与旧采集:不做并存特例**(不引入并存期的兼容复杂性)。入口的写入与撤销只走通用机制(`prior_value`、改前备份、逐字节还原):`on` 之前键里是什么(包括旧采集写下的值)就记什么、`off` 就还原什么,不为旧 asight 的值做识别、分支或额外标注。`com.asight.env` 只守 0.0 §过渡期遗留的那一条(旧采集开着时 MUST NOT 单独移除),无其他并存机制。翻转与退役见本节末。
- **退役**:本机过 §验收 的 MA 组(R2 等价 = MA3)后,`hasNewCollector('darwin')` 翻转,`asight on/off` 在 darwin 驱动新采集器,旧采集按 D39⑥ 退役(1.6 §4);翻转前 darwin 上 `on/off` 照旧驱动旧采集。

## 5. 引擎的代理入口(承 4.8 §5——跨 OS 核心,几乎零差异)

- §5.1 入口协议(CONNECT/SOCKS5/健康探测 204/407)、§5.2 上游拨法(direct/http/socks5、一条连接只拨一次、凭据只进前导)、§5.5 负缓存、§5.6 同一格式(`capture:'proxy'`,各平台的数据格式一致):照 4.8,`[合约]` 的引擎侧本来就在 darwin 上真跑过。
- **§5.3 pid 补全 = `lsof`**:`[本机]` 实验②,全表与定点均 ~28 ms;「单候选或 null」「表外持有者 → null」(4.8 W4 的规则,含 W43 的错认必须是 0)照抄;超预算 → `null` 且 `pid_ms` 记实测。
- **§5.4 判定**:core 缝(`registry.osMatch`、`envRead:false` 不否决、`osLayers`、标记容差、`facts-update`)照 4.8 W76;darwin 的 `envRead` 恒 `false`(无特权读不到别的进程环境,同 Windows),`environ-unreadable-fill` 的取舍照 4.8 §5.4。
- **引擎对上游的 TLS 验证改用合并集(§6.2 同一份)**:`[本机]` 实验④——darwin 上 Node 的默认验证集 = 自带 Mozilla 库(`'default'` 与 `'bundled'` 同为 145 张),不含钥匙串里后加的根;不改的话,企业代理的上游(如本机的 FeiLian)会校验失败 → `upstream-cert` 让路 → 采不到。本单元:引擎连上游的 CA = 合并集,把 4.6:96 的「Node 读不到 macOS 钥匙串里另加的根」这一已知局限**在 darwin 上关掉**(Linux 侧不动)。

## 6. 信任入口(darwin 的 D37④ + 合并包)

### 6.1 入口表

见 §2.3 的表(每行已含信任键);并块、哨兵、原子重建、逐字节撤销照 4.8 §6.1 / 4.6 §身份与信任。路径带空格的双引号处理保留(macOS 用户目录可带空格);正斜杠 / CRLF 条款不适用。

### 6.2 合并包(比 Windows 简单:无助手导出)

**组成 = `getCACertificates('bundled')` ∪ `getCACertificates('system')` ∪ SystemRootCertificates 导出 ∪ 该 harness 配置里的用户 CA ∪ asight CA**,按 fingerprint256 去重、原子重建、每 harness 一份(替换语义,D37④)。依据 `[本机]` 实验④:

- `'system'` 在 darwin = **钥匙串管理的本地信任锚**(用户域 + 管理员域;本机 5 张:清华 WiFi 门户证书(用户域 trust-as-root)、火山 FeiLian 根(管理员域)、3×GlobalSign)——正是「企业与杀软的 TLS 检查根」所在,两个 API 调用拿到,无需 `security` 导出、无需助手;
- 标准系统根由 `'bundled'`(145)+ `security find-certificate -a -p /System/Library/Keychains/SystemRootCertificates.keychain`(158,普通 CLI 只读)双保险,重叠部分去重;
- **绝不用固定的 `/etc/ssl/cert.pem`** 当 OS 根(4.8 §6.2 的告诫同款:企业根不在里面;且它是静态文件,不随后加的信任走)。

### 6.3 shim 与 rc PATH

照 4.8 §6.3:引用计数、`shim-not-on-path`(darwin 判法 `which -a`)、shim 目录只放 `kimi`。

### 6.4 CC-Desktop 与待实测项

**CC-Desktop 要采**,默认不开、用户级点名开启:信任 = login keychain(`security add-trusted-cert`,用户域,系统授权对话框,§2.4);代理入口 = [MacVM] 实测定(它自己读得到的入口;系统代理按 D43⑥ 点名也不做)。**2026-07-21 的教训如实带上**:import-only 对 Node 栈无效、当时的结论是 Desktop 只认 `NODE_EXTRA_CA_CERTS`(登录环境,D37④ 禁写)——带信任设置的钥匙串安装是否够、Desktop 的请求走 Node 栈还是 Chromium 栈,以实测为准;实测确认只认登录环境 → 如实报「不可采 + 原因」,不带特殊机制。Kimi 桌面版 / VS Code 扩展、Z-Code 桌面版 / app-server:待测(4.6 OPEN ②⑦ 的 darwin 半,MA4 逐个补)。Hermes `ssl_ca_cert`:本单元做(§2.3)。
