# asight · RFC 5.1 — 拦截 / 修改 / 重发(agent 界的 Burp Suite)

> **状态**:方向已定(**D30**);机制已定(**D33**,2026-10-05),随 [4.6](4.6-process-collector.md) 的引擎一起实现。
> **前置**:采集 = [4.1](4.1-capture-sources.md)(重设计方向见 **D31**);统一信封 = [4.1](4.1-capture-sources.md) §统一原始信封;归一化 = [3.2](3.2-normalized-model.md);服务 = [4.4](4.4-server.md);写通道的安全门 = D26。

## Goal

asight 不只看清 agent 发给模型的每一比特,还能**改**:拦下一条请求、改它的上下文再放行;或把一条历史请求改完再发一次。用途是调试和受控实验,比如「这一步换掉某块上下文,模型会怎么答」。

## 已定(D30)

1. **不分模式**。拦截、修改、重发是采集器本身的能力,不是另一个产品形态。
2. **授权 = 本机操作者**。运行 asight 的人在本机显式打开、随时可关。没有操作者的显式操作或显式配置的规则时,asight 原样转发,不主动发请求、不改包。
3. **凭据**。允许带着 agent 自己的凭据转发改后的请求,也允许重发历史请求;只限操作者触发的这两类动作。
4. **源真相与标注**。原始请求、改后请求都逐字存,外加一条 intervention 事件(谁、何时、改了什么、依据哪条规则);MUST NOT 用改后覆盖原始。看板 MUST 就地标明哪些请求被改过、哪些是 asight 发起的。(不变式 2、4)
5. **审计**。每次修改、重发都留可追溯的记录,操作者能查看和导出。
6. **WebSocket 上 v1 只记录、不改包**(D37)。规则、扣留、重发都不作用于 WebSocket 消息;命中规则或开了拦截时也原样转发,并在审计与 UI 标「WebSocket:v1 不支持改包」(不变式 4;验收 [4.6](4.6-process-collector.md) W11)。

## 机制(D33)

> **v1 范围**:先做**透明采集器**本身,拦截 / 修改 / 重发的**规则设计推迟**——采集器稳定后再定有哪些规则、怎么拦怎么改。本节描述的机制是目标形态;v1 只先落下面 §记录与标注 里的**信封字段 + 审计流 + `replays/` 目录 + `calls` 两列 + `interventions` 一张表**,够记录一次手动改包 / 重发即可。**不做** `intervention_blocks` 表、不做 `::orig:` 文本定位语法——「改了什么」v1 由补丁本身现场渲染(改动本来就小),等界面确实需要「按块看改动」再加(避免过度设计)。

**拦截点**在 [4.6](4.6-process-collector.md) 的引擎里,按「一次请求 / 一次响应」工作。没有规则、没开拦截时请求边收边转,与纯采集完全相同。

1. **请求规则(match & replace)**:按 agent、host、路径、请求体内容匹配,对请求头或请求体做字符串 / 正则替换。命中任一规则(或该 agent 开了拦截)的请求先收全,再改,再发;`content-length` 按新长度重写,其余头的顺序与写法不动。
2. **扣留队列(照 Burp 的做法)**:开拦截后,请求停在队列里等操作者「原样放行 / 改后放行 / 丢弃」。**没有默认超时**:agent 只是在等,不会坏,操作者扣多久都行;超时自动放行是可选项,默认关。唯一的边界是 agent 自己的客户端超时(例如 Claude Code 流停 20 秒会中止重试):agent 先放弃时,队列条目标「agent 已断开」,放行不再有意义,留一条记录。丢弃 = 重置该连接,agent 看到的是连接错误,自行重试。**`asight off` 时**([1.6](1.6-cli.md) §3.1):`off` 先停用规则(规则保留、不删),把扣留队列里的条目原样放行(不改一字节,审计记 `released-by-off`),再按在途请求处理(响应结束后关连接);`off` 之后新到的请求不再匹配规则。扣留没有默认超时,不这样做 off 保证就完成不了。
3. **响应规则**:流式响应按 SSE 事件逐条匹配、改 `data:` 里的文本;非流式改整个 JSON。被改过的响应按 chunked 重新分帧;原本压缩的,解压后改写并去掉 `content-encoding`。**响应也可以人工扣留**:先把响应收完整(流式则等流结束),交给操作者看、改,放行时一次发出;此时 agent 收到的不再是逐字流出的,这一点在记录里标明。扣留期间的限制与请求一样,只受 agent 自己的客户端超时约束。
4. **重发(Repeater)**:操作者选一条已记录的请求,可先改再发。按记录里的 `req_head_raw` + 请求体逐字重建,发往同一目的地;原连接经过 CONNECT 代理的,重发也走同一个代理。重发的响应不回给任何 agent,只记录。默认限速 1 次 / 秒、同时只有 1 个在途。
5. **入口**:只经守护进程的控制 socket(0600,属操作者);看板以后经 [4.4](4.4-server.md) 服务端转接,带 D26 的门;同机多用户隔离落地前这条转接不上线(见 §安全边界)。数据面仍然只读。

## 记录与标注(D33)

- **基准永远是上游那一侧的逐字字节。** `req_body` / `resp` 记**真正发给上游 / 从上游收到**的字节(模型实际看到的那份)。这就是每次调用本来就存的东西,所以 `content_hash`、AC-1、cache 分析、相邻 call 的前缀比对**全部照旧跑在真实线上字节上,零重建**——改请求对现有读路径就是一次普通 call,下一次调用的缓存断点因此仍然算得对。
- **另一侧用补丁还原,不存第二份完整体。** agent 原本发的请求(改请求时)、agent 实际收到的响应(改响应时)记在信封的 `intervention` 字段里:一组字节级编辑 `edits:[{at, del, ins}]`,外加 `base_sha256` / `result_sha256`。还原 = 对基准字段应用这组编辑,每次读都校验 `result_sha256`,对不上就**拒绝、不猜**。典型只多存变化的那一小段(例:40KB 请求改 1KB,多存约 1.2KB,而不是再来一份 40KB)。最坏(整体替换)退化为约多一份副本,绝不更差——编码器在「内联整份」与「补丁」里取小者,永不产出无法还原的形态。
  - **例外 · SSE**:流式响应的 `resp` 本就是重建体(见 [4.1](4.1-capture-sources.md) §统一原始信封),对它打字节补丁无意义;此时 `recover:'inline'`,把 agent 收到的那份整段存在 `client.body`,并标注「基准是 SSE 重建,补丁不适用」(不变式 4)。响应体积小,可接受。
- **重发**:写进 `replays/<session_id>.ndjson` 子目录,**没有** `calls` 行、**没有** cache_events 行(结构上就不进血缘与 cache 分析,不靠过滤);`req_body:null`(由源 call 的逐字 `req_body` + 补丁推出),`base_sha256` 钉死源字节(源 id 若是旧的重复 id,校验失败即拒绝,不会发错 prompt);存它自己真实的 `resp` 与 usage。
- **审计流** `audit/`(即 `interventions.ndjson`):每次修改 / 放行 / 丢弃 / 重发一行,带改前改后字节的 sha256,只追加、独立于 DB、DB 丢了也在。
- 看板 MUST 就地标出「已改(operator/规则)」「asight 发起」(不变式 4);改请求是一条正常 `calls` 行,带 `intervention_kind` / `intervention_ref` 两个**映射列**(不是埋进 `extra`)。

## 仍待定(OPEN)

- 拦截与改包的看板界面(Burp 式队列、规则编辑、Repeater 面板):先只有控制 socket 与 CLI,界面随设置面板一起做。CLI 动词(以后):`asight rules {list|add <file>|rm <id>|off}`(`off` 一次停掉全部规则,D30「随时可关」)· `asight queue {list|show|edit|release|drop} <id>` · `asight replay <call-id> [--edit]`(每次确认;默认每秒 1 次、同时 1 个在途)· `asight audit [--export F]`;都经守护进程的 0600 socket,改包或重发的命令打印审计记录 id;跨命令规则见 [1.6](1.6-cli.md) §1。
- 重发的额度与风控提示文案;是否允许并发重发。

## 验收(可跑 check · I 组)

上游一律用实验室 mock(`test/lab/mock-upstream/`);mock 的回复由它收到的请求决定(回显最后一条用户消息的前 80 字和请求体 sha256),据此判断模型「看到了什么」。

1. 请求规则把提示词里的 `ALPHA` 换成 `BRAVO`:mock 收到的是 `BRAVO`;agent 显示的回复含 `BRAVO`;信封 `req_body` 含 `BRAVO`;对 `req_body` 应用 `intervention.client.edits` 还原出的原始请求含 `ALPHA` 且 `result_sha256` 校验通过;审计一行。
2. 扣留后改系统提示再放行:mock 收到改后的版本。扣着不处理、但仍在 agent 的客户端超时之内时,agent 不报错、不重发,放行后正常完成。agent 在扣留期间自己放弃时,队列条目标「agent 已断开」并留记录。
2b. 人工扣留一条响应并改写文本:agent 收到改后的内容;记录里 `resp` 是 mock 原文,agent 收到的改后内容由 `intervention.client` 还原,且标明这条响应被扣留过(不是逐字流出的)。
3. 丢弃:agent 看到连接错误并重试,重试的请求正常完成并被记录。
4. 响应规则改 SSE 文本:agent 收到改后文本,信封 `resp` 仍是 mock 发出的重建体;因 SSE 的 `resp` 本就是重建、补丁不适用,agent 收到的改后文本整段存在 `intervention.client.body`(`recover:'inline'`),并带标注。
5. 响应规则把 mock 的文本回复改成一个 `tool_use`(让 agent 执行 `echo asight-tool-ok`):[VM] 真实 agent 执行了这个工具,下一轮请求里带着工具结果 —— 证明改包能改变 agent 的上下文与行为。
6. 重发一条记录并改其请求体:mock 收到改后版本;信封 `origin:'asight'`、源 call 引用与 `base_sha256` 正确、`req_body:null`、落在 `replays/`;agent 的会话流和 `calls` / cache_events 里都没有它;限速生效。
7. 没有规则、没开拦截时:转发字节与 T 组相同(改包能力不改变默认路径)。
8. 扣着一条请求时跑 `asight off`:mock 收到的请求与 agent 发出的逐字节相同;审计一行 `released-by-off`;规则仍在、`off` 之后新到的请求不匹配规则;这条请求的响应结束后连接被关([1.6](1.6-cli.md) §3.1)。

## 自动适配(auto-adapt · 原 5.1 保留部分)

从原始流量自动猜 provider 线格式与 harness 约定,少写或不写手工 dissector。它只读、只猜、可被手工 dissector 覆盖;猜测结果在 UI 标「自动推断,可能不准」(不变式 4)。可作为 [3.1](3.1-adapter-contract.md) 的 Extension 独立推进。

## 安全边界

这是对 agent 流量的中间人修改能力。合法用途 = 操作者调试、实验**自己机器上、自己账号下**的 agent;不用于拦截或修改不属于操作者的流量。单机、单用户、只绑 loopback 的边界不变(Non-Goals)。D36 起同一台机器上可能有别的系统用户,D26 的门挡不住他们的本地进程:经 [4.4](4.4-server.md) 转接的入口在按用户隔离落地前 MUST NOT 上线,入口只有 0600 控制 socket(见 [4.4](4.4-server.md) OPEN)。
