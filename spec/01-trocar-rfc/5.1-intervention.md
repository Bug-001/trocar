# trocar · RFC 5.1 — 规则:修改 / 拦截 / 注入 / 重发(agent 界的 Burp Suite)

> **状态**:方向 **D30**,记录形状 **D33**,规则系统 **D78**。
> **前置**:采集 = [4.1](4.1-capture-sources.md);引擎 = [4.6](4.6-process-collector.md);统一信封 = [4.1](4.1-capture-sources.md) §统一原始信封;归一化 = [3.2](3.2-normalized-model.md);命令 = [1.6](1.6-cli.md) §4.4 – §4.6;看板 = [2.7](2.7-rules-view.md) · [1.11](1.11-settings.md) §规则;写通道的门 = D26。

## Goal

trocar 不只看清 agent 发给模型的每一比特,还能动手术:改一条请求或响应、扣下来、断开、替上游回答、往流里插东西、把一条历史请求改完再发一次。用途是调试和受控实验,比如「这一步换掉某块上下文,模型会怎么答」「agent 碰到 429 怎么退避」「这个工具结果截短一半还能不能完成任务」。

操作者可以是人,也可以是操作者开的 agent:agent 靠 `trocar --help` 就能走完「写规则、在采到的记录上试、真发实验、上线、看结果、收手」这一圈。

规则在热路径上,坏规则能卡死 agent。所以这个单元的第一条设计约束是**没有用的工作一点不做,有用的工作有上限**:一条流量只碰可能命中的规则,没有候选规则时开销接近零;规则再慢,agent 也只多等最长延迟这么久。

## 已定

1. **不分模式**(D30)。修改、拦截、注入、重发是采集器本身的能力,不是另一个产品形态。
2. **授权 = 操作者**(D30 · D78①)。操作者是运行 trocar 的人和这个人开的 agent。没有操作者的显式操作或开着的规则时,trocar 原样转发,不主动发请求、不改包。
3. **凭据**(D30)。允许带着 agent 自己的凭据转发改后的请求,也允许重发历史请求;只限操作者触发的这两类动作。用户代理的凭据不在此列([4.8](4.8-win-collector.md) §5.2)。
4. **源真相与标注**(D30 · D33)。上游一侧逐字存,agent 一侧由补丁逐字节还原并校验;外加一条审计记录(谁、何时、改了什么、依据哪条规则)。MUST NOT 用改后覆盖原始。看板 MUST 就地标明哪些请求被改过、哪些是 trocar 发起的、哪些规则没能应用。(不变式 2、4)
5. **审计**(D30)。每次改动、扣留、放行、断开、代答、重发、超时都留可追溯的记录,操作者能查询和导出。
6. **规则默认关,先试再开**(D78③)。`rules add` 写入的规则是关着的;`--replace` 之后也是关着的。
7. **出错策略必填**(D78④)。每条规则写明 `on_error`,没有默认值。超时是一种出错。
8. **`off` 让规则停下**(D78⑥)。再 `on` 不会自己回来,要重新 `rules enable`。`update` 不算 off。`uninstall` 把规则全部转成关闭。
9. **规则只能改这条请求里的字节**(D78⑨)。服务端存着的上下文碰不到;重发续写请求要先补全成完整请求,补全的那份标明是重建的。

## 规则

规则系统五个词讲完:

| 词 | 意思 |
|---|---|
| `on` | 在哪动手:`request`、`response`、`ws-client`(agent 发的 WS 消息)、`ws-server`(服务端发的 WS 消息) |
| `match` | 什么时候动手 |
| `do` | 动什么手 |
| `on_error` | 出错或超时时放行还是断开 |
| `limit` | 动几次、动到什么时候 |

```json
{
  "name": "swap-alpha",
  "note": "why this rule exists",
  "on": "request",
  "match": { "harness": "kimi-code", "class": "llm", "body": "ALPHA" },
  "do": [ { "replace": "ALPHA", "with": "BRAVO", "literal": true } ],
  "on_error": "forward",
  "limit": { "times": 5, "until": "2026-11-05T12:00:00Z" }
}
```

| 字段 | 含义 |
|---|---|
| `name` | 规则的名字,`[a-z0-9-]+`,就是它的 id。`add` `test` `enable` `disable` `rm` `off` `max-delay` 是保留字 |
| `note` | 可选,写给以后的自己看 |
| `on` | 默认 `request` |
| `whole` | 只用于 `response`:SSE 也收完整个响应再处理。不是 SSE 的响应本来就按整个处理,见 §流式响应 |
| `match` | 全部条件都成立才算命中,见下表 |
| `do` | 按顺序做的动作,见下表 |
| `on_error` | **必填**:`forward` = 发出去,`drop` = 断开连接。两种都留记录 |
| `limit` | 可选:`times` 改动几次后停,`until` 到点停,都从最近一次 `rules enable` 算起。一条请求、一条响应、一条 WS 消息各算一次,不管里面改了几处 |

**匹配条件**。除了 `blocks`,每个键都是通用 HTTP 字段,所以模型调用、遥测、会话同步、文件上传、账户请求都走同一套,规则不围着 LLM 请求转。文本类的改动(替换、改 JSON、按块改)要体是 UTF-8;二进制的流量靠头上的条件、拦截类动作和 `script` 动手。只要是 trocar 解密的连接都能写规则;透传的连接 trocar 看不到内容,规则够不着,`rules test` 写明。

| 键 | `request` | `response` | `ws-client` · `ws-server` |
|---|---|---|---|
| `harness` | 名字、名字列表或 `"any"`,别名按 `resolveHarnesses` 规范化 | 同左 | 同左 |
| `pid` | 只动这个进程。`rules enable` 时钉成 pid + 启动时间,进程没了规则自动停并写明原因,所以 pid 被复用时不会改到别的 agent | 同左 | 同左 |
| `host` · `path` · `method` | 这条请求的 | 它对应的请求的 | 握手请求的 |
| `class` | 流量类别:`llm` `token-count` `session-sync` `telemetry` `files` `account` `other`,或用户自己加的 | 同左 | 同左 |
| `header` | `{ "名字": 条件 }`,请求头 | 响应头 | 握手请求头 |
| `req_header` | 不能 | 它对应的请求的头 | 不能 |
| `body` | 解压后的请求体 | SSE 上是这个事件,其余是解压后的响应体 | 这条消息 |
| `blocks` | 上下文里至少有一块符合选择器,只对模型调用成立 | 不能 | `ws-client` 能 |
| `status` | 不能 | 状态码 | 不能 |
| `event_index` | 不能 | 第几个 SSE 事件,从 0 起;不是 SSE 的响应上不算命中 | 连接上第几条消息,从 0 起 |

想只动一个会话,就匹配 harness 的会话头,比如 `x-claude-code-session-id`:请求规则写在 `header`,响应规则写在 `req_header`。采集端算不出读取侧的完整会话 id,所以不提供 `session` 键。

**条件的写法**,决定了它在哪跑:

| 写法 | 含义 | 在哪跑 |
|---|---|---|
| `"POST"` | 等于 | 主线程,几十纳秒 |
| `"/v1/messages*"` · `"*.anthropic.com"` · `"*telemetry*"` | 前缀、后缀、包含 | 主线程 |
| `["a", "b"]` | 任一 | 主线程 |
| `{ "not": … }` | 取反 | 主线程 |
| `{ "re": "…" }` | 正则 | 工作线程,多一次往返 |

`body` 的字符串值是字面量,意思是「文本里有这段字」,和 `replace` 的默认语义一样。普通 ASCII(不含引号、反斜杠、斜杠、控制字符)直接在字节上查,不解码,因为 JSON 不会转义它们;其余字面量(比如中文,在 JSON 里可能写成 `\uXXXX`)要解码才判得准,归工作线程。

两条硬规定,`rules add` 时不满足就退出 2,什么都不写:
- 必须有 `harness` 或 `pid`。想动全部就明写 `"any"`,不能漏写了变全部。
- 要读体的规则必须同时有 `host`、`path` 或 `class`。「要读体」= 条件里有 `body`、`blocks`,或动作里有 `replace`、`json`、`blocks`、`script`。否则这个 harness 所有流量都要先收全才能转发。

**动作**,十种,分三类:

| 类 | 动作 | 写法 |
|---|---|---|
| 修改 | 替换 | `{ "replace": "正则", "with": "…", "in": "text"\|"body", "literal": true, "blocks": {…} }` |
| | 改头 | `{ "header": "名字", "set": "值" }` 或 `{ "header": "名字", "remove": true }` |
| | 改 JSON | `{ "json": "/model", "set": "…" }` · `{ "json": "/messages/-", "add": {…} }` · `{ "json": "/tools/3", "remove": true }` |
| | 按块改 | `{ "blocks": {…}, "remove": true }` · `"truncate": 4000` · `"set_text": "…"` · `"append_text": "…"` |
| | 脚本 | `{ "script": "/abs/surgery.mjs" }` |
| 拦截 | 扣留 | `{ "hold": true, "release_after_ms": 60000 }`(后一项可选) |
| | 断开 | `{ "drop": true }` |
| | 延迟 | `{ "delay_ms": 3000 }`,上限 60000 |
| 注入 | 代答 | `{ "reply": { "status": 429, "headers": {…}, "body": "…" } }`,上游收不到这条请求 |
| | 插入 | `{ "inject": "<SSE 事件或 WS 消息的原文>" }`,插在命中的事件之前 |

重发不是规则动作,是 `trocar resend` 命令,因为它不在 agent 的路径上。

**动作和位置**:不成立的组合 `rules add` 退出 2。`rules add` 只看 `on` 和 `whole` 就能判,不用猜响应的类型。

| 动作 | `request` | `response` + `whole` | `response` | `ws-client` | `ws-server` |
|---|---|---|---|---|---|
| 替换 | 能 | 能 | 能 | 能 | 能 |
| 改头 | 能 | 能 | 能,只改响应头 | 不能 | 不能 |
| 改 JSON | 能 | JSON 响应能 | `data:` 或响应体是 JSON 时能 | 能 | 能 |
| 按块改 | 能 | 不能 | 不能 | 能 | 不能 |
| 脚本 | 能 | 能 | 能 | 能 | 能 |
| 扣留 | 能 | 能 | 不能(要写 `whole`) | 能 | 扣整轮回复 |
| 断开 | 能 | 能 | 能(已发出的收不回) | 能 | 能 |
| 延迟 | 能 | 能 | 能 | 能 | 能 |
| 代答 | 能 | 不能 | 不能 | 不能 | 不能 |
| 插入 | 不能(用 `json` 或 `blocks`) | 不能 | 能,只在 SSE 上 | 不能 | 能 |

**怎么算改动**,这几句定义全文通用:
- **替换**只对 UTF-8 的体做。`in: "text"`(默认)按 JSON 字符串节点取解码值:没命中的字符串一个字节不动,命中的字符串重新转义,所以换进去的引号和换行不会弄坏 JSON。`in: "body"` 在原始文本上替换。范围是全部字符串,model、签名字段都在内,用 `blocks` 收窄,`--help` 写明。
- **改动范围不超出被命中的字符串或节点**,其余字节一个不动,否则模型的缓存前缀就断了。`json` 和 `blocks` 用 `scanJson` 定位。删除和增加节点之后对结果跑一次 `JSON.parse`,不通过就算规则出错,所以删首、删尾、删相邻块这些情况都兜住了。只改字符串内容的不用跑,它破坏不了结构,而这一步是 2 MB 请求上最贵的一步。
- **改头**不许碰 `content-length`、`transfer-encoding`、`connection`、`upgrade`,碰了退出 2。
- **按块改跨 provider**。`src/dissect/` 给每种线格式加一个函数,产出统一的 `section` `kind` `role` `name`,以及改文本和删除各自对应的路径,Anthropic 也进 registry。规则代码只读这一个函数,没有 provider 分支(不变式 3)。选择器键:`section` `kind` `role` `name` `text` `min_bytes` `max_bytes` `newest` `skip_newest`。块选择器只作用于这条请求自己的字节。
- **脚本是逃生口**:`/abs/surgery.mjs` 是一个 ES 模块,默认导出一个函数,同步异步都行。它收到这条消息(位置、harness、pid、方法、host、路径、状态码、头、`bytes`、UTF-8 时还有 `text`),返回新的体或要改的头,返回空 = 不改。二进制的体也能改。它在规则加载时载入工作线程,之后每次调用只要 14–21 µs;每次起一个 node 进程要 50 ms,差三千倍,所以不做那种写法。凭据类请求头给的是遮住的值。非 JS 程序由脚本自己去调,代价自负。
- **代答**先收全请求再动作。长度由 trocar 算,用户不许写 `content-length`、`transfer-encoding`。`status` 限 200 到 599,204、304 不许带 body,否则 agent 的解析会错位。HEAD 只发头。信封标 `synthesized`,读取侧不把它算进用量和 cache。
- **延迟**不计入最长延迟,它是操作者要的延迟。请求上推迟发给上游;响应上推迟发给 agent。SSE 上每个命中的事件都推迟这么久,后面的事件排在它后面,所以是累加的,用 `event_index` 限到一个事件就是「流停在这里 30 秒」。`off`、`rules off`、`disable` 时正在延迟的立即发出。
- **插入**在命中的事件之前写入。想插在流的开头就写 `event_index: 0`,想插在结束之前就匹配结束事件的字面量,比如 `"body": "message_stop"`。采集端不知道哪个事件是最后一个,这个知识由规则给。

**多条规则都命中时**:
1. 所有修改动作按文件里的顺序执行,每条规则看到的是前一条的结果。
2. 然后任一命中规则有 `drop` 就断开;否则有 `reply` 就代答;否则有 `hold` 就扣留,这时操作者看到改过的版本,原始字节也留着。
3. `hold`、`drop`、`reply` 只能是 `do` 的最后一项。
4. 最后合成一条干预记录。

**四个词,别混**:
- **命中**:`match` 成立。
- **改动**:字节真变了,或者发生了扣留、断开、代答、延迟。`limit.times` 按改动算;超时触发的断开不是规则的 `do`,不计入。
- **跳过**:这条规则本该动手,但没动手,原因在 `skipped.why`(§记录与标注)。
- **转码**:响应解压、改分块,内容没变但线上字节变了,记成 `reframed`,不计入 `limit.times`。

审计行、`intervention` 字段写的是改动和跳过。

## 住哪,和开关什么关系

**住哪**:`~/.trocar/rules.json`(0600),顶层是 `max_delay_ms` 和规则列表,每次修改往 `~/.trocar/logs/rules.ndjson` 追加一行。CLI 写文件,守护进程读;守护进程不在时也能编辑。

**怎么写**:规则文件的写者不止一个(操作者、操作者开的几个 agent、看板),所以所有写者都走 `src/rules/` 的同一个 `edit()`:持锁读、改、rename,再通知守护进程。`classes.json` 是无锁的读改写,这里 MUST NOT 照抄:agent 的 `rules enable` 读到旧文件,能把操作者刚写的 `rules off` 盖掉,回执还说成功。

**什么时候生效**:CLI 写完文件后顺手调一次控制端点 `POST /rules/reload`,守护进程分两步换表:
- 停用、删除在主线程同步生效,不碰工作线程。所以 `rules off` 在线程被慢规则占着时也立刻起作用,还能放开正扣着的请求,哪怕此后再没有新请求。
- 新增、开启等工作线程编好正则、载入脚本才换表。第 0、1 档的判定函数在主线程从校验过的 JSON 构建(闭包不能跨线程传),1000 条规则几毫秒,只在重新加载时发生。

所以 `rules enable` 返回之后的下一条请求就生效。守护进程不在时不用通知:扣留只在它的内存里,它一启动就读文件。守护进程的 1 秒定时器顺带 stat 一次,防止通知丢了。转发路径上不读文件。

**文件坏了**:运行中继续用上一份读得通的规则,留一条 D38 记录并上 `status`,绝不用半份规则。守护进程启动时就读不了的话没有规则可用,同样记录并上 `status`。`rules off` 碰到坏文件时把它改名留着、写空规则,读得出的 `max_delay_ms` 留下,读不出就在回执点名,所以这条命令总能成功。

**规则活着的定义**,四个条件全要:

1. 这个 harness 正在记录(`isRecording`,闸在请求头到达时看一次,和 `record` 同一刻)。
2. 规则开着,没到 `limit`,`pid` 的进程还在。
3. 规则开启的时刻 `armed_at` 严格大于这个 harness 上次 off 的时刻 `off_at`。
4. 规则文件读得通。

第 1 条保证「没有记录的改动不存在」:off 之后到的请求规则不动手,off 之前已经在闸里的按采样走完。歇着的规则(§最长延迟)还算活着,只是这段时间不跑。

| 动作 | 结果 |
|---|---|
| `off` | 被 off 的 harness 上规则停止作用,连接按原有排空规则收尾。`rules.json` 一个字节不碰 |
| 再 `on` | 规则不回来。回执写明「N 条规则在上次 off 时停了,要用就 `trocar rules enable …`」 |
| `rules enable` | 重新打开,从这一刻算。`armed_at = max(现在, off_at + 1 ms)`,所以时钟回拨也不会让 `enable` 静默失效 |
| `rules enable` 在 `off` 之后、`on` 之前 | 下次 `on` 起作用,回执写明。先写规则再开采集是合理的顺序 |
| `update` | **规则不受影响**。update 的目标是「原来开着的照样开着」,脱敏规则不能因为升级悄悄停掉 |
| `uninstall` | 把所有规则转成关闭(和 `rules off` 同一个函数),`rules.json` 留着,`--purge-data` 时删。这样重装之后规则不会自己活过来 |
| `on` 时读不了 `state.json` | 同样先走这个函数,因为 `off_at` 丢了 |

**实现落点**:`off_at` 只在 CLI 的 `desiredOff`(`src/off/orchestrate.mjs`)那一处、真翻转时写,不进 `setDesired`。这样:
- 第二次 `off` 什么都不写(D54 不变)。
- 独立的 `trocar-off`、守护进程死了时的 `off` 走同一处,不需要懂规则。
- `replace-daemon`、Linux 的 exit 路径自然不写,渠道之间没有差异。
- `update` 调 off 时带一个入参,告诉它不写。

`off_at` 只在守护进程启动和处理 `on` 时读入,转发路径不读 `state.json`。

## 引擎

**不变量**:没有活规则时,转发的字节和写入时机都不变。

**还没实现的动作不能假装生效**:`rules enable` 只接受当前引擎支持的动作和位置,其余退出 1(`engine-unsupported`)并说明,所以脱敏规则不会静默不起作用。

### 分派:一条流量只碰可能命中的规则

规则加载时编译成一个索引(`on` → harness → host → 规则),`any` 和通配 host 的规则在加载时并进每个桶。规则数量不影响查询。

**三档代价**,规则编译时就定了每条规则在哪一档:

| 档 | 包括 | 在哪 | 代价 |
|---|---|---|---|
| 0 | 索引:`on`、harness、host | 主线程 | 12–76 ns |
| 1 | 方法、路径、类别、请求头、pid、状态码的字符串比较;普通 ASCII 字面量在字节上的查找;不用转义的字面量替换(`in: "body"`,或者模式和替换值都是普通 ASCII) | 主线程 | 每条候选规则约 60 ns,字节查找 33 KB 约 9 µs |
| 2 | 任何正则;其余字面量;`json`;`blocks`;`script` | 工作线程 | 往返 9–22 µs,加上传体的时间 |

**闸只在连接空闲时才看字节**。这一句决定了闸的全部边界问题:它从不自己猜请求从哪开始,而是问 tee(`boundary()`,drain 已经在用的那个)。

| tee 怎么答 | 闸怎么做 |
|---|---|
| 空闲(`idle`),不 `blind`,不是 WebSocket | 这是请求边界,可以读请求头 |
| 不空闲 | 请求体或响应还在走,字节原样过,闸不看 |
| 不空闲,但请求这一侧已收完 | 前一条响应没结束就来了下一条(pipelining)。这条请求不改,跳过 `pipelined`,按 `on_error` 走 |
| `blind` 或 WebSocket | 闸对这条连接永久让路 |

所以规则表变了之后,开着的长连接在下一个空闲点接手,不用等 agent 重连,也不会在一条请求中间或者已经升级的连接上乱读。`boundary()` 加两个字段:`ws` 和请求侧是否收完。

**路线**,每一步不成立就走原路,后面的步骤都不发生:

1. 这条连接的 harness + host 桶里有活规则吗。host 在 CONNECT 或 SNI 时就知道,答案缓存在连接上,之后每段字节只比一次规则表版本(一次整数比较)。明文 HTTP 的连接一条连接可以换 host,按每条请求的 `Host` 查。**绝大多数流量到这里就结束了**:不框定、不解析,和今天一样。
2. 这一段字节落在请求边界吗(见上表)。不是 HTTP(`classify` 的结果)就永久让路:解密连接上走的未知协议今天照常转,规则不能把它们冻住。
3. 收全请求头,当场采样 `record`、保存级别、时间戳,让 tee 预设这条交换(建好 `ex`、分配 `seq`)。这一步必须在这里,否则 off 放行的请求到 tee 时开关已关,会漏写信封。请求头超过 64 KiB,或者等它收全超过最长延迟,就放走已扣的字节,永久让路,写一条 D38。
4. 查索引拿到候选规则,通常 0 到 3 条,跑第 1 档。没有幸存者就放走:这条请求后面的字节不进闸,它的响应也不进闸,闸回去等下一个空闲点,**不解析 body,不读 body,不留第二个 framer 常跑**。
5. 幸存的规则只看头,动作也只在头上(改头、延迟):做完放走,请求体照常流过去,不缓冲,工作线程不参与。
6. 幸存的规则有第 2 档的头条件(正则):一次线程往返。
7. 幸存的规则要读体,或者动作是 `drop`、`reply`、`hold`:收全请求(chunked 的请求在这里解块,改发 `content-length`,头的变化记下来)。`drop` 要收全是因为信封要记下 agent 发的字节;只看头的 `drop` 不读体,也不等线程。
8. 要读体的交给工作线程。字面量在字节上查,**命中了才解码**:`isUtf8` 和 `indexOf` 是字节操作,512 KB 上都在 0.1 ms 左右;解码成字符串要 1.4 ms,贵十倍以上。
9. 算出改动,**先写审计行,写成功了才发**。写不成算规则出错。没有记录的改动不允许存在。
10. 记录器看到的是真正发给上游的字节(D33),带着第 3 步的采样值。

**响应要不要进闸,在请求时就定了**:只有 `host`、`path`、`method`、`class`、`req_header` 这些请求侧条件成立的 `on: response` 规则才进这条响应的计划,计划是空的,响应就走原路。

**闸放在哪**:agent 的每一段字节都先过这一问,包括新连接的第一段(`routeInner` 和 `handleHttp` 现在会在进 `relay()` 之前就写给上游,改成 `relay(c, u, first)`,无规则时字节和写入顺序不变)。

**响应这一侧**:闸接管的响应,原始 chunk 留在闸里,判完才交给 tee,tee 收一个到达时间戳保住 `tsStart` 和 `tsEnd`。这样 `intervention` 在最后一块之前就写好了。`drain` 也因此自然等着:tee 没看到最后一块,连接就不算闲。

**一个出口**:上游来的字节和合成的字节走同一个函数 `emitUpstream(bytes)`(`beforeUpstream` → tee → 写 agent → `afterUpstream`)。所以代答的响应一样能带上 `Connection: close`,一样能让 off 的排空收尾,不留一条经 trocar 的空闲连接。

### 最长延迟

- **一个设置**:`max_delay_ms`,存在 `rules.json` 顶层,默认 200 ms,范围 1 到 60000。看板设置页和 `trocar rules max-delay [<ms>]` 都能查和改。**没有单条规则的预算**:第二档算得慢的脚本就把这个数调大,代价是坏规则也能让 agent 多等这么久,这件事一个数说得清。
- **为什么是 200 ms**:一次模型调用是秒级,200 ms 看不出来;命中改写一条 8 MB 的请求在重负载的开发机上要 160 ms,放得下真实的大请求。设小了,健康的规则会在大请求上超时。
- **怎么算**:每个单元(一条请求、一个事件、一条消息)的时钟从它到齐算起,排队和线程往返都在内。不算 agent 发完请求体的时间、`hold`、`delay_ms`。所以流上规则跟不上时,排在后面的事件等得越来越久,到点就算超时,不需要另一个「滞后上限」,也不需要反压。
- **第 0、1 档不计时**,它们是有界的字符串比较。
- **到点先看工作线程是不是已经算完了**:共享内存里有完成标记。定时器和转发在同一个事件循环上,大记录同步写信封时循环会停,定时器可能先于已经到了的结果执行。已完成就 `setImmediate` 再取结果,只有确实还在跑才算超时。
- **超时算一种出错**,按 `on_error` 走。**这个判定只用主线程已有的东西,不等任何线程,所以 agent 绝不会被卡住。**

**超时的后果**:

1. 这个任务里所有规则的**修改**作废,发原始字节,不发半改的字节。脱敏规则写 `on_error: drop`,就不会被别的规则的超时绕过去。
2. 第 0、1 档已经判定的 `drop`、`reply`、`hold`、`delay` 不受影响,继续按§规则「多条规则都命中时」的次序作用在原始字节上。所以挡遥测的规则不会被一条慢的修改规则带着放行。
3. 这个任务里的规则,有 `on_error: drop` 的就断开。
4. 每条没应用的规则都写进 `skipped`:超时的那条 `timeout`,同任务被连累的 `peer-timeout`,排队到超时的 `queued`。只有 `timeout` 算在规则头上。

**出错时听谁的**:这条请求上所有还没判定的候选规则里取最严的 `on_error`,有 `drop` 就断开。

**晚到的结果**丢弃:每个任务带规则表世代和一个 `settled` 标记,放行、断开、连接结束时置位。结果回来先比世代:`rules off`、`disable`、`rm` 之后,算着的结果作废,发原始字节。`off` 不作废:§分派路线第 3 步已经采样的请求按采样走完。

**坏规则的隔离**:

- **有活的第 2 档规则就有两个工作线程常驻**,规则加载时预热,所以闲下来之后的第一条请求不用等线程启动(30 ms)。没有第 2 档规则就没有线程。阻塞在消息端口上的线程没有唤醒,常驻不花钱。
- **队列在主线程**,每个线程同一时间只有一个任务,派给空闲的那个。
- **杀线程的时钟从任务开始运行算**,到最长延迟就杀(实测 1 到 4 ms),排队超时的任务作废但不杀线程。不等 `terminate()` 完成就起替补(线程卡在同步的原生调用里时 `terminate()` 要等它返回)。替补约 30 ms 起来,这段时间任务排队,超时按上面走,两个线程同时被杀也一样。
- 工作线程把任务号、当前规则号、每条规则已用的时间写进共享内存,所以超时时不用通信就知道是谁的错:归已用时间最多的那条。
- **连续 3 次超时的规则歇 60 秒**:这段时间不跑,第 0、1 档成立的请求直接按它的 `on_error` 走,写 `skipped: cooling`。60 秒后放一条请求试,成了就恢复,没成再歇 60 秒。`rules enable` 立刻恢复,守护进程重启重置。所以一条坏规则只让 agent 多等三次最长延迟,而且不用人管就能恢复。`on_error: drop` 的规则歇着时会断开它第 0、1 档匹配到的请求,所以这类规则的条件要写窄,`rules add` 回执提醒。
- **内存**:工作线程设 `resourceLimits`,JS 堆超限只死这个线程。Buffer 不受这个限制,脚本自己分配巨量 Buffer 能拖垮守护进程,这时所有 agent 的连接都会断。脚本是操作者自己的代码,`--help` 写明。工作线程的 `env` 给空,脚本读不到守护进程的环境变量。
- **脚本载入带 2 秒时限**,顶层死循环的脚本会让 `rules enable` 失败并写明,不会占着线程。
- **编译**:正则长度上限 4 KB,规则数上限 1000。实测 1 MB 的超大正则编译要 0.9 到 4.7 秒,所以这个上限是必要的。

### 其余规定

**要动体时动不了的情况**。这张表只管替换、改 JSON、按块改和要读体的匹配,它们做不了,就写 `skipped`,按 `on_error` 走:

| 情况 | `skipped.why` |
|---|---|
| `Expect: 100-continue`(等请求体会和 agent 互相等死) | `expect-continue` |
| 解不开的 `content-encoding`(Node 22.15 以前没有 zstd) | `encoding` |
| 体不是 UTF-8(`script` 不受这一条限制) | `not-utf8` |
| 超过 64 MiB 的请求体或响应 | `too-big` |
| 超过 1 MiB 的 SSE 事件 | `event-too-big` |
| 多行 `data:` 的 SSE 事件 | `multi-line-event` |

**只看头的动作不受上面这张表限制**:改头、`delay`、只看头的 `drop` 一律照做,所以挡遥测的规则挡得住 chunked 和 protobuf 的请求。`reply`、`hold` 要收全请求,超过 64 MiB 就按 `on_error`。

**闸整个不动手的情况**,规则都不生效,写 `skipped`,按 `on_error` 走:

| 情况 | `skipped.why` |
|---|---|
| 前一条响应没结束时到达的请求 | `pipelined` |
| 这条连接的记录器已经停了(`framerError`、丢了 tee),和 `drain.loseTee` 同样的做法 | `no-recorder` |
| 明文请求经带凭据的用户代理:`forward.mjs` 按读入偏移插 `Proxy-Authorization`,闸改了长度或没写出去,用户的代理口令就会被插进请求体发给上游。这条路上闸不动手 | `credentialed-hop` |
| WebSocket 的 Upgrade 请求,WebSocket 落地之前:闸对这条连接永久让路,留一条「WebSocket: not changed」 | `ws-unsupported` |

**保存级别**:这个类别是 `log` 时,请求规则命中就按 `full` 记。响应规则要看到响应才知道命中,所以请求开始时,只要有活的响应规则的请求侧条件排除不了这条请求,就按 `full` 记,否则原始字节存不下,违反不变式 2。

**改完之后**:`content-length` 按新长度重写,其余头的顺序和写法不动。压缩的请求体解压后改,发出时去掉 `content-encoding`,请求头的变化也记下来。zstd 改明文上游接不接受实验室验不到,这一条写在 `--help` 里。

**改动范围**:`flow.mjs` 的入口、`relay`、`start`、`upstreamGone`、一个 `emitUpstream`;`exchange.mjs` 加一个预设入口和 `boundary()` 两个字段;`store.mjs` 的 `audit` 改成返回成败;`drain` 不动,只由 flow 组合 boundary。其余在新目录 `src/collector/core/intervene/`。规则的匹配和修改放在 `src/rules/`,引擎、`rules test`、`resend`、看板都走它的同一个入口。内建动作是纯函数,同样的规则集、同样的输入字节,三条路算出的结果相同,验收 9 守住。
