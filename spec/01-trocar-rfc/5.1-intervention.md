# trocar · RFC 5.1 — 规则:修改 / 拦截 / 注入 / 重发(agent 界的 Burp Suite)

> **状态**:方向 **D30**,记录形状 **D33**,规则系统 **D79**。
> **前置**:采集 = [4.1](4.1-capture-sources.md);引擎 = [4.6](4.6-process-collector.md);统一信封 = [4.1](4.1-capture-sources.md) §统一原始信封;归一化 = [3.2](3.2-normalized-model.md);命令 = [1.6](1.6-cli.md) §4.4 – §4.6;看板 = [2.7](2.7-rules-view.md) · [1.11](1.11-settings.md) §规则;写通道的门 = D26。

## 不变式

**规则的任何代码、任何资源用量,都不能让守护进程死掉,也不能让 agent 的连接断开。** 违反就是缺陷,不靠文档、`--help` 或默认值放行。

- 「任何」包括死循环、抛异常、主动退出、段错误、吃光内存或 CPU、灾难正则、超大或恶意的规则文件、大量扣留、超大的请求和响应。
- 唯一的例外是操作者写在规则里的断开:`do` 里的 `drop` 和 `on_error: drop`。它只断开这条规则碰到的这一条连接,「碰到」= 这条规则在这一刻判得了的条件都成立,判不了的条件算排除不了(§分派)。`on_error: drop` 的意思是「这条规则判不了这个单元就断开」,判不了的原因不只是它自己出错:账满了、规则进程起不来、同一单元上别的规则超时都算。脱敏规则靠这句话才不漏,所以不分原因。
- 上游自己关连接不是规则弄断的。请求还在闸里、一个字节都没发给上游时上游关了,trocar 重拨一次,agent 的连接不断(§扣留)。走隧道或带凭据的用户代理的连接不能替操作者再拨一次([4.8](4.8-win-collector.md) §5.2),这种连接上等得比上游的闲置超时久,连接跟着关,`rules add` 的回执写明。
- 连续崩溃跳闸(§住哪)时规则系统整个没开,这是 `on_error: drop` 唯一绕得过去的情况,否则断不开崩溃循环。`status` 第一行写明。
- 规则出任何事,这条请求按 `on_error` 走。别的连接的转发不受影响;它们的第 2 档规则可能排队或跳过(`queued`、`no-runner`),按各自的 `on_error` 走。
- 防的是 bug 和失控。同一用户的程序不用规则也能直接杀守护进程,蓄意破坏不在规则能防的范围内(§安全边界)。

守卫:验收 12b – 12h、38 – 62,mac、win、Linux 都跑。

## Goal

trocar 不只看清 agent 发给模型的每一比特,还能动手术:改一条请求或响应、扣下来、断开、替上游回答、往流里插东西、把一条历史请求改完再发一次。用途是调试和受控实验,比如「这一步换掉某块上下文,模型会怎么答」「agent 碰到 429 怎么退避」「这个工具结果截短一半还能不能完成任务」。

操作者可以是人,也可以是操作者开的 agent:agent 靠 `trocar --help` 就能走完「写规则、在采到的记录上试、真发实验、上线、看结果、收手」这一圈。

规则在热路径上,坏规则能卡死 agent。所以这个单元的第一条设计约束是**没有用的工作一点不做,有用的工作有上限**:一条流量只碰可能命中的规则,没有候选规则时开销接近零;规则再慢,agent 也只多等最长延迟这么久;规则再坏,也弄不断 agent 的连接:规则的代码不进守护进程。

## 已定

1. **不分模式**(D30)。修改、拦截、注入、重发是采集器本身的能力,不是另一个产品形态。
2. **授权 = 操作者**(D30 · D79①)。操作者是运行 trocar 的人和这个人开的 agent。没有操作者的显式操作或开着的规则时,trocar 原样转发,不主动发请求、不改包。
3. **凭据**(D30)。允许带着 agent 自己的凭据转发改后的请求,也允许重发历史请求;只限操作者触发的这两类动作。用户代理的凭据不在此列([4.8](4.8-win-collector.md) §5.2)。
4. **源真相与标注**(D30 · D33)。上游一侧逐字存,agent 一侧由补丁逐字节还原并校验;外加一条审计记录(谁、何时、改了什么、依据哪条规则)。MUST NOT 用改后覆盖原始。看板 MUST 就地标明哪些请求被改过、哪些是 trocar 发起的、哪些规则没能应用。(不变式 2、4)
5. **审计**(D30)。每次改动、扣留、放行、断开、代答、重发、超时都留可追溯的记录,操作者能查询和导出。
6. **规则默认关,先试再开**(D79③)。`rules add` 写入的规则是关着的;`--replace` 之后也是关着的。
7. **出错策略必填**(D79④)。每条规则写明 `on_error`,没有默认值。超时是一种出错。
8. **`off` 让规则停下**(D79⑥)。再 `on` 不会自己回来,要重新 `rules enable`。`update` 不算 off。`uninstall` 把规则全部转成关闭。
9. **规则只能改这条请求里的字节**(D79⑨)。服务端存着的上下文碰不到;重发续写请求要先补全成完整请求,补全的那份标明是重建的。

## 规则

规则系统五个词讲完:

| 词 | 意思 |
|---|---|
| `on` | 在哪动手:`request`、`response`、`ws-client`(agent 发的 WS 消息)、`ws-server`(服务端发的 WS 消息) |
| `match` | 什么时候动手 |
| `do` | 动什么手 |
| `on_error` | 出错或超时时放行还是断开 |
| `limit` | 动几次、动到什么时候 |

```json
{
  "name": "swap-alpha",
  "note": "why this rule exists",
  "on": "request",
  "match": { "harness": "kimi-code", "class": "llm", "body": "ALPHA" },
  "do": [ { "replace": "ALPHA", "with": "BRAVO", "literal": true } ],
  "on_error": "forward",
  "limit": { "times": 5, "until": "2026-11-05T12:00:00Z" }
}
```

| 字段 | 含义 |
|---|---|
| `name` | 规则的名字,`[a-z0-9-]+`,就是它的 id。`add` `test` `enable` `disable` `rm` `off` `max-delay` 是保留字 |
| `note` | 可选,写给以后的自己看 |
| `on` | 默认 `request` |
| `whole` | 只用于 `response`:收完整个响应再处理,agent 这段时间收不到字节。不写时 SSE 逐事件,其余最多等最长延迟,见 §流式响应 |
| `match` | 全部条件都成立才算命中,见下表 |
| `do` | 按顺序做的动作,见下表 |
| `on_error` | **必填**:`forward` = 发出去,`drop` = 断开连接。两种都留记录 |
| `limit` | 可选:`times` 改动几次后停,`until` 到点停,都从最近一次 `rules enable` 算起。一条请求、一条响应、一条 WS 消息各算一次,不管里面改了几处 |

**匹配条件**。除了 `blocks`,每个键都是通用 HTTP 字段,所以模型调用、遥测、会话同步、文件上传、账户请求都走同一套,规则不围着 LLM 请求转。文本类的改动(替换、改 JSON、按块改)要体是 UTF-8;二进制的流量靠头上的条件、拦截类动作和 `script` 动手。只要是 trocar 解密的连接都能写规则;透传的连接 trocar 看不到内容,规则够不着,`rules test` 写明。

| 键 | `request` | `response` | `ws-client` · `ws-server` |
|---|---|---|---|
| `harness` | 名字、名字列表或 `"any"`,别名按 `resolveHarnesses` 规范化 | 同左 | 同左 |
| `pid` | 只动这个进程。`rules enable` 时钉成 pid + 启动时间,进程没了规则自动停并写明原因,所以 pid 被复用时不会改到别的 agent | 同左 | 同左 |
| `host` · `path` · `method` | 这条请求的 | 它对应的请求的 | 握手请求的 |
| `class` | 流量类别:`llm` `token-count` `session-sync` `telemetry` `files` `account` `other`,或用户自己加的 | 同左 | 同左 |
| `header` | `{ "名字": 条件 }`,请求头 | 响应头 | 握手请求头 |
| `req_header` | 不能 | 它对应的请求的头 | 不能 |
| `body` | 解压后的请求体 | SSE 上是这个事件,其余是解压后的响应体 | 这条消息 |
| `blocks` | 上下文里至少有一块符合选择器,只对模型调用成立 | 不能 | `ws-client` 能 |
| `status` | 不能 | 状态码 | 不能 |
| `event_index` | 不能 | 第几个 SSE 事件,从 0 起;不是 SSE 的响应上不算命中 | 连接上第几条消息,从 0 起 |

想只动一个会话,就匹配 harness 的会话头,比如 `x-claude-code-session-id`:请求规则写在 `header`,响应规则写在 `req_header`。采集端算不出读取侧的完整会话 id,所以不提供 `session` 键。

**条件的写法**,决定了它在哪跑:

| 写法 | 含义 | 在哪跑 |
|---|---|---|
| `"POST"` | 等于 | 主线程,几十纳秒 |
| `"/v1/messages*"` · `"*.anthropic.com"` · `"*telemetry*"` | 前缀、后缀、包含 | 主线程 |
| `["a", "b"]` | 任一 | 主线程 |
| `{ "not": … }` | 取反 | 主线程 |
| `{ "re": "…" }` | 正则 | 规则进程,多一次往返 |

超过 256 字节的字面量一律归规则进程。在重复内容上,更长的字面量让查找从线性退化成 体长 × 字面量长:256 KiB 的体上,300 字节以内最坏 0.2 ms,512 字节 66 ms,64 KiB 4 秒。

`body` 的字符串值是字面量,意思是「文本里有这段字」,和 `replace` 的默认语义一样。JSON 里同一段字可以有不同的写法(Go 的 `encoding/json` 默认把 `<` `>` `&` 写成 `\u003c` 这种样子,Python 把中文写成 `\uXXXX`),所以字节上的查找只在结果确定时算数,其余归规则进程解码后判:

- 字面量只含字母、数字、空格和 `_ - . :`,才走字节查找。别的字符一律归第 2 档,所以 `<system-reminder>` 这样的字面量不走快路。
- 字节上查到了,而且前一个字节不是反斜杠:命中。
- 字节上没查到,体里也没有 `\u`:不中。体里有 `\u`:归第 2 档判,因为任何字符都能这样写。
- 压缩的体不走快路:字节上看到的是压缩后的内容,解压只在规则进程里做。

三条硬规定,`rules add` 时不满足就退出 2,什么都不写:
- 必须有 `harness` 或 `pid`。想动全部就明写 `"any"`,不能漏写了变全部。
- 要读体的规则必须同时有 `host`、`path` 或 `class`。「要读体」= 条件里有 `body`、`blocks`,或动作里有 `replace`、`json`、`blocks`、`script`。否则这个 harness 所有流量都要先收全才能转发。
- `on_error: drop` 的规则必须有 `host`。想全部就明写 `"*"`,和 `harness` 写 `"any"` 同一个规矩:h2-only、不是 HTTP 的连接上 `class`、`path` 都判不了,这条规则断不断只看 `harness` 和 `host`,所以范围要写出来。回执写明它会断哪几类判不了的连接。

**动作**,十种,分三类:

| 类 | 动作 | 写法 |
|---|---|---|
| 修改 | 替换 | `{ "replace": "正则", "with": "…", "in": "text"\|"body", "literal": true, "blocks": {…} }` |
| | 改头 | `{ "header": "名字", "set": "值" }` 或 `{ "header": "名字", "remove": true }` |
| | 改 JSON | `{ "json": "/model", "set": "…" }` · `{ "json": "/messages/-", "add": {…} }` · `{ "json": "/tools/3", "remove": true }` |
| | 按块改 | `{ "blocks": {…}, "remove": true }` · `"truncate": 4000` · `"set_text": "…"` · `"append_text": "…"` |
| | 脚本 | `{ "script": "/abs/surgery.mjs" }` |
| 拦截 | 扣留 | `{ "hold": true, "release_after_ms": 60000 }`,后一项必填 |
| | 断开 | `{ "drop": true }` |
| | 延迟 | `{ "delay_ms": 3000 }`,上限 60000 |
| 注入 | 代答 | `{ "reply": { "status": 429, "headers": {…}, "body": "…" } }`,上游收不到这条请求 |
| | 插入 | `{ "inject": "<SSE 事件或 WS 消息的原文>" }`,插在命中的事件之前 |

重发不是规则动作,是 `trocar resend` 命令,因为它不在 agent 的路径上。

**动作和位置**:不成立的组合 `rules add` 退出 2。`rules add` 只看 `on` 和 `whole` 就能判,不用猜响应的类型。

| 动作 | `request` | `response` + `whole` | `response` | `ws-client` | `ws-server` |
|---|---|---|---|---|---|
| 替换 | 能 | 能 | 能 | 能 | 能 |
| 改头 | 能 | 能 | 能,只改响应头 | 不能 | 不能 |
| 改 JSON | 能 | JSON 响应能 | `data:` 或响应体是 JSON 时能 | 能 | 能 |
| 按块改 | 能 | 不能 | 不能 | 能 | 不能 |
| 脚本 | 能 | 能 | 能 | 能 | 能 |
| 扣留 | 能 | 能 | 不能(要写 `whole`) | 能 | 扣整轮回复 |
| 断开 | 能 | 能 | 能(已发出的收不回) | 能 | 能 |
| 延迟 | 能 | 能 | 能 | 能 | 能 |
| 代答 | 能 | 不能 | 不能 | 不能 | 不能 |
| 插入 | 不能(用 `json` 或 `blocks`) | 不能 | 能,只在 SSE 上 | 不能 | 能 |

**怎么算改动**,这几句定义全文通用:
- **替换**只对 UTF-8 的体做。`in: "text"`(默认)按 JSON 字符串节点取解码值:没命中的字符串一个字节不动,命中的字符串重新转义,所以换进去的引号和换行不会弄坏 JSON。`in: "body"` 在原始文本上替换。范围是全部字符串,model、签名字段都在内,用 `blocks` 收窄,`--help` 写明。
- **改动范围不超出被命中的字符串或节点**,其余字节一个不动,否则模型的缓存前缀就断了。`json` 和 `blocks` 用 `scanJson` 定位。删除和增加节点之后对结果跑一次 `JSON.parse`,不通过就算规则出错,所以删首、删尾、删相邻块这些情况都兜住了。只改字符串内容的不用跑,它破坏不了结构,而这一步是 2 MB 请求上最贵的一步。
- **扣留的 `release_after_ms` 必填,没有默认值**,是 1 到 86400000 的整数。到点按 `on_error` 走:`forward` 发手里的字节,`drop` 断开。agent 也是操作者,给自己加一条扣留又没人看着时,到点自己解开。确实要长等的人写一个大数。
- **头的写法**由一个校验函数管,`rules add`、守护进程载入规则、脚本的结果都走它,守护进程不信 CLI。名字是 RFC 9110 的 token,值不含控制字符,所以 CR、LF 进不了头。`content-length`、`transfer-encoding`、`connection`、`upgrade` 不管大小写都不许碰,`reply.headers` 也一样。规则让一个头增大的总量 ≤ 8 KiB:Node 系的客户端收到超过 16 KiB 的响应头直接报错,连接就断了。不合规的 `rules add` 退出 2,运行时算规则出错。
- **按块改跨 provider**。`src/dissect/` 给每种线格式加一个函数,产出统一的 `section` `kind` `role` `name`,以及改文本和删除各自对应的路径,Anthropic 也进 registry。规则代码只读这一个函数,没有 provider 分支(不变式 3)。选择器键:`section` `kind` `role` `name` `text` `min_bytes` `max_bytes` `newest` `skip_newest`。块选择器只作用于这条请求自己的字节。
- **脚本是逃生口**:`/abs/surgery.mjs` 是一个 ES 模块,默认导出一个函数,同步异步都行。它收到这条消息(位置、harness、pid、方法、host、路径、状态码、头、`bytes`、UTF-8 时还有 `text`),返回新的体或要改的头,返回空 = 不改。二进制的体也能改。它在规则加载时载入自己的规则进程(§隔离),之后每次调用是一次进程往返,30–70 µs;每次起一个 node 进程要 50 ms,差一千倍,所以不做那种写法。凭据类请求头给的是遮住的值。`rules enable` 把文件的 sha256 记进规则(`script_sha256`),载入时对不上就不载入,这条规则不活,写 `script-load-failed`,所以没试过的改动不会上线:改了脚本要重新 `rules enable`,这时这个脚本的进程换新的。审计带这个 sha256。脚本不能起子进程、不能写文件,要用别的程序就走 HTTP(`fetch`),比如一个操作者在本机起的服务。这是能力边界,`--help` 的正文写明。
- **代答**先收全请求再动作,`Expect: 100-continue` 的请求除外(§其余规定)。长度由 trocar 算,用户不许写 `content-length`、`transfer-encoding`。`status` 限 200 到 599,204、304 不许带 body,否则 agent 的解析会错位。HEAD 只发头。信封标 `synthesized`,读取侧不把它算进用量和 cache。
- **延迟**不计入最长延迟,它是操作者要的延迟。请求上推迟发给上游;响应上推迟发给 agent。SSE 上每个命中的事件都推迟这么久,后面的事件排在它后面,所以是累加的,用 `event_index` 限到一个事件就是「流停在这里 30 秒」。`off`、`rules off`、`disable` 时正在延迟的立即发出。
- **插入**在命中的事件之前写入。想插在流的开头就写 `event_index: 0`,想插在结束之前就匹配结束事件的字面量,比如 `"body": "message_stop"`。采集端不知道哪个事件是最后一个,这个知识由规则给。

**多条规则都命中时**:
1. 所有修改动作按文件里的顺序执行,每条规则看到的是前一条的结果。
2. 然后任一命中规则有 `drop` 就断开;否则有 `reply` 就代答;否则有 `hold` 就扣留,这时操作者看到改过的版本,原始字节也留着。
3. `hold`、`drop`、`reply` 只能是 `do` 的最后一项。
4. 最后合成一条干预记录。

**四个词,别混**:
- **命中**:`match` 成立。
- **改动**:字节真变了,或者发生了扣留、断开、代答、延迟。`limit.times` 按改动算;超时触发的断开不是规则的 `do`,不计入。
- **跳过**:这条规则本该动手,但没动手,原因在 `skipped.why`(§记录与标注)。
- **转码**:换请求的 `accept-encoding`、响应改分块,内容没变但线上字节变了,记成 `reframed`。不计入 `limit.times`,不写审计行,记在信封里(§记录与标注)。

审计行、`intervention` 字段写的是改动和跳过。

## 住哪,和开关什么关系

**住哪**:`~/.trocar/rules.json`(0600),顶层是 `max_delay_ms` 和规则列表,每次修改往 `~/.trocar/logs/rules.ndjson` 追加一行。CLI 写文件,守护进程读;守护进程不在时也能编辑。

**怎么写**:规则文件的写者不止一个(操作者、操作者开的几个 agent、看板),所以所有写者都走 `src/rules/` 的同一个 `edit()`:持 `rules.lock` 读、校验、改、rename。调用方写完调 `POST /rules/reload`,`edit()` 只管文件。`classes.json` 是无锁的读改写,这里 MUST NOT 照抄:agent 的 `rules enable` 读到旧文件,能把操作者刚写的 `rules off` 盖掉,回执还说成功。一次编辑是毫秒级,所以锁的规矩很短:等锁最多 2 秒,持锁超过 2 秒的一律抢过来,不看进程身份;写者 rename 之前确认锁还是自己的,被抢了就放弃并报错。`edit()` 先 `stat`,只读普通文件,FIFO 卡不住它。

**什么时候生效**:收到 `POST /rules/reload`,守护进程分两步换表:
- 停用、删除在主线程同步生效,不碰规则进程。
- 新增、开启等规则进程编好正则、载入脚本才换表。内建的两个进程轮流载入,所以载入时也有一个进程在接任务。换表之前比较文件世代,不是最新的就丢掉重来:`rules enable` 等编译时跑了 `rules off`,旧的编译结果不会把规则放回来。第 0、1 档的判定函数在主线程从校验过的 JSON 构建,1000 条规则几毫秒,只在重新加载时发生。

所以 `rules enable` 返回之后的下一条请求就生效。载入失败时规则转回关闭,退出 1;守护进程不在时到它下次启动才知道,写 `script-load-failed`,`status` 显示。守护进程不在时不用通知:扣留只在它的内存里,它一启动就读文件。守护进程的 1 秒定时器顺带 stat 一次,防止通知丢了。转发路径上不读文件。

**`rules off` 不依赖磁盘和锁**:它先调 `POST /rules/off`,守护进程记下 `rules_off_at`,在内存里停下全部规则、放开扣着的请求,哪怕规则进程被慢规则占着、此后再没有新请求。然后才走 `edit()` 写文件。规则活着的第 3 条按 `rules_off_at` 判,所以文件写不成时(磁盘满、家目录只读、锁被占),后面任何写者、任何在途的编译都放不回旧规则,只有带新 `armed_at` 的 `rules enable` 才回来。`rules_off_at` 随 `rules-stats.json` 落盘。回执写明规则已停、文件没改;这份文件也写不进、守护进程又重启时规则会回来,回执同样写明。

**文件坏了**:运行中继续用上一份读得通的规则,留一条 D38 记录并上 `status`,绝不用半份规则。守护进程启动时就读不了的话没有规则可用,同样记录并上 `status`。`rules off` 碰到坏文件时把它改名留着、写空规则,读得出的 `max_delay_ms` 留下,读不出就在回执点名。不是普通文件时同样处理。

**连续崩溃时不开规则**。`rules.json` 在磁盘上,launchd、systemd、Windows 的监督进程都会把守护进程拉起来,所以万一有规则让守护进程死了,重启之后还会死,门一直断着。这是最后一道保险:守护进程启动时,上次没有干净退出(`noteUncleanStop`)、和这次是同一次开机(`boot_id`,所以重启机器不算)、当时有活规则,`collector/rules-stats.json` 的 `unclean_stops` 加一;到 2 就跳闸:守护进程自己做一次内存里的 `rules off`,写 D38 `rules-tripped`,`status` 第一行写明。所以恢复的条件只有一个:`rules enable`,这时写 `rules-ok` 结束这个状况。跳闸时规则文件一个字节不解释,脱敏规则不生效,`on_error: drop` 也不断开(§不变式)。稳定运行 10 分钟 `unclean_stops` 清零。`rules-stats.json` 写临时文件再 rename。

**规则活着的定义**,四个条件全要:

1. 这个 harness 正在记录(`isRecording`,闸在请求头到达时看一次,和 `record` 同一刻)。
2. 规则开着,没到 `limit`,`pid` 的进程还在。
3. 规则开启的时刻 `armed_at` 严格大于这个 harness 上次 off 的时刻 `off_at`,也严格大于 `rules_off_at`。
4. 规则文件读得通,也没有因为连续崩溃停着。

第 1 条保证「没有记录的改动不存在」:off 之后到的请求规则不动手,off 之前已经在闸里的按采样走完。歇着的规则(§隔离)还算活着,只是这段时间不跑。

| 动作 | 结果 |
|---|---|
| `off` | 被 off 的 harness 上规则停止作用,连接按原有排空规则收尾。`rules.json` 一个字节不碰 |
| 再 `on` | 规则不回来。回执写明「N 条规则在上次 off 时停了,要用就 `trocar rules enable …`」 |
| `rules enable` | 重新打开,从这一刻算。`armed_at = max(现在, off_at + 1 ms, rules_off_at + 1 ms)`,所以时钟回拨也不会让 `enable` 静默失效 |
| `rules enable` 在 `off` 之后、`on` 之前 | 下次 `on` 起作用,回执写明。先写规则再开采集是合理的顺序 |
| `update` | **规则不受影响**。update 的目标是「原来开着的照样开着」,脱敏规则不能因为升级悄悄停掉 |
| `uninstall` | 把所有规则转成关闭(和 `rules off` 同一个函数),`rules.json` 留着,`--purge-data` 时删。这样重装之后规则不会自己活过来 |
| `on` 时读不了 `state.json` | 同样先走这个函数,因为 `off_at` 丢了 |

**实现落点**:`off_at` 只在 CLI 的 `desiredOff`(`src/off/orchestrate.mjs`)那一处、真翻转时写,不进 `setDesired`。这样:
- 第二次 `off` 什么都不写(D54 不变)。
- 独立的 `trocar-off`、守护进程死了时的 `off` 走同一处,不需要懂规则。
- `replace-daemon`、Linux 的 exit 路径自然不写,渠道之间没有差异。
- `update` 调 off 时带一个入参,告诉它不写。

`off_at` 只在守护进程启动和处理 `on` 时读入,转发路径不读 `state.json`。

## 引擎

**不变量**:没有活规则时,转发的字节和写入时机都不变。

**还没实现的动作不能假装生效**:`rules enable` 只接受当前引擎支持的动作和位置,其余退出 1(`engine-unsupported`)并说明,所以脱敏规则不会静默不起作用。

### 分派:一条流量只碰可能命中的规则

规则加载时编译成一个索引。只有精确 host 的规则进 `on` → harness → host 的桶;通配 host 和不写 host 的规则进 `on` → harness 的一张表,`any` 是一个普通的 harness 键。一条连接查这几处,几次 Map 查询,几十 ns,答案缓存在连接上,所以规则数量不影响查询。MUST NOT 把通配和 `any` 并进每个桶:那是笛卡尔积,435 KiB 的合法文件能造出一亿个条目,撑爆堆是 V8 的致命退出,接不住。索引的条目数 = 每条规则的 harness 数 × 精确 host 数之和,编译之前就算出来,上限见 §隔离的表。

**三档开销**,规则编译时就定了每条规则在哪一档:

| 档 | 包括 | 在哪 | 开销 |
|---|---|---|---|
| 0 | 索引:`on`、harness、host | 主线程 | 12–76 ns |
| 1 | 方法、路径、类别、请求头、pid、状态码的字符串比较;符合 §匹配 快路的字面量在字节上的查找;不用转义的字面量替换(`in: "body"`,或者模式和替换值都只含快路的字符)。碰体的部分受下面的字节预算约束 | 主线程 | 每条候选规则约 60 ns,碰体的部分一个单元最多约 200 µs |
| 2 | 任何正则;其余字面量;`json`;`blocks`;`script` | 规则进程 | 往返 30–70 µs;带体时 33 KB 约 40 µs,512 KB 约 110–170 µs |

**主线程的字节预算**。第 1 档的工作里和长度成正比的,一个单元合计不超过 **256 KiB·遍**。一个计数器管住:字节查找、`*…*` 的包含比较、查 `\u`、拼接、替换、sha256,每做一遍之前把这一遍的长度加上去,超了就停下,**整个单元交给规则进程**,第 1 档的中间结果丢掉,它们还没有副作用。256 字节以内的字面量查找是线性的(§规则),一遍 256 KiB 最坏 0.2 ms,sha256 约 150 µs,所以一个单元最多占主线程约 200 µs。64 MiB 的体、100 条字面量规则在第一遍之前就超了,主线程一个字节都不扫。超过预算的单元不拼接、不解码、不跑 `isUtf8`、不算 sha256,这些都在规则进程里做,主线程只把收到的块交给异步的 `fs.writev`。

**第 1 档替换的输出也有上限**。先数命中,算出输出长度再分配:命中超过 4096 处、输出超过 1 MiB、或者比输入大出 256 KiB,就归第 2 档。结果分配之前先入账。多条规则接连改时,预算和这几条上限都用当前的体长,不用原始体长,所以放大不会逐级相乘。

**一个 tick 也有上限**。流上的小事件每个都在预算以内,但一个 16 KiB 的 chunk 能切出上千个事件,配 4096 个条件占循环 400 ms。所以同一个计数器按 tick 再算一次:每个条件比较算 64 字节·遍,一条连接在一个 tick 里累计超过 256 KiB·遍,剩下的事件留到 `setImmediate`。排着的事件照 §最长延迟 计时,到点算超时,这条流后面转原样,所以这种规则占不住循环,也拖不住 agent。

**闸只在连接空闲时才看字节**。这一句决定了闸的全部边界问题:它从不自己猜请求从哪开始,而是问 tee(`boundary()`,drain 已经在用的那个)。

| tee 怎么答 | 闸怎么做 |
|---|---|
| 空闲(`idle`),不 `blind`,不是 WebSocket | 这是请求边界,可以读请求头 |
| 不空闲 | 请求体或响应还在走,字节原样过,闸不看 |
| 不空闲,闸里还有这条连接没放行的单元 | 后到的字节排在单元后面,计入账,单元放行后才放,所以第二条请求不会抢到第一条前面。到顶按 `gate-full` |
| 不空闲,但请求这一侧已收完 | 前一条响应没结束就来了下一条(pipelining)。这条请求不改,跳过 `pipelined`,按 `on_error` 走 |
| `blind` 或 WebSocket | 这条连接上判不了:写 `skipped`,按 `on_error` 走 |

所以规则表变了之后,开着的长连接在下一个空闲点接手,不用等 agent 重连,也不会在一条请求中间或者已经升级的连接上乱读。`boundary()` 加两个字段:`ws` 和请求侧是否收完。

**路线**,每一步不成立就走原路,后面的步骤都不发生:

1. 这条连接的 harness + host 桶里有活规则吗。host 在 CONNECT 或 SNI 时就知道,答案缓存在连接上,之后每段字节只比一次规则表版本(一次整数比较)。明文 HTTP 的连接一条连接可以换 host,按每条请求的 `Host` 查。**绝大多数流量到这里就结束了**:不框定、不解析,和今天一样。
2. 这一段字节落在请求边界吗(见上表)。不是 HTTP(`classify` 的结果)就写 `not-http`,按 `on_error` 走:解密连接上走的未知协议今天照常转,`forward` 时规则不能把它们冻住。
3. 收全请求头,当场采样 `record`、保存级别、时间戳,让 tee 预设这条交换(建好 `ex`、分配 `seq`)。这一步必须在这里,否则 off 放行的请求到 tee 时开关已关,会漏写信封。请求头超过 64 KiB,或者等它收全超过最长延迟,这个单元判不了:写 `head-too-big` 或 `head-timeout`,按 `on_error` 走。`forward` 时放走已扣的字节,**只让路到下一个边界**:tee 还在框定这条连接,下一条请求照样判。
4. 查索引拿到候选规则,通常 0 到 3 条,跑第 1 档。没有幸存者就放走:这条请求后面的字节不进闸,它的响应也不进闸,闸回去等下一个空闲点,**不解析 body,不读 body,不留第二个 framer 常跑**。
5. 幸存的规则只看头,动作也只在头上(改头、延迟):做完放走,请求体照常流过去,不缓冲,规则进程不参与。
6. 幸存的规则有第 2 档的头条件(正则):一次进程往返。
7. 幸存的规则要读体,或者动作是 `reply`、`hold`:收全请求(chunked 的请求在这里解块,改发 `content-length`,头的变化记下来)。只看头的 `drop` 不收体,当场断开,信封记下已收的字节,标 `req_partial`,不等规则进程。
8. 要读体的交给规则进程:收到的块用异步的 `fs.writev` 写进它的槽文件,不拼接,不解压,消息只带长度。字面量在字节上查,**命中了才解码**:`isUtf8` 和 `indexOf` 是字节操作,512 KB 上都在 0.1 ms 左右;解码成字符串要 1.4 ms,贵十倍以上。
9. 算出改动,**先写审计行,写成功了才发**。一个单元至多一次写,只有真改动才写,一行几百字节、几微秒。写不成算规则出错。没有记录的改动不允许存在。
10. 记录器看到的是真正发给上游的字节(D33),带着第 3 步的采样值。

**闸没动手时不静默放行**。只要这条连接上有活规则排除不了而闸没动手,MUST 写 `skipped`,按这些规则里最严的 `on_error` 走。「排除不了」= 这一刻判得了的条件都成立:知道什么就判什么,透传和不是 HTTP 的连接只知道 `harness`、`host`、`pid`,判不了的条件(`class`、`path`、`body`)不算不成立。

- 让路只到下一个边界,`gate-error` 也一样。只有 `blind`、不是 HTTP、已压缩的 WebSocket 这种再也没有边界的连接才一路判不了,它们在第一次碰到时按 `on_error` 决定:`drop` 就断开,`forward` 就放行并留记录。
- **透传的连接也算**:h2-only、未信任、策略外的连接,host 在 CONNECT 或 SNI 时就知道。决定透传的那一刻(`flow.mjs` 写 `not_captured` 的地方)判一次:排除不了的规则里有 `on_error: drop` 就不透传,直接断开;全是 `forward` 就透传,写 `passthrough`。
- 记录写在这条连接的 `flows/` 行上(`rules_skipped`),不多写一行;`status` 有一行计数,看板 Rules 行上看得到。
- 真判不了的只有一种:不属于任何 harness 的进程的连接,它们没有桶,规则本来就不管(D51)。

规则开启之前已经在路上的请求不是候选,这条不动手,下一条才动手。

**响应要不要进闸,在请求时就定了**:只有 `host`、`path`、`method`、`class`、`req_header` 这些请求侧条件成立的 `on: response` 规则才进这条响应的计划,计划是空的,响应就走原路。计划不空时把请求的 `accept-encoding` 换成 `identity`,记 `reframed`:响应不压缩,就没有跨事件的解压状态,规则进程死在流中间时后面的字节也是对的。

**闸放在哪**:agent 的每一段字节都先过这一问,包括新连接的第一段:`routeInner` 和 `handleHttp` 都经 `relay(c, u, first)`,无规则时字节和写入顺序和没有闸一样。

**响应这一侧**:闸接管的响应,原始 chunk 留在闸里,判完才交给 tee,tee 收一个到达时间戳保住 `tsStart` 和 `tsEnd`。这样 `intervention` 在最后一块之前就写好了。`drain` 也因此自然等着:tee 没看到最后一块,连接就不算闲。

**一个出口**:上游来的字节和合成的字节走同一个函数 `emitUpstream(wire, agent)`(`beforeUpstream` → tee 收线上字节 → 写 agent 的字节 → `afterUpstream`,改过的响应这两份不同)。所以代答的响应一样能带上 `Connection: close`,一样能让 off 的排空收尾,不留一条经 trocar 的空闲连接。

**放行**:闸写出缓冲过的单元时按切片走:一次最多 1 MiB,写完 `setImmediate` 让出循环,几个单元轮流,对端不读就等 `drain`,和 `relay` 逐块的背压一样。单元的账到 write 回调才减。上游 close 时立刻结束请求方向的放行,不等 `drain`:死 socket 不再发它。所以 `rules off` 一次放开 256 个单元,循环也不会停几百毫秒;对端不读时,字节也不会从账上溜进 socket 的写队列。

### 最长延迟

- **一个设置**:`max_delay_ms`,存在 `rules.json` 顶层,默认 200 ms,范围 1 到 60000。看板设置页和 `trocar rules max-delay [<ms>]` 都能查和改。**没有单条规则的预算**:第 2 档确实算得慢的脚本就把这个数调大,这个数同时是坏规则最多能让 agent 多等的时间。
- **为什么是 200 ms**:一次模型调用是秒级,200 ms 看不出来;命中改写一条 8 MB 的请求在重负载的开发机上要 160 ms,放得下真实的大请求。设小了,健康的规则会在大请求上超时。
- **怎么算**:每个单元(一条请求、一个事件、一条消息)的时钟从它到齐算起,排队和进程往返都在内。不算 agent 发完请求体的时间、`hold`、`delay_ms`。所以流上规则跟不上时,排在后面的事件等得越来越久,到点就算超时,不需要另一个「滞后上限」,也不需要反压。不是 SSE、没写 `whole` 的响应例外:时钟从响应头到达算起,收全和规则计算共用这一个最长延迟(§流式响应)。
- **第 0、1 档不计时**,它们的上限在 §隔离的表里。
- **到点先看规则进程是不是已经算完了**:它把进度写在槽文件开头(§隔离),主线程到点同步读一次,几微秒,所有平台都一样。定时器和转发在同一个事件循环上,大记录同步写信封时循环会停,定时器可能先于已经到了的结果执行。进度里的任务号等于这个任务、而且写着算完了,就最多再等 20 ms 取结果;其余都算到点。
- **超时算一种出错**,按 `on_error` 走。**这个判定只用主线程已有的东西,不等规则进程,所以 agent 绝不会被卡住。**

**超时的后果**:

1. 这个任务里所有规则的**修改**作废,发原始字节,不发半改的字节。脱敏规则写 `on_error: drop`,就不会被别的规则的超时绕过去。
2. 第 0、1 档已经判定的 `drop`、`reply`、`hold`、`delay` 不受影响,继续按§规则「多条规则都命中时」的次序作用在原始字节上。所以挡遥测的规则不会被一条慢的修改规则带着放行。
3. 这个任务里的规则,有 `on_error: drop` 的就断开。
4. 每条没应用的规则都写进 `skipped`:单元到点时任务已经跑了最长延迟一半以上的那条 `timeout`,同任务被连累的 `peer-timeout`,没开始或者排队占了一半以上的 `queued`。这只是这个单元的说法,算在规则头上的是任务跑满最长延迟被杀(§隔离)。

**出错时听谁的**:这条请求上所有还没判定的候选规则里取最严的 `on_error`,有 `drop` 就断开。

**晚到的结果**丢弃:每个任务带规则表世代和一个 `settled` 标记,放行、断开、连接结束时置位。结果回来先比世代:`rules off`、`disable`、`rm` 之后,算着的结果作废,发原始字节。`off` 不作废:§分派路线第 3 步已经采样的请求按采样走完。

### 隔离

§不变式靠下面这些守住。

**规则进程**:

- **规则的代码只跑在这里**:`src/rules/runner.mjs`,由守护进程起,和 D63 的查询工作进程同一个做法。守护进程不 `new RegExp` 规则里的正则,不跑规则里的 JSON 编辑和脚本。
- **两种规则进程**:两个内建进程不载入任何脚本;**每个脚本文件一个进程**,只载入这一个脚本,内建动作它也能跑。所以脚本留下的定时器、未决的 rejection、内存泄漏只碰它自己。**一个单元只进一个进程**,一个任务一条回话:候选规则里有脚本就进那个脚本的进程,否则进内建进程,规则按文件顺序一条接一条,「每条规则看到的是前一条的结果」不用跨进程。一个单元碰上两个脚本时第二个跳过(`multi-script`),按 `on_error` 走。进程死了算谁的:跑满最长延迟被杀算进度里的当前规则;其余死法,脚本进程算这个脚本的规则(空闲时也一样),内建进程算当前任务的规则。开着的脚本文件 ≤ 4 个,再开 `rules enable` 退出 1;守护进程载入时同样校验,超了算坏文件。
- **权限收窄**:用守护进程自己的 Node(`process.execPath`:安装包带的那份,npm 和 git 的副本是用户的 Node)和 Node 的权限模型起,flag 就这一组:

  ```
  node --permission --allow-worker [--allow-net] --allow-fs-read=<app>/* --allow-fs-read=<脚本目录>/* \
       --allow-fs-read=<槽> --allow-fs-write=<槽> --max-old-space-size=<上限> runner.mjs <槽> [<脚本>]
  ```

  flag 用 `process.allowedNodeEnvironmentFlags` 探测,不认的不传,否则进程起不来。`--allow-net` 就是这样来的:新版本的权限模型也管网络,认这个 flag 的版本不传它脚本的 `fetch` 就不通,不认的版本网络本来不受管。实测 22.13、22.23、24.11、26.7 上这组 flag 行为一致,26.7 不传 `--allow-net` 时 `fetch` 失败。不认 `--permission` 就不起进程,写 `runner-down`。`--no-regexp-tier-up` 不在这份列表里探测不到,所以不放命令行,规则进程第一行调 `v8.setFlagsFromString`:不认的 flag 在这里只打一行 stderr,进程照常。

  `<app>` 是 trocar 的代码目录,路径一律 `realpath` 过,符号链接的路径进允许列表时进程起不来。内建进程没有脚本目录和 `--allow-net` 这两项,它不联网。`--allow-worker` 给看门狗线程,脚本也因此能开线程,线程的内存算在同一个 RSS 里。不能起子进程,不能载原生插件,只能写自己的槽文件。实测 `spawn`、`execSync`、`fork` 和 `process.binding` 这条绕过路都被拒,所以规则进程没有子进程,杀它不留孙子进程,不需要进程组。进程起来先自检(`process.permission.has`):能起子进程或能写代码目录就不载入规则,退出,写 `runner-down`,所以 Node 版本的差异不会悄悄放宽权限(验收 57)。`package.json` 的 `engines` 在实现这一段的 PR 里改成 `>=22.13`,更早的版本没有 `--permission`。`env` 只留 Linux 起 scope 要的 `XDG_RUNTIME_DIR`,stdio 除了消息通道都是 `ignore`,脚本的 `console.log` 只在 `rules test` 里看得到。优先级和守护进程一样:机器忙的时候它不能先饿死,否则规则全部超时。
- **Linux 上内存紧张时先死的是它,而且只死它**:`oom_score_adj` 设 1000。systemd 默认单元里任何进程被 OOM 杀掉就停整个服务(实测 `Result=oom-kill`),查询工作进程也一样,所以单元写 `OOMPolicy=continue`(实测服务不停)。用户管理器答话就把规则进程放进自己的 scope(`systemd-run --user --scope --collect --quiet`,绝对路径用守护进程的 `PATH` 找,实测消息通道照常),不看守护进程是不是单元起的,`systemd-oomd` 按 cgroup 杀时杀的也是这个 scope。`systemd-run` 用不了(没有用户总线)时退回直接起,写一条 D38 `runner-no-scope`,规则进程不因此没有,`OOMPolicy=continue` 还在。
- **有活的第 2 档内建规则就有两个内建进程常驻,有活的脚本规则就有这个脚本的进程常驻**,规则加载时预热,闲下来之后的第一条请求不用等启动。没有第 2 档规则就没有进程。闲着的进程阻塞在消息通道上,不占 CPU。
- **看门狗**:规则进程里有一个线程。任务跑着时每 20 ms 看一次,空闲时每秒看一次(`Atomics.wait`,不增加空转唤醒):当前任务过了最长延迟没有;RSS 过了上限没有(`min(1 GiB, 物理内存的 1/16)`,最多 6 个进程,合计不超过物理内存的 3/8);父进程还在不在(POSIX 看 `process.ppid` 变没变;Windows 上它不变,用 `process.kill(ppid, 0)`)。任一成立就写下原因,`SIGKILL` 自己。它的时钟从任务开始运行算。这个线程不依赖规则进程的主循环,也不依赖守护进程的事件循环:实测主循环卡在灾难正则里、死循环里、狂分配 Buffer 或对象时,它都杀得掉(设了 300 MiB 上限时停在 304 MiB),mac、win、Linux 上都杀得掉。所以内存上限不靠「任务到点就被杀」:最长延迟设到 60 秒时,RSS 一样停在上限。
- **内存不只看 RSS**:macOS 上压缩掉的页、Windows 上被修剪的工作集不算 RSS。所以还有两道:`--max-old-space-size` 封住 JS 堆;主线程每秒看一次 `process.memoryUsage()` 的 `heapUsed + external + arrayBuffers`,过了同一个上限就退出。主线程卡住时后一道不动,但卡住时新分配的页都在 RSS 里,看门狗管。
- **守护进程这边还有一道**:任务派出去之后满最长延迟 + 100 ms 还没完,`SIGKILL`。看门狗先到,这一道只防规则进程整个被冻住。这个时钟从派发算起,不从单元到齐算起:排队排到点的单元作废,写 `queued`,不杀进程,不算在规则头上。否则一次突发的大请求里,排过队的任务才跑 40 ms 就被杀,杀的是健康的进程,连杀 3 次还把规则歇掉。
- **队列在主线程**,每个进程同一时间只有一个任务,派给空闲的那个。规则进程死了,主线程马上收到退出事件,它手上的任务当场按 `on_error` 走,不用等到点。替补约 50 到 150 ms 起来,这段时间内建任务走另一个进程。没有进程可派时任务排队,到点按 §最长延迟走。
- **起替补有退避,和死因无关**:进程活不到 10 秒就死算连续死亡,替补按 1、2、4 秒退避,上限 60 秒,活过 10 秒归零。所以 1000 条坏规则、启动即死、空闲时死都一样,起进程的频率不超过每秒一次。退避中没有进程可派时第 2 档规则跳过(`no-runner`),转发照常。
- **一问一答**:一个任务一条回话,脚本碰不到消息通道(`process.send`、`process.channel` 在载入脚本之前就收走了),多余的消息或读不懂的结果直接杀进程。规则进程发之前量长度,回话超过 64 KiB 或序列化不了(循环引用)算规则出错,所以守护进程的主线程不解析大消息。结果的头修改过 §动作 的头校验才用。改后的体和 `edits` 走槽文件:体最多 64 MiB,入账之后才读回;`edits` 由规则进程序列化好,主线程不解析、不序列化,信封里按字节拼进去。这段字节不能弄坏记录:规则进程写槽之前自己 `JSON.parse` 一遍;主线程只做不随内容变贵的检查:长度和回话一致、首尾字节对、没有换行(`indexOf(0x0A)`,8 MiB 不到 1 ms)。任一不过算规则出错(`bad-result`),杀进程,这个单元发原始字节,信封不带这段。否则规则进程的一个 bug 或一次读短,就让信封不是合法 JSON,或者把 NDJSON 切成两行,读取侧跳过坏行,这条原始记录就静默丢了(不变式 2)。流上每个事件的 `edits` 当场序列化,攒的是字节。
- **进度**:规则进程把任务号、当前规则号、已用时间最多的规则、算完没有写在槽文件开头(24 字节)。主线程只在到点或进程死了时读一次,所以知道该算谁的。任务号不等于当前任务就算还没开始,上一个任务留下的「算完」骗不了它。
- **连续 3 次跑满最长延迟被杀或崩溃的规则歇 60 秒**:这段时间不跑,第 0、1 档成立的请求直接按它的 `on_error` 走,写 `skipped: cooling`。脚本进程空闲时死也算这个脚本的规则一次。60 秒后放一条请求试,成了就恢复,没成再歇 60 秒。`rules enable` 立刻恢复,守护进程重启重置。`on_error: drop` 的规则歇着时断开的是它第 0、1 档匹配到的请求,所以 `rules add` 回执提醒这类规则把条件写窄。
- **脚本和正则载入带 2 秒时限**:载入时把每个正则在单字节和双字节的样本上各跑一次,V8 按这两种编码分别编译;`--no-regexp-tier-up` 让它一次编成机器码(灾难正则也因此快几倍),所以第一条真实请求上不会再有一次长编译。顶层死循环的脚本和编译不完的正则让 `rules enable` 失败并写明。
- **不留残**(不变式 5):守护进程死了,看门狗 1 秒内杀掉规则进程。守护进程不按记下的 pid 清残:pid 会被复用,打错了就是 trocar 自己杀了 agent。`off`、`uninstall` 之后没有规则进程。

**槽文件**:

- 每个规则进程一个,`~/.trocar/collector/slots/<n>.bin`,目录 0700,文件 0600,Windows 上随 `~/.trocar` 的 ACL。规则进程只有这一个文件能写。
- 里面是正在判的那一个单元的体,明文,只有体,没有头。头走消息,凭据类的头不进去。
- 主线程只用异步写(`fs.writev`),没有同步写。
- `fs.writev` 的回调回来之前槽不派任务,这个单元作废了也一样,否则上一个单元的残余写入会盖掉下一个单元的输入。
- 任务结束就 `ftruncate` 到 0,所以通常赶在页缓存写回之前就没了。
- 规则进程退出时守护进程删它;守护进程崩了留下的,下次启动时删;`off` 把没有活规则的 harness 的槽清掉,没有规则进程时目录是空的。`uninstall` 删 `collector/slots/` 和 `collector/held/`。`rules test`、`resend --rule` 的一次性规则进程用系统临时目录里自己的槽,用完删。
- 它不是采集数据:不进 `raw/`,不算不变式 2 的源真相,D60 不封存它,`doctor` 列出它的大小。`log` 级别的体本来不落盘,在这里停留的时间就是这个任务的时长。
- 磁盘满或写不进:这个单元按 `gate-error` 走。
- 实测(Windows 上 Defender 实时防护开着,文件句柄常开所以不重新扫描)见 §性能线。

**事件循环被占住时,最长延迟靠什么守住**。定时器和转发在同一个事件循环上,循环被占住时定时器不准,所以这条线不能只靠定时器:

1. **规则造不出停顿**:规则的代码不在这个循环上,规则带来的主线程工作都有上限(下表)。
2. **杀失控的规则不靠这个循环**:看门狗在规则进程里自己到点动手,守护进程的循环停着也一样。
3. **算没算超时由规则进程说了算**:到点先读进度,算完了就取结果,不算超时。所以循环停顿造不出假超时,也不会把健康的规则判歇。
4. **别的东西占住循环时**,所有转发一起停,有没有规则都一样,这时连接不断,只是晚。这条线在这种情况下是「最长延迟 + 这次循环的停顿」。目前最大的停顿是写大记录(同步写信封:2 MB 7 ms,16 MB 55 ms,64 MB 252 ms),它和规则无关,规则改过的记录最多多 8 MiB,这部分不序列化(下表「tee 写盘」)。循环停顿超过 100 ms 写一条 D38(`loop-stall`,用 `monitorEventLoopDelay` 量),`status` 显示,所以这种情况看得见。

### 其余规定

**要动体时动不了的情况**。这张表只管替换、改 JSON、按块改和要读体的匹配,它们做不了,就写 `skipped`,按 `on_error` 走:

| 情况 | `skipped.why` |
|---|---|
| `Expect: 100-continue`(等请求体会和 agent 互相等死);`hold` 同样跳过 | `expect-continue` |
| 规则进程解不开的 `content-encoding`(Node 22.15 以前没有 zstd);上游不理 `identity` 还发压缩的 SSE | `encoding` |
| 体不是 UTF-8(`script` 不受这一条限制) | `not-utf8` |
| 超过 64 MiB 的请求体或响应 | `too-big` |
| 超过 1 MiB 的 SSE 事件 | `event-too-big` |
| 多行 `data:` 的 SSE 事件 | `multi-line-event` |
| 不是 SSE、没写 `whole`,最长延迟内没收全 | `streaming` |
| HTTP/1.0 上要改 SSE(没有 chunked) | `http10` |
| 写不下 `edits`(§记录与标注) | `edits-full` |
| 规则进程的结果校验不过(§隔离) | `bad-result` |
| 一个单元碰上两个脚本,第二个 | `multi-script` |

**只看头的动作不受上面这张表限制**:改头、`delay`、只看头的 `drop` 一律照做,所以挡遥测的规则挡得住 chunked 和 protobuf 的请求。`reply`、`hold` 要收全请求,超过 64 MiB 或无进展就按 `on_error`。`Expect: 100-continue` 的请求上 `reply` 不等体直接回答,带 `Connection: close`。

**闸整个不动手的情况**,规则都不生效,写 `skipped`,按 `on_error` 走:

| 情况 | `skipped.why` |
|---|---|
| 前一条响应没结束时到达的请求 | `pipelined` |
| 这条连接的记录器已经停了(`framerError`、丢了 tee),和 `drain.loseTee` 同样的做法 | `no-recorder` |
| 明文请求经带凭据的用户代理:`forward.mjs` 按读入偏移插 `Proxy-Authorization`,闸改了长度或没写出去,用户的代理口令就会被插进请求体发给上游。这条路上闸不动手 | `credentialed-hop` |
| 请求头太大,或等不到 | `head-too-big` · `head-timeout` |
| 不是 HTTP | `not-http` |
| tee 看不到这条连接的边界 | `blind` |
| 已经建立的压缩 WebSocket | `ws-compressed` |
| 透传的连接 | `passthrough` |
| 闸的账到顶 | `gate-full` |
| 闸自己的代码出异常,或写不进槽文件 | `gate-error` |
| 规则进程起不来 | `no-runner` |

**保存级别**:这个类别是 `log` 时,请求规则命中就按 `full` 记。响应规则要看到响应才知道命中,所以请求开始时,只要有活的响应规则的请求侧条件排除不了这条请求,就按 `full` 记,否则原始字节存不下,违反不变式 2。

**改完之后**:`content-length` 按新长度重写,其余头的顺序和写法不动。压缩的请求体解压后改,发出时去掉 `content-encoding`,请求头的变化也记下来。zstd 改明文上游接不接受实验室验不到,这一条写在 `--help` 里。

**改动范围**:`flow.mjs` 的入口、`relay`、`start`、`upstreamGone`、一个 `emitUpstream`;`exchange.mjs` 加一个预设入口和 `boundary()` 两个字段;`store.mjs` 的 `audit` 改成返回成败;`drain` 和 `relay` 持可替换的上游引用,由 flow 组合 boundary;`terminate()` 的上游一半抽成一个函数,首拨和重拨共用。其余在新目录 `src/collector/core/intervene/`。规则的匹配和修改放在 `src/rules/`,引擎、`rules test`、`resend`、看板都走它的同一个入口。内建动作是纯函数,同样的规则集、同样的输入字节,三条路算出的结果相同,验收 9 守住。

## 缓冲

| 规则 | 缓冲什么 | agent 多等多久 |
|---|---|---|
| 这条流量没有候选规则 | 什么都不缓冲 | 12 ns |
| 只看头、改头 | 只等请求头收全,通常已经在第一段里 | 微秒级 |
| `delay` | 不缓冲,暂停读 | 就是写的那段时间 |
| 要读请求体 | 整条请求,上限 64 MiB。上游晚收到请求:agent 写完请求体的时间,加规则时间 | 33 KB 约 0.1–0.3 ms;512 KB 不中约 0.4 ms,命中改写约 4 ms |
| `reply` · `hold` · 读体的 `drop` | 整条请求,上限 64 MiB | 等 agent 写完请求体 |
| 响应上的 SSE 逐事件(默认) | 排队的事件。规则跟得上时只留没收全的那一个,跟不上时排在后面的事件到点算超时 | 字面量每个事件不到 1 µs;正则每个事件多一次进程往返,30–70 µs |
| 响应上不是 SSE | 已收的部分。收全了就改,到最长延迟没收全就放走,后面直通(§流式响应) | 最多最长延迟 |
| `whole` 或扣留响应 | **整个响应**。agent 在响应结束前收不到一个字节,等于把流变成了非流 | 整个生成时间,秒到分钟,上限 10 分钟,agent 可能超时 |

`rules add` 碰到 `whole` 或扣留响应的规则时,回执写明这一点。这是最贵的一种,所以 SSE 上逐事件是默认。`on: response`、不写 `whole` 的规则碰上慢的非 SSE 响应不生效:`on_error: drop` 每次都断,`forward` 写 `streaming` 放行。回执写明,建议写 `whole`。

## 扣留

| 情况 | 结果 |
|---|---|
| 到点 | `release_after_ms` 必填,没有默认值(§动作),到点按 `on_error` 走。实际上限还受 agent 自己的客户端超时约束,`--help` 写明 |
| agent 在扣留请求时放弃了 | 引擎继续读 agent 的连接,所以能看到它断开。闸先把字节交给 tee 再走收尾,条目标 `agent-gone`,请求没发出去,信封记下 agent 发的字节。`held release` 退出 1 并说明 |
| agent 在响应被扣时放弃了 | 已收全的:上游响应完整记录,agent 什么也没收到,标 `agent-gone`。还在收的:记成 aborted 的部分记录,不改现有的「agent 走了就断上游」 |
| 请求还在闸里、这次交换还没有字节写给上游时,上游关了连接或发来字节(扣留、延迟、收全请求体、规则进程算着都算) | 上游的字节不转给 agent(否则 agent 把 408 当成被扣请求的回答),不进 framer 和 tee,信封记 `upstream_while_held`:前 4 KiB 和总字节数,其余丢弃,这是写明的保真边界。agent 的连接不动。放行时重拨一次:同样的 SNI、host、信任,走 `terminate()` 抽出来的上游一半,等到 `secureConnect`。重拨失败、证书不过,或者这条连接走隧道、带凭据的用户代理(这两种不能替操作者再拨,4.8 §5.2):条目标 `upstream-gone`,agent 的连接跟着关,agent 自己重试 |
| 其余时候上游关了(响应这一侧的扣留和 `whole`、SSE 上的延迟、WebSocket、已经写出过字节) | 按连接收尾,绝不重发:请求可能已经被执行了 |
| 响应已收全时上游关闭 | 不影响放行:`upstreamGone` 先等闸排空,再收尾 |
| `off`,请求在闸里(没扣留,收体或规则进程算着) | 等闸走完再排空,闸有未完成单元时 boundary 不算闲。已采样的请求按采样走完,改后字节照发 |
| `off`、`rules off`、`disable`,单元在 `delay` 里 | 立即发出 |
| `off`,请求被扣着 | **放行**,发的是扣留时手里的字节:只有扣留规则时就是 agent 原样的字节,有修改规则时是审计已写的改后字节,不撤销脱敏。审计记 `released-by-off`。任一命中规则 `on_error` 是 `drop` 的改成断开 |
| `off --now` | 闸里有东西也走切断,连接行标 `cut-by-off` |
| `rules off`、`disable`、`rm` | 这条规则扣着的放行,规则同样按 `on_error: drop` 断开。审计记 `released-by-rule-off`。harness 还开着,连接不关。规则进程算着的结果作废,发原始字节 |
| `limit.until` 到点 | 按 `disable` 处理这条规则扣着的单元,到点有定时器,不靠下一条请求。`limit.times` 用完时已经扣着的单元等自己的 `release_after_ms` |
| 守护进程停 | 不放行,直接切,标 `cut-by-stop`。放行也撑不过 2 秒的停止屏障,上游白收一次、agent 还要重试。`update` 走 off 时已经放行过 |
| 守护进程崩了 | 连接随之断,agent 看到连接错误后自己重试。下次启动时,`rules-stats.json` 记着正扣着、审计尾部又没有结果的,补一条 `held-lost` 记录 |

**控制路由**:`rules off`、`held`、`held release`、`held drop` 走守护进程自己的路由,不进查询队列,看板的控制动词也一样:查询工作进程忙着或进了冷却时,这几个按钮不能按不下去。列表不带体,最多 256 行。体不走 JSON:`held show` 按切片流式读。改后的体放在 `collector/held/<id>.body`(0600):`held release --body-file` 由 CLI 把操作者的文件拷过来,看板用 `PUT` 流式写。放行的路由只收 `id`,不收路径,单元结束就删这个文件。控制端点的 64 KiB 上限不变。`held` 的行带 `session_key`:只从请求头算出的会话键,只用于显示,不进原始层,不用于 `match`,算不出就没有。

## 流式响应

| 情况 | 结果 |
|---|---|
| 响应闸只接最终响应 | 跳过 1xx、101、CONNECT 2xx。HEAD、204、304 只改头 |
| 响应是不是 SSE | 看 `content-type: text/event-stream`。是的话默认逐事件。不是的话从响应头到达起,收全和规则计算共用一个最长延迟:到点前算完(`content-length` 的小响应、chunked 的 JSON 回复)就发改后的;到点没收全就放走已收的字节,后面直通,写 `streaming`,按 `on_error`;收全了没算完按超时走。所以 ndjson、流式 JSON、长轮询这些 trocar 认不出的流不会被攒住;要确定地改它们就写 `whole` |
| 默认(SSE) | **一个事件一个事件地改,流还是流**。改完的事件立刻转出 |
| 逐事件的开销 | 不用转义的字面量替换在主线程上做,每个事件不到 1 µs;其余每个事件一次进程往返 |
| 怎么切事件 | 按行增量切,判据和 `sseEvents` 一样(空行结束事件,EOF 冲出残余),所以 CRLF 的流也行。多行 `data:` 的事件和超过 1 MiB 的事件不改,留记录 |
| 一个词被拆在两个事件里 | Anthropic 和 Chat 上匹配不上。Responses 上更糟:增量事件没改,`output_item.done` 和终止事件里的整段文本改了,agent 显示的和写进历史的不一致。所以 Responses 上的文本规则要写 `whole`,`--help` 写明 |
| `"whole": true` 或扣留响应 | 收完整个响应再处理,一次发出。agent 这段时间收不到字节,可能触发它的超时,记录里标 `streamed:false`。上限 64 MiB 和 10 分钟,过限按 `on_error` |
| 压缩 | 响应计划不空时请求已经换成 `accept-encoding: identity`(§分派),流不压缩。上游不听话仍发压缩的 SSE:这条响应跳过(`encoding`),逐字转发,`content-encoding` 不动。收全的响应压缩时整个交给规则进程解压 |
| SSE 带 `content-length` | 逐事件的改动会让长度不对:响应计划不空时发头之前改成 chunked,记 `reframed`。HTTP/1.0 没有 chunked,这条响应跳过(`http10`) |
| 解不开的响应编码 | 按 `on_error` |
| 流上第一次出错或超时 | 这条流后面的事件转原样,记 `edits_stopped_at`。`drop` 时连接断开,已发出的收不回,agent 看到半截流,记录写明 |
| `rules off` 时流还在改 | 从下一个事件起不再改,转码继续到流结束,记 `edits_stopped_at`。规则在每个事件上都看一次世代 |
| 逐事件的审计 | 第一次改动前写一行(规则、规则 sha256、flow、seq),写成才发,结果 sha 在信封里。流中间崩溃时这行没有对应信封,这是保真边界,写明 |
| `match` 不成立的响应 | 逐字转发,和没有闸一样 |
| 插入 | 写在命中的事件之前,这段字节算改动,`agent_response.edits` 记下来 |
| 延迟 | 用定时器,什么都不占。每个命中的事件推迟 `delay_ms`,后面的事件排在它后面 |

## WebSocket

消息级别改包。`ws-client` 规则作用在 agent 发的消息上,`ws-server` 规则作用在服务端发的消息上(和 SSE 事件同一条路)。规则表在每条消息上都看一次。

- 难点是 permessage-deflate 的压缩上下文:改一条消息,后面的全解不开。解法是**有规则可能命中时,在握手里去掉 `Sec-WebSocket-Extensions`**,这条连接就不压缩,消息可以单独改。「可能命中」= 规则的 `harness`、`host`、`path` 和这次握手匹配。这一处修改记成 `reframed`。
- 已经建立的压缩连接上规则不生效,每条连接记一次原因。agent 下一次连接时生效。
- 改过的消息合成单帧,重新掩码。没改的消息逐字节转发。
- **只有 ping、pong 不进闸**。close 和数据帧同序排队,否则放行时数据帧落在 close 之后,RFC 6455 不允许。
- 101 之前客户端抢发的字节不判,沿用 framer 的 `upgrade-wait`,等 release 或 takeRest 决定。
- 扣留回复 = 从客户端消息打开的调用开始,扣到 harness 描述符声明的本轮终止消息(`wsTerminal`)。没有声明终止消息或进入 blind 状态的连接不能扣回复,按 `on_error`。无调用时服务端的推送直通。
- `drop` = 重置连接,和 HTTP 一样。
- trocar 从不自己造 close 帧(1.6 §3.4)。
- **保真边界**:WebSocket 上 agent 一侧只保证消息内容,不保证帧的切分和掩码。

## 记录与标注

**不变式 2 的存法(D33)**:一次上游往返一条信封,`req_body` / `resp` 是真实线上字节,所以真发出去的调用,`content_hash`、AC-1、cache 分析和前缀比对全部照旧。agent 这一侧用字节补丁还原,每次读都校验 sha256,对不上就拒绝不猜。「原始和改后都逐字存」的准确含义是:**两份都能逐字节还原,且有校验**,只有一份是完整存放的。

形状:

```json
"intervention": {
  "id": "iv_…", "kinds": ["modify-request"], "origin": "rule", "rules": ["swap-alpha"],
  "agent_request": {
    "recover": "patch", "head_raw": "…",
    "edits": [{"at": 123, "del": 5, "ins": "ALPHA"}],
    "base_sha256": "…", "result_sha256": "…"
  },
  "agent_response": {
    "recover": "patch", "target": "resp.raw", "head_raw": "…", "edits": […],
    "base_sha256": "…", "result_sha256": "…", "streamed": true
  },
  "held": { "ms": 12000 }, "outcome": "released-edited"
}
```

规定:
- **坐标是字节**。`scanJson` 和正则的下标是 JS 字符串下标,写 `edits` 时用 `Buffer.byteLength(前缀)` 换算,否则一个中文字符之后全部错位。验收有含中文和 emoji 的夹具,期望值手写。
- **`edits`** 按列出的次序,依次作用在上游字节上,得到 agent 的字节。每一步的 `at` 相对当时的状态。
- **`reframed`**:转码的记录,`[{"side": "request", "header": "accept-encoding", "from": "gzip, br"}]`。有它的信封一律带 `agent_request.head_raw` 或 `agent_response.head_raw`,所以 agent 的头能逐字节还原。`kinds` 不变,看板不标「改过」。
- **`upstream_while_held`**:`{ "bytes": 123, "head_b64": "…" }`,见 §扣留。
- **`edits` 有上限**:一条记录的 `edits`(每条按 `ins` 的字节加 32 算)和 `body_b64` 合计 ≤ min(8 MiB, max(1 MiB, 这个单元的字节数,流上是已收的字节数))。信封是同步写的,而 `ins` 展开之后的量和上游字节无关:100 KB 的 `inject` 打在 2000 个事件上是 191 MiB,`JSON.stringify` 要停 2.9 秒,再大就是 `RangeError`,整条记录丢掉。规则进程算出的 `edits` 按序列化好的字节拼进信封,实测 8 MiB 不增加同步时间,解析再序列化要多 55 ms。所以写不下就不改:流上从这个事件起转原样,其余单元的改动作废发原始字节,写 `edits-full`,按 `on_error` 走。`edits` 永远逐字完整,没有记录的改动不存在。
- **`recover: "inline"`** 时没有 `edits`,改用 `body_b64`。两种情况:补丁比整份大;压缩请求,这时内联 agent 发的线上压缩字节,压缩不可逆,文本补丁还原不出它们。
- **响应的基准**:`resp.raw`;JSON 响应没有 `raw` 时用 `JSON.stringify(resp.body)`(`parseJsonReply` 保证它等于线上文本);其余没有干净文本基准的情况(`raw_b64`、`resp.partial`),内联 agent 收到的解码后内容。
- **SSE 也走补丁**:`resp.raw` 逐字存了解码后的流。
- **WebSocket** 的 edits 带消息下标。
- **`kinds`** 是数组,因为请求和响应可能同时被改。闭集:`modify-request` `modify-response` `synthesized` `held` `delayed` `dropped` `resend`,插入算 `modify-response`。
- **`origin`** 闭集:`rule`(规则动的)、`operator`(`held release` 带改后的体)、`trocar`(重发发起的请求)。
- **`outcome`** 的闭集在 [1.6](1.6-cli.md) C.5。
- **`synthesized`**:代答的响应不是上游发的,`synthesized: true`,读取侧不算用量和 cache。
- **`skipped`**:`[{rule, why, ms}]`,这条请求上本该动手但没动手的规则,每条一项。`why` 是闭集:`timeout` `peer-timeout` `queued`(§最长延迟)、`crashed` `cooling`(§隔离)和 §其余规定两张表里的值。字节没变时 `kinds` 是空的,看板不标「改过」,只标「规则没应用」。
- **被丢弃的请求**没到上游,信封的 `req_body` 就是 agent 发的字节,标 `dropped`,错误写明。这类信封有 `error`,`usage` 已经排除它们。[3.3](3.3-cache-model.md) 的 mid-turn-retry 判据:带 `intervention` 的归操作者,不归 harness 或网络。
- **审计流** `collector/audit/<日期>.ndjson` 每次动作一行:谁、何时、依据哪条规则(含规则内容的 sha256,规则以后改了也能对上)、改前改后 sha256。`actor` 记系统用户和是否在终端里。读取时跳过坏行。
- **崩溃**:改动发出、信封还没写时守护进程崩了,下次启动补一条记录说明。在途信封崩溃时同样会丢,这是已有的保真边界。
- **没应用怎么看得见**。跳过不单独写文件,记录随这个单元已经要写的那一行走:

  | 在哪 | 写什么 |
  |---|---|
  | 信封 | `intervention.skipped`,数组,一个单元一行,不管有多少条规则 |
  | 连接行 | 没有信封的情况(透传、不是 HTTP):`flows/` 行上的 `rules_skipped`,一条连接一次 |
  | 计数 | 守护进程在内存里累加,每 5 秒异步写一次 `collector/rules-stats.json`:每条规则的改动数、各原因的跳过数、最后时间、最近 60 分钟的分钟桶、歇着没有,加上 `rules_off_at`、`unclean_stops` 和正扣着的单元。`rules --json` 只读这个文件,成本和规则条数成正比,不读审计流,守护进程不在也答得出;崩溃最多丢 5 秒的计数,逐次的事实在信封里 |
  | D38 失败事件 | `where: rules`,`code: rule-timeout`,作告警用,按现有规则折叠。`status` 和看板的警示灯读它 |
  | CLI | `trocar rules` 的 NOT APPLIED 列;`query interventions --skipped [<why>]` 读段索引;`status` 一行 |
  | 看板 | Rules 行上的计数和警示,点开列出每一次 |

  歇着的状态(`rule-cooled`、`rule-resumed`)是审计行,一次状态变化一行,不是每个请求一行。
- **审计流只记改动和状态变化**,所以它的大小跟着改动的次数走,不跟着流量走。按天分文件(`audit/<日期>.ndjson`),和 `flows/` 同样的封存与保留([4.6](4.6-process-collector.md) §日志体积预算)。
- **`limit.times` 的计数**在内存里,随 `rules-stats.json` 每 5 秒落盘。守护进程启动时读这份计数,再把它的时间戳之后的审计尾部折进来(异步,从文件尾往回最多读 1 MiB),所以重启不会多改几次,热路径不读文件,启动时读的量和审计流的总量无关。打满后规则的状态是 `limit-reached`,`rules enable` 从零算。正扣着的单元也记在这份文件里。
- **D38 的闭集**(`src/health/codes.mjs`):`where` 加 `rules`;`code` 加 `rules-unreadable` `rules-unparsable`(文件坏了)、`rule-timeout`、`rule-crashed`、`runner-down`(规则进程起不来)、`gate-error`、`gate-full`、`script-load-failed`、`audit-write-failed`、`held-lost`、`loop-stall`、`rules-tripped`、`runner-no-scope`;状态事件加 `rules-ok`(文件重新读得通,结束上面那个状况)。

## 重发

重发**把相关变成因果**:原样发 K 次量出模型自己的方差,没有这个基线,「改了之后变了」可能只是采样噪声。

- **发送方是 `trocar resend` 这个进程**,不是守护进程。取字节、校验 sha256、写 `replays/` 都是大块的同步工作,放在转发的事件循环上,一次 64 MiB 的重发要停 1.5 秒,所有 agent 一起等。CLI 自己读记录、自己拨 `hop`、自己写 `replays/`,不走控制端点,也不受它 64 KiB 的上限。看板的重发按钮起同一个命令,detached,Linux 上进自己的 scope,所以守护进程停了它也走完。`--rule` 带脚本时起一个一次性的规则进程。
- **默认每秒 1 次、同时 1 个在途**,跨进程也一样:`collector/replays/.lock`,发送时每秒刷新 mtime,5 秒没刷新就算没了;被占时退出 1(`resend-busy`)。`--times` 一批只确认一次。单次最多 10 分钟,响应最多 64 MiB,过了算失败并写记录。
- **写进 `collector/replays/`**,没有 `calls` 行、没有 cache 事件。**重发存它真实发出的完整字节**:`--rebuild`、`--body-file`、`--rule` 发出的字节从源记录推不出来,而重发很少,不值得分两种存法。标 `rebuilt` 或 `edited`,源记录由 `base_sha256` 钉死。
- **默认发 agent 一侧的字节**(校验过的还原),`--as-sent` 发线上那份。没被改过的记录两者相同。
- **续写请求默认拒绝**(`resend-continuation`):它不完整,发出去要么 404,要么追加进 agent 真实的服务端对话。错误信息说明怎么用 `--rebuild`。
- **`--rebuild`** 把续写补全成完整请求:拼接规则 `cc-threads.mjs` 已经有(`messages(N) = 前面的 ⧺ 上一条回复 ⧺ 这条`),`thread` 换成新建。这样不会碰 agent 的服务端对话。发出的是重建的字节,`replays/` 里标明,缺前驱时拒绝。Responses 的 `previous_response_id` 同理,随 §WebSocket。
- **走哪条路**:**不重算,直接拨采集时记下的那一跳**:源进程退出后,靠 `HTTPS_PROXY` 走的代理重算不出来。信封加一个小字段 `hop: {kind, host, port, credentialed}`:door 从 `meta.upstream` 取,Linux 从前导解析。这个字段不带凭据。拨号和前导(`viaHttp`、`viaSocks5`、`dialUpstream`)抽到 `src/collector/core/` 的公共模块,引擎和 CLI 共用。SNI 是记录的 host,必须校验证书,信任集和引擎这个 harness 用的同一份(`upstreamTrust`,`hop.trust` 记 harness 的名字),读不到就退出 1(`resend-hop-unknown`),MUST NOT `rejectUnauthorized: false`。
- **`credentialed` 的一跳退出 1**(`resend-hop-credentialed`):4.8 §5.2 写明用户代理的凭据只用于这一条 agent 连接。
- **没有 `hop` 的旧记录退出 1**(`resend-hop-unknown`)。那一跳拨不通就如实退出 1。不读 `flows/`:连接没关时那一行还不存在,守护进程重启后 `flow_id` 还会重复。
- **不换凭据**:过期就是 401,如实记录并提示。
- **`--rule`** 只接受 `on: request` 的修改动作。规则必须真改到字节,否则退出 1(`resend-rule-no-change`),不然 K 次发的都是原文,实验结论是错的。规则出错一律不发,这里没有 agent 要保活。
- **请求重建是一个函数**:chunked 改成 `content-length`,换了体就去掉 `content-encoding`,头的改动记进记录。
- **没有完整字节的记录拒绝**:`log` 级别、`req_truncated`、`req_partial`。
- **采集关着时**:`resend` 多确认一次,写明「仍会留下重发记录」。它不要守护进程,`off` 和守护进程的起停都碰不到在途的重发。
- **WebSocket 的重发**随 §WebSocket:开一条新连接,发开场消息,读到终止消息。

## 验收(可跑 check · I 组)

上游一律用实验室 mock(`test/lab/mock-upstream/`);mock 的回复由它收到的请求决定(回显最后一条用户消息的前 80 字和请求体 sha256),据此判断模型「看到了什么」。碰进程间缝或出站路径的项都要经真门的 e2e,再在 mac、win、Linux 的实验室留 run 记录。

1. 请求规则把提示词里的 `ALPHA` 换成 `BRAVO`:mock 收到 `BRAVO`;agent 显示的回复含 `BRAVO`;信封 `req_body` 含 `BRAVO`;对 `req_body` 应用 `intervention.agent_request.edits` 还原出含 `ALPHA` 的原始请求,`result_sha256` 校验通过;审计一行。
2. 扣留后改系统提示再放行:mock 收到改后的版本。扣着不处理、但仍在 agent 的客户端超时之内时,agent 不报错、不重发,放行后正常完成。agent 在扣留期间放弃时,条目标 `agent-gone` 并留记录。
2b. 响应被扣留改写:agent 收到改后的内容;`resp` 是 mock 原文,`agent_response` 还原出 agent 收到的内容,`streamed:false`。
3. 断开:agent 看到连接错误并重试,重试的请求正常完成并被记录。
4. 响应规则改 SSE 文本:agent 收到改后文本,`resp.raw` 是 mock 发出的,`agent_response.edits` 应用其上得到 agent 收到的文本。
5. 响应规则(`whole` + `script`)把 mock 的文本回复改成一个 `tool_use`(让 agent 执行 `echo trocar-tool-ok`):[VM] 真实 agent 执行了这个工具,下一轮请求里带着工具结果。
6. 重发一条记录并改其请求体:mock 收到改后版本;信封 `origin:'trocar'`、源引用与 `base_sha256` 正确、落在 `replays/`;agent 的会话流和 `calls` / cache 事件里都没有它;限速生效;发送方是 CLI 的进程,守护进程不在也发得出。
7. 有规则文件但没有活规则时,转发字节与 T 组相同;有活规则但 `match` 不成立时也相同。`match` 成立而没改动时内容相同;响应计划不空的请求 `accept-encoding` 换成 `identity`,SSE 带 `content-length` 时改成 chunked,都记 `reframed`,agent 的请求头能逐字节还原。WebSocket 例外:握手去掉扩展的连接,帧变成不压缩。
8. 扣着时 `off`:只有扣留规则时 mock 收到的与 agent 发出的逐字节相同;信封存在、`resp` 完整、`outcome=released-by-off`;`on_error: drop` 的变体断开。规则仍在,`off` 之后不匹配。
9. 同样的规则集、同样的输入字节,`rules test` 算出的字节 == 实时路径发出的字节(内建动作)。
10. `off` → `on` 之后转发字节等于 agent 发出的字节,回执点名停掉的规则;`rules enable` 后才再改。`update` 前后同一规则同样生效;`off` → `uninstall` → `install` → `on` 后规则是关的。
11. `on_error` 两种取值,在超时、脚本抛错、解不开的压缩、审计写不进四种故障下各跑一遍;加「前面的 forward 规则超时、后面有 drop 规则」。
12. 灾难正则写在 `path`、`header`、`body` 上,死循环写在脚本里:另一条连接的转发不被拖慢,agent 在最长延迟 + 2 ms 内拿到结果;两条请求同时命中同一条坏规则也一样。
12b. **真杀进程**:任务在途时 `kill -9` 规则进程,一个、两个、连杀 10 次;`SIGSTOP` 冻住规则进程。最长延迟 200 和 60000 各跑一遍。每一种都断言:守护进程 pid 不变;另一条连接上正在流的 SSE 不断、不丢字节;这条请求按 `on_error` 走;有审计行;新的请求照常处理。
12c. **真打满内存**:脚本无限分配 Buffer、无限分配 JS 对象、在全局变量里慢慢攒,最长延迟 200 和 60000 各跑一遍。断言同 12b,再断言规则进程的内存停在上限,守护进程的 RSS 不涨。Linux 和 macOS 的实验机上再跑一次机器真的没内存的情况(用外部程序把内存吃满):死的是规则进程,不是守护进程。Windows 上把 RSS 上限调大,断言 `memoryUsage` 这一道也杀得掉。
12d. **闸的内存**:扣留规则抓住一个不停发大请求的 agent,`whole` 规则碰上一个不停的大响应,几十条连接并发,再加十几个用户加的 harness 一起来:这个 harness 的账和总账都停在上限,守护进程 RSS 不再涨,新单元写 `gate-full`;别的 harness 的 `on_error: drop` 规则不受影响,同一个 harness 的修改规则不被扣留挤掉;没有规则的连接照常。
12e. **脚本的各种死法**:死循环、抛异常、未处理的 rejection、`process.exit()`、`process.abort()`、给自己发 `SIGSEGV`、顶层 `setTimeout` 里 `abort`、`setInterval` 里抛异常、试图起子进程(`spawn`、`execSync`、`process.binding`)、试图载原生插件、返回带 CRLF 的头、返回超大的头、超大的体、循环引用的对象。断言同 12b,再断言规则进程死后系统里没有它的子进程,别的脚本和内建规则一次都没跳过,空闲时的死也算在这个脚本头上。

12g. **主线程**:12b – 12f 跑着时,`monitorEventLoopDelay` 的 p99 ≤ 1 ms。64 MiB 的体、100 条字面量规则时,另一条连接的停顿过 §性能线的两行。
12h. **不留残**:守护进程被杀之后,规则进程 2 秒内全部退出,主循环卡在灾难正则里也一样,Windows 上也一样;守护进程启动时不按记下的 pid 杀任何进程;`off`、`uninstall` 之后没有规则进程。
13. `log` 级别的类别命中规则时,原始字节能还原。
14. 改请求后的前缀比对跑在线上字节上。
15. 全新上下文的 agent 只靠 `--help` 走完「写、试、重发、上线、看、收手」。

18. 上游发完即关时响应在闸里,agent 收到完整响应。
19. 请求体收到一半、规则进程算着、`whole` 响应收完未发三种状态,各跑 `off` 和 `off --now`。
20. 只扣着一条请求时 `rules off`,此后没有新请求也能放行。
21. 每次超时都进信封的 `skipped`,灾难正则写 `timeout` 并算一击,排队占一半以上的写 `queued` 不算,`query interventions --skipped timeout` 查得到,D38 有告警,审计流不涨;连续 3 次后规则歇着,歇和恢复各一行审计,60 秒后的试探成功就恢复;`rules --json` 在守护进程不在时也答得出。

25. 只看头的动作不受体的形状影响:chunked、二进制的遥测被 `drop` 挡住。
26. 超时不放行已判定的 `drop`、`reply`:同一条请求上有一条慢的修改规则时,它们照常生效。
27. 规则进程被慢规则占着时 `rules off` 立刻生效;算着的结果回来时发原始字节;两个写者同时 `rules enable` 和 `rules off`,后写的不丢前写的。
28. 明文请求经带凭据的用户代理时,规则不改字节,凭据只出现在请求头。
29. 代答带上 `off` 排空的 `Connection: close`,连接收尾;`status` 是 100、101 的 `reply` 被 `rules add` 退出 2。
30. 流上规则跟不上时,排在后面的事件到最长延迟算超时,这条流后面转原样,agent 不被拖慢。
31. §性能线每一行在 mac、win、Linux 各有 run 记录。
32. 字面量快路不静默漏:体里 `<` 写成 Go 的 `\u003c`,中文写成 `\uXXXX`,字面量 `<system-reminder>` 和中文都命中;gzip 的体上字面量命中;`\nALPHA` 不算字面量 `nALPHA` 的命中。
33. `on_error: drop` 绕不过去,也不越界:请求头超 64 KiB、等头超时、闸抛异常、`blind`、不是 HTTP、h2-only、未信任、策略外,每一种连接在 `on_error: drop` 的规则排除不了时都不放行,都有 `skipped`;`host` 对不上的连接不断;没写 `host` 的 `on_error: drop` 规则 `rules add` 退出 2;`forward` 时放行且 `status` 计数涨;请求头超限之后同一条 keep-alive 连接的下一条请求照样被规则判。
34. 没写 `release_after_ms` 的扣留 `rules add` 退出 2;到点按 `on_error` 走,没有人操作也解开。
35. 槽文件:0600,任务结束后长度是 0,守护进程崩了之后下次启动删掉,`uninstall` 之后不在;主线程没有同步写它(在 `fs.writeSync` 上挂探针断言)。
36. 100 条规则都歇着时,一个单元只写一行(信封),审计流不涨;`rules --json` 的耗时和审计流的大小无关。
37. 写者:持锁的写者被 `kill -9`、被 `SIGSTOP` 冻住时,别的写者 3 秒内写成,被抢了锁的写者醒来不覆盖结果。
38. **放大**:256 KiB 的空格体配 3000 字节的 `with`,几条规则接连放大,SSE 事件上同样:主线程过 12g,账不超,改动归规则进程或按 `too-big` 走。
39. **长字面量**:1 KiB 和 64 KiB 的字面量在重复内容上不占主线程;4096 条 `*…*` 条件配 64 KiB 的头值过 12g。
40. **异步错误**:`send` 的同一个 tick `SIGKILL` 规则进程、`disconnect` 之后 `send`、fd 用尽时起进程、闸的流报 `'error'`、定时器里的 async 拒绝:守护进程 pid 不变。
41. **Linux 的 OOM**:守护进程由 systemd 单元起和手动起各跑一遍,内核杀掉规则进程:服务还是 active,agent 的连接不断;规则进程在自己的 scope 里,`systemctl --user list-units --all 'run-*.scope'` 不留残。
42. **`edits`**:100 KB 的 `inject` 打在 2000 个事件上:主线程过 12g,记录写得进,`edits-full` 之后这条流转原样,记录逐字节还原出 agent 收到的内容。
43. **重发**:上游挂住和无穷流的重发到上限退出并写记录;64 MiB 的重发跑着时另一条连接过 12g;`off` 不等它;两个进程同时发,后一个退出 1;私有 CA 的中转站上证书照校验;看板起的重发在守护进程停了之后走完。
44. **压缩的上游**:响应计划不空的请求带 `identity`;上游不听话时逐字转发;流走到一半 `kill -9` 规则进程,这条流和另一条流的字节都对。
45. **认不出的流**:ndjson、长轮询、永不结束的 chunked 响应,没写 `whole`:agent 在最长延迟内收到字节,`streaming` 有记录;小的 chunked JSON 回复照改;`whole` 碰上不结束的流到上限按 `on_error`;响应头只发一半时到最长延迟放走。
46. **槽和任务号**:冻住空闲的规则进程后派任务,上一个任务的「算完」不被当成这一个的,这个单元到点按 `on_error`;`writev` 还在途时任务作废,槽不派下一个;发给上游的字节从来不是别的单元的。
47. **`rules off` 总能停下**:`rules enable` 等编译时、磁盘满、家目录只读、持锁的写者被冻住、`rules.json` 是 FIFO:规则都停下,扣着的放开,回执如实;文件写不成之后另一个写者 `rules add`,旧规则也不回来。
48. **突发不杀健康进程**:3 × 160 ms、8 × 60 ms、32 × 20 ms 的任务同时到,最长延迟 200:没有进程被杀,没有规则歇着,排过队的写 `queued`。
49. **头的校验**:CRLF、`Content-Length `、`x\r\ncontent-length`、20 KB 的值,写在 `header`、`reply.headers`、脚本结果和手改的 `rules.json` 里:`rules add` 退出 2,守护进程载入和运行时都拒绝,字节不上线。
50. **跳闸**:同一次开机里规则开着时守护进程连续崩溃两次:第三次起来不开规则,门开着,`status` 第一行写明;文件内容变了不恢复,只有 `rules enable` 恢复。重启机器不计数。
51. **放行**:256 个单元一次放开、64 MiB 单元放行、对端不读:另一条连接过 §性能线,账到 write 回调才减,RSS 不超账。
52. **收全**:`Expect: 100-continue` 上的 `reply`、`hold`、只看头的 `drop`;请求体发一半就停:agent 都不被挂死。`collector/held/<id>.body` 被换成 FIFO、指向 `/dev/zero` 的符号链接时 `held release` 退出 1,单元还扣着,文件操作不卡。
53. **SSE 带 `content-length`**:逐事件改短和改长之后 agent 都收完整,这条连接上的下一条响应不错位。
54. **流水线**:第一条请求在闸里算着、延迟着、扣着时到达第二条:上游收到的次序不变,agent 的连接不断。
55. **重拨**:mock 上游闲置 2 秒就关,`delay_ms: 5000`、扣留 30 秒、请求体慢慢收全、规则进程算着:放行后 mock 收到请求,agent 正常完成,`upstream_while_held` 记下上游发的 408;证书不过、隧道和带凭据的一跳标 `upstream-gone`;响应一侧、WebSocket、已写出字节时上游关了绝不重发。
56. **`until` 到点**:扣着时规则到 `until`,此后没有新请求也放行。
57. **Node**:规则进程用守护进程的 Node。矩阵至少 22.13、24、当前最新和安装包带的版本,每个版本断言:探测到的 flag 组起得来;12e 的每种拒绝成立;脚本能读同目录、不能写同目录;脚本进程的 `fetch` 到本机 HTTP 通,认 `--allow-net` 的版本上内建进程连不了网;自检不过的进程不载入规则,写 `runner-down`。换安装包的 Node 版本时重跑。
58. **磁盘真满**:`~/.trocar` 放在一个真的小卷上写满(macOS 磁盘映像、Linux tmpfs、Windows VHD),不用替身:槽文件写不进时这个单元按 `gate-error` 走;审计写不进时这个单元按 `on_error` 走,改后字节不发;别的连接不受影响,守护进程不死,腾出空间后下一个单元恢复。
59. **线程池**:6 个槽同时写 64 MiB:另一条新连接的 DNS 和转发过 12g。
60. **拼进信封的字节**:`edits` 被截短、带换行、不是 JSON:这条记录都完整可读,有 `skipped`,发出去的是原始字节。
61. **一个单元一个进程**:正则 + 脚本 + 替换的链中间被杀,整条作废发原始字节;碰上两个脚本第二个写 `multi-script`;手改 `rules.json` 开 1000 个脚本算坏文件;脚本文件改了之后重启守护进程,这条规则不活,`rules enable` 后新代码生效。
62. **小事件洪流**:1 字节 `data` 的 SSE 打满上游,配 4096 个条件:另一条连接过 12g,这条流到点转原样。

## 自动适配(auto-adapt)

从原始流量自动猜 provider 线格式与 harness 约定,少写或不写手工 dissector。它只读、只猜、可被手工 dissector 覆盖;猜测结果在 UI 标「自动推断,可能不准」(不变式 4)。可作为 [3.1](3.1-adapter-contract.md) 的 Extension 独立推进。

## 安全边界

这是对 agent 流量的中间人修改能力。合法用途 = 操作者调试、实验自己机器上、自己账号下的 agent;不用于拦截或修改不属于操作者的流量。

- **规则的代码不进守护进程**:见 §不变式、§隔离。
- **蓄意破坏**:同一用户的程序不用规则也能 `kill` 守护进程、改 agent 的配置、读 0600 的采集,脚本直接往消息通道的 fd 写东西也算在这里。规则进程防的是 bug 和失控,不防同一用户的恶意程序,这个边界和没有规则时一样。
- **入口**:规则文件(同用户)、控制端点(0600 或带口令)、看板走 D26 的门(每用户口令就是这道门)。含 `script` 的规则看板不接受,只走 CLI,否则网页的写权限就升到了运行任意程序。
- **同一信任域**:同用户的程序能写 `rules.json`,和它能写 agent 的配置、能读 0600 的原始采集是同一个域,没有变宽。`status` 列出活着的规则,不能悄悄存在。
- **agent 改到自己**:给自己所在的 harness 加扣留规则,下一次调模型就停住了。`--help` 第一段写明;`pid` 匹配让规则只动测试进程;`trocar rules off` 从任何终端都能解。
- **凭据默认遮住**:`held`、`rules test`、`resend` 的输出里凭据类请求头一律遮住,也没有 `--reveal`;改头用 `--set-header`,不需要把真值拿到手。
- **不做**:改目标地址、换上游(D31③);后台自动演化规则;替换过期凭据;重发时重算代理链。
