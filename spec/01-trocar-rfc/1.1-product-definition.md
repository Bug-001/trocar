# trocar · RFC 1.1 — 产品定义

> **服务意图(A2)**:本模块奠定顶部意图 ①② 的共同地基——定义"trocar 是个什么软件"。1.x–4.x 全部据此展开;它是下游一切的对齐锚。
> **受众**:人(核对这是不是你要的软件)+ agent(据此不漂移地实现)。
> **状态**:已定稿。顶部意图与 Non-Goals 的单一权威在 [0.0-overview](0.0-overview.md)。

---

## Goal

构建 **trocar**——一台**跨 provider 的透明 agent 流量示波器**:不改被测程序(唯一的有界例外见 D37④:dsh、OpenCode 与 pi 没有只对自己生效的数据入口,用一个进程内插件,只把 trocar CA 追加进该进程的信任,不读、不改、不发请求 / 响应字节,不联网,不写 agent 配置;边界见 [4.6](4.6-process-collector.md) §身份与信任)、不接 SDK,把任意 agent 应用真正发给大模型的完整上下文 + 流式回复 + usage 逐字采下来,按步回放、逐层拆解。**为何做**:透明采集 + 逐字上下文回放 + cache 真相在 Claude Code 单 harness 上已验证可行;trocar 把它泛化成"跨 provider 产品"。

## 前置定义(Definitions)

- **harness**:一个 agent 应用。v1 八个(D37):Claude Code · Codex · OpenCode · Kimi Code · DeepSeek `dsh` · Hermes · Z-Code · pi;按进程身份认,不按 UA(见 [0.0-overview](0.0-overview.md) D37)。
- **线格式 / 厂商**(原「provider」,D37 拆成两条轴):线格式按端点与 body 认(Anthropic Messages / OpenAI Responses over HTTP 或 WebSocket / OpenAI Chat Completions),是适配层要抹平的"轴 B";厂商按上游 host 认,决定 cache 语义与价格。
- **session**:某 harness 一次任务的**全部上下文流**(一串 `/v1/messages` 或等价调用)。trocar 的核心对象。
- **context-block**:一次 call 的上下文里一个有序块(tool 定义 / system 段 / 一条 message 的一个 content 块)。回放的最小粒度。
- **cache-event**:某步相对上一步的缓存事实(前缀复用了多少、在哪断、命中/未命中 token),用真实 response usage 得出、非臆测。
- **adapter**:把某 (线格式 × harness 约定) 的原始流量归一化到统一模型的适配器(即 D25 的 dissector)。加线格式 = 加一个 dissector;加 harness = 加一个 harness 约定文件(D37)。
- **采集源(capture source)**:拿到字节的机制——按进程采集器([4.6](4.6-process-collector.md),D31:Linux 驱动模式 / macOS、Windows 代理模式)。与 adapter 正交:源管"怎么拿到 bytes",adapter 管"bytes 什么意思"。
- **逐字忠实 vs 元数据**:原始 bytes 逐字存 = 忠实;只存名字/大小/计数 = 元数据(如**旧 v0 trace 的 tool schema** 只留参数名+长度、D40 之前的非 LLM 调用只存了请求体长度——**D15 后 tool schema 逐字存,D40 后非 LLM 调用也逐字存**,见 §4)。

## 产品定义(连贯叙事)

**为谁 · 解决什么 job。** 你——研究 / 构建 agent 系统的人。你反复要回答两类问题:**(行为)**"这个 agent 这一步到底往上下文里加了什么、为什么这么决策";**(上下文 / cache 工程)**"它的上下文怎么拼、缓存命中在哪断、什么随每步变化"。今天这两类问题都难答:你要么盯着一堆原始 JSON,要么在代码里 print,要么信任某个 SDK 替你抽象过的视图。

**替代方案 + 差异化。** 现有手段都残缺:harness 自己的转录 JSONL **看不到真实 payload**(只有渲染后的对话);`OTEL_LOG_RAW_API_BODIES` 只有部分 harness 支持;Langfuse / LangSmith 这类 LLM 可观测**要你改代码接它们的 SDK**、且展示的是**它们的抽象**不是线上真相;print 调试是盲人摸象。→ **trocar = 透明(不改被测程序 / 不接 SDK)× 逐字忠实(线上原始 bytes)× 跨 provider(同一镜头看 CC / Codex / DeepSeek)× cache 真相(用真实 usage 不臆测)。** 这四条同时成立,是市面上没有的。

**主线怎么合成(信息架构)。** 核心对象是一条 **session**。你在一条**时间轴**上 scrub;正中是**忠实回放的对话流(骨)**——每一步一张 call-turn card(时间 / 模型 / token / 花费 / cache 命中),点开即逐字看那一步的完整上下文与回复。**cache 与资源(文件 / MCP / skill / plugin / tool)的进出与命中,是可勾选的叠加轨道(叠加层)**,挂在同一条时间轴上——想看行为就看骨,想看 cache/资源就勾亮对应轨。左侧 outline 导航,右侧上部资源管理器、下部可关闭的原始数据 panel。**同一个镜头适配三种 provider**;因为三家 cache 设计完全不同,cache 叠加层天然成了**横向对比"厂商如何做缓存工程"**的仪器——直接兑现意图②。每个功能都挂回一个 outcome:回放骨→意图①;cache/资源叠加→意图②;适配层→"换个 agent 也能用"。

**成功长什么样(可观测)。** 见下「验收」。

## 人-机-agent 协同(六要素)

trocar 本身就是人 + 确定性代码 + agent 协同的软件,产品定义须刻画:

1. **角色与职责**:**确定性代码**做采集 / 解析 / 归一化 / 渲染(枯燥、重复、要逐字准确);**agent** 做"面板如何随新数据进化"(D7,单独立项);**人**定方向 / 约束 / 验收,做产品与 cache 的判断。
2. **双向信息流**:人**输入**——显式选 session / 勾叠加轨 / 调面板布局 / 配采集源;隐式反馈——你实际在看什么。人**获取**——每步发生了什么(回放)+ 为什么(与上一步 diff)+ **置信度**(哪些字段逐字忠实、哪些只是元数据)。
3. **交互边界与监督**:采集是 **on-the-loop**(你不逐条批准每次抓包,但有一键开关 `trocar off` + `trocar doctor` 自检兜底);改包、重发只出于本机操作者的显式操作或其显式配置的规则(D30,见 [5.1](5.1-intervention.md)),没有操作者意图时原样转发。
4. **能力与可靠度边界(can vs how-well)**:**能**——逐字复现八个 harness、四种线格式(D37)的每步上下文与回复,**含 tool schema**(D15 已逐字采集);**何时失效 / 打折**——D40 之前的非 LLM 调用只存了请求体长度、操作者设为「只记日志」的类别没有体(D40)、跨记录拼接的上下文缺了前序记录(标「不完整」)、采集本身改变了客户端行为(标注)、超长内容按显示上限截断、**D15 前的旧 trace 的 tool schema 仅元数据**(每块标 `verbatim`/`metadata` 区分)——这些**保真边界 UI 里逐处写明**,不让人误判。
5. **委派代价**:把采集委派给按进程采集器,给你**新增**一项监督任务——"信任入口 / 引流配置是否正确、是否真在抓"。用 **`trocar on` 的计划确认 + `trocar status` / `trocar doctor`**([1.6](1.6-cli.md))兜底,把这项代价压到最小。
6. **连贯性测试(一段话闭环)**:*你打开 trocar → 选一条 Codex session → 在时间轴上 scrub 到某步 → 勾上 cache 轨 → 看到这步的 cache 断点 + 前缀复用了多少 → 点开这步的原始 payload,和真实 usage 对上 → 明白了 Codex 的自动前缀缓存这一步为什么没命中。* 能一段话讲完 = 产品连贯。

## Non-Goals

(全局权威在 [0.0-overview](0.0-overview.md);此处复述以便本文件自足)

- 没有本机操作者的显式操作时改包,或用被测程序的凭据发请求(D30)。
- 多用户 / 账号 / 云端分享(同一台机器上几个系统用户各装一套不算,见 D36)。
- 面板自演化工作流(单独立项)。
- 动系统代理,或接管整机流量(D31)。
- 实时告警 / 生产监控——trocar 是研究 / 学习仪器,不是运维监控。

## 验收(成功可观测 · 每条写成可跑的 check)

- **AC-1(意图①,忠实)**:取一条真实 CC / Codex / DeepSeek session,trocar 逐字回放出每步的完整上下文 + 回复;把回放导出的 bytes 与采集到的原始 NDJSON 对应字段 **diff,零差异**(**tool schema 亦纳入零差异**,D15;仅真正元数据字段——`log` 级的体、D40 之前只存了长度的非 LLM 请求体、旧 v0 trace 的 tool schema——除外,且这些字段 UI 标了"元数据")。
- **AC-2(意图②,cache 真相)**:对同一 session,cache 叠加层每步显示的"前缀复用 / 命中 / 断点"与该步 response 的真实 usage(`cache_read`/`cached_tokens`/`prompt_cache_hit_tokens` 等按 provider)**数值一致**;三家不同 cache 设计各取一例,都能在同一叠加层里正确表达。
- **AC-3(适配层通用)**:从只有 CC 适配器,新增第二 / 第三个适配器(Codex、DeepSeek),**不改前端主干代码**即点亮对应 session 的面板。可检验的判据:前端 `web/legacy/` 不含任何线格式 / provider 词表(`test/web-v2/no-provider-branches.test.mjs`),且加 harness 不改 `web/` 下任何文件(注册表一行 + 图标文件在 `src/off/`,随构建进看板)。
- **D37 读法**:上面「三条线 / 三家 / 第二、第三个适配器(Codex、DeepSeek)」读作「四种线格式 × 八个 harness」;DeepSeek 的 harness 是 `dsh`(Anthropic Messages),验收表 1b 的 DeepSeek 一条取 dsh 的真实 session;各 harness 的端到端门见 [4.6](4.6-process-collector.md) R2。

## Extensions(预留,不在 v1)

- 面板自演化工作流(D7):新数据到 → agent 自动开发 / 调试 / 让面板进化(依赖本 RFC 的适配契约 3.1 + 验收标准)。
- 更多 harness / provider 适配器(照 3.1 契约加,不改前端)。
- **修改 / 拦截 / 注入 / 重发([5.1](5.1-intervention.md) · D30 · D79)**:除了看,trocar 还要能改——拦下一条请求、改它的上下文再放行,替上游回答或往流里插东西,或把历史请求改完重发("agent 界的 Burp Suite")。trocar 不分观测 / 主动模式——这是采集器本身的能力,由本机操作者(运行 trocar 的人和这个人开的 agent)显式打开,上游一侧逐字存,agent 一侧由补丁逐字节还原并校验。自动适配(auto-adapt,只读)也归 [5.1](5.1-intervention.md)。机制见 5.1(D33)。
