# trocar · RFC 3.5 — 查询层(具名查询 + 段索引)

> **服务意图(A2)**:意图 ①②——前端与脚本一切视图的数据都经此层取。
> **受众**:人(核对每个视图都有对应查询)+ agent(据此实现查询集)。
> **前置**:原始记录与段索引在 [4.2](4.2-storage-etl.md);读出来的字段语义在 [3.2](3.2-normalized-model.md);用户可见的名字、参数与速度目标在 [1.6](1.6-cli.md) §4.1(**权威**,本单元不重复列);HTTP 外壳在 [4.4](4.4-server.md)。
> **决策**:D59(读数据只有 `trocar query` 一个核心,看板是它的 HTTP 外壳)· D63(这份代码跑在守护进程的查询工作进程里,两个壳先问它)。

## Goal
定义**哪些视图靠哪个具名查询**、查询函数的形状,使前端只按**名字**取数:它既不知道数据在明文段还是封存件里,也不拼路径、不解析原始记录。

## Plan(选定方案 + 取舍)
**选定**:一组**具名只读查询**,每个 = 一个纯函数 `(params, ctx) → 文档`,直接读原始记录([4.2](4.2-storage-etl.md) 的段 + 段索引)。`trocar query <名字>` 与 `GET /api/<名字>` 调同一个函数、返同一个文档([1.6](1.6-cli.md) §4.1,验收 V80)。
**备选(未选)**:① 先把记录摊进一个分析库再查 —— 多一条写路径、一份要维护的派生真相,而速度诉求由段索引 + 回源就能满足(D59);② 前端直发任意查询语言 —— 把存储细节漏进前端(违「适配缝不漏进前端」)。
**取舍**:具名查询集 = 存储变化只改查询层一处,前端稳定;派生层只剩 `~/.trocar/index/` 里可删可重建的段索引与用量旁注。

## 查询集(视图 → 查询)
名字、参数与分页键的权威在 [1.6](1.6-cli.md) §4.1 与附录 C;这里只记每个视图靠谁、读什么。

|---|---|---|

| 排轴 / 时间轴(1.3) | `session` | 该会话的记录按步排;每步的块构成按 [3.1](3.1-adapter-contract.md) 的 dissector 解出 |
| 中央回放:某步上下文(1.4/2.3) | `session`(页内)+ `block` | 有序块 + 回源逐字字节 + `faithfulness`([4.2](4.2-storage-etl.md) §回源指针) |

## 访问模式(MUST)
- **只凭段索引答的**:`traffic` 与 `overview` 除 `usage` 以外的数都只读段索引的行(行里本来就有 `ts, harness, class, host, path, status, stored_bytes, sent_bytes, received_bytes, session_key, is_llm`),一遍扫完就能聚合,和 `classes` 一样便宜;**MUST NOT** 为它们打开记录体(`usage` 见下一条)。
- **`overview.usage` 读按段的用量旁注,没补齐的部分有覆盖上限(保真边界 · 不变式 4)**:每次调用的用量不在段索引里;全窗现算要打开窗内每一条 LLM 记录(O(corpus),破 [1.6](1.6-cli.md) §4.1 的速度目标),让守护进程的索引器去解 provider 的体又被 D20 / [0.1](0.1-engineering-rules.md) §5 禁止。所以每次调用的用量进一份**读取侧写**的按段旁注:在 `~/.trocar/index/` 里与该段的索引并列,失效规则与段索引相同(D59),封存段的旁注一次写成、不再变,正在写的段只为新追加的字节补算;守护进程的写路径与段索引都不动。`overview` 读旁注;旁注已覆盖的调用一律计入;窗内还没有旁注的调用,查询只在**字节预算**(不是条数)内现算:按会话从新到旧、会话内按调用从新到旧,第一条装不下的调用让现算停下(这个会话与之后的会话都不再现算,结果确定、有界),已现算的与旁注覆盖的照样相加,一个会话不会因为一条大调用整体丢掉;其余由工作进程在答案发出之后补建(见下「谁执行它」),`coverage{sessions_read, sessions_in_window, calls_read, calls_in_window, capped_at, reason}` 逐字写明这一次读到哪、为什么停(`calls_in_window` = 窗内会话的模型调用数,`calls_read` = 其中旁注覆盖的加上现算了的;`sessions_read` 只数每条调用都读到了的会话),UI 就地标这条边界。所以第一次打开可以是部分覆盖,之后的读取补齐;旁注计入 D62④ 的写放大与每条记录的索引字节。依据:在 300 MB / 23 会话的参考数据上实测,只靠字节预算现算时 16 MiB 覆盖 0/23、守住 0.5 s 冷线的最大预算约 48 MiB 也只有 2/23,加预算换不来覆盖;只在工作进程内存里缓存,它闲置退出后冷启动又是 O(语料),守不住 D64 的 0.5 s;要求是真实语料上 ≈ 花费与主对话命中两格有数。旁注是派生结构([0.2](0.2-architecture-overview.md) §2),格式与谁写哪一笔见 [4.2](4.2-storage-etl.md) §用量旁注;落地它的 PR 在正文里请用户单独确认格式。
- **只读**。查询唯一会写的是 `~/.trocar/index/` 里可删可重建的段索引与用量旁注([4.2](4.2-storage-etl.md));不需要先跑别的命令。
- **谁执行它**(D63):守护进程按需 fork 一个低优先级的**查询工作进程**,`trocar query` 与 `GET /api/<名字>` 都先经它(于是两边共用同一份温缓存);没有守护进程应答时谁问谁就在自己进程里跑同一份代码,文档逐字节相同——所以查询 **MUST NOT** 把守护进程当前置条件。**还没有工作进程时守护进程立刻说「没有温的工作进程」**,问的人就地答(冷查询 MUST NOT 比本地慢),工作进程在背后被同一条查询热起来;「为下一次查询建的东西」(用量旁注的补建)只在工作进程里建,在答案的帧**整个写出之后**才开始(帧头与末字节之间工作进程不做别的事,这类工作失败也拿不走已发出的答案;一次性的 CLI 进程紧接着就退出,不替它付这笔钱)。会话骨架(下文「内存有界」)是答这一次本来就要折出来的,工作进程把它留下;缓存命中与不命中走同一条路,文档 MUST 逐字节相同。**工作进程的寿命**:没有请求排队、也没有请求在答时,守护进程起一个闲置钟(`service.mjs` 的常量 `QUERY_IDLE_MS`,120 秒),到点仍没人问就结束工作进程、把内存还回去;来了请求就停钟,所以闲置退出 MUST NOT 截断在答的查询,也不算失败(不留 `query-failed`)。看板开着时每 1.5 秒问一次,工作进程一直是温的;没人看时它不常驻,之后的第一条查询照上面的冷路由新 fork 的工作进程答。钟归守护进程不归工作进程:只有守护进程知道有没有请求在途,工作进程自己的钟在一次答案没写完时一直停着。依据:会话界面不得因文件大而闪断、要保持稳定,trocar 运行要轻量,要随时监测 CPU / 内存 / I/O / 网络上潜在的性能问题(实测:三条 CLI 查询之后工作进程闲着驻留约 396 MB 超过 6.5 分钟);不变式 4;[1.5](1.5-states-aesthetics.md) K-06。
- **缓存按依赖失效,不答陈旧**(D63 · D62③):工作进程缓段索引行、回读的记录与会话骨架,每次请求按源文件的 (大小, mtime, ctime) 核对。一个会话的答案只依赖**它自己的记录表**:别的会话添了记录 **MUST NOT** 使它的骨架作废(否则采集着就没有「附近的查询」);反过来,会话 X 新添的记录 MUST 出现在 X 的下一次查询里。会话长了,骨架接着折它还没折过的那几条记录,不论它们在步序上排在哪:调用结束时才写记录,所以并行的子代理、与长主调用并行的调用,记录会排在已折的记录之前。折叠按车道分开(车道内按步序,车道间互不读;子代理按 agent 分车道:harness 给 agent id 时每个 id 一条,WebSocket 上一条连接即一个子代理,两样都没有的合成一条;子代理的上一条调用是它 cache-break、前缀链与 compaction 判定的基线;看板上扁平线格式的子代理仍显示成一条车道),跨车道的次序(全局步序号 `gi`、流的编号)在出文档时按步序给,所以晚到的记录只落在它自己的车道上;它排在本车道已折的调用之前时,只重折这一条车道(该车道的记录按 id 回读);所以并行子代理里晚到的一条只重折它自己那个 agent 的调用;只有子代理只能靠到达顺序区分的会话(harness 既不给 agent id 也不给线程)才从头折,骨架丢了它留着的行(下文的堆预算挪了截断点)时也从头折。几条路折出的文档逐字节相同,MUST NOT 为同一会话的每个版本各留一份。依据:会话界面要保持稳定、随时监测 CPU / 内存 / I/O / 网络上潜在的性能问题、trocar 运行要轻量——晚到的记录在有并行子代理的活会话上几乎每次轮询都有,从头折一次是 O(会话)(已实测),按车道折让它只花一次温轮询的量级。车道按 agent 分是 [3.4](3.4-session-identity.md) 「一个 agent-id 一条子 agent 车道」同一条规则,扁平线格式(OpenAI Responses / Chat、WebSocket)不另立一套:按种类合一条时,一个子代理的晚到调用要重折全部子代理,它的 cache-break 也会跟别的子代理的上一条比。`block` / `calls` 回读的记录按**记录 id** 记住(记录只追加、从不改写,不变式 2,所以键不需要戳);折会话时的回读是一次扫读,不进这份缓存(骨架已经留下了它要的东西)。
- **读不全不静默(D38)**:某段读不出、某行坏了,照样给出文档,读不到的列进 `errors: [{where, code, reason}]`(`code` 是闭集码,`reason` 是人话、不带码),可选 `level`;`level:'note'` 是关于这一次读的事实(如 `index-cold`:这次读自己建了索引所以慢),不是丢失;客户端只把不带 `level` 的条目算作「没读全」。工作进程崩了或超时同理:查询照样答(重新 fork 或走本地那条),并留下一条带闭集 `code` 的记录;记录的 `reason` 带致命原因那一行(如 V8 的 `FATAL ERROR: …`)与 stderr 的尾巴,不只是调用栈的尾巴。同一条请求刚让工作进程崩过,冷却期(`service.mjs` 的一个常量)内再来就直接答 500 并带这条原因,不再 fork 进同一个崩溃;同一条请求接连的崩溃只留一条记录。超时只量工作进程的**沉默**:帧头到了之后,读者慢、响应在背压里等着不算沉默。依据:会话界面不得因文件大而闪断、要保持稳定,trocar 运行要轻量;不变式 4;[1.5](1.5-states-aesthetics.md) K-06。
- **分页**:大结果按游标分页(承 D6 虚拟化),契约在 [1.6](1.6-cli.md) §4.1(`--limit` / `--after`、文档里的 `page.next` / `page.has_more`)。`session` 的游标单元是**全局调用序号**:全部调用恒回时间轴要的轻量 meta,**重载荷(请求体、逐字块、响应文本)只回窗口内的调用**,窗口外的标 `paged_out:true`(保真边界 · 不变式 4:不静默丢)。按行回读记录的列表页(`calls`)除了条数还按段索引行的 `stored_bytes` 截(常量 `PAGE_STORED_BYTES` 只写一处,`src/query/named/index.mjs`),至少一行,`next` / `has_more` 照样说从哪接着。`session` 的一页另受一个**正文预算**(窗口内带正文的调用所带上下文的字节之和——逐块计,即每条调用的组成 `comp` 之和,所以跨记录缝合的上下文按缝合后的整段计,不按它那条记录的增量;常量 `PAGE_BODY_BYTES` 只写一处,`src/query/named/index.mjs`):从窗口中点(`--after` + `--limit` 的一半)向两侧、近的先带正文,带不下的照样回轻量 meta 并标 `paged_out`;至少一条带正文;`page.returned` 写明这一页实际带了几条。看板把要看的那一步放在窗口中点(跟随时是锚车道的最后一条,[1.2](1.2-shell-layout.md) 「跟随最新」),所以它总在页里。依据:会话界面不得因文件大而闪断、要保持稳定,trocar 运行要轻量;不变式 4;[1.5](1.5-states-aesthetics.md) K-06。
- **内存有界(按堆字节,先算后读)**:读取侧能占的堆由**一个**预算定:`min(进程的 heap_size_limit, 工作进程的堆上限)` 的三分之二(余下三分之一留给序列化答案与 GC;取 min 让本地与工作进程截在同一处,文档逐字节相同)。温缓存的条目与正在算的查询都按段索引行的 `stored_bytes` × 一个实测的堆倍数估算,在读记录、建装配**之前**让位(最久没用的缓存条目先走,所有缓存共用这一本账);估算超出预算的东西照样答这一次、但不留。MUST NOT 用条数或存储字节直接当内存上限。`session` **一条条折记录**(流式装配,车道内按步序,见上文「缓存按依赖失效」):每条记录解析、分车道、与同车道上一条比完前缀链与 cache-break 之后,只留时间轴要的轻量 meta(会话骨架:车道、用量、cache-break 与前缀摘要、状态、组成),正文随即放手;块键的记忆与事件的预览也只留自己的字节(每条车道只记它上一条调用的块键;切片会把整段原文一起留住)。跨记录缝合的上下文(Message Threads、WebSocket 链,D37 ②)**按定位符留,不按记录留**:每一段只记它在哪条记录(id)、哪个字段、哪条 JSON 路径,以及块能寻址到的那几层字节偏移;最新的几条链尾(主线程与并行的子代理)留着各自的上下文,续接与页里要看的调用是它的前缀;更早的链要用时按 id 分块回读那几条记录现取。留哪些只影响花费,不影响答案。一页要带正文的调用(上文「分页」的正文预算)再按 id 回读,用折时同一套函数现算。所以 `session` 的堆 = 骨架(O(调用数))+ 每条车道上一条调用的块 + 几条链尾的上下文 + 一页正文,不随会话的存储字节涨。只有连骨架都放不进预算时(按行数估)才只读从尾部往前放得进的记录,文档的 `truncated{shown, total, kept_mb, file_mb}` 写明(不变式 4,看板的非完整视图横幅,[1.5](1.5-states-aesthetics.md) K-06);**工作进程 MUST NOT 因为任何一个会话的大小而退出**。查询不把一整段读进内存;回源按偏移或帧解码。依据:会话界面不得因文件大而闪断、要保持稳定,trocar 运行要轻量;不变式 4;[1.5](1.5-states-aesthetics.md) K-06。

## 验收(可跑 check)
- 上表每个视图都有一条具名查询,在真实采集数据上跑出正确结果。
- `overview` 与 `traffic` 在跑完之后,每个段文件的 inode / 大小 / mtime 不变;`traffic` 与旁注齐全时的 `overview` **一条记录体都没有被打开**(只读段索引与旁注)。
- 字节预算截住现算时 `reason == 'byte-budget'`、`calls_read < calls_in_window`,被截会话里旁注覆盖的每条调用都在 `usage.rows` 的和里;装不下的那条之前(更新)的未覆盖调用都已现算。
- `overview.usage` 带 `coverage`:旁注还没建、语料又超过字节预算时,`sessions_read < sessions_in_window` 且 `reason` 写明为什么停;预算够时两个数相等。任何情况下 `usage` 都不冒充全窗精确值。
- 用量旁注:工作进程补建完之后再问同一个窗,`sessions_read == sessions_in_window`,且用量和等于这些会话在 `session` 里的 `steps[].usage` 之和;删掉旁注,答案只是退回部分覆盖再补齐,补齐后逐字段相同(不变式 2)。
- `trocar query <名字>` 与 `GET /api/<名字>` 逐字段相等([1.6](1.6-cli.md) V80)。
- 速度目标见 [1.6](1.6-cli.md) §4.1(冷启动进程、附录 D 的参考数据)。
- 删掉段索引后结果不变、只是慢;同时删掉的用量旁注只让 `overview.usage` 退回部分覆盖(上一条)([4.2](4.2-storage-etl.md) 验收 7)。

## Edge cases
- 空数据:每个查询返空列表 + `page.has_more:false`,不报错、不建空壳文件。
- 超大会话:分页契约兜底;查询不把整段读进内存。
- 缺字段(DeepSeek 没有 `cache_write`):聚合 MUST 容缺(用 `hit` / `miss` 而非 `write`)。
- 正在写的段:查询读到它已索引到的偏移为止,半行不当记录。

## Risk / 回滚
查询层是纯读:改查询不动数据,可即时回退;结果可疑时删段索引重建,源零损失。

## Extensions
更多分析查询(cache 工程对比、跨 harness 行为模式)——新增一个名字 = 加一个模块 + 一行注册,前端与外壳不改。
