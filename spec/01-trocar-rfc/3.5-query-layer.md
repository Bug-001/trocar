# trocar · RFC 3.5 — 查询层(具名查询 + 段索引)

> **服务意图(A2)**:意图 ①②——前端与脚本一切视图的数据都经此层取。
> **受众**:人(核对每个视图都有对应查询)+ agent(据此实现查询集)。
> **前置**:原始记录与段索引在 [4.2](4.2-storage-etl.md);上下文投影的格式在 [4.3](4.3-parse-index-cache.md) §上下文投影;读出来的字段语义在 [3.2](3.2-normalized-model.md);用户可见的名字、参数与速度目标在 [1.6](1.6-cli.md) §4.1(**权威**,本单元不重复列;会话读三个查询的文档形状以本单元 §会话读为准);HTTP 外壳在 [4.4](4.4-server.md)。
> **决策**:D59(读数据只有 `trocar query` 一个核心,看板是它的 HTTP 外壳)· D63(这份代码跑在守护进程的查询工作进程里,两个壳先问它) · D69(看板把会话读成骨架 + 每车道的块 id 列表,数据来自上下文投影)。

## Goal
定义**哪些视图靠哪个具名查询**、查询函数的形状,使前端只按**名字**取数:它既不知道数据在明文段还是封存件里,也不拼路径、不解析原始记录。

## Plan(选定方案 + 取舍)
**选定**:一组**具名只读查询**,每个 = 一个纯函数 `(params, ctx) → 文档`,直接读原始记录([4.2](4.2-storage-etl.md) 的段 + 段索引)与由它们抽出的上下文投影。`trocar query <名字>` 与 `GET /api/<名字>` 调同一个函数、返同一个文档([1.6](1.6-cli.md) §4.1,验收 V80)。
**备选(未选)**:① 先把记录摊进一个分析库再查 —— 多一条写路径、一份要维护的派生真相,而速度诉求由段索引 + 回源就能满足(D59);② 前端直发任意查询语言 —— 把存储细节漏进前端(违「适配缝不漏进前端」)。
**取舍**:具名查询集 = 存储变化只改查询层一处,前端稳定;派生层只剩 `~/.trocar/index/` 里可删可重建的段索引、用量旁注与上下文投影(`~/.trocar/index/ctx/`,格式见 [4.3](4.3-parse-index-cache.md) §上下文投影)。

## 查询集(视图 → 查询)
名字、参数与分页键的权威在 [1.6](1.6-cli.md) §4.1 与附录 C;这里只记每个视图靠谁、读什么。

| 前端视图 | 查询 | 读什么 |
|---|---|---|
| session 选择器 / fork 树(1.2) | `sessions` | 段索引的 session 键 + 时间 + 条数;血缘与 fork 判定按 [3.4](3.4-session-identity.md) 在读取侧算 |
| 排轴 / 时间轴(1.3) | `session` | 骨架:每条调用一行(以记录 id `rid` 为键)+ 车道头 + 事件,由上下文投影归约出(§会话读);每步的块构成按 [3.1](3.1-adapter-contract.md) 的 dissector 在抽取时解出 |
| 中央回放:某步上下文(1.4/2.3) | `session`(骨架)+ `lane` + `block` | `lane` 给该车道每步的块 id 列表与块定义;`block` 按 ref 回源逐字字节 + `faithfulness`([4.2](4.2-storage-etl.md) §回源指针) |
| cache 叠加(1.3) + call card(2.2) | `session` | 每步的 usage 与 cache 事实;cache-break 的散度点 = 本步块的帧哈希 `fh` 序列与本车道上一条成功调用的最长公共前缀,在归约里算([3.3](3.3-cache-model.md)),**前端不比任何文本** |
| 资源管理器(2.4) | `lane` | 资源生命周期:flat 事件在归约里折成 per-resource 段 + loads,部件只渲染折叠结果 |
| 总览页的统计(1.7) | `overview` | 一个时间窗(`--since` / `--until`)里的调用数与字节、会话数、按 harness 的分布,外加**有覆盖上限的**用量汇总(见下);按类别的分布与盘上占用归 `classes`,这里不重复(D24) |
| 流量表(1.10) | `traffic` | 一个时间窗里每个 (harness, host) 的末见、条数、发出与收到的字节、未记录的条数、按类别的计数;首见与 `harness_since` 取整个索引、与窗无关;合计带「这是下限」 |
| 跨会话分析(② 招牌)· host 页的请求列表与单条请求(1.10) | `calls` | 任何类别的调用列表(类别、host、路径、状态码、大小、保存级别、记录 id);`--host` 按域名筛,`--ref` 回那一条记录;凭据类头的值置空(`ctl.masked`),`--reveal <头名>` 与 `--ref` 一起给出那一个值 |
| 存了什么(D60③ · [2.6](2.6-detail-panel.md)) | `classes` | 类别表 + 每类在 24 h / 7 d / 全部的条数与大小 + 盘上占用,全部出自段索引 |

| 费用 | `pricing` | 价格表与它的来源 |
| 采集健康 | `status` / `doctor` | 分别调 `src/cli/status.mjs` 的 `statusDoc()` 与 `src/cli/doctor.mjs` 的 `doctorDoc()` |

## 访问模式(MUST)
- **只凭段索引答的**:`traffic` 与 `overview` 除 `usage` 以外的数都只读段索引的行(行里本来就有 `ts, harness, class, host, path, status, stored_bytes, sent_bytes, received_bytes, session_key, is_llm`),一遍扫完就能聚合,和 `classes` 一样便宜;**MUST NOT** 为它们打开记录体(`usage` 见下一条)。
- **`overview.usage` 读按段的用量旁注,没补齐的部分有覆盖上限(保真边界 · 不变式 4)**:每次调用的用量不在段索引里;全窗现算要打开窗内每一条 LLM 记录(O(corpus),破 [1.6](1.6-cli.md) §4.1 的速度目标),让守护进程的索引器去解 provider 的体又被 D20 / [0.1](0.1-engineering-rules.md) §5 禁止。所以每次调用的用量进一份**读取侧写**的按段旁注:在 `~/.trocar/index/` 里与该段的索引并列,失效规则与段索引相同(D59),封存段的旁注一次写成、不再变,正在写的段只为新追加的字节补算;守护进程的写路径与段索引都不动。`overview` 读旁注;旁注已覆盖的调用一律计入;窗内还没有旁注的调用,查询只在**字节预算**(不是条数)内现算:按会话从新到旧、会话内按调用从新到旧,第一条装不下的调用让现算停下(这个会话与之后的会话都不再现算,结果确定、有界),已现算的与旁注覆盖的照样相加,一个会话不会因为一条大调用整体丢掉;其余由工作进程在答案发出之后补建(见下「谁执行它」),`coverage{sessions_read, sessions_in_window, calls_read, calls_in_window, capped_at, reason}` 逐字写明这一次读到哪、为什么停(`calls_in_window` = 窗内会话的模型调用数,`calls_read` = 其中旁注覆盖的加上现算了的;`sessions_read` 只数每条调用都读到了的会话),UI 就地标这条边界。所以第一次打开可以是部分覆盖,之后的读取补齐;旁注计入 D62④ 的写放大与每条记录的索引字节。依据:在 300 MB / 23 会话的参考数据上实测,只靠字节预算现算时 16 MiB 覆盖 0/23、守住 0.5 s 冷线的最大预算约 48 MiB 也只有 2/23,加预算换不来覆盖;只在工作进程内存里缓存,它闲置退出后冷启动又是 O(语料),守不住 D64 的 0.5 s;要求是真实语料上 ≈ 花费与主对话命中两格有数。旁注是派生结构([0.2](0.2-architecture-overview.md) §2),格式与谁写哪一笔见 [4.2](4.2-storage-etl.md) §用量旁注;落地它的 PR 在正文里请用户单独确认格式。
- **只读**。查询唯一会写的是 `~/.trocar/index/` 里可删可重建的段索引、用量旁注([4.2](4.2-storage-etl.md))与上下文投影、它的折叠日志及两者的旁索引(`~/.trocar/index/ctx/`,只由查询工作进程写,[4.3](4.3-parse-index-cache.md) §上下文投影);不需要先跑别的命令。
- **读一场大会话的设计界**(设计约束,不是计时测试;在真实数据上量):① 一场自上次回答以来没长的会话,再问一次花工作进程 CPU ≤ 50 ms(D62「附近的查询 ≤ 50 ms · 采集着也算」,[1.6](1.6-cli.md) §4.1);② 跟随一场在长的会话,每条新调用让回答多约 4 KB 原始字节(约 1 KB gzip),花工作进程 3–10 ms(抽取 + 归约 + 行差);③ 工作进程闲置退出后重开一场已投影的会话,读投影并答出看板画首屏要的东西(`session` 的骨架回答加一条在握车道的一页 `lane`)≤ 0.3 s、答完留堆 ≤ 40 MB(6,600 条调用处),所以 fork、回答与画出合起来守住 D64 的 0.5 s 打开;整份文档的归约不在首屏的路上,只守下文「内存有界」的堆预算;抽取的峰值堆不随会话长度涨(门槛与量法见 [4.3](4.3-parse-index-cache.md) §4「门槛」);从没投影过的会话第一次打开,回答停在归约前沿并带 `pending`(下文「谁执行它」),不等全部抽完、折完;④ 看板的任何行为都不让工作进程一直热着(一条一直失败或一直贵的读,在客户端与服务两边都退避,见下文「读不全不静默」)。下文的上下文投影(每条记录只抽一次)、按版本的答案缓存与 `session --since` 的增量(§会话读)就是为这四条立的。依据:随时监测 CPU / 内存 / I/O / 网络上潜在的性能问题、trocar 运行要轻量、会话界面要保持稳定;D62([1.6](1.6-cli.md) §4.1);D64;D69;不变式 2、4;在一场约 5 800 次调用、906 MB 的真实活会话上的基线(没长的会话每次温读 0.8–2.0 s 工作进程 CPU、跟随时至多 40 % 单核、每次回答 1.08 MB gzip、冷首开 28–62 s、一串失败约 110 条 `query-failed`)与设计时的估算。
- **谁执行它**(D63):守护进程按需 fork 一个低优先级的**查询工作进程**,`trocar query` 与 `GET /api/<名字>` 都先经它(于是两边共用同一份温缓存);没有守护进程应答时谁问谁就在自己进程里跑同一份代码,文档逐字节相同——所以查询 **MUST NOT** 把守护进程当前置条件。**还没有工作进程时守护进程立刻说「没有温的工作进程」**,问的人就地答(冷查询 MUST NOT 比本地慢),工作进程在背后被同一条查询热起来;「为下一次查询建的东西」(用量旁注的补建)只在工作进程里建,在答案的帧**整个写出之后**才开始(帧头与末字节之间工作进程不做别的事,这类工作失败也拿不走已发出的答案;一次性的 CLI 进程紧接着就退出,不替它付这笔钱)。会话的归约状态(下文「内存有界」)是答这一次本来就要算的,工作进程把它留下;缓存命中与不命中走同一条路,文档 MUST 逐字节相同。**答案缓存**:一个名字 MAY 在 `QUERIES` 里与 `params` / `run` 并列声明 `version(ctx)`——它的答案依赖什么,只从温的段索引行与归约前沿里读,MUST NOT 读任何记录;`src/query/answers.mjs` 按请求(名字、参数、缩进、是否 gzip)留几份答过的字节串,合计不超过一个字节上限;版本相同就原样交回那串字节,不归约(在任何归约之前定)。`errors` 里多于版本自带的索引问题的答案(读失败、坏行这类)不留,所以读失败的结果从不被记住。`session` 与 `lane` 的版本 = 该会话成员的段索引行的身份 + 归约前沿 + 截断点(`truncated`)+ 索引问题。命中与不命中逐字节相同照旧成立(验收 #18)。**工作进程的寿命**:没有请求排队、也没有请求在答时,守护进程起一个闲置钟(`service.mjs` 的常量 `QUERY_IDLE_MS`,120 秒),到点仍没人问就结束工作进程、把内存还回去;来了请求就停钟,所以闲置退出 MUST NOT 截断在答的查询,也不算失败(不留 `query-failed`)。看板开着时每 1.5 秒问一次,工作进程一直是温的;没人看时它不常驻,之后的第一条查询照上面的冷路由新 fork 的工作进程答。钟归守护进程不归工作进程:只有守护进程知道有没有请求在途,工作进程自己的钟在一次答案没写完时一直停着。依据:会话界面不得因文件大而闪断、要保持稳定,trocar 运行要轻量,要随时监测 CPU / 内存 / I/O / 网络上潜在的性能问题(实测:三条 CLI 查询之后工作进程闲着驻留约 396 MB 超过 6.5 分钟);不变式 4;[1.5](1.5-states-aesthetics.md) K-06。
  - **后台抽取与归约**(D69②):工作进程按写入序把会话的成员抽进上下文投影,再按同一次序把抽好的成员折进归约状态、把产出追加进折叠日志([4.3](4.3-parse-index-cache.md) §4)。写入序 `pos` = 段序号 + 行号:记录 id 本来就是段名 + 行号,守护进程一次只写一个段([4.2](4.2-storage-etl.md)),所以它是全序,新记录不会落在已有记录之下。抽取与归约都以切片跑,每片 ≤ 50 ms CPU,片与片之间让出事件循环;后台切片里抽取与归约各得半片:抽取的预算是半片(一个成员不再细分,可以超出),归约至少得另半片,所以从第一片起归约前沿就往前走、`pending.done` 随之长,不等全部抽完才动(依据:本节「一片的固定开销与一次回答的功夫不随成员数涨」;要加载或更新的东西尽量增量、尽量少;不变式 4);请求本身仍严格串行、原子,切片只往投影与折叠日志追加。工作进程在三种时候续做:答一场有未抽或未归约成员的会话时,先在请求里按写入序做 ≤ 50 ms(跟随时这就盖住了上次轮询以来新落的一两条,所以最新的调用在紧接着的这次回答里);答案的帧整个写出之后,在后台切片里做到最后一个成员;闲置 ≥ 2 s 时,做最近写过的那场会话。切片不是请求:它们不占守护进程的闲置钟 `QUERY_IDLE_MS`,所以最后一个请求之后 120 秒工作进程照样退出;被退出截断的切片至多留一行撕裂的末行,按 [4.3](4.3-parse-index-cache.md) §上下文投影 在下一次追加之前截掉。工作进程不在时写下的记录(看板藏起或关掉超过 120 秒、agent 还在干活)是积压,下一次打开从前沿接着做。还没有这场会话归约状态的工作进程不折叠,从折叠日志按日志的前沿答;只有截断里有成员落在日志的前沿之上时,才在后台切片里从头重建归约状态(越过日志的前沿之前不写日志),再接着折那些成员——会话没长,重开的工作进程就不重建(依据:本节「读一场大会话的设计界」①④;trocar 运行要轻量;实测:没长的 6,572 条会话,重开的工作进程答完首屏后后台还花约 5.7 s CPU 重建归约)。投影与折叠日志只有工作进程写:本地那条(上面的冷路由)读它们,缺的成员抽取并全部归约,新行只进进程外的内存 arena、盘上什么都不写([4.3](4.3-parse-index-cache.md) §4),所以它从不带 `pending`,答案与工作进程在同一 `mark` 处的逐字节相同。归约按切片续做、没有状态的工作进程从折叠日志答、本地那条全折,依据:本节「内存有界」的本意(骨架就是归约状态,定义的全文不常驻);[4.3](4.3-parse-index-cache.md) §4「门槛」;实测(把投影留在堆里的工作进程约 11.5k 条调用处 OOM;一场 12.6k 条调用的真实会话整份折叠一次 2.6–3.6 s、每条调用常驻 10–16 KB);D69;不变式 2、4;D38;要加载或更新的东西尽量增量、尽量少、trocar 运行要轻量。一片的固定开销与一次回答的功夫不随成员数涨:成员的写入序位置在内存里是一个整数,即它在会话成员表里的位次(`indexRows` 段从旧到新、段内按采集次序;`segmentFiles` 给段排序与 `posCmp` 用同一条规则);抽取与折叠从游标接着走,成员表是上一次的延长时计划也只延长;新成员按二分插入并进留着的次序;回答只读变了的那些的行(依据:§访问模式「读一场大会话的设计界」②;实测的切片固定开销)。
  - **归约前沿**:一场会话的抽取前沿 `F` = 最大的 `pos`,使每个 `pos ≤ F` 的成员都已抽取;归约前沿 = 归约按写入序走到的最后一个成员,不超过 `F`。每个 `session` / `lane` 回答都是**归约前沿处**的文档:只归约 `pos` 不超过它的成员,`mark` = 归约前沿处那个成员的 rid;有成员在 `mark` 之上时带 `pending: {done, total}`,`done` = `pos ≤ mark` 的成员数,`total` = 成员数。它是 (盘, `mark`) 的纯函数,所以 `since` 的差是确定的,回答从不是抽了一半或折了一半的混合。`pending` 是就地说明的不完整态(不变式 4),没有控件;`trocar query session` 在终端里等:回答带 `pending` 时以该回答的 `mark` 问 `--since`,一旦有一次不带,就按它自己的参数问一次并印出那份(依据:§访问模式「读一场大会话的设计界」②;本条);看板不等、每次轮询把新折到的部分当普通的 `since` 增量收下。
  - **服务队列**(`src/query/service.mjs`):工作进程一次只答一条(它的内存靠这个有界)。排着队的请求,调用方在轮到它之前已经离开的,跳过不跑;服务次序是 `block`、`lane`、`session`、其余,同类之内先来先服务。所以一次 `block` 至多等正在答的那一条加一个抽取切片(≤ 50 ms),从不排在一串 `session` 读后面;看板一次至多发一条 `session`,所以它不会饿死。依据:不显示加载步骤,也不造成任何界面卡顿;D64;D69。

## 会话读(D69)

看板读一场会话只用三个具名查询:`session`(骨架)、`lane`(一个车道每步的块 id 列表 + 块定义)、`block`(块正文)。CLI、HTTP、工作进程与本地走同一条代码路径([1.6](1.6-cli.md) §4.1,D59);每个回答只是它的参数与盘上字节的函数。依据:D69;要加载或更新的东西尽量增量、尽量少,不显示加载步骤,也不造成任何界面卡顿;不变式 2、3、4。

- **id**:`rid` = 记录 id `<段>:<行号>`;车道键 = 该车道第一条调用的 `rid`;`bid` = 22 个 base64url 字符,即 `sec 0x1F role 0x1F 逐字字节` 的 SHA-256 截取前 128 位(截断,只取决于字节、区与角色);`fh` = 帧哈希,块的帧文字(不含缓存标记 `cache_control`)的 SHA-256,在线上与 `bid` 同形(截取前 128 位)。`bid` 管身份与传输(列表、定义、正文都按它);`fh` 是内容键:cache-break 的最长公共前缀与步间「新」/ 移除([2.3](2.3-context-window.md) §步间 diff)都按它比,所以缓存标记挪了位置不算内容变了;`mark` = 归约前沿处的 `rid`(空会话为 `null`;依据:§访问模式「归约前沿」——每个 `session` / `lane` 回答都是归约前沿处的文档);会话被截(`truncated` 不为 `null`)时后接 `@` 与截断点第一行的 `rid`(`<rid>@<rid>`),所以一个 `mark` 也说出它的文档是在哪个截断点下答的,客户端把它当不透明的串原样传回 `--since`(依据:本节验收 #19 `apply(full(M), since(M))` 与 `full(现在)` 逐字节相同;不变式 4)。逐字字节 = 块的 ref 指的那一段:请求块是 `req_body` 里的 JSON 节点,缝合来的项是它源记录里的节点,回复块是 `resp.raw::<a>-<b>` 的 SSE 区间。
- **每个回答**:`schema: 2`、`command`、`ok`、`errors: [{where, code, reason, level?}]`;`ok` 为真当且仅当 `errors` 里没有不带 `level` 的一条(依据:[1.6](1.6-cli.md) C.1「一切与期望一致」与 C.5「带 `level:'note'` 的一条不算读不全」)。
- **`session`**(`--id`;`--since M` 或 `--before R`;`--limit N`,默认与上限都是 1000;`--since` 与 `--before` 同给 → 400):
  - 整份:`base: null`、`mark`、`pending?: {done, total}`、`truncated`(`null` 或 `{shown, total, kept_mb, file_mb}`)、`more`(这一页之前还有行)、`meta`、`stats`、`logged`、`probes`、`unknown?: {records, reason, endpoints}`(会话里没有一个已注册的解析器读成调用的记录:条数、人话原因、它们的端点;没有这种记录时省去)、`lanes: [车道头]`(全部车道)、`calls: [行]`(这一页,按步序;不给 `--before` 时是最新的一页;≤ 1 MB 原始字节、至少一行)、`events: [{type, rid, lane}]`(这一页的行的)、`records: [{id, ts_request, is_llm_call, response:{status}}]`(落在这一页步序范围里的成员)。
  - 增量(`--since M`):`base: M`、`mark`、`pending?`、`truncated`、`meta`、`stats`、`logged`、`probes`、`unknown?`(与 M 处的不同时才带,变成没有时为 `null`)、`calls`(与 M 处的文档相比新出现或变了的行)、`gone: [rid]`、`lanes`(变了的车道头)、`lanes_gone: [车道键]`、`events`(`calls` 里每个 rid 的全部事件)、`records`(M 之后到 `mark` 为止新加入、落在归约读的范围里的每个成员的,是不是调用都算,与整份按页范围收成员是同一条规则;外加 `calls` 里每个 rid 的;按步序;依据:本节验收 #19 `apply(full(M), since(M))` 与 `full(现在)` 逐字节相同——只带调用的记录,非调用成员的记录跟随的客户端永远拿不到;不变式 4;D69 客户端靠增量同步)。M 处的文档 = 只归约 `pos ≤ M` 的成员,它是确定的,所以增量就是两份确定文档之差;行按步序(`src/view/step-order.mjs`:`ts_request`,再按 id)排,晚到的行可能排在客户端已有的行之前,客户端按这个次序插入。认不出的 M → 整份,`base: null`:M 的 `rid` 不是成员,或 M 说的截断点(`@` 之后;没有 `@` = 没截)与现在的第一行不同。截断点挪了,M 处与现在之间进出截断点的成员不在 `calls`、`gone`、`records` 任何一个里,增量补不齐(依据:本节验收 #19;不变式 4;认不出的 M 本就答整份)。`unknown` 的依据:不变式 4;D38;[1.5](1.5-states-aesthetics.md) K-20;[3.1](3.1-adapter-contract.md) 验收 #4。
  - 行(闭集):`rid, lane, ts, ctx, comp, usage, tools, status, error, errMsg, unparsed, rec{id, request{model}}, compaction, compactionInferred, gt, probe, reqIncomplete, wsIncomplete, respIncomplete, wire{cacheSemanticsKnown, contextState, contextMissing, reqEncoding, labels[{id, label}]}, cacheBreak{cause, attribution, idx, refRid, gt, firstCall}`;没有的字段省去。`cacheBreak.idx` = 本步块的帧哈希 `fh` 序列与本车道上一条成功调用的 `fh` 序列的最长公共前缀长度,在归约里算([3.3](3.3-cache-model.md));前端不比任何文本。
  - 车道头(闭集):`lane, kind, icon, label, task, note?, count, first, last, peakCtx, spawnRid, parent, flagged`。
- **`lane`**(`--id`、`--lane K`;`--from RID`、`--to RID` 与 `--ledger C` 至多给一个,多给 → 400、CLI 退出码 2):`lane, base, mark, steps, defs, resources, seen, events, prev, next, ledger_next`(`--ledger` 的依据见下文「`resources` 与 `seen`」)。
  - 不给 `--from` / `--to`:该车道的尾页,`base: null`。`--from` 在车道里:它之后的步,`base: RID`。`--from` 不在车道里:重置 = 尾页,`base: null`。`--to`:恰在 RID 之前结束的那一页。一页 ≤ 1 MB 原始字节,步、`defs`、这一页发出的每个事件与账本条目都计入,`base: null` 时另带的压缩与摘要事件也算(依据:D69③ 页只是传输分块)。`base: null` 的回答(尾页、重置、`--to`)首步是关键帧;`--from` 的回答首步的 `ops` 相对 `base` 那一步的列表(客户端手里已有),所以跟随时一次更新只传复制段与新增的 `bid`。`next` / `prev` = 取相邻页时当 `--from` / `--to` 传的 rid,到了尖端 / 车道起点为 `null`。
  - 步:`{rid, parent, ops, reply, attrs, detail}`。`ops` 从父步的列表重建本步的列表:`[0, from, len]` 复制父列表的一段,`[1, bid…]` 新增;关键帧是一个装着整份列表的新增操作。ops 在回答时按物化出的列表对 id 贪心匹配算出,不取决于投影里存的是哪种基准。`reply: [bid]`;`attrs: {"<pos>": {query?, volatile?}}` 只给新增操作引入的位置(复制带着它的 attrs);`detail: {norm{stop_reason, usage}, respRefs, nonBlockKeys, extraMessages, wire}`。
  - 定义(闭集):`bid, fh, ref, sec, role, kind, label?, name?, mcp?, cc?, ff, head{role, tag, label}, preview, chars, bytes, resKey?, r{as, tone?, title?, f?}`;寻址不到的块 `ref: null`,带 `unaddressable`(原因)与 `inline`;tool_result 的 `r` 是合并后的渲染规格。`defs` = 这一页的步引用到、且 `base` 那一步的列表与 `reply` 里都没有的定义,每个一次(没有 `--from` 时是这一页引用到的全部);引用过、离开、又回来的块再发一次(依据:§访问模式「读一场大会话的设计界」②;下文「定义按车道重发」——客户端按 `bid` 只留一份,重发有界;旧规则每次回答都要物化本车道到 `--from` 为止的每一份列表)。
  - `resources` 与 `seen`:`resources` = 本车道在 `mark` 处账本里的资源,带 rid(`segments[{enter, evict}]`、`loads[{rid, range, via}]`);`seen: [{path, firstRid, count}]` = 本车道在 `mark` 处账本里的条目原样,不按已打开的资源去掉,不设上限;`base: null` 时两者全部发,`--from` 时只发在 `mark` 处新出现的条目,以及在 `base` 处重放的账本与 `mark` 处的账本里字节不同的条目。要发的条目按键序(先资源按 `kind::label`,再 `seen` 按 `path`,都按 UTF-16 码元序),在这一页的步、`defs` 与事件之后还有地方时依次装进这一页,没装下的由 `ledger_next` 指名(不透明的游标,都装下了为 `null`);`lane --ledger C` 不答步,答本车道 `mark` 处账本里键在 `C` 之后的条目,至多一页、至少一条,带它自己的 `ledger_next`(依据:本节「一页 ≤ 1 MB」;不变式 4;代码从少——游标只是加宽 `lane` 已有的翻页,另立具名查询要多一行 `QUERIES`、参数、版本、戳与 1.6 / C.5 / 4.4 的行)。客户端按资源键替换资源、按 `path` 替换 `seen`,所以较晚 `mark` 处的一块也是准确的,手里那步之后的变化照样随 `--from` 来;去掉已打开的路径(`sameFile`)与排序归看板的模型([2.4](2.4-resource-explorer.md) §涉及源文件与接口)。依据:本条之前的增量规则;不变式 4([2.4](2.4-resource-explorer.md) 验收 #1:只见到名字的条数照实,不被服务端的上限截短);D69。
  - `events`:车道事件,`step` 换成 `rid`、`streamId` 换成 `lane`;发的是这一页覆盖到的步上的事件:`base: null` 时是这一页自己的步,`--from` 时是 `base` 之后到这一页最后一步为止的步。`base: null` 时另带本车道在 `mark` 处的全部 `compaction` 与 `summarize` 事件。客户端按回答覆盖到的步整步替换事件,另带的那些按 (`type`, `rid`) 合并。依据:上条「一页 ≤ 1 MB」;D69③(页只是传输分块);D69 的「要加载或更新的东西尽量增量、尽量少」;本节「手里车道的页」;§访问模式「读一场大会话的设计界」②;[2.4](2.4-resource-explorer.md) 的压缩组与生命周期文字读整条车道的压缩事件;主对话车道的事件在 1,236 条调用时单独就有 1.8 MB。
  - 每个 `user` 事件带 `k`:它在本车道 `mark` 处的 `user` 事件里按步序的序号,从 1 数。依据:不变式 4 与 [2.2](2.2-call-turn-card.md) 的「第 K 次提问」(K 不随客户端手里有几页而变)。
  - 安全审查调用的结论只在 `lane` 回答的 `events` 里:`{type:'monitor', rid, lane, verdict, flagged}`;骨架的行与车道头都不带 `verdict`,行也不带 `flagged`(依据:D69 骨架只给每一步从首次画出就要的东西、按车道的内容随车道来;[1.5](1.5-states-aesthetics.md) K-22 读的就是 `events[type=monitor].verdict`;每行都带一段审查回复会撑大骨架)。
- **`block`**(`--ref` 可重复):`blocks: [{ref, bytes, encoding, fidelity, truncated}]`,按 ref 的次序一个 ref 一项;读不出的 ref `bytes: null`,并在 `errors` 里有一条 `where: <ref>`,其 `code` 取自闭集 `BLOCK_PROBLEMS`(`src/health/codes.mjs`:`record-missing` · `record-unreadable` · `field-missing`)(依据:本节「每个回答」的每条 `errors` 都带闭集 `code`)。
- **客户端取哪个 `from`**:只凭 `since` 增量,客户端为每条手里的车道找出它最早受影响的步:车道是本车道的新行、手里的行车道换走了(重新分车道、只按到达区分的子代理)、或 `gone` 的 rid。受影响的行都排在手里的尖端之后时,问 `from=<手里的尖端>`;否则丢掉从最早受影响那步起手里的步,问 `from=<它前一步>`,那步是车道首步时整条车道重取。没有这条规则,一条排在尖端之前的晚到调用(辅助车道里的并发调用、重新分车道)永远到不了客户端,因为 `from=<尖端>` 只说尖端之后的步。
- **手里车道的页**:大于一页的车道按页拿着。首次画出之后,先顺着锚车道的 `ledger_next` 取完它的账本,再在空闲时从新到旧取余下的页(依据:不变式 4——[2.4](2.4-resource-explorer.md) 的组头条数等这条链走完才准);拖动时播放头离手里的边缘不到 32 步就请求下一页,所以拖动在实际中碰不到缺页的步;碰到时按 [2.3](2.3-context-window.md) 的车道未到手规则画那一步。
- **定义按车道重发**:共享的工具与系统定义每条车道发一次(各约 8 KB gzip)。这是有界的(把全部车道走一遍约 1.5 MB),客户端按 `bid` 只留一份;跨车道的定义字典会让回答取决于客户端手里有哪些车道(D69 的备选,未选)。
- **ETag 两段**:`session` 与 `lane` 回 `ETag: "<stamp>:<version>"`。守护进程比 stamp 段([4.4](4.4-server.md) 的 stat stamp,D66②),相同就独自答 304、不唤工作进程;否则转发,工作进程比版本段(上文「谁执行它」的 `version(ctx)` 加参数),相同就答 304 并带新的完整标签,花工作进程 CPU ≤ 50 ms。所以别的会话在采集时,没长的会话照样答 304(守卫 `test/query/stamp.test.mjs`)。
- 契约样例:`test/fixtures/session-read-contract.json` 的 `session_full` · `session_since` · `session_pending` · `lane_keyframe` · `lane_ops` · `lane_reset` · `lane_ledger` · `block_multi`

- 字节预算截住现算时 `reason == 'byte-budget'`、`calls_read < calls_in_window`,被截会话里旁注覆盖的每条调用都在 `usage.rows` 的和里;装不下的那条之前(更新)的未覆盖调用都已现算。
- `overview.usage` 带 `coverage`:旁注还没建、语料又超过字节预算时,`sessions_read < sessions_in_window` 且 `reason` 写明为什么停;预算够时两个数相等。任何情况下 `usage` 都不冒充全窗精确值。
- 用量旁注:工作进程补建完之后再问同一个窗,`sessions_read == sessions_in_window`,且用量和等于这些会话在 `session` 里的 `steps[].usage` 之和;删掉旁注,答案只是退回部分覆盖再补齐,补齐后逐字段相同(不变式 2)。
- `trocar query <名字>` 与 `GET /api/<名字>` 逐字段相等([1.6](1.6-cli.md) V80)。
- 速度目标见 [1.6](1.6-cli.md) §4.1(冷启动进程、附录 D 的参考数据)。
- §访问模式「读一场大会话的设计界」四条在真实活会话上量(前后同一方法);不写成计时测试。
- 删掉段索引后结果不变、只是慢;同时删掉的用量旁注只让 `overview.usage` 退回部分覆盖(上一条)([4.2](4.2-storage-etl.md) 验收 7)。

## Edge cases
- 空数据:列表查询返空列表 + `has_more:false`;空会话的 `session` 返 `mark: null`、`more: false`;不报错、不建空壳文件。
- 超大会话:上下文投影让抽取只付一次、骨架按行有界(§访问模式「内存有界」);连骨架都放不进预算时才由阶梯截断兜底(`truncated`,K-06);查询不把整段读进内存。
- 缺字段(DeepSeek 没有 `cache_write`):聚合 MUST 容缺(用 `hit` / `miss` 而非 `write`)。
- 正在写的段:查询读到它已索引到的偏移为止,半行不当记录。

## Risk / 回滚
查询层是纯读:改查询不动数据,可即时回退;结果可疑时删段索引重建,源零损失。

## Extensions
更多分析查询(cache 工程对比、跨 harness 行为模式)——新增一个名字 = 加一个模块 + 一行注册,前端与外壳不改。
