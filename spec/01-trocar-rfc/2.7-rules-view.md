# trocar · RFC 2.7 — Rules 视图

> **服务意图(A2)**:[5.1](5.1-intervention.md) 的看板入口(D30 · D79⑩)。它不直接回答意图 ①②,而是让受控实验做得起来,也让实验看得清:什么被扣着在等人、哪条规则动过什么、哪条没能应用、重发的结果和源记录差在哪。
> **受众**:人(放行或断开一条被扣的单元;写、试、开、关规则;看规则做了什么;比较重发和源记录)+ agent(据此实现 `web/src/screens/rules/**`,只读本单元 §数据与刷新 列的文档与路由,只写 §写 列的路由,不碰 harness 分支)。
> **前置**:规则、扣留、记录的全部语义 = [5.1](5.1-intervention.md);命令、回执、错误码与文档形状 = [1.6](1.6-cli.md) §4.4 – §4.6 与 C.5;控制面与计划—确认协议 = [4.4](4.4-server.md) §控制面 · D26;侧栏、路由、页头、右侧栏 = [1.2](1.2-shell-layout.md);词表、状态矩阵、数据规则 = [1.5](1.5-states-aesthetics.md);请求详情部件与「规则动过的请求」的标记 = [2.6](2.6-detail-panel.md) §C;Max rule delay = [1.11](1.11-settings.md) §规则;会话键 = [3.4](3.4-session-identity.md);决策 D26 · D30 · D33 · D79。

## Goal

规则和扣留不属于某一场会话,所以 Rules 是一个全局页。agent 被扣住时,人不用碰巧打开那场会话才看得到:

- **左侧栏的规则项**(`#/rules`)每一页都看得到;有单元被扣着时带一个数「Held 3」([1.2](1.2-shell-layout.md) §侧栏)。
- **全局页**从上到下四块,跨全部 harness、全部会话:**Held**(什么在等人)· **Rules**(有哪些规则、做了什么、哪些没应用)· **New rule**(写、试、存)· **Replays**(重发的结果)。
- **回放台右侧栏的 Rules 标签**只是这一页按这场会话筛出的一小块,同一组部件。

写都走 D26 的控制面:先回计划,确认后才改。Held 列表、Release、Drop 走守护进程自己的路由,不进查询队列,查询工作进程忙着或进了冷却时这几个按钮照样按得下去([5.1](5.1-intervention.md) §扣留「控制路由」)。

## 前置定义(Definitions)

- **单元**:闸判定和扣留的对象:一条请求、一条响应或一条 WebSocket 消息([5.1](5.1-intervention.md))。
- **单元的头**:请求上是它自己的请求头,响应上是它对应的请求的头,WebSocket 消息上是握手请求的头。
- **这场会话的单元**:单元的头经 `src/dissect/harnesses.mjs : sessionKeyOf()` 只看头取出的会话键,等于这场会话的 `session_id`。守护进程把这个键放在 held 行的 `session_key` 上;看板只比较这个值,不认头名(不变式 3)。这是 D20 的有界例外:只看头,只用于显示,不进原始层和审计流,也不用于 `match`,所以 `source: audit` 的行是 `null`。头里没有会话键的单元不算任何一场会话的,只在全局页(会话键只在 body 里的、合成键的 harness、遥测这类不属于会话的流量都是)。
- **控制路由**:守护进程自己答的路由,不经查询工作进程。
- **没应用**:[5.1](5.1-intervention.md) 的「跳过」:规则本该动手但没动手,原因在 `skipped.why`。
- **灰行**:Held 里已经结束的单元(`agent-gone` · `upstream-gone`)。

## Plan(选定方案 + 取舍)

**选定**:一个全局页,四块;回放台的标签用同一组部件,多一个 `session` 入参。第一版写规则就是一个 JSON 编辑框,agent 写的也是 JSON。

**备选(未选)**:
1. 只放在回放台的标签里——人要碰巧打开那场会话才看得到扣留;头里没有会话键的单元没有地方放。
2. 全站横条写「有请求被扣着」——[1.2](1.2-shell-layout.md) 否决了横条;侧栏的数每一页都看得到,够了。
3. 表单向导——规则的字段是 JSON,向导要把 [5.1](5.1-intervention.md) 的表再画一遍,还总落后于它。
4. 放行走查询工作进程——工作进程忙或冷却时按钮按不下去,而这正是 agent 在等的时候。
5. 「命中次数」一列——命中但没改动不留记录,没有这个字段;想知道会命中多少,用 Test on captured calls。

## 状况卡

规则整体不正常时,第一张卡说这件事,所以它不进页头区。原因码与原文在技术细节。

| 状况 | 屏上 | 来源 |
|---|---|---|
| 连续崩溃后不开规则(D38 `rules-tripped`) | 「No rules are running: the daemon stopped unexpectedly twice with rules on.」+「Rules that drop on error are not running either. Only Enable brings rules back; changing the rules file does not.」 | `rules` 的 `tripped`;[5.1](5.1-intervention.md) §住哪「连续崩溃时不开规则」 |
| 规则文件读不通(`rules-unreadable` · `rules-unparsable`) | 「The rules file can't be read. trocar keeps running the last good copy it read, if it has one.」 | `rules` 的 `errors` 里指向 `rules.json` 的条目;这时 `rules` 是空的,这张卡说清它不等于没有规则 |

## Held

有行才画,放在最上面,因为它在等人。没有行时这块不出现,不写「什么也没扣」。

| 元素 | 屏上(例,虚构) | 来源 | 规则 |
|---|---|---|---|
| agent | 图标 + 名字 | `harness` → `harnessKey()` | [1.2](1.2-shell-layout.md) §agent chip |
| 路径 | 「POST /v1/messages」;响应前面写「Response」,WebSocket 写「WebSocket message」 | `on` · `method` · `path`;`host` 在说明气泡里 | 等宽,照原样 |
| 等了多久 | 「held 40 s」 | `waited_ms` | 两次读之间本地走表 |
| 到点 | 「20 s left, then forward」/「20 s left, then drop」 | `left_ms` · `on_timeout` | 到点按 `on_error` 走;没有人操作也解开([5.1](5.1-intervention.md) §动作) |
| 规则 | 规则名 | `rules[]` | 链到 `#/rules?rule=<name>` |
| 展开 | 点行头看这个单元的头和体 | 头:`GET /control/held?id=<id>`(`held show` 的文档);体:`GET /control/held/body?id=<id>`(切片流式读) | 凭据类头遮住,没有「显示」([5.1](5.1-intervention.md) §安全边界);有修改规则时这里是改过的版本,和 Release 发出的字节一样 |
| 编辑 | 文本框 | 同上 | 文本体在显示上限(`BODY_SHOW_CHARS`)以内才可编辑。更大的或二进制的只读,体的显示同 [2.6](2.6-detail-panel.md) §C,改法 `trocar held release <id> --body-file <file>` 在技术细节。改头只走 CLI |
| 按钮 | Release · Release changed · Drop | §写 | Release changed 只在文本框的内容和收到的不同时画 |
| 灰行 | 灰掉,写结果,例「Agent gave up while held」 | `state`(`agent-gone` · `upstream-gone`),词归 [2.6](2.6-detail-panel.md) §C | 没有按钮,不计入侧栏的数;到它自己的 `release_after_ms` 离开列表,事实留在 `query held` 与审计流 |

行以 `id` 为键。到点、被 agent 放弃、被别的写者放行的行在下一次读时变灰或离开;读者开着的编辑框里的字不被轮询改掉,按钮回 `held-gone` 时就地写结果。

## Rules

每行一条规则,次序照 `rules.json`:它就是多条规则命中时的执行次序([5.1](5.1-intervention.md) §规则)。

| 元素 | 屏上(例,虚构) | 来源 | 规则 |
|---|---|---|---|
| Name | 「swap-alpha」 | `name` | `note` 在说明气泡里 |
| What it does | 「Replaces ALPHA with BRAVO in claude-code model calls」 | `summary` | 服务端从规则生成(`src/rules/`),前端不解读规则 |
| Changes | 「12」 | `changes` | 改动数,定义见 [5.1](5.1-intervention.md) §规则「四个词」;`'unknown'` 写「—」,不写 0 |
| Last | 「12:01」 | `last_change` | `fmtWhen()` |
| Not applied | 「3」 | `not_applied` | 点开列出每一次(§Not applied);`'unknown'` 写「—」 |
| State | 见下表 | `state` | 每行恰好一个控件 |
| 展开 | 规则的 JSON;技术细节里是它在哪一档、要不要缓冲 | `GET /api/rules?rule=<name>` 的 `rule` · `tier` · `buffers` | 这些在写完规则时就告诉人它贵不贵 |
| Turn all rules off | 卡头的按钮 | §写 | 有开着的规则或扣着的单元时才画 |

| `state` | 屏上 | 控件 |
|---|---|---|
| `disabled` | 「Off」 | 开关 |
| `live` | 「On」 | 开关 |
| `waiting` | 「On · waits for trocar on」(开着,它的 harness 都没在记录) | 开关 |
| `stopped-by-off` | 「Stopped by off」 | Enable |
| `limit-reached` | 「Limit reached」 | Enable |
| `resting` | 「Too slow, trying again at 12:03」(时刻来自 `resting_until`) | 开关 |
| `process-gone` | 「Its process ended」(规则用 `pid` 钉着的进程没了) | Enable |
| `load-failed` | 「Script changed or didn't load」(脚本文件和 `script_sha256` 对不上,或载入失败) | Enable |
| `tripped` | 「Not running」,原因在 §状况卡 | Enable |
| 其他值 | 原值进技术细节,外面写「State unknown」 | —([1.5](1.5-states-aesthetics.md) §数据规则) |

含 `script` 的规则(行的 `script` 为真)照常列出,控件见 §写「含 `script` 的规则」。规则列表为空、文件也读得通时这张卡写「No rules yet」。

### 警示行

有没应用的,这张卡的第一行起每个 (规则, 原因) 一行,这条规则的 `last_not_applied` 在最近 1 小时里才出现。话按原因写:「swap-alpha did not apply to 3 requests: it took longer than 200 ms」;这条规则 `on_error` 是 `drop` 时后面加「They were dropped.」。字面上不写「went out without」:一条 `forward` 规则没应用的请求,可能被同一单元上别的规则的 `on_error: drop` 断开了。数是 `not_applied_by[<why>]`。行是链接,打开 §Not applied。

| `why` | 冒号后面的话 |
|---|---|
| `timeout` | it took longer than <`max_delay_ms`> ms |
| `peer-timeout` | another rule ran out of time |
| `queued` | it was still waiting for the rule process when the time ran out |
| `crashed` | its rule process crashed |
| `cooling` | it is resting after repeated failures |
| `no-runner` | the rule process can't start |
| `expect-continue` | the agent was waiting on Expect: 100-continue |
| `encoding` | the body's compression can't be read |
| `not-utf8` | the body isn't UTF-8 text |
| `too-big` | the body is over 64 MiB |
| `event-too-big` | the event is over 1 MiB |
| `multi-line-event` | the event has several data lines |
| `streaming` | the response didn't finish in time; add whole to wait for it |
| `http10` | HTTP/1.0 can't carry a changed stream |
| `edits-full` | the changes were too large to record |
| `bad-result` | the rule process returned a result trocar couldn't use |
| `multi-script` | another rule's script already ran on this request |
| `pipelined` | the request arrived before the last response ended |
| `no-recorder` | the connection's recorder had stopped |
| `credentialed-hop` | the request goes through a proxy with a password |
| `head-too-big` | the request head is over 64 KiB |
| `head-timeout` | the request head didn't arrive in time |
| `not-http` | the connection isn't HTTP |
| `blind` | trocar can't see where requests start on this connection |
| `ws-compressed` | the WebSocket was already compressed |
| `passthrough` | the connection isn't decrypted |
| `gate-full` | too much is held or buffered already |
| `gate-error` | trocar hit an error handling this request |
| 其他值 | 原值进技术细节,外面写「reason unknown」 |

`timeout` 行带一个链接「Max rule delay ›」→ `#/settings/rules`。这张表就是 [5.1](5.1-intervention.md) `skipped.why` 的闭集,词在 `labels/rules.mjs`,键的完备性归 [1.5](1.5-states-aesthetics.md) `test/web-v2/labels-complete.test.mjs`。

### Not applied

点开一条规则的 Not applied 或一行警示,列出每一次:时间、harness、路径、原因、这一单元实际发生了什么(发出去了或被断开);有 `ref` 的行链到 host 页的请求详情。来源 `GET /api/interventions?rule=<name>&skipped=<why>`,按 `next` 翻页,读的是段索引,所以带「截至」。透传、不是 HTTP 这类没有信封的情况在 `flows/` 的连接行上,这里没有 `ref`,一条连接一行。

## New rule

一个 JSON 编辑框(等宽文本框,不是表单)加两个按钮。框里的字只在内存里;轮询、读写失败都不动它。

| 元素 | 屏上 | 规则 |
|---|---|---|
| Test on captured calls | 结果就在按钮下面:「Matched 3 of 20 calls」,每条一行:`ref`、改了什么(`would` 或 `edits` 的摘要)、用了多久 | 对框里还没存的规则跑 `rules test` 同一个函数,取最近 20 条记录(`--last 20`),什么都不写、不发。`over_max_delay` 点名时警告:「It took 340 ms; the limit is 200 ms」。`cannot-test` 的记录写「Can't test: <原因>」,不算没命中;`counts.continuations` 不为 0 时单独一行「N are continuations, with only the new part」 |
| Save | 回执写在框下面:「Saved swap-alpha. It is off: test it, then turn it on」 | 等于 `rules add`;同名时计划写明「Replaces swap-alpha. It will be off」,确认后走 `--replace`。计划里带 `rules add` 回执的全部 `notes`([1.6](1.6-cli.md) §4.4) |
| 校验失败 | 服务端的话写在框下面,框里的字不动 | `rule-invalid`:`rules add` 退出 2 的全部情况都走这里,`rules.json` 一个字节不变 |
| 超过 64 KiB | 「Too large for the board: use trocar rules add <file>」 | 控制端点的 JSON 上限([5.1](5.1-intervention.md) §扣留「控制路由」);先在页面上判,不发请求 |

规则存下时是关着的,先试再开([5.1](5.1-intervention.md) 已定 6)。

## Replays

重发不进会话时间轴(没有 `calls` 行),都列在这里,新的在前。

| 元素 | 屏上 | 来源 | 规则 |
|---|---|---|---|
| 行 | 时间 · agent · 路径 · 「rebuilt」/「edited」 · 状态 · 「Sent by trocar」 | `replays` 的 `ts` · `harness` · `path` · `rebuilt` · `edited` · `status` | 「rebuilt」「edited」照记录;没有就不标。失败的行写 `error`。确认之后被拒的重发(`resend-busy`)也是这样一行,什么都没发,没有并排看 |
| 批次 | 同一批的行紧挨着,批头「2 of 5」 | `batch` | 批次在跑时行一条条长出来,不另开进度条 |
| 并排看 | 点行:左边这次重发,右边它的源记录 | 都是 `GET /api/block?ref=`(重发的 `id` 与源记录的 `ref`);源记录取这次重发用的那一侧(`input`),体按 [2.6](2.6-detail-panel.md) §C 的体画 | 凭据类头遮住,没有「显示」 |
| Resend | 行上的按钮;`#/rules?resend=<ref>` 打开同一个表单 | §写 | 表单三项:Times(默认 1)· Rule(只列 `resend_ok` 为真、`script` 为假的规则,可不选)· Rebuild continuation(`resend-continuation` 时才出现)。`--body-file`、`--set-header`、`--as-sent` 只走 CLI |

没有重发时这张卡写「No replays yet」。

## 回放台的 Rules 标签

右侧栏的一个标签,这个单元启动时登记一次:`web/src/screens/replay/Sidebar.tsx : addSidebarTab({id: 'rules', label, Panel})`([1.2](1.2-shell-layout.md) §回放台 B 布局)。`Panel` 就是全局页的部件带上 `session`:

| 块 | 内容 | 来源 |
|---|---|---|
| Held | 这场会话的单元(§前置定义),按钮和全局页一样 | 同一份 held 读,按 `session_key` 筛 |
| Rules | 动过这场会话或在这场会话上没应用的规则,一行的样子和全局页一样 | `GET /api/interventions?session=<session_id>` 折出规则名,行取 `rules` 文档 |
| Replays | 源记录在这场会话里的重发 | `GET /api/replays?session=<session_id>` |
| 别处 | 「N held elsewhere ›」→ `#/rules`;N = 其余没结束的 held 行,包括不算任何一场会话的 | 同一份 held 读;N 为 0 时不画 |

New rule 只在全局页。三块都空时写「No rule has touched this session」和「All rules ›」;别处的行照样画。标签名上有这场会话的单元被扣着时带数(「Rules 2」)。

## 写

全部经 D26 的控制面:回环 + Host / Origin + 每用户口令,端点只调 CLI 同一批函数,MUST NOT 自己推导改动([4.4](4.4-server.md) §控制面)。端点形状归 4.4,回执与错误码归 [1.6](1.6-cli.md)。

| 控件 | 等于 | 路由 | 谁答 |
|---|---|---|---|
| Release | `held release <id>` | `POST /control/held/release {id, confirm?}` | 守护进程 |
| Release changed | `held release <id> --body-file <file>` | `PUT /control/held/body?id=<id>`,然后 `POST /control/held/release {id, changed:true, confirm?}` | 守护进程 |
| Drop | `held drop <id>` | `POST /control/held/drop {id, confirm?}` | 守护进程 |
| Turn all rules off | `rules off` | `POST /control/rules/off {confirm?}` | 守护进程 |
| 开关 · Enable · Remove | `rules enable` · `rules disable` · `rules rm` | `POST /control/rules {kind, name, confirm?}` | 查询工作进程 |
| Save | `rules add`,同名时 `--replace` | `POST /control/rules {kind:'add', rule, replace?, confirm?}` | 查询工作进程 |
| Test on captured calls | `rules test`,不写,没有计划这一步 | `POST /control/rules {kind:'test', rule, last}` | 查询工作进程 |
| Resend | `trocar resend <ref>` | `POST /control/resend {ref, times, rule?, rebuild?, confirm?}` | 确认后路由生成这批的 `batch`,起一个 `trocar resend … --batch <batch> --yes` 进程,发送方是它,不是守护进程([5.1](5.1-intervention.md) §重发);路由答 `{batch}`,结果读 `replays --batch` |
| Max rule delay | `rules max-delay <ms>` | 见 [1.11](1.11-settings.md) §规则 | 查询工作进程 |

- **先计划,确认后才改**:第一次请求不带 `confirm`,回 409 带计划;页面把计划逐行放进确认框(`web/src/ui/Confirm.tsx`),确认后带 `plan_id` 再发(`core/control.mjs : planConfirm()`)。计划写明这一下会发生什么:Release 写发给谁、改没改;Turn all rules off 写停几条规则、几个单元放行、几个按 `on_error: drop` 断开;Resend 写 `planned` 的次数、估算的 token 和花费、走哪一跳,`capture_off` 时写「A replay record is written even with capture off」。项的形状见 [1.6](1.6-cli.md) C.2「`planned`」。计划过期时回 409 带新计划,确认框换成新计划,什么都没改。
- **初始焦点**:Drop、Remove、Turn all rules off 在「Cancel」上;其余在确认按钮上。取消不发确认请求。
- **改后的体**:放行的路由不收路径,JSON 上限是 64 KiB([4.4](4.4-server.md) §控制面),而浏览器手里没有文件。所以 `PUT /control/held/body` 由守护进程把请求体流式写进 `~/.trocar/collector/held/<id>.body`(0600,最多一个单元的上限 64 MiB,入这个 harness 的账),之后走 `--body-file` 同一条路;单元结束就删。
- **含 `script` 的规则看板不接受**,否则网页的写权限就升到了运行任意程序。守卫在路由上,不在按钮上:`add`、`test` 里的规则带 `script`,回 `rule-invalid`,说「Rules with a script can only be added with trocar rules add」;`enable` 和 `resend` 的 `rule` 点名一条带 `script` 的规则同样拒绝。这类规则的行上开着时只有关的方向,关着或要 Enable 时控件换成「Use trocar rules enable <name>」,命令在技术细节。Disable 和 Remove 照常,它们不跑代码。
- **控制面没挂**(守护进程以 root 跑,`GET /control/status` 回 `root:true`):不画开关、按钮、编辑框,也不画灰掉的控件;这几块照读,命令在技术细节。

| 回答 | 就地写什么 | 技术细节 |
|---|---|---|
| 200 | 回执:动词和 `outcome`,例「Released」「Dropped」「swap-alpha is on」 | 回执原文 |
| 200,`rules off` 的 `file.written` 为假 | 「Rules are stopped and stay stopped. The file didn't change.」 | 回执原文 |
| 同上,`stats.written` 也为假 | 「Rules are stopped, but nothing on disk says so: they come back if the daemon restarts.」 | 回执原文 |
| 409 | 确认框换成新计划 | 服务端原文 |
| 403 | [1.5](1.5-states-aesthetics.md) K-30 | — |
| 400 / 退出码类错误 | 服务端的话(`rule-invalid` · `rule-unknown` · `engine-unsupported` · `resend-*`) | 码 |
| `held-gone` · `held-unknown` | 「It's no longer held」+ 结果;这一行随下一次读变灰或离开 | 码 |

| 读 | 来源 | 周期 |
|---|---|---|
| 侧栏的数、Held 块 | `GET /control/held`(控制路由,最多 256 行,不带体) | 全站一份 TanStack Query,页面可见时每 2 s(`INTERVAL.held`),窗口回到焦点立刻一次,读失败按 `backoffMs` 退避 |

- Held 不读 `query held`:那份文档折自审计流,要过查询工作进程,而这里要的是工作进程忙着时也答得出。`query held` 留给 CLI 和守护进程不在时。

## 保真边界(不变式 4)

1. **看板上的计数最多落后 5 秒**:`changes`、`not_applied` 来自 `collector/rules-stats.json`,表注写「截至 <`stats_at`>」;守护进程崩溃时最多丢 5 秒,逐次的事实在信封里(§Not applied 读这个)。两边对不上时以逐次的为准。
2. **Not applied 的列表截至 `as_of`**:读段索引,写「截至」;还没进索引的不在里面。
3. **会话归属只看头**:一个单元不在标签里,不等于它和这场会话无关;所以标签总写「N held elsewhere」,不写「什么也没扣」。
4. **`summary` 是生成的**:一句人话不是规则本身;规则的 JSON 在展开里,以它为准。
5. **Test 不是实发**:`script` 不在看板上跑;命中数只在这些记录上算数,`log` 和截断的记录算「Can't test」,不算没命中。
6. **扣着的字节只在守护进程内存里**:守护进程崩了就没了,下次启动补一条 `held-lost`;列表这时不写它,事实在 `query held` 与审计流。
7. **重发的记录标明**:`rebuilt`、`edited`、「Sent by trocar」就地写;发出的字节是 `replays/` 存的完整字节。
8. **不声称已隔离**(D26③):页面不写「只有你能改」之类的话。

## Edge cases

- **同一个单元被两个写者同时动**(人在看板上,agent 在 CLI):后到的回 `held-gone`,就地写结果,不算失败。
- **确认框开着时单元到点**:确认回 `held-gone`。计划不带走表的数(C.2),确认框里的「N s left」取自打开时的 held 行,不走表。
- **一次有 256 行**:列表上限;再来的不扣,写 `gate-full`,所以列表不用翻页。
- **`rule=` 指的规则不在列表里**(被删了,或改了名:`name` 是 id,改名 = 删了再加):不展开任何行,不提示。标记上的旧名字照原样。
- **`resend=` 的 `ref` 读不到**:表单不开,就地写读不到的原因(K-29)。
- **很窄的窗口**:四块的表在框内横向滚动,页面本身不横向滚动([1.2](1.2-shell-layout.md) §窄屏);< 1200 px 标签在底部一行里。

## Risk / 回滚

- 一个看板 XSS 能放行、断开、改规则。这和它能开关采集是同一道门(D26);它升不到运行任意程序,这就是 `script` 不进看板的原因。
- 读取侧的改动都在新目录 `web/src/screens/rules/`;出问题可以整个摘掉侧栏项与标签,规则照样走 CLI,不碰转发路径。
- 侧栏每 2 秒读一次 held:这是守护进程内存里最多 256 行的列表,不唤工作进程,不碰磁盘。
