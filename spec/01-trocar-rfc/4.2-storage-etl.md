# trocar · RFC 4.2 — 存储(原始层按段存 + 封存 + 段索引)

> **服务意图(A2)**:同时服务 ①(逐字回放)与 ②(cache 叠加)——它定义**采集到的字节落在哪、怎么被压实、怎么被定位回去**。
> **受众**:人(核对派生层不覆盖源、崩溃不丢数)+ agent(据此实现写路径、封存器与段索引)。
> **前置**:源信封(怎么拿到 bytes、NDJSON 长什么样)= [4.1](4.1-capture-sources.md);记录→归一化块的纯函数 = [3.1](3.1-adapter-contract.md);读取侧的模型 = [3.2](3.2-normalized-model.md);cache 真相规则 = [3.3](3.3-cache-model.md);身份/血缘判定 = [3.4](3.4-session-identity.md);谁读这些文件 = [3.5](3.5-query-layer.md)。
> **决策**:D27(家目录)· D34(体积预算)· D35(封存格式)· D59(读数据只有 `trocar query`,派生层只剩 `~/.trocar/index/` 里可重建的投影)· D60(按大小切段、守护进程自动封存)· D69(查询工作进程写的每会话上下文投影也住在 `~/.trocar/index/` 下)。

## Goal
定义原始层:守护进程把信封追加到**段**文件、段关闭后被**无损封存**、读取侧靠**段索引**随机定位某条记录与某块字节。原始 NDJSON 是唯一源真相;**派生层只有 `~/.trocar/index/` 里可删可重建的投影**——段索引、读取侧为 `overview` 写的用量旁注,与查询工作进程写的每会话上下文投影(D69,[4.3](4.3-parse-index-cache.md) §上下文投影)(不变式 2([0.0](0.0-overview.md) §核心不变式),**必拒**违反)。

## 前置定义(Definitions)
- **段(segment)**:一个 append-only 的 NDJSON 文件 `~/.trocar/raw/<段>.ndjson`(0600),一行一次上游往返(HTTP 请求,或 WebSocket 上的一次逻辑调用,D37)。段名 = 开段时刻的 UTC `YYYYMMDDTHHMMSSZ`,撞名加 `-2`、`-3`。**分流归属(承 D20)**:写路径是纯 tee,只按时间切段,**不按 session 预分流、不取 session 键**;session 归组与血缘判定都在读取侧([3.4](3.4-session-identity.md))。
- **封存件**:`~/.trocar/raw/<段>.sealed`,一个段一个,格式见 §封存格式。一个段的长期副本只有一份:明文,或封存件。
- **记录 id** = `<段>:<行号>`(行号从 1 起,opaque 行也计),封存前后不变。这是唯一的 ref 形状。
- **段索引**:`~/.trocar/index/` 里每段一个文件,**由守护进程随写维护**(D62),读取侧在它缺失时自己建。它只是加速器,**可删、丢了就重建**,MUST NOT 成为新的真相源。
- **用量旁注**:`~/.trocar/index/<段>.usage.json`,每段至多一个,存该段每次模型调用的用量事实;**由读取侧写**(守护进程不解体,D20),同样可删、丢了就重建,见 §用量旁注。
- **标题表**:`~/.trocar/index/titles.json`,一份,每场会话一条标题;读取侧写,可删可重建,见 §标题表。
- **上下文投影**:`~/.trocar/index/ctx/<k>/`(`k` = sha256(会话 id) 的前 32 位十六进制),每会话一个目录,存该会话每条成员记录抽取一次的块定义与调用行(`extract.*`)、归约的折叠日志(`fold.*`)与看板读的答案文件(head、包、尾);**只由查询工作进程写**,可删、丢了就在下次打开该会话时重建,答案逐字节不变;格式、有效性与回收见 [4.3](4.3-parse-index-cache.md) §上下文投影(D69)。
- **块字节引用 `text_ref`** = `<记录 id>` + 块在该记录某个字段里的字节区间,见 §回源指针。

## 写路径(段的生命周期)
- 守护进程**启动时总是开新段**,不续写旧段(前一次运行的段状态不可知)。
- 每条信封追加一行;**追加后段 ≥ 128 MB 就关闭**并开下一段。按大小切,不按日期——一天的量差几个数量级(D60)。
- 守护进程停下时关闭当前段。崩溃留下的半行(没有结尾换行)**原样保留**,封存也逐字节保留;索引项标「无换行」。
- 守护进程把当前段名写进自己的锁文件 `~/.trocar/collector/lock` 的 `segment` 字段,**次序 MUST**:新段在它的文件创建之前写进锁;段关闭后,锁先改成不再写着它(`null`,或下一段的名字),**然后**才把它交给封存队列——队列立刻 fork 封存 worker,worker 读锁,锁要是还写着刚关的段,这次封存就会被拒(不靠计时器的下一拍)。**「关闭」的判据**:`~/.trocar/raw/` 里的一个段,只要它不是某个活着的守护进程的当前段(锁里的 pid 与该进程启动时间都对得上才算活着)、又还没有封存件,它就是关闭的。**没有关闭标记文件**:标记文件会在崩溃后留下谎言,而锁 + 封存件已经足够。
- `flows/<日期>.ndjson`、`audit/`、`replays/` 不是记录流,照旧按日期分文件。

## 自动封存(D35 · D60②)
- 关闭的段进封存队列;守护进程启动时先扫 `~/.trocar/raw/`,把所有关闭的明文段也放进去(上次运行留下的)。
- **一次一个**,在 `child_process.fork` 出来的封存 worker 里做,**MUST NOT 阻塞守护进程的事件循环**(证据:守护进程里只有 fork,`sealSegment()` 只在 worker 里调;见 §验收 4);worker 的父进程一断开它就退出,不留孤儿。
- **只有守护进程封存,所以没有封存锁**:一个用户只有一个守护进程(它的单实例锁),它只有一条队列、一次只封一个段,没有第二个封存者;也没有手动封存命令(`trocar raw` 只印记录)。封存器仍然拒绝锁里写着的那个段(纵深防御,不变式 2)。
- **封存流程(MUST)**:同目录建临时文件(open 时即 0600)→ 写入并 fsync → 逐条解码**全部**记录与原行比 sha256、再按行号重拼整段比长度与整文件 sha256 → rename 成 `<段>.sealed` → fsync 目录 → **才**删明文 → fsync 目录。任何时刻崩溃都只留下明文,或两者并存;校验不符就保留明文并报告。
- **崩溃残留**:明文与 `<段>.sealed` 并存 = 上次封存在 rename 之后、删明文之前断了。**明文为准**(读者只读明文),封存器照常重封,新封存件覆盖旧的;启动扫描先删掉 `raw/` 里残留的临时文件。
- **失败不静默(D38)**:明文留着,`collector/flows/` 一条 `failure`(`where:'raw'`、`code:'seal-failed'` + 一句原因)+ `~/.trocar/raw/journal.jsonl` 一行;**同一次运行里不再重试它**,下次守护进程启动的扫描**重试一次**,不循环重试;`trocar status` 报出条数。被拒(锁里写着这个段)也是一次失败、照此办理,运行中不因锁后来变了再试(依据:本条「不循环重试」与 D38,且上面关段的次序已让刚关的段不会被锁挡住——还被拒只可能是那一刻锁写不进去,守护进程为此另记一条失败,运行中再试只会再撞同一把写不进去的锁)。
- **封存不能打断采集**:守护进程停下时**不把最后一个段交给队列**(下次启动的扫描封它),被这次停止切断的 worker **不是封存失败,什么也不记**(它有自己的退出码);崩溃后的启动把锁里的 `segment` 先清成 null 再扫,所以上次运行的最后一个段不会被旧锁名挡住,只有本次运行自己正在写的段(进程内已知)被排除。
- **不向后兼容**:这一版只读 `~/.trocar/raw/` 里的段。更早版本写的采集文件(`~/.trocar/collector/capture-<日期>.ndjson`)与更旧的位置(`~/.trocar/sessions/`、旧根 `~/.atrace`)**不读、不碰、不搬**;**没有任何向后兼容代码**,也没有转换脚本(用户点名要才做)。

## 封存格式(D35)
两个版本:**版本 2 是现行写格式**,封存器只写它;**版本 1 只读,读者 MUST 永远能读**。(依据:D71⑤(会话总占用 ≤ 1.5x 硬线)+ D72(重封成新的封存格式)+ 实测:v1 在活语料上是原始的 9.2–10 %,LLM 记录只有 31.7 % 找到了前驱。)
- **记录编码(版本 2)**:一条记录 = **同一封存文件**里块帧上若干字节区间 (帧号, 偏移, 长度) 按序拼接。块帧把本文件的每个唯一块存一份(块所在帧比可引用窗口旧时再存一份,见下文编码器);解码是纯字节拼接,不解析、不重新序列化任何东西,与 provider 无关。
- **拼接表(MUST)**:一条记录的拼接表是一串 LEB128 varint,每三个一组描述一个区间:`zigzag(帧号 − 上一帧号)`、`zigzag(偏移 − 上一区间末)`、`长度`(≥ 1);每条记录开头 `上一帧号 = 上一区间末 = 0`,每组之后更新为 `(帧号, 偏移 + 长度)`;`zigzag(x) = x ≥ 0 ? 2x : −2x − 1`。读者 MUST 检查:区间所在帧存在且是块帧、`偏移 + 长度 ≤ 该帧解码长`、拼出的总长 = 记录表里的行长。空行的拼接表为空。
- **编码器启发(SHOULD,不属格式;只影响压缩率,永远不影响正确性)**:切点(`src/raw/chunk.mjs` : `cutPoints()`,行字节的纯函数)——≤ 8 KB 的行整行一块;JSON 容器 > 8 KB 时在每个成员 / 元素起点切、递归;内容是 JSON 的字符串下钻一层;长字符串里用 gear CDC(最小 512 B、平均 2 KB、最大 16 KB);认不出的行(非 JSON、截断、非 UTF-8)整行 CDC;不认任何字段名、provider 或 harness(切到 1 KB 时小记录和遥测事件碎成约 30 B 的成员,拼接项与丢掉的 brotli 上下文比去重省下的多)。块按 sha256 去重。按流分组(信封的 host + 路径):一组的记录先走共用缓冲区(按到达顺序),这组有一整帧(约 4 MiB)的记录走过共用缓冲区之后才有自己的缓冲区,自己的缓冲区最多 8 个同时开着(每条换一个路径的流量因此不会被冲成一条一帧的小帧);一个块只从帧号最新的 12 帧(开着或已落盘,算上本条自己的缓冲区要取的新帧号)里引用,开着的缓冲区落出这 12 帧就先冲出;一条记录最多碰 9 帧(自己的缓冲区、拼接帧、它取字节最多的另 7 帧),别处的可引用块和连续不足 256 B 的可引用块在本缓冲区里再存一份(brotli 在上下文里压它们比拼接项便宜)。以上取值来自真段测量。
- **记录编码(版本 1,只读)**:关键帧(行字节本身),或增量 = (指向同一封存件里更早一条记录的回指, ops),ops 只有 `COPY(offset,len)` / `INSERT(字面字节)`;从一条记录沿回指到关键帧 MUST ≤ 16 步,读者在打开时检查。
- **分帧**:约 4 MiB(解码后)的独立帧,各自 brotli(quality 9、lgwin 24)压缩,每帧可单独解码。版本 2 有两种帧:块帧(kind 0)与拼接帧(kind 1)。一条记录的拼接表 MUST NOT 跨帧;一条记录的新块从不在记录中途被切到两帧(记录的新块写进它所在的缓冲区,缓冲区只在一条记录写完之后、解码长 ≥ 帧大小时冲出;所以比帧大的记录整条落在同一个块帧里,这帧大于约 4 MiB,它的拼接表照样只在一个拼接帧里);版本 1 的记录 MUST NOT 跨帧。用 brotli:不是每个 `engines` 允许的 Node 的 `node:zlib` 都有 zstd。
- **文件布局**:头(magic、格式版本)· 帧 · 索引尾 · 定长尾标(索引尾的偏移与长度、magic)。索引尾含帧表(每帧 `[偏移, 压缩长, 解码长, kind]`)、记录表(两个版本同样 12 列:id、流、帧号、帧内偏移、编码长、行长、类型、回指、行的 sha256、有无换行、来源段、行号;版本 2 的帧号 / 偏移 / 编码长指向拼接帧里的拼接表,类型 2 = 拼接,回指恒为 −1)、来源段表(段名 + 封存时测得的整文件 sha256 与长度,原段因此能逐字节还原),和一个校验和(头 + 各表的 sha256)。版本 2 的帧号在缓冲区开启时分配,帧在文件里的顺序可以不同于帧号;读者 MUST 检查全部帧按偏移排好后恰好铺满 [头末, 索引尾偏移),不重叠、无空隙。索引尾实测约为原始的 0.2 %。
- **版本分派**:读者按头里的格式版本分派到版本 1 或版本 2 的解码;认不出的版本 MUST 带原因拒绝,MUST NOT 猜着解。版本 2 的记录类型 2 让只认版本 1 的读者即使不查版本,也在打开时拒绝(版本 1 只有类型 0 / 1),从不交出错字节。
- **读**:记录 id → 查记录表 → 解码所需帧(版本 1:至多沿回指 16 步;版本 2:记录 → 拼接帧 → 区间 → 块帧)→ 重建行 → **交给调用方之前校验 sha256** → 切字节。同一个重建出的行实例只校验一次;只为重建后继而解出的前驱行不单独校验(它坏了,后继的校验就不过;它自己被要时照样校验)。解码后的帧进**按字节封顶**的有界缓存(读者默认 64 MiB,顺序读另有一份同样封顶的窗口):版本 2 的一条记录引用的块帧落在连续 12 个帧号里(算上它自己的缓冲区要取的新帧号),所以按记录次序读时同时要用的至多是 12 个块帧 + 1 个拼接帧(写者保证,与组数无关);顺序读的窗口在每帧最后一次被用到之后放掉它,超过封顶时先放掉持有最久的帧、再被引用时重解,所以任何合法文件(别的编码器写的、后面的记录回指早帧的)都在有界内存里读完;按记录次序读完一个文件,每帧约解一次(`test/raw/sealed-v2.test.mjs` 断言 ≤ 1.1 倍帧数);查询层用按字节封顶的共享缓存([3.5](3.5-query-layer.md) §访问模式「冷路径的派生缓存不能改变答案」)。(依据:不变式 2——交出的字节与 sha256 相符,一字不弱;D71②;真数据实测:首折里 raw 校验读了 3,233 MB,多为只作前驱的别的会话的行。)读者跳过或认不出的文件 MUST 报告,MUST NOT 折叠成空。
- **并存期**:明文与封存件并存时(崩溃后),读者只用其一并保持一致:封存件声明的来源段与现存明文的字节一致(前 `length` 字节的 sha256 相同)就用封存件;否则读明文并报告。

## 段索引(D59)
- 每段一个索引文件,**由守护进程随写维护**(D62):它是段的唯一写者,所以它是唯一能「随写就索引」的一方。记每行的字节偏移与长度,外加查询要过滤的少量取自信封的键(时间、harness、host、`traffic_class`、`is_llm_call`、是不是 WebSocket 逻辑调用(`transport`)、session 键、调用 id)。索引不存记录全文,看全文一律回源。条目另存请求与响应两个方向的线上字节 `sent_bytes` / `received_bytes`,取自信封的 `body_wire_bytes.req` / `.resp`;不是有限数的记为 `null`(没记下来),**不写 0**(依据:[1.6](1.6-cli.md) C.5 `traffic` 要分开的发出与收回,[3.5](3.5-query-layer.md) §访问模式要求 `traffic` 只读段索引——加总后的一个数拆不开;不变式 4:未知不写 0)。
- **格式 = 只追加的 NDJSON**:一段一个文件,一行一件事——一条索引条目、一条 `{"p":…}` 问题,或一行 `{"m":…,"v":<INDEX_V>}` mark(「到此为止这段已被索引到 `m.end`」)。一次补索引**只追加**自己的新条目、问题和一行 mark;读者取到**最后一行完整 mark** 为止,后面的残批(写到一半的批)忽略。这是 D62 的硬条件:保持新鲜的代价与**新记录**成正比,而不与整段的记录数成正比(整体重写一份文档的老做法,每段要写 ≈ e·N²/2 字节索引,稀疏到来时写放大能到两位数)。mark 里的身份指纹存**摘要**而不是那两段 4 KB 字节,否则每行 mark 自己就有 11 KB。
- **谁维护它(D62)**:正在追写的那个段由守护进程自己按追加的字节增量补(`src/collector/index-keeper.mjs`:写路径上只记一个段名,按写入事件批量、防抖、分块做;不轮询,空转时不干活;每遍去抖后的补完把新建索引行里是模型调用的那些(`is_llm` 且不是只记日志的)的记录 id 一次 kick 给查询服务(哪条在哪场会话由工作进程照 `sessionGroups` 说),[3.5](3.5-query-layer.md) §谁执行它,id 取自它本来就算出的索引条目,守护进程不解析 body、不算查询);段关闭时先补最后一次(这一遍的新模型调用同样 kick)再交接,封存完成后由**封存子进程**按封存件重建那段的索引(字节改按行号寻址,不再是明文偏移)——整段解析从不在守护进程的事件循环上。一份索引文件同一时刻只有一个写者。
- **谁写哪一笔**：① **明文段的索引只由守护进程的 keeper 写，且只追加**；两个例外：追加前把残批截回最后一行 mark，以及身份规则判定重建时整体重写。keeper 只读索引文件尾部的最后一行 mark（不解析条目），所以它每趟的 CPU 也不随 N 长。**关段时的交接有截止（D62）**：封存队列等 keeper 补完，等超了就把该段的索引**取走**（记一条 `index-failed`），从那一刻起 keeper 对它再不写一个字节；且 keeper 的追加 MUST 走它自己打开的 fd（ftruncate / 按偏移写），于是一笔和封存器的 rename 相撞的写落在**已被 unlink 的旧 inode** 上，永远不动新文件。② **封存段的索引整体写**（临时文件 + rename）：封存子进程写，发现它缺失或过期的读者也写——两者写的内容相同，竞争无害。③ **读者从不写明文段的索引**：它用索引覆盖到的那部分，在内存里扫没被覆盖的尾巴，这尾巴超过一块时在文档的 `errors` 里报一条 `index-cold`,带 `level:'note'`:这次读慢了,但什么都没缺(仍然不静默,D38);它只说这一次读,从不存进索引文件。
- **失效与增量**:段的身份 = (大小, mtime, ctime) 加 `fp`(mark 覆盖到的字节首尾各 4 KB 的摘要;明文段覆盖到 `end`,封存件覆盖整个文件)。三者都没变 → 照用;大小与 mtime 没变、只有 ctime 变了(克隆、备份恢复、迁移助理把同样的字节换了 inode 与 ctime,或只改了权限)→ 核对 `fp`,相同即照用,不重建也不重写(`fp` 只说首尾各 4 KB 没变:大小、mtime 与首尾都没变而中间的字节变了——坏的恢复、位翻转——认不出,照用旧索引);明文段长了且 `fp` 相同 → **按已索引到的偏移增量补**,只追加不重算;其余(改写、截短、大小或 mtime 变了、`fp` 不同、mark 里没有 `fp`)→ 整段重建,封存件一次建完。依据:不变式 2(派生层可删可重建,不因文件身份挪动就重建)+ D71③(离开再回来不重读)+ 实测(克隆的冷 home 重开 41–46 s,原地 3.1 s)。增量补可以分块做(`segmentIndex({maxBytes})` 停在行边界、报 `done:false`),分块补出来的索引与一次建完的**记录逐字段相同**(文件只多出每块一行 mark)。读者同样只读它上次读到的最后一行完整 mark 之后的字节(索引文件还是那一个、那行 mark 的字节没变时),否则整读;读出的条目与整读相同。
- 索引坏了、删了、版本不符(v5 及更早一律算过期) → 读取侧自己重建,**MUST NOT** 因此拒绝回答查询;这是唯一的退路,且**不静默**:自己建的量超过一块时在文档的 `errors` 里留一条 `index-cold`,带 `level:'note'`(这次读慢了,什么都没缺;D38)。`trocar query segments` 印每段的时间范围、大小、封存与否。

## 用量旁注(读取侧写的投影)
- **为什么在这**:`overview.usage` 要每次调用的用量,它在记录体里;守护进程的写路径不解 provider 的体(D20 · [0.1](0.1-engineering-rules.md) §5),所以由读取侧在答完查询之后写([3.5](3.5-query-layer.md) §访问模式)。它不是新的真相源:删掉只让 `overview` 退回字节预算内的部分覆盖,补齐后逐字段相同(不变式 2)。守护进程与段索引都不碰它。
- **格式 = 只追加的 NDJSON(USAGE_V 3;别的版本按身份规则作废、整体重建)**,`~/.trocar/index/<段>.usage.json`(0600),一行一件事:
  - **一次调用** `{"line":<行号>,"lane":<泳道>,"model":<string|null>,"failed":<bool>,"cache_known":<bool>,"usage":[input, output, cache_read, cache_write]|null}`:只为段索引里是模型调用(`is_llm` 且不是只记日志)、又被该会话的抽取当成一次调用的行写;值来自该会话自己的抽取与归约(`src/view/extract.mjs` + `src/view/reduce.mjs`),在补建那一块里对该会话的记录在内存里跑——`lane` = 该调用所在车道头的 `kind`,`model` = 请求里的模型,`failed` = [3.5](3.5-query-layer.md) §访问模式的调用行规则(失败时 `usage` 为 `null`、不计价),`cache_known` = 这个厂商的缓存数含义已知,`usage` = [3.2](3.2-normalized-model.md) 的规范映射(按线格式与厂商,`input` 是未命中缓存的输入;`cache_write` 没报为 `null`,**不写 0**);没失败而 `usage` 为 `null` = 回复里没有用量。被认作不是调用的行(dissector 不收)不写,只算进覆盖。
  - **一条问题** `{"p":{"where":<记录 id>,"reason":…}}`:这条记录的**内容**解不开;之后每次用到这份旁注都再报一次(D38)。**读失败从不被记住**([3.5](3.5-query-layer.md) §访问模式 验收 #8):某次补建里有记录读不出来(EIO、打开不了、封存帧解不出),这次就不写这段的旁注——下次 `warm` 的 `overview` 在字节预算内现算、把原因列进 `errors`,工作进程再补一次;补建自己写不出旁注(目录或文件不可写)也不静默:记下来,进下一次 `overview` 的 `errors` 一次(D38)。
  - **一行 mark** `{"m":…,"v":3}` = 「这段到第 `m.lines` 行为止的调用都在上面了」。身份与段索引同一条规则(§失效与增量):明文段 `{size, mtimeMs, ctimeMs, end, lines, fp}`(`end` = 第 `lines` 行之后的字节偏移,`fp` = `end` 前首尾各 4 KB 的摘要),封存段 `{size, mtimeMs, ctimeMs, end, fp, sealed:true}`(覆盖整段:`end` = 文件大小,`fp` = 整个文件首尾各 4 KB 的摘要)。复用 / 续 / 作废照段索引判;读者取到最后一行完整 mark 为止,后面的残批忽略。
- **谁写哪一笔**:① **只在查询工作进程里、答案发出之后写**(D63 的 `warm`);一次性的 CLI 从不写,窗内还没有旁注的调用它只在字节预算内于内存里现算。② **封存段的旁注整体写**(临时文件 + rename):内容只取决于封存件,两个写者写的相同,竞争无害。③ **明文段(正在写的,或已关闭还没封存的)的旁注只由工作进程续写**:按它自己打开的 fd 写(先截回最后一行完整 mark,再按偏移写),身份规则判作废时整体重写(临时文件 + rename);没有两个按路径追加的写者。段封存后旧旁注按身份规则作废,封存段的旁注整体重建。④ **只为新追加的模型调用写**:一次续写 = 新行里的调用 + 问题 + 一行 mark,没有新的模型调用就不写;补建分块做(每块约 4 MiB 存下的字节),块与块之间让出事件循环,一次补建不挡住工作进程的其他查询;没有查询、也没有新采到的模型调用时什么都不跑(没有不经查询或 kick 就跑的定时器)。
- **资源**:旁注计入 D62④ 的写放大与每条记录写出的索引字节([1.6](1.6-cli.md) §3.1 的两条线)。

## 标题表(读取侧写的投影)
一个文件 `~/.trocar/index/titles.json`(0600),整份 JSON:`{"v":<TITLE_V>,"titles":{"<会话 id>":{"t":<string|null>,"r":<rid|null>,"c":<读过的模型调用数>,"m":<成员数>}}}`,读法见 [3.5](3.5-query-layer.md) §访问模式。`t` = 标题(`null`:读过的调用里没有提问),`r` = 它来自的主对话调用(`t` 可以有值而 `r` 是 `null`:这场会话还没有主对话调用,`t` 是第一个子代理车道的 `task`,之后找到的主对话调用换掉它),`c` = 按步序读到第几条模型调用,`m` = 写这一条时会话的成员数。
- **失效**:`TITLE_V` 不符或文件读不出 = 空表,下一次 `sessions` 与下一个工作进程行表之后的那一遍重建(整份重建读每场会话最前面的几条调用,实测 32 场会话 980 ms,与 `INDEX_V`、`PROJ_V` 无关)。条目按新成员核对:成员数到 `m` 为止不看;之后的成员里有排在 `r` 之前(步序)的模型调用 → 条目作废,这场会话重算;`r` 是 `null` 时,这场会话的模型调用数到 `c*9/8` 才从第一条重折(`c ≤ 8` 时每条新调用都重折),直接读到 `c` 之后的下一档,所以标题至多落后 `c/8` 条调用([3.5](3.5-query-layer.md) §访问模式);`t` 是 `null` 而 `r` 有值 = 主对话调用找到了、它没有提问,不再往后读。一场会话的新成员只核对一次(工作进程记着核对到哪)。
- **谁写**:只有查询工作进程写,整份写临时文件再同目录 rename;表没变不写,决定标题的记录读不回时也不写(`title_source: 'unread'`,[3.5](3.5-query-layer.md) §访问模式)。一次性的 CLI 只读,表上没有的在内存里算(文档相同)。
- **为什么不进段索引**:段索引的行由 keeper 在转发 agent 流量的事件循环上写,不解 provider 的体(D20);而且标题只要每场会话的前几条调用,进行里要付每条记录的抽取(真实采集 21.3 GB,约 50 MB/s),`INDEX_V` 一次重建从实测 70 s 涨到约 8 分钟(D78)。

## 回源指针(`text_ref` · AC-1 的技术兑现)
- 形态:`<段>:<行号>::<start>-<end>`(默认是请求体 `req_body` 的字节区间),或带字段段 `<段>:<行号>::<field>::<start>-<end>`,`field ∈ resp.raw | resp.messages.<j> | req_extra_messages.<k>`。区间是该字段文本的 JS 字符串下标。
- **重建 = 定位记录(封存件经索引解码并校验 sha256)→ 取该字段 → `slice(start,end)`**。AC-1:每个块的字节与源逐字 diff = 0。
- **按块字段比,不比整包字节**:请求体三个顶层字段(tools/system/messages)的 JSON key 顺序是 SDK 细节;真相是 assembly order 下每块内容的字节。
- 字段值不是文本(`{b64}`、`{omitted_bytes}`、`{raw_chars}`)时回源报「无文本」,**MUST NOT 臆造字节**。
- 块内容的指纹 `content_hash` MUST 是全内容 sha-256 over 块的**逐字序列化字节**(采集所见,非 key 规范化;算法钉在 [3.1](3.1-adapter-contract.md),承 D19):它是 cache-break 比对的依据,前缀 hash 或 32-bit hash 会把不同的块并成一个。键序规范化只供 [3.3](3.3-cache-model.md) 的成因分类。

## 源文件上允许的动作(必拒不变式,承不变式 2([0.0](0.0-overview.md) §核心不变式))
只有三种:① 写路径追加;② 同设备 rename 整个文件或目录(D27③),记录字节不动;③ 封存器把一个关闭的段无损换成封存件(§自动封存的顺序)。截断、改写、搬进外部 chunk store、按 session 重组一律**必拒**。读路径(`trocar query` / `serve`)只读,唯一会写的是 `~/.trocar/index/`。

## 保真边界(承不变式 4([0.0](0.0-overview.md) §核心不变式),必拒隐瞒)
源 NDJSON 本身已有非逐字之处,读取侧 MUST 原样承接 `faithfulness` 标记:
- **工具定义逐字(D15)**:采集逐字存完整 tools schema;D15 之前的旧记录只有元数据,UI 每块标 `verbatim` / `metadata`。
- **请求头逐字**:含 `authorization` / `x-api-key` / `cookie`([4.1](4.1-capture-sources.md) §凭据处置);保护手段是文件 0600 + `trocar doctor`。
- **响应在采集侧重建**:SSE 已在采集点重建成 `resp.{usage,text,tool_calls}`,读取侧不复解。
- **截断 / opaque**(超长内容、Codex 加密 reasoning):标 `truncated` / `opaque`,UI 就地标注。
- **只记日志的类别**:`body_retention:'log'` 的调用没有体,标「只记日志」,MUST NOT 读成空体([4.6](4.6-process-collector.md) §类别与保存级别)。
- **非 LLM 调用(D40)**:请求体与 LLM 同等逐字。D40 之前的 `{raw_chars, verbatim:false}` 记录标「采于 D40 之前,只存了长度」。
- **磁盘总量跟随顶层链接**:home 的顶层文件夹(`raw/`、`collector/`、`index/`…)是指向别处目录的符号链接时(用户把它挪到了另一块盘),磁盘总量跟进去算,每个目录按 (dev, ino) 只算一次;跟不进去的链接(悬空、读不了)写进查询文档的 `errors`,不悄悄少算。更深层的链接按链接本身算。

## 验收(可跑 check · 明确测试要求)
1. **段与轮转**:写够 128 MB 后换段;两次启动写进不同的段;段名撞了加 `-2`;停下时当前段关闭。记录 id 与写入顺序一致(`test/collector/record-store.test.mjs`)。
2. **半行**:杀掉写者留下半行,之后的读与封存都逐字节保留它,索引标「无换行」。
3. **封存往返(D35)**:封存前后,每条记录的字节、顺序、记录 id 与每个 `text_ref` 解出的字节都相同;明文只在全部记录校验通过后才删;中途崩溃只留明文或两者并存。
4. **自动封存**:两个关闭的段依次被封,明文消失、每条记录的字节与记录 id 不变(`test/collector/seal-queue.test.mjs`);封存失败留 `failure` + journal 各一条、同一次运行不重试、重启后只重试一次(同文件);**不阻塞事件循环的证据**:默认路径真的 fork 一个子进程(`test/collector/seal-fork.test.mjs`:封存发生在 pid 不同于测试进程的子进程里,父进程断开时 worker 以自己的退出码退出,队列不记失败);两个守护进程入口(Linux 与 model OS)都接了封存(`test/collector/seal-wiring.test.mjs`);停下时最后一个段不交给队列,下次启动扫描封它;**运行中轮转关闭的段在同一次运行里被封、不被拒**:真的写入仓库切段、真的锁、真的 fork 出的 worker(`seal-queue.test.mjs`),且段交给队列的那一刻锁已不再写着它(`test/collector/record/segments.test.mjs`)。
5. **「关闭」的判据**:锁里写着的当前段被拒(`test/collector/seal-queue.test.mjs`);`~/.trocar/raw/` 里没有关闭标记文件;明文与封存件并存时读者用明文,封存器重封并覆盖旧封存件。
6. **不向后兼容**:盘上放一份旧版的 `collector/capture-<日期>.ndjson`,启动前后它一个字节没动、也没被搬进 `raw/`;源码里 grep 不到 `capture-` 这类旧路径的读取(`test/collector/seal-wiring.test.mjs`)。
7. **段索引可弃**:删掉 `~/.trocar/index/` 后每个查询的结果不变(只是慢,且这次读在 `errors` 里说清楚;`overview.usage` 的覆盖除外,见本条下半);正在写的段追加后,增量补索引的结果与整段重建逐字段相同。用量旁注同理:删掉 `index/<段>.usage.json` 后 `overview` 只退回字节预算内的部分覆盖,补齐后逐字段相同;明文段追加后续补出的调用行与整段重建的逐字段相同。
8. **索引不冷(D62)**：守护进程写过的记录，在任何查询跑之前就已在索引里（按索引文件的覆盖范围断言，不按计时）；封存完成后那段的索引来自封存件；守护进程停之后不再写索引。**一个写者**：交接截止后在飞的那趟不再写（`test/collector/index-keeper.test.mjs`），和 rename 相撞的那一笔落在旧 inode 上、新文件一个字节不动（`test/query/segment-index.test.mjs`）。
9. **源不可变**:`trocar query` 与看板跑前后,每个段文件的 inode、大小、mtime 不变;对源路径调用 rename / unlink / truncate 的只有 `src/raw/` 与写路径(测法 = stub `node:fs` 跑各命令,记下调用的路径)。
10. **版本 2 往返(性质测试)**:按轴生成的行——转义、非法 JSON、巨型字符串、深嵌套、非 UTF-8、空记录、共享长前缀、交错的流——封存后每条记录逐字节相同;切点严格递增、以 0 开头、以行长结尾(`test/raw/sealed-v2.test.mjs` · `test/raw/chunk.test.mjs`)。
11. **旧读者拒绝版本 2**:只认版本 1 的读者打开版本 2 文件时带原因拒绝,从不交出字节;认不出的版本号同样带原因拒绝(`test/raw/sealed-v2.test.mjs`)。
12. **版本 1 永远可读**:冻结的版本 1 夹具(`test/fixtures/sealed-v1/`)每条记录读出的字节与 sha256 相符(`test/raw/sealed-file.test.mjs`)。

## Edge cases
- **目录迁移**:同设备 rename(D27③)——段索引按段名与 (大小, mtime) 失效,迁移后重建,不丢记录。
- **空段**:开了没写过的段关闭时直接删,不留空壳,也不封存。
- **超大单行**:比帧还大的记录的新块整条写进它所在的缓冲区,记录写完才冲出,所以落在同一个块帧里(这帧大于约 4 MiB),拼接表在一个拼接帧里;读者只解这条记录要的帧,内存随最大的那一帧有界。
- **撞名**:同一秒内重启两次 → `-2`;`raw/` 里已有同名封存件时,新段用下一个后缀,两个写者永不互相覆盖。
- **半包 / error 记录**:`error:true` 的信封照样是一条记录,不当 200。

## Risk / 回滚
段索引是一次性可弃投影:逻辑错 → 删 `~/.trocar/index/` 重建,源零损失(不变式 2 的直接红利)。封存器出错 → 明文留着,`journal.jsonl` 写明原因,人可以把封存件删掉重来。

## OPEN
- 无。

## Extensions
- 封存帧改用 zstd(level 3、窗口 ≥ 2^22):等 `engines` 允许的每个 Node 的 `node:zlib` 都有 zstd 后换,实测更小也更快(D35)。
- 冷热分层:很老的封存件搬到别的卷(仍只有一份长期副本)。
- 索引加更多过滤键:只要它仍可从段重建,读取侧零改动。
