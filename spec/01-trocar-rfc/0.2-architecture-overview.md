## 0. 架构铁律

1. **单机、单用户、所有端口只绑 `127.0.0.1`**。D36 起同一台机器上每个系统用户各一套实例;`127.0.0.1` 不隔离这些用户,所以数据面与控制面都要每用户一份持久口令(D26③,[4.4](4.4-server.md) §服务形状)。
2. **四层单向**:采集 → 原始 NDJSON → 服务端分析 → 浏览器呈现。下游不回写上游;采集不知道 session;前端不解析 provider 字节。
3. **一条读路径**(D24 · D59 · D63):每个读是一个具名查询,直接读源 NDJSON 与可重建的段索引(`~/.trocar/index/`);`trocar query` 是它的命令行壳,看板是它的 HTTP 壳,两边同一个文档。这份查询代码**跑在守护进程的查询工作进程里**(温缓存、低优先级、按需 fork;D63),两个壳都先问它;没人应答时壳在自己进程里跑同一份代码,文档一字不差。
4. **看板读写各一条路**:读只走具名查询 `GET /api/<名字>`(D59);写只走控制面(与数据面同一个 Host / Origin 门和同一个每用户口令,D26①),调 CLI 同一批函数(D26②)。看板由守护进程托管(D66),`trocar install` 之后一直在。

   看板这一面由守护进程转给同一个工作进程,304 由守护进程按 stat 直接答)

两种引流的共同点:默认只有被识别为 agent 的进程的连接经过 trocar,其余连接的字节不经过它(D31④)——Linux 上内核只改写 agent 进程的连接,代理模式下只有被配置去用门的 agent 经过它。差别在认进程的时刻与办法:Linux 由引擎向能力助手查内核表;macOS / Windows 在门 accept 时刻按对端 4 元组向系统定点问出 pid(D47)。trocar 不动系统代理、不接管整机流量、不往任何 VPN / 代理软件里写东西。

## 2. 核心数据结构

| 结构 | 一句话 | 在哪 | 谁产 → 谁用 |
|---|---|---|---|
| 原始信封 | 一次上游交互一行 | `~/.trocar/raw/<段>.ndjson`(正在写或刚关闭的段)· 封存文件(D35 · D60)| 采集器 → 封存器 / query / serve |
| block | 上下文里的一块;唯一跨 provider 的统一单元(D25) | 内存 | dissector → 看板装配 / 查询 |
| 段索引 | 守护进程随写维护的投影,可从 NDJSON 重建(D59② · D62) | `~/.trocar/index/`(可删) | query → 看板 / 命令行 |
| 用量旁注 | 每段每次模型调用的用量事实(泳道、模型、失败、规范用量),`overview.usage` 读它;读取侧写,可从 NDJSON 重建([4.2](4.2-storage-etl.md) §用量旁注) | `~/.trocar/index/<段>.usage.json`(可删) | 查询工作进程答完查询后补建 → `overview` |
| cache 分叉记录 | 这一步从哪块开始和上一步不同、为什么 | `session` 查询的回放载荷 | 读取侧按相邻调用的 `content_hash` 算 → 看板 |
| 看板载荷 | 一个 session 的回放视图 | HTTP JSON | view → index.html |
| 采集健康载荷(D38) | 采集器的失败、当前条件、守护进程状态、已接管的代理与拓扑(adopted · topology) | HTTP JSON(`/api/status`,[1.6](1.6-cli.md) C.3),读自 `flows/` 等运行元数据 | `src/health/` → index.html · `trocar status` |

**2.1 原始信封**(`src/capture/envelope.mjs::buildEnvelope`,采集器的 `src/collector/core/record/envelope.mjs` 在其上追加字段)
- `ts` `method` `endpoint`;`req_headers` 逐字,含凭据,所以文件是 0600。
- `req_body`:存原始 UTF-8 **字符串**,不 parse(下游要按字节切块、算哈希);D40 起一切调用同一规则,不分 LLM;不是 UTF-8 的体 `req_body:null` + `req_body_b64`;压缩的体 `req_body_b64` + `req_content_encoding`,解得出时 `req_body` 另存解压后的文本,解不出时 `req_body:null`(LLM 调用的 `req_body` 因此不总是字符串)。操作者设为只记日志的类别 `req_body` 是 `{raw_chars, verbatim:false}`,另带 `body_retention:'log'`。D40 之前采的非 LLM 记录只有 `{raw_chars, verbatim:false}`。
- `resp`:`{status, headers, kind, …}`。`kind:'json'` 存解析后的 `body`(线上原文与重新序列化不等时另存 `raw`);`'sse'` 的 `raw` 是解压后的原文,另带按 Anthropic 形状的重建;`'text'` 存 `raw` 或 `raw_b64`;没有体是 `'empty'`;WebSocket 上的逻辑调用是 `'ws'`(服务端消息逐字,原始帧在 `ws_raw`);上游失败是 `'error'`,并带顶层 `error:true`,失败的一步不会从时间轴上消失。体不完整或没解码时就地标注(`req_truncated` / `req_partial` / `resp.truncated` / `resp.partial` / `*_encoding_error`),由读取侧在显示处标出。
- 观测元数据 `id` `ts_request` `ts_response_start` `ts_response_end` `duration_ms`;派生标签 `is_llm_call`(只认端点 `/v1/messages`、`…/responses`、`…/chat/completions`,另有 Gemini 的 `:generateContent`)、`capture`(Linux = `transparent`,代理模式 = `proxy`;更早的记录里还有 `reverse-proxy` / `mitm`)、`auth_mode`。
- D37 / D40 追加字段(都在 `req_body` 之后):`host` `traffic_class` `body_wire_bytes`;`proc:{pid, exe, agent}` `flow_id` `seq`;WebSocket 的 `transport` `ws_frames` `ws_ext` `ws_raw` `req_extra_messages` `partial` `partial_reasons` `ws_truncated`;`trocar_added`(trocar 往转给客户端的字节里加了东西时才有)。形状以 [4.6](4.6-process-collector.md) §记录 为准。
- 正在写的段只追加、不按 session 分文件(D20 · D60②);已关闭的段由守护进程封存成无损文件(D35,见 [4.2](4.2-storage-etl.md) §原始层封存);读取端永远兼容 v0 旧字段名 `request_headers / request / response`。

**2.2 block** — `{section, role, kind, content_hash, faithfulness, volatile, cache_control, resource_ref, text_ref}`
- `section` 按装配序 tools → system → messages;Codex 的 `instructions` 归 system,`input[]` 归 messages。
- `faithfulness` ∈ verbatim / opaque(只有签名或密文)/ summarized(compaction 摘要)/ metadata / omitted / truncated。非 verbatim 在 UI 上必须有标。
- `content_hash` = 块逐字字节的 SHA-256(D19),既是去重主键,也是 cache 分叉信号。
- `volatile` = 每次都变的块(CC 的 `x-anthropic-billing-header`),不算 cache break 的责任。

**2.3 归一化表**(DDL:`src/model/ddl.sql`)
`sessions`(会话与血缘)· `calls`(`class` = llm / control,`lane` = main / subagent / monitor / aux / probe;`wire_format` `vendor` `transport` `context_state` `observer_effect` `harness` 记这次调用的线格式、厂商、传输、上下文是否完整、采集引起的客户端行为变化与 harness)· `block_contents`(按 `content_hash` 去重)· `call_blocks`(每个 call 的有序块索引)· `usage`(`input_uncached / cache_read / cache_write / output / reasoning`;`cache_write` 为 NULL 表示该 provider 没有写缓存概念,不能填 0)· `resource_events` · `cache_events`。除 `call_blocks` 外每张表都有 `extra JSON`,收未映射的原生字段,永不丢。

**2.4 cache 分叉记录**
- `cause` ∈ append / volatile-nonce-only / compaction / tool-array-reorder / json-key-reorder / content-changed,认不出是 unknown(另有三种由 adapter 判的成因,见 [3.3](3.3-cache-model.md)),附 `attribution`(谁的锅)与 `fixHint`。
- 地面真相(拿 usage 对账):`read>0` 正常;`read=0, write>0` = TTL 重建;`read=0, write=0` 而前缀逐字相同 = provider 矛盾。

**2.5 看板载荷**(`/api/session`)
- `meta` + 若干 lane;每个 call 带中立 usage `{read, create, fresh, out}`、`comp`(9 段字节构成,每个 call 都带,时间轴才能画全)、`cacheBreak`、`prefixSha256`。
- `flat` 只有块的元数据和 `text_ref`,**不带正文**;展开时再经 `/api/block?ref=` 回源取。窗口外的 call `flat=[]` 并标 `paged_out`。
- 长 session 按 `cursor / limit` 分页;被截掉的部分在 `truncated` 里写明。

## 3. 关键管线

- **P1 采集**:agent 的连接到达引擎(Linux 由 eBPF 改写而来;代理模式从门进来)→ 引擎问出对端进程、按 harness 注册表判是不是 agent、核对它是否确认信任 trocar CA → 是:先与上游完成 TLS 再终结客户端 TLS,否则透传 → 两个方向转发的都是收到的原始字节,被动分帧器只读一份副本,调用结束时解压、必要时重建 SSE、`buildEnvelope`,追加一行到 `raw/<段>.ndjson`。透传的连接、失败与生命周期事件写 `flows/`;上游失败也写一条 `error:true` 信封。记录出错不影响转发。
- **P2 看板回放**(默认路径):看板经具名查询读采集目录(`~/.trocar/raw/` + `~/.trocar/` + 采集器目录 `~/.trocar/collector/` 顶层 + 旧根 `~/.atrace/trocar/`;封存文件同样读,D35)→ 按 session 分组 → `assembleSession` 经 dissector 注册表按线格式选 dissector → `analyze()` 切 lane / turn、抽资源 → 逐 call 算 cache 分叉、前缀 SHA-256、中立 usage、`comp` → `sessionView` 开窗 → JSON。认不出线格式的字节计数并标「未识别」,不套任何已知 harness 的身份。
- **P4 开与关**(D39 · D55 · D57 · [1.6](1.6-cli.md)):`trocar install` 在本机生成根、装成用户级根,给根够不到的形态放证书载体,并写独立撤销程序;`trocar on` 先查已安装,请守护进程开门(Linux 经能力助手挂 eBPF 链接)并读回,再写第 1 类代理入口、建开关文件,`trocar off` 撤掉这些、证书留着,`off` 后持有者仍经门、门只转发。`trocar uninstall` 只在全部 harness 已 `off`、也没有持有者时撤证书载体、根和根的密钥,再删 trocar 自己,否则拒绝并说出是哪些;每一步只撤自己写的部分,改用户文件前先存改前副本,macOS / Windows 的完整模型见 [4.11](4.11-collector-model.md),Linux 见 [4.6](4.6-process-collector.md)。

## 4. 进程与接入

| 进程 | 监听 / 通道 | 做什么 | 默认写到 |
|---|---|---|---|
| 采集守护进程(`trocar daemon`,自启单元拉起;每个系统用户一个) | 引擎只听回环:Linux = 本实例自己的一个端口(`127.0.0.1` 与 `::1`);macOS / Windows = 每个入口组一扇门(端口记在 `ingress.json`)+ 引擎自己的 ingress 端口。控制面:Linux = `$XDG_RUNTIME_DIR/trocar/collector.sock`(0600);macOS = 用户 `$TMPDIR` 下随机名 unix socket;Windows = 随机名命名管道;后两者的名字与 token 在 `control.json` | 认进程、确认信任、解密 / 透传、记录、开关、控制面;macOS / Windows 上另在 PAC 组的门端口应答 `GET /trocar.pac`,每次启动请根签一张 7 天的中间证书(D57)。另有**读**:控制面的 `GET /query` 按名字转给查询工作进程(D63),字节流着过去——转发 agent 流量的这个事件循环 **MUST NOT** 自己算查询 | `~/.trocar/collector/` |
| 查询工作进程(D63;守护进程按需 fork,低优先级) | 父进程的管道(自己不听任何端口) | 跑具名查询(`runQuery`)并把段索引行与最近打开过的会话缓在内存里;每次请求按文件重新核对、不答陈旧;只读(唯一会写的是 `~/.trocar/index/` 里可重建的段索引与用量旁注);闲置几分钟后退出 | — |
| 能力助手(仅 Linux) | 守护进程的子进程,经控制通道 | 持有 eBPF 的 bpf_link:装卸程序、改表、按请求查表;不碰任何连接字节;每台机器 `sudo` 装一次(D36) | — |
| 只读助手(仅 Windows) | 守护进程拉起的常驻 PowerShell | 只读:进程与 TCP 连接表的事实,进程的环境、当前目录与创建链(D57);根密钥的操作走一次性的 `custody.ps1`,不进常驻助手 | — |
| 签名助手(仅 macOS,`trocar-sign-helper`) | `install` 与守护进程按需调用,一次一个动词 | 在用户的图形登录会话里,用登录钥匙串里不能导出的根私钥签固定形状的中间证书;动词只有 `create` / `exists` / `issue` / `remove`(D57②) | — |
| `procenv`(仅 macOS) | 守护进程按需调用 | 只读:同用户进程的启动环境(上游第 3 步、证书变量) | — |
| `socktable`(仅 macOS) | 守护进程与 `status` / `doctor` 按需调用 | 只读:同用户进程的 TCP 套接字(门的「谁连的」、监听者) | — |
| 看板(守护进程托管,D66) | `127.0.0.1:9800`(端口记在 `ingress.json`) | 静态面、`GET /api/<名字>` 与 `POST /control/*`(D26);校验 Host / Origin 与每用户口令;`trocar board` 只印带口令的网址并打开浏览器 | — |
| `trocar on / off / status / uninstall / doctor / keep` 等 | 一次性命令 | 改状态的(`install` `on` `off` `uninstall` `keep` `daemon`)按用户运行、拒绝 root;`status` / `doctor` 读盘并问控制面 | 见 §5 |

- **Linux · 驱动模式**:agent 的配置里不出现 trocar。内核侧 eBPF 把认定为 agent 进程的新连接改写到引擎;fail-open 两层(助手死 → 内核摘钩;引擎死或卡住 → 内核看监听与心跳不再改写)。机制见 [4.6](4.6-process-collector.md)。
- **macOS / Windows · 代理模式**:没有特权钩子、没有内核代理。`on` 把每个 harness 的代理入口指向引擎的门:第 1 类写进它自己的配置,第 2 类建开关文件、由 `install` 放的钩子读(D57③);连接到门时引擎按对端套接字问出 pid,按形态判定,是 agent 才解密,其余只转发。引擎就是守护进程,死了由自启机制重拉(macOS = launchd `KeepAlive`;Windows = 监管父进程),期间门是关的,agent 的连接被拒后自己重试。设计见 [4.11](4.11-collector-model.md),操作系统一层见 [4.9](4.9-macos-collector.md)(macOS)、[4.8](4.8-win-collector.md)(Windows);门的核心跨 OS 共用([4.6](4.6-process-collector.md))。

- **信任**(D55 · D57):`install` 把每台机器自己生成的根装成用户级根(macOS 登录钥匙串的用户信任、Windows `CurrentUser\Root`,OS 的框即同意),`uninstall` 撤;根够不到的形态,证书交给它自己读的东西(配置键、安装目录包装、插件),选哪种由描述符定;登录环境不加任何变量。见 [4.11](4.11-collector-model.md) §1。Linux 按 harness 写信任入口,见 [4.6](4.6-process-collector.md) §身份与信任。
- **系统代理感知**:`src/netenv/` 只读 agent 自己的代理与 OS 系统代理(D49),结果给引擎算上游、给 `status` / `doctor` 画拓扑;不识别 VPN / 代理产品,trocar 不写进它们(D43)。见 [4.7](4.7-netenv.md)。

## 5. 状态归属(写者与撤销)

| 状态 | 写者 | 位置 | 撤销 / 重建 |
|---|---|---|---|
| 采集流(正在写的段) | 采集守护进程 | `~/.trocar/raw/<段>.ndjson`(0600) | 只追加,写着时永不改写;段満 128 MB 或守护进程停下时关闭,封存校验通过后删明文(D60) |
| 封存文件 | 封存器(`src/raw/`,D35) | 按分片的与源同目录;按 session 的在 `sessions/<sid>/`(D20 的 D35 修订) | 只做经校验的无损重编码,随时可逐字还原 |

## 6. 三层怎么做

### 6.1 采集(`src/collector/` · `src/off/` · `src/health/` · `src/netenv/` · `src/cli/`)
- **按 OS 与 harness 分目录**(详见 [4.6](4.6-process-collector.md) §结构):`core/` 平台无关(引擎、分帧、TLS、记录、信任入口、开关状态机、控制面、harness 注册表与进程跟踪器),`arch/<os>/` 平台相关(Linux:eBPF 程序与能力助手;macOS:`lsof` / `ps` / `scutil` 的定点问询;Windows:只读 PowerShell 助手),`harness/` 每个 harness 一个描述符,是数据:进程名、已知 host,macOS / Windows 的 `proxyMode`(形态、代理入口、证书载体、信任来源;[4.11](4.11-collector-model.md) §2);插件模板在 `harness/templates/`。核心不出现 `process.platform` 分支,也不出现任何 harness 名(`test/collector/layering.test.mjs`)。`daemon.mjs` 是唯一把三者接线的地方。
- **撤销是另一块**:`src/off/` 只依赖 `node:*` 与自己,所以 `trocar off` 在 trocar 自己坏了时也能用(0.1 §2)。`src/health/` 读盘出采集健康;`src/netenv/` 只读感知代理设置(D49)。
- **共用件**:信封构造、请求体规则、保存级别、`redact`、`sse-reconstruct` 在 `src/capture/`,被采集器引用,同一份实现。
- 透明契约:客户端收到的字节先于记录;记录发生在副本上;记录出错不影响被测程序。
- 自检:`trocar doctor`(是否在抓、抓得对不对、凭据文件权限、全机 TLS 是否完好、`trocar-off` 副本是否可用)。
- 详见 [4.1](4.1-capture-sources.md)、[4.5](4.5-distribution.md)、[1.6](1.6-cli.md)。

### 6.2 后端分析(`src/dissect` `src/view` · `src/cache` `src/identity` `src/query` · `src/server.mjs`)
- **dissector**(`dissect/cc.mjs`、`dissect/openai.mjs`、`dissect/openai-ws.mjs`,经 `dissect/registry.mjs` 按线格式分派):把一种线格式的原始请求拆成 block,看板与查询共用(D25)。读取侧的 harness 表(session 键、请求类别、观测者效应)在 `dissect/harnesses.mjs`。线格式覆盖现状见 `ledger`。
- **看板装配**(`view/`):`analyze.mjs` 切 lane / turn、抽资源、算 cache 分叉与地面真相;`assemble.mjs` 经注册表选 dissector、烤中立 usage 与前缀哈希;`board.mjs` 出项目列表、session 视图、分页和控制面列表。
- **查询与回源**(`query/`):`queries.mjs` 是 [1.6](1.6-cli.md) §4.1 的那组具名查询;`source.mjs` 用 `text_ref` / `raw_ref` 回 NDJSON 或封存文件(D35)取逐字正文;`memo.mjs` 是进程内 LRU。
- **服务**(`server.mjs`):`node:http`,`GET /api/*` 与 `/control/*`(D26),同时托管前端;挂在守护进程上(D66),没有单独的服务进程。
- 详见 [3.1](3.1-adapter-contract.md)–[3.5](3.5-query-layer.md)、[4.2](4.2-storage-etl.md)–[4.4](4.4-server.md)。

### 6.3 前端呈现(`src/web/v2/`)
- 原生 ES 模块,没有构建步骤,守护进程发在 `/`([1.2](1.2-shell-layout.md) §托管与打开)。读只走具名查询 `GET /api/<名字>`,写只走控制面。
- 界面:外壳与顶栏([1.2](1.2-shell-layout.md))· 时间轴、轨道与概览 brush([1.3](1.3-timeline-tracks.md) / [2.1](2.1-track-widget.md))· 中央看板与上下文回放([1.4](1.4-central-board.md) / [2.3](2.3-context-window.md))· call-turn 卡([2.2](2.2-call-turn-card.md))· 资源管理器([2.4](2.4-resource-explorer.md))· 左栏 outline([2.5](2.5-outline-nav.md))· 原始数据面板与控制面侧栏([2.6](2.6-detail-panel.md))· 状态与审美([1.5](1.5-states-aesthetics.md))。
- 只读服务端给的中立字段,不认识 provider;非逐字的块按 `faithfulness` 打标。
- 守卫:`test/web-v2/`(纯模块与经 `real-face.mjs` 的真服务端)与浏览器套件 `test/web-v2/browser/`(`npm run test:browser`)。
