# trocar · RFC 4.11 — 采集器模型(macOS · Windows)

> **这是什么**:macOS 与 Windows 上采集器怎么装、怎么开关、怎么解密的唯一权威:模型正文(§1)、实现它的通用原语与描述符格式(§2)、模型空白处的裁定(§3)。加 harness 只填描述符数据。
> **受众**:agent(实现 `install` / `uninstall` / `on` / `off`、守护进程与各操作系统后端;加 harness)。
> **Source-decision**:D43 · D47 · D51 · D55 · D56 · D57。模型正文(§1)定稿后不改。§2 的原语按「模型里的各部分设计得尽量通用,新来的 harness 能迅速兼容」取舍。
> **不含 → 去哪查**:Linux(驱动模式、证书、撤销顺序)→ [4.6](4.6-process-collector.md);引擎、记录、D51 认进程、门的共用契约 → [4.6](4.6-process-collector.md);Windows 后端(身份与环境读取、助手动词、CNG 保管、`CurrentUser\Root`、系统代理读取、自启、控制面)→ [4.8](4.8-win-collector.md);macOS 后端(ps / netstat 身份、procenv、签名助手、钥匙串信任、scutil、LaunchAgent、控制面)→ [4.9](4.9-macos-collector.md);系统代理怎么读 → [4.7](4.7-netenv.md);命令与回执 → [1.6](1.6-cli.md);每个 harness 的具体值 → 描述符 `src/collector/harness/<name>.mjs`。
> **标注**:§1 冻结(见 §1 开头)。证据编号(R3-M1、W3、M8 这类)指实验室逐格记录。验收编号 CM* 只在本单元内有效,不复用。

## Goal

- 一份模型管 macOS 和 Windows:`install` 装根和根够不到时的证书载体,`on` / `off` 只管连接走不走门,解密按进程名认、只解密验过信任的形态。
- 模型的每一部分都是通用原语;harness 只在描述符里用数据选原语。加 harness 不写机制代码。
- Linux 不在本单元:照 [4.6](4.6-process-collector.md)。

## 1. 模型

> **定稿,此后不改。** 本节是模型正文,之后任何 PR 都不改它。与原稿的四处差别记在 §3 开头;标题层级随本单元下移一级。
> 各类事实现在住在别处:路径、键、进程名、主机写在描述符里(`src/collector/harness/<name>.mjs`,0.1 §2);每格状态(含本节的「未测」)记在实验室的逐格记录里(D45),不在本节;实验室测到一个「未测」项,改那条记录,不改本节。结果改变设计时,§3 加一条,点名它取代本节哪一句。会动的规范只有 §2 和 §3。

依据：四轮实验室实验；逐格结果和证据记在实验室的逐格记录里；标「未测」的是推断。规则来自 D43、D55、D56，定稿记在 D57。Linux 见 4.6。

几个词：
- **门**：trocar 在本机开的代理端口，一组 agent 共用一个。
- **开关文件**：trocar 自己目录里的文件，每个 harness 一个，写着门的地址；这个 harness on 时建，off 时删。

### install（装一次）

总规则：只加，不改。登录环境里不加任何变量。用户已经让某个设置指向一个证书文件时，在那个文件末尾追加一段带标记的 trocar 证书，设置本身不动；只对用户自己的文件这样做，包管理器或系统自带的证书文件不碰，`status` 说明。install 记下自己加了什么，uninstall 只撤这些。

1. **生成 trocar 根证书**：在本机生成；不限主机名；只能往下签一层中间证书；装上以后到 uninstall 都不换。证书上标「只用于服务器认证」：Windows 因此不认它签的代码，macOS 不因此收窄。私钥不能导出：
   - macOS：登录钥匙串里的密钥，只由 trocar 的签名助手使用；助手在用户的图形登录会话里运行，只签固定形状的中间证书。
   - Windows：不可导出的 CNG 密钥，有 TPM 就放进 TPM。
   - 守护进程每次启动检查这把密钥还在；不在就报出，提示重新 install。
2. **中间证书**：守护进程每次启动新做一张，有效期 7 天，签发满 6 天时再做一张；私钥只在内存里，由根签。门给出叶证书时总是一并给出中间证书。签不出中间证书时（macOS 没有图形登录会话，例如只有 ssh 登录），门只转发、不解密，留一条带原因的记录，`status` 报出。
3. **把根装成用户级根证书**。
   - macOS：登录钥匙串的用户信任，不限用途；系统弹框要登录密码。
   - Windows：`CurrentUser\Root`；系统弹「是 / 否」框。
   - 只靠这一条就够的：Claude Code 的所有形态（含 Claude Desktop 和它的 Code 标签）、Codex、Hermes、OpenCode 的所有形态，以及 Kimi 的 VS Code 扩展。
4. **根够不到的，证书交给它们自己读的东西**：
   - Z-Code：`~/.zcode/cli/config.json` 的 `network.caCertFile` 指向 trocar 的合并包：Node 自带的根 + 用户加的 CA（描述符 `merges` 列的设置所指的文件，只取证书块：install 所在环境的 `NODE_EXTRA_CA_CERTS`，这个键会让它失效；`ZCODE_AGENT_CA_CERT` 与桌面端的 CA 设置，它们设着时盖过这个键，一并放进来是为了它们撤掉以后包里仍有用户的 CA）+ trocar 根。这个键会替换掉默认的根，所以不能只放 trocar 根；不带用户 CA 时，Z-Code 和按它的信任验上游的门都连不上私有 CA 的主机（trocar 开着时 macOS 实测）；trocar 关着时也一样（推断，未测：键归 install，off 后还在）。用户已经设了自己的文件时，按总规则在那个文件末尾追加。
   - Kimi：第 5 条的包装在启动 Kimi 时加上 `NODE_EXTRA_CA_CERTS`，只在它没设时才加；用户已经设了时，按总规则在那个文件末尾追加。
   - DeepSeek：第 6 条的插件在进程里加上 trocar 根。
   - 用户设了 `CLAUDE_CODE_CERT_STORE=bundled` 的 Claude Code：`~/.claude/settings.json` 的 `env` 加 `NODE_EXTRA_CA_CERTS`，只在 settings 和 install 所在的环境里都没有它时才加；有时按总规则在那个文件末尾追加。
   - 用户设了 `SSL_CERT_FILE` 的 Codex、自己设了 `ssl_ca_cert` 的 Hermes 路由：按总规则在那个文件末尾追加（Codex 这一项未测）。
5. **Kimi 安装目录里的包装**：把 Kimi 的真程序挪进同目录的 `.trocar-real`，文件名不变，原位放一个包装。
   - 没有开关文件时，只加上第 4 条的证书变量，其余原样执行真程序：参数、输入输出、退出码一字不差。
   - 有开关文件时，再把用户原来的代理记进 `TROCAR_PRIOR_PROXY`（没有就写 `none`），把代理指向门。
   - 接住所有启动方式：各种 shell、绝对路径、编辑器起的 `kimi acp`、`kimi web`。
   - Kimi 自己的升级落在真程序上，不碰包装。重跑官方安装器会盖掉包装：`status` 按哈希报出，再跑一次 install 补上。
   - Windows 未测三项：包装加证书变量；`TROCAR_PRIOR_PROXY` 这个名字和 `none`；官方安装器盖掉包装。
6. **DeepSeek 插件**：`~/.dsh/cordis.patch.yml` 里加一行加载它。它在进程里加上 trocar 根；每个请求读一次开关文件：在就交给门，不在就交回 dsh 原来的走法。
7. **注册登录自启并拉起守护进程**(D61):macOS 写 `~/Library/LaunchAgents/com.trocar.collector.plist`,`launchctl enable`(清掉早先留下的停用覆盖)再 `bootstrap`;Windows 注册计划任务 `\trocar\collector`(`/Create` 被拒时走 Run 值后备,4.8 §7);Linux `systemctl --user enable --now`。从 `install` 到 `uninstall`,守护进程每次登录都起来——`on` 改过 agent 的配置,守护进程不回来它们就全连不上。计划里单列一行(1.6 §3.2)。
   - **自启项里的 node 要熬过 node 升级**(三个系统同一条规则,`src/collector/arch/autostart-node.mjs`):取 PATH 上的**第一个**绝对路径里的 `node`、照 PATH 的写法原样写(不解析),且只在它与当前进程的 `node` realpath 相同时才用它;相对路径的 PATH 项(`node_modules/.bin`、`.`)跳过——登录项里的程序路径必须是绝对的;都不满足时写 `process.execPath`。写死解析后的版本目录(Homebrew 的 `Cellar/node/<版本>`、nvm 的 `versions/node/<版本>`)会在下一次 node 升级后让守护进程登录时起不来——`on` 过的 agent 于是全连不上(实测:本机 2026-10-18 的 LaunchAgent 正指着 Cellar)。
   - 照 PATH 原样写 = 登录项的文本跟 install 所在 shell 的 PATH 有关:换一个 PATH 再 `install` 会把这个文件重写(V21 的「已到位不动」对它不成立),这是有意的——最新一次 install 看到的 node 就是登录时要用的 node。

同用户的剩余风险：本用户名下的任何程序都能借 trocar 的签名助手（macOS）或直接调用这把密钥（Windows）签出被信任的证书，也能删掉它，只是拿不走私钥；怀疑被用过时，uninstall 再 install。

### uninstall

- 有任何 harness 还开着，或还有 on 期间启动、仍连着门的进程（含仍在用 trocar PAC 的 Claude Desktop），就拒绝，并说出是哪些。
- 报出可能仍信任 trocar 的在跑进程（`liveness.<h>.trust_rereads` 与 [4.6](4.6-process-collector.md) 撤销顺序第 5 步）；`off` 不报任何进程仍信任证书（证书归 `install` / `uninstall`，D55①）。
- 倒序撤：Kimi 包装的哈希还是 trocar 放的那个时，把真程序原样放回；不是时（官方安装器已盖掉）不放回，只删 `.trocar-real`。删插件和加的配置项；证书文件里按标记删掉自己那一段，用户之后加的内容留着；撤根证书（系统同样弹框）；最后删根的密钥和 trocar 的证书文件。

### on / off：只管连接走不走门

共同规则：
- 不碰证书,也不碰登录自启(D61:自启由 `install` 注册、`uninstall` 撤销)。`on` 只确认守护进程在(不在就起一个);持久化的期望态决定守护进程每次启动开哪些门,所以 on / off 跨关机重启都不变。
- 不碰证书。改用户文件之前，先备份到 `~/.trocar/backup/`。
- **门只在代理链里插一环**。门往外连时，用这个 agent 没有 trocar 时本来会用的代理，按下面的先后取第一个有的：
  1. trocar 的钩子交给门的值：在进程里改代理变量的钩子（Kimi 包装、OpenCode 插件）把用户原来的值写进 `TROCAR_PRIOR_PROXY`，没有就写 `none`；在进程里加根的插件钩子，只在加上了根、又把代理变量指向门时，再写 `TROCAR_HOOK_PID` = 自己的 pid。这些变量会被 agent 起的子进程（工具调用里的 git、npm、curl）继承：子进程认不出是 agent，门仍从它自己的环境里取 `TROCAR_PRIOR_PROXY`；DeepSeek 插件不改变量，在连门时带上 dsh 自己的代理（macOS 实测，Windows 未测）。
  2. on 时在这个 agent 配置里记下的用户原值（例如 Hermes `.env` 里用户自己的代理行）。
  3. 这个 agent 进程环境里的代理变量，大小写的先后按这个 agent 自己的规则。macOS 读它的启动环境，Windows 读它的当前环境；值等于门的跳过，沿创建它的进程一级级往上找（这一步 Windows 实测，macOS 未测）。
  4. 系统代理，只对本来就跟系统代理的 agent，连同绕过列表；系统代理是 PAC 时 trocar 不执行它，如实标出。
  5. 都没有才直连。第 3 步找不回来（父进程已退出、中间隔着 Git Bash）时算「不知道」，不算「没有」：不论这个 agent 跟不跟系统代理，都取系统代理，没有系统代理才直连；`status` 报「窗口里的代理没接上」。
- PAC 的门（`auth:false`，Claude Desktop）不走上面五步：PAC 里写明了 app 本来的走法，门照它连（P10）。
- `status` 按 harness 显示这条链：agent → 门 → 上游，上游从哪来；trocar 写的代理值和用户原来的值并排列出。
- trocar 写代理变量时大小写两种都写；写 `NO_PROXY` 时写「本机回环 + 用户原来的值」，同样两种大小写。
- off 不杀、不重启 agent。on 期间启动、off 后还在跑的进程仍连着门：门只转发，不解密、不记录，`status` 报还剩几个。

#### 第 1 类：在 agent 自己的配置里写代理（on 写，off 删）

| harness · 形态 | 系统 | 写在哪 | 何时生效 |
|---|---|---|---|
| Claude Code · 命令行、VS Code 扩展 | mac、win | `~/.claude/settings.json` 的 `env` | 下次启动 claude |
| Codex · 命令行、VS Code 扩展、app | mac、win | `$CODEX_HOME/.env` 里一段，含 `NO_PROXY`；Windows 上必须写 `NO_PROXY`，不写时系统代理绕过列表里的主机不经门 | 下次启动 codex，包括它的后台进程（用户重启，trocar 不杀） |
| Hermes · 全部形态 | mac、win | Hermes 目录的 `.env` 里一段，放在用户自己的代理行之后 | 下次启动；dashboard 和 gateway 要重启它们自己 |
| Z-Code · 命令行（自带程序、Node 版）、桌面版 | mac、win | `~/.zcode/cli/config.json` 的 `network.httpProxy` | 下一个会话，app 不用重启 |
| OpenCode · 全部形态 | mac、win | 它的插件目录里一个 trocar 插件，只在开着时放 | 下一个 OpenCode 实例；v2 在跑的后台服务下一次 `run` 就生效，不用重启。长会话（ACP）：1.x 到会话结束都不变；v2 下一轮生效，只有会话中途 on 过的，off 后到会话结束仍走门 |
| Kimi · VS Code 扩展 | mac、win | VS Code 用户设置 `http.proxy`，并加进 `settingsSync.ignoredSettings` | 未测 |
| Claude Desktop（含 Code 标签） | mac、win | 用户级配置库（mac `~/Library/Application Support/Claude-3p/configLibrary`，win `%LOCALAPPDATA%\Claude-3p\configLibrary`）里当前生效那一条的 `egressProxyPacUrl`；没有生效的条目时 trocar 建一条只含这一键的并设为生效，off 时删掉它、生效项恢复原样（只含这一键时 app 仍是 Anthropic 账号模式：win 实测，mac 未测） | 下次启动 app；不要管理员 |

Claude Desktop 的 PAC 由 trocar 守护进程在本机 http 地址提供，回环地址（含 `*.localhost` 与 127.0.0.0/8）直连；用户绕过列表里的主机「先走门、门直连目标；门不通才直连」（P10）；其余「先走门；门不通走这个 app 没有 trocar 时本来的走法」：用户的固定系统代理，没有才直连。门往外连也是这条走法（绕过列表里的直连），不看 app 进程环境里的代理变量。明文 http（`http:` 地址）不经门，只走 app 本来的走法（P10）。off 后守护进程在同一地址继续提供 PAC，内容只剩这个 app 本来的走法，直到 app 重启（在跑的 app 何时重新取 PAC，未测）。

|---|---|---|---|

### 解密

引擎按进程名认出 agent（D51），只解密预设名单里在实验室验过信任的形态（D51④；每个形态的进程名在描述符的 `processes` 里（证据见实验室逐格记录））。没验过的，或者这个进程没带上证书（比如 install 之前就在跑），只转发、不解密，留一条带原因的记录，`status` 提示重开。靠证书变量信任的进程（Kimi、bundled 的 Claude Code），引擎先读它环境里那个变量指的文件，里面没有 trocar 根（例如用户 install 之后才设的文件）就同样只转发、留记录。

### 没覆盖的

- 范围外：Kimi 桌面版；WSL 里的 Codex。
- Claude Desktop 登录后的模型回合两个系统都未测：Anthropic 账号模式下、未登录时测过路由（mac、win）和信任（mac）；回合是在第三方推理模式下测的。
- Claude Desktop：它的进程连 Anthropic 自己主机（claude.ai、更新、下载）的流量按 D40 也解密，未测；其中有钉证书的，会断登录、更新或 Code 标签的下载。
- Claude Desktop：PAC 路线上的明文 http（PAC 收到的地址以 `http:` 开头）不经门、不采，走 app 本来的走法（P10）：Chromium 经代理发明文 http 用绝对形式的请求，门不收。
- Claude Desktop：trocar 守护进程停了、PAC 取不到时，mac 上 app 直连、绕过用户的系统代理；win 未测。守护进程在跑时 PAC 总有答复（认不出取 PAC 的进程也答不带门的那份，P10）。
- Claude Desktop：用户的系统代理本身是 PAC 时，PAC 里写不出用户的上游；机器上有托管配置时配置库不生效（读代码得知，未测），`status` 说明。
- Claude Desktop @mac：门不通时 Code 标签里的 claude 能否退到用户上游，未测（win 实测能）。
- Z-Code 的网络设置整组取自一处（环境变量或配置），三种情况不采，`status` 说明：用户在 `~/.zcode/v2/setting.json` 设了代理（盖过 cli 配置，还让 `caCertFile` 失效，mac 实测；on 不写那里）；用户环境里有 `ZCODE_HTTP_PROXY`（`caCertFile` 不生效，不信门）；用户环境里有 `ZCODE_AGENT_CA_CERT`（配置的 `httpProxy` 被忽略，直连，win 实测）。
- Z-Code：合并包只从 install 所在的环境读 `merges` 里的环境变量，不读在跑的 Z-Code 进程的环境；只在那个进程环境里加的 CA 不在包里，重跑 `install` 时带上它。用户靠 `NODE_USE_SYSTEM_CA` 或系统信任加的根不在包里。
- Z-Code 网页版没试：发行版没有这个模式。
- OpenCode：插件加载之前发出的请求（`models.opencode.ai`）不经门（win 实测）。
- OpenCode 1.x：用户原本没有任何插件时，trocar 插件会让它每次启动去 npm 装依赖，并在配置目录留下 `package.json` 和 `node_modules`，off 后还在；npm 不通时 mac 多等约两分半，win 卡住不发请求。
- Kimi：解析到另一份安装（npm 版）的 `kimi` 不经包装。
- Kimi VS Code 扩展：整个扩展宿主都走门，按进程名分不出 Kimi 的连接，只解密 Kimi 主机的办法没定；win 上带中间证书的链未测。
- Windows 窗口代理：Git Bash 里起的 Claude Code，门找不回窗口里设的代理。
- Windows 窗口代理：起 Claude Code 的窗口已关（例如 `start` 起的），门找不回窗口里设的代理；Codex 不受影响。
- Windows 窗口代理：agent 启动后窗口里改了代理值，门用的是新值。
- 只在某个终端里设的 `NO_PROXY`：on 时读不到，Claude Code、Codex、Hermes 配置里 trocar 写的值会盖过它，那些主机改走门再走用户的代理，内网主机可能连不上。
- 只在 install 看不到的终端里设的 `NODE_EXTRA_CA_CERTS`：用户设了 `CLAUDE_CODE_CERT_STORE=bundled` 的 Claude Code 会改用 settings 里 trocar 加的值，用户自己的证书文件（例如公司根）不再生效。
- Codex @win：用户在窗口里设了 `HTTPS_PROXY` 时，系统代理绕过列表里的主机直连、不经门；trocar 写的 `NO_PROXY` 能否改变这一点未测。
- 根的密钥 @mac：签名助手更新后是否不弹登录密码框（要 Developer ID 签名）未测；钥匙串锁着时能否签名未测。
- 没跑：Cursor、Windsurf 等 VS Code 衍生版；真实的 ACP 编辑器（Zed、JetBrains）；Hermes 预编译的桌面版（DMG、MSIX）；OpenCode TUI 和桌面版的长会话在 on / off 时的表现。

## 2. 原语与描述符

本节是规范。每个原语只定义一次;harness 只通过描述符数据(§2.3)在原语里选。每个 harness 的具体值(路径、键、进程名、主机)只写在描述符里,本单元不抄(0.1 §2)。

### 2.1 四个角色

| 角色 | 做什么 | 从不做 |
|---|---|---|
| **命令行**:`install`、`on`、`off`、`uninstall`,和独立的 `trocar-off`(`src/off`,只用 `node:*`) | 对用户文件、agent 文件的每一次写,对清单的每一次写。请守护进程开门、关门,并读回结果。 | 读或改流量。 |
| **守护进程**:每个用户一个,macOS 是 LaunchAgent,Windows 是计划任务 | 门(D47)。PAC。接受连接时认进程(D51)。解密判定。上游链。每次启动签中间证书。跟踪持有者。记录。 | 写 agent 文件。往信任库写证书。 |
| **钩子**:由 `install` 放,OpenCode 的由 `on` 放 | 在 agent 自己的进程树里:加 trocar 根,把连接交给门。 | 读或改字节。连门以外的地方。写 agent 配置。 |
| **操作系统后端**(`arch/<os>/`) | 密钥保管。用户级根证书库。按 pid 的进程事实:名字、启动时间、父进程、环境、cwd、套接字的所有者(uid / SID)。给持有者判定用的进程表。系统代理读取。持久环境变量和托管策略的读取(win:以用户身份用 `reg.exe` 读注册表;mac:托管偏好 plist)。core 要用的平台事实由它给,core 不写操作系统名:`envCaseInsensitive`、`pathKey(p)`、`persistentEnv(names)`。自启。控制通道。生成包装。 | 任何 harness 知识。守卫:`arch/` 与 `core/` 的代码里没有 harness id,`core/` 的代码里没有操作系统名字面量(注释不算);插件模板在 `src/collector/harness/templates/`(CM27)。 |

### 2.2 原语

**P1 密钥保管**(操作系统后端;一个接口):

```
custody = {
  kind: 'keychain' | 'cng' | 'file',
  create({ subject }) → { rootDer, fp256 }   // 在后端里生成密钥,并自签固定形状的根
  exists() → boolean
  issueIntermediate({ spkiDer, serial, notBefore }) → certDer   // 后端自己拼待签内容:CA:true、pathLen 0、EKU serverAuth、7 天、颁发者 = 根
  remove()
}
```

- 三个后端共守的规则:私钥不出后端;`issue` 自己拼待签内容,不收调用方给的(CM3);后端用不了密钥时(例如 macOS 没有图形会话)答 `unavailable`;钥匙串锁着时能不能签,未测(§1「没覆盖的」),签不出就同样答 `unavailable`。密钥参数、动词的实现、助手的换新办法只写在各后端:
  - `keychain`(macOS):[4.9](4.9-macos-collector.md) §6.1(签名助手的预编译与哈希钉住见 §3 ⑮)。
  - `cng`(Windows):[4.8](4.8-win-collector.md) §6.1(一次性脚本见 §3 ⑯)。
- `file`(Linux):现有的 `ca/ca.key`,0600。没有 `issueIntermediate`,叶证书仍由根直接签。Linux 不变。

**P2 签发**(`core/tls`):

- 根的形状:没有名称约束,pathLen 1,EKU 只有 serverAuth(§1 install 第 1 条;M8、W6)。
- 守护进程每次启动时在内存里新生成一把 P-256 密钥,请保管后端为它签一张 7 天的中间证书;这张满 6 天时签下一张。
- 重签失败(例如没有图形会话、密钥不在)时,继续用当前这张,记一条 `cert-intermediate-unavailable`,每小时重试;当前这张到期后门只转发,直到签出新的。
- 叶证书的到期不晚于它的中间证书。换中间证书时清掉叶证书缓存。
- TLS 总是发「叶 + 中间」(§1 install 第 2 条;t4-nointer、t2d)。
- 保管后端返回 `unavailable` 或密钥不在时,没有签发器:门只转发,记 `cert-intermediate-unavailable` 或 `cert-key-missing`。
- `cert.mjs` 收一个 `sign(tbs)` 回调,所以 mac / win 上根的私钥从不进 Node。

**P3 用户级根证书库**(操作系统后端;命令行参数只写一处,在可独立运行的 `src/off/root-store.mjs`,采集器导入它;各系统的命令写在 [4.9](4.9-macos-collector.md) §6.2、[4.8](4.8-win-collector.md) §6.2):

- `add(rootDer)`:装成本用户的根,不限用途。
- `has(fp256)`。
- `remove(fp256)`:按指纹撤,先撤信任、再删证书。
- 操作系统弹的框就是同意。从不写机器级信任库。

**P4 证书载体**(`install` 写,清单阶段 `install`):一条规则加四种。

- **规则 U:用户自己的文件。** 描述符 `userCertFiles` 列出的某个设置已经指向一个文件时,`install` 在这个文件末尾追加一段带标记的 PEM(清单 `text` / `pem-block`),设置本身不动。
  - 只对本用户拥有、可写、不在包管理器目录或系统目录里的文件这样做。
  - 不满足时跳过这个文件,`status` 报 `not-users-file`。
  - `uninstall` 按标记逐字节删掉这一段,用户之后加的内容留着(M5、W4)。
  - 几个 harness 的设置指向同一个文件时(Claude Code 与 Kimi Code 都读 `NODE_EXTRA_CA_CERTS`,Codex 与 Hermes 都读 `SSL_CERT_FILE`),文件里只有一段:先到的 harness 追加并记那一项,后到的见清单里已有这把根的那一段就记 `intact`(回执带 `shared_with`),不另记一项,`uninstall` 只撤一次(win 套件:第二个 harness 被拒「already holds trocar's text」,install 退出 1)。`status` 判每个设置指向这个文件的 harness 时,都按清单里这一段那一项判 `user_file`(在 = `intact`,被改或删了 = `changed`),后到的不报 `not-users-file`(复核发现后到的读成 `not-users-file`、「没采」、`status` 退出 1,再跑 `install` 也改不了;守卫 `test/collector/core/proxymode/status-facts.test.mjs`「rule U · one user file named by Claude Code and Kimi Code」)。
- `root`:只用 P3。每个形态的底线。
- `config-key` `{ file: <loc>, format, keys, semantics, when?: <cond> }`(位置和条件都是数据,§2.3):
  - `replace`:键指向每个 harness 一份的合并包,内容是 Node 自带的根、`merges` 列的设置指向的用户 CA 文件里的证书块(这个键让它们失效;读不了或是相对路径的在回执里点名)、trocar 根,同一张证书只放一次(Z-Code;R3-M6、R3-W3);
  - `add`:键指向 `trocar-ca.pem`(bundled 的 Claude Code);
  - 只在键没设时写。键已设时按规则 U。
- `wrapper`:P8。
- `plugin`:P9。

**P4b 这个 harness 装好了没有**(`status` 的 `setup`,D65④):把每个形态的 `present`(§2.3 的数据)与清单里该形态 `phase: 'install'` 的那几项(载体项和它们记下的哈希)对一下:

- 形态不在这台机器上 → 不算,它本来就不要载体;
- 形态由根承载 → 不要载体项,`install` 见没见过这个 harness 都一样(trocar 装好之后才装、只靠根的 harness 直接 `ready`,`on` 照开);
- 形态在、要自己的载体、清单里没有它的载体项 → `carrier-absent`(trocar 装好之后才装的 harness);
- 形态在、清单里有,但盘上那个文件的哈希与记下的不同 → `carrier-overwritten`(这个 harness 自己的更新盖掉了 trocar 放的包装或证书段;Kimi 的包装是典型,P8);
- 根本身不在用户的信任库里(`status` 的 `cert.root.state` 为 `missing`:装过、后来被移走)→ `root-missing`,整机一条,在 `missing` 里不按形态重复。根**待定或被拒**(`pending` · `declined`)不算:那是 `install` 自己留下的待办,`on` 照常、够不到的形态只转发([1.6](1.6-cli.md) §3.3「之后的效果」)。

三类都没有 = `ready`。读不出来(文件读不了、清单读不了)= `unknown` 加原因,**不写 `ready`**(D38)。`status` 的 `setup` 与 `on` 的前提 ⑪ 是同一个判断(一处代码),根的状态两边同一问法(向用户信任库问一次 `trocar-ca.pem` 在不在,`status` 本就问这一次;`on` 多这一问,仍在 D62 的 0.5 s 线内):`needed` 时 `on` 只拒绝这个 harness,码 `setup-needed`([1.6](1.6-cli.md) §3.3)。本条只定义在本单元的描述符上(macOS · Windows);驱动模式(Linux)的 `setup` 是 `unknown` 加原因。补它只有一条路:幂等的 `install`(V67,只写缺的那几项),命令行跑,或从看板那一行的 **Set up** 调同一个函数([4.4](4.4-server.md) §控制面 · D26②)。字段名与闭集在 [1.6](1.6-cli.md) 附录 C.3。

**P5 代理入口**(`on` 写,清单阶段 `on`)。第 1 类写进 agent 自己的配置,第 2 类是开关文件。

每种入口的接口相同:`write(ctx, doorUrl)` / `undo` / `check`。每次写:

- 只为至少一个**装着的**形态(描述符 `present`,§2.3)用到的入口写;一个 harness 没有装着的、`status` 判的形态(有验证过的形态时只算验证过的,范围外的桌面应用这类不算)时不写入口,`status` 判它没采到:码 `not-routed`,排在入口那一步之前(门判过的进程以门的判定为准),修法是用它自己的安装器装上一个形态、再 `trocar install`。不属于任何装着的形态的进程(另一份安装,如 Kimi 的 npm 版;宿主型形态只收 `hosts.processes` 点名的宿主进程,安装目录包装承载的形态只收它那一个程序,在原处或被移到旁边)同样判 `not-routed`,`doctor` 给它画一条不经 trocar 的直连路径;
- 先备份到 `~/.trocar/backup/`;
- 带哨兵标记;
- 按描述符给的名字,两种大小写都写;
- `NO_PROXY` 按 P6 写;
- 把被替换的值记成 `prior_value`(上游第 2 步);
- 目标文件不在时按入口的 `absent`:`create` 就建,`not-routed` 就不写并写明原因(§3 ㉑)。

每次撤销都逐键(或逐段):一个键或一段还是 trocar 写的值时,才恢复记下的原值;用户在 `on` 期间改过的,照用户的留着(D48②)。只有用户什么都没改时,才按整个文件的字节比对。

- **一个文件一份记录**(必拒):清单里同一个文件 MUST NOT 有两份彼此不一致的记录。trocar 自己新建的入口文件也由它自己那一条入口记录记着(`json-key` 的 `existed_before: false` 与 `created_dirs` 就是「这文件和这几层目录是 trocar 建的」),不再另记一条 `owned-file`:两条记录在写完第二条的那一刻就对不上(先记的哈希是空文件的),status 会把逐字完好的入口报成被改过(`entry-missing` / `proxy-changed` 误报,mac 真机 2026-10-19)。

| 种类 | 写什么 | 清单项 |
|---|---|---|
| `json-key` | JSON / JSONC 文件里的键;值是门的地址,或 PAC 地址(`value: 'pac-url'`)。两个可选的数据字段让它盖住 GUI 的情况,不用每个 app 一种:`arrayItems`(trocar 往数组里加的一个元素,例如 VS Code 的 `settingsSync.ignoredSettings` 加 `http.proxy`)和 `select`(文件是一个元文件选中的那一条:`{ dir, meta, idKey, createIfNone }`;Claude Desktop 的配置库是 `_meta.json` 和 `appliedId`;没有生效的条目时,建一条只含这一键的并设为生效) | `json-key`(加 `json-array-item`;建了条目时,这条新文件就是它自己那一条 `json-key`(`existed_before: false`),另加元文件上的 `json-key`;不另记 `owned-file`——见下「一个文件一份记录」。`off` 把这两个键撕回去;文件空了就连文件和 trocar 建的目录一起删,用户在 `on` 期间往里写过的就只拿走 trocar 的键) |
| `dotenv-block` | 一段,放在用户同名键的行**之后**;不注释任何一行 | `text` / `dotenv-block` |
| `plugin-file` | agent 插件目录里一个 trocar 拥有的文件,门的地址写死在里面(内容来自 P9 的 `opencode-plugin` 模板) | `owned-file` 角色 `plugin` |
| `switch-file` | `~/.trocar/collector/switch/<harness>`(0600),内容是门的地址 | `owned-file` 角色 `switch` |

**P6 `NO_PROXY` 合并**:

- 值 = 本机回环(`localhost,127.0.0.1,::1`)∪ 用户原来的值。
- 用户原来的值 = `on` 之前写入处已有的值(两种大小写合并),加上 `arch.persistentEnv(['NO_PROXY'])` 读到的(§3 ⑤)。core 不写操作系统名。
- 合并时不分大小写去重,保持原来的顺序。两种大小写都写(R3-M8、R3-W5)。

**P7 上游链**(`core/proxymode/chain.mjs`,所有 harness 共用一个函数):

```
upstreamFor({ desc, form, facts /* pid, start, env, parentOf;认不出的进程只有 pid, start, env 与 hookOnly */, recordedPrior, systemProxy, proxyFile }) → { url | null, source, bypass }
source ∈ 'hook' | 'config-prior' | 'process-env' | 'system-proxy' | 'direct' | 'unknown'
```

各步照 §1 on / off 共同规则的 1–5:

1. **hook**:进程环境里的 `TROCAR_PRIOR_PROXY`(`none` = 没有代理),或 CONNECT 头 `X-Trocar-Upstream`(一个代理地址;agent 自己对这个主机本来就直连时是 `none`——钩子连门之前先套用 agent 自己的绕过规则)。只有认出的进程所在形态用的是会发这个头的钩子(今天只有 `cordis-plugin`)时才认这个头;别的进程带来的一律不认,记一条。入口剥掉这个头,从不记它的值。没有 `X-Trocar-No-Proxy`。认不出的进程连到要凭据的门,只在本步读它自己环境里的 `TROCAR_PRIOR_PROXY`(同一个读取器、同一份 pid 加启动时间的缓存,只问这一个名字;代理变量指向门而又认不出,多半是从进程内钩子继承来的),然后走第 2、4、5 步;它的 pid 不知道或环境读不到时,有第 2 步的原值就取它(`on` 记了原值的路线是配置把代理指向门,没有进程内钩子),没有就是 `unknown`(D38:读不到不算没有),不直连。
2. **config-prior**:`on` 记下的 `prior_value`。
3. **process-env**:按描述符 `proxy.env` 的先后,逐个名字取 agent 启动后实际用的值。agent 自己的代理文件(描述符 `proxy.files`)按各条的 `applies` 参与:`override` 的文件盖过环境(Claude Code 的 settings `env`、Codex 与 Hermes 的 `.env`),`fill` 的文件只补环境里缺的那个名字(dsh 的 `.env`、Z-Code 的 `network.httpProxy`、pi 的 `httpProxy`);同类的文件按列出的先后。dotenv 的键就是名字;JSON 键路径的末段是 `proxy.env` 里的名字时就是那个名字,否则代表该条 `names` 列出的名字(默认 `proxy.env` 全部)。这一步套用发生在 agent 进程内,读启动环境的 mac 看不到,所以门照同一规则自己读文件:路径按这个进程的环境解析(条目的 `env` 写明挪目录的变量,进程环境按它取),经 `ctx` 读,每个进程生命(pid + 启动时间)读一次,读不到的至多每秒重读一次。文件里的值等于门的逐个跳过,接着看后面的文件与环境;环境里的值等于门的,沿 `parentOf` 往上找(上层进程只看环境)。需要的文件读不到是 `unknown`(D38:读不到不算没有),失败记录带上哪个文件、什么原因。`on` 写进这些文件的路线,用户原来的值已是第 2 步的原值。
4. **system-proxy**:只对跟系统代理的 agent(`proxy.systemProxy`),连同绕过列表。trocar 从不执行 PAC:系统代理是 PAC 时,跟系统代理的形态不写入口(`not-routed`),`status` 写明原因。
5. **direct**:都没有才直连。

第 3 步找不回来时,或认不出的进程环境读不到、又没有第 2 步的原值时,结果是 `unknown`:有系统代理就用系统代理,没有才直连,记 `prior-proxy-unknown`。

PAC 那一组门(`auth:false`)不走这五步:它往外连用 PAC 写的本来的走法(P10)。

每一个来源都过 `isTrocarDoor(url)`(本机回环加 trocar 的凭据)。

操作系统后端的读取器是 `proc.envOf(pid, names)`、`proc.cwdOf(pid)` 和 `proc.parentOf(pid) → { ppid, startedAt }`:

- mac 用 `procenv` 读启动环境(M2),用 `procenv <pid> :cwd` 读 cwd;
- win 用助手动词 `proc-env` 读 PEB 里的环境和当前目录(W2;读一次 PEB 两样都有)。
- 读到了的结果按 pid 加启动时间缓存,进程活着期间只读一次:忙的 agent 只花一次读取,不是每个连接一次(Windows 的助手只有一条按序应答的通道)。读不到的(助手超时、进程拒读)不缓存,之后的连接再读,同一进程至多每秒一次;启动时间不知道的同样至多每秒读一次、不长期缓存(pid 会被复用)。读不到不等于没设(D38)。缓存有上限,满了先丢最旧的。(依据:缓存读失败得出的判定,会让这个进程活着期间一直只转发)

**P8 安装目录包装**(通用;描述符 `{ kind: 'wrapper', command, binDir: <loc>, certVar, layout: 'native-binary' }`):

- **前提**(`install` 时检查;不满足就跳过这个载体,`status` 报 `not-users-file` 并写明原因):目标是一个原生可执行文件(Mach-O / PE,不是脚本,也不是 npm 的 `.cmd` / `.ps1` / sh 启动脚本),在本用户拥有、不在包管理器目录里的文件夹里,并且 agent 自己的更新按文件名换掉这个文件。最后这一条由描述符的 `layout: 'native-binary'` 声明;Kimi 的是实测的(M4、W3)。启动脚本会被包管理器重写的命令行,用 `plugin`,否则不支持。
- **install**:
  - 解析出 `<binDir>/<command>[.exe]`;
  - 它已经是 trocar 的包装(哈希一致)时什么都不做;
  - 在同一卷内改名,把真程序挪到 `<binDir>/.trocar-real/<同名>`,文件名不变,Kimi 的自动更新于是落在它上面(M4、W3);
  - 写包装,记下两个 sha256。
- **各系统的包装**:
  - mac:由 `arch/darwin/wrapper.dash.tmpl` 生成的 `/bin/dash` 脚本(M4:用 dash,不用 `/bin/sh`);
  - win:`install` 时用系统自带的 `csc.exe` 从 `arch/win32/wrapper.cs` 编译出的小程序,与 W3 的做法相同;路径与 Smart App Control 的判定见 [4.8](4.8-win-collector.md) §6.3。
- **运行时**:
  - 没有开关文件:只在 `certVar` 没设时设上它,然后用一字不差的参数、标准输入输出和退出码执行真程序。
  - 有开关文件:再设 `TROCAR_PRIOR_PROXY`(agent `proxy.env` 里第一个设了的值,没有就是 `none`),并把描述符给的代理变量名指向门。
- **撤销**:包装的哈希还是 trocar 的,才放回真程序;不是时只删 `.trocar-real`。
- **status**:哈希变了报 `entry-changed`,命令是 `trocar install`。

**P10 PAC**(`core/proxymode/pac.mjs`):

- 守护进程在 PAC 这一组门的端口上(`auth:false`)应答 `GET /trocar.pac`。
- 内容:
  - 回环地址 → `DIRECT`。回环 = `localhost` 与所有 `*.localhost`、127.0.0.0/8、`::1`,与门判回环用同一个判定(`chain.mjs` 的 `isLoopbackHost`)。只放 `localhost`、`127.0.0.1`、`::1` 时,用户绕过列表里的一行 `domain-suffix localhost`(Clash Verge 的默认)把 `*.localhost` 送进门;
  - 用户的绕过列表 → `PROXY <门>; DIRECT`,门按 `bypassHit` 直连目标,与 env 路线(`NO_PROXY` 只放回环、门在上游拨号时用绕过列表)一致(依 D40 / D38 / D49):绕过列表直接给 `DIRECT` 时,mac 上 Claude Desktop 发往绕过列表里主机的 turn 不经门、零记录(实验室的 `*.test`;真实用户把内网网关放进绕过列表也一样),而用户要的只是「这些主机不走我的代理」,门直连正是这个走法;
  - 其余 → `PROXY <门>; <本来的走法>`,本来的走法是用户的固定系统代理,没有就是 `DIRECT`;
  - 明文 http(PAC 收到的地址以 `http:` 开头)→ 不经门,只给这个 app 本来的走法:绕过列表里的 `DIRECT`,其余 `<本来的走法>`。这是保真边界(不变式 4,§1「没覆盖的」):PAC 路线上的明文 http 不采:经 HTTP 代理时 Chromium 发明文 http 用绝对形式的请求(`GET http://主机/…`),门只收 CONNECT 和 SOCKS5;门接下连接之后,PAC 里门后面的 `; DIRECT` 不再起作用,所以经门的明文 http 一律断,绕过列表里的内网 http 主机(网关、MCP 服务)也跟着断。门转发绝对形式的请求不在这一轮;
  - `off` 之后只剩 `<本来的走法>`。
- PAC 这一组门往外连,用的就是 PAC 写的本来的走法:用户的固定系统代理,连同它的绕过列表(`bypassHit` 命中的直连);没有固定系统代理就直连。PAC 的内容与门的上游出自同一个函数(`pac.mjs` 的 `pacLeg`)。这是 `auth:false` 门的通则,不按 harness 分:到这扇门的连接是照 PAC 来的,P7 五步里的描述符事实(读哪些代理变量、跟不跟系统代理)属于这组门 harness 的别的形态,不属于 PAC 的客户端;CONNECT 带来的 `X-Trocar-Upstream` 照 P7 第 1 步不认,记一条。此前这扇门按 Claude Code 的描述符取上游(不跟系统代理),非绕过主机被直连、不经用户的系统代理(与 1.6 附录 A 第 29 行不符);app 进程环境里有 `HTTPS_PROXY` 时,连绕过列表里的主机也拨经那个代理,违背上面「门直连目标」。
- PAC 的门不带凭据,所以接受连接时只放行对端进程属于本用户的(mac 按 uid,或套接字表证明这一端的持有者都是本用户的进程(4.9 §5.3 第 1 步的 `sameUser`:助手只列本用户的进程,所以它答出的持有者不论认出 pid 与否都已证明是本用户的;认出了 pid 而那个 pid 的 `ps` 一时答不出(超时或非 0 退出,如合盖时几秒钟的 DarkWake)也算,这样的连接透传 `untracked`·`facts-unavailable`,取 PAC 的得到带门的 PAC;`ps` 的超时或退出码写进原因(D38)。依据:P10 自己的规则「本用户的进程放行」与本条「与 D51 认进程读的是同一组事实」;证据:真机 Mac 合盖期间 5 个 DarkWake 窗口里 8 条 `pac-peer-refused` 与 3 条 `pac-owner-unread`,拒的都是本用户的 Claude 进程,套接字表已认出 pid、`ps` 超时);win 按 SID;与 D51 认进程读的是同一组事实)。本用户的但 pid 认不出的连接照 4.8 §5.3「没有 pid」透传 `untracked`·`pid-unresolved`,不拒。拒绝(别的用户,或认不出是本用户的)= 不回话、直接关连接,不回 407(门不收凭据,407 要的是它根本不收的东西;Chromium 遇 407 不落到 PAC 的下一项),每个连接只记一条 `pac-peer-refused`(带 `peer`),不另记 `ingress-auth-failed`。读不出属主(`no-row` / `unreadable` / `shared`,即不是确证别的用户的)、且被判定期间已经走了(关了或半关了自己那一端)的连接(发完 CONNECT 就关:它的 fd 已关,内核里那个套接字没有持有者,属主问题因此答 `no-row`)什么也没被拒:照样关、不回话,不记 `pac-peer-refused`,只计入 `engine.stats().ingress.left`(4.8 §5.1);确证属于别的用户的连接不论走没走都记它那一条 `pac-peer-refused`(审计信号)。取 PAC 的请求读不出属主而请求者已走,同样不答、不记 `pac-owner-unread`。它只送来开头,agent 的字节一个也没丢,不是采集失败(D38 管的是采集失败),记成拒绝反倒是假记录(不变式 4)。依据:不变式 4、D38;真机 Mac 上曾一天记下 26 条 `owner no-row` 的拒绝,门边并没有别的用户的进程。取 PAC 的请求认不出是本用户的(读不出属主)时照样答 PAC,只是不带门、只写 `<本来的走法>`(与 `off` 之后同一份),记一条 `pac-owner-unread`(带 `peer`),如实写「答了不带门的 PAC」与认不出的原因:答空会让 app 退成直连、绕过用户的系统代理。别的用户的取 PAC 请求被拒并记 `pac-peer-refused`。依据:trocar 必须对系统代理有所感知——开了系统代理就走系统代理,否则就走直连;本用户但 pid 认不出的透传、拒绝不回 407 且一条记录,依 4.8 §5.3「没有 pid:splice untracked」与不变式 5。
- 下面四种情况不写入口(`not-routed`,§3 ③):
  - 系统代理本身是 PAC;
  - 用户当前生效的条目里已经有自己的出口代理或 PAC;
  - 机器上有托管配置(一个 `{policy}` 拦截项,§2.3);
  - 本来的走法要凭据(沿用现在的 `entryGate`:只有地址的门不能把用户代理的凭据借出去)。

**P11 代理模式的解密判定**(`core/proxymode/verdict.mjs`)。下面各条都成立才解密;少一条就只转发,并记原因:

1. D51 按名字认出了进程,而且这个形态在本系统上 `verified`(否则 `not-verified`);
2. 主机不在形态的 `forwardOnlyHosts` 里(否则 `not-verified`,带上主机);
3. 进程的启动晚于这个形态的载体的 `installed_at`(否则 `config-after-start`);
4. 进程的信任集里有 trocar 根:形态的证书是插件载体(P9:钩子在进程内把根加进它的默认信任集)时有——插件加不上根时从不交给门(⑦),经门的连接都来自已加根的进程——这时形态的信任来源只供门验上游(⑭),来源设没设、文件里有没有根都不因信任只转发,但来源或它指的文件读不到时仍只转发且不缓存(⑭ 要用它,D38);形态的信任带 `when` 而它不成立时也有(进程用系统根);插件载体的形态下,进程环境里有 `TROCAR_HOOK_PID` 而它不是这个进程自己的 pid 时没有:这个进程从父进程继承了门,自己没有跑钩子、没加根(`hook-inherited`;没有这个变量时照上文;macOS 读的是启动环境,所以嵌套在跑过钩子的同 harness 进程下的那一个也只转发);插件载体的形态下进程环境读不到时只转发且不缓存(`environ-unreadable`:判不了它自己跑没跑钩子,D38);否则按 **agent 自己的先后**(§2.3 `trusts`)走形态的信任来源,第一个设了的来源指向的文件里要有 trocar 根(没有根或文件不在时 `ca-not-in-file`);一个都没设时,有 `required` 的来源或基底是 Node 自带的根(其中从没有 trocar 根)就 `var-missing`,否则有(基底是系统根,`install` 把用户级根放在那里);
5. 签发器在(否则 `cert-intermediate-unavailable`);
6. 没有拦截项命中。

判定按 (pid, 启动时刻, 门, 主机) 缓存,只缓存依据读到了的判定:依据读不到得出的(`environ-unreadable`、`config-unreadable`、`file-unreadable`、`start-time-unknown`)和挂在签发器状态上的(`cert-*`)不缓存,下一条连接重读。安装清单读不到时沿用上一次读到的那份并记一条 `manifest-unreadable`(从读得到变成读不到时记一次),不当作没有载体(`not-routed`);一份都没读到过时得出的判定也不缓存。读不到不等于没设(D38)。按设计只转发的判定码(`not-verified`、`outside-host-set`,[4.6](4.6-process-collector.md) §记录「连接行」的预期类)只记在连接行里,不另写失败事件;其余判定码每个 (pid, 启动时刻, 门, 主机, 码) 写一条失败事件。

D51④ 的 `trust-rejected` 仍是兜底。

**`status` 的进程判词与门同一条规则,证据在推断之前**:守护进程的 `GET /status` 在 `agents` 里列出门对每个进程(pid 加启动时刻)最近一次下的判词(`trusted` 与 `decrypt`,与驱动模式的行同名同义,网络事实的 `watched` 读 `decrypt`;不解密时 `reason` = 上面的码;按设计只转发的码不列),有上限,只按内存答、不读进程表;`status` 只取进程表里还活着的那些。代理模式下一个进程的判词按下面的先后取,先取到的为准(依据:不变式 4(证明不了的失败不报)、D38(不知道不等于失败)、V16「已被采集的进程经 `off` → `on` 仍被解密」;正被采集的 Claude Code 曾被判成没在采集):

1. **门对它这一生的判词**:守护进程内存里的(`GET /status` 的 `agents`);没有时读门的持久记录 `~/.trocar/collector/door-seen.json`(P12)里这一生(pid 加启动时刻)有效的一行:`accept` 行给出门的判词,`pac` 行算被采集。
2. **Chromium 宿主并入**:没有 `--type=` 的进程,有一个同 harness 的子进程是网络服务([4.6](4.6-process-collector.md) Chromium 角色)时,取那个子进程的判词,显示为它的宿主。只往下找网络服务,从不由命令行进程往上并到父进程。
3. **P11 第 3 条**:进程早于它可能是的形态的载体 `installed_at`(与门取同一组形态)→ `config-after-start`,这是确定的。
4. **只在历史已知的范围里推断**(`liveness.<h>`,P12):在记下的某一段 on 期间启动(当前一段,与 `windows` 里最近一次部分门变动之后的各段;入口会被重读的 harness 只要活着就算)→ 被采集(读到了入口);在已知的 off 间隙里启动、没有被路由的同 harness 祖先(沿父进程链,祖先按本条或第 1 条被采集)→ `config-after-start`(D31①:从没读到入口);在已知的间隙里启动、有这样的祖先 → `not-seen`(环境继承:在真机 Mac 上实测,Desktop 托起的 claude 带着 `HTTPS_PROXY` = Desktop `library` 的 PAC 门)。
5. **其余**:启动在载体之后、但在历史起点之前(没有 `since`,且早于最早一段),或在最近一次部分门变动之前的某一段里启动 → `captured:null`、`not-seen`,不给重启步骤。

这几步与 P12 的持有者是同一个判定:`off` 前判为被采集或 `not-seen` 的进程,`off` 后都是持有者。代理模式的 `GET /status` 另带 `negatives`(`engine.negatives()`);`agents` 里列出的进程在负缓存里有条目时,`status` 判它为 `negative-cache`([1.6](1.6-cli.md) 附录 A.2 第 6 行;依据:status 与门同一条规则,不变式 4)。门判「读到过入口」从不看 `on_at`。

**P12 持有者与排空**(`core/proxymode/holders.mjs`;判定在 `src/off/holders.mjs`,与 `status` 共用,门的持久记录在 `src/off/door-seen.mjs`,另用早先 `off` 判活的代码 `src/off/proc.mjs`、`src/off/signature.mjs` 和 `undo.mjs`):

- **持有者**是 `off` 之后还可能用门的活进程(pid 加启动时间),只往安全的方向算:宁多一个,不少一个(依据:D50(判活宁多一个持有者)、不变式 5(不断 agent)、不变式 4)。harness h 的进程(按 D51 认)有下面任一条就是:
  - 门的持久记录里有它这一生有效的一行(`accept` 或 `pac`);
  - 在记下的某一段 on 期间 `[on_at, off_at)` 启动(当前一段与 `windows`);
  - 入口会被运行中的 agent 重读(入口数据 `rereads: true`:Z-Code 的下一个会话、OpenCode v2 的后台服务),`off_at` 时还活着;
  - 启动晚于清单里最早的载体时刻(h 的 `install` 各项与系统根的 `installed_at`),又早于不知道的历史起点(没有 `since`,且早于最早一段),判定带 `why: history-unknown`;
  - 门的持久记录读不了(门的证据不知道),这个 harness 已经开过、它又不凭别的证据算持有者的活进程,判定带 `why: history-unknown`(不知道有没有它的那一行,早于载体的也算);
  - 沿父进程链(ppid)有一个同 harness 的祖先是持有者;
  - Chromium 宿主与它的网络服务子进程:其中一个是持有者,另一个也是。
  - Claude Desktop 按同一条算:取 PAC 就是读入口(`pac` 行)。
  - 不算持有者:在已知的 off 间隙里启动、上面一条证据都没有的;早于最早的载体时刻、又不在任何一段里启动的;每个请求都重读开关文件的钩子(`per_request`:`cordis-plugin`)。`off` 后它的下一个请求走 dsh 原来的路,开着的连接按 [1.6](1.6-cli.md) §3.1 逐条排空。
- **门的持久记录** `~/.trocar/collector/door-seen.json`(`src/off/door-seen.mjs`):守护进程在门接受连接与送出 PAC 时写行 `{harness, group, pid, start, kind: accept|pac, at, n, decrypt?, reason?}`(`n` = 这一生在这扇门上的次数,`decrypt` / `reason` 是门对 `accept` 的判词),整文件原子替换、行数有上限,删掉进程表里已不在的那些生;守护进程启动时读回它。一行有效,当且仅当它的 `at` 不早于 `door_since[group]`(这个门组的门值从那时起没变)、也不早于 `since`。`off` 的回执、`status` 和守护进程不在时的 `uninstall` 读同一个文件;文件读不了 = 门的证据不知道:持有者照安全方向算,`status` 不凭它说 `captured:false`。守护进程启动时读不了它,报 `door-record-unreadable`、从空起记,写回时带上 `unknown_before`(读不了的那一刻;读回的文件已带它就沿用,字段在而值不是时刻按读到它的那一刻算):带这个字段的文件同样算门的证据不知道,守护进程启动时沿用其中的行接着记、每次启动都报一次 `door-record-unreadable`,守护进程自己也照此答,直到进程表里不再有任何开过的 harness 的、在那一刻之前启动(或启动时刻不知道)的进程,它才去掉这个字段;从不把只含之后见到的那几生的文件写成完整的(依据:D50、不变式 4、本条「门的证据不知道」的安全方向)。`status` 的「读到过入口」与持有者是同一个判定([1.6](1.6-cli.md) 附录 A.2 第 32 行)。依据:D50(判活宁多一个持有者)、不变式 5(不断 agent)、不变式 4。
- 「在某段期间启动」按进程表读取者标明的启动时刻精度判:真实启动在 `[startedAt, startedAt + startGrain)` 里任一处都可能,这段与期间相交就算(按整秒读的 macOS `lstart` 落在 `on_at` 那一秒的进程是持有者;读得更细的按读到的值判)。`status` 的判词、持有者和 `undo` 用同一个判定,同一行进程在 `off` 前判为被采集或 `not-seen`、`off` 后就是持有者,门不会在它还用着时关([1.6](1.6-cli.md) 附录 A.2 第 32 行;依据:不变式 5「不断 agent」与 status 同一条规则,不变式 4)。

- `off` 之后,只有没有 harness 开着、没有持有者活着、也没有开着的连接时,门才关。代理模式的守护进程**不因 `off` 退出**(D62⑥):门关完它空转留着。驱动模式(Linux)照旧排空后退出。
- 清单的 `liveness.<h>` 记 `identity`、`rereads`、`trust_rereads`、`on_at`、`off_at`、`since`、`door_since` 和 `windows`,守护进程不在时命令行用进程表算出同一张表(可独立运行)。`rereads` 是本 OS 各形态的路由数据(§2.3)里有没有会被在跑进程重读的,是持有者判定与 `status` 的「读到过入口」读的唯一一个重读数据;`trust_rereads` 是描述符的 `trust.rereadsEntry`,只给 `uninstall` 的仍信任 / 合并包几步读([4.6](4.6-process-collector.md) 撤销顺序第 2、3、5 步),持有者判定从不读它;没有 `trust_rereads` 的记录(较早的 trocar 写的)在那几步按它的 `rereads` 判,直到下一次 `install` 改写。依据:§2.3 把持有者数据放在路由上;D55① 证书归 `install` / `uninstall`;4.6「`off` 的撤销」`off` 不报「重启前仍信任」;Windows 实验室 `off claude-code` 曾把 install 前 22 小时启动、从没连过门的六个 Claude Desktop 进程报成仍连着、仍信任。`windows` 是以前各段 on 期间 `[{on_at, off_at}]`:一次 `on` 重开期间时把上一段收进去。`since` 是这个 harness 的历史从哪一刻起完整:清单里还没有 `on_at` 的记录第一次 `on` 时写成那次的 `on_at`;一次 `on` 之后 h 的每个门组的门值都变了时,同样写成那次的 `on_at`,并清空 `windows`(以前各段启动的进程指向的已经不是这扇门)。只有部分门组的门值变了时,`door_since.<组>` 写成那次的 `on_at`,`windows` 留着(那几段启动的进程按 P11 `status` 第 5 步判 `not-seen`,仍是持有者)。`windows` 最多 32 段,裁掉最早一段时一并删掉 `since`;没有 `since` 的记录(较早的 trocar 写的,或被裁过的)在最早一段之前的历史按不知道算。依据:D50(判活宁多一个持有者)、不变式 5(不断 agent)、不变式 4。
- 用到它的地方:`off` 的回执和 `status`(「还剩 N 个」,带 pid)、[1.6](1.6-cli.md) §3.1 的排空、`uninstall` 的拒绝。

### 2.3 描述符(每个 harness 一个文件,所有系统共用)

Linux 保留它的字段(`trust`、`inject`、`layers`)。代理模式只读 `proxyMode` 和共用字段。没有按系统分开的覆盖文件;系统不同的路径用 `_common.mjs` 的 `perOs({ darwin, win32 })` 写成数据。

**`proxyMode` 里没有函数。** 描述符指向的每个地方都是三种封闭的数据之一,由 core 的一个读取器(`core/proxymode/sources.mjs`)读,托管策略再加每个系统一个读取器。所以新 harness 只是数据,第八个 harness 的守卫(CM27)才证明得了东西:夹具里夹带不进机制。

- 每个 `form.route`、`form.cert`、`form.trust` 都找得到;每个形态的 `present` 不为空;

- 每个 `verified` 的值是 `true`,或者带原因;
- `effects` 每条是 `{ id, paths, when }`,`notes` 每条是 `{ id, text }`;
- 每个**写入目标**(入口文件、`config-key` 的文件、包装的 `binDir`、插件目录、加载行所在的文件)都在用户的 home 或 agent 的安装目录下;只读的地方(`blockers`、`policy`、`/Library` 或 `ProgramData` 下的托管设置)可以在任何地方。

### 2.4 加一个 harness

1. 写 `processes`(D51 的名字)、`forms` 和每个形态的 `present`,依据实验室的普查。
2. **入口**:agent 从它自己拥有的文件读代理时,用第 1 类:`json-key`(设置需要时带 `arrayItems` / `select`)、`dotenv-block`;有插件目录、且没有 `install` 期的钩子带着它的证书时用 `plugin-file`。`install` 期的钩子(`plugin` 或 `wrapper`)已经带着证书时,用第 2 类 `switch-file`,由同一个钩子读开关文件。否则用 `switch-file`,再配一个钩子载体。
3. **证书**:实验室表明根够得到这个 agent 时,用 `root`。否则依次选:
   - `config-key`(`replace` → 合并包,`add` → `trocar-ca.pem`);
   - 不行就 `wrapper`(命令行是用户自己文件夹里的一个原生可执行文件,agent 的更新按文件名换掉它,即 P8 的前提);
   - 再不行就 `plugin`(宿主的插件接口已经有模板)。
4. **信任**:写 `trusts`(基底,以及哪些设置能遮住或带上信任,**按 agent 自己的先后**),再写 `userCertFiles`、`blockers`、`effects`;用户怎样启动它就不经门、不被采时(一个命令行参数、一项设置、一个太旧的运行时),写一条 `notes`。
5. 写 `proxy.env` 的先后、`systemProxy` 和 `takesEffect` 的文字。
6. **实验室**:每个形态一行 cells;跑哪些由描述符的形态 × 系统生成。还没有流程脚本的形态,在矩阵里记 UNT 并带指针,直到有了为止。

不写机制代码。只有 P1–P13 都够不到这个 agent 时才允许加新原语,PR 要写明现有的为什么加宽不了(0.1 §6 第 15 条)。守卫 CM27。

### 2.5 不做

改系统代理、接管整机流量、写登录环境或全系统的 `HTTPS_PROXY` 一类代理变量(D43)。

① **谁写文件**:用户文件和清单只由命令行写(`install`、`on`、`off`、`uninstall`、独立的 `trocar-off`)。守护进程只开门、提供 PAC、认进程、解密、签中间证书,不写任何 agent 文件,也不写 `ingress.json`。`on` 先请守护进程开门并读回,再写入口、建开关文件。`on` 每跑一次按 [1.6](1.6-cli.md) §1 在 `flows/` 写 `install-note`(最后一行 `kind:'result'`,失败的也写),与 `off` 的 `off-note` 对称;守护进程收到 `on` / `off` 不另写记录(依据:从看板关掉又打开时,`flows/` 里开与关都要有)。门的端口记在 `ingress.json`,由 `on` 选、`uninstall` 删;看板的端口也记在那里,由 `install` 选(D66 · [4.4](4.4-server.md) §Plan「端口」:`install` 之后看板就该在,不等第一次 `on`);自启单元重新拉起的守护进程沿用记下的端口,从不另选;端口被别的 socket 占了,它记一条 `engine-port-taken`,下一次 `on` 换一个端口并改写这一组的入口。`on` 发现这一组记下的端口被别的程序占了而换端口时,也记一条 `engine-port-taken`(失败行,`where: 'ingress'`,带 `door`、旧端口 `port`、新端口 `moved_to`),回执的提示里原样写出这个码(守护进程停着时端口被占,只有 `on` 看得见,不记就静默,违 D38)。

② **off 之后的守护进程**:持有者是还活着、可能读过入口的进程,判法见 P12(宁多一个、不少一个):门的持久记录里有它这一生有效的一行(接受过连接或取过 PAC);这个 harness 的进程(按 D51 认)在记下的某一段 on 期间启动的;入口会被在跑的 agent 重读的(路由数据 `rereads`),off 时还活着的这个 harness 的进程;启动在载体之后、历史又不全的;祖先或 Chromium 宿主 / 网络服务是持有者的。取过 PAC 的 Claude Desktop 按同一条算。每个请求都重读开关文件的钩子(DeepSeek 插件)不算持有者,它在途的连接按 [1.6](1.6-cli.md) §3.1 逐条排空。是否还活着按进程表轮询(排空期间每 10 秒),不按开着的连接数:闲着的持有者也算。每一次 `off` 都从它自己当时读的进程表起算:上一轮排空留下的答案(哪怕是「没有」)从不替这一轮回答 `GET /holders` 与「能否退出」,新一轮的第一张表还没读完时就用 off 刚判的那张;轮询停下即忘掉答案,此后 `GET /holders` 现读现判(实验室 G11「守护进程在时 uninstall 退出 0」的成因;守卫 `test/collector/core/proxymode/collector.test.mjs`「a second off answers GET /holders and mayExit from its own table」)。持有者都退出、也没有开着的连接之前,门不关;这段时间门只转发,PAC 只给 app 本来的走法。清单的 `liveness.<h>` 记下 `on_at`、`off_at`、`since`、`door_since` 与 `windows`,守护进程把门认出的进程写进 `door-seen.json`;守护进程不在时命令行读这两份、用同一套判定(`uninstall` 据此拒绝)。macOS 上 `off` 不碰 LaunchAgent(D61:既不 `disable` 也不 `bootout`),也不请守护进程退出(D62⑥):关完门它空转留着、照常应答,下一次 `on` 直接请它开门(不经 launchd 重拉,那里的 `ThrottleInterval` 要 10 s)。Windows 同理:不停监管父进程。驱动模式(Linux)照旧:排空后守护进程自己以 0 退出(那次退出就是摘掉内核的 watch 表与 link)。§1 uninstall 一节的「仍连着门的进程」按本条的持有者判。

③ **PAC**:守护进程在这一组门的同一端口上应答 `GET /trocar.pac`。这扇门不带凭据,所以接受连接时只放行属于本用户的进程(macOS 按 uid,Windows 按 SID),别的拒绝并记录。下面四种情况不写 Claude Desktop 的入口,`status` 说明原因(`not-routed`):系统代理本身是 PAC(写不出 app 本来的走法);当前生效的配置库条目里,用户已经设了自己的出口代理或 PAC(trocar 不执行 PAC,接不上);机器上有托管配置(配置库不生效);app 本来的走法要用户名和密码(不带凭据的门不能把用户的凭据借给本机别的进程,沿用 `entryGate` 的规则)。

④ **`.env` 里的一段**一律放在用户自己同名键的行之后,不注释用户的行;用户的值就是上游第 2 步的原值。Hermes 实测最后一行算数。Codex 读 `.env` 时逐行写进进程环境(实测 `.env` 盖过启动环境),同一文件里后一行算数;实验室格「`.env` 里已有用户代理行」核实这一点。

⑤ **`NO_PROXY` 里「用户原来的值」**:on 之前写入处已有的值,两种大小写合并;再并上操作系统后端给的持久环境变量(Windows:命令行以用户身份用 `reg.exe` 读 `HKCU\Environment` 和 `HKLM\…\Session Manager\Environment`;macOS 没有这一项)。只在某个终端里设的值读不到(§1「没覆盖的」)。

⑥ **上游按连接取**:认出进程之后,按 §1 的五步取;认不出时,先取它自己环境里的钩子值(P7 第 1 步,只读 `TROCAR_PRIOR_PROXY`),没有再走第 2、4、5 步;它的环境读不到时只看第 2 步,没有原值就是 `unknown`,不是直连。任何一步里,值等于 trocar 的某一扇门(本机回环加 trocar 的凭据),都跳过。进程的环境、cwd 读到了就按 pid 加启动时间缓存,一个进程只读一次;读不到的下一条连接再读(P7)。CONNECT 头 `X-Trocar-Upstream` 只对用着会发它的钩子的形态(DeepSeek 插件)算数,值是代理地址或 `none`(dsh 对这个主机本来就直连);别的进程带来的一律不认,记一条。

⑦ **进程标记**(`run/trust/<pid>`)在 macOS / Windows 不再用。DeepSeek 插件加不上根时,不把连接交给门,连接照 dsh 原来的走法;`status` 报「开着但没经过门」。Linux 的标记照旧。

⑧ **证书变量从哪读**:靠证书变量信任的形态,来源由描述符写明,**按这个 agent 自己的先后列**,引擎取第一个设了的。Claude Code 把 settings 的 `env` 盖在进程环境上(`Object.assign`),所以它的先后是:项目本地 settings、项目 settings(在进程的 cwd 下)、用户 settings,最后才是进程环境(macOS 读启动环境,Windows 读当前环境)。「什么时候算 bundled」(`CLAUDE_CODE_CERT_STORE`)按同一先后读。没有固定的「先环境、后配置」。本条取代 §1 解密一节「引擎先读它环境里那个变量指的文件」的读法。

⑨ **被遮住的根**:用户用某个设置把信任库整个换掉时(Codex 的 `SSL_CERT_FILE`、bundled 的 Claude Code 的 `NODE_EXTRA_CA_CERTS`、项目 settings 里改的这些),引擎读那个设置指的文件;里面没有 trocar 根,就只转发、留记录(`ca-not-in-file`)。引擎只看进程环境、进程 cwd 下描述符列出的项目文件和描述符列出的配置。Hermes 路由自己的 `ssl_ca_cert`,靠 `install` 的追加和 D51④ 的「信任被拒」兜底。项目 settings 里设了自己的代理、绕过了门的,`status` 报「开着但没经过门」并点名可能的原因。

⑩ **拦住采集的用户设置**(Z-Code 的三种、Claude Code 的托管设置、Claude Desktop 的托管配置)写在描述符的 `blockers` 里,用三种数据之一指位置:环境变量、文件里的键、托管策略(macOS 的托管偏好 plist、Windows 注册表里的策略键,只读描述符声明的键)。命中时,这个形态不写入口,`status` 点名是哪一处。

⑪ **`on <harness>` 的前提**:这个 harness 的 `install` 项都在,而且没被改(含包装的哈希)。不成立时,只拒绝这一个 harness,提示再跑一次 `trocar install`;`install` 幂等,只补缺的。

⑫ **Kimi VS Code 扩展**:按 §1 第 1 类,`on` 写 VS Code 的 `http.proxy`,不用点名;只在这个形态装着时写(描述符 `present`:扩展目录在),只装了 Kimi 命令行的用户,`on kimi-code` 不碰 VS Code。整个扩展宿主都走门:`on` 的回执和 `status` 写明「VS Code 里所有扩展的连接都经这扇门(只转发)」(`harness-note`,由形态的 `hostTree` 生成,任何宿主型形态同理)。引擎只解密 Kimi 的主机,用 [4.8](4.8-win-collector.md) OPEN 22 定下的主机集,其余连接只转发。这回答了 §1 的「只解密 Kimi 主机的办法没定」。

⑬ **叶证书**的到期不晚于签它的中间证书;换中间证书时,清掉叶证书缓存。满 6 天重签失败时(例如没有图形会话、密钥不在),继续用当前这张,记一条 `cert-intermediate-unavailable`,每小时重试;当前这张到期后门只转发,直到签出新的。Linux 不签中间证书,叶证书照旧由根直接签。

⑭ **门验上游证书**用这个 agent 自己的信任集,去掉 trocar 根:agent 的来源是替换型的(`SSL_CERT_FILE`、`caCertFile` 这类),就只用那个文件;否则用描述符写明的基底(系统根含用户级根,或 Node 自带的根)加上追加型来源指的文件。描述符没写的,用并集(系统根、Node 自带的根、守护进程自己的 `NODE_EXTRA_CA_CERTS`、这个进程证书变量指的文件)。

⑮ **macOS 的原生部件**:签名助手、读启动环境的小程序、列本用户 TCP 套接字的小程序,各一个,预编译好的通用二进制随仓库提交,测试钉住 sha256;`npm pack` 只拷贝,不重编;重编是一次专门的提交,同时改钉住的值(因为改了以后钥匙串会再要一次登录密码,R3-M2)。`install` 先用新文件名写入、再改名,不原地覆盖;已装的助手哈希不同时,只在交互运行的 `install` 里替换,并当场签一次,让密码框在前台出现,不落到后台守护进程上。Developer ID 签名未定(§1「没覆盖的」)。

⑯ **Windows 的密钥操作**是一次性的 PowerShell 脚本,不进常驻助手。常驻助手仍然只读,只多一个动词:读进程环境、当前目录和创建链。包装在 `install` 时用系统自带的 `csc.exe` 编译。Smart App Control 开着时不放包装,`status` 报 `smart-app-control`。包装只用于「安装目录里只有一个原生可执行文件、agent 自己的更新按文件名换掉它」的命令行(描述符 `layout: 'native-binary'`);包管理器生成的 `.cmd` / `.ps1` / sh 启动脚本不适用,`status` 报 `not-users-file` 并写明原因。

⑰ **v2 清单**(本分支之前的构建写的):任何命令(含 `install`)都在写任何东西之前拒绝,连 `~/.trocar/bin/trocar-off` 也不覆盖;退出 1,点名撤 v2 的工具:先是本分支之前 `main` 上的 trocar(`trocar off`,再 `trocar uninstall`),没有时用机器上的独立撤销程序(Windows 印成 `node "<路径>"`)。先撤干净,再 `trocar install`。这取代「各已知装机都证明干净之前保留旧种类的撤销代码」的条件:拒绝在一切写入之前,点名的构建还带着那些撤销代码。

⑱ **原因码**:沿用 `entry-changed`(包装被盖掉等,命令是 `trocar install`)、`config-after-start`(进程早于证书装上)、`var-missing`(必需的来源没设,或基底是 Node 自带的根而一个来源都没设)、`ca-not-in-file`(证书变量指的文件里没有 trocar 根)、`engine-port-taken`、`harness-note`(描述符生成的提示:宿主型形态、已知影响、说明清单 `notes`)、`trust-rejected`、`smart-app-control`(Windows 不放包装)、`not-routed`(带原因)。新增 `cert-key-missing`、`cert-intermediate-unavailable`、`prior-proxy-unknown`、`not-users-file`、`not-verified`(形态没验过,或形态里的这个主机没验过)、`not-seen`(只给 `status`:门没见过这一生、历史又不全,P11 `status` 第 4、5 步;不是要重启的码)、`hook-inherited`(插件载体形态的进程从父进程继承了门、自己没跑钩子,P11 第 4 条;不是要重启的码)。macOS / Windows 上不再产生 `opt-in-needed`、`shim-not-on-path`、`not-via-entry`、`needs-admin`、`route-without-ca`、`win-doors-rejected`、`env-unreadable-fill`;`cert-env-not-inherited` 随 (b) 级一起删(从未产生过);Linux 用到的码照留。

⑲ **Claude Desktop 连自己主机的连接**(登录、更新、Code 标签的下载)先只转发,主机列在描述符的 `forwardOnlyHosts` 里;实验室格(开着 trocar 时的登录页、检查更新、Code 标签下载)过一个,就从数据里删一个。这是 D40「默认全解密」在「不断 agent」下的例外,理由是 §1「没覆盖的」里钉证书的风险。

⑳ **OpenCode 1.x 的 npm 残留**:用户原本没有插件时,OpenCode 1.x 为 trocar 的插件在配置目录建 `package.json` 和 `node_modules`,off 后还在;npm 不通时 mac 多等约两分半、win 卡住。这登记为已知影响(描述符 `effects`,[1.6](1.6-cli.md) §3.1、[3.1](3.1-adapter-contract.md)):`on` 的回执与 `status` 写明(`harness-note`),契约测试按描述符的 `effects` 放行这两个路径,别的残留照样判红。trocar 不删它们(是 OpenCode 建的,用户之后可能加了自己的插件)。

㉑ **入口文件不在时**:由描述符的 `absent` 定,建或不写。Hermes 的 home `.env` 不在时不写(`not-routed`):建了它会让检出目录里的 `.env` 从「覆盖」变成「补缺」,改了无关键的优先级;`status` 提示先跑 Hermes 自己的设置。

㉒ **密钥丢了时的 `install`**:清单记着根和根的密钥,保管后端的 `exists()` 却答没有(`cert-key-missing`)时,`install` 换一套根,不拒绝。次序:按清单的指纹撤旧根(系统弹框);在后端生成新密钥和新根,装成用户级根(再弹一次框);再把装着根字节的每个载体按新根重写:`trocar-ca.pem`、Z-Code 的合并包、规则 U 追加进用户文件的每一段 `pem-block`(按标记换掉那一段,用户的内容不动)。重写过的载体,`installed_at` 都改成这次的时间;在跑的 agent 于是算 `config-after-start`,重启后才被解密。旧根的移除被拒或待定时照常往下走:旧根没有密钥,已经失效,`status` / `doctor` 报「孤儿 trocar 根」并给出移除命令([1.6](1.6-cli.md) 附录 A 的 `orphan`),退出 1。守护进程在跑时,`install` 换完根请它立刻重签中间证书、清掉叶证书缓存(同 ⑬ 的换中间证书);不在时,它下次启动就用新根。本条细化 §1 install 第 1 条的两句:「装上以后到 uninstall 都不换」,只在密钥丢了时换,换法就是本条;「不在就报出,提示重新 install」,重新 install 走的就是本条。守卫:CM35。

㉓ **每次遍历从本副本自己的 harness 表出发**:`install`、`on`、`status`、`doctor`、看板和守护进程(开关、`GET /status`、采集健康)只遍历本副本自带的描述符表(`src/collector/harness/` 的描述符;`src/off` 与命令行用 `HARNESS_IDS`,与描述符表保持相等);对表里的每个 harness,读盘上属于它的东西(清单的项、`liveness`、`install.harnesses`、`state.json`、`door-seen.json` 的行、`ingress.json` 的门组)。为表外的 id 写下的记录(由更新的 trocar 写的)这些遍历走不到:不读、不计数、不改、不报出。于是:不带名字的 `on` = 表里、`install` 记下的那些 harness;`status` 的行与计数都是表里的;`on <名字>` / `off <名字>` 只收表里的名字。`off` 与 `uninstall` 的撤销不按表走:清单的项是通用记录(`kind`、`phase`、路径),撤它不需要认出 harness。不带名字的 `off` 按种类撤清单里每个 `phase: on` 的项,并把 `state.json` 里每个 id 设成 off,不论 id;`uninstall` 的「有任何 harness 还开着」也不论 id:清单里还有 `phase: on` 的项、或 `state.json` 里有 `on`,就拒绝并点名(§1「uninstall」;不变式 5:卸载不留残、不断 agent)。没有「不认识的 harness」这个概念:没有为它设的码、回执行或用法错误。依据:一个副本认不出它不认识的 harness,所以不按 harness 读它的记录;撤销只读通用字段。守卫:CM39。
