# trocar · RFC 3.4 — session / fork / 分支识别

> **服务意图(A2)**:意图 ①(按 session 导航回放)+ 顶栏"同名 session 也可能 fork/不同分支怎么显示"(见 [1.2](1.2-shell-layout.md))。
> **受众**:人(核对血缘判定是否可信)+ agent(据此填 [3.2](3.2-normalized-model.md) 的 `sessions` 血缘列)。
> **前置**:各 harness 线上信号强弱不同(见下表,来自已验证调研;D37 起八个);判定逻辑在此,顶栏**视觉**在 1.2。

## Goal
给每条 session 分配**稳定 `session_id`** 并复原**血缘**(parent / fork_of),在各 harness 差异极大的线上信号下尽量可信,并如实标 `confidence`。

session 键是 **harness 约定的读取侧**,以数据写在 `src/dissect/harnesses.mjs`(D37,见 [3.1](3.1-adapter-contract.md));具名查询(`src/query/named/sessions.mjs`)与看板(`sessionIdOf`)MUST 共用这一份。**会话归属只在读取侧算**(D60②):原始层按大小切段、不取 session 键、不按 session 分文件,所以头里的键、Kimi 的 body 键与 Hermes 的合成键在读取侧一样用得上,没有「分片器扫不到」这种限制。

**body 键只从推理调用读(D40)**:上表里「body」一列的键(Kimi 的 `prompt_cache_key` / `metadata.user_id`、Hermes 的 `session_id` / `prompt_cache_key`、`dsh_session_log…`)与 lane / parent / compaction 的 body 线索,只在 `is_llm_call:true` 的记录上读。D40 之前非推理调用的请求体是 `{raw_chars}`,从不给出键;D40 起它们的体逐字存在记录里,若照读,Hermes 一次遥测体里的 `session_id` 就会给它一个 session,同一次调用在 D40 前后归属不同,且同一条记录在不同读者眼里不一致。所以非推理记录(`is_llm_call !== true`)**只由请求头**认 session,与 D40 之前一样;`harnesses.mjs::parseableBody` 是这条规则唯一的实现,查询、信封 adapter 与 `bodyOf` 同用。守卫:`test/dissect/retention-labels.test.mjs`(「F9 — a session key in the body of a call that is not inference …」)。

**血缘**:会话的 `parent_session_id` / `fork_of_session_id` = trocar 采到的这场会话**第一条模型调用**(按步序;只记日志级的调用不留 body,不算)里声明的父 / fork id,按该 harness 行上的两列数据 `parentKeys` / `forkKeys` 读出(取值见上表「父 / subagent / fork」一列;键的形状与 session 键同:头、body 路径,值本身是 JSON 字符串时再取其中一个字段;空值算没声明)。它与标题在同一遍、从同一条已读的记录算出(`src/query/titles.mjs : titleOf()` 经 `hintsOf()`),存在标题表的条目里([4.2](4.2-storage-etl.md) §标题表),`sessions` / `session` 从不为它另读记录;两列都空的 harness 不比标题多读一条。每份带血缘的回答有 `lineage_source`,闭集:`wire` = 读了那条调用,能声明的键都看得到,两个 id 键都在,各是声明的 id 或 `null`(`null` = 那条调用没声明);`no-keys` = 这个 harness 行不声明血缘的键;`unread` = 不知道:还没有可读的模型调用,或那条记录读不回(只有这种在 `errors` 里有一条,D38,表不写),或那条调用的 body 没有整份留下(没存、只存了大小、截断或没收全、WebSocket 消息只存了大小或没解开)而父或 fork 有一类只剩 body 键能声明、没读到值,或这场会话没有 harness 行(没有行就说不出它声明了什么)。body 没整份留下与没有 harness 行是那条记录的定论,照样存进标题表,不报错、不重读。`no-keys` 与 `unread` 两个 id 键都不出现;头键总看得到,所以 body 看不到时只靠头键的类照样是 `wire`。认亲、同名、时间窗这类推测 MUST NOT 填这两个字段;声明的 id 逐字保留,即使它指的会话没被采到;不输出 confidence。依据:字段只说 trocar 采到的第一条推理调用里声明了什么,不是对 harness 本身的断言;不变式 4(不知道不能读成没有:不看 `lineage_source` 的读者也拿不到一个当「没有父」用的 `null`);D78①(与标题同一处算、同一份表,列表不为它读记录)。

**工作目录(项目)**:会话的项目 = 请求自己写明的工作目录。规则是读取侧每个 harness 行上的一列数据 `cwd: [{in:'system'|'user', re} | {key:[…]}]`(默认 `[]`,`re` 的捕获组 1 是路径,`key` 是 body 里只放路径的字段;取值见上表「工作目录」一列),唯一的读者是 `src/dissect/project.mjs : projectOf(rec)`。它只读推理调用的体(`bodyOf`,同上一段 D40 的规则),按规则顺序试:`system` = 这次调用的系统文本,每段单独看:合成键的锚点(见 Plan 合成键),再加 `messages` / `input` 里每条 `system`、`developer` 角色的消息,`user` = user 消息的文本,按顺序。第一个是绝对路径的捕获胜出:以 `/`、`X:\`(或 `X:/`)、`\\` 开头,不超过 1024 个字符,不含控制字符,首尾没有空白;别的一律算没写明。规则为空的 harness 一律没写明,文本里有类似的行也不读。一场会话的项目 = 标题那一遍读过的调用里,按步序第一条写明工作目录的调用写的那个(第一条调用常是不带环境块的小调用,[4.2](4.2-storage-etl.md) §标题表);它从不用来归组,也不按 pid 或连接取。`project_path` = 那个字符串逐字,没写明为 `null`;`project_slug` = 它 UTF-8 字节的 SHA-256 前 12 位十六进制,没写明为 `_unresolved`。MUST NOT 拿进程的 cwd 补:信封只记 pid / exe / agent(D10),一个守护进程同时服务多场会话(见「关键区分」)。守卫:`test/dissect/project.test.mjs`。

## Plan(选定方案 + 取舍)
**选定:分级可信度 · 显式优先 · 缺失合成。**
- **Codex**:fork 由 `forked_from_thread_id`(见上表)建 `fork_of_session_id`(`confidence=high`);这个 id 是线上声明值,与这场会话自己的 session 键不同,原样保留,不解析成已采会话。Codex 不声明父。
- **Anthropic / CC**:`native_id`=会话头;子 agent 的 lane 判定见上表;CC 不声明父(`no-keys`),trocar 不靠认亲、匹配或推测给它设 `parent_session_id`(守卫:`test/dissect/harnesses.test.mjs : "hints: every declared parent / fork key gives its id; none is guessed"`);compaction 优先用 `x-cc-compaction-request` 头(high),缺头才按 message_count 大幅骤降推断(medium,见「关键区分」);compaction 标在 `calls.compaction`(**不是 fork**)。
- **合成键(`synth: true` 的 harness:Hermes 自定义端点;Kimi 缺 body 键时;pi 的 anthropic-messages / chat-completions)**:**合成 `session_id`** = 同一 harness、同一系统提示里的一条消息链 + 时间窗;进程 / 连接 MUST NOT 参与切分;`native_id=NULL`、`confidence=low`;**先对真实抓包核对再定合成键**。dsh 有原生 id,不合成。
  - **当前默认(规则只在 `src/dissect/synth-key.mjs` 一处)**:同一 harness、首个系统文本(Anthropic `system` / Responses 的 `instructions` 或 `input` 里第一个 system / developer 项 / Chat 开头的 system 或 developer 消息 / Gemini `systemInstruction` 的各段;没有就按空串算)的 SHA-256 相同的无键调用是一组;一组里可以同时开着几条**消息链**,一条链是一场 session。调用的历史 = `messages` 的各项,没有时是 `input` 的各项(`input` 是字符串时算一项),再没有时是 Gemini `contents` 的各项;比较时每项去掉所有层级的 `cache_control` 键(它在线上逐次挪位置)。按序对每次无键调用:
    1. 它是该 harness 的压缩请求时,先照下面「按内容认亲」找归属。
    2. **延伸**:它的历史以组里某条链最近一次调用的整段历史为前缀(相等也算) → 归入这条链,不看时间窗;几条都中时取最长的那条,同长取最近一次调用更晚的。依据:历史里整段带着另一次调用的历史,按构造就是同一场对话的下一轮,中间停多久都一样;第 3 步、第 4 步与按内容认亲靠的是推测,仍只看距上一条调用 ≤ 30 分钟的链。链为延伸开着的界见下「有界」:最近一次调用过了 24 小时、或被同一 harness 的链数上限挤掉的链不再被延伸,之后的调用照下面几步走,多半读作新链。
    3. **改过的历史**:先看调用还留着哪条链的项:它最后 12 项(system 与 developer 项不算,组里每个 agent 都带)里至少 2 个不同的项,逐字节等于(不看 `cache_control`)组里某条链最近一次调用最后 12 项里的项,其中要有那次调用的最后 2 项之一,而这些相同的项不算组里别的链(过了时间窗、项还没丢的也算)也有的 → 归入这条链,取相同项最多的,并列时最近一次调用更晚的胜。harness 就地改较早的项(实测 Hermes:有时改工具结果,有时改模型的消息)、或压缩时留下几轮,都在这里接上:累积哈希从改动处起全变,没动过的项不变。从两轮以前 fork 的只留着分叉之前的项,没有最后 2 项,读作新链,被 fork 的链不受影响;从最后一轮 fork 的,字节上和改了最后一条消息一样,算同一条链;「Done.」这种别的 agent 也说过的项不算数;开场相同的两个 agent 只共一项,不相连。否则看下面的压缩证据:压缩换掉一条链的历史,这条链此后不再从旧历史延伸;并发的新 agent 则在别的链旁边开新链。调用到来的那一刻还看不出「此后不再延伸」,所以那一刻由 harness 的压缩证据加内容认亲定:一次不延伸任何链的调用,候选链是组里在**等压缩**的链(该 harness 的压缩请求已按内容认亲归给它,之后它还没有调用),以及——这次调用自己带着该 harness 的压缩文本标记时(标记在历史里也算,如 Hermes 压缩之后的那一轮)——组里每条链;只看距上一条调用 ≤ 30 分钟的。与它共同的 user 文本指纹最多、且至少 2 个的候选链(指纹同「按内容认亲」;并列时最近一次调用更晚的胜)认领它;这次调用不带压缩标记时,只数它第一条 user 文本以外的 user 文本给出的指纹:第一条 user 文本是新 agent 也带的开场(同一份系统文本的 agent 常共用一段开场白),等压缩时新起的 agent 只有它,不算改写的证据;压缩后的调用带着原链后来几轮的 user 文本(pi 留下的最近几轮);带标记的调用全数,标记本身就是改写的证据。认领后它归入那条链,那条链的历史换成它的,不再等压缩。既没留下项、也没有压缩证据的改写,或认不上的,读作新链。
    4. 调用读不出历史(没有 `messages` / `input`,或没存体)时无从判延伸:归入组里最近一次调用最晚的那条链,组里没有开着的链才开新的。
    5. 都不中 → 新链、新 session。键 = `synth-<harness>-<哈希前 12 位>-<首条调用的 UTC 时间 YYYYMMDDTHHMMSSZ>`;同组另一条开着的链已占了这个键时,后面加 `-2`、`-3`……取第一个没被占的。
    - 同一系统提示的并发 agent(例如工作流里的多个子 agent)因此各是一场 session,不是一场 session 的车道:字节里没有把它们连到父会话的线索,归成一场就断言了字节没给出的关系(不变式 4)。带父会话线索的 harness 照 Claude Code 的做法分车道(上表「父 / subagent」列)。
    - 系统文本逐轮变化的调用(Hermes 同一任务里系统文本变了的轮次)落在不同组,这条规则不把它们并回一场。
    - **有界**:段索引每条无键调用只存它历史的最多 12 个累积哈希(各 16 位十六进制,按前缀长度排):历史最后 4 项处各一个(最后一个覆盖整段历史),再往前只存轮界处的——轮界 = 模型输出开始的地方(下一项是 `assistant` 或 `model` 角色,或 Responses 的 `reasoning` / `*_call` 项,而这一项不是),按格式认,不按产品;前一次调用正停在那里,不管那一轮模型返回了多少项(一条 assistant 加 N 个并行工具结果只占一个);另存最后 12 项各自的哈希(各 8 位十六进制)、一个「带压缩标记」的标志和「第一条以外的 user 文本给出几个指纹」的计数,不存消息文本;所以一次调用比链多出的历史既超过 3 项、链的末尾又不在它存下的轮界上(多出 8 轮以上,或停在轮中间)时认不出延伸,读作新链;续传(`previous_response_id`)不带前序,同样读作新链。读取侧每条链存最近一次调用的整段历史哈希、最后 12 项的哈希、是否在等压缩、和有总上限的指纹;最近一次调用过了 2 × 30 分钟的链只留整段历史哈希(此后只有第 2 步读它;没有这个哈希的链整条丢掉),过了 24 小时整条丢掉。每个 harness 最多同时开着上限那么多条链(无键的与带键会话里的一起数),开新链时满了先丢最近一次调用最早的那条;上限 = 真实采集上一个 harness 在任一 24 小时里开着的不同链数之最的 2 倍,向上取到 2 的幂。所以读取侧的状态有界,与采集的总量无关;被丢掉的链之后的调用读作新链,与过了 24 小时的一样。按回复认亲(见下「按内容认亲」)同样不存文本:一段文本按指纹的窗口与抽样取窗口(32 个字符一个窗口,哈希的低 32 位落在 1/8 抽样上的留下),每个窗口记 64 位哈希;段索引为每条带回复的调用存一项:窗口数 n、前 3 个与后 3 个窗口、整串窗口的 64 位摘要(256 个字符的回复平均 28 个窗口,不到 6 个的回复不存);压缩请求一侧用它 user 文本末尾的窗口,按顺序,有上限(压缩请求里越晚的回复越靠后),上限之前的回复认不出;取这些窗口只读 user 文本末尾的一段,每条请求读的字符数有固定上限,与请求多长无关,这一段里的窗口不到上限时就用读到的那些,这一段之前的回复同样认不出。这些窗口不进段索引、也不常驻:行表的规则走到一条压缩请求时,从原始记录读回这一条(一次寻址,与 `session` 读记录同一条路)现算;读不回时它不由回复定(按指纹认),并照 D38 报出。「整段含着」= 请求的窗口串里有一段从这项的前 3 个窗口起、第 n − 2 个起是它的后 3 个、这 n 个窗口的摘要等于它的摘要;从前往后找,前后 3 个窗口都对上、摘要却不等的位置(窗口反复重复的一段,或改过同样长度的副本)到第 8 处就认作不含,所以一段回复最多核 8 次摘要,在它前面有 8 份以上这样改过的副本时整段的那份认不出。误配的界:不含这段回复的请求要碰上 6 个窗口哈希和一个摘要才误配,一次请求误配某段回复的概率不超过「请求窗口上限 × 回复上限 × 2⁻⁶⁴」(现行常量下小于 2⁻³⁸);改过的副本只在两个相邻窗口之间改了 k 个字符、又没多出一个抽样窗口时认作整段,概率 (7/8)^(k+31),不超过 1.4%;第一个窗口之前、最后一个窗口之后的字符不核对。读取侧每个 harness 最多记上限那么多段回复(同一段文本一项,记它最近的几个归属),满了先丢最早记下的那段;上限 = 真实采集上一个 harness 在任一 24 小时里记下的不同回复数之最的 2 倍,向上取到 2 的幂。常量只写在 `src/dissect/synth-key.mjs`。
    - 进程与连接不参与。看板与查询按同一段内顺序给键,段与段之间续用上一段结束时的状态,同一份抓包两边得到同一组键;sessions 文档与会话 meta 带 `session_synthesized: true`,看板 chip 标「按推测归组」。
  - **带键会话里的消息链(harness 行写了 `chainLane` 的;Kimi 写 `aux`)**:有的 harness 把主对话和它另开的 agent 放在同一个会话键下,又不声明哪次调用是谁的。这样的会话里,每次没有 harness 声明 lane 的推理调用照上面第 2–5 步(不做第 1 步的按内容认亲)归一条消息链,链只在「这个会话键 + 这次调用的首个系统文本」里找;段索引为这类调用存系统文本的哈希与消息链(同上「有界」),读取侧给出它的链,即 `lane_key`。会话不因此变成按推测归组(`session_synthesized` 不变)。
    - **主系统文本** = 会话里到此为止消息数最多的那次调用的系统文本(并列时不换:取按记录顺序先到这个数的那次调用,所以与读取侧收到调用的先后无关;读不回、记成失败的调用不计),随会话增长重新判定:采集可能从会话中途开始,看到的第一次调用未必是主对话的,而主对话是会话里历史最长的那一路。主系统文本一换,该会话的车道从头重新折叠,查询与看板同一份判定。
    - 系统文本是主系统文本的调用归 `main`,不论它在哪条链上:harness 自己的压缩把历史整段改写(例如 25 条变 6 条),系统文本不变,仍是主对话的一轮,由主车道上的骤降判定标出。别的系统文本的调用归 harness 行写的 lane(Kimi:`aux`),一条链一条子车道(延伸 → 同一条;新的历史 → 新的一条;同一种 agent 起两次是两条),各自判 compaction、各自做缓存基线,所以主车道不会因为夹进一次另开 agent 的短调用读成骤降。
    - 车道只在每次调用一条 lane 的线格式上分(Chat Completions、Responses、Gemini):Anthropic Messages 线上这类会话的调用照旧全在 `main`,段索引照样给出它们的链。还没有采到这类 harness 在这条线上的会话,不为没测过的形状写规则。
    - harness 声明的 lane 提示(上表「父 / subagent」列)总是优先。这些调用不记 `subagent`、不建父血缘:字节里没有把它们连到主对话的声明(不变式 4)。规则以 harness 行的数据开关,代码里没有按产品、按工具名的分支。
  - **按内容认亲(无键的压缩请求)**:一次没有会话键的推理调用,若它本身就是该 harness 的压缩请求(上表 compaction 列的头提示,或文本标记落在它自己的某一段系统文本里;每段单独看,因为 OAuth 线上 pi 在自己的系统提示之前还放一段 Claude Code 的身份段),先按回复认,再按 user 文本指纹认。**按回复**:压缩请求把要丢掉的那段对话逐字写进 user 文本,其中多半是模型早先的回复,而会话一侧的指纹只取 user 文本。同一 harness 每次推理调用(带键与无键的都算)的回复文本(产品读出的回复文本,即看板显示的那段)空白折成一个空格后至少 256 个字符的,连同这次调用得到的会话键记下:带键的调用记在它的键下,无键的记在它归入的会话下,没认回会话的压缩请求自己的回复不记;同一段文本记在几个会话下,就有几个归属;最近一次记下已过 24 小时的回复不再参加。压缩请求的 user 文本(按顺序以一个空格相连,空白折成一个空格)整段含着记下的回复时,取其中最近一次记下的那段:它只有一个归属 → 归入那个会话;有几个归属,它一段说明不了什么:只在这几个会话里比,各数这次请求整段含着的、记在它下面的不同回复有几段,最多的唯一一个胜,仍并列就不由回复定。带键的会话与合成的会话一样参加,不看 30 分钟的时间窗。回复定不了的,**按指纹**:在同一 harness 里最近一次调用距它 ≤ 30 分钟的会话里找归属:带键的会话与合成的会话(每条链)一样参加(它自己那组系统提示的链除外)。两边的指纹都取自 user 角色消息的文本(`messages` / `input` / Gemini `contents`;`input` 是字符串时算一条),空白折成一个空格:按固定宽度的字符窗口取片段、求哈希,只留落在固定抽样上的哈希。两边用同一条规则,所以一段足够长的共同片段,只要落在两边各自留下的指纹里,就给出共同的抽样指纹:每次调用留的指纹有上限(会话一侧从最新的 user 文本取起),会话攒下的指纹也有总上限、最早的先丢;落在这些之外的共同片段认不回,该调用落回合成键。共同指纹最多、且至少 2 个的会话认领这次调用;并列时最近一次调用更晚的会话胜;否则落回上面的合成键。不论按回复还是按指纹,认回的调用取该会话的键,认回的是合成的会话时,那条链开始等压缩(见上第 3 步),该会话**不**因此变成「按推测归组」(`session_synthesized` 不变:带键的会话仍不是推测,合成的会话因它别的调用仍是推测)。pid、连接与流不是输入。只在 `synth: true` 的 harness 上取指纹,带键与无键的调用都取。文本标记只在历史里的调用不去认亲:标记一旦进了历史,之后每个 call 都带(Hermes 压缩之后的每一轮),那是它所在会话的一轮,不是在找会话的压缩请求;否则同一任务的两条无键会话会因共同的 user 文本被并成一条。带 compaction 提示的调用即使很小(消息少、不带 tools)也算它所压缩那条对话的一轮,不归入后台 aux 车道,所以压缩判定有前一轮可比。认回的压缩请求本身就是这次 compaction 所在的调用:`compaction_from` 是它前一轮的消息数,`compaction_to` 是压缩请求自己的消息数(摘要器的输入),其后的调用以它为基线。窗口、抽样与上限是常量,只写在 `src/dissect/synth-key.mjs`。看板与查询按同一顺序重放,得到同一结果。

**备选(未选)**:① 只按标题/native_id 分组——同名不同分支会**错并**(用户正担心的问题);② 一律靠时间窗合成——丢掉 Codex/CC 的显式高可信血缘。
**取舍**:能拿显式血缘就用(Codex 最强),拿不到降级推断/合成并**如实标 confidence**,让 UI 区分"确证血缘"与"猜测分组"。

## 关键区分（MUST）
- **compaction ≠ fork**:compaction 是**同一条 session 内**的换血(标 `calls.compaction`);fork 是**派生出新 session**(标 `sessions.fork_of`)。二者 MUST NOT 混。没有会话键的压缩请求按内容认回原会话(带键的或合成的,见 Plan 合成键「按内容认亲」);认不回(没有共同片段,或出了时间窗)才落回合成键;合成键的延伸(第 2 步)不看时间窗,压缩之后停了一阵、历史仍整段接着上一次调用的,照样接回原链。
- **「骤降」怎么算:harness 的显式标记 / 请求优先,否则只有大幅下降才算**:一个 call 是不是 compaction,按此次序判,**查询与看板共用一份判定(`compactionVerdict`),没有第二套规则、没有可注入的阈值**:① harness 的显式请求 / 头提示(高,见上表;lane 的第一个 call 上也算);② harness 的文本标记,只认**上升沿**(中;标记一旦进了历史,之后每个 call 都带,lane 的第一个 call 没有前驱也就没有上升沿);③ 都没有时,**只有消息数的大幅下降才算**(中):比同 lane 上一个 call **少 6 条以上、且不到它的 70%**(CC 前言的一个例外见下一条)。小幅回落**不是** compaction——真实 CC 会话的主 lane 先有一次 58 → 55(不是),随后才是 55 → 4(是)。lane 的第一个 call 没有前驱,不靠骤降判定,`compaction_from` 留 NULL,不发明 0。看板与查询对同一份抓包给同一组 compaction、同样的 from → to(守卫 `test/identity/compaction.test.mjs`)。
- **一次压缩只算一次**:harness 标出的压缩请求(判定第 ① 档,`basis:'hint'`)还带着完整历史,摘要回来之后历史才换掉,所以它之后的骤降或文本标记说的是同一次压缩:判定给 `{compaction:false, lands:true, compaction_from, compaction_to, basis}`。「之后」有界:这次请求之后 4 个下了判定的 call 之内(失败的 call 与上下文不明的 call 不占名额,见下文);落地一次就结束,过了界的骤降或标记是一次新的推测压缩,所以很久以后真的一次下降不会被吞掉。落地的这一步(`lands`)不标 `calls.compaction`、不发 `compaction` 事件、不进任何压缩计数、不写「推测」:这次压缩有 harness 自己的请求作证。它发一条 `compaction-landed` 事件,`from → to` 是这次压缩真实的消息数(压缩请求那条 `compaction` 事件的 `to` 只是请求自己的消息数,历史那时还没换),[2.4](2.4-resource-explorer.md) 的压缩行读它。这一步仍是上下文换血的那一步:资源照压缩移出([2.4](2.4-resource-explorer.md)),`cacheBreak.cause` 是 `compaction`([3.3](3.3-cache-model.md))。推测的压缩(文本标记、骤降)没有前面的请求,就在自己这一步算一次。`stats.compactions`、会话信息弹层、问题道的记号与章都从 `calls.compaction` 得出,没有第二份规则;章的边界见 [1.3](1.3-timeline-tracks.md) §章。依据:一场真实会话的 47 个压缩标记里 20 个是这样的重复,合并后 27 次,20 次有 harness 作证,7 次仍是推测。守卫:`test/identity/compaction.test.mjs`。
- **CC 的前言只在它刚出现的那个 call 上算**:规则是:没有标记时,只有消息数的大幅下降才算,取看板当时的阈值;看板当时的判据除了「少 6 条以上且不到 70%」还带一条——CC 自己的「continued from a previous conversation」前言落在最前 4 条消息里时,任何减少都算——它并进共用规则,算作该阈值的一部分。这一条是上面「大幅」规则的例外,只在**前言刚出现的那个 call**(同 lane 上一个 call 的最前 4 条里没有它,这个 call 的有)上算:一次小 lane 上的真压缩可能没到「少 6 条」,前言仍能指认它。前言一旦进了历史,之后每个 call 的最前 4 条都带着它,所以它和文本标记一样**只认上升沿**——否则一次真压缩之后,该 lane 上每一次少一条的回落(30 → 27)都成了 compaction,正是要排除的 58 → 55 那种小幅回落。带着前言的后续 call 若真的大幅下降(第二次压缩),照「大幅」规则判,不需要前言。看板对靠前言判出的那一次标 `preamble+msg-count-drop`,其余的下降标 `msg-count-drop`;查询与看板仍同一份判定、同样的 from → to(守卫 `test/identity/compaction.test.mjs`)。
- **上下文不明的 call 不下 compaction 判定**:message_count 骤降(中)只在前后两个数都是**观测到的**消息数时才算证据。一个 call 的消息数不是观测值的情形:`context_state='partial'`(WebSocket 续传缺前序、自己的请求没存、请求体只存了一部分——[3.1](3.1-adapter-contract.md) §OpenAI Responses over WebSocket、[3.2](3.2-normalized-model.md) `context_state`),或请求体没解出来(`req_body` 是个不能解成 JSON 对象的字符串;这样的 call 读成 `context_state='partial'`,同 [3.2](3.2-normalized-model.md) 对 `req_truncated` / `req_partial` 的读法)。这样的 call **不下判定**(`compaction=false`,`compaction_from` / `compaction_to` 留 NULL,不发明 0),也**不成为同 lane 下一个 call 的比较基线**(链上仍留着上一个已知的数);`previous_response_id` 续传本身永远不是 compaction。harness 的头提示 / 文本标记在这样的 call 上同样不下判定(`compaction_to` 无从填起)。看板与查询同守这一条,否则同一个缺口两边各说各话(不变式 4)。
- **失败的 call 不下 compaction 判定**:失败的请求([3.5](3.5-query-layer.md) §访问模式 ②)什么都没换成:头提示、文本标记、骤降都不算(`compaction=false`,`compaction_from` / `compaction_to` 留 NULL),不记 `evict`,也不开始等落地;它不成为下一个 call 的比较基线,所以重试的 call 看到的上升沿与骤降和失败之前相同,也不占等落地的名额。算新消息的那个计数也一样:失败的 call 只能把它往上推,所以失败的骤降之后 harness 带完整历史继续时,旧消息不重发成事件、不重复进账本;带着新消息失败再重试时,新消息也只算一次。一次失败的压缩请求加一次成功的重试算一次压缩,全部失败算零次。这一条不分证据的种类:pi 的压缩请求靠文本标记认(上表)。判定收 `cur.failed`,下一个 call 的比较基线由 `compactionBaseline()` 给出,查询与看板共用。依据:失败、重试、落地这样三步原先算两次,切出 2、1、2 步的章;失败的头提示给每个资源记移出,而上下文没有变。守卫:`test/identity/compaction.test.mjs`、`test/query/ctx-head.test.mjs`。
- **改写步里的提问**:改写步重发历史,历史里的 user 消息不是这一步有人提问。harness 标出的压缩请求(`basis:'hint'`)是 harness 在说话,不发 `user` 事件。其余压缩步与落地步只看最后一条有文字的 user 消息(与 `aux` 表的 `last` 同一条规则,[2.1](2.1-track-widget.md)):它后面没有别的角色的消息、不是这一步头一条有文字的 user 消息(那是摘要)、也不同于这条 lane 上一次提问,才发 `user` 事件。所以 `chapters[].prompts`、`cols` 的 `user` 位与「第 K / P 次提问」数的是提问。账本与 `observation` 不走这一条,改写步照旧读全部消息。保真边界,这两种情形 `prompts` 少算一条:提问和摘要合在开头同一条消息里时认不出,算摘要;一条 lane 的第一次调用就是 harness 标出的压缩请求时,那一步没有 `user` 事件。守卫:`test/query/ctx-head.test.mjs`。
- **子 agent = parent 血缘**,不是 fork(它是父任务派生的独立上下文流,非分支重来)。
- **session-less 控制面 ≠ session(D9)**:harness 在会话周边发的 telemetry / registry / account / feature-flag 调用**无 session 身份信号**(非推理、且没有该 harness 声明的 session 键;例如 CC 无 `x-claude-code-session-id`)。它们**不参与身份判定、不建 session**:落 `calls.class='control'` + `session_id NULL`(归宿见 [3.2](3.2-normalized-model.md) 控制面投影),顶栏/选择器(1.2)把它们归到独立 `session-less` 分组(见 [2.6](2.6-detail-panel.md) §C)。MUST NOT 为它们合成会话身份、MUST NOT 混进真 session 列表。
- **session MUST NOT 按 pid 或连接切分(D37)**:一个 Codex app-server 守护进程、一个 Hermes gateway 同时服务多个 session;一条 Codex WebSocket 连接跨多轮。没有 session 头的推理调用(Kimi、Hermes)仍是 `class='llm'`,用 body 键或合成键。

## 验收(可跑 check)
- 血缘:OpenCode / dsh 子会话的 `parent_session_id`、Codex fork 会话的 `fork_of_session_id` 等于线上声明的 id(未采到的也逐字);没有声明的会话(同名也一样)两个字段都 `null`、来源 `wire`;不声明键的 harness 与读不回的会话没有这两个字段;压缩会话不得 fork。
- CC:`lineage_source` 是 `no-keys`,不靠匹配或推测挂父;compaction 标在 `calls.compaction` 且**未**误建 fork。
- compaction 之后 CC 前言留在该 lane 每个 call 的最前 4 条里:此后的小幅回落(30 → 27)**不**判 compaction,只有前言刚出现的那个 call 与大幅下降判;查询与看板同结论。
- 上下文不明的 call(缺前序的续传、请求没存、请求体没解出来)**不**被判成 compaction,也不拉低下一个 call 的比较基线;查询与看板同结论。
- 一次压缩只算一次:harness 标出的压缩请求之后的骤降或标记,中间隔 0 到 3 个下了判定的 call,`compaction` 为假、`lands` 为真、`cacheBreak.cause` 是 `compaction`、资源照样移出,`compaction-landed` 事件的 `from` / `to` 是这次下降的真实消息数;隔 4 个的是一次推测的压缩;`stats.compactions` 与行上 `compaction` 的条数相等;推测的压缩不受影响;中间隔一个上下文不明的 call 结论相同;查询与看板同结论。
- 失败的 call:失败 × 重试 × 中间的 call 三条轴生成的车道上,`stats.compactions` 等于成功的压缩次数,没有一步的章,失败的压缩请求不移出任何资源;全部失败时压缩数是 0;`user`、`observation` 事件与账本的 `loads` 和没有失败的同一条车道条数相同;查询与看板同结论。
- 改写步里的提问:每一章的 `prompts` 等于车道操作算出的提问数(首步、有人提问的步、骤降后面跟着新问题的步),压缩请求步、落地步重发的历史不算。
- Hermes(自定义端点):合成键把"同一次任务的连续请求"归成一条 session,`confidence=low` 显式暴露;抓真实数据核对不误并/误分。
- 无键的压缩请求认亲:pi 形状(带键的调用 + 一次带文本标记的无键调用)→ 摘要调用落进原会话、标 `calls.compaction`,该会话不被标成按推测归组;两条并发的 pi 会话各自认回自己的摘要调用;与任何会话都没有共同片段、或在时间窗之外的摘要调用仍是一条合成会话;跨段、删掉索引重建之后、在追写的段变长时,结果都相同;查询与看板一致。摘要请求与会话不共 user 文本、只整段带着会话早先的一段长回复时(openai-responses 线上的带键会话与无键摘要,Anthropic 线上的合成会话),归入那个会话;摘要自己的回复记在它归入的会话下;同一段回复记在两个会话下时它单独不定,带着某个会话另一段回复时归那个会话,只带它一段时按指纹定;短于 256 个字符的回复、只引了长回复开头或结尾的请求、过了 24 小时的回复都不认;两条会话的调用以三种顺序到来,一遍读、在任一处切成两段读、追写的段逐条变长,成员都相同。
- 合成键按消息链:同一系统文本、交错发出的几个无键 agent 各成一场 session,没有一次 compaction 标记(`cache_control` 在调用之间挪位置也一样);一条链里的真压缩(pi 的无键压缩请求加压缩后的调用,Hermes 带标记的压缩后调用)留在原 session、标在压缩那一次,旁边同时有并发 agent 时也一样,各 agent 共用开场白、或在摘要请求与压缩后的调用之间新起一个 agent 时也一样;一轮带回 1、2、8、12 个并行工具结果(chat 与 Responses `input`)时链照样延伸;隔了 2 小时的延伸仍接回原 session,不延伸的仍是新 session;没有压缩证据的改写是一场新 session;整段一遍读、在任一处切成两段读、追写的段变长后再读,成员都相同;段索引里没有消息文本。
- 带键会话里的消息链(Kimi 形状:21 次主对话调用、旁边一条 4 → 6 的另一系统文本的链、一次 25 → 6 的改写):车道是 `main` 加 `aux`;主车道的 compaction 恰是 25 → 6 那一次,另开的链开头不标;`has_subagent` 与 `session_synthesized` 为假;查询与看板一致。Gemini 的对话按 `contents` 与 `systemInstruction` 分组,两场无关的对话不并成一场。
- 每个 harness(D37):各自的 session 键按上表取到(在 [4.6](4.6-process-collector.md) R2 的记录上验);同一 Codex 守护进程上并行两个 session 不被并成一个。
- 工作目录:有规则的 harness 取到请求里写明的绝对路径,逐字;读不到、相对路径、非推理调用 → `_unresolved` / `null`;pi 系统文本里引着的 `Working directory:` 行不算;提问里引着的工作目录行不算;不拿进程 cwd 补。

## Edge cases
- 合成键误并/误分 → confidence=low 暴露,允许人工纠正(记为 Extension)。
- CC `/rewind` 等终端操作(开发者侧,非 agent 动作)在线上如何表现 = **待数据决策 R**(见 [0.0-overview](0.0-overview.md) §待数据决策):待真实 `/rewind` 抓包确认后补判定(疑似 message_count 骤降)。
- 并发多 session 同 harness:靠各自 native_id / thread_id 隔离;合成键的 harness 靠系统提示 hash + 消息链 + 时间窗区分,不靠连接(D37)。

## Risk / 回滚
身份判定是纯函数(记录→血缘);用固化真实记录回归。合成规则改动只影响合成键的 harness(Hermes 等),可独立回退。

## Extensions
人工合并/拆分被误判的 session;更多显式-fork 的 harness 直接接入 fork 树。
