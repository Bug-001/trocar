# trocar · RFC 4.4 — 本地服务(看板的 HTTP 面与控制面)

> **服务意图(A2)**:把具名查询([3.5](3.5-query-layer.md))的文档通过 loopback 交给自建前端;看板是 `trocar query` 的 HTTP 外壳,不是第二条读路径(D59),由守护进程托管(D66)。
> **受众**:人(核对数据只读、控制面的门与不被外部网页读到)+ agent(据此实现守护进程的 HTTP 面与控制面)。
> **前置**:查询集与文档形状在 [3.5](3.5-query-layer.md) 与 [1.6](1.6-cli.md) §4.1 / 附录 C;记录与段在 [4.2](4.2-storage-etl.md);守护进程与它的控制面在 [4.6](4.6-process-collector.md)。
> **决策**:D11(服务端执行查询、HTTP 返 JSON)· D26(控制面的写只调 CLI 同一批函数)· D59 · D61(守护进程登录自启)· D63(查询归守护进程的工作进程)· D64(看板的性能线)· D65(装的生命周期)· D66(看板归守护进程)。

## Goal
守护进程在 `http://127.0.0.1:<port>` 上托管看板:静态文件 + `GET /api/<名字>`(具名查询的文档)+ `GET /control/status` 与 `POST /control/*`,外加挡住别的网页读你语料的 Host / Origin 门和每用户口令。**没有别的东西**。`trocar install` 之后看板一直在(守护进程每次登录都起来,D61);`trocar board` 只是把带口令的网址印出来并打开浏览器([1.6](1.6-cli.md) §4.3)。

## 前置定义(Definitions)
- **数据面** = `GET /api/<名字>`,参数来自 query string,文档逐字段等于 `trocar query <名字>`(验收 V80);带 `stored` 的答案(§存下的答案)是这条查询在 `stored.at` 那一刻的文档加上 `stored` 这一个键。
- **静态面** = 构建产物目录 `src/web/board/` 里的文件(由 `web/` 经 Vite 构建、入库,D75③),发在 `/`(只有一个看板,[1.2](1.2-shell-layout.md) §托管与打开),都从内存里发。浏览器与 CLI 必须用同一个事实的那几个 `src/` 模块(如 `src/cli/words.mjs` 的失败词与原因句、`src/off/token-header.mjs` 的口令头名、`src/off/userinfo.mjs` 遮网址凭据的规则、`src/view/step-order.mjs` 的步序、`src/view/head-cols.mjs` 的 head 位定义、`src/off/harness-names.mjs` 的 harness 注册表)由看板直接 import、**打包进构建产物**:前端不把这些事实抄第二遍(0.1 §2 一个外部事实只写一处),也不为读它们开数据面端点。harness 的官方图标由构建从 `src/off/harness-icons/` 复制进构建产物(D76)。**MUST**:看板 import 的每个 `src/` 模块在 `src/` 内对 import **闭合**、不 import 任何 `node:*`(守卫 `test/web-v2/imports.test.mjs` 逐个读 import 并断言两条);守护进程除构建产物外不从 `src/` 发任何文件,构建产物以外的路径一律 404。静态面的目录是 `createServer({ webDir })` 的参数,默认 `WEB_DIR`(= `src/web/board/`);守护进程只发默认目录,测试可以传另一份构建产物的目录(如 `vite build --mode desk-next` 的临时构建,[1.2](1.2-shell-layout.md) 验收脚注)。
- **控制面** = `GET /control/status` + `POST /control/*`,每个写端点只调 CLI 同一批函数(D26)。
- **门** = Host allowlist + Origin 校验,三个面都过;数据面与控制面另要每用户口令(D26③)。
- **stamp** = 一个名字的答案所依赖的那些**文件的身份**的摘要(不是文档本身的摘要),答案里读了 `now` 的名字再加一个**分钟刻度**;住查询层,是 ETag 的值。

## Plan(选定方案 + 取舍)
**选定(D66)**:**看板归守护进程**。守护进程的事件循环只做五件事:① 从内存里发静态文件;② 用 stat 算出的 stamp 直接答 304,**不唤工作进程**;③ 把 `GET /api/<名字>` 原样转给查询工作进程,与 `GET /query` 同一条路(D63:字节转发,守护进程既不 parse 也不 stringify 大文档;超时只量工作进程的沉默,折叠中报的进度同样算出声(3.5 §读不全不静默);工作进程在已经发出帧头之后退出时,守护进程**中断**这条响应、不以正常结束收尾,读者看到的是没收全的传输,不是一个短了的 200;响应因背压停着超过 `PAUSE_MS`(`service.mjs` 的常量,60 秒)没有 drain:放弃这个读者、断开它的连接(不以正常结束收尾),不记 D38,队列往下走 —— 依据:会话界面不因文件大而闪断、保持稳定,trocar 运行时保持轻量;不变式 4;[1.5](1.5-states-aesthetics.md) K-06;背压上限的依据另有:曾有一个从不 drain 的读者把所有客户端的读卡了 17 分钟);④ 把 `/control/*` 转给工作进程,由它调 CLI 同一批函数;⑤ 原样发出工作进程写好的文件:按白名单的答案文件(§答案文件)与存下的答案(§存下的答案)(依据:D71① + D63①——读文件不是查询)。工作进程在页面加载时 fork,页面还在轮询期间一直活着,页面走了之后闲几分钟退出(D63①)。**D63① 不破**:查询仍不在守护进程自己的循环里算,它每条请求的份额仍是 ≤ 5 ms([1.6](1.6-cli.md) §4.1)。
**外壳只做三件事**:把 query string 变成查询参数、把文档的字节交出去、挡住跨源读取;发答案文件与存下的答案也只是 stat、读、交字节,不解析。**MUST NOT** 在外壳里写第二套取数逻辑、第二套分页、或任何缓存真相。
**备选(未选)**:① **单独一个 `trocar serve` 前台进程**——未选(serve 也应能自启):前台进程要用户自己起,看板就不是「装完就在」,而守护进程已经为 `on` 跨开关机而登录自启(D61),再加一个要自启、要收尾、要开关的常驻件是多一份状态;② **另起一个专门的后端进程**——同上,且没有任何新能力;③ 浏览器内查询引擎(D11 的 (B))——装载与内存代价大、把存储细节推向前端,记为 Extension;④ 只读看板、在改状态处印出要敲的命令——未选(开关要能真开关)。
**端口**:看板的端口与门的端口一起持久在 `~/.trocar/collector/ingress.json`,所以网址稳定、可以收藏(口令在 fragment 里)。**端口由 `install` 选**(第一次选,之后沿用;从 9800 起往上取第一个空着的端口,到 9899 为止,这一段是 `ingress-config.mjs` 里的一个常量;一段都占满时 `install` 把这一项记成 pending 并说原因),守护进程只读、从不另选——与门的端口同一条规矩([4.11](4.11-collector-model.md) §3 ①),所以 `install` 之后不跑别的命令看板就在(验收 12)。守护进程的 `/status`(控制端点)回答带看板监听的端口与状态(`board:{port, state, reason}`,`state` ∈ `serving` · `port-taken` · `no-port`),`trocar status` 据此印 Board 一行、给出 `--json` 的 `board`,地址不带口令([1.6](1.6-cli.md) §3.5 · C.3 · V90)。口令只在控制端点的 `GET /board` 上答(`{port, state, reason, token}`;控制端点本来只有本用户够得到,[4.6](4.6-process-collector.md) §控制面):`trocar board` 经它取口令,所以印出的永远是守护进程手里正在核对的那一份,口令文件被换过也对得上(依据 = 1.6 §3.5「口令只由 `trocar board` 印」+ 本节「口令不进 status」)。
**取舍**:外壳越薄,`query` 与看板越不可能漂移;CLI 与看板只有一个实现要测(V80)。

## 服务形状
- **零依赖 · loopback · 守护进程托管**:只用 `node:http/fs/path`,`listen(port, '127.0.0.1')`。所有响应 `content-type: application/json; charset=utf-8`(静态文件按扩展名)+ `cache-control: no-store`(条件 GET 走 ETag,不走 HTTP 缓存)。
- **压缩归工作进程**:`/api/*` 的请求在 Accept-Encoding 允许 gzip 时,答案由查询工作进程压缩,带 `content-encoding: gzip` 与 `vary: accept-encoding`;守护进程只转字节(D63 ①);`GET /query` 不压缩;控制动词不压缩;304 与 ETag 不变(ETag 的 stamp 段仍只由 stat 算)。依据:D63 ①;会话界面不因文件大而闪断、保持稳定,trocar 运行时保持轻量,随时监测 CPU、内存、I/O、网络上潜在的性能问题;实测一份会话文档 13.7 MB → gzip 后 2.3 MB。工作进程每答一次量自己的 CPU 并随帧头交回,守护进程按名字累计读次数、出字节、工作进程 CPU、最慢一次的墙钟,有读的那一分钟往自己的日志写一行。
- **反 DNS-rebind 门 MUST 覆盖数据面**(2026-07-18 对抗评审实测,**必拒**违反):只设在某一类路径上不算。`Host` 不在 allowlist(`127.0.0.1:<port>` / `localhost:<port>`)或带跨源 `Origin` → 403,什么都不读。
- **门的次序(每个请求都走这一条链)**:Host / Origin → 口令 → 名字 → 方法 → 参数。① Host / Origin 不合格 → 403;② 没带或带错口令 → 403;③ 不认识的名字 → 404;④ 方法:数据面与 `GET /control/status` 上非 `GET` → 405,`/control/` 下不是三个写端点的非 `GET` 也一律 405(那些写根本没有端点,§控制面);⑤ 畸形参数 → 400。**前两步没过之前不读任何文件**(验收 2 与 8 注入 fs 断言零读)。
- **每用户口令(D26③)**:32 个随机字节的 base64url,存在 `~/.trocar/collector/board.token`(0600)里,**持久**——守护进程重启仍是同一个口令,所以看板的网址可以收藏;守护进程托管看板时读它,文件不在就生一个(只有守护进程写它)。`trocar board` 印的网址把它放在 **fragment** 里(`#t=<口令>`):fragment 不随请求发出去,不进服务、代理或任何日志;页面读 `location.hash`、`history.replaceState` 抹掉它,存进看板这个源(`http://127.0.0.1:<port>`,端口持久,见上)的 `localStorage['trocar.token']`;之后不带 fragment 的载入(浏览器历史、收藏、新标签页)从那里读,所以收藏的网址打得开(D66①)。这份存储的暴露面**比那份 0600 文件大**(保真边界,不变式 4):看板这个源上的任何脚本都读得到它,不管端口上的页面是谁发的。守护进程没占着看板端口时——守护进程没在跑,或端口先被别人占了(两者都进 `status` 与持久记录,见下文「端口被占」、D38),Linux 上还有不带名字的 `off` 让守护进程排空退出(D66⑤ 的已知缺口)——同机别的系统账号可以绑上这个端口发一页脚本;用户这时从收藏或历史打开看板,`localStorage['trocar.token']` 就交了出去,而这份口令在重装之前一直有效。页面里的任何措施都挡不住同源脚本读它。这个风险是接受下来的:D66① 要收藏与不带 fragment 的历史打得开,这在上述窗口里与 D26③(口令防同机别的系统账号)相抵,取 D66①;窗口本身由 `status` 照实报出,不静默。存储用不了(隐私窗口、被禁)时,fragment 里的口令照样服务这一次载入,不报错;某个请求回 403 时,页面删掉它存着的那份——只在存着的就是这次发出去的那份时删(别的标签页刚存的新口令不受影响),整页按 [1.5](1.5-states-aesthetics.md) K-30 说怎么用 `trocar board` 拿新网址。每个 `/api/*` 与 `/control/*` 请求用**同一个头名常量**(`CONTROL_TOKEN_HEADER`,住 `src/off/token-header.mjs`;两个秘密不同,头名只写一处)带它,它同时就是 CSRF 口令。**静态面不门口令**——页面得先加载才知道口令,所以前端目录里 **MUST NOT** 有任何采集到的数据(它就是一份静态包)。口令文件随 `uninstall` 一起撤。带了口令的 `curl` 也读得到数据面,没带就读不到——这正是 D26③ 要的(环回不分系统账号)。
- **条件 GET(ETag / `If-None-Match`)**:每个 `GET /api/<名字>` 回 `ETag: "<stamp>"`;请求带的 `If-None-Match` 与它相同 → **304、空体、零语料读、不唤工作进程**。`session` 与 `lane` 回两段的 `ETag: "<stamp>:<version>"`:守护进程只比 stamp 段,相同就照上面独自答 304;不同就转发,工作进程比版本段(该会话自己的 `version(ctx)` 加参数,[3.5](3.5-query-layer.md) §会话读),相同就答 304 并带新的完整标签,花工作进程 CPU ≤ 50 ms、不归约——所以别的会话在采集时,没长的会话照样 304,长了的会话照样 200(依据:D66② 的 stat 304 不变;D69;D62 附近的查询 ≤ 50 ms)。带 `pending` 的答案没有版本段,所以不带 ETag:后台折叠往前走时戳算的文件一个都没变,带了标签就会被戳段 304 在没折完的那份上(依据:不变式 4;本节「漏了一个依赖 = 看板永远显示陈旧数据」;[3.5](3.5-query-layer.md) §归约前沿 看板每次轮询收下新折到的部分)。存下的答案(§存下的答案)同样不带 ETag:它是 `stored.at` 那一刻的文档,戳却是此刻那些文件的身份,带上戳当标签,下一次轮询就被 304 钉在这份旧答案上,刷新落地之后也换不上来(依据:不变式 4;本节「漏了一个依赖 = 看板永远显示陈旧数据」)。stamp **只由 `stat` 算**(大小 + mtime + ctime),**MUST NOT** 先算出文档再 hash(那只省带宽,不省一分计算);**答案里读了 `now` 的名字,把 `floor(now / 60 s)` 也折进 stamp**(依据:不变式 4 与本节下面那句「漏了一个依赖 = 看板永远显示陈旧数据」——时钟就是这些名字的一个依赖,而把它当依赖并不要求读任何语料,所以 stamp 仍然只是几十次 `stat` 加一次 sha1)。它住**查询层**:每个名字在 `QUERIES` 里与 `params` / `run` 并列一个 `stamp(ctx)`;外壳只比字符串——否则外壳就持有了第二份「这个文档依赖什么」的意见,两份一定漂(也违「外壳只做三件事」)。每个名字的来源:

  | 名字 | stamp 算哪些东西的身份 |
  |---|---|
  | `session` `lane` `calls` `block` `segments` `traffic` | `raw/` 里的段名单 + 每个段的 `<段>.ndjson` 与它的封存文件 |
  | `sessions` | 上行那些 + 标题表 `index/titles.json`(表写下之后戳变,新标题不会被 304 挡住) |
  | `overview` | 上行那些 + 每个段的用量旁注 `index/<段>.usage.json`(工作进程补建旁注后覆盖变大;戳不跟着变就会 304 住部分覆盖的答案,[4.2](4.2-storage-etl.md) §用量旁注) |
  | `classes` | 上行那些 + `~/.trocar/classes.json` + `~/.trocar/logs/classes.ndjson` + **分钟刻度**(它的 `counts` 把 24 h / 7 d 对着 `now` 算);`disk` 读整个 `~/.trocar`,它的陈旧同样以这一个分钟刻度为上限(依据:本节陈旧上限——给 `disk` 单独算整棵树的身份要遍历全部文件,一次 304 就不再只是几十次 `stat`) |
  | 任何名字,给了**相对**的 `--since` / `--until`(`24h` 这类)时 | 该名字上面那些 + **分钟刻度**(窗口的两端跟着 `now` 走;给的是绝对时间时不加,窗口不动) |
  | `pricing` | 价格文件(内置的那份,或 `TROCAR_PRICING` 指的那个) |
  | `status` `doctor` | **不带 ETag**:它们读的是机器此刻的实况(进程、信任库、守护进程),不是盘上的语料,永不 304 |

  漏了一个依赖 = 看板永远显示陈旧数据而且什么都不报(违不变式 4),所以验收 9 要每个依赖各一个用例。一次 304 只花几十次 `stat` 加一次 sha1,不读记录、不返体。

  **陈旧上限**:只因为时钟走了而过期的答案,最多陈旧**一个分钟刻度(≤ 60 s)**——下一次轮询(`status` 5 s、别的名字 1.5–30 s)落在新刻度上,stamp 就变了,于是「一条新记录都没有、但记录正在滑出 24 h 窗」这件事照样会被看到。刻度取 60 s 是因为看板上没有一个数的精度细于一分钟(相对时间、窗口端点都按分钟显示),取更细只会让 304 白白失效。
- **会话读的路由**([3.5](3.5-query-layer.md) §会话读,参数与 `trocar query` 同名):`GET /api/session?id=…&since=…&before=…&limit=…&head=1`(骨架;`since` 与 `before` 同给 → 400;`head` 见 §会话读「`session --head`」)· `GET /api/lane?id=…&lane=…&from=…&to=…&ledger=…&pack=<n>.<part>&tail=<part>`(一条车道的一页,或一个包 / 尾)· `GET /api/block?ref=…&ref=…`(重复的 `ref`,按次序一个 ref 一项)。外壳只把 query string 变成这些参数,校验归查询层。
- **答案文件**(第五件;依据:D71①——冷开 0.2 s 里放不下 fork 与模块载入;D63① 不破——读文件不是查询;D66② 的 stat 304 同一条思路):`GET /api/d/<f>?id=<会话 id>`,`f` 只认正则白名单 `^(head|p\d+\.(main|rest)|open\.(main|rest))$`,分别是 `ctx/<k>/` 里的 `head.json.gz`(不在时 `head.pending.json.gz`:还在折的 head,[3.5](3.5-query-layer.md) §会话读「`session --head`」)、`p<n>.<part>.ndjson.gz`、`open.<part>.ndjson`(`k` 由 `id` 算,[4.3](4.3-parse-index-cache.md) §4「目录」);门、口令与次序同 `/api/*`,白名单外的 `f` → 404,缺 `id` → 400。
  - 守护进程只 stat、读、交字节:head 与包 `ETag: "<size>-<mtimeMs>"`,`If-None-Match` 相同 → 304,还在折的 head 也一样(主 agent 定;依据:§条件 GET「带 `pending` 的答案不带 ETag」守的是戳段在折叠推进时不动的具名回答,head 文件则在它的 `pending` 每动一次——第一片、每 512 条、折完——都整份重写,标签随之换,所以 304 不会把读者扣在旧的折叠上,不变式 4);head 与包按存的 gzip 原样发、带 `content-encoding: gzip`,请求不收 gzip 时当成文件不在(下一条);`open.*` 认 `Range: bytes=N-`:`N` < 大小 → 206 带 `content-range: bytes N-<size−1>/<size>`,`N` ≥ 大小 → 416 带 `content-range: bytes */<size>`;不带 Range → 200 整份。
  - **尾的代标签**:`open.*` 的 200 / 206 / 416 都带 `ETag: "<ino>-<birthtimeNs>"`(打开的那个文件的 `fstat`,bigint)。它标的是文件的**代**、不是内容:工作进程只追加时不变(读者手里的字节仍是文件的前缀),整份重写(临时文件 + 同目录 rename,[3.5](3.5-query-layer.md) §谁执行它「答案文件」)时换。Range 读认 `If-Range: <标签>`(强比较,RFC 9110 §13.1.5):相同 → 206 / 416 如上;不同 → 不理 Range,200 整份带新标签;不带 If-Range → 照上一条。尾不认 `If-None-Match`(代标签相同时内容仍可能长了,从不 304)。取 `ino` 与 `birthtime` 两者:darwin(APFS)两者都随 rename 换、追加不动;win32 上 Node 的 `ino` 是 NTFS 文件 id(高 16 位是序号,可超过 2^53,所以用 bigint),`birthtime`(创建时间)会被 NTFS 的名字隧道带过去(15 s 内换进同名的文件继承旧的创建时间),靠 `ino` 分开;Linux 上旧文件释放后它的 `ino` 可被后来的新文件复用(两次重写之间读者没读),靠 statx 的 `birthtime` 分开(文件系统不给 birthtime 时为 0,只剩 `ino`)。依据:不变式 4(手里的偏移恰好落在新文件的行界上时,按偏移接着读会把另一份渲染的中段静默当成新行)+ D71②③(接着读仍是一次 Range、守护进程不唤工作进程)+ RFC 9110 If-Range。
  - 文件不在 → 当成对应的具名查询(`session --head` / `lane --pack <n>.<part>` / `lane --tail <part>`)转给工作进程,答的字节与这个文件的相同。head:工作进程答 `session --head` 时写下 head 文件,守护进程等它答完,再按上面几条从这个文件答(同一次 open、fstat、读;工作进程那份字节不交出,所以这次转发不要 gzip),所以这一读就带文件的 `<size>-<mtimeMs>`,同一状态的下一轮条件读得 304;答完文件仍不在(没有这场会话,或没写成)→ 这次转发的回答就是这一读的答案:守护进程留着短的回答(「没有这场会话」只有几百字节,上限是 `server.mjs` 的一个常量),原样交出,不再转发;超过上限的不留在内存里,再转发一次、原样交出。读者在等的时候走了:与别的转发一样,排着的这一单不跑([3.5](3.5-query-layer.md) §服务队列)。包与尾:答案原样交出。转发出去的答案文件都不带 ETag:工作进程的版本标签不是文件的标签,带着它的条件读在文件上永远对不上(包只读一次、不做条件读;尾由折叠的切片写,`lane --tail` 的回答不写它,读者手里没有代标签时下一次不带 Range 整份读;缺尾只在尾还没写时发生,只多一次整份读)。主 agent 定,依据:不变式 4(字节与标签出自同一份文件:工作进程答完之后又写了新的一份时,交出的是新的那份和它自己的标签,读者不会拿着新标签停在旧字节上);D71②③(打开会话之后的轮询从第一轮起就是 304,不再整份重读一次 head);工作进程的版本标签(§条件 GET)是 `/api/<名字>` 两段 ETag 的一段,对答案文件的条件读不起作用,而且新起的工作进程在这次回答里把折叠前沿推了一步时它根本没有版本标签。
  - 响应头 `x-trocar-tip`:index keeper 为这场会话最近索引到的 ≤ 64 个模型调用 rid,旧到新,空格分隔;只对带会话键的会话有(Edge cases)。客户端凭它看出 head 落后几条([1.5](1.5-states-aesthetics.md) K-32)。
  - 文件都在时一次 head / 包 / Range 读不 fork 工作进程,只有一个例外:读到的是还在折的 head(`head.pending.json.gz`)时,守护进程照常答(200 或 304),再调服务的 `follow(id)`,它像 kick 一样送 `{follow: id}`、没有工作进程就 fork 一个([3.5](3.5-query-layer.md) §谁执行它「后台抽取与归约」;主 agent 定,依据:3.5「从没折过的会话……打开时才折」+ D66②「工作进程在页面加载时 fork、页面轮询期间一直活着」;不 fork 只为首屏快,D71①,文件仍是立刻交出);守护进程启动时给工作进程送一次 `sweep`([3.5](3.5-query-layer.md) §谁执行它「答案文件」)。
- **存下的答案**(`sessions` 冷时也立刻答;依据:[1.6](1.6-cli.md) §4.1 `sessions` ≤ 0.5 s 的冷启动线——冷的或被挤的工作进程答 `sessions` 要付 fork、模块载入与整份段索引的一次解析,在 1.3 GB 的语料上实测 1.3–3.8 s,机器负载高时一次 7.2 s,温的工作进程 0.2–0.6 s;D63① 不破——读文件不是查询):一个名字可以在 `QUERIES` 里声明 `stored(params)`,即这组参数的答案要不要存下([3.5](3.5-query-layer.md) §谁执行它「存下的答案」)。现在只有 `sessions` 声明,且只在每个参数都是 `limit` 或 `after` 时为真(看板翻的不带窗口的列表);带 `since` / `until` / `harness` 的照常转发。
  - **次序**:门 → 口令 → 名字 → 方法 → 参数 → stamp / 304(不变)→ 本条 → 转发。本条只在三样都成立时走:参数可存(`stored(params)` 为真)、请求收 gzip、存下的文件在(`index/stored/<名字>.v<STORED_V>.<键>.json.gz`,3.5);文件不在(第一次跑、索引被删)→ 照常转发,答案不带 `stored`。
  - **刷新**:三样都成立时,守护进程问服务的 `refresh({name, params})`。刷新按名字算、不按页算:这个名字有一次刷新排着队或正在跑 → 为真,不再排;没有工作进程 → 为真,服务为这组 (名字, 参数) 排一次刷新(由它 fork 工作进程);工作进程活着而行表还没读完 → 为真;为真时守护进程立刻从文件答。其余(工作进程温着 = 送过 `{rows: true}`([3.5](3.5-query-layer.md) §服务队列),这个名字没有刷新在等,0.2–0.6 s 答得出新的)为假 → 照常转发,别的页由温着的工作进程新答,它们存下的文件随之重写。所以一次冷启动至多排一次刷新,它落地之后每一页都转发、都是新的(依据:按页去重时,看板每 1.5 s 读遍多页的列表,工作进程跑完各页的总时长超过 1.5 s 就总有一页又在等,列表永远停在旧答案上、工作进程不停地跑 `sessions`;不变式 4)。主题在冷却期里([3.5](3.5-query-layer.md) 失败期)时 `refresh` 为假:转发照常答 500 带原因,失败从不藏在存下的答案后面(D38)。
  - **答法**:stat、读、交字节:200、`content-encoding: gzip`、`vary: accept-encoding`、`cache-control: no-store`,不带 ETag(§条件 GET);一次 open、fstat、读、close,工作进程同时 rename 进新文件时交出的仍是一份文件的整份字节;不解析、不编码(D63①)。
  - **答案自己说它旧**(不变式 4):文档带 `stored: {at}`,`at` = 这份答案算出的时刻:它是工作进程上次写下的答案,在工作进程算新的那段时间里先交出来;`as_of` 的意思不变([1.6](1.6-cli.md) C.5),所以是 `at` 那一刻的 `as_of`,`errors` 也是那一刻的。看板据 `stored` 就地说明并很快再读(§live-poll;[1.8](1.8-session-library.md) §说明行)。显示这份答案的只有会话库页;别的页面拿 `sessions` 下结论(流量页的覆盖说明 [1.10](1.10-traffic.md)、概览、`#/session/<id>` 链接按 id 找会话)时不用带 `stored` 的回答,隔 1.5 s 再读,直到拿到新的:旧列表里没有的会话不能说成「不在列表里」,旧的数也不静默地显示出来。
- **live-poll**:传输无状态,每个请求独立返当前快照;前端轮询驱动「空 → live 无缝转正」([1.5](1.5-states-aesthetics.md))。间隔:

- **第一次点开会话不落在冷路径上(D64①)**:页面一加载就是一次 `sessions` 刷新(§存下的答案「刷新」):没有工作进程时守护进程 fork 它并让它跑一次 `sessions`——用户还在看首页时工作进程已经温了,而页面的第一次 `/api/sessions` 落在这次刷新跑着的时候,从存下的答案答,不排在它后面;工作进程已经温着时不再跑;工作进程在页面轮询期间不退。
- **只读**:数据面 MUST NOT 写记录、不删、不改。唯一会落盘的是 `~/.trocar/index/` 里可删可重建的段索引([4.2](4.2-storage-etl.md))与上下文投影、折叠日志、答案文件(`index/ctx/<k>/`)与存下的答案(`index/stored/`),都只有查询工作进程写([4.3](4.3-parse-index-cache.md) §上下文投影;[3.5](3.5-query-layer.md) §谁执行它);写侧只有守护进程(追加)与封存器(无损替换)。服务改写源 = 违不变式 2 → **必拒**。
- **永不 originate 上游请求**:D30 的修改与重发经守护进程的控制端点,不走看板这一面。
- **路径安全**:静态只发构建产物目录内的文件,拒 `..`;读哪些记录文件由查询决定,不由请求里的路径决定。
- **人类标题的来源(保真边界)**:会话的标题 = 这场会话**主对话 lane 的 `task`**(§看板 v2 需要的补充),即采集到的请求里主对话第一次调用的第一句提问,折空白后至多 80 字;模型调用里一条主对话调用都没有时取按步序第一个子代理车道的 `task`;每条带 `title_source:'wire'`(取自采集到的字节,但只是一个截短的便利标签,不是原文)。`sessions` 的标题来自标题表([4.2](4.2-storage-etl.md) §标题表,读法见 [3.5](3.5-query-layer.md) §访问模式):表上没有的会话当场读它最前面的几条模型调用算出来再答,所以回答里没有「还不知道」;每条模型调用都读过而没有提问时 `title` 与 `title_source` 都是 `null`(看板说没有采到提问);决定它的记录读不回时 `errors` 里有一条、表不写:已有带标题的条目时它照旧,来源 `wire`,否则这一次 `title` 是 `null`、`title_source` 是 `unread`(不变式 4 · D38)。`session` 的 `meta.title` 与 `title_source`,head 与 tier 0 都一样,都出自 `titleOf`:一条规则、一段代码;`unread` 自己不让 head 写。被测 harness 自己的本地存储不读(依据:D20 与 D78①(为什么放标题表不放段索引)、不变式 3(每个 harness 一条规则)、不变式 4(来源就地标明))。
- **provider 中立**:响应只讲 [3.2](3.2-normalized-model.md) 的 canonical 词汇,provider 原生字段只在 `extra` 里。
- **健壮性**:看板这一面出的 `uncaughtException` / `unhandledRejection` 记日志但不弄倒守护进程(仪器要在长采集里活着)。**端口起不来不拦采集**:守护进程照常转发 agent 流量,这件事进 `status` 与一条带原因的持久记录(D38),`trocar board` 印出原因;不偷偷换端口。
- **Linux 的已知缺口**:驱动模式下不带名字的 `off` 仍让守护进程排空后退出(D62⑥),守护进程一走看板也就没了,直到下一次 `on`。macOS / Windows(代理模式)不受影响——那里的 `off` 从不请守护进程退出。这个缺口补上之后三个平台同形。

## 控制面(D26)
- **默认可用,门是同一条链**(D26①):`GET /control/status` 与 `POST /control/*` 与数据面一起在,过同一个 Host / Origin 门和同一个口令;没有另一个要操作者先打开的开关。写仍然只出于操作者在页面上的点击(不变式 1 · D30):控制面 **MUST NOT** 自己推导出任何改动。
- **守护进程以 root 跑时整个控制面不挂**:`on` / `off` 本来就拒绝 root([1.6](1.6-cli.md) §1.5),数据面只读所以照旧;`GET /control/status` 回 `{control:false, user, root:true, harnesses:[]}`,页面据此说明为什么没有开关;三个写端点不挂,落到 405。比让每个端点各自拒绝更省、更清楚。
- 四个端点,就这些:

  | 端点 | body | 调谁 | 回执 |
  |---|---|---|---|
  | `GET /control/status` | — | 什么都不写 | `{control:true, user, root:false, harnesses:[{harness, desired, setup}]}`;`setup` 的取值与来源见 [1.6](1.6-cli.md) 附录 C.3 |
  | `POST /control/classes` | `{kind:'set'\|'add'\|'rm'\|'reset', class?, keep?, host?, path?, harness?, rule?}` | `src/cli/classes.mjs : classesChange(op, …)` → `src/classes/table.mjs : edit(op, {home})` —— `trocar classes` 的同一个函数与写者,op 的形状就是这个 JSON | C.2 的 `classes` 回执 |
  | `POST /control/harness` | `{harness, on, confirm?}` | `src/cli/on.mjs : runOn(…)`(参数解析之后的 `on` 本体,root / 旧安装 / Node 下限 / 提权口令的拒绝都在里面)/ `src/off/orchestrate.mjs : runOff(…)` —— `trocar on` / `off` 调的同一个函数(**不是**它们的 argv 外皮);`flows/` 里这次跑写的每条记录带 `source:'board'` | C.2 的 `on` / `off` 回执 |
  | `POST /control/setup` | `{harness, confirm?}` | `install` 的同一个函数,只补这个 harness 缺的证书载体(幂等,V67) | C.2 的 `install` 回执 |
- **先计划后确认**(1.6 §1.4,由构造满足):
  ```
  POST /control/harness {harness:'codex', on:false}
    → 409 {need:'confirm', plan:[{path, how, harness}…], receipt:<dry-run 的回执>, plan_id:<planned 的 sha256>}
  POST /control/harness {harness:'codex', on:false, confirm:'<plan_id>'}
    → 200 <C.2 的真回执>
  ```
  计划**不是重新推导的**,就是 dry-run 回执自己的 `planned[]` 字节。`plan_id` 对不上(两次请求之间机器变了)→ 409 带**新**计划,一个字节都不改;这是浏览器给 CLI 协议加的唯一一样东西(一次 sha256)。`POST /control/setup` 与 `/control/classes`(改动类的 op)走同一套。
- **没有 `install` / `uninstall` / 自启 / 证书整装 / 提权助手的端点**(D55① · D61 · D53 · D65③):不是「挂着但拒绝」,是**根本没有**,所以 405 的只读规则继续覆盖它们。`POST /control/setup` 是唯一与装有关的写:它只补这个 harness 缺的那几项,且只在 `status` 说这个 harness 需要时才在页面上出现(D65④)。
- **调的就是 CLI 那批函数**:不构造 argv、不另写一套校验(`ClassArgError` / `QueryArgError` → 400,与数据面同一处);`io` 是缓冲区,CLI 自己的文字进回执的 `notes`,不上守护进程的 stdout。备份与事件由那些函数自己写(D39③),端点 **MUST NOT** 预建或清理 `~/.trocar/backup/` 里的东西;端点只在传下去的 op 上加 `source:'board'`,于是每次改动在日志里都认得出是从看板来的。
- **在哪个环境里跑**:这些函数在守护进程的工作进程里跑,环境就是守护进程的环境 = 登录项给它的那份(macOS 的 launchd 作业、Windows 的登录任务,加上 `install` 写进登录项的 `NODE_EXTRA_CA_CERTS`;直接拉起的守护进程按同一份裁剪,[4.9](4.9-macos-collector.md) §4 · [4.8](4.8-win-collector.md) §7),也就是从 Dock / 开始菜单启动的 agent 看到的那份。用户只在某个 shell 里 export 的变量(`CODEX_HOME` · `CLAUDE_CONFIG_DIR` · `HERMES_HOME` · `DSH_HOME` 这类定位 harness 文件的,`SSL_CERT_FILE` · `NODE_EXTRA_CA_CERTS` 这类规则 U 读的)只作用于从那个 shell 跑的 CLI:看板的 on / off、Set up 与 `GET /control/status` 按登录环境判断与落盘,浏览器也没有任何通道把 shell 的环境带进来。所以 V91 的「逐字段相等」是**同一环境下**的相等;两边环境里这些变量不同时,看板与那个 shell 的 `trocar status` 可以不同,这是边界不是缺陷,`trocar status` / `install` 从那个 shell 跑仍是那个 shell 的答案(依据 = D26②「每个写端点只调 CLI 同一批函数」——调的是函数,环境是调用者的;D56⑨ 守护进程的环境是它的作业环境、trocar 不往登录环境写变量,所以守护进程拿不到、也不该另存一份 shell 的环境;另存一份 shell 变量的做法会把某一时刻某个 shell 的值冻进清单,与此后从别的 shell 跑的 CLI 一样对不上)。
- **Set up 的三件实话**(就地写进回执与页面):根已经被信任时不弹框(V67:只补缺的载体);真要弹框时,OS 的框**不能**归因于网页里的一次点击,没有图形会话时可能根本不弹 → 回执如实记 pending,并给出要在终端里跑的 `trocar install`;**MUST NOT** 在后台替用户改刚装好的程序的文件(D43 · D65④)。

## 看板 v2 需要的补充
看板 v2(1.2–1.9、2.x)要的、服务端在已有文档上加的字段。都按字段在不在判断,不按版本;一个 harness 一条规则也没有(不变式 3)。

- **`sessions[].title` / `title_source`**:见 §人类标题的来源。`title_source` ∈ {`wire`, `unread`, `null`};有 `title` 时总是 `wire`。

- 上表除 #19 都在 `npm test` 里;#19 用 `scripts/deploy-check.mjs` 手跑。
- 速度:看板的每个请求就是对应查询的耗时([1.6](1.6-cli.md) §4.1 的目标),外壳自身不引入额外的整文件读取或缓存层;看板上的交互按 **D64** 量(打开会话 ≤ 0.5 s、换 step ≤ 50 ms、其余按钮与面板 ≤ 0.5 s,p50 与 p95 都算),达不到就按 D64⑥ 报出来。

## Edge cases
- **没有数据**:每个端点返空文档(列表名字 `has_more:false`),不 500、不返空字符串。
- **索引被删**:请求照样成功(重建),只是慢。
- **同一台机器上几个系统用户共用 `127.0.0.1`**(D36 引出):环回不分用户,A 的服务在端口上开着时 B 能读到 A 的逐字语料(含活凭据)。**已定**(D26③):每用户一份持久口令(0600,`~/.trocar/` 下),`trocar board` 印出带它的网址;没带口令的 `/api` 与 `/control` 请求一律 403;端口照旧。
- **端口被占**:看板这一面起不来,采集照常;原因进 `status` 与一条持久记录(D38),`trocar board` 照实说,不换端口。
- **还没 `trocar install`**:守护进程没在跑,看板也就不在;`trocar board` 说要先 `trocar install`(D65②)。这台机器上早先采过的数据在 `install` 之后照样能翻(`uninstall` 默认留 `raw/`)。
- **`uninstall` 之后**:看板随守护进程一起消失;页面上最后一次轮询失败,显示终局状态而不是一直转。
- **合成键的会话没有 `x-trocar-tip`**:它的归属要读取侧的规则([3.4](3.4-session-identity.md)),守护进程与 index keeper 不知道;这类会话的 head 落后只能从 `pending` 与 `markTs` 看出,[1.5](1.5-states-aesthetics.md) K-32 那时不亮(依据:D20——守护进程不解 provider 的体 + 不变式 4,写明这条边界)。按内容认回带键会话的无键调用([3.4](3.4-session-identity.md) 按内容认亲)同理也不在该会话的 tip 里:它的归属同样只在读取侧算。
- **答案文件在读的时候被换掉**:rename 是原子的,读到的是旧的或新的整份;旧 ETag 的条件读在新文件上答 200;尾的 Range 读带着旧代标签的 `If-Range`,在新文件上答 200 整份(§答案文件「尾的代标签」),看板整份替换,从不把新文件从旧偏移接着读。

## Risk / 回滚
数据面是纯读:出问题就不开看板,`trocar query` 照样能用,数据零影响。控制面只调 CLI 那批函数并先回计划:出问题就不点,改状态照样走 CLI。看板这一面挂在守护进程上,所以它的错**MUST NOT** 弄倒转发:每条路由各自收敛异常,端口起不来只少一个看板。

## OPEN
无。

## Extensions
- 浏览器内查询引擎(D11 的 (B)):判据触发才做,前端契约不变。
- **SSE / WebSocket 推送代替轮询:不做**。一次 304 只花几十次 `stat` 加一次 sha1,省下的那点开销换来的是一个**有状态的外壳**(谁订阅了什么),违「外壳只做三件事」,而守护进程的循环更不该长出订阅表。判据:304 的轮询在剖析里真成了瓶颈。
- **一个 `/api/version` 一次返回所有 stamp(每 tick 1 个请求而不是 3 个):不做**。那会是 CLI 不印的第 12 个文档(D24:没有看板专用文档),要合法就得占一个查询名字。判据同上。
