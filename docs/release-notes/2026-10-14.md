# Release notes — 2026-10-14

## Agents are recognised by executable name, on every platform (D51)

**What changed.** asight used to recognise an agent process on macOS and Windows by its install path, and on Linux by
a separate signature table. An install it had not measured (a Homebrew cask, a platform package, an editor
extension in Cursor or VSCodium, a Codex app bundle, a private Python of a newer minor version) was not recognised, and
its connections were forwarded without capture. Now one name list decides on all three platforms. The name comes from
the real executable and `argv[0]`, lower-cased, without `.exe` or a version number. An interpreter (`node`, `python`,
…) counts only with its script's arguments. Each agent's helper processes are listed as exclusions, on every
platform: on macOS the Kimi plugin runner and the Codex sandbox and updater are no longer shown as a second agent.
Being on the list only makes a process a candidate: it is decrypted only when it also trusts the collector CA.

**Impact.** Agents installed in places asight never measured are now captured, if they trust the collector CA.
`asight off` judges which agents are still running from the same list (`on` records it in the install manifest).
An install made before this release still has the older record, which `off` keeps reading until the next
`asight on` rewrites it.

## `~/.asight/agents.json`: add a name, or ignore a preset

**What changed.** The preset names ship with asight. A new file, `~/.asight/agents.json`
(`{"version":1,"agents":[{"harness":"…","name":"…","args":"…","ignore":true}]}`), adds names to an agent or
removes preset ones. The daemon reads it again within seconds when it changes, without a restart. A broken item is
skipped (the rest are used); a broken file is ignored as a whole. Either way asight records `agent-list-invalid`
with each item's number and reason. `asight on` and `asight off` never write this file. The README section
"Which processes are captured: the name list" has the format.

**Impact.** Nothing changes until you create the file.

## `asight status` and `asight doctor` show the list and what fell outside it

**What changed.** `asight status <harness>` lists the names in effect (preset or yours), the presets you ignored,
and the problems in `agents.json`. It also lists the processes that came through that agent's entry but are on no
list: their connections are forwarded, not captured, and only the name is recorded, never the command line.
`asight status --json` carries the same data: `agents.json` itself once, at the top level, as `agent_list` (its path,
state and problems), and per harness an `identity` with the names in effect, the ignored presets and the processes on
no list. `asight doctor` has two new findings:
for each such process it prints the exact line to add to `agents.json` (for an interpreter it says the item needs
`args`), and it reports a broken `agents.json` with the file, item number and reason. The old
`form-path-unknown` finding is gone.

## A decrypted agent that refuses asight's certificate is a critical record

**What changed.** When an agent asight judged trusted is decrypted and then refuses the collector's certificate,
asight writes a critical `trust-rejected` failure. It names the harness, the entry group, the process name and pid,
the host, the client's alert, and the trust entry asight believed was in effect. There is one record per process and
host. The daemon also writes it to its log (stderr), and `asight status` prints it above everything else
(「‼ 严重」; `critical` in `--json`). The existing negative cache still stops decrypting that host after the second
refusal.

## Chromium desktop apps: only the network service is decrypted, by its own trust entry

**What changed.** In Claude Desktop (macOS and Windows) and Z-Code's Windows desktop app, the process that holds the
model connections is the Chromium network service. It is now decrypted only when that app's own trust entry is in
place and confirmed (the login-keychain item on macOS, the `CurrentUser\Root` item on Windows, Z-Code's app settings).
On Windows, Claude Desktop no longer counts as trusted because Claude Code's `settings.json` names the CA.
Other Chromium child processes are never decrypted (`chromium-child` in `status`). The Claude Code bundled inside
Claude Desktop on macOS is now recognised as `claude` and judged by Claude Code's `settings.json`, like the CLI.
Before, it was mistaken for the desktop app and never captured.

## Hermes: no longer decrypted with a built-in provider on macOS, or at all on Windows

**What changed.** On macOS, Hermes's HTTP client verifies only against the route it actually uses (`ssl_ca_cert` in
`config.yaml`), and the `SSL_CERT_FILE` that asight writes into `.env` has no effect on it. asight now decrypts Hermes
only when that route (the `providers` / `custom_providers` entry `model.provider` names, or the `model` block itself)
carries asight's `ssl_ca_cert` line with the collector CA. With a built-in provider, or a route without that line,
`asight status` says `route-without-ca` and the connections go direct. On Windows, a test machine measured the live client
ignoring every entry asight writes there, so Hermes is still recognised but never decrypted (`win-doors-rejected`)
until that is resolved.

**Impact.** Hermes on macOS with a built-in provider is no longer captured. Before, decryption was attempted and failed.
What `asight on` writes for Hermes is unchanged.
