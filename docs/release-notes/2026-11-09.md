# 2026-11-09

## Uninstall

- **`trocar uninstall` says what it does in a few lines.**
  - The plan lists each of your files it takes trocar out of. Several files in one folder share one line, with their count.
  - Then one sentence covers what trocar deletes of its own, and one line covers what is kept and its size.
  - The receipt says it is done and what was kept.
  - Every file, key, backup and process is still printed with `trocar uninstall --details`.
  - `--json` is unchanged.
- **The uninstall question no longer says "Nothing was changed" just above itself.** An interactive `trocar uninstall` used to print "Nothing was changed. Run it with --yes to do it." right before `Proceed? [y/N]`. Now only `--dry-run` says that.
- **After `trocar uninstall --purge-data`, running `trocar uninstall` once more leaves nothing behind.** On Linux, when another account still uses the capability helper, the README asks you to run `uninstall` a second time. That run used to start a new record under `~/.trocar/collector/flows/`, which you then had to delete by hand. A clean run no longer creates that folder. A failure or a warning is still written there, and the folder is made for it.
- **A refused `trocar uninstall` says why in one line, then the steps.** When capture is still on for an agent, a program may still be using trocar, or trocar's service does not answer, it says so in one line, adds "Nothing was changed.", then lists each step, in order. The full sentence is in `--details` and in the JSON `message`.

## Update and install

- **`trocar update` says what it does in a few lines.**
  - The plan is the version it goes from and to, and the agents not captured while it runs; the question has one `[y/N]`.
  - A finished update is one line, plus a line for each thing left to you (a `sudo` line, an install in a desktop terminal), with its command.
  - An update that stops after the code changed says where it stopped, which agents are not captured until it finishes, and one thing to run: `trocar update`. A step it cannot do itself, such as `npm install`, comes first.
  - Commits, the service rows and each step's own reason are printed with `--details`. `--json` is unchanged.
- **A stopped update pulls newer code before it finishes.** In a checkout, `trocar update` with an update waiting first fetches: newer code upstream is fast-forwarded and finishes the update, so a fix that landed since is used. An agent switched on since is switched off first and on again at the end. Code that cannot be pulled is said in one line, and the code there finishes.
- **`trocar install` prints a short plan and receipt.** The plan names each file of yours it changes, by full path, the login item too; trocar's root and its own files are one sentence. The receipt is the conclusion, what is left to you, `Next: trocar on` and the line that undoes trocar if it breaks. The rows (fingerprint, each agent's certificate setting, the login item) are printed with `--details`.
## On and off

- **`trocar on` and `trocar off` say the conclusion and what to do; `--details` prints the rest.**
  - The `on` plan is one line per agent and file of yours, with `new` on a file you have not said yes to before.
  - `off` counts the processes still passing through trocar per agent, without pids.
  - A file `off` could not undo, a fact it could not read, and a refusal stay in the default text, each with its command.
- **On macOS and Windows, `trocar on` names the agents to restart.** Processes started before capture was on are one line, as on Linux; their pids are in `--details` and the JSON `restart` key.

## All capture commands

- **`--details` on `install`, `on`, `off`, `status`, `uninstall`, `doctor` and `update`.** The short default text of each command is coming in the next changes, and `--details` will keep printing everything it leaves out. Until those land, every command but `uninstall` prints what it printed before.

## Status and doctor

- **`trocar status` is one short screen.** The first line says how many agents are captured and which one needs a restart. The table names each agent with a short reason and no process numbers. Under it are only the lines that ask something of you or are not right, such as the certificate or a service that is not running, then the problem count and whose they are (`46 in the last 24 hours, 34 of them pi's`), and the board's address.
- **`trocar status --failures` is a table of what happened.** Each row has when, how many times, the agent, and one sentence with what to do. Problems that say the same for the same agent are one row. The codes, programs and hosts are in `trocar status --failures --details`.
- **`trocar doctor` lists only what needs you.** The headline counts the problems and says which agent needs a restart. Capture failures are one line that points at `trocar status --failures`. Notes are counted in the last line and printed with `trocar doctor --details`, together with every process number, command and what the last install noted.
- **The Problems row's "latest" is the newest problem.** It used to give the time of a newer note, such as a slow upstream, so it could say "latest 21 min ago" beside problems from hours before. The board's "latest failure" for each agent follows the same rule. In `--json`, `failures.latest` is now `null` when there is no problem.
- `--details` prints what each of these commands printed before, and `--json` is unchanged except `failures.latest`, above.
- **On Linux, "the setting that points at trocar is gone" says `trocar install` when trocar's certificate for that agent is missing too.** `trocar status <agent>` and `trocar doctor` used to say `trocar on <agent>`, which `on` then refused until `trocar install` had run.
- `--details` prints what each of these commands printed before, and `--json` is unchanged.

## Board

- **After an update that re-indexes your capture files, a session you never opened shows up long before re-indexing ends.** The capture files are re-indexed newest first. A session grouped by its own session key answers from the capture files already re-indexed. It says that older capture files are still being re-indexed, and that it may lack calls until that ends. Sessions grouped by an inferred key, and Kimi Code's side chains, still wait for the whole re-index.
- **Storage no longer says "Not changed" when the service fails while changing a level.** If the service answers a confirmed change with an error, the change may already have been made, so the receipt now says that it may or may not have been made. The level shown is the one the service reports afterwards.
- **`--details` on `install`, `on`, `off`, `status`, `uninstall`, `doctor` and `update`.** The short default text of each command is coming in the next changes, and `--details` will keep printing everything it leaves out. Until those land, every command but `uninstall`, `update` and `install` prints what it printed before.
