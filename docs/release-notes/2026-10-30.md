# 2026-10-30

## Command line

- **Harnesses are listed in the order of the names table.** The harness table of `trocar status`, the receipts of
  `on` and `off` when you name harnesses, and the `Known:` line of a mistyped name now list them as `claude-code,
  codex, opencode, kimi-code, deepseek-dsh, hermes, z-code`. Before, these listed `hermes` third. `trocar` and the
  standalone `trocar-off` now read the harness names from one table, so they cannot disagree.
- **`trocar install` says when the login entry could not be registered.** `install` registers
  `trocar-collector.service` with `systemctl --user enable --now`. Where that fails, for example in a shell with no
  systemd --user to ask, `install` used to print "Installed", exit 0 and suggest `trocar on`, which then refused.
  It now ends with "trocar install did not finish", names systemctl's own reason as a problem, exits 1, and leaves
  out "Next: trocar on". With `--json`, the receipt carries `autostart: {entry, enabled}` and `daemon`, as it
  already did on macOS and Windows.
- **Running `trocar install` again puts the login entry back.** A second `install` used to stop at "Already
  installed" when every certificate was in place, so an entry that had been switched off, or never registered,
  stayed that way. Every `install` now asks for the entry and the daemon, and leaves every certificate byte alone.
- **`trocar on` tells "could not be read" from "not registered".** With no systemd --user to answer,
  `systemctl --user is-enabled` prints no state. `on` now refuses with "could not be read" and systemctl's reason,
  not "is not registered". An entry that is enabled only until the next boot (`enabled-runtime`) is not taken as
  the login entry. The refusal no longer says that agents pointed at trocar's doors would fail to connect: on Linux
  trocar points no agent at a door, and without the entry capture would stop at the next login instead.

- **`trocar status <harness>` prints the notes of each form.** On macOS and Windows a harness can carry notes that
  `on` already printed: VS Code's extensions all going through trocar (Kimi's extension), what OpenCode 1.x leaves in
  its config folder, a way of starting the agent that skips trocar's hook. `status <harness>` now prints them too,
  after `Forms`, each once. Before, only `status --json` had them. The note about Kimi's VS Code extension now names
  that form and says in plain words that the editor's other extensions connect through trocar and are passed on
  without being captured.
- **`trocar status` no longer calls a harness captured when none of its forms is installed.** On macOS and Windows,
  a harness that is on while none of the forms trocar sets up is on the machine (for example Kimi Code installed only
  through npm) is now `not captured` with the code `not-routed`, and its fix says to install it with its own
  installer and run `trocar install`. A process that belongs to none of its installed forms gets the same code.

## Capture

- **DeepSeek `dsh` is decrypted on macOS and Windows.** `dsh` connections through trocar were forwarded
  without capture when `NODE_EXTRA_CA_CERTS` was unset (`var-missing`) or named a file without the trocar root
  (`ca-not-in-file`). The trocar plugin that `install` puts in `dsh` adds the trocar root inside the
  process, so trocar no longer looks at that setting to decide; it still uses the files it names to check the
  upstream's certificate, so when it cannot read that setting or its file the connection is still forwarded and
  judged again on the next one.
- **pi is the eighth harness.** `trocar install`, `on`, `off`, `status` and `uninstall` take `pi` as a harness name.
  On Linux `install` puts one extension, `trocar-ca.js`, in pi's `extensions/` folder (`~/.pi/agent`, or
  `PI_CODING_AGENT_DIR`), which pi loads by itself; it adds the trocar root inside pi and nothing else. On macOS and
  Windows `install` puts a different extension there, `trocar-pi-extension.js`: it adds the root and reads the switch
  file once when pi starts, so a pi you start while capture is on goes through trocar and a pi started before `on`
  does not, even after pi's `/reload`. A pi started with `--no-extensions`, or with settings that leave the extension
  out, does not run it: on Linux it is not decrypted, and on macOS and Windows it does not go through trocar at all.
  `install` on Linux, and `on` and `trocar status pi` on macOS and Windows, say so. Capture of pi has not been shown end
  to end on any OS yet.
- **`trocar off` without an install record now looks where `on` wrote.** When the install record is missing or
  unreadable, `off` undoes by trocar's own marks. On macOS and Windows it now also finds the `trocar.js` routing plugin
  `on` put in OpenCode's `plugins/` folder, and the Codex and Hermes proxy blocks where `on` wrote them: under
  `XDG_CONFIG_HOME`, `CODEX_HOME` or `HERMES_HOME` when set, and Hermes's under `%LOCALAPPDATA%` on Windows. A proxy
  block is now taken out whole; before, only its first line went and the proxy lines stayed. This has not been shown on
  a real macOS or Windows machine yet.
- **An orderly stop no longer counts as a problem.** Each time the collector stopped in the ordinary way, it
  recorded its capture helper as having gone down. That happened after an `off` that let it drain and exit, a
  logout, and a `systemctl --user stop`, so `trocar status` then showed "Problems 1" with nothing wrong. The stop is
  now recorded only as the daemon's stop. A helper that ends badly while being closed is still recorded.

- **A program that speaks something other than a proxy request to trocar is named.** Such a connection used to be
  recorded with its port only, so `trocar status --failures` and the board could not say who sent it. The record now
  carries the program's name and pid (or why they could not be read), and for a plain HTTP request its method and
  host, never its path, query or headers; the failure line ends with the latest program it came from. trocar's
  answer to that program is unchanged: the connection is closed.
- **Z-Code keeps the CAs you added when trocar sets its `caCertFile`.** On macOS and Windows `install` points
  `network.caCertFile` in `~/.zcode/cli/config.json` at a bundle trocar writes, and that key replaces Node's
  default roots. The bundle held Node's roots and the trocar root only, so a private CA you added through
  `NODE_EXTRA_CA_CERTS` stopped counting once the key was set: Z-Code could not reach a host signed by it. The bundle
  now also holds the certificates of that file, as `install` finds it in its own environment. It also holds the
  certificates named by `ZCODE_AGENT_CA_CERT` and the desktop app's CA setting: while either is set it takes the
  place of the key, and with them in the bundle your CA still counts once you unset them. A file it cannot read, a
  relative path and a block that is not a certificate are named in the install receipt. Run `trocar install` again
  to rebuild the bundle.
- **A host whose certificate did not verify is no longer reported as a program refusing trocar's certificate.**
  When trocar stops decrypting a program's traffic to one host, `trocar status`, `trocar status --failures`,
  `trocar doctor` and the board now say why: the program refused trocar's certificate, the host's certificate did
  not verify with the program's own trust, or the handshake with the host did not finish. Only the first one asks
  you to restart the program.
- **Receipts no longer print a proxy password.** `install`, `on`, `off`, `uninstall`, `update`, `daemon` and
  `classes` changes, and the lines they write to `collector/flows/`, show a URL's `user:password@` as `***@`; the
  `off` receipt used to print the whole proxy URL trocar had written, password included. The undo record keeps
  what undo needs; `query` and `raw` still print captured data as it is.
- **The board's capture page hides a proxy login in any form a URL holds it.** It showed `***@` only for a URL with both a user name
  and a password. A URL with only a user name (`http://alice@proxy:8080`), only a password (`http://:pw@proxy:8080`), or
  a password holding an unescaped `@` showed the name, the password or part of it, in the page and in "Copy
  diagnostics". It now hides them by the same rule as the receipts.

## Linux

- **The Linux helper builds on kernels Ubuntu has no tools package for.** `make -C src/collector/arch/linux` used
  the first `bpftool` on `PATH`. On Ubuntu that is a wrapper that refuses any kernel it has no `linux-tools` package
  for, which is common on cloud and container kernels, so the build stopped at the first step. The build now uses
  the first `bpftool` that can read this kernel's BTF: the one on `PATH`, `/usr/sbin/bpftool`, then each
  `linux-tools` build, newest version first. `BPFTOOL=<path>` still wins. With none, the build stops with a message
  naming `bpftool`, and on a kernel built without BTF it says that instead. A step that fails no longer leaves a
  half-written file that the next `make` would take as done.
- **`setup-helper` on a fresh clone says how to build the helper.** The Linux helper is built from source, but
  the README did not say so, and on a clone where it was not built `sudo trocar setup-helper` stopped with
  `trocar setup-helper: trocar setup-helper: built binarySrc not found: …`. It now says the helper is not built
  yet and prints the `make -C …/src/collector/arch/linux` command for that copy of trocar, ready to paste, and still installs
  nothing (exit 1). A `--binary` path that is not a file is named the same way. The Install section lists the
  build step, the Ubuntu packages and the kernel BTF it needs, and runs `setup-helper` with node by its path, since
  `sudo` does not see a node installed with nvm. The upgrade note says to build it again and install it
  again. The helper installer's other messages no longer repeat the command name.
- **Stopping the login unit no longer reports the helper as down.** `systemctl --user stop trocar-collector` (a
  logout, or anything that stops the unit) sent its signal to the Linux helper as well as the daemon. When the helper
  went first, the stop was recorded as `helper-down "loader exiting"`, and `trocar status` showed a problem after a
  clean stop. The unit now has the stop signal go to the daemon alone, which closes the helper itself. Run
  `trocar install` again (or `trocar update`) to rewrite the unit.
- **A daemon whose helper fails at start now ends.** When the Linux helper refused to start (for example a kernel
  below the floor, or a namespace it cannot work in), `trocar daemon` wrote why, said it could not start, and then
  kept running with its engine port open. The next start was refused because "the engine port … is held by another
  process". It now closes everything it opened and exits 1, so the next start, by systemd or by hand, gets the same
  port.

## Install and update

- **trocar is on npm as `trocar-cli`.** Install it with `npm i -g trocar-cli`; the command is still `trocar`. Each
  GitHub Release carries the same tarball with its `SHA256SUMS`, and `npm i -g` on that file installs it the same way.
  Run `trocar install` from the global install, not through `npx`: it registers a login item that runs that copy,
  and npm may clear the `npx` cache. On Linux the package carries the capability helper's source, not a build:
  build it with `make -C "$(npm root -g)/trocar-cli/src/collector/arch/linux"`, then install it with
  `sudo "$(command -v node)" "$(command -v trocar)" setup-helper`, before `trocar install`.
- **trocar is licensed FSL-1.1-ALv2.** You may use, copy, modify and redistribute it for any purpose except making
  it available to others in a commercial product or service that competes with it. Each released version becomes
  Apache-2.0 two years after its release. The kernel-side eBPF program in `src/collector/arch/linux/bpf/` is
  GPL-2.0-only OR MIT, as its license string declares, because the Linux kernel lets only a program under a
  GPL-compatible license use the kernel helpers it needs.
- **`trocar update` knows a copy installed with npm.** Before, a trocar installed with npm (globally, in a
  project, through `npx`, or from a release tarball) only said it was not a git checkout. Now it tells you to run
  `npm i -g <package>@latest`, using the package name of the copy you run, and changes nothing. After you have
  installed the newer copy, run `trocar update` again: when the collector still runs the old code, it finishes the
  way a git update does, after the same plan and `--yes`: the collector is stopped and started again on the new
  code, `install` runs again, and the agents being captured are switched on again. `install` now records which code
  ran it, so the update also finishes when the collector already came back on the new code by itself (a reboot or a
  new login in between): it runs `install` and switches capture on again, instead of asking for the npm install
  you already did. Setting up one agent on the board does not count as running `install`. If the collector comes back on
  another copy of trocar (the login entry starts a global copy while you ran a project's or `npx`), it says so and
  exits 1 instead of claiming the update. `trocar update` does not run npm itself, because a global npm install
  often needs administrator rights and trocar refuses to run as root.
