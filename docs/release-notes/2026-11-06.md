# 2026-11-06

## Capture

- **On Linux, `trocar off` no longer stops the collector.** The daemon and the board keep running, as on macOS and
  Windows. `off` takes trocar's links off, and once the connections it was relaying are through, the capability helper
  exits, so no capture path of trocar's is left in the kernel; `--now` cuts them and the helper exits at once. The next
  `on` starts the helper again without waiting for the daemon to start, so it is quicker. A login with nothing on starts
  the daemon with no helper, and a helper that crashed is not restarted until the daemon restarts.
- **The `off` receipt says what the daemon does.** It now reads `The daemon (pid N) keeps running.`
- **Plain http from programs Claude Code, Codex and Hermes start goes through trocar too.** `trocar on` set only
  `HTTPS_PROXY` in their settings or `.env`, so a tool or helper they started sent plain `http://` requests straight
  out, past trocar. It now sets every proxy variable each one reads (`HTTP_PROXY` as well, and `ALL_PROXY` for Codex
  and Hermes), in both spellings, and `trocar off` takes them out again. A value of your own goes back as it was. An
  agent started that way is captured like any agent; any other program is only forwarded: it gets a connection row
  (`not_captured`), not its bytes.

## Linux

- **`trocar status` says whether each agent is set up.** On Linux, each agent in `trocar status` and on the board now
  carries `setup`: ready, needed (with the reason) or unknown. An agent installed after trocar is listed too.
- **`trocar on <agent>` refuses only the agent that is not set up.** If the certificate entry trocar installed for an
  agent is missing or was overwritten, `trocar on` leaves that agent off with `setup-needed` and names the two
  commands: `trocar install`, then `trocar on <agent>`. `trocar install` (or Set up) puts that entry back, and undoing it later
  restores the value the agent had left there. The other agents named in the same command still turn on.
- **Set up on the board works on Linux.** It adds only what that agent is missing and needs no `sudo`; when it cannot put an entry back
  (for example the file is now a link to nothing), it refuses with `setup-needed` and the reason, and changes nothing.
- **An agent counts as installed when its own files or command are there.** On Linux, `trocar status` and `trocar on` now
  decide whether an agent is installed from its own install folder, config folder or command on your PATH (the PATH of
  the terminal you last ran trocar from), not from whether trocar would have something to write for it. An agent that is
  installed but has nothing trocar can set up (for example Codex before its first run, or Kimi Code without the PATH
  line its installer adds) shows `setup` needed, and `trocar on`
  leaves it off with `setup-needed`. The board's Set up for such an agent says why it cannot set it up and changes nothing,
  instead of saying there is nothing to set up.
- **`trocar install` writes nothing for an agent that is not installed.** On Linux, `trocar install` used to add its
  certificate entry or plugin for every agent it knows, so an empty home got `~/.claude/settings.json`,
  `~/.config/opencode/plugins/trocar-ca.js`, `~/.dsh/cordis.patch.yml` and `~/.pi/agent/extensions/trocar-ca.js`. It now
  sets up only the agents whose own files or command are there, and lists only those as installed. Run `trocar install`
  again after installing a new agent. What it set up for an agent you later removed stays until `trocar uninstall`. Set up on
  the board refuses an agent that is not installed with `setup-needed` and changes nothing.
- **The board and the terminal agree on an agent whose folder you moved.** On Linux, when you point an agent at another
  folder with its own variable (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `DSH_HOME`, `HERMES_HOME`, `PI_CODING_AGENT_DIR`,
  `XDG_CONFIG_HOME`, `XDG_DATA_HOME`), trocar now remembers that variable's value from the terminal you last ran it in,
  next to your PATH. The board's status and Set up, which run in the background service without your shell's variables,
  now look in the same folder as `trocar status` and `trocar on`.

## All platforms

- **A certificate entry trocar cannot read is no longer reported as overwritten.** When the file holding it cannot be
  read (for example its permissions changed), `setup` is now `unknown` with the reason, and `trocar on` turns the agent
  on with a note instead of refusing it as `setup-needed`.
- **A proxy address of trocar's own left in a settings file is no longer taken for yours.** When the install record
  was lost while a settings file still pointed at trocar's local proxy, the next `trocar on` recorded that address as
  your own proxy (the Claude desktop app's PAC setting was even read as your own egress, and `on` did not write it),
  and the `trocar off` after it put the address back, so the agent pointed at a closed port. `trocar on` now takes such
  a value out in the same single write that points the file at trocar, and keeps one backup of your file without
  that address (so the backup holds no password of trocar's proxy); `trocar off` leaves the key out. A proxy of your own on
  another local port is kept as before.
- **trocar no longer keeps the password of its local proxy in the install record or in backups.** The install record
  now holds that password only as a fingerprint, so the record, and the backups made from your files, no longer
  carry a credential. One `on` writes each settings file once and keeps one backup of it, with your bytes from before
  trocar changed it. Backups made by an older trocar can still hold the password: `trocar doctor` names each one, and
  you can remove it.
- **A `NO_PROXY` of your own is no longer taken for your proxy.** With a `NO_PROXY` in the settings `trocar on`
  writes to (Claude Code's `settings.json`, for one) and no proxy of your own, trocar read that bypass list as the
  proxy to chain through, so the agent's requests failed where they went direct before. Trocar now takes only the
  proxy setting you had, and `trocar status` shows the upstream as direct.

## Capture on / off

- **`off` without an install record no longer leaves pi, DeepSeek dsh and Kimi pointed at a closed door.** When the
  install record is gone or unreadable, `off` undoes what trocar changed by trocar's own marks. On macOS and Windows it
  left out the switch files `on` writes for these three agents (`~/.trocar/collector/switch/<agent>`). Those files
  still named the door that the same `off` had just closed, so the next pi, dsh or Kimi could not connect at all. `off`
  now deletes them as well. `~/.trocar/bin/trocar-off` gets the fix the next time `install` runs; `trocar doctor` says when it is out of date.
- **`off` without an install record also takes the proxy setting out of Claude Code, VS Code, Claude Desktop and Z-Code.**
  On macOS and Windows, `on` points a proxy setting in these apps' own config at trocar's local proxy: Claude Code's
  `settings.json` (`env.HTTPS_PROXY`, `env.HTTP_PROXY`), VS Code's `http.proxy` (for Kimi's extension), the applied Claude Desktop
  configuration (`egressProxyPacUrl`) and Z-Code's `network.httpProxy`. With the install record gone, `off` left
  these settings in place, so the apps kept using a closed port. The next `on` also saved trocar's own address as
  the user's original setting. `off` now removes a setting when it points at a local port that trocar recorded for
  its proxy (`~/.trocar/collector/ingress.json`). It puts back the value from trocar's backup of the file, or deletes the key
  if the backup has none. A proxy of your own on another local port stays as it is. If trocar cannot read
  `ingress.json`, it changes nothing, and the receipt names each setting it could not check. A config file that no
  longer parses but still holds trocar's address is left as it is, and `off` names it and exits 1.
- **`off` without an install record no longer removes trocar's certificate settings.** The certificate settings that
  `install` writes belong to `install` and `uninstall`, but with the install record gone `off` removed them too: Claude
  Code's `env.NODE_EXTRA_CA_CERTS`, Z-Code's `network.caCertFile`, the certificate block in Codex's and Hermes's `.env`,
  and the trust plugins of OpenCode, pi and DeepSeek dsh. After that, `on` refused Z-Code until `install` ran again.
  `off` now leaves all of them as they are; `uninstall` still removes them, with or without the record.
- **`uninstall` without an install record also cleans an agent folder you moved with its variable.** When the install
  record is lost, `trocar uninstall` removes trocar's entries by trocar's own marks, but it looked only in each agent's
  default folder. A Claude Code, Hermes, OpenCode, DeepSeek dsh or pi folder that you moved with its variable
  (`CLAUDE_CONFIG_DIR`, `HERMES_HOME`, `XDG_CONFIG_HOME`, `DSH_HOME`, `PI_CODING_AGENT_DIR`) kept trocar's entries.
  `uninstall` now looks where the variable points, and in the default folder as well, so a variable set since `install`
  is still covered. A folder `install` used under a value you have since cleared or changed is not found this way;
  undo it there by hand or set the variable back before `uninstall`. `~/.trocar/bin/trocar-off` gets the fix the next time `install` runs; `trocar doctor`
  says when it is out of date.
- **A DeepSeek dsh patch file stays a list after `uninstall` without an install record.** If trocar's row was the
  only item, the file came back holding only your comments, and dsh does not start on a patch file with no list in it.
  It now comes back with its `[]` as before, comments and blank lines kept.
