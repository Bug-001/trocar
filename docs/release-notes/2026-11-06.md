# 2026-11-06

## Capture

- **The prebuilt Hermes desktop app on macOS is recognised.** Its backend starts Python with different interpreter flags
  than the installer's build, so it was not recognised as Hermes and none of its turns were captured. trocar now
  recognises any Python that loads Hermes's entry module, whatever flags it starts with.

- **Hermes installed with pip is captured on Linux.** A `pip install hermes-agent` puts a Python console script on your
  PATH, and that program was not recognised as Hermes: its connections went direct, and nothing said so. trocar now
  recognises it like the installer's build, and judges its certificate settings the way a release build reads them.
- **trocar says that OpenCode can stall at start where npm is out of reach.** With trocar's plugin in its config
  directory, OpenCode 1.x installs `@opencode-ai/plugin` there, and every start waits for that install until it has
  succeeded once. On a network where the npm registry cannot be reached, each start stalls until the install gives up,
  about 6.5 minutes measured. The note `install` prints on Linux, and the note `on` prints on macOS and Windows, now say
  so. They used to say the fetch happens once.
- **No false "refused trocar's certificate" when an agent exits.** An agent that quits closes the spare connections it
  had opened and never used. When that happened just after they were set up, trocar read them as the agent refusing
  its certificate: `status` showed a critical `trust-rejected` for a process whose calls were all captured. trocar now
  waits a second on such a close from a process that has already used its certificate; if the process is gone by
  then, the close counts for nothing. A process that is still running is judged as before.
- **On Linux, `trocar off` no longer stops the collector.** The daemon and the board keep running, as on macOS and
  Windows. `off` takes trocar's links off, and once the connections it was relaying are through, the capability helper
  exits, so no capture path of trocar's is left in the kernel; `--now` cuts them and the helper exits at once. The next
  `on` starts the helper again without waiting for the daemon to start, so it is quicker. A login with nothing on starts
  the daemon with no helper, and a helper that crashed is not restarted until the daemon restarts.
- **The `off` receipt says what the daemon does.** It now reads `The daemon (pid N) keeps running.`
## Linux

- **`trocar status` says whether each agent is set up.** On Linux, each agent in `trocar status` and on the board now
  carries `setup`: ready, needed (with the reason) or unknown. An agent installed after trocar is listed too.
- **`trocar on <agent>` refuses only the agent that is not set up.** If the certificate entry trocar installed for an
  agent is missing or was overwritten, `trocar on` leaves that agent off with `setup-needed` and names the two
  commands: `trocar install`, then `trocar on <agent>`. `trocar install` (or Set up) puts that entry back, and undoing it later
  restores the value the agent had left there. The other agents named in the same command still turn on.
- **Set up on the board works on Linux.** It adds only what that agent is missing and needs no `sudo`; when it cannot put an entry back
  (for example the file is now a link to nothing), it refuses with `setup-needed` and the reason, and changes nothing.
- **An agent counts as installed when its own files or command are there.** On Linux, `trocar status` and `trocar on` now
  decide whether an agent is installed from its own install folder, config folder or command on your PATH (the PATH of
  the terminal you last ran trocar from), not from whether trocar would have something to write for it. Claude Code and
  Codex also count when only their VS Code extension is installed, including one that VS Code's Remote - SSH put on this
  machine; trocar then sets them up in the same files as their command-line versions (Codex once it has its own
  `~/.codex` folder). An agent that is
  installed but has nothing trocar can set up (for example Codex before its first run, or Kimi Code without the PATH
  line its installer adds) shows `setup` needed, and `trocar on`
  leaves it off with `setup-needed`. The board's Set up for such an agent says why it cannot set it up and changes nothing,
  instead of saying there is nothing to set up.
- **`trocar install` writes nothing for an agent that is not installed.** On Linux, `trocar install` used to add its
  certificate entry or plugin for every agent it knows, so an empty home got `~/.claude/settings.json`,
  `~/.config/opencode/plugins/trocar-ca.js`, `~/.dsh/cordis.patch.yml` and `~/.pi/agent/extensions/trocar-ca.js`. It now
  sets up only the agents whose own files or command are there, and lists only those as installed. Run `trocar install`
  again after installing a new agent. What it set up for an agent you later removed stays until `trocar uninstall`. Set up on
  the board refuses an agent that is not installed with `setup-needed` and changes nothing.
- **The board and the terminal agree on an agent whose folder you moved.** On Linux, when you point an agent at another
  folder with its own variable (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `DSH_HOME`, `HERMES_HOME`, `PI_CODING_AGENT_DIR`,
  `XDG_CONFIG_HOME`, `XDG_DATA_HOME`), trocar now remembers that variable's value from the terminal you last ran it in,
  next to your PATH. The board's status and Set up, which run in the background service without your shell's variables,
  now look in the same folder as `trocar status` and `trocar on`.
- **trocar says when Kimi Code's VS Code extension is not captured.** On Linux the extension's calls cannot be captured:
  VS Code uses its own certificate list there, which only your login environment can extend, and trocar does not change
  that environment. When the extension is installed (also by Remote - SSH), `trocar install`, `trocar on` and
  `trocar status` now say so for Kimi Code, and `trocar status --json` lists it under `setup.uncaptured`.
- **`trocar status --json` says whether each agent is on this machine.** Each agent in `harnesses` now has `present`:
  `true` when one of its own forms is installed here, `false` when none is (it is listed because trocar set it up
  before), `null` when that could not be read. A new key; nothing else in the document changes. On every platform.

## All platforms

- **A certificate entry trocar cannot read is no longer reported as overwritten.** When the file holding it cannot be
  read (for example its permissions changed), `setup` is now `unknown` with the reason, and `trocar on` turns the agent
  on with a note instead of refusing it as `setup-needed`.
## The board

- **The capture page and the capture log no longer show a proxy password in their technical details.** A reason the
  capture service reported in its own words, such as why it could not reach an upstream proxy, appeared as written,
  `user:password@` included, both on screen and in what **Copy** put on the clipboard. Every value under **Technical
  details** and every log row's sentence now shows that part as `***@`, as the rest of the page already did.
- **Claude Desktop's plain http is captured too.** trocar's proxy settings file (PAC) used to send the app's
  unencrypted `http:` requests the app's own way, past trocar, so they were never recorded. They now go through
  trocar like the app's https and WebSocket connections, and take the app's own way only if trocar does not answer.
  Hosts on your proxy bypass list and this machine's own addresses are handled as before; after `trocar off` the
  file again names only the app's own way.
## The command line

- **`trocar uninstall` names a file it left in place once.** When the reason a file could not be taken out already
  began with the file, the receipt printed the file twice on one line, the second time in full. It now prints it
  once, with the rest of the reason after it.
- **A proxy address of trocar's own left in a settings file is no longer taken for yours.** When the install record
  was lost while a settings file still pointed at trocar's local proxy, the next `trocar on` recorded that address as
  your own proxy (the Claude desktop app's PAC setting was even read as your own egress, and `on` did not write it),
  and the `trocar off` after it put the address back, so the agent pointed at a closed port. `trocar on` now takes such
  a value out in the same single write that points the file at trocar, and keeps one backup of your file without
  that address (so the backup holds no password of trocar's proxy); `trocar off` leaves the key out. A proxy of your own on
  another local port is kept as before.
- **trocar no longer keeps the password of its local proxy in the install record or in backups.** The install record
  now holds that password only as a fingerprint, so the record, and the backups made from your files, no longer
  carry a credential. One `on` writes each settings file once and keeps one backup of it, with your bytes from before
  trocar changed it. Backups made by an older trocar can still hold the password: `trocar doctor` names each one, and
  you can remove it.
- **A `NO_PROXY` of your own is no longer taken for your proxy.** With a `NO_PROXY` in the settings `trocar on`
  writes to (Claude Code's `settings.json`, for one) and no proxy of your own, trocar read that bypass list as the
  proxy to chain through, so the agent's requests failed where they went direct before. Trocar now takes only the
  proxy setting you had, and `trocar status` shows the upstream as direct.
## CLI

- **`trocar status | head` no longer crashes.** When the program reading trocar's output stopped early (`head`, `less`
  quit before the end, a closed pipe), trocar threw a `write EPIPE` error with a stack trace, possibly halfway through
  a command. The output that has no reader is now dropped, and the command finishes with its own exit code.
- **Kimi Code's PATH line goes where your shell always runs it.** trocar's line in your shell rc came right after the
  Kimi installer's own PATH line. When that line sat inside an `if`, a `case`, a loop or a function, trocar's line landed
  inside it too and ran only when that block did, so `kimi` could miss its launch shim and not be captured. The line now
  goes at the end of the rc file. A line already in your rc stays where it is until you run `trocar off`,
  `trocar uninstall` and `trocar install`.
  `kimi` is not captured in these shells, and `status` reports a running `kimi` that did not start through its shim:
  - a shell that leaves the rc before the end (`exec fish`, `exec tmux`, or a top-level `return` or `exit`). This is new:
    those lines used to be fine when they came after the installer's line;
  - an rc whose last line is unfinished (a trailing `\`, an unclosed block or heredoc);
  - a shell where a function adds Kimi's folder only after the rc has been read.
- **The standalone Codex command line is no longer listed as verified on Windows.** It had not been measured there, yet
  its description claimed it was. It now shows as not verified yet on Windows. On macOS it has been measured and stays
  verified.
## Windows

- **SYSTEM is refused with UAC off too.** `on`, the daemon, `off` and `uninstall` refuse a SYSTEM token, but on a
  machine with UAC turned off a SYSTEM token was taken for an administrator with no split token and let through. A
  SYSTEM token is now known by either of two signs Windows gives in every language — its user is SYSTEM, or its
  integrity level is System — and it is refused with `elevated-token` whatever UAC says. An administrator on a
  machine with UAC off is still let through, as before.
## Status

- **`trocar status` says which harness needs setting up.** A harness you installed after trocar was listed under
  `not installed:`, and you learned it needed `trocar install` only when `trocar on` refused it. It now has its own row
  in the summary with `set up first: trocar install`, as does a harness whose own update overwrote trocar's certificate
  file.
- **pi installed with npm, and pi in RPC mode, are captured on macOS.** They were judged only through the official
  installer's pi. Both are now measured on macOS with nothing but trocar's pi extension adding its certificate.
  On Windows they stay not verified until measured the same way.
## Status, doctor and on

- **A local proxy is shown by its port, not by the program behind it.** When an agent's traffic went through a proxy on
  this machine, `trocar status`, `trocar doctor` and the chain `trocar on` prints named that hop after the program
  listening on the port. For a VPN client, that name is the product. The hop is now its port (`:7897`), with the
  listener's pid in `trocar status <harness>`, in the text and in `--json`.
## Uninstall

- **A refused `trocar uninstall` no longer takes the daemon away.** When the daemon did not confirm that its doors were
  shut, `uninstall` stopped with exit 1, but only after it had already removed the login autostart and, on macOS,
  stopped the daemon with it (on Windows it deleted the scheduled task). Agents still pointed at trocar then had
  nothing to connect to. Now nothing about the autostart or the daemon changes until the doors are confirmed shut; a
  refused run leaves both as they were and says why.
## Off and uninstall

- **`trocar off` and `trocar uninstall` delete a file trocar created only if it still holds what trocar wrote.** A plugin,
  launch script or switch file that has changed since trocar wrote it, or that cannot be read, now stays where it is.
  The receipt lists it under what was left, with the reason, and the next run checks it again. Before, these files
  were deleted whatever they held. The program trocar moved aside for a wrapper follows the same rule.
- **`trocar uninstall` no longer stops a daemon that is running but does not answer.** It used to stop it and go on
  undoing while agents could still be pointed at it. Now it refuses before changing anything (exit 1, code
  `collectors-online`) and names the daemon's pid; run `trocar off`, which stops it and confirms the routing is off,
  then `trocar uninstall`. The receipt marks that daemon `left-running` and no longer suggests `kill -9`, which would
  leave the agents pointed at a dead door.
## The board

- **The capture state's lamp now means the same thing everywhere.** "Capture has problems" lit the red lamp meant for a
  stopped service, and states that only say the board does not know (unreadable, unknown, not refreshed) lit an amber
  one. Now a stopped or silent service is red, problems and leftover changes are amber, capturing shows the green dot,
  and the not-known states show only the grey unlit dot, on the overview card and on the capture page alike.
## The board

- **A host's request list names every column.** The marks column (log only, length only, failed) is headed **Notes**,
  and each row's words sit on one line.
## The board

- **A tab showing "open the board with trocar board" reopens when you paste the link it prints into that tab.** It used
  to stay on that page until you refreshed it.
## Receipts

- **`trocar off <harness>` says which harnesses the daemon still serves.** It used to say the daemon keeps serving
  "the other harnesses" even when none was on. It now names them, and says nothing of the kind when none is left on.
  `--json` gains `still_on` with the same list.
- **`trocar off` lists the files an agent wrote because of trocar's plugin under one heading.** It used to repeat a
  sentence for each file, and said they were written while capture was on. They appeared after install, because of
  the plugin install put in place; the receipt now says that once and lists the files below it.
- **A file is one row in the `off` and `uninstall` receipts.** `trocar off kimi-code` on macOS listed VS Code's
  `settings.json` twice when its two entries ended a little differently, and `trocar uninstall` on Windows could list
  `trocar-ca.pem` twice when the install record spelled the path two ways. Each file is now one row with each of its
  changes once.
- **`trocar classes` folds its error lines at spaces.** A file it could not read was said on one long line that the
  terminal cut mid-word, and a usage error ran its usage lines together. Both now fold like every other receipt.
- **`trocar uninstall` on Windows says the scheduled task it deleted as a task.** The receipt listed
  `\trocar\collector` under Removed as if it were a path on the current drive; it now reads
  "the scheduled task \trocar\collector".
- **`trocar classes` names an unreadable class table as `~/.trocar/classes.json`.** When the table could not be
  read or parsed, the message printed the full home directory; it now shortens it to `~` like every other path.
## Capture on / off

- **`trocar on` is faster, on every OS.** With everything already on, `on` took 720 to 870 ms on Linux. It no longer
  rebuilds `~/.trocar/bin/trocar-off` to find out that nothing changed, reads no certificate it will not write, saves
  the install record only when it changed, and asks the root store once instead of twice. `trocar-off` now has one more
  line at its top, a digest, so `on` can tell that the file is current without rebuilding it. The next `on` after you
  update rewrites the file once to add that line. A copy that is lost, edited or out of date is still written again.
  An `on` that turns agents on also waits on the disk less: on macOS and Windows it saves the install record about once per
  file it changes, where it saved it up to three times, and on every OS the lock that keeps two commands apart is no longer flushed
  to disk. Wiring every agent after an `off` makes about a third fewer disk flushes.
- **`off` without an install record no longer leaves pi, DeepSeek dsh and Kimi pointed at a closed door.** When the
  install record is gone or unreadable, `off` undoes what trocar changed by trocar's own marks. On macOS and Windows it
  left out the switch files `on` writes for these three agents (`~/.trocar/collector/switch/<agent>`). Those files
  still named the door that the same `off` had just closed, so the next pi, dsh or Kimi could not connect at all. `off`
  now deletes them as well. `~/.trocar/bin/trocar-off` gets the fix the next time `install` runs; `trocar doctor` says when it is out of date.
## The board
- **`off` without an install record also takes the proxy setting out of Claude Code, VS Code, Claude Desktop and Z-Code.**
  On macOS and Windows, `on` points a proxy setting in these apps' own config at trocar's local proxy: Claude Code's
  `settings.json` (`env.HTTPS_PROXY`, `env.HTTP_PROXY`), VS Code's `http.proxy` (for Kimi's extension), the applied Claude Desktop
  configuration (`egressProxyPacUrl`) and Z-Code's `network.httpProxy`. With the install record gone, `off` left
  these settings in place, so the apps kept using a closed port. The next `on` also saved trocar's own address as
  the user's original setting. `off` now removes a setting when it points at a local port that trocar recorded for
  its proxy (`~/.trocar/collector/ingress.json`). It puts back the value from trocar's backup of the file, or deletes the key
  if the backup has none. A proxy of your own on another local port stays as it is. If trocar cannot read
  `ingress.json`, it changes nothing, and the receipt names each setting it could not check. A config file that no
  longer parses but still holds trocar's address is left as it is, and `off` names it and exits 1.
- **`off` without an install record no longer removes trocar's certificate settings.** The certificate settings that
  `install` writes belong to `install` and `uninstall`, but with the install record gone `off` removed them too: Claude
  Code's `env.NODE_EXTRA_CA_CERTS`, Z-Code's `network.caCertFile`, the certificate block in Codex's and Hermes's `.env`,
  and the trust plugins of OpenCode, pi and DeepSeek dsh. After that, `on` refused Z-Code until `install` ran again.
  `off` now leaves all of them as they are; `uninstall` still removes them, with or without the record.
- **`uninstall` without an install record also cleans an agent folder you moved with its variable.** When the install
  record is lost, `trocar uninstall` removes trocar's entries by trocar's own marks, but it looked only in each agent's
  default folder. A Claude Code, Hermes, OpenCode, DeepSeek dsh or pi folder that you moved with its variable
  (`CLAUDE_CONFIG_DIR`, `HERMES_HOME`, `XDG_CONFIG_HOME`, `DSH_HOME`, `PI_CODING_AGENT_DIR`) kept trocar's entries.
  `uninstall` now looks where the variable points, and in the default folder as well, so a variable set since `install`
  is still covered. A folder `install` used under a value you have since cleared or changed is not found this way;
  undo it there by hand or set the variable back before `uninstall`. `~/.trocar/bin/trocar-off` gets the fix the next time `install` runs; `trocar doctor`
  says when it is out of date.
- **A DeepSeek dsh patch file stays a list after `uninstall` without an install record.** If trocar's row was the
  only item, the file came back holding only your comments, and dsh does not start on a patch file with no list in it.
  It now comes back with its `[]` as before, comments and blank lines kept.

- **`off` without an install record no longer deletes your setting when a backup cannot be read.** To undo a value
  trocar replaced in a JSON settings file, `off` takes your old value from the newest backup of that file in
  `~/.trocar/backup/`. When that backup could not be read (not JSON, an unknown encoding, or a read error), `off` acted
  as if you had no value and deleted the key, although an older backup still held it. `off` now skips such a backup
  and takes your value from an older one. When no backup that it can read holds the value, `off` leaves the key as it is,
  names the backup it could not read, and exits 1. `uninstall` without an install record no longer deletes the backups
  of a file it could not undo: before, the receipt named a backup that `uninstall` had already removed.
- **`off` without an install record also takes out what `on` wrote next to the proxy setting.** On macOS and Windows,
  `off` without the record removed the proxy keys but left the rest: Claude Code's `env.NO_PROXY` / `env.no_proxy`, the
  `http.proxy` item in VS Code's `settingsSync.ignoredSettings`, the `env` or `network` object trocar had created for
  them (left as `{}`), and the Claude Desktop configuration trocar created, with the `appliedId` in `_meta.json` that
  selects it. `off` now restores these from the newest backup trocar made before `on`, or removes them when the file had
  none of them. A file that trocar created and that is now empty is deleted. A `NO_PROXY` you changed while trocar was
  on stays as it is. If no readable backup can show your earlier value, the file stays as it is, and the receipt names
  it. The receipt now lists each file once and counts files, not keys.
## Capture

- **A record that failed to read once no longer stays marked unreadable.** After one failed read, the board and
  `trocar query session` kept reporting the record unreadable even once it read again, and its blocks could point back
  to a later record. The next open now answers as if the session had been read in one go.
- **A program an agent starts keeps using your proxy.** If your proxy was set only in the shell you started the agent
  from (`HTTPS_PROXY` and friends, with no proxy in the agent's settings and no system proxy), a tool the agent ran,
  such as `curl` or `git`, went out directly on macOS and Windows instead of through your proxy, and failed on a
  network that only lets the proxy out. Without trocar that tool would have used the agent's proxy, so now it does:
  trocar finds the nearest agent above it that is switched on and uses that agent's proxy and `NO_PROXY`. The tool is
  still only passed on, not captured.
## The board

- **The overview hides proxy passwords too.** A reason on the overview could carry a proxy address with its user
  name and password, in the capture card's technical details, a failed read's details or an item's line. These now
  show `***@` in their place, as the capture page already did.
## The board

- **Following a session shows the newest step at once.** While following, the desk waited for the newest step's reply
  text before drawing that step, so the step number and the window stayed on the old step for as long as the text took
  to come: seconds right after a session was read for the first time, when it could read "1 / 1" while the session
  already held hundreds of steps. The desk now draws the new step within 150 ms of its arrival, and its reply text
  fills in when it comes, with no second read and no jump of the window.
## Turning off

- **`trocar off` right after the collector started no longer crashes it on macOS and Windows.** For up to a second
  after it began answering, the collector was still reading its own process details, and an `off` that asked it to
  exit in that window made it crash instead of stopping. It now finishes that read and stops cleanly, with nothing left
  behind; `off` is not refused or held up meanwhile.
- **A program that never answers trocar's password request now shows up as a failure.** trocar's proxy asks a
  program for its password (a 407 reply) when the program connects without it, or with one trocar cannot read.
  Most programs answer at once and nothing is recorded. A program that never comes back with the password used to
  leave no trace, so its lost traffic was silent. Now, when the same program has not come back with the right
  password within ten seconds, the board shows one failure naming the program and what it sent instead. The
  password itself is never written. A program that keeps failing gets one line until it gets through.

## Status

- **`trocar status --failures` prints each reason whole.** A long reason used to be cut at 100 columns and end in
  `...`, often mid-sentence. Now the whole reason folds inside 80 columns, and any command in it still prints on a
  line of its own. The failure above reads as a sentence: which program and pid, for which agent, how many times
  it was asked, how long trocar waited, and that its connection was not made. The program and pid are said once,
  and the agent is named as you know it, not by trocar's internal name for its proxy.
## Data

- **`trocar classes` counts only captured records as records.** The storage numbers counted the index's own files
  (session projections kept for fast reading) as captured records, so `records_bytes` could read ten times the size of
  what was captured. Those files now count toward the index.
- **The Storage page and Overview no longer fail because the disk is slow.** Measuring what trocar takes on disk reported no progress, so on a busy machine a healthy query worker could be treated as stuck: the page showed an error and kept showing it for a minute. It now reports progress as it goes.
- **A read that races a seal no longer reports a record as unreadable.** When a capture file was sealed between a read looking for it and opening it, the read failed for that file, or that record, until the next read. It now reads the sealed copy, which is always in place by then.
- **A write counter a vendor does not report now shows as a dash, not 0.** On wires with no cache-write counter, such as DeepSeek and OpenAI Responses, the board and `trocar query` said 0, which reads as a measured zero, and the cost of a cache break was priced from it. Sessions are read again once in the background after the update, so old sessions are corrected too.
- **The collector's doors open sooner after login.** The engine used to read the OS trust store before its doors
  accepted a connection, a large part of its start-up. It now reads the store when the first connection that has to
  verify an upstream arrives, and keeps that set from then on. On macOS and Windows most connections verify against
  the agent's own set, so the store is often never read. Starting the engine and opening a door went from about
  35 ms to about 6 ms on a test Mac. A trust store that cannot be read is still recorded, with the same code, when
  the store is read.
## Uninstall

- **macOS `uninstall` names the launchd entry it cannot remove.** After `uninstall`, `launchctl print-disabled`
  still lists `"com.trocar.collector" => enabled`: `launchctl` has no command that removes it. The receipt now says so
  in a note, and the README's Uninstall section explains it. The entry is harmless: with no LaunchAgent file, it
  starts nothing.
## Records

- **A compressed reply keeps its wire bytes.** When a reply arrives compressed, the record now holds the compressed
  bytes as they were on the wire beside the decompressed text. An older record of a compressed reply says in place
  that only the decompressed text is stored. In the request detail, a body shown decompressed, request or reply, is
  captioned "decompressed from <coding>" instead of "verbatim".
- **Plain http from programs Claude Code, Codex and Hermes start goes through trocar too.** `trocar on` set only
  `HTTPS_PROXY` in their settings or `.env`, so a tool or helper they started sent plain `http://` requests straight
  out, past trocar. It now sets every proxy variable each one reads (`HTTP_PROXY` as well, and `ALL_PROXY` for Codex
  and Hermes), in both spellings, and `trocar off` takes them out again. A value of your own goes back as it was. An
  agent started that way is captured like any agent; any other program is only forwarded: it gets a connection row
  (`not_captured`), not its bytes.
## Install and uninstall

- **Your machine trusts one trocar root, never two.** With trocar's install record deleted, a second `install` on
  macOS or Windows could not see the root the first one had made, so it made another one and trusted that too; a
  later `uninstall` took out only the new one, and the earlier root stayed trusted. `install` now checks your user
  trust store first: a trocar root that its record does not list stops it before it writes anything, exit 1, with
  that root's fingerprint and the advice to run `trocar uninstall` first (`--json`: `error.code` `stray-root`; a
  trust store that cannot be read stops it the same way, `unreadable`). `uninstall` takes out every trocar root in
  your user trust store, with a record or without one, and trocar's root key with them; each is listed in the
  receipt, and one that could not be removed is named, with the command that removes it, and exits 1.
