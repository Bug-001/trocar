# 2026-11-06

## Capture

- **A proxy address of trocar's own left in a settings file is no longer taken for yours.** When the install record
  was lost while a settings file still pointed at trocar's local proxy, the next `trocar on` recorded that address as
  your own proxy (the Claude desktop app's PAC setting was even read as your own egress, and `on` did not write it),
  and the `trocar off` after it put the address back, so the agent pointed at a closed port. `trocar on` now takes such
  a value out in the same single write that points the file at trocar, and keeps one backup of your file without
  that address (so the backup holds no password of trocar's proxy); `trocar off` leaves the key out. A proxy of your own on
  another local port is kept as before.
- **trocar no longer keeps the password of its local proxy in the install record or in backups.** The install record
  now holds that password only as a fingerprint, so the record, and the backups made from your files, no longer
  carry a credential. One `on` writes each settings file once and keeps one backup of it, with your bytes from before
  trocar changed it. Backups made by an older trocar can still hold the password: `trocar doctor` names each one, and
  you can remove it.
- **A `NO_PROXY` of your own is no longer taken for your proxy.** With a `NO_PROXY` in the settings `trocar on`
  writes to (Claude Code's `settings.json`, for one) and no proxy of your own, trocar read that bypass list as the
  proxy to chain through, so the agent's requests failed where they went direct before. Trocar now takes only the
  proxy setting you had, and `trocar status` shows the upstream as direct.
- **`trocar on` and the board now say that requests to this computer are not captured.** The settings `trocar on`
  writes send `localhost`, `127.0.0.1` and `::1` straight to their target, so a model or relay running on your own
  computer was never captured, and nothing said so. On macOS and Windows the `on` receipt now has one note naming
  those addresses when this run wrote such a setting, `trocar status` shows it under that agent, and the board's
  capture page shows it in that agent's technical details. Kimi Code's launch wrapper sends them to trocar, so it
  gets no such note.
- **On macOS and Windows, a certificate file of yours that replaces an agent's trusted roots no longer breaks its first
  connection.** When Hermes's `ssl_ca_cert` for a provider names a bundle without trocar's certificate, trocar decrypted
  the first connection anyway, Hermes refused it (`unknown CA`), and only then did trocar pass its connections through.
  trocar now reads that file before the first connection and, when trocar's certificate is not in it, passes the
  connections through from the start and records `replace-without-ca`; `trocar install` appends its certificate to your
  file, to each one when providers name different files, and `trocar status` reports the one that lacks it. A path
  written `~/…` is read under your home everywhere. A file that already holds trocar's certificate, as `install`
  leaves it, is captured as before. When a provider names such a file after `install`, `trocar status` no longer calls
  it "not yours": it reports `replace-without-ca`, as the capture does, or the certificate in effect when the file
  already holds trocar's certificate.
## Capture on / off

- **On Linux, `trocar off` no longer stops the collector.** The daemon and the board keep running, as on macOS and
  Windows. `off` takes trocar's links off, and once the connections it was relaying are through, the capability helper
  exits, so no capture path of trocar's is left in the kernel; `--now` cuts them and the helper exits at once. The next
  `on` starts the helper again without waiting for the daemon to start, so it is quicker. A login with nothing on starts
  the daemon with no helper, and a helper that crashed is not restarted until the daemon restarts.
- **The `off` receipt says what the daemon does.** It now reads `The daemon (pid N) keeps running.`
- **On macOS and Windows, `trocar off --now` after a plain `trocar off` cuts what the first `off` left running.** A
  plain `off` lets a streaming response finish and tells you to run `trocar off --now` to cut it, but that second
  command cut nothing: it listed the same connections again and the stream ran to its end. It now cuts them, marks them
  `cut-by-off`, and the receipt counts them as cut. With nothing left running it does nothing and exits 0.
- **`trocar on` is faster, on every OS.** With everything already on, `on` took 720 to 870 ms on Linux. It no longer
  rebuilds `~/.trocar/bin/trocar-off` to find out that nothing changed, reads no certificate it will not write, saves
  the install record only when it changed, and asks the root store once instead of twice. `trocar-off` now has one more
  line at its top, a digest, so `on` can tell that the file is current without rebuilding it. The next `on` after you
  update rewrites the file once to add that line. A copy that is lost, edited or out of date is still written again.
  An `on` that turns agents on also waits on the disk less: on macOS and Windows it saves the install record about once per
  file it changes, where it saved it up to three times, and on every OS the lock that keeps two commands apart is no longer flushed
  to disk. Wiring every agent after an `off` makes about a third fewer disk flushes. The collector no longer rewrites its
  copy of what is on when `on` already wrote the same thing, so each agent keeps the time it was last turned on or off. When `on` has to start the
  collector, it looks for it every 25 ms for the first half second, where it looked every 250 ms. A collector that
  has just started answers `on` before it has read the board's files from disk; the first board page after a start can
  take a little longer.
- **On macOS and Windows, a `trocar on` that is running stops when you run `trocar off`.** `off` marks capture off
  before it waits for the lock `on` holds, but `on` went on wiring every agent while `off` waited. `on` now looks at
  that mark before each agent and while it waits for the collector to start: it stops there, keeps the record of
  what it already wrote, says why with the code `stopped-by-off`, and exits 1. `off` then undoes everything. On Linux
  `on` already stopped; its receipt now carries the same `stopped-by-off` code, where it said only `failed`.
- **An agent `on` does not route this time keeps no proxy setting from an earlier `on`.** When `on` writes no entry for
  an agent (for example Claude Desktop while the system proxy is a PAC script, while the system proxy needs a login, or
  under a managed policy), the setting an earlier `on` wrote stayed in the agent's config and still pointed at trocar.
  `on` now takes it out the way `off` does: your earlier value comes back, and what trocar created goes. A value trocar
  has no record of stays as it is; `on` still says why the agent is not routed. If that file cannot be changed (it is
  read-only, or a link), `on` still goes on to the other agents and says the earlier setting is still there; `off` tries
  again.
  `on` now reads the system proxy itself (once, and only when Claude Desktop is set up), so a PAC script there is seen;
  before, it was never read and Claude Desktop stayed routed. When `on` does not finish, the first line of its receipt
  names only the agents that did not finish, each row says why in plain words, and a long path stays whole on its line.

- **`off` without an install record no longer leaves pi, DeepSeek dsh and Kimi pointed at a closed door.** When the
  install record is gone or unreadable, `off` undoes what trocar changed by trocar's own marks. On macOS and Windows it
  left out the switch files `on` writes for these three agents (`~/.trocar/collector/switch/<agent>`). Those files
  still named the door that the same `off` had just closed, so the next pi, dsh or Kimi could not connect at all. `off`
  now deletes them as well. `~/.trocar/bin/trocar-off` gets the fix the next time `install` runs; `trocar doctor` says when it is out of date.
- **`off` without an install record also takes the proxy setting out of Claude Code, VS Code, Claude Desktop and Z-Code.**
  On macOS and Windows, `on` points a proxy setting in these apps' own config at trocar's local proxy: Claude Code's
  `settings.json` (`env.HTTPS_PROXY`, `env.HTTP_PROXY`), VS Code's `http.proxy` (for Kimi's extension), the applied Claude Desktop
  configuration (`egressProxyPacUrl`) and Z-Code's `network.httpProxy`. With the install record gone, `off` left
  these settings in place, so the apps kept using a closed port. The next `on` also saved trocar's own address as
  the user's original setting. `off` now removes a setting when it points at a local port that trocar recorded for
  its proxy (`~/.trocar/collector/ingress.json`). It puts back the value from trocar's backup of the file, or deletes the key
  if the backup has none. A proxy of your own on another local port stays as it is. If trocar cannot read
  `ingress.json`, it changes nothing, and the receipt names each setting it could not check. A config file that no
  longer parses but still holds trocar's address is left as it is, and `off` names it and exits 1.
- **`off` without an install record no longer removes trocar's certificate settings.** The certificate settings that
  `install` writes belong to `install` and `uninstall`, but with the install record gone `off` removed them too: Claude
  Code's `env.NODE_EXTRA_CA_CERTS`, Z-Code's `network.caCertFile`, the certificate block in Codex's and Hermes's `.env`,
  and the trust plugins of OpenCode, pi and DeepSeek dsh. After that, `on` refused Z-Code until `install` ran again.
  `off` now leaves all of them as they are; `uninstall` still removes them, with or without the record.
- **`off` without an install record no longer deletes your setting when a backup cannot be read.** To undo a value
  trocar replaced in a JSON settings file, `off` takes your old value from the newest backup of that file in
  `~/.trocar/backup/`. When that backup could not be read (not JSON, an unknown encoding, or a read error), `off` acted
  as if you had no value and deleted the key, although an older backup still held it. `off` now skips such a backup
  and takes your value from an older one. When no backup that it can read holds the value, `off` leaves the key as it is,
  names the backup it could not read, and exits 1. `uninstall` without an install record no longer deletes the backups
  of a file it could not undo: before, the receipt named a backup that `uninstall` had already removed.
- **`off` without an install record also takes out what `on` wrote next to the proxy setting.** On macOS and Windows,
  `off` without the record removed the proxy keys but left the rest: Claude Code's `env.NO_PROXY` / `env.no_proxy`, the
  `http.proxy` item in VS Code's `settingsSync.ignoredSettings`, the `env` or `network` object trocar had created for
  them (left as `{}`), and the Claude Desktop configuration trocar created, with the `appliedId` in `_meta.json` that
  selects it. `off` now restores these from the newest backup trocar made before `on`, or removes them when the file had
  none of them. A file that trocar created and that is now empty is deleted. A `NO_PROXY` you changed while trocar was
  on stays as it is. If no readable backup can show your earlier value, the file stays as it is, and the receipt names
  it. The receipt now lists each file once and counts files, not keys.

  `HTTPS_PROXY` in their settings or `.env`, so a tool or helper they started sent plain `http://` requests straight
  out. It now sets every proxy variable each one reads (`HTTP_PROXY` as well, and `ALL_PROXY` for Codex and Hermes),
  in both spellings, and `trocar off` takes them out again. A value of your own goes back as it was.
- **A `NO_PROXY` of your own is no longer taken for your proxy.** With a `NO_PROXY` in the settings `trocar on`
  writes to (Claude Code's `settings.json`, for one) and no proxy of your own, trocar read that bypass list as the
  proxy to chain through, so the agent's requests failed where they went direct before. Trocar now takes only the
  proxy setting you had, and `trocar status` shows the upstream as direct.
- **Claude Desktop's plain http is captured too.** trocar's proxy settings file (PAC) used to send the app's
  unencrypted `http:` requests the app's own way, past trocar, so they were never recorded. They now go through
  trocar like the app's https and WebSocket connections, and take the app's own way only if trocar does not answer.
  Hosts on your proxy bypass list and this machine's own addresses are handled as before; after `trocar off` the
  file again names only the app's own way.

## Install and uninstall

- **Your machine trusts one trocar root, never two.** With trocar's install record deleted, a second `install` on
  macOS or Windows could not see the root the first one had made, so it made another one and trusted that too; a
  later `uninstall` took out only the new one, and the earlier root stayed trusted. `install` now checks your user
  trust store first: a trocar root that its record does not list stops it before it writes anything, exit 1, with
  that root's fingerprint and the advice to run `trocar uninstall` first (`--json`: `error.code` `stray-root`; a
  trust store that cannot be read stops it the same way, `unreadable`). `uninstall` takes out every trocar root in
  your user trust store, with a record or without one, and trocar's root key with them; each is listed in the
  receipt, and one that could not be removed is named, with the command that removes it, and exits 1.
- **`trocar doctor` names a trocar root that no install record lists.** On macOS and Windows, such a root in your user
  trust store is now a problem of `doctor` (exit 1), named by its thumbprint, with the fix `trocar uninstall`, then
  `trocar install` (`--json`: finding `stray-root`). A trust store that cannot be listed is reported as not judged
  (exit 3), never as no root. `trocar status` does not list the store for this; Linux keeps its root in no trust store.

- **On macOS and Windows, `install` and `uninstall` refuse a `HOME` that is not your account's home.** The login entry
  (launchd, the Windows login task) starts the background process with your account's own home, not the shell's
  `HOME` (`USERPROFILE` on Windows). Run as `HOME=/tmp/x trocar install`, install wrote one home while its background
  process used the other, so install reported it as not started, and a later `uninstall` left a background process
  it could neither find nor stop. Both commands now stop before they read or write anything, exit 2, and name both
  homes (`--json`: `error.code` `home-mismatch`). Run them with `HOME` unset, or set to your account's home.
  Linux is not checked: systemd `--user` uses its own `HOME`, and enabling the unit fails at once when that is another home.

- **A login with trocar not installed no longer restarts the background process every few seconds.** When the login
  entry was there but the install was not (an `install` that never finished, or certificates removed by hand), the
  background process refused to run and the system started it again every few seconds, on Linux, macOS and Windows.
  It now stops after one try and leaves one record saying why. `trocar daemon` run by hand in a terminal still exits 1.

- **The background process refuses a Node that is too old, as `trocar on` does.** On macOS and Windows, `on` refused a
  Node below trocar's floor, but the background process that launchd or the login task starts ran on it anyway. It now
  refuses before it opens anything, leaves one failure record (`node-too-old`) that names the Node it runs on and
  the floor, so `trocar status` and `trocar doctor` show it, and exits 0 so the system does not restart it into the
  same refusal. The login entry starts a fixed Node: update that Node, or run `trocar install` with a newer Node so
  the entry starts that one. `trocar install` and `trocar on` no longer wait about 15 seconds and report a
  collector that does not answer when the background process refused to start: they stop at its record and print
  its reason.
## Data

- **`trocar classes` counts only captured records as records.** The storage numbers counted the index's own files
  (session projections kept for fast reading) as captured records, so `records_bytes` could read ten times the size of
  what was captured. Those files now count toward the index.
## Turning off

- **`trocar off` right after the collector started no longer crashes it on macOS and Windows.** For up to a second
  after it began answering, the collector was still reading its own process details, and an `off` that asked it to
  exit in that window made it crash instead of stopping. It now finishes that read and stops cleanly, with nothing left
  behind; `off` is not refused or held up meanwhile.
- **A program that never answers trocar's password request now shows up as a failure.** trocar's proxy asks a
  program for its password (a 407 reply) when the program connects without it, or with one trocar cannot read.
  Most programs answer at once and nothing is recorded. A program that never comes back with the password used to
  leave no trace, so its lost traffic was silent. Now, when the same program has not come back with the right
  password within ten seconds, the board shows one failure naming the program and what it sent instead. The
  password itself is never written. A program that keeps failing gets one line until it gets through.
- **`trocar uninstall` on Windows says the scheduled task it deleted as a task.** The receipt listed
  `\trocar\collector` under Removed as if it were a path on the current drive; it now reads
  "the scheduled task \trocar\collector".
- **`trocar classes` names an unreadable class table as `~/.trocar/classes.json`.** When the table could not be
  read or parsed, the message printed the full home directory; it now shortens it to `~` like every other path.
- **`uninstall` without an install record takes out every certificate carrier `install` placed.** On macOS and
  Windows, with trocar's install record deleted, `uninstall` used to leave Kimi Code's install-folder wrapper (the
  real `kimi` stayed in `.trocar-real`), dsh's plugin and its row in `~/.dsh/cordis.patch.yml`, pi's extension, and
  the certificate block trocar adds at the end of your own certificate file. It now finds each of them where
  `install` puts it and takes it out: the real program goes back under its own name with its own mode, only
  trocar's row or block leaves your file, and a plugin goes only while it holds exactly what trocar wrote. One it
  cannot take out as it is (the real program gone, a wrapper an agent update replaced, a plugin you edited) stays,
  is named with the reason and the command that takes it out, and `uninstall` exits 1. The plan (`--dry-run`, and
  the one printed before it asks) lists them, one row per file, also when two agents read the same certificate file.
- **A port held by trocar's own background process is no longer reported as taken, and a system proxy that cannot
  be read is no longer reported as changed.** When the background process was still starting or stuck and did not
  answer, `trocar on` recorded `engine-port-taken` for every door port and moved them; when that process is there
  (its control channel takes the connection, or its lock is alive), `on` now keeps the ports and records
  `door-unconfirmed`. A system proxy that could not be read was recorded as a
  change to "unreadable" and the doors stopped using the proxy last read; it is now one `system-proxy-unreadable`
  failure, the doors keep the last proxy read, and the next reading is compared with that one.
  Your certificate file is looked for wherever the agent reads its name: this shell's variable, the agent's own
  settings and, on macOS, the variable set with `launchctl setenv` (on Windows, your user environment). When none of
  them names it any more, the receipt says that trocar's block may still be at the end of that file and gives the
  command that takes it out (for example `SSL_CERT_FILE=<your certificate file> trocar uninstall`).
- **The `uninstall` receipt no longer says backups were kept that it deleted, and names the real program it puts
  back.** Without an install record, the receipt listed the backups it removed and then a note saying they were left
  in place. That note is gone from `uninstall`; `off`, which does keep them, names them under `~/`. A Kimi Code
  program put back in place of trocar's wrapper now has its own row, with the install record too. A root's
  SHA-256 fingerprint is printed whole on a line of its own.

  `...`, often mid-sentence. Now the whole reason folds inside 80 columns, and any command in it still prints on a
  line of its own. The failure above reads as a sentence: which program and pid, for which agent, how many times
  it was asked, how long trocar waited, and that its connection was not made.
  failure, the doors keep the last proxy read, and the next reading is compared with that one. The refusal `on`
  prints for a background process that does not answer no longer names a spec section. In `trocar status
  --failures` these lines name the agent and give only what the words above them do not say (the port kept,
  the port moved to); the `on` note for a moved port is in words instead of its code.

## Windows

- **SYSTEM is refused with UAC off too.** `on`, the daemon, `off` and `uninstall` refuse a SYSTEM token, but on a
  machine with UAC turned off a SYSTEM token was taken for an administrator with no split token and let through. A
  SYSTEM token is now known by either of two signs Windows gives in every language — its user is SYSTEM, or its
  integrity level is System — and it is refused with `elevated-token` whatever UAC says. An administrator on a
  machine with UAC off is still let through, as before.
- **A certificate file or setting trocar cannot read is reported as not known.** When the certificate file your
  `SSL_CERT_FILE` or `NODE_EXTRA_CA_CERTS` names cannot be read, `trocar status` used to report the agent's
  certificate as changed (`entry-changed`); when the agent's own setting that names that file cannot be read, it
  treated the setting as naming no file and reported the certificate in effect. Both are now unknown: in `--json`
  the form's `certificate.in_effect` is `null` with the read code (`file-unreadable` or `config-unreadable`) and
  `user_file.state` is `unknown` with the reason; the text says which file could not be read. A process whose
  setting cannot be read is forwarded, not decrypted, with a `config-unreadable` record. When your trust store itself
  cannot be read, a form whose certificate is the root is also `in_effect: null` (its code `null`), no longer `false`:
  `null` is the one way `--json` says not known, and `false` always carries a code and a command.
- **The prebuilt Hermes desktop app on macOS is recognised.** Its backend starts Python with different interpreter flags
  than the installer's build, so it was not recognised as Hermes and none of its turns were captured. trocar now
  recognises any Python that loads Hermes's entry module, whatever flags it starts with.

- **Hermes installed with pip is captured on Linux.** A `pip install hermes-agent` puts a Python console script on your
  PATH, and that program was not recognised as Hermes: its connections went direct, and nothing said so. trocar now
  recognises it like the installer's build, and judges its certificate settings the way a release build reads them.

- **A local proxy is shown by its port, not by the program behind it.** When an agent's traffic went through a proxy on
  this machine, `trocar status`, `trocar doctor` and the chain `trocar on` prints named that hop after the program
  listening on the port. For a VPN client, that name is the product. The hop is now its port (`:7897`), with the
  listener's pid in `trocar status <harness>`, in the text and in `--json`.
## Uninstall

- **A refused `trocar uninstall` no longer takes the daemon away.** When the daemon did not confirm that its doors were
  shut, `uninstall` stopped with exit 1, but only after it had already removed the login autostart and, on macOS,
  stopped the daemon with it (on Windows it deleted the scheduled task). Agents still pointed at trocar then had
  nothing to connect to. Now nothing about the autostart or the daemon changes until the doors are confirmed shut; a
  refused run leaves both as they were and says why.
## Off and uninstall

- **`trocar off` and `trocar uninstall` delete a file trocar created only if it still holds what trocar wrote.** A plugin,
  launch script or switch file that has changed since trocar wrote it, or that cannot be read, now stays where it is.
  The receipt lists it under what was left, with the reason, and the next run checks it again. Before, these files
  were deleted whatever they held. The program trocar moved aside for a wrapper follows the same rule.
