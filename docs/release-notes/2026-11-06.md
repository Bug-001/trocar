# 2026-11-06

## Capture

- **The prebuilt Hermes desktop app on macOS is recognised.** Its backend starts Python with different interpreter flags
  than the installer's build, so it was not recognised as Hermes and none of its turns were captured. trocar now
  recognises any Python that loads Hermes's entry module, whatever flags it starts with.

- **Hermes installed with pip is captured on Linux.** A `pip install hermes-agent` puts a Python console script on your
  PATH, and that program was not recognised as Hermes: its connections went direct, and nothing said so. trocar now
  recognises it like the installer's build, and judges its certificate settings the way a release build reads them.
- **trocar says that OpenCode can stall at start where npm is out of reach.** With trocar's plugin in its config
  directory, OpenCode 1.x installs `@opencode-ai/plugin` there, and every start waits for that install until it has
  succeeded once. On a network where the npm registry cannot be reached, each start stalls until the install gives up,
  about 6.5 minutes measured. The note `install` prints on Linux, and the note `on` prints on macOS and Windows, now say
  so. They used to say the fetch happens once.
- **No false "refused trocar's certificate" when an agent exits.** An agent that quits closes the spare connections it
  had opened and never used. When that happened just after they were set up, trocar read them as the agent refusing
  its certificate: `status` showed a critical `trust-rejected` for a process whose calls were all captured. trocar now
  waits a second on such a close from a process that has already used its certificate; if the process is gone by
  then, the close counts for nothing. A process that is still running is judged as before.
- **On Linux, `trocar off` no longer stops the collector.** The daemon and the board keep running, as on macOS and
  Windows. `off` takes trocar's links off, and once the connections it was relaying are through, the capability helper
  exits, so no capture path of trocar's is left in the kernel; `--now` cuts them and the helper exits at once. The next
  `on` starts the helper again without waiting for the daemon to start, so it is quicker. A login with nothing on starts
  the daemon with no helper, and a helper that crashed is not restarted until the daemon restarts.
- **The `off` receipt says what the daemon does.** It now reads `The daemon (pid N) keeps running.`
## Linux

- **`trocar status` says whether each agent is set up.** On Linux, each agent in `trocar status` and on the board now
  carries `setup`: ready, needed (with the reason) or unknown. An agent installed after trocar is listed too.
- **`trocar on <agent>` refuses only the agent that is not set up.** If the certificate entry trocar installed for an
  agent is missing or was overwritten, `trocar on` leaves that agent off with `setup-needed` and names the two
  commands: `trocar install`, then `trocar on <agent>`. `trocar install` (or Set up) puts that entry back, and undoing it later
  restores the value the agent had left there. The other agents named in the same command still turn on.
- **Set up on the board works on Linux.** It adds only what that agent is missing and needs no `sudo`; when it cannot put an entry back
  (for example the file is now a link to nothing), it refuses with `setup-needed` and the reason, and changes nothing.
- **An agent counts as installed when its own files or command are there.** On Linux, `trocar status` and `trocar on` now
  decide whether an agent is installed from its own install folder, config folder or command on your PATH (the PATH of
  the terminal you last ran trocar from), not from whether trocar would have something to write for it. Claude Code and
  Codex also count when only their VS Code extension is installed, including one that VS Code's Remote - SSH put on this
  machine; trocar then sets them up in the same files as their command-line versions (Codex once it has its own
  `~/.codex` folder). An agent that is
  installed but has nothing trocar can set up (for example Codex before its first run, or Kimi Code without the PATH
  line its installer adds) shows `setup` needed, and `trocar on`
  leaves it off with `setup-needed`. The board's Set up for such an agent says why it cannot set it up and changes nothing,
  instead of saying there is nothing to set up.
- **`trocar install` writes nothing for an agent that is not installed.** On Linux, `trocar install` used to add its
  certificate entry or plugin for every agent it knows, so an empty home got `~/.claude/settings.json`,
  `~/.config/opencode/plugins/trocar-ca.js`, `~/.dsh/cordis.patch.yml` and `~/.pi/agent/extensions/trocar-ca.js`. It now
  sets up only the agents whose own files or command are there, and lists only those as installed. Run `trocar install`
  again after installing a new agent. What it set up for an agent you later removed stays until `trocar uninstall`. Set up on
  the board refuses an agent that is not installed with `setup-needed` and changes nothing.
- **The board and the terminal agree on an agent whose folder you moved.** On Linux, when you point an agent at another
  folder with its own variable (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `DSH_HOME`, `HERMES_HOME`, `PI_CODING_AGENT_DIR`,
  `XDG_CONFIG_HOME`, `XDG_DATA_HOME`), trocar now remembers that variable's value from the terminal you last ran it in,
  next to your PATH. The board's status and Set up, which run in the background service without your shell's variables,
  now look in the same folder as `trocar status` and `trocar on`.
- **trocar says when Kimi Code's VS Code extension is not captured.** On Linux the extension's calls cannot be captured:
  VS Code uses its own certificate list there, which only your login environment can extend, and trocar does not change
  that environment. When the extension is installed (also by Remote - SSH), `trocar install`, `trocar on` and
  `trocar status` now say so for Kimi Code, and `trocar status --json` lists it under `setup.uncaptured`.
- **`trocar status --json` says whether each agent is on this machine.** Each agent in `harnesses` now has `present`:
  `true` when one of its own forms is installed here, `false` when none is (it is listed because trocar set it up
  before), `null` when that could not be read. A new key; nothing else in the document changes. On every platform.

## All platforms

- **A certificate entry trocar cannot read is no longer reported as overwritten.** When the file holding it cannot be
  read (for example its permissions changed), `setup` is now `unknown` with the reason, and `trocar on` turns the agent
  on with a note instead of refusing it as `setup-needed`.
## The board

- **The capture page and the capture log no longer show a proxy password in their technical details.** A reason the
  capture service reported in its own words, such as why it could not reach an upstream proxy, appeared as written,
  `user:password@` included, both on screen and in what **Copy** put on the clipboard. Every value under **Technical
  details** and every log row's sentence now shows that part as `***@`, as the rest of the page already did.
- **Claude Desktop's plain http is captured too.** trocar's proxy settings file (PAC) used to send the app's
  unencrypted `http:` requests the app's own way, past trocar, so they were never recorded. They now go through
  trocar like the app's https and WebSocket connections, and take the app's own way only if trocar does not answer.
  Hosts on your proxy bypass list and this machine's own addresses are handled as before; after `trocar off` the
  file again names only the app's own way.
## The command line

- **`trocar uninstall` names a file it left in place once.** When the reason a file could not be taken out already
  began with the file, the receipt printed the file twice on one line, the second time in full. It now prints it
  once, with the rest of the reason after it.
- **A `NO_PROXY` of your own is no longer taken for your proxy.** With a `NO_PROXY` in the settings `trocar on`
  writes to (Claude Code's `settings.json`, for one) and no proxy of your own, trocar read that bypass list as the
  proxy to chain through, so the agent's requests failed where they went direct before. Trocar now takes only the
  proxy setting you had, and `trocar status` shows the upstream as direct.
## CLI

- **`trocar status | head` no longer crashes.** When the program reading trocar's output stopped early (`head`, `less`
  quit before the end, a closed pipe), trocar threw a `write EPIPE` error with a stack trace, possibly halfway through
  a command. The output that has no reader is now dropped, and the command finishes with its own exit code.
- **Kimi Code's PATH line goes where your shell always runs it.** trocar's line in your shell rc came right after the
  Kimi installer's own PATH line. When that line sat inside an `if`, a `case`, a loop or a function, trocar's line landed
  inside it too and ran only when that block did, so `kimi` could miss its launch shim and not be captured. The line now
  goes at the end of the rc file. A line already in your rc stays where it is until you run `trocar off`,
  `trocar uninstall` and `trocar install`.
  `kimi` is not captured in these shells, and `status` reports a running `kimi` that did not start through its shim:
  - a shell that leaves the rc before the end (`exec fish`, `exec tmux`, or a top-level `return` or `exit`). This is new:
    those lines used to be fine when they came after the installer's line;
  - an rc whose last line is unfinished (a trailing `\`, an unclosed block or heredoc);
  - a shell where a function adds Kimi's folder only after the rc has been read.
- **The standalone Codex command line is no longer listed as verified on Windows.** It had not been measured there, yet
  its description claimed it was. It now shows as not verified yet on Windows. On macOS it has been measured and stays
  verified.
## Windows

- **SYSTEM is refused with UAC off too.** `on`, the daemon, `off` and `uninstall` refuse a SYSTEM token, but on a
  machine with UAC turned off a SYSTEM token was taken for an administrator with no split token and let through. A
  SYSTEM token is now known by either of two signs Windows gives in every language — its user is SYSTEM, or its
  integrity level is System — and it is refused with `elevated-token` whatever UAC says. An administrator on a
  machine with UAC off is still let through, as before.
## Status

- **`trocar status` says which harness needs setting up.** A harness you installed after trocar was listed under
  `not installed:`, and you learned it needed `trocar install` only when `trocar on` refused it. It now has its own row
  in the summary with `set up first: trocar install`, as does a harness whose own update overwrote trocar's certificate
  file.
- **pi installed with npm, and pi in RPC mode, are captured on macOS.** They were judged only through the official
  installer's pi. Both are now measured on macOS with nothing but trocar's pi extension adding its certificate.
  On Windows they stay not verified until measured the same way.
## Status, doctor and on

- **A local proxy is shown by its port, not by the program behind it.** When an agent's traffic went through a proxy on
  this machine, `trocar status`, `trocar doctor` and the chain `trocar on` prints named that hop after the program
  listening on the port. For a VPN client, that name is the product. The hop is now its port (`:7897`), with the
  listener's pid in `trocar status <harness>`, in the text and in `--json`.
## Uninstall

- **A refused `trocar uninstall` no longer takes the daemon away.** When the daemon did not confirm that its doors were
  shut, `uninstall` stopped with exit 1, but only after it had already removed the login autostart and, on macOS,
  stopped the daemon with it (on Windows it deleted the scheduled task). Agents still pointed at trocar then had
  nothing to connect to. Now nothing about the autostart or the daemon changes until the doors are confirmed shut; a
  refused run leaves both as they were and says why.
## Off and uninstall

- **`trocar off` and `trocar uninstall` delete a file trocar created only if it still holds what trocar wrote.** A plugin,
  launch script or switch file that has changed since trocar wrote it, or that cannot be read, now stays where it is.
  The receipt lists it under what was left, with the reason, and the next run checks it again. Before, these files
  were deleted whatever they held. The program trocar moved aside for a wrapper follows the same rule.
