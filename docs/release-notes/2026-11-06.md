# 2026-11-06

## Capture

- **The prebuilt Hermes desktop app on macOS is recognised.** Its backend starts Python with different interpreter flags
  than the installer's build, so it was not recognised as Hermes and none of its turns were captured. trocar now
  recognises any Python that loads Hermes's entry module, whatever flags it starts with.

- **Hermes installed with pip is captured on Linux.** A `pip install hermes-agent` puts a Python console script on your
  PATH, and that program was not recognised as Hermes: its connections went direct, and nothing said so. trocar now
  recognises it like the installer's build, and judges its certificate settings the way a release build reads them.
- **trocar says that OpenCode can stall at start where npm is out of reach.** With trocar's plugin in its config
  directory, OpenCode 1.x installs `@opencode-ai/plugin` there, and every start waits for that install until it has
  succeeded once. On a network where the npm registry cannot be reached, each start stalls until the install gives up,
  about 6.5 minutes measured. The note `install` prints on Linux, and the note `on` prints on macOS and Windows, now say
  so. They used to say the fetch happens once.
- **No false "refused trocar's certificate" when an agent exits.** An agent that quits closes the spare connections it
  had opened and never used. When that happened just after they were set up, trocar read them as the agent refusing
  its certificate: `status` showed a critical `trust-rejected` for a process whose calls were all captured. trocar now
  waits a second on such a close from a process that has already used its certificate; if the process is gone by
  then, the close counts for nothing. A process that is still running is judged as before.
- **On Linux, `trocar off` no longer stops the collector.** The daemon and the board keep running, as on macOS and
  Windows. `off` takes trocar's links off, and once the connections it was relaying are through, the capability helper
  exits, so no capture path of trocar's is left in the kernel; `--now` cuts them and the helper exits at once. The next
  `on` starts the helper again without waiting for the daemon to start, so it is quicker. A login with nothing on starts
  the daemon with no helper, and a helper that crashed is not restarted until the daemon restarts.
- **The `off` receipt says what the daemon does.** It now reads `The daemon (pid N) keeps running.`
## Linux

- **`trocar status` says whether each agent is set up.** On Linux, each agent in `trocar status` and on the board now
  carries `setup`: ready, needed (with the reason) or unknown. An agent installed after trocar is listed too.
- **`trocar on <agent>` refuses only the agent that is not set up.** If the certificate entry trocar installed for an
  agent is missing or was overwritten, `trocar on` leaves that agent off with `setup-needed` and names the two
  commands: `trocar install`, then `trocar on <agent>`. `trocar install` (or Set up) puts that entry back, and undoing it later
  restores the value the agent had left there. The other agents named in the same command still turn on.
- **Set up on the board works on Linux.** It adds only what that agent is missing and needs no `sudo`; when it cannot put an entry back
  (for example the file is now a link to nothing), it refuses with `setup-needed` and the reason, and changes nothing.

## All platforms

- **A certificate entry trocar cannot read is no longer reported as overwritten.** When the file holding it cannot be
  read (for example its permissions changed), `setup` is now `unknown` with the reason, and `trocar on` turns the agent
  on with a note instead of refusing it as `setup-needed`.
