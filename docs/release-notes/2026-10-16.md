# 2026-10-16

- `asight install` is its own command (D55): on Linux it installs the collector CA and its trust entries once. It prints the plan and
  asks first (`--yes`, `--dry-run`, `--json`). `asight collector install` now means `asight install`; plain `asight install` is no longer an
  alias of `asight on`. On macOS / Windows it refuses for now (exit 1) and changes nothing: there `asight on` still installs the certificates
  itself, and a root installed first would stop it starting.
- macOS / Windows: `asight uninstall` refuses while capture is on, or while a process started during an on window may still use a door; it names
  them and changes nothing — run `asight off` first. Offline, it undoes install in reverse and removes the root's key last.
- Linux: `asight on` refuses with `cert-not-installed` (exit 1) until `asight install` has run: `on` no longer writes a certificate item, so run
  `asight install` once first.
- `asight off` leaves every certificate item `install` wrote (the config keys, bundles, loader lines, plugins, wrappers, certificate blocks and the
  root): a later `asight on` needs no install again. Only `asight uninstall` takes them out. The standalone `asight-off` is version 14 for this.

## macOS / Windows: the collector model (RFC 4.11, D57)

- `asight install` works on macOS and Windows now, and replaces the "refuses for now" above. It makes this machine's own root, whose key cannot
  be exported, adds it as a user-level root (one OS prompt: the login password on macOS, yes / no on Windows), and puts the certificate only
  where the root does not reach: Z-Code's `network.caCertFile`, a wrapper in Kimi's install directory, DeepSeek `dsh`'s plugin, Claude Code's
  settings when you chose `CLAUDE_CODE_CERT_STORE=bundled`. A certificate file of your own gets a marked block at its end. Nothing goes into the
  login environment, no administrator step, no launcher, no `PATH` change.
- `asight on` on macOS / Windows writes only proxy entries (a proxy key in the agent's own config) or a switch file per harness, after the
  daemon has opened the doors. It refuses with `cert-not-installed` until `install` has run. `off` removes them; a process started while on
  keeps its door, which only forwards, and `status` says how many are left.
- `asight on --opt-in …` (and `--opt-in=…`) exits 2 with 「D57 起没有点名项」 and changes nothing; `asight help on` no longer lists it. The
  Kimi / OpenCode PATH shims, the Claude Desktop and dsh launchers and the opt-in certificate items are gone; Claude Desktop is routed by its
  config library's `egressProxyPacUrl` instead.
- `asight status` gains a certificate block (`cert-not-installed`, `cert-key-missing`, `cert-intermediate-unavailable`, `not-users-file`) and
  the proxy chain per harness: agent → door → upstream, with where the upstream comes from.
- `asight status <harness>` on macOS / Windows draws each form's chain (it used to say the path could not be worked out) and prints per form a
  `certificate:` and a `proxy:` line, then what asight wrote beside your own value; `status --json` carries them under `forms`.
