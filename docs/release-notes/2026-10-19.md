# 2026-10-19

## Windows: `status`, `status <harness>` and `doctor` are about four times faster

On Windows these three read-only commands used to start a `powershell.exe` for
every question they had — the process table, the daemon pid's identity, the
holder poll inside the daemon, and a resident helper that the network facts
started only to close again. Each start costs about 450 ms on the test machine,
and `status` took 2.4 s.

The daemon already keeps one read-only PowerShell helper warm, so now the
commands ask that one over the control channel (`POST /helper`, a closed subset
of read verbs), and the daemon's own holder poll reads it too. Measured on the
Windows test machine, five runs each:

| command | before | after |
|---|---|---|
| `asight status` | 2,414 ms (p95 2,765) | **504 ms** |
| `asight status codex` | 2,582 ms (p95 2,949) | **581 ms** (p95 612) |
| `asight doctor` | 2,687 ms (p95 3,075) | **650 ms** |

A whole `status` now starts one subprocess (`certutil`, 40 ms) instead of four.
Nothing changed about what they report: when the daemon cannot answer a read,
the command asks the OS itself exactly as before and says in `errors` why it
had to. macOS is unchanged (190 ms). The switches were measured too, and they
did change — see the next section.

What is left is no longer the OS: it is node's own start plus the modules the
CLI loads before it does anything, so these commands are still at the 0.5 s
line of D62.

## The switches: `off` then `on` in a fifth of a second

`asight off` used to stop the daemon on every platform, so the next `asight on`
paid for a cold start — a daemon, its engine, its doors and its helpers. Off
and on again took 6.7 to 9.7 s.

In proxy mode (macOS and Windows) `off` now closes the doors and leaves the
daemon running, idle: the same state the machine is in right after a login.
Nothing is captured in that state — no door is open, nothing of asight is on
an agent's path — and `on` is a door opening, not a start. Linux keeps
drain-and-exit, because there the daemon only exists while the helper steers.

Measured on a macOS test machine: **`on` 215 ms, `off` 236 ms**. On the Windows test
machine `off codex` went from 2,034 ms to **315 ms** and `on codex` from 990 ms to
**561 ms**. An idle daemon costs 80 ms of CPU per minute and 1.8 wakeups per
second.

Two cases `asight daemon` now distinguishes: another daemon already answering
is nothing to do, so it exits 0 (a non-zero exit would have the platform
re-launch it for as long as the other one lives). The control endpoint held by
something that does *not* answer is the opposite — it records a
`control-endpoint-held` failure and exits 1, so `asight status` shows it
instead of the machine quietly having no collector.

## Queries are answered by a warm worker, over an index the daemon keeps current

`asight query` and the board now ask the daemon first, and a low-priority query
worker in it answers. It stays warm between queries and holds what it read, so
the questions you ask while looking at one session cost nothing twice.

The worker is never a prerequisite. With no worker yet the daemon says so at
once and the asking side reads the records itself, at local speed, while the
same query warms a worker for the next one; with no daemon at all the command
reads locally. Every path returns the same document, byte for byte.

Underneath it, the daemon keeps the segment index of what it writes current, by
appending to it as the records arrive — so no query ever pays to build an index
for a corpus that was just captured. A query that still had to build one says
so in the document's `errors` (`index-cold`), instead of charging you seconds
without a word.

Measured on a macOS test machine: `asight query session --id` 162 ms through the
daemon against 548 ms locally, and inside the worker a query about the session
already on screen is 11 ms or less.

## `--cursor` is now `--after`

**Breaking.** The paging flag of `asight query` (and of the board's data
requests) is `--after`. There is no `--cursor` alias: on some machines security
software SIGKILLs any `node` process whose command line contains the old word,
which made the flag unusable where it was installed. The document field is
unchanged — `page.next` still carries the value you pass to `--after`.

## New failure codes you can see

All four are closed codes, with a reason, in `~/.asight/collector/flows/` and
in `asight status` (`--json`: the same codes):

- `index-failed` — the daemon could not keep a segment's index current. The
  records are on disk; the next query indexes them itself.
- `index-cold` — a reader's note in a query document: this query had to build
  the index itself, which is what made it slow.
- `query-failed` — the daemon's query worker crashed or went silent. The query
  is still answered, locally.
- `control-endpoint-held` — the daemon's control endpoint is held by something
  that does not answer (see above).

## Queries through the daemon are fast on Windows too

Three fixes, all found by a Windows test machine's acceptance of the release above and all
Windows-only in effect:

- **`asight query sessions` took 5.7 s and now takes 0.2 s.** The daemon relays
  the worker's answer straight into your socket, and it pauses the worker while
  that socket is full. On a Windows named pipe the last write of a 50-session
  list fills it — and the "socket has room again" event never arrives for a
  reply that is already complete, so the worker stayed paused and the NEXT query
  got nothing until the CLI gave up on the daemon (5 s) and answered locally.
- **`asight query segments` and `asight query classes` took ~0.7 s and now take
  ~0.2 s.** Both asked Windows for the identity of the daemon's process — one
  `powershell.exe` start, ~450 ms — only to label one segment as the one being
  written. A reader no longer asks: a segment is "writing" when the daemon's
  lock names it and was refreshed within the last five seconds. A daemon that
  died or a machine that rebooted now leaves no segment labelled `writing`.
- **The daemon's children really do run at low priority on Windows now.** They
  asked for nice 5, which Windows maps to NORMAL — i.e. above the daemon that
  forwards your agent's traffic. They now ask for "below normal" by name.

## `asight doctor` no longer cries wolf on a Mac right after install

Four fixes, all found on the author's own Mac a minute after installing main:

- **`entry-missing` and `proxy-changed` for claude-code, with every byte of
  asight's entry in place.** The Claude desktop app's config library has no
  applied entry until you make one, so `on` creates one. It was recorded twice —
  once as a file asight owns (hashed while still empty) and once as the key
  written into it — and the first record was stale from that moment, so `status`
  read a byte-intact entry as changed. A file asight creates is now carried by
  one record. `off` still deletes it, and the directory it made, and still takes
  only asight's key out of a file you wrote into while capture was on.
- **A dead proxy under asight's door told you to remove the key asight
  wrote.** With your own proxy quit and asight's door chained to it, `doctor`
  said `proxy-dead` and "Remove env.HTTPS_PROXY from …/settings.json" — the key
  that now holds the door; removing it changes nothing. It now says
  `upstream-unreachable` ("without asight it would not connect either") and, if
  you want off that proxy for good, names **your own** keys that still point at
  it, each one, around `asight off` / `asight on`. No remedy ever names a key
  asight wrote.
- **The restart step for the VS Code ChatGPT extension was the CLI's.** It said
  to end the managed `codex app-server` process; for the extension's own
  app-server the step is to reload the VS Code window. Each form of an agent now
  carries its own words, and the step comes from the form your process runs
  from.
- **The event log no longer flaps.** The daemon wrote `netenv-change` events
  whose before and after were the same ("off -> off"), and pairs seconds apart
  when one reading of the system proxy timed out. An event is written only when
  the summarized state really changes; one unreadable reading between two equal
  ones is not a change.

## New queries for the board: `traffic` and `overview`

- **`asight query traffic`** (and `GET /api/traffic`): one line per agent and
  host — requests, bytes sent and bytes received, when the pair was first
  seen — plus totals. It reads the segment index only. Byte sums cover the
  calls that recorded a size, so the totals say `is_floor: true`; a sum with
  nothing to add up is `null`, never 0.
- **`asight query overview`** (and `GET /api/overview`): the board's stats
  card over a `--since` / `--until` window — sessions, calls, bytes and token
  usage. Usage needs the replies, so it reads sessions newest first under a
  16 MiB budget and says in `coverage` how far it got.
- **`asight query calls --host <host>` and `--ref <segment>:<line>`.** `calls`
  now filters, counts and pages on the segment index, and reads back only the
  records of the page it returns, so it stays fast on a large corpus.
- **`as_of`** on every document read from the index (`sessions`, `calls`,
  `traffic`, `overview`, `classes`, `segments`): the time of the newest call
  the numbers were counted over.

## `asight status --json`: `changed[]` and `failures.groups`

The status document now lists every place asight changed or created for each
agent (`changed[]`; `null` when the install record cannot be read), and folds
capture failures into `failures.groups` by code, each with its count and first
and last time, newest first. The text output is unchanged.

## One index rebuild after the upgrade

The segment index now keeps bytes sent and bytes received apart, so its format
changed. Every segment's index is rebuilt once: the daemon does it after it
restarts, and a query that gets there first says `index-cold` in its `errors`
while it pays for it. Your records are not touched.
