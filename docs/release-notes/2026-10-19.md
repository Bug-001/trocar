# 2026-10-19

## Windows: `status`, `status <harness>` and `doctor` are about four times faster

On Windows these three read-only commands used to start a `powershell.exe` for
every question they had — the process table, the daemon pid's identity, the
holder poll inside the daemon, and a resident helper that the network facts
started only to close again. Each start costs about 450 ms on the test machine,
and `status` took 2.4 s.

The daemon already keeps one read-only PowerShell helper warm, so now the
commands ask that one over the control channel (`POST /helper`, a closed subset
of read verbs), and the daemon's own holder poll reads it too. Measured on the
Windows test machine, five runs each:

| command | before | after |
|---|---|---|
| `asight status` | 2,414 ms (p95 2,765) | **504 ms** |
| `asight status codex` | 2,582 ms (p95 2,949) | **581 ms** (p95 612) |
| `asight doctor` | 2,687 ms (p95 3,075) | **650 ms** |

A whole `status` now starts one subprocess (`certutil`, 40 ms) instead of four.
Nothing changed about what they report: when the daemon cannot answer a read,
the command asks the OS itself exactly as before and says in `errors` why it
had to. macOS is unchanged (190 ms). The switches were measured too, and they
did change — see the next section.

What is left is no longer the OS: it is node's own start plus the modules the
CLI loads before it does anything, so these commands are still at the 0.5 s
line of D62.

## The switches: `off` then `on` in a fifth of a second

`asight off` used to stop the daemon on every platform, so the next `asight on`
paid for a cold start — a daemon, its engine, its doors and its helpers. Off
and on again took 6.7 to 9.7 s.

In proxy mode (macOS and Windows) `off` now closes the doors and leaves the
daemon running, idle: the same state the machine is in right after a login.
Nothing is captured in that state — no door is open, nothing of asight is on
an agent's path — and `on` is a door opening, not a start. Linux keeps
drain-and-exit, because there the daemon only exists while the helper steers.

Measured on a macOS test machine: **`on` 215 ms, `off` 236 ms**. On the Windows test
machine `off codex` went from 2,034 ms to **315 ms** and `on codex` from 990 ms to
**561 ms**. An idle daemon costs 80 ms of CPU per minute and 1.8 wakeups per
second.

Two cases `asight daemon` now distinguishes: another daemon already answering
is nothing to do, so it exits 0 (a non-zero exit would have the platform
re-launch it for as long as the other one lives). The control endpoint held by
something that does *not* answer is the opposite — it records a
`control-endpoint-held` failure and exits 1, so `asight status` shows it
instead of the machine quietly having no collector.

## Queries are answered by a warm worker, over an index the daemon keeps current

`asight query` and the board now ask the daemon first, and a low-priority query
worker in it answers. It stays warm between queries and holds what it read, so
the questions you ask while looking at one session cost nothing twice.

The worker is never a prerequisite. With no worker yet the daemon says so at
once and the asking side reads the records itself, at local speed, while the
same query warms a worker for the next one; with no daemon at all the command
reads locally. Every path returns the same document, byte for byte.

Underneath it, the daemon keeps the segment index of what it writes current, by
appending to it as the records arrive — so no query ever pays to build an index
for a corpus that was just captured. A query that still had to build one says
so in the document's `errors` (`index-cold`), instead of charging you seconds
without a word.

Measured on a macOS test machine: `asight query session --id` 162 ms through the
daemon against 548 ms locally, and inside the worker a query about the session
already on screen is 11 ms or less.

## `--cursor` is now `--after`

**Breaking.** The paging flag of `asight query` (and of the board's data
requests) is `--after`. There is no `--cursor` alias: on some machines security
software SIGKILLs any `node` process whose command line contains the old word,
which made the flag unusable where it was installed. The document field is
unchanged — `page.next` still carries the value you pass to `--after`.

## New failure codes you can see

All four are closed codes, with a reason, in `~/.asight/collector/flows/` and
in `asight status` (`--json`: the same codes):

- `index-failed` — the daemon could not keep a segment's index current. The
  records are on disk; the next query indexes them itself.
- `index-cold` — a reader's note in a query document: this query had to build
  the index itself, which is what made it slow.
- `query-failed` — the daemon's query worker crashed or went silent. The query
  is still answered, locally.
- `control-endpoint-held` — the daemon's control endpoint is held by something
  that does not answer (see above).
