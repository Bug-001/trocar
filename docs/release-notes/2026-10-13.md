# Release notes — 2026-10-13

## macOS and Windows: `asight off` no longer deletes a bundle a running agent still uses

**What changed.** Codex, Hermes and Z-Code verify TLS against the combined bundle asight's entry points them at
(`combined-<agent>.pem`), and Codex reads it again at every new connection. `asight off` keeps such a bundle — without
the collector CA — while a process of that agent that may have loaded it is running, and removes it on a later `off`.
On macOS and Windows it could not tell any process was an agent (the process signatures it judges by existed for Linux
only), so it read every bundle as unused and deleted it: a Codex started after `asight on` then had no certificates at
its next connection. `on` now records, for macOS and Windows, the same process forms the collector routes by, and `off`
reads the real executable of each process (`lsof` on macOS) to match them. The bundle is kept, the receipt names the
pid, and Codex is reported as trusting asight until its next connection. An install made before this release has no
such record on these systems: `off` then keeps the bundle, says it cannot tell who uses it and exits 1 — run
`asight on` once and it is recorded. On macOS and Windows another process's environment cannot be read at all, so a
Claude Code (or Kimi) process started after `on` now counts as holding `extra-cc.pem` / `extra-kimi.pem`: the file is
kept without the collector CA and the pid named, instead of being deleted under it.

**Impact.** On a Mac or a Windows machine with agents running, `asight off` may now list kept files and pids where it
used to delete them, and `asight status` lists the agent processes it infers from the process table there too (it found
none before). Linux is unchanged, except for an install made before 2026-10-07 (its record
has no process data at all): its bundles and extra trust files are kept as "not known" while some process may have read
the entry (its extra trust files were judged by environment alone before), and removed when none could have.

## The combined bundles say which OS roots they lack

**What changed.** A combined bundle (`combined-<agent>.pem`) leaves out every OS root certificate Node cannot parse —
one broken block makes Codex refuse the whole file — and on macOS it takes the union of three sources, one of which can
fail while the others answer (on Node 20 there is no keychain read at all, and the keychain is where a corporate CA you
added lives). asight counted both and told no one. Now `on` prints one line in its receipt for each (and an install
note, so `asight doctor` shows it), naming the bundles; the daemon records a failure under `bundle` at every rebuild,
shown by `asight status` and the board (`有系统根证书解析不了,没进合并包` / `合并包少了一部分系统根证书`). On Linux the
system bundle's unparsable blocks are counted the same way. A macOS source that simply has nothing — a Mac with no root
added to its keychain — is not a failure and is not reported.

**Impact.** Nothing changes in the bundles themselves. A machine where nothing is left out sees no new line.

## Linux: the combined bundles carry the OS roots on Fedora, RHEL and openSUSE too

**What changed.** The combined bundles (`combined-<agent>.pem`, what Codex's and Hermes' `SSL_CERT_FILE` and Z-Code's
`caCertFile` point at) start from the OS roots. On Linux asight read only Debian's `/etc/ssl/certs/ca-certificates.crt`;
on Fedora / RHEL / CentOS / openSUSE that file does not exist, so the bundles carried Node's roots alone and dropped the
CAs installed system-wide — a corporate proxy's among them — and an agent behind such a proxy could not verify its
upstream. asight now takes the first system bundle the machine has (`/etc/pki/tls/certs/ca-bundle.crt`,
`/etc/ssl/ca-bundle.pem`, …), reads it again at every rebuild, and `asight off` uses the same list. A machine with none
gets bundles with Node's roots only, and that is said: a line in `on`'s receipt and an install note (`asight doctor`
shows it among the last install's notes), and a failure under `bundle` in `asight status` and the board, recorded again
at every rebuild while no bundle is found. A system bundle that exists but cannot be read stops `on` before any file is
changed (where asight is already installed, `asight status` lists that failed `on` too); the daemon then keeps the
bundles it has and records the failure. On every platform, `on` and the daemon now read the OS roots the same way, from
one place in the code.

**Impact.** On Debian / Ubuntu the bundles are the same as before. On the other distributions, the next daemon start
or daily rebuild rewrites the bundles with the OS roots in them.

## `asight off` rebuilds a missing bundle from this machine's own roots (macOS: the keychain's, not `/etc/ssl/cert.pem`)

**What changed.** When a combined bundle has gone missing while an agent that may still use it is running, `asight off`
rebuilds it without the collector CA so the agent keeps its network. It used to take the OS roots from a fixed list of
PEM files on every platform: on macOS that is `/etc/ssl/cert.pem`, which lacks the roots added to the keychain — a
corporate proxy's CA among them — so Codex behind such a proxy lost its relay after `off`; on Windows it found nothing.
`off` now reads the roots exactly as `on` and the daemon do, from one place in the code: macOS takes Node's set, the
keychain's anchors and Apple's system roots; Windows takes the system store; Linux the first system bundle. It reads them
only when there is a bundle to rebuild. The receipt now says "重建了" for such a bundle, and says when only Node's roots
went in or a source could not be read (Windows with Node older than 22.15: the standalone `asight-off` has no helper to
export the stores).

**Impact.** Nothing changes while every bundle is in place. The next `asight on` rewrites `~/.asight/bin/asight-off`
(version 8); `asight doctor` flags the older copy until then.

## A named `--opt-in` takes effect in the same run, and accepts the item ids the plan prints

**What changed.** `asight on <harness> --opt-in <form>` now turns that harness on in the same `on`. Before, it wrote the
shim or the named item but left the desired state off, so the daemon parked the harness's processes and a second bare
`on` was needed before anything was captured (the symptom was steering without a single record). The plan's
"you have to name these" section prints item ids (`cert-store-current-user`, `desktop-launcher`, …), and `--opt-in` now
accepts them: when exactly one form carries the item it expands to that form; when several do (`desktop-launcher` and
`user-path-shim` on macOS, the two shim items on Windows) the command stops with a usage error that lists the carriers,
and you name the form.

**Impact.** Form ids work exactly as before.

## macOS: the Kimi Code, Z-Code, Hermes and OpenCode CLIs are captured; Codex's VS Code extension and the DeepSeek desktop app join the form table

**What changed.** Each of the four CLIs had its own gap; all are closed, and one turn per CLI is captured byte-identical
with the mock:

- **Kimi Code**: the shim writes a per-process launch marker (the same trust door `dsh` uses), and the descriptor
  declares the `layers` contract the verdict needs. darwin cannot read another process's environment, so Kimi's only
  environment-variable trust door could never open before.
- **Z-Code**: `-p` rewrites the whole command line to `zcode-cli`; the form's command-line gate now lists both the
  original path and the rewritten title (the Windows twin form shares the same list).
- **Hermes**: the form's `image` gains `python3.14`, the name `lsof` reports after resolving the symlink.
- **OpenCode**: the opt-in's rc `PATH` line now goes after the last line that sets `PATH`. With Kimi installed
  alongside, it used to land between the two installers' lines, the real binary shadowed the shim, and OpenCode went
  straight to the upstream and refused the collector certificate.

Two additions to the form table:

- **Codex's VS Code extension** — the binary the extension ships (`~/.vscode/extensions/openai.chatgpt-*/bin/*/codex`)
  is recognised as `codex.vscode` and goes through the `codex.env` door (one turn byte-identical).
- **DeepSeek desktop app** — a new form `deepseek-dsh.desktop` with its own launcher group (Chromium `--proxy-server`,
  credential-less loopback door); the launcher item is now a per-app table instead of a Claude Desktop special case.

## Windows: plugin-type harnesses are judged and decrypted

**What changed.** The launch marker that the `dsh` and OpenCode plugins write on Windows was compared byte-exactly and
always read as `marker-stale`, so the process was judged untrusted, its traffic was relayed blind and nothing was
recorded; the comparison now carries the same marker tolerance as macOS. Z-Code's command-line gate shares one list with
macOS. On Windows, one turn each of Claude Code, Codex (WebSocket), `dsh`, Z-Code, OpenCode's CLI and Codex's VS Code
extension is now recorded byte-identical with the mock, with the daemon started by asight's own scheduled task in the
user's console session.

## Windows: Anthropic's own exe install of Claude Desktop, and the machine-PATH item

**What changed.** Anthropic's downloadable exe install (`%LOCALAPPDATA%\AnthropicClaude\claude.exe`) is recognised as
`claude-code.desktop`; the form rule matched only the Store / MSIX layout, so the most common install read
`form-path-unknown`. Whether that exe build honours the same HKCU policy door has not been measured. The machine-PATH
opt-in item (`machine-path-dispatcher`) builds again: the daemon's own apply path passes no dependencies, and the item
failed every time with "no command resolver is wired in"; it now falls back to the real command resolver and the
machine-PATH reader.

## status, doctor and on no longer name your VPN

**What changed.** asight now reads only the proxy settings: the agent's own proxy and the system proxy. It no longer
tries to recognise your VPN product, so the product name, its mode and the TUN line are gone from `status`, `doctor`
and the `on` plan and receipt, and so is the "本机网络环境" line. In each agent's chain, the proxy hop shows its address
and the process listening on it. `status --json` has no `netenv` key any more, and `netenv.json` keeps only the record
of what `on` adopted and the topology. The upstream choice is unchanged: the agent's own proxy, then the system proxy,
then a direct connection.

**Why.** asight only has to sense the system proxy; it does not need to know which VPN you use. Naming products meant a per-product adapter that
had to be kept in step with each VPN's own changes, and asight never writes into a VPN anyway.

**Impact.** Scripts that read `netenv` from `status --json`, or the product line from `status`, need to drop it. What
`on` and `off` do to your agents is unchanged.
