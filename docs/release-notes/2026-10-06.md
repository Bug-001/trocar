# Release notes — 2026-10-06

## Collector captures on the board

**What changed.** With no `--source`, `asight serve` now also reads the per-user process collector's
`~/.asight/collector/capture-<date>.ndjson` (only when that directory exists). The collector's
`flows/`, `audit/` and `replays/` subdirectories are not envelopes and are never shown.
`asight etl <dir>` now accepts a directory: it ingests the directory's top-level `*.ndjson` in name
order in one run, and each call's `raw_ref` names the file that call was read from.

**Why.** The collector writes one capture file per day under `~/.asight/collector/` (RFC 4.6 §记录),
and the board's default roots never reached it, so Claude Code traffic captured by the collector
never appeared on the board (spec 4.4:129).

**Impact.** Run `asight serve` with no arguments to see collector-captured Claude Code sessions next
to the older captures. Run `asight etl ~/.asight/collector` to load them into DuckDB. Existing
single-file `asight etl <ndjson>` runs are unchanged.

The collector now picks the daily file by the UTC date at which it writes the envelope, not by the
request's start time (`ts` is still recorded). A call that starts before midnight and ends after it
goes into the new day's file, so, barring a clock step back, an earlier day's file never grows after
a later one exists, and an incremental `asight etl <dir>` matches a full rebuild across midnight. For a directory where an
earlier file can still grow (such as `~/.asight`, with several captures), an incremental run that
would have to skip a record refuses instead and asks for `--rebuild`.

A running board follows a live capture: a call captured after `asight serve` started opens with its
exact bytes. When a block is not in its index, the board indexes only what was appended since it
last looked, then answers.

**Known limit.** A collector directory created after the board started becomes a root at the next
restart.

## Symlinked capture files show on the board

**What changed.** A `*.ndjson` capture in a source directory that is a symlink to a file (on some
machines `~/.asight/codex-capture.ndjson` links to `~/.atrace/codex-capture.ndjson`) is now listed on the
board, the same as a regular file. A file reached from two roots (a link in one, its target in
another) is read once. The board, the block resolver and `asight etl <dir>` follow one rule. A link
that points nowhere is not a capture file: it is skipped (the resolver notes it as `broken-symlink`
in its internal scan, which nothing displays yet) instead of failing every capture in that
directory.

**Why.** The board's file scan used `isFile()`, which is false for a symlink, so the sessions in a
linked capture never appeared, while the block resolver did read it.

**Impact.** Sessions from a linked capture (such as Codex captured by the old relay tee) appear after
upgrading; nothing to do.

## The board and `asight etl` say what they did not read

**What changed.** When a file in a capture source is not read, the board now shows it in a line next
to the session list, with the reason. Examples: a link that points nowhere, a compressed file, a
`*.ndjson` that is not a regular file, or a session folder with no `meta.json`. Each file's count of
lines that do not parse is shown too. Other entries (config files, the CA, folders) are counted on
that line and listed when you hover over it. `asight etl <dir>` prints the same list to stderr.

**Why.** These entries used to be dropped without a word, so a broken or compressed capture looked
like no capture at all (RFC 4.4:83).

If the session list itself cannot be read (for example a capture directory the server may not list),
the board now shows the server's reason instead of "No sessions captured yet". A single capture file
it may not open is listed as not read, and the other sessions still show.

A running board no longer loses a call it happens to read while the collector is still writing it.
Before, that call was counted as a bad line and never shown; now the board says a file ends in an
incomplete line and shows the call once the line is whole. A last record that is complete but has no
trailing newline is shown as well.

**Impact.** If the line appears, the files on disk are untouched; it names what to check. Nothing to
do otherwise.

## The board says why a captured request is incomplete

A request the collector stored only in part now says why on the board, instead of showing an empty context. The board reads the labels the collector has written since #21:
- 「请求体已截断」: the body was cut at the 64 MiB capture cap, and only its first N bytes are stored.
- 「请求体不完整」: the capture did not get the whole body. Either it never finished uploading (the upstream answered first, e.g. 413 / 401, or the connection was aborted), or the collector lost the request's HTTP framing and stopped storing it (the rest may still have reached the upstream).

The reason appears in the raw panel and at the top of the context window, including for a call whose body is not loaded on the current page. A call whose stored prefix cannot be parsed shows a notice with that reason. Before, it drew an empty window, which read as "the model saw nothing". Captures without these labels (v0, legacy MITM) keep the old "truncated / corrupt capture" wording.

## 看板按进程认 harness,按各 harness 自己的键分 session(D37)

- **改了什么**:新增读取侧 harness 表 `src/dissect/harnesses.mjs`(七个 harness 的 session 键、lane / 父 / 压缩提示、观测者效应)。看板的 harness 改取自记录的 `proc.agent`;只有没有 `proc` 的旧记录才按 User-Agent 推断,agent chip 上标「· 推断自 UA」。session 按各 harness 自己的键分组(dsh、Z-Code、OpenCode、Kimi、Hermes 的键第一次被认出),从不按 pid 或连接分。限于扁平源:分片源仍只按 Claude Code 的头分文件;Kimi / Hermes 没有键的调用仍归控制面。
- **为什么**:D37 要求三条轴(harness / 线格式 / 厂商)分开认,harness 不能由 UA 臆断;观测者效应要能按 harness 标出来,这张表是第一步(写进 DuckDB、在看板标注随后跟上)。
- **对你的影响**:旧抓包里 Claude Code 的 harness 值从 `claude-code` 变成 3.2 的 id `cc`,chip 显示不变,只多了「· 推断自 UA」。D37 之前生成的 `meta.json` 同样显示为推断。
