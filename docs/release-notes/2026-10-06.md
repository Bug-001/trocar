# Release notes — 2026-10-06

## Collector captures on the board

**What changed.** With no `--source`, `asight serve` now also reads the per-user process collector's
`~/.asight/collector/capture-<date>.ndjson` (only when that directory exists). The collector's
`flows/`, `audit/` and `replays/` subdirectories are not envelopes and are never shown.
`asight etl <dir>` now accepts a directory: it ingests the directory's top-level `*.ndjson` in name
order in one run, and each call's `raw_ref` names the file that call was read from.

**Why.** The collector writes one capture file per day under `~/.asight/collector/` (RFC 4.6 §记录),
and the board's default roots never reached it, so Claude Code traffic captured by the collector
never appeared on the board (spec 4.4:129).

**Impact.** Run `asight serve` with no arguments to see collector-captured Claude Code sessions next
to the older captures. Run `asight etl ~/.asight/collector` to load them into DuckDB. Existing
single-file `asight etl <ndjson>` runs are unchanged.

The collector now picks the daily file by the UTC date at which it writes the envelope, not by the
request's start time (`ts` is still recorded). A call that starts before midnight and ends after it
goes into the new day's file, so, barring a clock step back, an earlier day's file never grows after
a later one exists, and an incremental `asight etl <dir>` matches a full rebuild across midnight. For a directory where an
earlier file can still grow (such as `~/.asight`, with several captures), an incremental run that
would have to skip a record refuses instead and asks for `--rebuild`.

A running board follows a live capture: a call captured after `asight serve` started opens with its
exact bytes. When a block is not in its index, the board indexes only what was appended since it
last looked, then answers.

**Known limit.** A collector directory created after the board started becomes a root at the next
restart.

## Symlinked capture files show on the board

**What changed.** A `*.ndjson` capture in a source directory that is a symlink to a file (on some
machines `~/.asight/codex-capture.ndjson` links to `~/.atrace/codex-capture.ndjson`) is now listed on the
board, the same as a regular file. A file reached from two roots (a link in one, its target in
another) is read once. The board, the block resolver and `asight etl <dir>` follow one rule. A link
that points nowhere is not a capture file: it is skipped (the resolver notes it as `broken-symlink`
in its internal scan, which nothing displays yet) instead of failing every capture in that
directory.

**Why.** The board's file scan used `isFile()`, which is false for a symlink, so the sessions in a
linked capture never appeared, while the block resolver did read it.

**Impact.** Sessions from a linked capture (such as Codex captured by the old relay tee) appear after
upgrading; nothing to do.

## The board and `asight etl` say what they did not read

**What changed.** When a file in a capture source is not read, the board now shows it in a line next
to the session list, with the reason. Examples: a link that points nowhere, a compressed file, a
`*.ndjson` that is not a regular file, or a session folder with no `meta.json`. Each file's count of
lines that do not parse is shown too. Other entries (config files, the CA, folders) are counted on
that line and listed when you hover over it. `asight etl <dir>` prints the same list to stderr.

**Why.** These entries used to be dropped without a word, so a broken or compressed capture looked
like no capture at all (RFC 4.4:83).

If the session list itself cannot be read (for example a capture directory the server may not list),
the board now shows the server's reason instead of "No sessions captured yet". A single capture file
it may not open is listed as not read, and the other sessions still show.

A running board no longer loses a call it happens to read while the collector is still writing it.
Before, that call was counted as a bad line and never shown; now the board says a file ends in an
incomplete line and shows the call once the line is whole. A last record that is complete but has no
trailing newline is shown as well.

**Impact.** If the line appears, the files on disk are untouched; it names what to check. Nothing to
do otherwise.

## The board says why a captured request is incomplete

A request the collector stored only in part now says why on the board, instead of showing an empty context. The board reads the labels the collector has written since #21:
- 「请求体已截断」: the body was cut at the 64 MiB capture cap, and only its first N bytes are stored.
- 「请求体不完整」: the capture did not get the whole body. Either it never finished uploading (the upstream answered first, e.g. 413 / 401, or the connection was aborted), or the collector lost the request's HTTP framing and stopped storing it (the rest may still have reached the upstream).

The reason appears in the raw panel and at the top of the context window, including for a call whose body is not loaded on the current page. A call whose stored prefix cannot be parsed shows a notice with that reason. Before, it drew an empty window, which read as "the model saw nothing". Captures without these labels (v0, legacy MITM) keep the old "truncated / corrupt capture" wording.

## 看板按进程认 harness,按各 harness 自己的键分 session(D37)

- **改了什么**:新增读取侧 harness 表 `src/dissect/harnesses.mjs`(七个 harness 的 session 键、lane / 父 / 压缩提示、观测者效应)。看板的 harness 改取自记录的 `proc.agent`;只有没有 `proc` 的旧记录才按 User-Agent 推断,agent chip 上标「· 推断自 UA」。session 按各 harness 自己的键分组(dsh、Z-Code、OpenCode、Kimi、Hermes 的键第一次被认出),从不按 pid 或连接分。限于扁平源:分片源仍只按 Claude Code 的头分文件;Kimi / Hermes 没有键的调用仍归控制面。
- **为什么**:D37 要求三条轴(harness / 线格式 / 厂商)分开认,harness 不能由 UA 臆断;观测者效应要能按 harness 标出来,这张表是第一步(写进 DuckDB、在看板标注随后跟上)。
- **对你的影响**:旧抓包里 Claude Code 的 harness 值从 `claude-code` 变成 3.2 的 id `cc`,chip 显示不变,只多了「· 推断自 UA」。D37 之前生成的 `meta.json` 同样显示为推断。

## Per-user process collector: Claude Code on Linux

**What changed.** New commands: `sudo asight setup-helper` installs the capability helper once per
machine; `asight collector install | start | on | off | status | uninstall` run as the user. Install
first lists every file it will change (a symbolic link as link → target), then mints a collector CA
under `~/.asight/collector/ca/` (in no trust store), sets Claude Code's
`env.NODE_EXTRA_CA_CERTS` in `~/.claude/settings.json`, and records every change in
`~/.asight/collector/install-manifest.json`. If you already gave Claude Code a CA (in the install
shell, a running Claude Code, `~/.claude.json`, settings or managed settings), the key points at
`~/.asight/collector/ca/extra-cc.pem` instead: your CA's certificate blocks plus the collector CA,
never a private key. `start` runs the daemon; `on` steers the connections of trusted Claude Code
processes to it and records them as `capture-<date>.ndjson`, which `asight serve` shows.

**Why.** RFC 4.6 (D31, D36, D37④): capture by process, with no system proxy, base URL or VPN change,
and trust given to the agent alone, never to the login environment.

**Impact.** Linux only. asight does not count on a Claude Code process that was running before install
picking up the new `NODE_EXTRA_CA_CERTS` (a test-machine check saw `claude -p` do so; the other modes are
unverified), so `status` lists it as untrusted (`config-after-start`, with a hint to restart it) and its
connections go direct, unrecorded, until it is restarted. A process whose start time cannot be read is
treated the same way (`start-time-unknown`). The
daemon verifies upstreams with Node's default store, so a relay with a private CA needs the same
`NODE_EXTRA_CA_CERTS` in the environment that starts the daemon. `asight collector uninstall` puts
the settings file back key by key (byte-identical when you have not edited it since), removes the CA,
and keeps captures unless `--purge-data`.

Capture failures are never silent: every failure the collector owns — install and uninstall steps,
helper and engine errors, heartbeats, attach, envelope writes, agents judged untrusted — leaves a line
with its reason in `~/.asight/collector/flows/` (deleted with the captures by `--purge-data`), and
`asight collector status` prints the recent ones, from disk when the daemon is not running.

**Known limits.**
- No autostart: run `asight collector start` yourself. A helper that dies is not restarted; `status`
  says why, `on` fails, and connections go direct until the daemon restarts.
- The engine port is chosen at install. If another program holds it later, `start` refuses and
  nothing is steered; uninstall and install again to pick a new port.
- Only Claude Code is wired in this release; the other harnesses follow.
- `install` replaces L-07's `installUser` / `uninstallUser` and its placeholder systemd unit
  (`ExecStart=/usr/bin/false`), which are gone.

## 封存原始日志(D35):采集日志可缩到原始的几个百分点,逐字节无损

**改了什么**:新增 `asight raw` 命令族。已关闭的采集分片可以封存成 `<流名>.<段号>.sealed`(按记录字节级增量 + 独立 brotli 帧 + 索引尾);看板、`asight etl`、「回源逐字」面板都直接读封存文件,看到的记录、`raw_ref` / `text_ref`、DuckDB 表都和封存前一样。原文件只在每条记录与整个文件都被证明能逐字节还原之后才删。
- `asight raw seal <分片>`:只封带关闭标记(`<分片>.closed`)的分片,按 session 分文件,写到 `~/.asight/sessions/<session>/`;`asight serve --source <分片所在目录>` 会把它们当作该目录的一部分读入。
- `asight raw seal --legacy <文件|目录>`:D35 之前的文件(如 `~/.asight/sessions/`)。有 `asight shard --watch` 在跑、有进程持有文件、文件在静默窗口(默认 10 秒)里还在变,都会拒绝并说明原因;默认**保留原文件**,加 `--delete-original` 才删,且删前逐字节比对、比对后再确认原文件没变。旧根 `~/.atrace/asight/` 一律拒绝(先迁进 `~/.asight`)。先跑 `--dry-run` 看会封什么、会拒绝什么。
- `asight raw verify <封存文件|目录> [--against <原文件>]`:解码封存副本,与原文件逐字节比较。
- `asight raw export <session|文件.sealed>`:还原成普通 NDJSON(`~/.asight/export/`,0600)。
- `asight raw journal`:每一次拒绝、失败、删除及原因的持久记录(`~/.asight/raw/journal.jsonl`)。

**为什么**:原始 NDJSON 每次调用都重写整段对话,体积随调用数平方增长(作者机器上约 70 GB,对比 Claude Code 自己的约 1.5 GB)。

**对你有什么影响**:不运行 `asight raw` 就什么都不变。运行后磁盘占用大幅下降;封存文件同样含明文与凭据,仅属主可读,`asight doctor` 会检查封存文件和导出目录的权限。看板读不全某个文件时,会在顶部提示条(与上面「说出没读的文件」是同一条)标明哪个文件、多少条、为什么,不再显示成一个看似正常、实则少了记录的看板;看起来是采集数据却没被读的文件(压缩的采集、改了名的封存文件)也会列出来。raw journal 写不进去时,那条记录会打到终端。

基准(合成 2.5 GiB 分片,Apple M5、Node 22):封存 26.8 秒、峰值内存 421 MB;随机读 1,000 个 `raw_ref` 冷 p95 9.6 ms、热 p95 9.9 ms。合成数据的压缩比(1.29 %)不能代表真实数据。

## 封存:删原文件之前的比对工具,以及第三轮审查的修复

**改了什么**:
- 新增 `asight raw compare <目录> [--list]`:删原文件之前,逐 session、逐 control 类比对看板 / ETL / 回源面板经原文件读到的与经封存副本读到的——记录次序、每条记录的字节、每个 id 的回源结果。它比对的正是 `--delete-original` 会删的那些原文件(用删除时同一个判断),`--list` 逐个列出,好和 `--dry-run` 的清单对照;有差异、读不全、或一条都没比到时退出码 1,并写进 raw journal。它取代此前「起两个 `asight serve` 再 `curl` 比哈希」的做法(那样两边都是空字符串,永远相等)。
- `--delete-original` 只删**已经有**封存副本、且逐字节比对通过的原文件;还没有副本的拒绝并提示「先封存」,不再一次运行里封存又删除。`--dry-run --delete-original` 逐个列出会删哪些、拒绝哪些。删除中途失败时,记录与输出都写明原文件是否已经删了。
- 封存后看板读一个 session 的次序和封存前一样(calls → probes → other;以前删原文件后变成 calls → other → probes,影响大 session 只显示最近若干条时选中的是哪些)。
- `asight shard --watch` 在删原文件之后新写的 `calls.ndjson` 会被封成下一个段;旁边那个旧段是旧记录唯一的副本,不再被当作「这份文件的早先版本」而拒绝,也不再提示删掉它;`raw verify` 对它单独校验。
- 带着原文件与封存副本一起复制出来的目录(备份、恢复、换盘),只要复制时保留了文件时间(`cp -p` / `cp -a`、`rsync -a`、`ditto`),不再把每条记录读两遍;没保留时间的复制(如普通 `cp -R`)仍会读两遍,但看板会逐个文件标出「记录可能出现两次」。
- `asight raw seal --legacy` 不封存的文件(如中断的 resplit 留下的 `*.premigrate`、`.resplit-tmp/`)逐个列出并写进 journal;`meta.json` 等已知标记只计数。
- `asight raw export <session>` 改为输出到目录 `~/.asight/export/<session>/`,每个封存段一个文件(以前拼成一个文件,末行没有换行的流会和下一个流的首行粘在一起)。
- 两个封存器同时往一个目录写时不会互相覆盖段文件,也不会删掉对方正在写的临时文件;被 kill 留下的 `.sealing` 锁会在下一次封存该目录时清掉并记入 journal;`asight shard --rebuild-meta` 对坏行的计数在封存前后一致,并单独打印坏行数,读不全的封存段记入 journal。
- `asight raw verify` 对「文件后来变长、副本只含它前面一段」的情况显示 `ok (prefix)`,不再是普通的 ok。
- 读不了的目录(权限)在看板顶部横幅里点名,不再当作无关目录略过;raw journal 写不进去之后,下一次写成功时先补一条「中间丢了几条」的记录;raw journal 本身读不了时 `asight raw journal` 报错,不再显示为空。
- 删原文件这条路径(`--delete-original`)再收紧:每删一个之前先在 raw journal 里写一条「正在删 X」,journal 写不进去就一个都不删;另一个 `asight raw seal` 正在同一棵目录上跑时拒绝;删的时候持有该文件的封存锁;原文件在比对之后被改写、连大小和修改时间都改回去,也认得出来(看 ctime),不删;读不了的目录、原文件、封存段都点名拒绝(写进 journal,不再报一屏错误栈,也不再说成「还没有副本」);中断的封存留下的空段在删除前先清掉(写进 journal)。
- `asight raw compare` 比对的范围改成与 `--delete-original` 完全相同的那批文件(包括 session 目录里额外的流、不是 session 的子目录;不包括符号链接);会删却没比对到的,单独列出并让 compare 失败;汇总里「not covered」按文件数计。

**对你有什么影响**:已经用上一版封存(保留原文件)的副本仍然有效,不需要重封;删原文件前先跑 `asight raw compare`。删完原文件后请用这一版的 `asight serve`:旧版看板读封存段的次序与原文件不同。
