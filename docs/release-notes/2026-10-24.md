# 2026-10-24

## Replay desk

### Board

- **Coming back to a session shows the step you left.** Leave the replay desk for Sessions, the overview or another
  session, then come back by the session's row, Back, the sidebar or a link: the desk is on the step you left, drawn
  at once, and asks only for what is new. Before, it read the whole session again and, from a Sessions row, landed on
  the newest step. On a 21k-call live session, coming back from Sessions drew the step in 85 ms and sent one small
  read; Back from the overview took 27 ms. The board keeps up to three sessions this way while the tab is open;
  nothing is stored in the browser.
- **A link to a step lands on that step.** Opening a replay link with `?step=500` on the same session used to show
  thirteen other steps on the way, walking back one part every few seconds, and took 39 s. It now lands on step 500
  in about 2 s and draws no other step first; the address keeps naming step 500 while it waits. Home on a session
  still being read goes the same way.
- **The whole history of a session arrives in seconds.** The desk reads the older parts of a session one right after
  another, at most three at a time, instead of one per refresh. On the same session the full history (about 48 MB)
  arrived in 13 s instead of 72 s.
- **Stepping stays light.** The outline, the resource list and the raw data panel change only what differs between
  two steps: on that session the resource list went from rebuilding about 750 elements per step to none. While you
  rest on a step, the replies of the eight steps either side are read in the same request, so stepping nearby does
  not wait for a reply's text.
- **A session opens at once, also from cold.** Open a replay link in a new tab with no query worker running and the
  page draws at once from a small summary the worker wrote earlier: the header with its totals, the whole-session
  overview, the bars of the part you are in, the step number, the lane names and an empty context frame of the right
  size. The step's blocks follow a moment later. On a 21k-call live session this first page took 48 ms (p95); the
  full step was on screen within 120 ms.
- **Parts between compactions.** A session is cut into parts at its compactions. The row above the trace says
  **Part k of n · steps a–b**, with **(inferred)** when the boundary is a guess; ‹ and ›, or the keys [ and ], go to
  the part before or after, and the overview marks every boundary. The bars stay inside the part you are in. Going to
  another part took 15 ms (p95) on that session.
- **Following reads only what is new.** A desk that follows a session asks every 1.5 s for the bytes added since its
  last look. When nothing new was captured, nothing comes back and no query worker starts. Coming back to a session
  you left costs one such look.
- **The board says how current it is.** **Reading this session for the first time · N %** shows while the worker
  reads a session it has never read; until then the overview shows calls over time only, with no bars per step and no
  parts. **N newer calls are not shown yet** shows when the capture holds calls the summary on screen does not, and goes
  away with the next summary.
- **Each step changes only what differs.** Stepping one step changes only the context window's rows that differ, and
  the window keeps as rows only the blocks near what you can see; the rest are placeholders of the right height.
- **A cold replay link starts reading sooner.** The page asks for the session before the rest of the board's code
  has loaded, and loads that code all at once; the first request now leaves about 20 ms earlier.

## Query

- **A session that is still being read shows the work moving.** `trocar query session` on a session the worker has
  not finished now carries `pending.work`: how many calls the worker has read and folded so far. It grows while the
  worker works, also while it rebuilds a session whose saved state it could not reuse, when `pending.done` stays put.
- **A session is read as it is captured.** When the daemon records new model calls, it hands them to the query
  worker, which works out their sessions (synthesized session keys included, so every harness) and reads the new
  calls in the background at low priority. Opening a running session no longer starts with a backlog. The worker
  leaves two minutes after the last query, newly captured call or piece of background reading, so a first read that
  takes longer than that (it did on that session) is finished instead of being cut off and started over by the next
  worker; while it reads, the worker saves its place at least once a minute, so a stop or crash loses at most that. What it costs: while an agent is being captured the
  worker stays resident, using about 135–140 MB of memory between calls on a 25k-call session (at most 159 MB, within
  the 160 MB target) and about 600 MB right after a first read; it spends about 19 ms of CPU on each new call, against a
  target of about 12 ms that is not met yet; and on a session that was never read, the first new call starts the whole first
  read in the background (57 s on that session), not just that call.
- **A cold read no longer reads a big session twice.** With no worker running yet, `trocar query session` (and
  `lane`) answers at once only when what is on disk covers the session; otherwise it waits on the worker the daemon
  starts for it, and reads the records itself only when the worker makes no progress for 5 s. Without `--json` it
  says on stderr when it waits and when it answers by itself, and why.

- **`trocar query session --head`, `lane --pack`, `lane --tail`.** `session --head` gives the summary the board opens
  from. `lane --pack <n>.main` (or `.rest`) gives the board's file for the session's n-th settled group of 512 calls
  (`main` = the main conversation, `rest` = everything else), and `lane --tail main` (or `rest`) the file of the part
  still growing. These are the same bytes the daemon serves to the board.

## Storage

- **Sealed captures take about 38 % less disk.** A closed segment is now sealed by storing each repeated piece
  once, so new captures take about 38 % less disk once sealed: on 12 segments of a 21k-call live session (1.5 GB
  raw) they came to 7.3 % of the raw size, against 11.7 % before, and sealing took 29 % less time. Every record still reads back byte for byte.
  Segments sealed before this release are unchanged and still readable. An older trocar cannot read segments
  sealed from now on and says so.
- **The board's files take a third of the space they did.** Each session now has its own directory under
  `~/.trocar/index/ctx/`, and the settled part of its working files is stored compressed (brotli). On the 21k-call
  live session everything trocar keeps for it came to 498 MB, 0.84× the 590 MB of Claude Code's own log for it, against
  972 MB (2.0×) before. The derived files alone are 0.26× of that log, above the 0.1× target.

## Upgrading

- Nothing to do. At its first start the daemon moves each session's existing files into the session's directory (a
  rename, nothing is read again) and writes a summary for every session at once, so every session opens straight away.
  It then builds the board's files in the background while it is idle, sessions you opened or follow first, then the
  newest. A session whose files are not built yet opens on its summary and is read when you open it: on the 21k-call
  session the first open after the upgrade was complete in 9 s. A session that was never read shows calls over time
  with **Reading this session for the first time** until its first read is done.

## Known limits

- Following a running session costs the worker about twice the CPU of the previous build: on a generated 5,000-call
  session about 39 ms per new call against 20 ms, and up to 199 MB of memory between calls against a 160 MB target.
- A very large session is still cut: of a generated 105k-call session the board shows the newest 22 %, and a 210k-call
  one does not get past its summary.
