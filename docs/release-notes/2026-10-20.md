# 2026-10-20

## `trocar update` takes trocar to the newest code

The version number lives in `package.json` and nowhere else; it stays 0.0.0 until the rename, so `--version` reads `0.0.0+<commit>` for now.

One command now does what used to be five: `trocar update` refuses a checkout with changes of your own, fetches,
fast-forwards (never merges), runs `npm install` when what trocar needs changed, replaces the collector, runs
`install`, and switches capture on again for the agents that had it on. It prints the plan — from which commit to
which, and which agents go off and on again — and asks first (`--yes` answers, `--dry-run` only prints). While it
runs those agents are not captured, their connections still work, and connections the collector still holds are cut
when it is replaced. An update that stops half way is written down: run it again and it goes on from there.

`trocar --version` now says which code this is: `0.0.0+1a2b3c4` in a git checkout, `0.0.0` outside one, and the
collector reports the same value, which is how `update` tells whether it still runs the old code.

From the first release on, `install` and `update` take over any `~/.trocar` that release or a newer one left. Moving an
install made before it over is a one-time manual step, because the old code has no `update`: `trocar off`, `git pull`,
`npm install`, `trocar install`, `trocar on`.

## `trocar query overview`: token usage covers the whole window

The stats card's token usage used to read the reply bodies themselves, newest session first, and stop at a 16 MiB
budget, so on a real corpus it covered almost nothing. Now the background query worker writes, after it has
answered, a small per-call usage file beside each segment's index (`~/.trocar/index/<segment>.usage.json`).
`overview` reads those and computes only what they do not cover yet, within the same budget. The first look can
still be partial, and `usage.coverage` says how far it got; later looks cover the whole window, with the same
numbers `trocar query session` shows call by call. Deleting the files is safe: the next looks rebuild them.

## macOS 27: captures again, and Claude Desktop keeps your system proxy

On macOS 27, `netstat` prints no TCP table when it runs under a Node built by Nix or Homebrew. trocar read that table
to tell which process opened each connection. It could not tell, so it captured nothing, and it refused Claude
Desktop's PAC request. Desktop then went direct, around your system proxy. trocar now reads the sockets of your own
processes with a small built-in helper (`socktable`, about 5 ms per check), so connections are recognized and captured
again. A process trocar cannot confirm is yours still gets a PAC, with your system proxy and no door.

`trocar status` now shows Desktop's route out through your system proxy. That is the way the door really dials,
where it used to say `direct`. On macOS the daemon reads the system proxy as soon as it changes: it waits for the
system's change notice instead of checking every 5 seconds, and checks once every 30 seconds as a fallback. Proxy
ports owned by another user (a proxy core running as root) show as unknown in `status`, never as down.

## Claude Code on Message Threads: the whole conversation is back on the board

Claude Code 2.1.304 keeps the conversation on the server (`thread` in the request): after the first call of a thread,
each request carries only its new messages and a billing header, with no system prompt and usually no tools. The
board read each request as the whole context, so most turns looked like background calls or new subagent branches,
and the replay stopped after a few turns. The board now follows `thread.previous_message_id` to the call whose reply
it names and rebuilds what the model saw: the thread's system prompt and tools, every earlier message and reply, then
the new messages. The main conversation and each subagent stay in their own lanes even when their calls interleave.
Calls without `thread` read as before; Claude Code's background calls (`x-claude-code-request-class: auxiliary`:
progress summaries, suggestions) go to the background lane, even when they carry a subagent's id. If an earlier call
of a thread was not captured, or its reply did not fully arrive (an error, a cut or partly unreadable stream, no
content), the call and every later call of the thread are marked partial and say which call and why. System-role messages and tools added
mid-conversation (`tool_addition`) show as blocks and count as tools; removed ones (`tool_removal`) come off the count.
