# 2026-11-07

## Status and doctor

- **`trocar status --json` and `trocar doctor --json` no longer report a verdict as a failure.** When status or doctor
  concluded something was wrong, the document said `ok: false` (its verdict, as the manual says) but also carried
  `error: {code: "failed", message: "trocar status did not finish; …"}`, as if the command had broken off. A reading's
  `ok` is its own conclusion now, with no `error`; a status or doctor that really fails still says so.
## Capture problems

- **A connection its agent closed before trocar could see where it came from is named as such.** On Linux, when an
  agent closed a connection the moment trocar accepted it, the problem read "no original destination for
  undefined:undefined" and its record had an empty `peer`. It now says the connection was closed by its client before
  trocar could read its address, nothing was forwarded, and `peer` is `null`.
## Install and uninstall

- **On Linux, the Z-Code desktop app is captured when its CA setting names a certificate file of your own.** The desktop
  setting `httpProxyCaCertPath` (in `~/.zcode/v2/setting.json`) reaches the app's agent as `ZCODE_AGENT_CA_CERT`, which
  wins over the `network.caCertFile` that `install` writes, so the desktop was passed on unread (status said
  `desktop-ca-override`). `install` now appends a marked trocar block to the end of the file that setting names, and to
  the file a `ZCODE_AGENT_CA_CERT` in the install shell names, and leaves the setting alone; `uninstall` takes the block
  out by its marks. A file that is not yours (another user's, read-only, or inside a package manager's or the system's
  tree) is left alone, and the receipt says so and why.

## Capture

- **On Linux, a Z-Code started with `ZCODE_HTTP_PROXY` is no longer taken to trust trocar through `caCertFile`.** Z-Code
  takes its network settings as one group, from the environment or from its config: with `ZCODE_HTTP_PROXY` set (yours, or
  the desktop's from its proxy setting) it does not read `caCertFile`. trocar now judges such a process only by
  `ZCODE_AGENT_CA_CERT` and `NODE_EXTRA_CA_CERTS`, and passes it on unread, with the reason in `status`, when neither
  carries trocar's root; before, it was judged by `caCertFile`, which that process does not read.

- **On macOS, the Z-Code CLI is captured while the desktop's CA setting is set, and an npm-only Z-Code is captured with a
  desktop setting left behind.** trocar tells Z-Code's forms apart by their program file (the desktop's agent is the app's
  `ZCode Helper`, the CLI the app's `ZCode`, the npm CLI `node`; their titles are all `zcode-cli`), so the desktop's
  setting keeps only the desktop off trocar. Measured on ZCode 3.14.4.
- **On Windows, the Z-Code CLI run with `-p` is captured while the desktop's CA setting is set.** The desktop and the CLI
  are the same `ZCode.exe` there, but their command lines differ: the desktop's agent runs `app-server`, the CLI `-p`. A
  Z-Code that shows neither, such as the interactive CLI, is still forwarded only while the setting is set. Measured on
  ZCode 3.14.5.

## Status

- **`trocar status` no longer calls a process captured that trocar would only forward.** When trocar cannot tell which of a
  harness's apps a process belongs to, it decrypts that process only if every one of those apps on the route the process
  came in by can be decrypted. Status called such a process captured unless every one of them was blocked; it now says not
  routed when any one on that route is, as trocar does. A process that may come in by more than one route, where the routes
  would be handled differently, reads not known, with which route decrypts and which forwards. Seen on Windows with the
  Z-Code desktop's CA setting set: the desktop's network service read as captured.
- **On macOS and Windows, `status` says when the Z-Code desktop's CA setting keeps it off trocar.** With
  `httpProxyCaCertPath` set in `~/.zcode/v2/setting.json`, the desktop's agent goes direct; `status` used to say captured
  and draw it through trocar. It now marks the desktop `not routed`, names the setting, and says to remove it. A Z-Code
  form trocar cannot tell from the desktop reads `forwarded only`: its connections reach trocar, which passes them on
  unread. When trocar cannot read the setting, the desktop is not known, never captured.
- **HOME paths in `status` are shortened before the text is laid out,** so a sentence no longer breaks around a `~/…`
  path that would have fit.
## Capture

- **On macOS, a busy machine no longer loses a call to a program that keeps starting children.** trocar looks up a connection's
  owner in the socket table. While a program starts children, each look can catch a different child holding its socket, and
  after five looks trocar gave up and passed that connection on unread. Now the one process holding it on every look is the owner.
## Capture

- **An agent that exits no longer reads as refusing trocar's certificate.** A process exit closes its idle connections all at
  once. If the process had one working connection to a host and two spare ones, trocar counted the two spares as refusals:
  a false critical `trust-rejected` problem, and in a process that kept running, 10 minutes of its calls to that host passed
  on unread. Now a process that has already sent data to a host takes five such closes in a row, with no data in between,
  to count as refusing it, or ten in five minutes whatever comes between, so a client that really refuses beside a busy one
  still ends up passed on unread. Those closes show under Expected in `trocar status --failures`, not as problems. A certificate
  alert still counts at once, and a process that has sent no data still counts after two.
## Capture problems

- **A slow upstream is a note, not a problem.** trocar records a wait of more than 5 seconds on an upstream and the connection
  goes on, with nothing lost. These records counted as problems and turned the health to failing, for example on a telemetry
  host the network blocks. They are still listed in `trocar status --failures`, now as notes.
## Capture problems

- **`trocar status --failures` lists a failure once per harness.** A failure shared by several harnesses was one line with one
  name: `x5 kimi-code` could be three of claude-code's, one of hermes's and one of kimi-code's. Each harness now has its own
  line with its own count, in `--json` (`failures.groups`) and on the board too.
## Status

- **`trocar status` now says when an agent's certificate bundle is missing a CA you added.** Z-Code reads trocar's
  bundle instead of its default roots, and that bundle holds the CAs your settings named when you ran `trocar install`.
  A CA added afterwards (for example in the file `NODE_EXTRA_CA_CERTS` points at) was not in it, so every call to a
  host signed by that CA failed certificate checks while status still said the certificate was in effect. Status
  now shows the problem, with `trocar install` as the fix, and `trocar on` asks you to run it first.
## Windows

- **When Windows refuses trocar's login task, install says so and uninstall cleans up after it.** If the Task
  Scheduler refused the task (for example because a task under the same name was made from an elevated window),
  install starts trocar at login through a value in your Run key instead. The receipt now names that Run value
  as the login entry and says why the task was refused; `trocar status --failures` lists the refusal; and
  `trocar uninstall` removes the Run value, or puts back a value of yours that was there before, and its receipt says
  which. The install plan names both the task and the Run value, since it is printed before the Task Scheduler answers.
  trocar records a value of yours under that name before it writes its own, and writes nothing there when it
  cannot record it; a refusal it cannot write down makes install (and `trocar update`) report a problem.
- **Uninstall no longer tells you to keep backups it is about to delete.** It deletes every backup trocar made
  and lists them; the note that suggested keeping some of them is only printed by `trocar off` now.
## Capture

- **`trocar status` says when the login entry is gone.** If the login entry `install` registered was removed or switched
  off (the LaunchAgent on macOS, the scheduled task or its Run key on Windows, the systemd user unit on Linux), `status`
  used to say capture was fine, and after the next restart nothing of trocar started and every agent pointed at it could
  not connect. `status` now asks the same question `trocar on` asks before it writes anything: a missing or switched-off
  entry is a `Login` line with `trocar install` and exit 1 (`autostart-missing` in `--json` and in `trocar doctor`); an
  entry that could not be read is said as unknown with the reason, exit 3.
## Uninstall

- **`trocar uninstall` seals the records the collector was still writing.** The collector seals each full file of
  records as it goes, but the one it was writing when it stopped was left for its next start, and after an uninstall
  there is none: up to 128 MB stayed unsealed for good. The collector now finishes the files already waiting to be
  sealed, then seals every unsealed file left before it exits, and `uninstall` waits while it reports progress
  (`sealing <segment>: n of m MB`). The receipt says `Sealed <segment> (n MB → m MB)` for each, or that a file stays
  unsealed until trocar runs again when its seal could not finish. `--purge-data` seals nothing, because the records are deleted afterwards.
## Capture

- **An app trocar does not cover no longer blocks `trocar on`.** On a Mac with only the Kimi Code desktop app, `install`
  placed nothing for it, and every `on` then refused kimi-code and asked for `trocar install`, which could never help. On
  Windows the same machine got a switch file nothing reads, and could have a certificate block added to your own CA file.
  A form trocar leaves out of scope now counts as not on the machine, for `install`, `on` and `status` alike. `on` with no
  names exits 0 and says there is nothing to capture; `on kimi-code` says why it was not turned on; `status` has an
  `out of scope:` line naming the app (`out_of_scope` in `--json`). Codex on a Windows machine with `wsl` and no Codex no
  longer gets a `~/.codex/.env`, for the same reason.
## Words

- **Three receipts read better.** `uninstall` said "only trocar's line undefined was taken out" for a certificate block in a
  file you had edited; it now says "certificate block". A note that the daemon did not answer named an internal verb and a
  raw system code (`ps: ETIMEDOUT`); it now says "the process list: no answer in time". And `uninstall` no longer says the
  collector "was stopped" when `off` had already stopped it and only its old lock was left.
## Status

- **`trocar status` shows how long the collector has been up again.** `daemon.since` was `null` on every system, so the
  Daemon line never said "up …" and the board had no uptime. The collector now gives its own start time in its answer.
## Windows

- **`trocar on` no longer starts a task that is not trocar's.** If a scheduled task named `\trocar\collector` was
  registered by someone else, `on` ran it to start the collector, and `status` took it for trocar's login entry. A task
  now counts as trocar's only when its action is the one `trocar install` wrote. Otherwise `on` refuses and names only
  the program that task runs, and `trocar install` replaces it. `trocar off` and `trocar uninstall` leave such a task
  where it is and say so.
## Uninstall

- **`uninstall` says how to end a program that still holds trocar.** A process started while capture was on keeps
  trocar in its environment until it exits, and `trocar off` cannot end it, so the refusal's only steps (`trocar off`,
  then `trocar uninstall`) did not help. OpenCode's desktop app leaves its sidecar and crash handler running after you
  quit it. The refusal now gives each program a step: quit it, and end any of its processes still running by pid with
  the system's own command (`kill <pid>`, or `Stop-Process -Id <pid>` on Windows). `trocar off` is a step only when
  capture is still on.
## Capture

- **trocar's proxy settings file (PAC) for the Claude desktop app is served only to a request that carries this
  install's key.** On macOS trocar cannot tell, without administrator rights, whether a program it cannot identify
  belongs to you or to another user of the machine, so another user's request for the PAC was answered with the
  version that names your own proxy. The PAC address `trocar on` writes into the app's settings now carries a random
  key of this install, in a file only you can read; a request without it is refused and recorded, whoever sends it.
  After an update, the app's settings still hold the old address without the key, and trocar refuses the app's request
  for it. Measured on macOS: the app then sends its model calls directly, around trocar and around your system proxy,
  and nothing is captured. `trocar status` and the board say so, with `trocar on` as the way out: `trocar on` now
  replaces an address trocar wrote earlier (with another key, or none) with the current one, also for an agent that is
  already on. A value you put in that setting yourself is kept, and `trocar on` says so.
  This needs the collector running this version's code. `trocar update` restarts it. If you upgrade trocar another
  way, such as replacing its files in place, the collector from before keeps running and still gives the app the old
  address; `trocar off` and `trocar on` leave it running. Restart the computer, so the collector starts again from the
  new files.
- **On Linux, `trocar install` over a masked login unit says it changed a file of yours.** A unit you masked by hand (a
  link to `/dev/null`) is replaced by trocar's unit. The install receipt used to say "No file of yours was changed." next
  to that, and the plan named the unit twice. The plan now has one row saying the unit is masked and will be replaced,
  and the receipt lists your link as changed, with no backup because the link held nothing.
## Capture

- **DeepSeek dsh's requests made with Node's own `http` / `https` modules go through trocar too.** trocar's dsh plugin
  routed only requests made through `fetch` (undici), so a request on `node:https`, such as dsh's telemetry, went
  direct with capture on. Those connections now go to trocar like the rest while capture is on, kept-alive ones included,
  and a proxy Node itself would use for them is still used. A request that brings its own connection function, or a
  proxy library that replaces it, is not seen.
## Status

- **`trocar status <harness>` draws each route once.** When one process stood for several forms of a harness (OpenCode's
  background service, for one), its route was printed once per form, with trocar and again without. A route is now one
  line; the forms are named only when some form goes another way. The one-line route `trocar on --json` records for an
  agent (`adopted.<harness>.chain`) is shorter the same way.
## Install

- **On Linux, `trocar install` says once why it skipped an agent.** An agent install skips (Codex with no Codex home, for
  one) was named under `Skipped:` in the plan and again, in the same words, as a `Note:` in the receipt. The receipt now
  leaves it to the plan, and `--json`, the `--dry-run` one included, lists each skip with its reason under `skipped`.
## Install and status

- **An upgrade that replaces trocar's files no longer leaves the collector on the code from before.** Outside a git
  checkout, two trees of one version reported the same code id (the plain version), so `trocar install` saw nothing to
  replace and the collector kept running the earlier code, with nothing said. Outside a git checkout the code id now
  carries a hash of the code itself, so `trocar install` restarts the collector on the new code whenever the code
  differs. `trocar status` says when the collector runs other code than this trocar, `trocar doctor` lists it as a
  problem, and both give `trocar install` as the way out. Neither restarts the collector by itself.
## Fixes

- **A call the agent closed right after a complete reply is no longer failed.** Some agents close the connection as soon as the reply's last event arrives, before the server ends the exchange. Such calls showed as failed with no usage. They now read as the reply they got, with usage, cost and cache, and say "Agent closed the connection after the reply". A reply cut before its last event still says "Reply never finished" and stays failed. After the update, sessions are re-read once in the background.
- **A stream that ends in its own error event now shows as failed.** A reply with HTTP status 200 whose stream ends in an error event (Anthropic) or an error chunk (Chat Completions) used to show as a success. It now shows as failed, so you may see new failed marks on calls that already had these errors. The overview's count of failed calls still counts by HTTP status, so it does not include them.
## Fixes

- **A security review's `flagged` now says what the review said.** It used to be true unless the reply started with
  "no", so nearly every real review came out flagged. It's now read the way the agent's own parsers read it, by the
  reply's shape: a `<severity>` score is `true` above the boundary the review's prompt states (50), and an older
  `<block>yes` / `<block>no` reply says it directly, `<thinking>` left out either way. A reply that says neither gives `null`, and the lane's count takes only
  `true`. It describes that one reply: an agent that reviews in two stages passes a first-stage `yes` on to a second
  stage, so `true` alone doesn't mean the action was blocked. `flagged` can now be `null` in `trocar query lane`. Sessions already read are read again once, because the
  stored versions changed.
## Fixes

- **Codex's tool list now shows as tools.** Recent Codex versions send their tools inside the request's `input`, as an
  `additional_tools` item with namespaces of tools, and no top-level `tools`. The board showed that item as one unknown
  block in the conversation, and the tool count and message count were off. Each tool is now its own definition in the
  tools section (a namespace too, for its name and description), and the item isn't counted as a message. A list of any
  other shape stays visible as an unknown block. Sessions already read are read again once, because the stored
  projection's version changed.
## The board

- **Safety-review calls no longer carry a mark.** The folded background row and a review lane's own row drew a red
  mark on nearly every safety-review call. The verdict behind that mark is read wrongly today: almost any verdict
  that opens with a tag counts as flagged. The mark is gone until the verdict is read right. The verdict's own text
  is still in the call drawer, word for word.
