# 2026-10-25

## Replay desk

### Board

- **A live session never shows two renders mixed together.** When trocar rebuilds a live session's newest part from
  scratch (for example after its main lane changed), the desk now notices for certain and reads that part again
  whole. Before, if the rebuilt file happened to break between lines exactly where the desk had read up to, the
  desk kept steps from the old version next to the new one, with no error.
- **Coming back to a live session reads only what is new, also after the worker restarted.** The query worker leaves
  two minutes after its last piece of work, and a new one used to write the files of the part still growing afresh,
  so a desk that came back read those files again whole. The new worker now carries them on where the last one
  stopped, and the desk asks only for the bytes added since its last look.
- **Following a live session holds less memory, but takes more worker time per call.** The session's summary is
  now written only when a group of 512 calls is sealed, a new chapter starts or the reading state changes; the newest
  calls reach the desk through the growing part's files, and lane names and counts travel there too, so a settled
  group of 512 calls is never written again because a lane grew. Replaying the last 150 calls of a live session of
  about 30,000 records, the worker held at most 161–175 MB between calls, against 223–227 MB before, and spent about
  22 ms of CPU per call, against about 15 ms before. A new call is in the growing part's files within about 1 s
  (p95), as before.
- **"N newer calls are not shown yet" counts from the newest call the desk holds.** Before, it counted from the
  summary, which can lag a moment behind the calls already on screen.
- **A stopped read says why.** When the background reading of a session stops, because the session no longer fits
  in the worker's memory or because of an error, the line under the header says reading stopped and why; the details
  are under **Technical details**.

### Reading large sessions

- **A session ten times the size of a large live one is readable.** Where a session is cut is now decided only by the
  memory the worker measures while it reads, never by an estimate made beforehand. A generated 210k-call session,
  which used to answer every read with an error after about 80 s, is now read whole in the background in
  about 4 minutes and answers every read.
- **A damaged settled file no longer breaks a session for good.** If a file the worker keeps for a session turns out
  not to decode when it is first read, that read rebuilds the session's working files and answers, with a note that
  they were rebuilt. Before, that read and every later one failed.
