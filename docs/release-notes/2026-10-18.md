# 2026-10-18

## Nothing to do at upgrade

Your records move themselves. At its first start after this upgrade the daemon renames every
`~/.asight/collector/capture-<date>.ndjson` into `~/.asight/raw/` (a same-device rename, not one byte
changed) and from then on they are ordinary segments. Locations older than that
(`~/.asight/sessions/`, the v0 `~/.atrace`) are neither read nor touched; if you still want what is in
them, keep a copy yourself. Should the rename fail (a separate filesystem, a read-only home), the
files stay where they are, capture goes on, and `asight status` shows the failure.

## Where records live, and that they shrink by themselves

- Records are appended to a segment under `~/.asight/raw/`, closed at 128 MB or when the daemon
  stops. A record's id is `<segment>:<line>`.
- The daemon seals each closed segment by itself — a lossless re-encoding, typically a few percent of
  the original. The plain copy is deleted only after every record decodes back byte for byte. A
  segment that fails to seal keeps its plain copy, is tried again at the next daemon start, and shows
  in `asight status`. **There is no manual seal any more**: `asight raw seal|verify|compare|export|journal`
  are gone, and nothing replaces them — you no longer have to run anything to keep the logs small.
- `asight raw <segment>[:<from>[-<to>]]` prints records byte for byte, sealed or not.

## Reading: one core, no database

- `asight query <name>` is the one way to read the records (status, doctor, classes, segments,
  sessions, session, calls, block, pricing), and `asight serve` is a read-only board over
  `GET /api/<name>` serving the same documents.
- **DuckDB and the ETL step are gone.** `asight etl` and `asight shard` no longer exist, there is no
  `.duckdb` file to build or load, and `asight serve` no longer takes `--db` / `--source` /
  `--control`. If you had a `.duckdb` file or a `watermark` from an earlier version, it is dead weight
  and you can delete it. Nothing is lost: the raw segments were always the source of truth.

## What is kept: `asight classes` replaces retention

- `asight classes` both shows and edits the class table in `~/.asight/classes.json`: which host and
  path regexes make up a traffic class, and per class whether to keep the whole call (`full`) or one
  line per call (`log`).
  - `asight classes [<class>] [--json]` · `classes set <class> full|log` ·
    `classes add <class> <host-regex> [<path-regex>] [--harness <harness>]` · `classes rm <class> [<rule>]` ·
    `classes reset`
- **`asight keep` and `~/.asight/retention.json` are gone.** A `retention.json` left from an earlier
  version is ignored; set the levels you want with `asight classes set` once. As before, a change
  reaches the calls that start after it and never touches what is already stored.

## The CLI

- One command table now generates both the help and the dispatch, so `asight help` and what the
  binary accepts cannot drift apart. `asight help <command>` explains one command.
- Every command has a JSON document (`--json`), and a `--json` failure is one document too.
- Exit codes: 0 done · 1 not done, or a problem was found · 2 a usage error (nothing was touched) ·
  3 `status` / `doctor` could not judge · 70 the daemon crashed.
- Running one of these commands as root exits 2 with one line.
- `asight status` and `asight doctor` write nothing at all.
- `install`, `on`, `uninstall` and `daemon` speak English, conclusion first, inside 80 columns, and
  their plans name every file and key they will touch.
- `asight uninstall` now always prints its plan and asks first. Without a terminal and without `--yes` it changes nothing and exits 2
  (it used to uninstall straight away).
- `--json` keeps stderr empty: the plan is the `planned` key of the one document on stdout, and no run asks a question.
- `asight on --no-unit` is gone. `asight on --no-autostart` writes no login autostart entry at all and starts the collector this once
  — on Linux too, where it used to write the systemd unit and `systemctl --user start` it.
- `asight daemon` refuses before `install` has run: it writes nothing (not even the collector directory) and exits 1. Its readiness line
  never prints a null port.
- **Removed, with no replacement**: `asight etl`, `asight shard`, `asight keep`,
  `asight raw seal|verify|compare|export|journal`, `asight serve --db/--source/--control`, and the
  hidden one-word aliases (one feature, one name). If one of these is in a script of yours, drop the
  line: the work it did is either automatic now (sealing) or belongs to `asight classes` /
  `asight query`.

## `--json`: a refusal's code has one place

- **Breaking for `--json` readers.** A refusal no longer puts a top-level `code` on the receipt. Every refusal is
  `error: {code, message}` (附录 C.1), the one place a client looks: `asight uninstall` while capture is on is
  `error.code` `collectors-online`, and `asight on` before `install` is `error.code` `cert-not-installed`
  (macOS / Windows and Linux alike). If you read `doc.code`, read `doc.error.code`.
- `asight on --dry-run` that the real run would refuse still exits 0 with `blocked` and carries no `error`:
  nothing went wrong in a dry run.
