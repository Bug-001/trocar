# 2026-11-05

## The board

- **The Readable view draws the content.** The Readable view often showed a block's stored bytes in a reading font, or
  "Could not render" above a JSON wrapper. It now draws the parsed block: messages, system prompts and thinking as Markdown, a shell call as `$ command`, an edit as a diff,
  a file read as numbered code, JSON as a tree. A block still opens in Raw, its stored bytes; Readable is one click away, or `v` on the block. The copy button
  follows the view: Copy text in Readable copies the block's whole text, including what is not drawn yet, and Copy bytes
  in Raw copies the stored bytes. In the Readable view the section header says "Readable view"; "verbatim below"
  shows in Raw.
- **A reply reads as a message.** A reply showed stream events such as `event: content_block_start`. Each part now shows
  what the model said or called, and all parts are open, except reasoning with no plaintext. A reply built from a stream
  says so once at its end, and each part's Raw view shows the stream events it came from.
- **Real Markdown.** Headings, lists, tables, code fences and links now render, and bold next to Chinese text works.
  Absolute http, https and mailto links open in a new tab; any other link shows as its text. Images in Markdown are
  never loaded. Tag lines such as `<total_tokens>` show as a small label and a value.
- **Tool definitions read as text.** A definition shows its description, with its parameters folded below: name, type,
  whether it is required, allowed values and description. Tool arguments no longer sit in a narrow grid: a short value
  follows its key, a long one gets its own lines.
- **What you expand inside a block stays expanded** when you scroll away and when new data arrives.
- **A cell with nothing parsed says so.** Request parameters and the whole raw reply have Raw only, with no switch. A block
  that should have parsed and could not says so and shows its bytes.
- **A compaction counts once.** A compaction request still carries the whole history, and the history is replaced
  only on a later call, so one compaction could be counted twice: once for the request and once when the history
  dropped. It now counts once, in the session's totals and in the parts, and a compaction that failed and was tried
  again counts once too. A failed compaction no longer shows files as having left the context: the context was not
  replaced, so they stay where they were.
- **The compaction row gives the real message counts.** The row now takes the numbers before and after from the step
  where the history was actually replaced, not from the request that asked for it. A number that is not known still
  shows as a dash.
- **Background calls have names.** The kinds the board knows are named for what they do, such as Web search, Web page
  summary and Next-prompt suggestion. A background call it cannot name says **Unnamed background call**, not a guess.
- **Sub-agents are told apart by their task.** A sub-agent takes the description it was started with. Without one, it
  takes the first line of its task that few other sub-agents of the session share, so sub-agents started from the
  same boilerplate no longer look alike.
- **Files read through a shell command are found.** The path of a shell read is now worked out from what the command
  itself says: a variable set earlier in the command, a `cd` to an absolute directory, a `for` loop, `~`. A read written
  in any of those ways joins the other reads of the same file. A path only the running shell could know stays as the
  command wrote it, and Resources lists it under **Path known only at run time** with the reason, not among the files
  read.
- **More commands count as reads.** `sudo cat`, `sed -n 5p`, `grep`, `jq`, `awk` and names with no dot, such as
  `cat Makefile`, now count. A command that reads several files gives each file its own entry, and each of those
  entries leads to the block. `head -n -5` reads as all but the last 5 lines and `tail -n +5` as from line 5.
- **`trocar query` carries the new facts.** A lane header in `session` has `parts`, the lane's number of parts, and
  each entry of `chapters` in `session --head` has `prompts`, its number of prompts. The history a compaction or a
  failed call sends again no longer counts as prompts, or as anything new. The step where a compaction's history was
  replaced is a `compaction-landed` event with `from` and `to`; it is not a second compaction.

This update indexes each session again once, the first time you open it after updating, because the stored index changed shape.

- **Less waiting while a session is first read.** Taking in a piece of the session that had just arrived could hold
  up jumping to another lane, scrubbing and following. A piece is now taken in in short slices and the desk redraws
  afterwards, so no single step of that work stalls the page. Changing step on a session that is still growing is
  not yet as fast as on a finished one.
- **Moving around a session that is still being read keeps up with you most of the time.** Reading a growing session
  used to run in a long chain of small jobs that kept the next frame waiting, so a step change could take two or
  three times as long whenever a piece had just arrived. The desk now lets your key press or click reach the screen
  first and reads and redraws what arrived a moment later; the side panels and the call drawer follow once you stop.
  A typical step change takes about 20 ms. The slowest one in twenty still misses the 50 ms target on a busy
  machine, usually the step taken just as new data lands.
- **A click on a lane tick is no longer lost.** If new data redrew the lanes between pressing and releasing the mouse,
  the browser dropped the click and the step stayed where it was. The lanes now wait for you to let go, even when
  the redraw had already started as you pressed. The click also selects the call you pressed: a tick, a bar or the
  drawer's way back could pick its neighbour when older steps had arrived but were not drawn yet.
- **Opening a step lands where it should when its neighbour is still loading.** A step that arrived before the step
  it is compared with showed no new rows, or marked them against an older step, and the window stayed where it was.
  It now marks and lands when that step arrives, unless you have moved the window yourself. A step near the end of
  a long list also lands with its row at the top, where it used to stop some way short.
- **The Readable view says it is one.** With the desk's default cell view set to Readable, a context section's header
  still claimed its blocks were verbatim. It now says "Readable view", and goes back to its verbatim claim when you
  return to Raw.

## Query

- **`trocar query block` also gives the parsed block.** Each block gains an optional `view`: the parsed content and how to
  draw it. For a reply that is the assembled text or tool call, so an agent can read it without parsing a stream. `bytes`
  and `fidelity` are unchanged, and `view` is parsed, not verbatim. A view that cannot be read leaves `bytes` in place and
  adds a note with the code `view-unreadable` to `errors`; `ok` does not change.
## Capture

- **A slow process lookup no longer loses a connection.** On macOS under heavy load, an agent connection went uncaptured
  when reading its process took more than 2 s. Slow is no longer a failure: each question asked about a connection now
  only has a limit against hanging, and an answer that arrives late still counts.
- **One connection waits at most 20 s.** If trocar still cannot tell whose a connection is after 20 s, the connection is
  passed on as usual, not decrypted, and its row says why (`door-deadline`). The question keeps running, so the next
  connection from that program is judged normally.
- **On macOS the collector runs at foreground priority.** Agent connections wait on it, and at the background priority
  it had it ran much slower under load. Sealing and queries stay at low priority. `trocar install`, or a `trocar update`
  that brings new code, writes this into the login entry.
- **Replacing the collector no longer stops capture.** While the old collector finishes its open connections, a new
  connection from an agent that is on is captured as usual; it used to be passed on unread. This covers `trocar install`
  from another copy and a `trocar update` that only has the collector to replace. An update that brings new code still
  switches those agents off until it is done, and connections the old collector holds at the end are still cut. A
  response on a new connection gets the same 30 s as one that was already on its way. On Linux, `install` no longer
  leaves capture off after it replaced the collector. The old collector does the handing over, so the first replacement
  after this release still goes the old way: on Linux run `trocar on` after it. In the second or so between the two
  collectors, a new connection is refused on macOS and Windows, and on Linux it goes straight out and is not captured.
- **A change to the login entry takes effect with `trocar update`.** The entry is now written before the collector is
  replaced, so the new collector starts from it, not from the old entry until the next login.

## Records

- **Connection rows say where the time went.** Rows of connections through a door gain `facts_ms` (time spent asking
  about the process) and `held_ms` (time from accepting the connection to handing it on, machine sleep included). A row
  that could not read its process gains `unread`, with what the reader reported.
- **Three new state records, none of them a failure.** `loop-late`: the collector itself ran late by a second or more.
  `client-left-held`: a program gave up on a connection while trocar was still judging it. `client-left-queued`: a
  program dropped a connection before trocar picked it up.
