# 2026-11-02

## Installing

- **trocar installs with one line, with no npm and no Node.** On macOS and Linux:
  `curl -fsSL https://github.com/Bug-001/trocar/releases/latest/download/install.sh | sh` (or the same with
  `wget -qO-`). On Windows: `powershell -NoProfile -ExecutionPolicy Bypass -c "irm https://github.com/Bug-001/trocar/releases/latest/download/install.ps1 | iex"`.
  - The script downloads the same package as npm and an official Node build of its own, and checks both.
    The package is checked against the integrity the npm registry records; Node against the hashes the package pins.
  - It puts both in `~/.trocar/app`, needs no root, and then runs `trocar install`. That command prints its plan and
    asks before it changes anything.
  - In China, the scripts are also at `https://cdn.jsdelivr.net/npm/trocar-cli/install/install.sh` (or
    `install.ps1`). Each download tries npm and nodejs.org first and moves to npmmirror when that source fails
    or is too slow.
  - npm stays the way in for developers: `npm i -g trocar-cli`, then `trocar install`.
- **A script install puts `trocar` on your PATH.** `trocar install` adds `~/.trocar/bin` at the end of your PATH.
  On macOS and Linux this is one marked line in your shell's start file, which is backed up first. On Windows it
  is one element of your user `Path`. `trocar uninstall` takes out exactly that line or element. The rest of the
  file or value stays as you have it.
- **`trocar update` updates a script install.** It downloads and checks the new version before any agent goes off.
  Then it switches to the new version and finishes the way an npm update does. A failed download changes nothing
  and exits 1 with `error.code` `installer-failed`. Running the install line again does the same update.
  The collector starts at login through the `~/.trocar/bin/trocar` launcher, so after the switch it comes back
  on the new version. `update` prints its plan once.
- **`trocar uninstall` removes a script install's own code last.** That is `~/.trocar/app`, the `trocar` launcher
  and the PATH item, and it happens only after everything else was undone. On Windows the folder goes as soon as
  the command exits. On Linux, while the capability helper is still installed, the code stays. `uninstall` then
  prints the `sudo` line that removes the helper; run `trocar uninstall` again after it.
- **`~/.trocar/bin/trocar-off` runs on a machine with no `node` on PATH.** It starts the Node of the install that
  wrote it, and falls back to `node` when that one is gone.
- **Plans fold every line at 80 columns.** In the `install`, `on` and `update` plans, the lines under a label were
  folded well short of 80 columns. They now fill the line like the first one.
- **The Linux `sudo ... setup-helper` line names full paths.** `trocar install` and `trocar on` print it when the
  helper is missing. It names this copy's Node and code, because root's PATH usually has neither.
- **On Linux, `trocar install` finishes before the capability helper is installed.** A script install never has the
  helper yet when it runs `install`. The collector used to exit at once without it, so `install` exited 1. Now the
  collector runs and captures nothing until the helper is in, and `trocar status` and the board say so. The first
  `trocar on` after the `sudo` line starts the helper.
- **`trocar status --json` says which code the collector runs**: `daemon.code`, as the collector itself answers it.
- **The `uninstall` receipt lists every place it keeps**: `~/.trocar/collector/flows/` (and `audit/`, `replays/`)
  besides the records and their index. `--purge-data` deletes exactly those. The receipt names each removed thing
  once, in plain words; on Linux it no longer says a root certificate left your trust settings, because there it
  was never in them.

## The board

- **A session that was never read before finishes loading while you watch it.** Opening such a session showed
  "Reading this session for the first time · 0 %" and stayed there, unless new calls came in or it was the newest
  session. Opening it now starts the read, and the percentage climbs until the session is fully read.
- **The traffic list shows the newest calls first.** Calls were listed oldest first, and calls whose times and
  capture order disagreed were out of order. They are now sorted by time, newest first.
- **Settings › Storage loads faster once the board has read your capture.** Its counts now come from the same in-memory
  index the other pages use, so the index is no longer read again segment by segment. The first open after the index is
  rebuilt (for example right after an update) is not faster yet: it can take more than a minute, and the overview may say
  that storage could not be read until it finishes.
- **A link to a step no longer shows "Follow latest" on while that step loads.** A replay link that names a step
  (`step=` in the address) showed "Follow latest" pressed until the session's calls arrived, then the chip turned
  itself off and the desk stayed on the named step. "Follow latest" is now off from the moment such a link opens,
  and going back to the session's address without a step turns it on again, even before the named step arrived.
- **The request view and the "Logged only" label show the class a call was recorded under**, also for classes you
  added. They used to work out a class of their own for any class that was not built in. A call recorded before
  classes existed now says it has no recorded class, instead of showing a guessed one.
- **One rule decides which calls failed.** A model call over HTTP that got no status (the connection ended before
  an answer) now counts as failed on the board and in `trocar query session`, as it already did in the overview's
  failed count. A Codex call over a WebSocket has no HTTP status, so the overview no longer counts it as failed; the
  session view still marks one whose reply says it failed. The index and the session views are rebuilt once after
  the update.
  A call answered with a status below 400 other than 200 (201, 204, a redirect) is no longer marked failed on the
  replay rail or in the stats.
- **The stats card computes less token usage in one go.** Before the per-segment usage files exist, `overview`
  now works out usage for at most 10 MiB of newest calls (was 16 MiB): each call now goes through the same
  extraction the session view uses, which costs more per byte, and the smaller budget keeps the first open as fast
  as before. `coverage` still says how far it got; the background worker fills in the rest.
- **On the capture page and the capture log, selecting text never folds a row, and Technical details stay open across
  refreshes.** A row opens and closes from its head button, with a click, Enter or Space; a click or a drag inside an
  open row leaves it open. While a row is open the rows keep their order, so the row you are reading does not move
  when a refresh brings new counts.
- **The overview keeps what you opened while it refreshes.** Technical details you opened stay open, the text you
  selected stays selected and the focused control keeps focus when the overview reads new numbers. Switching the stats
  window dims the old numbers until the new window answers, instead of swapping in a blank card. Clicking a problem
  item opens the capture page with that agent's row already expanded. The rest of the page stays usable while the ⓘ
  beside the failure list is open.

## Capture

- **Plain `http://` requests sent through trocar's proxy work again, and an agent's own are captured.** A program
  an agent starts inherits the agent's proxy settings, for example a network login helper run from inside an
  agent, and its plain `http://` requests used to be refused. trocar now passes them on, taking out only what was meant
  for trocar itself (its proxy password, which is never recorded), and records an agent's own like the rest of its
  traffic.

## Installing and updating

- **The board is now built with React from `web/`, and the daemon serves the built copy in `src/web/board/`.** It looks
  and works the same as before. The built board is part of the repository and of the npm package, so every way of
  installing trocar gets the same board and nothing is built on your machine.
- **A git install and `trocar update` no longer fetch the development tools.** The install lines in the README use
  `npm install --omit=dev`, and `trocar update` does the same; trocar still has no runtime dependencies.

## Status

- **The board and `trocar status` agree on which forms are installed.** A form found only through a command (such as
  the `codex` or `dsh` command line) used to be "not routed" on the board, because the daemon looked for the command on
  the login service's PATH. Each `install`, `on`, `off` or `uninstall` you run now records your PATH, and every part of
  trocar looks commands up on it. `uninstall` removes that record with the rest of trocar's state.
- **Routes show only the API host trocar read.** A direct hop used to name the first host trocar knows for the
  harness, with `:443`, as if you had configured it. It now names the host your agent's own config sets. When the
  config sets none, it says "the API host it uses".
- **An agent whose only provider runs on this machine is "not captured".** When every API address in the agent's own
  config is on this machine, such as a local relay, its model calls never pass through trocar. Before, status said
  "captured" for it. Status and the board now say why, and `doctor` names the local address and says no action is
  needed.
- **No carrier on record is reported as a certificate problem.** It used to show as "not routed".
- **Forms and Routes say what they mean.** The certificate column says how the certificate reaches the agent ("reads
  your user trust store"). The proxy column shows trocar's port. `(was: …)` appears only when a value was recorded.
  The text shows trocar once per route, and the reasons a hop could not be read appear as words. A route row names
  the process the door saw on that form, or says "new processes". Forms that are outside the supported scope are no
  longer listed.
- **Claude Desktop's route without trocar goes through the system proxy**, as the app does.
