# Release notes — 2026-10-12

## macOS and Windows: the collector's engine is the local proxy (D47)

**What changed.** On both platforms the collector's engine opens its own loopback door per agent group, and the
agent's proxy entry and trust entry point straight at it. When a connection is accepted, the engine makes one targeted
lookup on the connection's 4-tuple to find the owning process, then decides which form that process belongs to. The
mihomo kernel, `asight-forwarder` and the process-scan table are gone: `asight on` has no download step (the kernel
download of 2026-10-11 goes with them) and the receipt has no kernel row. `asight uninstall --purge-data` still
removes `kernel/`, `kernel-archive/` and `forwarder/` directories that an older install left behind. The kernel family
of failure codes (`forwarder-download-failed`, `forwarder-start-failed`, `forwarder-restart`, `fallback-active`, …) is
no longer produced; `forwarder-down` stays and now means the engine's door is not running.

**Why.** The engine is stable, so the collector itself is the proxy server and the
process-scan machinery is dropped.

**Impact.** Linux is unchanged (eBPF). Your own VPN / proxy software is still only read, never written, and it still
decides asight's upstream. If the engine dies, launchd (macOS) or the supervising parent process (Windows) restarts the
daemon; agents whose connection was refused in the gap reach the restarted door on their own retry.

## `asight status` is a one-screen digest; `--failures` shows the full wall (D46)

**What changed.** `asight status` without a name prints at most 10 lines: the verdict first (`在采 N/7`), every
topology that is entirely unknown folded into one line, and for health only the failure count, the kinds and the latest
one. The full failure wall moved to `asight status --failures`; naming a harness still shows its per-process detail.
All output is Chinese; colour appears only on a terminal, respects `NO_COLOR`, and `--json` is never coloured. The
receipt of `on` speaks per platform (launchd on macOS, no systemd) and explains a harness only when it is newly wired.
The daemon's stdout / stderr land in `~/.asight/collector/logs/` (the launchd plist and the systemd unit each carry
the output paths; `uninstall` removes the files by manifest).

## `asight on` no longer reports a false failure on macOS and Windows

**What changed.** The CLI finds the daemon through one resolver: macOS and Windows read `control.json` and send its
token, Linux keeps the XDG socket. Before, the first `asight on` on those two platforms reported "no daemon answers on
null" and exited 1 while the daemon was healthy, and requests carrying a token were answered 401. `uninstall` no longer
runs `systemctl` on macOS / Windows, `on`'s receipt no longer carries systemd linger wording there, and a failed run's
receipt marks only the real problems as problems (success lines used to be printed under the problem label).

## macOS: `off` really stops the daemon; Homebrew- and PATH-launched agents are captured

**What changed.** `launchctl bootout` now uses the `gui/<uid>/<label>` slash form. The two-argument form answers
an I/O error for every job on macOS 26, `KeepAlive` pulled the drained daemon back, and `off` still reported it
stopped. The form path table gains Homebrew's npm-global layout (`/opt/homebrew/bin/{claude,codex}`) and
`/usr/local/bin/*`; before, those installs all read `form-path-unknown` and were never decrypted. The form is matched
on the real executable path that `lsof` reports, so launching `claude` straight from `PATH` (no path in argv) is
recognised too.

## Windows: the daemon and capture chain are connected; the scheduled task is honest

**What changed.** On Windows, `asight on` / `status` used to crash at once, `asight daemon --supervise` crash-looped,
and even a running daemon recognised no agent process, so capture stayed empty; that chain now works end to end. When
the scheduled task that `on` registers answers `/Run` with success but starts nothing (LastTaskResult 267011, no
interactive session), asight reads the result back, starts the daemon directly and says so in the receipt. `off` and
`uninstall` really `/Change /DISABLE` (or `/Delete`) the task instead of only claiming it is disabled. Failure hints use
`schtasks /Query` wording instead of telling you to run `systemctl`.

## Claude Desktop (macOS): the `desktop-launcher` opt-in

**What changed.** `asight on claude-code --opt-in claude-code.desktop` writes a launcher
(`~/.asight/collector/bin/claude-desktop-asight`) that execs the real Claude Desktop with Chromium's `--proxy-server`
pointing at the engine's credential-less loopback door (with a loopback bypass list). Naming the form applies two
items together: the collector certificate in the login keychain (the system's own confirmation dialog is yours to
click) and the launcher. Only an instance started through the launcher is captured; environment variables have no effect
on Desktop (measured), so the receipt and `doctor` say that Desktop must be restarted. `off` removes the launcher, and
it now also cleans up a half-failed state where the dialog was declined midway, the certificate was imported and no
trust was set.

## `uninstall --purge-data` cleans more

**What changed.** Besides the data directory it removes `control.json` and `ingress.json`, so the next `on` is a true
first install.
