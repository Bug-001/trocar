# 2026-10-31

## The board

- **Replies and tool definitions with no source location show their text.** When a reply comes back as plain JSON
  rather than streamed, the capture holds no byte span for each part. Those rows said "This block has no body and
  no source location", although the reply had been parsed. They now show the text the server sends with them.
  A tool definition in the same situation shows its description and schema, where before it said they had not
  been kept. A tool that has neither on the wire, such as a server tool like web search, no longer claims that
  its schema was dropped.
- **The reply looks like the blocks above it.** The context window no longer ends with a separate Reply header.
  The reply's thinking, text and tool calls are rows of the same form as the request's blocks: role, kind,
  preview, fidelity mark and characters. Each row carries its own mark. A row read from the streamed reply's bytes
  shows none; any other row shows "◐ parsed reply". The stop reason sits on the last row. A reply with no part says
  whether the reply was empty or could not be read.
- **Request rows show the fidelity the capture recorded.** Every request row used to say "◐ fidelity unknown".
  - A block proven to be the bytes that went over the wire now shows no mark. Tool definitions are included.
  - Every other block shows the mark for what is known about it.
  - Tool definitions that an older capture kept only as metadata say so.
  - A pinned tool capability lists each tool's name and size, and says whether all of its definitions are proven.
- **Turning follow latest on from an earlier step lands on the newest reply.** Before, the window stopped short
  of it. Step changes are no slower.
- **A section stops saying "verbatim below" once a block in it turns out not to be.** Opening a block whose bytes come
  back re-serialized, or cannot be read, marked that block and took back the section's "verbatim below", but the next
  redraw of the step said it again. It now stays taken back while the block is open.
- **A capture from the v0 prototype says its content cannot be traced back to the raw bytes.** Such a record kept the
  request only as a parsed object. Its blocks were located in a re-serialized copy and shown as verbatim until each was
  opened; now each of its steps carries **This step's content cannot be traced back to the raw bytes (it was parsed
  again)** and its blocks open on the text the record holds. Stored context projections are rebuilt from the capture
  once after this update.
- Under that line a screen reader hears **not addressable** on each block again; the page says it once, on the line.
- **When a request, its messages or its reply is incomplete for a reason the board has no word for**, the call's fidelity line
  still says so, and its technical details now name the reason instead of "unknown flag". The line's **messages:** fact gets
  its missing space.
- The "≈" before the tool definitions' size, meaning the size is estimated from metadata, now shows only when a definition
  was kept as metadata, not when an opened one could not be read back.
- **A long context window no longer stops the page.** Rows and prompt cards off screen are laid out at a preset
  height until they come on screen, and the preset was shorter than the real thing: a closed row by 2 px (more when
  its head wrapped), a folded prompt card by 6 px. In an open card of hundreds of blocks, drawing the rows near the
  visible part and putting back the ones that had left it moved the rows around them, and with some mixes of rows
  the window kept drawing and putting back the same rows without end: the page stopped answering. A row's head and a
  card's head now have one set height, so a closed row or a folded card is the same size on screen and off it, and
  drawing rows in place of the space they held moves nothing.
- **At 600 px and narrower a row's head is two lines.** The role, the tag and the marks are on the first; the
  preview and the size are on the second. Nothing in a head wraps any more: short of room, the preview and then the
  tag are cut short with an ellipsis (hover it for the whole word). The role and the size never shrink; the marks
  shrink only on a two-line head that has no room even for them.
- **A large live session no longer fails to open with an error 500.** Now and then, opening a session that was
  still being written answered "Unexpected non-whitespace character after JSON". A stored line was read from the
  place an older index named, after that file had been cut back and written again. A line read that way is now
  checked to be a whole line of the file. If it is not, the session's stored state is reopened and read once more
  in the same request, so the answer is the same as a fresh read. The daemon log records the first such read for
  each file.
- **A session the worker has open keeps its stored state, and a stored line is never answered for another one.** The
  cleanup that keeps stored state under 512 MiB could delete a session the worker had opened in the background (the
  agent was still writing it, but nobody had asked for it yet), or every session when the capture folder could not be
  listed. The worker then wrote and read that session's state at the wrong places. Now an open session is never deleted;
  when the capture folder cannot be listed nothing is deleted and the daemon log says why. A stored line is also checked
  to be the line asked for, so another call's or block's line is never answered in its place; the session is read once
  more instead.

## Command line

- **An older Node gets one line saying which Node trocar needs.** trocar needs Node 22 or newer. On an older Node,
  every command used to stop with a SyntaxError stack while loading its own code (on Node 20.11: `node:util` has no
  `styleText`). It now prints `trocar needs Node 22 or newer; this is Node 20.11.0.`, exits 2 and touches nothing.

## Linux

- **`sudo trocar setup-helper` says why `setcap` could not run.** When `setcap` was not installed, or not on root's
  PATH, setup-helper stopped with `setcap failed:` and nothing after it. It now says
  `setcap could not run (spawnSync setcap ENOENT); is it installed and on root's PATH?`. A `setcap` that runs and
  refuses still reports its own message.
