# 2026-10-31

## The board

- **Replies and tool definitions with no source location show their text.** When a reply comes back as plain JSON
  rather than streamed, the capture holds no byte span for each part. Those rows said "This block has no body and
  no source location", although the reply had been parsed. They now show the text the server sends with them.
  A tool definition in the same situation shows its description and schema, where before it said they had not
  been kept. A tool that has neither on the wire, such as a server tool like web search, no longer claims that
  its schema was dropped.
- **The reply looks like the blocks above it.** The context window no longer ends with a separate Reply header.
  The reply's thinking, text and tool calls are rows of the same form as the request's blocks: role, kind,
  preview, fidelity mark and characters. Each row carries its own mark. A row read from the streamed reply's bytes
  shows none; any other row shows "◐ parsed reply". The stop reason sits on the last row. A reply with no part says
  whether the reply was empty or could not be read.
- **Request rows show the fidelity the capture recorded.** Every request row used to say "◐ fidelity unknown".
  - A block proven to be the bytes that went over the wire now shows no mark. Tool definitions are included.
  - Every other block shows the mark for what is known about it.
  - Tool definitions that an older capture kept only as metadata say so.
  - A pinned tool capability lists each tool's name and size, and says whether all of its definitions are proven.
- **Turning follow latest on from an earlier step lands on the newest reply.** Before, the window stopped short
  of it. Step changes are no slower.
