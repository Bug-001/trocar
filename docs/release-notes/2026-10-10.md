# Release notes — 2026-10-10

## Windows runs the per-process collector: `asight on` flips to it

**What changed.** On Windows, `asight on` no longer answers 「本平台未实现」 (exit 1): it runs the new
per-user process collector (RFC 4.8), the same generation Linux has. A Windows user running `asight on`
now sees the plan first — the bundled kernel it will run (`asight-forwarder.exe`, from the
`asight-kernel-win32-x64` package; loopback only, no TUN, never the system proxy, nothing written into
your VPN), one row per agent group with the upstream the kernel will dial for it (a system proxy or a
direct connection named as such), Codex's WebSocket, Smart App Control, and the autostart task
(`\asight\collector`, this user, at logon) — and, after the usual confirmation, the proxy and trust
entries written in the agents' own config files with the prior values recorded. The forms that reach
further are opt-in, each named with what it touches: `asight on <harness> --opt-in <form>` (Claude
Desktop's user-level certificate store, the Kimi / OpenCode PATH shims, the Kimi VS Code extension
capture, the OpenCode and Z-Code desktop launchers and app settings; the machine-level ones run in the
administrator step asight shows — asight never draws a password field of its own). `asight off` and
`asight uninstall` run the new undo — supervisor, daemon and kernel stopped, every entry and opt-in item
taken out — and also take out whatever the old capture left on the machine. `asight status` is the new
per-agent table (a harness name other than `claude-code` is no longer a usage error), `asight daemon`
passes the gate, and `asight help`'s first screen says Windows drives the per-process collector.

**Why.** The Windows collector is built: the pinned kernel, the scheduled-task autostart with its
supervisor parent and Run-key fallback, the control pipe, and the `off` seams that work without the
daemon or the source tree (plan Task 9(b); RFC 4.8). The one question every command asks —
`hasNewCollector(platform)` — now answers yes for `win32`, so every gated command dispatches to the new
collector instead of the old capture.

**Impact.** Windows only; macOS is unchanged (`on` / `off` still drive the old capture there), and Linux
is unchanged. The old capture's commands (`capture`, `mitm`, `desktop`, `monitor`, `shard`) keep working
on every platform for the transition (1.6 §4): `asight off` also undoes what the old capture left on the
machine. The web switch's "off" on Windows is no longer `asight off` — like on Linux, it only takes the
old CC-CLI steer out and the switch's status says so (「只管旧 CC-CLI steer,不等于 `asight off`」), until
the board's per-user isolation lands (RFC 4.4). Exit codes and command shapes are unchanged: the
not-implemented refusal (exit 1) remains for platforms that have neither collector (macOS's `daemon`
still says so, now naming Linux and Windows as the ones that have it).
